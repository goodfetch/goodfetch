# Conformance suites

The conformance suites, with `clients/` and `mcp/` (ADRs 0069 and 0070). Area 2 and the areas that own each contract fill this folder.

Each suite declares its capabilities and, for each, its cases with the Features each covers (ADR 0072). `goodfetch-conformance` (`crates/goodfetch-conformance`) runs a suite against a target and a running Proving ground, or turns the case log another runner wrote (ADR 0069), into one Result document of kind `conformance`, whose types, outcome constructor and reader are `goodfetch-protocol`'s `result_document` module. Its executable's `goodfetch-conformance read <file>` loads one document through that reader and exits 0 when it accepts it, 1 otherwise, so the TypeScript and Python helpers' tests check what they write; `goodfetch-conformance write <case list> <header> <case log> <document>` turns a case log and a case list such as `clients/cases.toml`, with the document's header as JSON, into a `conformance` document through the writer, so a runner that is not written in Rust gets its document the same way. A capability is `proved` only when every case it declares ran and passed: one the suite did not reach is `unproved`, never `proved` (ADR 0033).

Gate mode (`run_protocol_suite_in_gate_mode`, for the Clean-up rules' daily channel, ADR 0047) runs a protocol suite twice, interleaved: each case runs on the target as given, with Filter-list blocking on, then at once on a second engine started on a Goodfetch home of the target's own, configured as its home was before the run, with every Run's Filter lists off and no extra one, before the next case runs. Each case entry names its `blocking`, `on` or `off`, and the header says `gate`; outside gate mode, entries are judged as any others. A case that passes with blocking on is `passed`. One that fails with blocking on is `failed` when it passes with blocking off, and `inconclusive` when it fails both ways, a vendor's own scoring change, or has no entry with blocking off; `inconclusive` leaves its capability `unproved`. Both runs of a case thus meet the outside world as it is at that moment. An entry also names what it could not reach, such as a vendor's site, in `unreachable` (ADR 0064): such an entry never passes, and a case whose entry with blocking on could not reach everything, or whose entry with blocking off did not pass, is `inconclusive`, never `failed`; outside gate mode, it is `inconclusive` unless another entry failed. The harness names nothing unreachable yet: telling a vendor's outage apart comes with the online Proving ground's vendor pages. Each run against the online Proving ground is a Live check: `xtask results live-check` writes each document as one JUnit test case, `conformance <suite> <target>[ gate]`, failed, skipped (inconclusive) or passed, for the results store's `live` tier. A case that checks blocking itself always fails with blocking off, so its failure with blocking on is `inconclusive`, never `failed`: gate mode suits cases of pages blocking may break, not those of blocking itself. A document blocks (`ConformanceDocument::blocks`) when a capability failed, except an `online` document outside gate mode, which only reports (ADR 0043).

- `clients/cases.toml` (written by area 11): the Client conformance case list. Each case lists the `surfaces` it applies to and, when its capability exists in some modes only, its `modes`; `xtask clients check` fails when a surface it lists has no test carrying it in each of that surface's modes, or a test carries an unknown case (TESTING.md, [SDKs](../docs/testing/sdk-and-cli-tests.md#sdks)).
- `protocol/cases.toml`: the JSON-RPC protocol suite (#172), which runs against any target that speaks Goodfetch's protocol: either Product's Attached engine (`<executable> attached-engine`) or Daemon (`<executable> daemon launched`, found through the runtime file it prints), its executable taken by path, and so the Browser host and Goodfetch Cloud's engine, which is a published Product executable run unmodified (ADR 0096). Its `product` is the smallest Product that carries its contract: the harness announces it in `hello` and refuses an engine of another Product (ADRs 0094 and 0095). Every case runs in order over one Connection, and each case's checks and exchanged messages land in the document; a case after the target closed the Connection is not reached. It runs in `goodfetch-conformance`'s `tests/it` against the Scripted engine (a conforming script and one that drops cancellation mid-suite) and against Collie's and Foxhound's executables of the commit, in both modes.
- `delivery/cases.toml`: the delivery suite (#217), a protocol suite of `product = "foxhound"` that the same harness runs the same way (`ProtocolSuite::delivery`): a crawl whose handler is the harness, with a 1 ms `timeout.handler` so each lease lasts its 10 s margin, checks at-least-once delivery (a lease that ends unanswered is cancelled with `$/cancel` and its work item asked for again under a later lease epoch), exactly-once commits (an answer in time is asked for once, never cancelled, and the Run finishes complete) and a late commit refused (an answer after the cancel changes nothing); and a `hello` naming a protocol major the engine cannot speak, on a Connection of its own, refused with `protocol_version_unsupported` before any other message, the Connection then closed (ADR 0066). Once the Run finished, `run.records` reads back what committed: each Record once, numbered in commit order, and never a late answer's. It runs in `goodfetch-conformance`'s `tests/it` against Foxhound's executable as an Attached engine and as a Daemon.
- `fetch/cases.toml`: the fetch suite (#759), a protocol suite of `product = "foxhound"` that the same harness runs the same way (`ProtocolSuite::fetch`): a crawl of the `content-coding` family's gzip page under `fetch.tier: http`, whose handler is the harness, is asked for with `tier: "http"` and the ID of a page served from the fetched document; `page.formats` on that page reads the page's decoded text, the Proving ground saw one request for it (beside the robots.txt the crawl reads, ADR 0086), and the page answers `closed` once its attempt ended. Its `fetch.edge.http` cases (#763, ADR 0118) crawl `fetch-edge.test` over plain HTTP/1.1 under `fetch.tier: http`: each cut body ends `failed` with `response_truncated` after its one retry, which waits out no backoff of its domain, and no handler is asked for it; a body its connection's close delimits reaches the handler whole; and `/reuse/close`, enqueued after a page left its connection idle, is sent once more on a new connection, its handler asked once for its first attempt under `crawl.retry.max: 0` and with no 3 s domain delay waited. Its redirect-chain cases (#762) check that a loop under `fetch.redirect.max: 5` ends `failed` with `too_many_redirects`, not retried, at a cost of 6 requests while a chain of 5 reaches its handler; that a `POST` answered 302 reaches its target as a `GET` with no body and one answered 308 as a `POST` with it; that a 300, a redirect with no `Location` and one to `ftp:`, `file:`, `gopher:` or `data:` end `failed` with `response_not_ok` while a 301 `crawl.handle_statuses` lists reaches the handler; that a hop robots.txt disallows ends `skipped` with `robots_txt`, unsent, and a hop waits out the domain's delay; that a redirect to a page admitted for another request ends `skipped` with `duplicate`, and one off the scope with `out_of_scope`; that, under `all` narrowed by `crawl.scope.exclude` and with `bücher.test` blocked, seeds added to the live crawl after a `run.outcomes` call with `kinds: ["skipped", "blocked"]` and `after: "now"` reach it as they end, a redirect leaving the scope `skipped` with `out_of_scope` and one to `bücher.test` in punycode or to the loopback address, dotted or in hex, with `domain_policy`, none of their targets requested, while an in-scope chain reaches its handler, and the Run report counts each reason; that a 302's `Retry-After` of 2 s delays its hop and one of an hour past the bound ends `failed` with `response_unavailable` carrying the 302; that a 503 whose `Retry-After` of 2 s passes a `politeness.retry_after.max` of 1 s ends `failed` with `response_unavailable`, not retried, as does a request admitted to its domain meanwhile, unsent, and that once the site is back `run.retry_failed` re-admits both in the same Run, answering 2, each handed to its handler under its ID and its Record committed once in the same Dataset; and that refresh stubs reach their target within `fetch.refresh.max_delay` at its default, at `null` and at `0`, and never with no URL, to themselves or inside `<noscript>`. It runs in `goodfetch-conformance`'s `tests/it` against Foxhound's executable as an Attached engine.
- `reset/cases.toml`: ADR 0001's permanent reset gate (#224), a protocol suite of `product = "collie"` that the same harness runs the same way (`ProtocolSuite::reset`). Each case has the Proving ground plant Secret canaries (`POST /canaries`, ADR 0067) and puts them in a Run: a token in its Key-value store and a password as its status line, or the Session cookie the `canaries/3` login sets in its browser. Once the Run ended, `run.discard` discards it, and the harness searches every regular file of the target's Goodfetch home, raw and in Goodfetch's encodings (the forms of test support's canary search, checked against its shared fixture), finding the values there before the discard and nowhere after; a later Run under the same Run ID then finds an empty Key-value store and is sent no cookie (the account page sends it to log in). The search follows no symbolic link and reads nothing outside the home, so a Profile directory used in place and a Borrowed browser are never scanned (ADR 0056). It runs in `goodfetch-conformance`'s `tests/it` against Collie's executable as an Attached engine and a Daemon in the per-run layout, and as a Daemon in the per-install layout (ADR 0002); the cookie case launches the pinned browser, so the test joins the Linux arm64 and musl exclusions in `.config/nextest.toml`.
- `run-start/cases.toml`: ADR 0102's start table (#1544), a protocol suite of `product = "collie"` that the same harness runs the same way (`ProtocolSuite::run_start`). Each case starts a Run under an ID of its own, brings it to the row it checks and starts it again under that ID: a new Run ID begins a Run (`new`), a stopped Run's ID resumes it (`resumed`), as does the ID of a Run whose engine, a second Attached engine on the same Goodfetch home, the harness killed while it ran, a finished Run's ID answers it as it ended (`ended`), a live Run's ID fails with `run_in_use`, and the ID of a Run the Run index lists whose run file was removed from the target's Goodfetch home fails with `run_state_unavailable`, twice, no Run having begun. It runs in `goodfetch-conformance`'s `tests/it` against Collie's executable as an Attached engine, with no browser.
- `run-start-crawl/cases.toml`: the start table's crawl rows (#1544), a protocol suite of `product = "foxhound"` that the same harness runs the same way (`ProtocolSuite::run_start_crawl`), its crawls fetching the Proving ground's plain host on the `http` tier and the harness answering each handler request with no Record. A crawl start under a finished crawl's ID answers it as it ended (`ended`), no handler asked before the answer or after it; one with other seeds fails with `run_conflict` listing `seeds`, and a Collie Run's start under a crawl's ID, which has no seeds, with `run_conflict` listing `product`, `kind` and `seeds`; and once a crawl's `run` Limit of one request, set with `usage.set`, stopped it, a start under its ID fails with `limit_reached` naming the Limit's scope, the scope's ID and its Usage kind, twice, the crawl not resumed. It runs in `goodfetch-conformance`'s `tests/it` against Foxhound's executable as an Attached engine. `run_conflict` naming `caller` has no case: the caller is the operating system user on every target the harness has, until a Daemon with accounts gives callers that differ.
- `two-copies/cases.toml`: ADR 0003's fencing of a Run's two copies (#2348), a protocol suite of `product = "foxhound"` that the same harness runs the same way (`ProtocolSuite::two_copies`). A crawl of the Proving ground's plain host on the `http` tier checkpoints and exports its Dataset; a second Attached engine on a Goodfetch home of its own, standing in for another machine, resumes that Checkpoint at the next run epoch, checkpoints and exports; then the first copy, which nothing stopped, checkpoints and exports again. Each Checkpoint and Export goes to the harness's stand-in destination, which compares and sets the run epoch its answer carries: the first copy's land until the second copy's do, then are refused. It runs in `goodfetch-conformance`'s `tests/it` against Foxhound's executable as an Attached engine; a Daemon's further Connections reach the same engine, so it has no second copy.
- `sample-store/cases.toml`: the suite of Collie's sample Plugin kind, `sample_store` (#171), which the harness's process Plugin target runs (`PluginSuite::sample_store`, `run_plugin_suite`). The harness starts the Plugin from its executable and arguments with the plugin protocol's cookie in its environment, sends `hello` announcing the suite's `product`, and refuses a Plugin that declares no implementation of the suite's `kind`; it then runs, over that one Connection, the cases of each capability the Plugin declares, one capability at a time, so a capability the Plugin does not declare is never reached and stays `unproved` (ADR 0033). It runs in `goodfetch-conformance`'s `tests/it` against the toy Plugin `goodfetch-toy-plugin`, conforming, broken in `replace` (`--forget`) and with a capability left out (`--leave-out`).
- `self-test/cases.toml`: the self-test suite, which proves the Proving ground's own oracle. Its target is the Proving ground itself: each case submits the reference result read from the pages, or a known-wrong result made from it, and checks the oracle's outcome. It runs in `goodfetch-conformance`'s `tests/it`, in the Pre-merge suite of every pull request whose change reaches the harness or the Proving ground, against the local copy.
