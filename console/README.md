# Console

The Console, with Foxhound's screens as a package of their own (ADR 0087). Area 12 fills it.

Each package commits the routes its build reads as `routes.json` at its root, `{ "routes": ["/runs", …] }`, which the Feature inventory reads for its `screen:` Features (ADR 0072), and at which the executable serves the Console's page (`xtask console build` keeps it beside the build). A segment that begins with `$` stands for any one segment of the page's path, the route's parameter, as in a run's page, `/runs/$run`, which the executable serves at `/runs/<run-id>`. Collie's are declared in `collie/src/routes.ts`, whose unit test fails when `routes.json` differs.

Each state of a component is a Storybook story beside it (`*.stories.tsx`; `collie/.storybook/`), which the root Vitest configuration's `component-stories-light` and `component-stories-dark` projects render as tests with the a11y addon's axe pass; `pnpm --dir console/collie exec storybook dev` shows them.

A screen that keeps its view in the page's address, as Runs keeps its filter so a view can be shared (ADR 0117), reads and replaces the address's query through the `Address` the build entry passes the shell (`src/address.ts`); its tests pass their own.

Each `screen:` Feature gets a keyboard walk and axe case from `screens.spec.ts`, with no test written for it (ADR 0073). Give each new screen its route and sign-in state in `screens.toml`, or its case fails.

`collie/` is `@goodfetch/console`, Collie's Console: its shell, design system and build entry. `just console-build` (`xtask console build`) builds it into the brotli files Collie's executable embeds (ADR 0057); `pnpm --dir console/collie run messages` rewrites its message catalog, which `just lint` checks. The catalog is English with two pseudo-locales Lingui generates from it, `en-XA` and `ar-XB` (right to left), which a browser whose first language is one of them reads (ADR 0073); `src/errors/` gives each Error code its catalog message, rendered from the error's fields (ADR 0079), for a failed call and for the error and warnings a Run report names alike. A run's page shows, once the run ended, the Run report `run.report` answers (`src/runs/run-report.tsx`), each part as the engine produced it and a part the report does not carry as absent; a run that replayed a Response recording carries the replayed mark on its page and its Runs row (`RunIndexRow.replayed`).

Its Client, `src/client/`, runs the Collie client package's browser entry over the WebSocket on the Console's own origin, or over Server-Sent Events plus `POST` where a proxy refuses WebSockets, signed in through the link `goodfetch-collie console` opens (`src/sign-in.ts`); its unit tests pass the in-memory adapter of the protocol. It reconnects by itself, sending again its subscriptions and its reads and idempotent writes, never an Effect, while the shell keeps the page read-only under a banner. A call takes an `AbortSignal`, which cancels it on the engine too, as a run's page cancels its waiting `run.progress` read when it closes. `src/generated/operations.ts`, the operation map that types its calls, is `xtask codegen`'s and never edited by hand.

The Runs screen and a run's page name the Product each run needs and, while it is live, the engine that owns it (`src/runs/owner.tsx`). Collie's build imports none of Foxhound's screens (ADR 0087): on Collie's engine, a run that needs Foxhound keeps the views every run has in a tab of their own, beside one tab per Foxhound view (`src/runs/foxhound-views.ts`), each named by the operation of Foxhound's catalog it reads, which `src/generated/foxhound.ts`, `xtask codegen`'s list of the operations only Foxhound carries, types. Each such tab calls its operation (`ConsoleClient.callFoxhound`) and shows the `not_in_product` the engine answers, whose fix names Foxhound. Until Foxhound's own build exists (#1202), Foxhound's executable embeds Collie's build, so the major's Daemon serves the same Console on the same port whichever Product runs it, and an open Console reconnects by itself when the Daemon hands over to a newly installed Product (ADR 0098).

The page follows the Console's own links itself (`src/navigation.ts`), with no new page load, so a page whose Daemon stopped still moves between its screens. `src/offline/` is the offline cache (ADR 0031): the Runs screen and a run's page keep what they show in IndexedDB, through `summaries.ts`'s allow-list, which keeps no text a program writes, and show it while they have no answer from the engine. Rows are encrypted under a key the page holds only in memory; IndexedDB keeps it wrapped by the Daemon, which unwraps it at `POST /offline-key` only for the cookie of the sign-in it belongs to. Sign out, a page signed out and `console.offline_cache` set to `false` wipe the cache.
