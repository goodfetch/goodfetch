# Console

The Console, with Foxhound's screens as a package of their own (ADR 0087). Area 12 fills it.

Each package commits the routes its build reads as `routes.json` at its root, `{ "routes": ["/runs", …] }`, which the Feature inventory reads for its `screen:` Features (ADR 0072), and at which the executable serves the Console's page (`xtask console build` keeps it beside the build). A segment that begins with `$` stands for any one segment of the page's path, the route's parameter, as in a run's page, `/runs/$run`, which the executable serves at `/runs/<run-id>`. Collie's are declared in `collie/src/routes.ts`, whose unit test fails when `routes.json` differs.

Each state of a component is a Storybook story beside it (`*.stories.tsx`; `collie/.storybook/`), which the root Vitest configuration's `component-stories-light` and `component-stories-dark` projects render as tests with the a11y addon's axe pass; `pnpm --dir console/collie exec storybook dev` shows them. Foxhound's stories (`foxhound/src/**/*.stories.tsx`) render in the same Storybook, and the root configuration compiles messages with Foxhound's Lingui configuration, which holds Collie's catalog and Foxhound's, so a Foxhound story loads Foxhound's catalog as its build entry does.

A screen that keeps its view in the page's address, as Runs keeps its filter so a view can be shared (ADR 0117), reads and replaces the address's query through the `Address` the build entry passes the shell (`src/address.ts`); its tests pass their own.

Each `screen:` Feature gets a keyboard walk and axe case from `screens.spec.ts`, with no test written for it (ADR 0073). Give each new screen its route, sign-in state, keyboard walk and ready element in `screens.toml`, or its case fails.

`collie/` is `@goodfetch/console`, Collie's Console: its shell, design system and build entry. `foxhound/` is `@goodfetch/console-foxhound`, Foxhound's Console: Foxhound's screens and Foxhound's build entry, which starts Collie's (`collie/src/start.tsx`) with Foxhound's build (`foxhound/src/foxhound-build.ts`), so every route of Collie's build is in Foxhound's unchanged (ADRs 0087 and 0094). Collie's package cannot import Foxhound's: it does not depend on it, so its build cannot resolve it, and oxlint refuses the import. A build is a `ConsoleBuild` (`collie/src/console-build.ts`): the Product it is, which names it in the page's title and first screen ("Goodfetch Foxhound", then "Foxhound"), and the views of a run that needs Foxhound it carries, none in Collie's. Foxhound's package's operation map, `foxhound/src/generated/operations.ts`, holds the operations only Foxhound carries, typed from Foxhound's SDK package, and is `xtask codegen`'s. `just console-build` (`xtask console build`) builds each Product's Console into the brotli files its executable embeds (ADR 0057): Collie's into `crates/goodfetch-collie/console-build/`, Foxhound's into `crates/foxhound/goodfetch-foxhound/console-build/`, whose routes are Collie's and then Foxhound's own; `pnpm --dir console/collie run messages` rewrites its message catalog, and `pnpm --dir console/foxhound run messages` Foxhound's and Collie's alike (Foxhound's build compiles both), which `just lint` checks. The catalog is English with two pseudo-locales Lingui generates from it, `en-XA` and `ar-XB` (right to left), which a browser whose first language is one of them reads (ADR 0073); `src/errors/` gives each Error code its catalog message, rendered from the error's fields (ADR 0079), for a failed call and for the error and warnings a Run report names alike. A run's page shows, once the run ended, the Run report `run.report` answers (`src/runs/run-report.tsx`), each part as the engine produced it and a part the report does not carry as absent; a run that replayed a Response recording carries the replayed mark on its page and its Runs row (`RunIndexRow.replayed`).

Its Client, `src/client/`, runs the Collie client package's browser entry over the WebSocket on the Console's own origin, or over Server-Sent Events plus `POST` where a proxy refuses WebSockets, signed in through the link `goodfetch-collie console` opens (`src/sign-in.ts`); its unit tests pass the in-memory adapter of the protocol. It reconnects by itself, sending again its subscriptions and its reads and idempotent writes, never an Effect, while the shell keeps the page read-only under a banner. A call takes an `AbortSignal`, which cancels it on the engine too, as a run's page cancels its waiting `run.progress` read when it closes. `src/generated/operations.ts`, the operation map that types its calls, is `xtask codegen`'s and never edited by hand.

The Runs screen and a run's page name the Product each run needs and, while it is live, the engine that owns it (`src/runs/owner.tsx`). A run that needs Foxhound keeps the views every run has in a tab of their own, beside one tab per Foxhound view; a Collie run shows only the views every run has. In Foxhound's build, those tabs are Foxhound's views (`foxhound/src/runs/run-views.tsx`: the crawl's progress, its seeds, its requests' outcomes and its failed requests), each reading its operation from Foxhound's engine. The Progress tab (`foxhound/src/runs/crawl-progress.tsx`) follows `run.progress` to its last value and shows the crawl's parts of each (ADR 0102): the status message and a keep-alive crawl's idle state, the requests in flight with their phase, tier and attempt, why due requests wait per reason with the domains held, their next admission and the setting behind the wait with its value and layer, each sitemap seed's progress, and the handlers against their concurrency with the Resource governor's level. `RunProgress` keeps those parts as members it does not name, so `foxhound/src/runs/crawl-parts.ts` types them after `goodfetch-protocol`'s `CrawlRunProgress`. The Outcomes tab is the request log (`foxhound/src/runs/request-log.tsx`): it follows `run.outcomes` page by page until the sequence ends, each request's latest outcome only, with its attempts and the error of each failed attempt. A `handler_failed` or `hook_failed` shows the program's exception from its details (`exception_type`, `exception_message` and `exception_stack`, empty from Rust), and a `hook_failed` its `stage`, `hook`, `label` and `wrapped_code`. Its filters (outcome, Label and Error code) run in the engine, and it renders only the rows on screen. Collie's build imports none of Foxhound's screens (ADR 0087): on Collie's engine, each tab is named by the operation of Foxhound's catalog it reads (`src/runs/foxhound-views.ts`), which `src/generated/foxhound.ts`, `xtask codegen`'s list of the operations only Foxhound carries, types, calls its operation (`ConsoleClient.callFoxhound`) and shows the `not_in_product` the engine answers, whose fix names Foxhound. The major's Daemon serves its Product's build on the Console's port, so installing Foxhound adds screens without moving anything, and an open Console reconnects by itself when the Daemon hands over to a newly installed Product (ADR 0098). `foxhound/tests/served/route-walk.spec.ts` visits every route of Collie's build, read from `collie/routes.json`, on Foxhound's executable (ADR 0094).

The page follows the Console's own links itself (`src/navigation.ts`), with no new page load, so a page whose Daemon stopped still moves between its screens. `src/offline/` is the offline cache (ADR 0031): the Runs screen and a run's page keep what they show in IndexedDB, through `summaries.ts`'s allow-list, which keeps no text a program writes, and show it while they have no answer from the engine. Rows are encrypted under a key the page holds only in memory; IndexedDB keeps it wrapped by the Daemon, which unwraps it at `POST /offline-key` only for the cookie of the sign-in it belongs to. Sign out, a page signed out and `console.offline_cache` set to `false` wipe the cache.
