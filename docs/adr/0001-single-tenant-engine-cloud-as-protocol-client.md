# Single-tenant engine; the cloud is an ordinary protocol client

Goodfetch Cloud must power an actor platform, a crawl and extraction API, and hosted browsers, yet the engine has no notion of tenants or prices: in Goodfetch Cloud each run gets its own engine (a local Daemon hosts many runs, ADR 0024), and the cloud isolates runs (container or VM) and turns usage into prices, as Apify, Spider Cloud and Browserbase do with their open-source libraries. The cloud drives the engine through the same JSON-RPC protocol as the SDKs, where usage, limits and lifecycle signals (checkpoint, abort, migrate, resume) are ordinary messages, so one conformance suite covers both and anything the cloud does can be reproduced locally. Decided in [Cloud readiness: which cloud businesses the engine must serve](https://github.com/goodfetch/goodfetch/issues/69).

> Amended by [ADR 0096](0096-the-browser-host-runs-from-either-products-executable-and-goodfetch-cloud-runs-each-run-on-the-product-it-needs.md): each run gets the engine of the Product it is started for: the Product its Client needs, or, for a run started from the Console or by Goodfetch Cloud itself, Foxhound's when its target names something only Foxhound carries and Collie's otherwise; a Recipe that names Foxhound runs on Foxhound's, since a Recipe's manifest, not its settings or steps, decides its Product. Every engine and Browser host Goodfetch Cloud runs is a published Product executable, unmodified, with Private components added only as process Plugins.

> Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.

## Considered Options

- **Multi-tenant engine** (one process serves many tenants): rejected. One crash or hang in it would stop every tenant's runs, and the lab showed that a pool reused without reset leaks one tenant's cookie to the next 30 times out of 30.
- **Separate worker protocol for the cloud**: rejected. Two protocols means two conformance suites, and cloud behaviour that cannot be reproduced locally.

## Consequences

- A reset or discard must leave no state behind; a permanent conformance gate checks it. Saved identities are the one exception: named objects that outlive runs by design, kept outside run state and removed only by their own delete (ADR 0035). A Profile directory a run uses in place and a Borrowed browser are the person's own data, not Goodfetch state, so the gate neither removes nor scans them (ADR 0056).
- The engine counts usage and enforces limits but never knows prices.
- Goodfetch Cloud chooses the version of the Clean-up rules for each run and hands its digest to the engine through the protocol; a local run reproduces it with `clean_up.version` (ADR 0047).

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-23, [#224](https://github.com/goodfetch/goodfetch/issues/224): a reset and a discard are one erasure, the operation `run.discard` (SDK reach only, no CLI command or MCP tool until a surface asks for one), refused for a Run its engine still runs (`run_live`) and for one whose writer lock another engine holds (`run_in_use`). It overwrites the Run's wrapped data key in its run file with `secure_delete` on and truncates that file's WAL, then removes the run folder (the lock file last); in the per-install layout the install database, which now keeps `secure_delete` on for every write so a rewritten chunk's old page is zeroed too, deletes the run folder's files and truncates its WAL. The Run index row stays `erased` (ADR 0036) without its owner, tags or status line, and the index's WAL is truncated; a later `run.start` under the Run ID starts a new Run. The gate is `conformance/reset/cases.toml`, whose cases plant Proving ground canaries and search every regular file of the Goodfetch home, following no symbolic link. No Response cache, compiled Clean-up rules or `filter_lists.extra` list is kept outside a run folder yet, so the discard deletes none; the ticket that keeps one deletes a discarded Run's entries in `runs::discard`.
