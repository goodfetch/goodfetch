# Run state is a portable SQLite file; runs resume from checkpoints, not shared storage

Each run keeps its state (frontier, staged results, sessions, effect journal, usage) in its own SQLite database in WAL mode with a single writer, and resumes on another machine from a checkpoint: a consistent, self-contained copy of that database, written to a location the caller gives and reported over JSON-RPC with its size, digest, run epoch and journal position; a run that ADR 0056 binds to its machine does not resume elsewhere. The cloud stores checkpoints wherever it likes and never swaps anything inside the engine, which keeps the single writer and the one engine per run of ADR 0001. Running the engine as a separate process is not what keeps this file safe from crashes: the [binding prototype](https://github.com/goodfetch/goodfetch/issues/74) showed SQLite surviving crashes in-process too. The separate binary isolates Clients from each other (ADR 0024). Decided in [Adopt runtime and state decisions](https://github.com/goodfetch/goodfetch/issues/70).

> Amended by [ADR 0103](0103-a-handler-pushes-records-staged-with-its-attempt-into-datasets-its-crawl-declares-and-a-reader-never-slows-the-crawl.md): a Checkpoint also holds each Dataset's name, key and schema hash, which a resume checks before any work: a Dataset holding Records that the crawl no longer declares fails it with `dataset_unknown`, and a changed key with `dataset_key_invalid`.

> Amended by [ADR 0142](0142-a-runs-state-lives-in-memory-its-run-file-is-written-in-batches-and-a-clean-stop-writes-everything.md): a Foxhound Run's state lives in memory and its run file is written in Run-state batches; the default Durability level becomes `batch`, every existing level stays as a preset of the batch settings, and "an acknowledged commit survives a power cut" holds at `full`. The portable file, the single writer, Checkpoints and resume elsewhere are unchanged.

## Considered Options

- **Pluggable live storage (PostgreSQL) that the cloud swaps in**, the R&D's working view: rejected. Every state contract would need conformance tests on two implementations, and it brings back the multiple writers that ADR 0001 avoided. PostgreSQL stays possible as a sink for results.
- **One database per install holding every run**: kept as a local setting, not the default. It gives up one file per run: one database, written by the Daemon (ADR 0024), holds all of that install's runs. When two product majors are installed, each keeps its own such database (ADR 0030). The single writer holds; as with any Daemon, a crash stops every run it hosts. Goodfetch Cloud always uses one database per run. Export, import and checkpoint produce the same per-run file in both layouts. In either layout, a per-user, per-major Run index lists every run, and in the per-run layout run files go to a per-user, per-major data folder by default (ADR 0031).
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#223](https://github.com/goodfetch/goodfetch/issues/223): the setting is `run_state.layout` (`per_run` by default, or `per_install`), taken only from the machine's own layers and read when the Daemon starts. The install database is `run-state.sqlite` in the per-major folder. It keeps each Run's run file byte for byte, as chunks of the bytes of every file SQLite opens under the run folders (the run file and its WAL), which a VFS registered under one name serves at the paths the per-run layout gives them; so the run state's writer, its readers, Checkpoints and their restores are the per-run layout's code unchanged, and a Checkpoint taken in either layout is the same file, byte for byte, for the same steps. Each write of a run file is one transaction of the install database, committed without a sync; a sync of the run file commits with `synchronous=FULL`, which syncs the install database's WAL. The run folder keeps only the Run's writer lock, its page bodies and its default Checkpoint. An Attached engine in this layout relays its Client's Connection to the Daemon of its major, which it starts when none runs, adding the Daemon's token to the Client's `hello`; the Runs are then the Daemon's and stop with that Connection. Run-state import is `run.resume` from a per-run file (the #218 note under Consequences); its fuzz target is `run_state_import`.
- **A separate log as the source of truth, with the database rebuilt from it** (rqlite's design): rejected for V1. It would double the recovery code and tests, for a speed gain that grouped commits can give at large batch sizes.

## Consequences

- By default an acknowledged commit survives a power cut: `synchronous=FULL`, many operations grouped per commit by the single writer, `fullfsync` on macOS (plain `fsync` there does not flush the drive cache), and a bundled SQLite.
- An opt-in fast mode (`synchronous=NORMAL`) is labelled everywhere as surviving a process crash only: an OS crash or power cut may roll back recent commits, possibly many, without corruption.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#223](https://github.com/goodfetch/goodfetch/issues/223): the setting is `run_state.durability` (`full` by default, or `fast`), which any layer may set; a Run opens its run file in the mode its resolved settings name, and a resume in the mode the resume's settings name. `fast` is a setting that weakens a guarantee (ADR 0028): the run report's `weakened_by` and `config explain` label it. The Console's label waits for its run views.
  > Amended by [ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md), 2026-11-06, as [#1577](https://github.com/goodfetch/goodfetch/issues/1577) built it (its details are agent decisions, pending owner review): `run_state.durability` takes four Durability levels. `full`, the default, and `fast` keep their meaning. `periodic` is `fast` with one synced commit every `run_state.commit_interval` (5 s by default), so a power cut loses at most that interval of work ([#1927](https://github.com/goodfetch/goodfetch/issues/1927)). `off` (`synchronous=OFF`) syncs nothing, and a run file that a crash or a power cut left still carries its `unclean` mark, so it is discarded when the Run is next started or resumed, and the Run starts again from nothing. At every level a clean stop leaves a consistent run file and Checkpoint, so a paused Run resumes even at `off`. Every level below `full` weakens a guarantee, which the run report's `weakened` and `config explain` label. Each attempt writes two jobs: its claim, which holds the charge's journal, its Lease and its Session draws ([#1924](https://github.com/goodfetch/goodfetch/issues/1924)), and its outcome, which holds learning, enqueued links, the Lease's commit, the settlement, the charge and the Records, all or none ([#1925](https://github.com/goodfetch/goodfetch/issues/1925)). Each job has its own savepoint, and the single writer commits everything queued in one transaction, without a timer. At `full` a group syncs only when a job in it needs a sync. The claim, a handler's `learn` and enqueue, a followed redirect's check-and-set and the per-domain queues' journal commit on a second writer connection at `synchronous=NORMAL` and become durable with the next synced group, so an outcome, a readable Record, `run.finish`'s answer and a Checkpoint are still synced before anything is told outside ([#1926](https://github.com/goodfetch/goodfetch/issues/1926)). `journal_position` is written once per group commit that writes, and a read commits nothing, so the position counts those commits. The writer's connection runs no automatic checkpoint: a checkpointer on its own connection runs a `PASSIVE` checkpoint once the WAL passes 16 MB, and a `TRUNCATE` one after the writer's last write ([#1922](https://github.com/goodfetch/goodfetch/issues/1922)). Reads leave the writer for a bounded group of four kept read-only connections ([#1923](https://github.com/goodfetch/goodfetch/issues/1923)). The Effect journal ([#1550](https://github.com/goodfetch/goodfetch/issues/1550)), which does not exist yet, must sync its entry at `fast` and `periodic` too.
- None of the crawler libraries surveyed (Crawlee, Scrapy, spider-rs, Colly, Katana) fsyncs run state by default; Restate, DBOS, and Temporal and Hatchet on PostgreSQL do. The speed cost was measured on one Mac only, so the V1 benchmark measures both modes on the Linux reference host, and a large gap there may reopen the separate-log option.
- Checkpoints are taken on the `checkpoint` and `migrate` signals, on a clean stop, and periodically at an interval the caller sets (off by default locally). Between checkpoints, the journal covers a crash on the same machine.
  > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): a stop at the `critical` storage level writes no Checkpoint copy onto the full filesystem, since the run file on this machine resumes the Run. A periodic Checkpoint onto a filesystem at `low` is skipped, and one whose write fails is skipped with a `file_write_failed` warning.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#218](https://github.com/goodfetch/goodfetch/issues/218): a Checkpoint is the run file copied in one step of SQLite's online backup from a reader beside the Run's writer, so it holds the run file as of one commit, in rollback-journal mode so it is one self-contained file; it is written to a hidden `.<name>.<nonce>.partial` file beside its location, synced, then renamed, and reported once complete with its size and SHA-256. Where the engine keeps a Run's Checkpoints is its folder, `checkpoint.sqlite`, the latest one taken there. Its journal position is the number of commits the run file holds, until the Effect journal (area 9) gives its own. Every stop the engine makes (an abort, a pause, a migration, a Client's end) writes a Checkpoint after the Run's end, with ADR 0122's exceptions above: a stop at the `critical` storage level writes no Checkpoint copy onto that filesystem, and a periodic Checkpoint onto a filesystem at `low` is skipped (the engine has no storage levels until ADR 0122's resource governor lands). One that fails is logged and the stop goes on, since the run file resumes the Run. The catalog's operations are `run.checkpoint` (`location` optional), `run.pause`, `run.migrate` (`location` optional) and `run.resume` (`checkpoint` optional): a resume from a Checkpoint restores it as the Run's run file in this engine's run folder, through SQLite's backup in one transaction of that file, rather than a separate import operation. A resume elsewhere starts the Run's kind's driver again on the resuming Connection, a crawl counting each attempt the state shows in flight as `handler_lost`. Corrected 2026-10-21: it said every stop writes a Checkpoint, ignoring ADR 0122's `critical` and `low` exceptions.
- After a machine is lost, the run redoes the work since its last checkpoint. Effects in the checkpoint's journal are checked rather than repeated. Journal entries after the checkpoint are lost with the machine, so every effect the redone work reaches is checked first when it has a check, and otherwise reported as uncertain.
- The reset gate of ADR 0001 runs in both layouts. In the per-install layout, a discarded run must leave no recoverable bytes of its secrets. The saved-identity store of ADR 0035 sits beside both layouts, outside the gate, and its delete must leave no recoverable secrets.
- Checkpoints and exported run files contain session secrets: those fields stay encrypted under a key the caller holds, results Exports never carry them, and discarding a run destroys its key (ADR 0015).
- Responses reused across runs live in the per-user Response cache, outside run state: a run resumed on another machine only misses the cache, and resetting or discarding a run deletes the entries it fetched (ADR 0046).
- A run records the digest of the Clean-up rules it holds to, and a resumed run uses the same version. A missing release set is fetched as a pinned download; a missing daily set only where the channel is configured or `clean_up.version` names it (ADR 0047).
