# The frontier learns which URLs are the same page, and every run reports its completeness

The frontier applies the fixed URL rules competitors use, then learns three more from what it fetches: query parameters that do not change the page (by page signature), trap paths to close, and cursor pagination preferred over offset. Every run reports a completeness of complete, incomplete or unverified, and a run stopped by a Limit is never complete. In the lab, the naive frontier ran out of budget on a trap site where the learned one finished in 75 requests, and offset pagination over a table modified during the crawl lost rows while reporting success 15 times out of 15. Decided in [Adopt collection decisions](https://github.com/goodfetch/goodfetch/issues/71).

> Amended by [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md): a crawl request's identity in the Frontier is its method, its URL after these rules and a hash of its body, as Crawlee's `useExtendedUniqueKey`, so a POST to one URL with two bodies is two requests; a declared `key` still wins.

> Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): the fixed rules are written out (the WHATWG parser's own work, RFC 3986's percent-encoding normalization, the fragment dropped, `utm_*`, `gclid` and `fbclid` dropped and the parameters sorted, `;jsessionid=` dropped), and they make a key while the request is fetched at its own URL. Firecrawl's `www`, scheme, trailing-slash, `index.html` and `index.php` merges are no longer fixed: each is learned per host on evidence (a redirect between the forms, matching page signatures, `rel=canonical`) and reported as `equivalent_form`. `rel=canonical` is evidence for a learned rule, never a merge. A finished run that refused a URL by one of the caps on a URL's shape is `unverified`.

Competitor evidence: [frontier and sessions research](https://github.com/goodfetch/goodfetch/blob/research/frontier-sessions-competitors/rnd/research/2026-10-10-frontier-sessions-competitors.md).

## Considered Options

- **Fixed rules only**: rejected. None of the nine competitors surveyed (Crawlee, Scrapy, Spider, Firecrawl, Crawl4AI, Stagehand, Browser Use, Skyvern, Apify) learns traps or no-effect parameters. Their fixed rules differ (Crawlee strips `utm_*` and sorts parameters, Firecrawl merges `www`, scheme, trailing slash, `index.html` and `index.php`, Crawl4AI also strips `gclid` and `fbclid`); Goodfetch applies all of them first, and learns on top.
  > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): only RFC 3986's safe rules and the parameter rules stay fixed; Firecrawl's `www`, scheme, trailing-slash, `index.html` and `index.php` merges are learned on evidence.
- **Canonicalization declared only by the run's code**: kept as an override, not as the only mechanism. It suffices for a known site, not for discovery.
- **Success or failure only, as competitors report**: rejected. Crawlee's `run()` returns statistics without a stop reason and only logs a limit stop, and Firecrawl reports `completed` at its page limit; only Scrapy's `finish_reason` names a limit, and it still reports a depth cutoff as finished.

## Consequences

- Each learned rule is kept in run state with its evidence and the number of URLs it merged, and is reported; rules never cross registrable domains. Declared canonicalization always wins.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#851](https://github.com/goodfetch/goodfetch/issues/851): spec #581's thresholds, built. A page signature is the SHA-256 of the document's title, a NUL and its main content's text, white space collapsed in each; a link's text is part of that text, its `href` is not, and a document with no main content is signed by its title alone. Only a `GET` with no body that a fetch tier fetched is evidence, once per crawl request (a retry makes no pair with itself), learned before its handler runs so the links it enqueues count against what the page taught; under `fetch.tier: auto`, where the engine fetches nothing yet, nothing is learned. Every rule holds on one host, so never across a registrable domain. A parameter learned to have no effect makes a URL's identity its key without it: a candidate is a `duplicate` when it differs from an admitted request only by learned parameters, whichever of the two carried them, and the report lists it among the rule's merged URLs. A trap's path pattern writes numeric segments `{number}`, dates (a 4-digit year and a month, with or without a day, or the day first, joined by `-`, `_` or `.`) `{date}` and tokens of 6 or more hexadecimal digits holding both a digit and a letter `{hex}`; its run of pages counts each page under it whose signature the host showed before, and starts again at a new signature or at a URL outside the pattern that one of its pages adds (a link to an admitted URL counts as nothing new); the 100th page in a row closes it, and every later URL under it is not added with the new reason `trap_path`, its count the Completeness reason `trap_path`. Offset pagination is a parameter whose integer values on one path, at least 3 of them, fill one progression with a step of 2 or more, a page size, so page numbers (a step of 1) are no offset and a crawl of a numbered listing stays `complete`; a cursor link is a URL enqueued from a page of that path, of the same path, without the offset and with a parameter that is no offset, after which the path's offset URLs are not added with `duplicate` (pending ones are left to the rule that ends them `skipped`, #856); a listing paged by an offset and no cursor makes a finished Run `unverified` with the reason `offset_pagination`, counted per listing. The Run report's `learned_rules` gives each rule's `kind` (`no_effect_parameter`, `trap_path` or `cursor_pagination`, the SDK sketch's names), `host`, `path` (the pattern or the listing), `parameter`, `evidence` in words naming its URLs, and `merged`, every URL it merged or refused in the order met, in place of a count, so each merge can be audited.
  > Amended by [ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md), 2026-11-06, as [#1577](https://github.com/goodfetch/goodfetch/issues/1577) built it (agent decisions, on a guarantee, not read by the owner): the page signature reads the main content of the Run's chosen Extractor (the Label's `content.extractor`, else the Run's), with the formats' fallback, the text outside the page's navigation landmarks. So a page in which the step finds nothing is signed by that text, no longer by its title alone ([#1913](https://github.com/goodfetch/goodfetch/issues/1913)). It is read on the page's one tree as it was served, the last of its readers, since its main-content step consumes the tree: one parse and one readability run per page, and the Clean-up rules' removals take no part ([#1910](https://github.com/goodfetch/goodfetch/issues/1910)). ADR 0138 says it reads the cleaned page's main content, but the clean-up runs only for a format read from the cleaned page ([#1909](https://github.com/goodfetch/goodfetch/issues/1909)). The setting `frontier.learning`, on by default, switches learning off: with it off, no page is signed, no readability runs for it and no rule is learned, while the fixed URL rules and the check for an exact duplicate stay. The Run report's `learned_rules` is then empty, with the warning `learning_off`; the Audit log records the setting as `learning_switched_off`, and the report's `weakened` lists it ([#1909](https://github.com/goodfetch/goodfetch/issues/1909)).
  > Note (2026-11-10): since [ADR 0142](0142-a-runs-state-lives-in-memory-its-run-file-is-written-in-batches-and-a-clean-stop-writes-everything.md), learning runs against the run file once per written batch, at most one batch after the page, and no longer before its handler runs (the owner's decision of 2026-11-10 on [#2169](https://github.com/goodfetch/goodfetch/issues/2169)). A parameter or a form that is settled takes no more evidence (the owner's decision of 2026-11-10, [#2253](https://github.com/goodfetch/goodfetch/issues/2253), Q6; [#2287](https://github.com/goodfetch/goodfetch/issues/2287)).
  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-11, [#2309](https://github.com/goodfetch/goodfetch/issues/2309): a cursor is learned on evidence of a cursor, no longer on a parameter's name. Once a path's offset is known, the link each of its first two pages gives to that path under a parameter that is no offset is kept, with its value and its page. The parameter is a cursor once a third page links it with a value of its own, the first two having each linked one value of their own, as a token for the rows after a page changes from page to page; a third page's link is what shows that the first two gave all their links. One that a page links with two values, as a filter's, or that two pages link with one value, as a sort or a view, is refuted for the Run and never a cursor, so a listing whose pages each link a previous and a next cursor under one parameter keeps its offset. The rule's `evidence` names the three pages and their links. A link the visited set already holds is not read, so a sort every page links alike is met once and teaches nothing. Each offset URL a learned cursor refuses is counted under the Completeness reason `cursor_pagination`, which makes a finished Run `unverified`, as a trap's refusals do. With `frontier.learning` off, an admission keeps none of this evidence, nor an offset's values, and no learned cursor refuses a URL: the setting is recorded with the crawl's bounds in the run file, which every admission reads already.
- A wrongly learned no-effect parameter merges distinct pages. The report makes that visible, and a conformance fixture covers it.
- Unverified covers a frontier exhausted only through offset pagination or a heuristic.
- Unverified also covers a finished run that left pages in scope at the Block cause `payment_required`, which it lists (ADR 0045).
- The same holds for pages left at the Block cause `consent_required` (ADR 0048).
- The frontier also takes priority scores and forefront insertion, for parity with Spider and Crawlee.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#836](https://github.com/goodfetch/goodfetch/issues/836): `crawl_request.enqueue` takes `forefront` beside `priority`, both ordering only the requests of one domain key (ADR 0004). A `forefront` request goes ahead of every request its domain holds pending when it comes, whatever their priority, so of two `forefront` requests the later goes first, as Crawlee's `forefront`; the others go highest priority first, then in the crawl's order, and a retried request keeps its place. The run file keeps a `forefront` work item's position in its `forefront` column, so the order survives a crash and a resume. A full per-domain queue keeps the requests that go first: one that goes ahead of its last takes that one's place, the other waiting in the run file, and while any waits there a request that would go after it waits there too, until the queue drains and fills again in order. A seed takes `forefront` as an enqueue does, at the start and through `run.add_seed` ([#914](https://github.com/goodfetch/goodfetch/issues/914)), among the options ADR 0093 lists. Corrected 2026-10-22: it said seeds take no `forefront` until `run.addSeed`, which #914 gave `Seed`'s `forefront`.
