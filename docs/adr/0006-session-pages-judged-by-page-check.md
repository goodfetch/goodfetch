# Session pages are judged by a Page check, never by the HTTP status alone

Every page fetched in a session is judged against a Page check declared by the run's code: the expected page is a success, a recognized login page is a lost session, anything else stops the work item with `page_check_failed` (Error code style of ADR 0038). Without a declared Page check, a built-in detector (a password field, a redirect to a known login URL) applies and the pages it judged are reported as weakly checked. In the lab, a portal answering `200` with its login form after expiry produced 20 false successes out of 20 for a client trusting the status, and none with the Page check. Decided in [Adopt collection decisions](https://github.com/goodfetch/goodfetch/issues/71).

> Amended by [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md): under `fetch.tier: auto`, a page that fails its expected page on a non-browser tier (any tier but `browser`) escalates the request to the browser instead of stopping the work item; on the browser tier, or under a forced tier, it fails with `page_check_failed`. A login page is a lost session on every tier.

> Note (agent decision, on a guarantee, not read by the owner but for when the built-in detector raises, which the owner's decision of 2026-11-10 under the next note amends (grilling of G-06, Q2 and Q16)), 2026-10-24, [#710](https://github.com/goodfetch/goodfetch/issues/710): a Collie page is judged after `goto`, `reload`, `goBack` and `goForward` reached a document with a response, once the call's `waitUntil` state came, so selectors and texts read the document a program then sees. Page matches are tagged by `kind`: `glob` and `regex` (the matcher `page.route` uses) on the document's final URL, `css` and `xpath` on any element of the main frame's document, visible or not, and `text`, a substring of the body's text with runs of white space read as one space, case kept; a selector the document refuses raises `setting_invalid`. The login page is matched first, so a page matching both is a login page; without `login_page` no page is judged a login page, and without `expected_page` every other page passes. A login page raises `logged_out` (details: `url`, `status`, `judged_by` `page_check` or `built_in`) until the ladder ticket (#747) runs recovery before it and adds its steps. The built-in detector judges a login page from a navigation redirected to a URL whose last path segment, its extension aside, is `login`, `log-in`, `log_in`, `logon`, `signin`, `sign-in`, `sign_in` or `authenticate`, or from a page outside such a path showing exactly one password field, visible and not `autocomplete="new-password"`; a navigation sent to a login path itself is the program going to log in, never a lost login. Each page it judges writes a `page_weakly_checked` Provenance entry with its URL and its verdict, `passed` or `login_page`.

> Note (decision of the spec #577 review, on a guarantee, not read by the owner but for "the redirect sign still judges it", which the owner's decision of 2026-11-10 below replaces (grilling of G-06, Q2 and Q16)), 2026-10-24: every page of a Session is judged, not only those `goto`, `reload`, `goBack` and `goForward` reach, as the spec and story 5-79 say. A document a click, a form, a script, a redirect or a popup's opener reached is judged once, its Block cause first and then its Page check: by a wait that waited for its navigation (`page.waitForURL`, `waitForLoadState`, `waitForRequest` and `waitForResponse`, whose code a failure to read the document raises), or else by the page's next call, for which such a failure reads as a document showing nothing. The built-in detector reads a document no call sent as sent to the first URL of its redirect chain. A Session that holds no login, having opened from no Session source (a fresh Session, until a `login` or a Saved identity can give it one), is not judged by the password-field sign: a password field it shows is the program's own way in; the redirect sign still judges it.

## Considered Options

- **Blocked status codes** (Crawlee's `[401, 403, 429]` plus three challenge selectors): rejected as the only signal; it lets the `200` login page through. No surveyed competitor detects a lost login from page content: Crawlee, Scrapy, Spider, Firecrawl and Stagehand have nothing (Browserbase tells users to write their own checks), and Browser Use and Skyvern leave it to an LLM's reading of the page. Evidence: [frontier and sessions research](https://github.com/goodfetch/goodfetch/blob/research/frontier-sessions-competitors/rnd/research/2026-10-10-frontier-sessions-competitors.md).
- **The R&D's "recipe contract"**: renamed Page check, because a Recipe is a publishable package and a short SDK script needs the same protection.
- **Logging in again on every run**: rejected. It is exact but costs a login per resume; resuming the session state from the run's journal halved logins in the lab.

## Consequences

- Session state lives in run state (ADR 0002; a Session on a Borrowed browser or behind a person's own Browser host keeps it in that browser, and its run resumes only through it, ADR 0056) and is revalidated on the first page after a resume.
- Recovery goes, in order: the declared refresh, a re-import from the source of an imported login (ADR 0056), a scripted login with a Secret reference, an AI agent login, then a pause for a human through an interactive live view in the Console or CLI. Each step consumes the shared attempt budget, at most two recoveries per page, and every step is logged.
  > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): in code, the Page check is the Session setting `session.page_check` (a login page and an expected page, matched in the engine); the scripted login step is the program's own `login` function given when the Session opens; `session.recovery.human_pause` switches the Human pause step off for an unattended program; and a login the ladder does not bring back raises `logged_out`, a `PageError` listing each step and why it did not recover.
  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): `session.recovery.agent`, `true` by default, switches the AI agent login step; the step is skipped, and the error that ends the recovery says why, when no model is configured and no login Plan replays it, or under `plan.frozen` without one.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
- MFA: the engine generates authenticator-app (TOTP) codes, reads email or SMS codes through a user-configured source, and pauses for a human on push approvals or hardware keys. Credentials and TOTP seeds are reached through Secret references, resolved by Secret providers, vaults included (ADR 0015). Email or SMS codes and magic links come from IMAP, the Gmail API, Microsoft Graph, an inbound webhook, a polled endpoint or Twilio, matched by sender, pattern and a time window starting at the login attempt, and used once; a Human pause takes over when none arrives. Agent mechanics are decided in [Adopt AI and agent decisions](https://github.com/goodfetch/goodfetch/issues/72).
- The session pool scores, rotates and retires sessions (Crawlee's model) and adds account rotation, which no surveyed competitor offers. Each session binds one Access mode, one Identity profile and one proxy; proxy kinds and escalation by new Session are set in ADR 0021. A Session on a Profile directory used in place or on a Borrowed browser is never rotated or retired; a failure that would do so raises a Human pause (ADR 0056).
  > Amended by [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md): the Session pool belongs to a crawl, so only Foxhound has one. A Session a program or an Agent opened itself, in either Product, is never rotated, retired or replaced: a Challenge goes on down ADR 0035's ladder without its new `stealth` Session, and any other Block cause is reported on the call that met it, on a Profile directory or a Borrowed browser too. The Human pause above holds for a crawl's Session.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#920](https://github.com/goodfetch/goodfetch/issues/920): the pool lives in `goodfetch-session-pool` under `crates/foxhound/`. A request goes to a new Session while fewer than `session.pool.max_size` are open, as Crawlee's pool does, then to one drawn from the Run's `Entropy` among those open at its domain's proxy tier; with none open there, the drawn Session is retired (`pool_full`) to make room. A Session is retired once its error score reaches `session.pool.max_error_score` (Crawlee's `>=`), once it served `session.pool.max_uses` requests (counted when drawn) or at `session.pool.max_age` after it opened, by the wall clock so the age survives a resume. A committed answer is a success, `blocked` and `page_check_failed` score it down, and any other ending (a skip, the handler's own failure, a lost lease) leaves its score. Sessions and their domains' proxy tiers are kept in run state (`pool_sessions`, `pool_tiers`); every Session read back on a resume is revalidated on its first page, which `crawl_request.handle`'s `session.revalidate` tells the handler until the engine's page runs the Page check and its recovery (area 5).
  > Amended by [ADR 0143](0143-a-crawls-browsers-grow-with-its-concurrency-a-browser-is-recycled-for-growth-after-its-warm-up-and-a-sessions-page-serves-its-next-request.md): by default (`session.pool.growth: on_demand`), a request goes to an open Session at its domain's proxy tier that serves fewer than `session.pool.session_concurrency` requests (1), preferring one last used on the request's host (`session.pool.affinity: host`) and otherwise drawn from the Run's `Entropy`, and a new Session opens only when none has room and fewer than `session.pool.max_size` are open; `eager` keeps the rule above.
  > Note (agent decision, not read by the owner), 2026-11-14, [#2414](https://github.com/goodfetch/goodfetch/issues/2414): a pool Session sends from one client for its life, its own HTTP transport or its browser, taken when it opens and kept in `pool_sessions.sends_from`; a draw asks for the client its attempt's plan sends from (a tier forced onto `http`, `discovered_api` or `light_browser`, and a sitemap's fetch, from the transport; the engine's choice and a tier forced onto `browser_fetch` or `browser`, from the browser) and only ever answers a Session of that client. `session.pool.max_size` counts both clients together: with no room and none of the wanted client open at the domain's proxy tier, the drawn Session is retired (`pool_full`) as for another proxy tier. A run file whose pool table predates the column is not resumed: the Run ends as failed with `run_state_unavailable`, its message saying the pool was stored by an earlier build and to start a new Run.
- The Page check can be switched off per run (ADR 0023); the pages it would have judged are then reported as unchecked.
