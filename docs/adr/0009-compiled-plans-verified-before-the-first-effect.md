# Plans are committed files, verified in full before the first Effect

AI work is compiled once into a Plan: concrete steps whose targets each carry a Target fingerprint, built from what identifies the element to a person (such as its kind, type, label and visible text), never from its selector. The Plan is a readable file versioned next to the script or Recipe, like a lockfile, and later runs replay it with no model call and report which Plan version they used. Before the first Effect, every step's target is checked against its Target fingerprint; on Drift the engine makes one Repair (a fresh observation and one recompile, checked in full again, drawn from the run's Limits), and a second Drift fails the run. In the lab, compiled replay cost 0.17 to 0.34 times the model spend of an agent that replans each run ([rnd/README.md](https://github.com/goodfetch/goodfetch/blob/main/rnd/README.md) §4.15), with no false success across three real models. Decided in [Adopt AI and agent decisions](https://github.com/goodfetch/goodfetch/issues/72).

> Amended by [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md): in an SDK program each AI verb call (`act`, `observe`, `extract`) is its own unit: its targets are checked against their Target fingerprints before it acts, it gets at most one Repair, and a Drift that remains after that Repair fails the call with `plan_drift`. The engine sees one call at a time, so it cannot check the whole sequence first; a repaired step is kept only after a `verified` run, and an `act` is vouched for only by a Success check evaluated after it, so the lab's wrong booking would read `rejected` or `needs-review`. A Plan replayed toward a goal keeps the whole-Plan rule, which ADR 0100 reads, for an Agent's task, as below.

> Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): for an Agent's task (`page.agent`), whose replay may cross pages and whose entry records when each target was first observed, the check before the first Effect reads: before each Effect, the Effect's own target and every remaining target the recorded run observed before that Effect, on a page already open, are checked, and any other step is checked when it is reached, before it acts, since a page or element that exists only after an Effect cannot be observed before it. An Agent's task gets no Repair: on Drift, or when its Success check fails after a replay, the replay ends and the task goes on live with the model from there, within its bounds, and those steps replace the rest of its entry. Every live step acts on the page as observed, the Effect journal keeps an Effect from being sent twice, and the new steps become a Plan version only after a verified run, with this ADR's review of Plans with Effects.

Evidence: [AI-in-the-loop browser frameworks](https://github.com/goodfetch/goodfetch/blob/research/ai-browser-frameworks/rnd/research/2026-10-10-ai-browser-frameworks.md).

## Considered Options

- **Checking step by step**: rejected. In the lab it ticked a consent box before seeing the Drift, and the repair then reported a wrong booking as a success.
- **A cache held by a service**: rejected. Stagehand v4's cache works only with Browserbase-hosted browsers and receives secret values; users ask for a versioned file they can run in CI.
- **Automatic regeneration on every break** (Skyvern): rejected for Plans with Effects; an unreviewed new Plan could act on the wrong control.

## Consequences

- A Repair is used within its run once checked, but becomes a new Plan version only after the whole run finishes verified (Midscene never writes back a partly repaired plan; Momentic re-caches only after the rest of the test passes). Read-only Plans are promoted automatically; Plans with Effects produce a reviewable diff unless the Recipe opts into auto-approval.
  > Amended by [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md): a first compile is promoted only after a `verified` run too, and a new version from a run that is not `verified` is kept pending for a person's review ("Needs you", ADR 0031), never written silently; once accepted, it reaches the file through the next Run that names it or the CLI. A version is written by entry, and an entry two Runs both changed is kept pending. `plan.frozen` replays only, calling no Model provider, Decision providers included, and writing nothing.
- Login Plans skip the review: when the built-in agent recovers a login (ADR 0006), the Page check judges whether the login succeeded, and its steps become a scripted login Plan that is promoted automatically after a verified run, because a login changes no state on the site that the run is meant to change. Secrets and authenticator codes in it are typed by the engine; a stuck agent hands over to the Human pause, and a CAPTCHA follows ADR 0035's escalation ladder, which reaches the Challenge solver when `solve_challenges` is on.
- `observe` and `act` become Plan steps; `extract` stores its selectors but reads values live; a Success check is never cached.
- A Decision provider (Jev or OpenAI's Decisions API, hosted, or a small open model run inside the engine) may sit between the Target fingerprint check and the LLM, and also checks during replay that a target is still the same element. It returns a choice with a confidence or abstains, its calls are journaled and counted like any model call, and a provider's confidence threshold is used only once a lab campaign has measured it on unseen pages; until then the step stays off. Evidence: [decision models research](https://github.com/goodfetch/goodfetch/blob/research/decision-models/rnd/research/2026-10-10-decision-models.md).
- The Console recorder writes Plans in this format, from DOM actions and network traffic across frames and shadow DOM, preferring a discovered API route with the browser as fallback, together with the matching TypeScript or Python code.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
- The check before the first Effect can be switched off per run (ADR 0023); Effects then run marked unverified in the Effect journal.
- Plans never contain steps for Consent prompts a rule recognises: the engine answers a prompt before each step and its Target fingerprint check, and the recorder leaves such steps out; a step a person keeps after review is theirs (ADR 0048).
- Before a step's Target fingerprint check, the engine lifts any live-hiding rule that matches its target, so a target hidden by newer Clean-up rules is never Drift (ADR 0047).
