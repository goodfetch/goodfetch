# Secrets are references; run state encrypts only its secret fields, under a key the caller holds

A run never holds a raw credential in its code, configuration, Plan or state, only Secret references (`env:NAME`, `keychain:goodfetch/portal`, `op://vault/item/field`). A Plan or a prompt names a secret by its `%var%` placeholder (ADR 0014); the run binds each placeholder to a Secret reference and to the domains allowed to receive it, and a Secret provider resolves the reference at the moment of use. V1 ships these providers: environment variables, the OS keychain (through `keyring-core`), an encrypted local file for machines without a keychain, the caller over JSON-RPC (how Goodfetch Cloud injects a tenant's secrets without the engine storing them), 1Password, Bitwarden and Vaultwarden, HashiCorp Vault and OpenBao, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, and a custom HTTP provider (now an implementation of the Secret provider Plugin kind, ADR 0033). TOTP seeds, proxy passwords, sink and webhook secrets and model API keys all go through the same mechanism; where a vault generates TOTP codes itself, the seed never leaves it. What a run creates itself (session cookies, tokens, login state) must sit in run state and checkpoints (ADR 0002), so those fields are encrypted with a random per-run data key, stored only wrapped by a key-encryption key that the caller holds: the OS keychain locally, a KMS in Goodfetch Cloud. A checkpoint is useless without the caller's key, and a resumed run gets the key back over JSON-RPC. In a Daemon group, the key-encryption key and every rotating credential live in a Secret provider every Group member reaches, never the OS keychain or the local file (ADR 0055). Decided in [Security and compliance model](https://github.com/goodfetch/goodfetch/issues/73).
> Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): the run's bindings are the setting `secrets.<name>`, `{ reference, domains }` (with `totp` for a seed) or `{ code_source, domains }`, set at the connection, a Run or a Session by the program's own code, configuration or an Operator policy, never bound by a Recipe and never set by a Client acting for a model, as `session.http_credentials` and `proxy.server` with the proxy's credentials, which also send a reference's value; a program answers `caller:` references with `connect()`'s `resolveSecret`; and `GOODFETCH_TOKEN` holds a value, since references resolve in the engine it is needed to reach.

## Considered Options

- **Encrypting the whole SQLite file (SQLCipher)**: rejected. rusqlite supports it, at about 5 to 15% overhead, and it would also protect results, but DuckDB can no longer read run files, which ADR 0008 relies on, and the engine would move to a separate SQLite build. Results at rest are left to disk or volume encryption.
- **Secret values passed in code** (Browser Use's `sensitive_data`, which binds them to domains as ADR 0014 also does): rejected. The values end up in scripts and checkpoints. Browser Use offers 1Password only in its cloud; Skyvern keeps credentials in its vaults; Stagehand's `%var%` values reach Browserbase when its server cache is on.

## Consequences

- The data key is never written in clear into a checkpoint, an export or a log.
- Discarding a run destroys its data key, which crypto-shreds every secret left in its file, including bytes in SQLite free pages. The secret tables also use `secure_delete`, and browser profiles and temp files under the run's directory are removed. A Profile directory a run uses in place and a Borrowed browser are the person's own data: they keep what the run writes to them, and the reset gate neither removes nor scans them (ADR 0056). The permanent reset gate of ADR 0001 plants canary cookies, tokens and secret values, resets, scans every byte the container can reach on disk and in memory-backed directories, and requires zero hits; the next run must find no cookies, storage, cache, service workers, connection pools or DNS entries. The lab's leak (30 times out of 30 with a reused pool) is its regression fixture.
- Exports of results never contain session secrets. Moving a logged-in Session to another machine or into the cloud is a separate session export (an import bound to its machine cannot move, ADR 0056): a bundle encrypted with `age` to a public key or a passphrase, whose import needs the key and is recorded in the Audit log. A person may also export a Saved identity as a clear-text Playwright `storageState`, only in the Console or an interactive CLI prompt, never through an agent surface, and the export is recorded in the Audit log (ADR 0056). Saved identities (ADR 0035) are the one place Goodfetch keeps session secrets outside run state: a per-install store whose secret fields are encrypted under a key reached through a Secret reference, with every save, reuse, copy and delete recorded in the Audit log.
- Field encryption and `secure_delete` cost CPU and writes, so a run can switch them off (ADR 0016); the switch is recorded in the Audit log.

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-23, [#616](https://github.com/goodfetch/goodfetch/issues/616): `keychain:service/account` reaches the macOS login keychain and the Windows Credential Manager through keyring-core's stores, and Linux's Secret Service directly over zbus 6 (a `plain` session on the user's own bus, items found by their `service` and `username` attributes as `secret-tool` writes them; a locked collection is refused, never prompted for), because keyring-core's Secret Service stores still use zbus 5, whose split crates RustSec marks unmaintained. `run_state.key_reference` defaults to `keychain:goodfetch/run-state-key`, or to `secretfile:run-state-key` where the OS keychain does not open, which `config explain` shows at the default layer; a Run start resolves only a reference a layer set, and the default's item is made where run state first wraps a data key ([#617](https://github.com/goodfetch/goodfetch/issues/617)). The encrypted local file `secretfile:name` is `secrets/<name>.age` in Goodfetch home, age-encrypted (binary or armored) to an X25519 identity of `secrets/identity.txt`, refused unless only its owner may read that identity (no group or other mode bit on Unix; on Windows an access list granting only its owner, SYSTEM and Administrators), and a value's one trailing line ending is dropped.

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-23, [#617](https://github.com/goodfetch/goodfetch/issues/617): a Run's data key is made when the Run first seals a field (`Run::key`), not at its start, so a Run that seals nothing never reaches the keychain or the encrypted local file; it is wrapped with XChaCha20-Poly1305 under HKDF-SHA256 of the key-encryption key's text, the Run ID as associated data, and stored in run state's `run_key` table with the reference that wrapped it. The engine makes the default's item, 32 random bytes in Base64, where it is missing at that first seal, never on a resume, and never for a reference a person chose. Until the caller provider ([#652](https://github.com/goodfetch/goodfetch/issues/652)) answers `secrets.resolve`, "the key back over JSON-RPC" is the reference a Client sends in `run.resume`'s project configuration; once it lands, `caller:` carries the key itself. A resume whose reference gives no value fails with `secret_unavailable`, and one whose key does not open the data key with `run_key_mismatch`, an Error code of this decision's making; a cleared `run_state.key_reference` falls back to the host's default.

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, step 7 review finding 564-7 ([#617](https://github.com/goodfetch/goodfetch/issues/617)): `run_key_mismatch` stays. #617's criterion asks a resume without the key to fail "with a typed Error naming `run_state.key_reference`", and a moved Checkpoint whose host resolves its own default key gives a value that does not open the data key, which `secret_unavailable` (no value at all) cannot say; `run_key_mismatch` names the setting, the reference resolved and the one that wrapped the key. Spec [#564](https://github.com/goodfetch/goodfetch/issues/564)'s list of the Error codes its area adds should gain it (`UnavailableError`, not retryable).

> Note (agent decision, on a default, not read by the owner), 2026-10-26, [#647](https://github.com/goodfetch/goodfetch/issues/647): the external providers live in `goodfetch-secret-providers`, whose contribution each Product composition adds, and the engine builds each one for each Run from its resolved `secret_providers.<scheme>.*` (a setting key writes the scheme in snake case: `aws_sm`, `gcp_sm`, `azure_kv`). 1Password and Bitwarden run their vendor CLI (`secret_providers.<scheme>.command`); Vault and the three cloud managers call their HTTP API through the engine's own client as Operator-configured endpoints. Each takes its sign-in from the engine's environment, under the variable its vendor documents, so no setting holds a credential: AWS Secrets Manager signs `GetSecretValue` with Signature Version 4 from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`; GCP Secret Manager sends the access token in `GOOGLE_OAUTH_ACCESS_TOKEN`; Azure Key Vault gets a token from Microsoft Entra ID by the client-credentials grant for `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_CLIENT_SECRET`. Instance roles, workload identity, managed identity, profiles and service-account key files are not read yet.
