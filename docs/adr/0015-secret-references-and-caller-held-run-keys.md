# Secrets are references; run state encrypts only its secret fields, under a key the caller holds

A run never holds a raw credential in its code, configuration, Plan or state, only Secret references (`env:NAME`, `keychain:goodfetch/portal`, `op://vault/item/field`). A Plan or a prompt names a secret by its `%var%` placeholder (ADR 0014); the run binds each placeholder to a Secret reference and to the domains allowed to receive it, and a Secret provider resolves the reference at the moment of use. V1 ships these providers: environment variables, the OS keychain (through `keyring-core`), an encrypted local file for machines without a keychain, the caller over JSON-RPC (how Goodfetch Cloud injects a tenant's secrets without the engine storing them), 1Password, Bitwarden and Vaultwarden, HashiCorp Vault and OpenBao, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, and a custom HTTP provider (now a form of the Secret provider Plugin kind, ADR 0033). TOTP seeds, proxy passwords, sink and webhook secrets and model API keys all go through the same mechanism; where a vault generates TOTP codes itself, the seed never leaves it. What a run creates itself (session cookies, tokens, login state) must sit in run state and checkpoints (ADR 0002), so those fields are encrypted with a random per-run data key, stored only wrapped by a key-encryption key that the caller holds: the OS keychain locally, a KMS in Goodfetch Cloud. A checkpoint is useless without the caller's key, and a resumed run gets the key back over JSON-RPC. Decided in [Security and compliance model](https://github.com/Jbmanllr/automan/issues/73).

## Considered Options

- **Encrypting the whole SQLite file (SQLCipher)**: rejected. rusqlite supports it, at about 5 to 15% overhead, and it would also protect results, but DuckDB can no longer read run files, which ADR 0008 relies on, and the engine would move to a separate SQLite build. Results at rest are left to disk or volume encryption.
- **Secret values passed in code** (Browser Use's `sensitive_data`, which binds them to domains as ADR 0014 also does): rejected. The values end up in scripts and checkpoints. Browser Use offers 1Password only in its cloud; Skyvern keeps credentials in its vaults; Stagehand's `%var%` values reach Browserbase when its server cache is on.

## Consequences

- The data key is never written in clear into a checkpoint, an export or a log.
- Discarding a run destroys its data key, which crypto-shreds every secret left in its file, including bytes in SQLite free pages. The secret tables also use `secure_delete`, and browser profiles and temp files under the run's directory are removed. The permanent reset gate of ADR 0001 plants canary cookies, tokens and secret values, resets, scans every byte the container can reach on disk and in memory-backed directories, and requires zero hits; the next run must find no cookies, storage, cache, service workers, connection pools or DNS entries. The lab's leak (30 times out of 30 with a reused pool) is its regression fixture.
- Exports of results never contain session secrets. Moving a logged-in Session to another machine or into the cloud is a separate session export: a bundle encrypted with `age` to a public key or a passphrase, whose import needs the key and is recorded in the Audit log.
- Field encryption and `secure_delete` cost CPU and writes, so a run can switch them off (ADR 0016); the switch is recorded in the Audit log.
