# Security is on by default; compliance is off by default and switchable

Goodfetch must stay competitive with Crawlee and Spider, which ignore robots.txt by default, and it ships stealth and a Challenge solver, while still helping the users who want to be compliant. So the two kinds of control get opposite defaults. Security controls, which protect the user (Secret references, field encryption of run state, SSRF checks, the browser sandbox, endpoint authentication, release signing, redaction), are on by default. Compliance controls, which concern what the user collects and how (robots.txt, AI-use signals, personal-data notices), are off or advisory by default, can be switched on per run, and never block stealth or the Challenge solver. Every security control that costs speed or resources can be switched off per run: field encryption and `secure_delete` (ADR 0015), the resolved-IP check, the egress proxy of raw CDP sessions and the browser sandbox (ADR 0017), the Audit log's hash chain, and redaction (of logs, traces and HAR files, and the masking of screenshots and recordings). The V1 benchmark publishes what each one costs, and switching one off is recorded in the Audit log. Controls with no run-time cost cannot be switched off: secrets never reach the model, Plans, caches, the Effect journal or observations, endpoints require a token, releases are signed. Decided in [Security and compliance model](https://github.com/goodfetch/goodfetch/issues/73).

> Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): robots.txt and its Crawl-delay are no longer among the compliance controls that are off by default. Every crawl request obeys them unless a setting turns them off, and that setting is recorded. The parity with Crawlee and Spider argued above did not hold against site owners' reports. The AI-use signals and personal-data notices stay as this ADR set them.

## Considered Options

- **Respecting robots.txt by default** (Firecrawl, and Scrapy's project template): rejected, because it would block collection that Crawlee and Spider, which ignore robots.txt by default, allow.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): adopted for crawl requests. A program's own navigation stays ungated.
- **Honouring the signals of the declared Purpose by default, but not robots.txt**: rejected for the same reason; nothing is enforced until the user switches it on.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): still rejected, for another reason: a Purpose left at its default `search` is not a declaration to judge the signals against. robots.txt is now obeyed by default for crawl requests.
- **A logged confirmation before stealth on personal data for AI training**, the R&D's working view after the CNIL guidance: reduced to a notice, under this rule.

## Consequences

- Every run declares a Purpose: `search` by default, or `ai-input`, `ai-train` or `collect`. The engine always reads robots.txt, Content Signals, IETF aipref (honoured even while still a draft) and TDMRep, and records them with the Purpose in Provenance. One `respect_site_preferences` switch, off by default, turns on robots.txt with its crawl-delay and the signals that apply to the Purpose. Ignoring them while the switch is on is an explicit, recorded override.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the switch is `site_preferences.respect_use_signals` and covers only the AI-use signals and RSL. robots.txt and its Crawl-delay have their own setting, `site_preferences.respect_robots_txt`, on by default for crawl requests. `site_preferences.max_crawl_delay` (30 s) bounds the Crawl-delay a crawl waits out.
- A run or a schema can mark fields as personal. The engine then shows the relevant notice once (such as the CNIL measure for AI training) and records it, applies a Dataset's retention period itself, offers an erasure operation across a run's Datasets, Baselines and checkpoints, and flags personal columns in exports. Nothing is blocked.
- An Audit log, separate from the Effect journal, records each use of a Secret reference (never its value), confirmations, every override (Site preferences ignored while the switch is on, security switches off, private addresses allowed), the use of stealth, raw CDP attaches, Human pause actions and endpoint authentication failures. It is append-only and hash-chained so that an edit or a deletion shows, exported as JSONL and as OpenTelemetry events, and kept as long as the user decides (in a Daemon group, one chain kept by the Lead Daemon, ADR 0055); the docs note that the EU AI Act asks deployers of high-risk systems to keep logs for at least six months.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): it also records each politeness or robots.txt value that presses a site harder than its built-in default, once per run, with its layer.
  > Note (agent decision, pending owner review), 2026-10-24, [#613](https://github.com/goodfetch/goodfetch/issues/613): `audit.export` answers every entry with its `hash`, and the CLI's hand-written `audit export` writes them as JSONL, one entry per line with its `hash` beside the entry's fields; `audit verify --file` verifies such an export in the CLI's own process, from its first line (an export has no head file, so its tail is its last line). `audit.retention` (milliseconds, unset by default) and `audit.otlp` (off) are machine settings, user configuration and Operator policy only, since the log is per user. Each append first prunes the entries older than the retention from the beginning only: they give way to an anchor entry, kind `audit_log_anchor`, at the last pruned sequence, whose hash is that entry's and whose `details.last_pruned_hash` repeats it, and a chained pruning record, kind `audit_log_pruned`, is appended with `through_sequence`, `last_pruned_hash` and `retention`; verification starts from the anchor and reports it broken unless it is exactly the anchor the last pruning record names, so a rewritten or moved anchor shows. The OpenTelemetry events go to a new machine setting, `otlp.logs_endpoint` (OTLP/HTTP logs, unset by default), read when the process starts: each entry the engine appends is the event `goodfetch.audit`, its exported line as the body and `goodfetch.audit.sequence`, `.kind` and `.hash` as attributes.

  > Note (agent decision, pending owner review), 2026-10-28, step 7 review findings 563-565-7 and 563-565-8 ([#613](https://github.com/goodfetch/goodfetch/issues/613)): `otlp.logs_endpoint` stays: #613's criterion sends each entry as an OpenTelemetry event "while `audit.otlp` is on and OTLP export is configured", events travel on OTLP's logs signal, and area 3 has only a traces and a metrics endpoint, each a full signal URL that a logs exporter cannot reuse; area 3's spec and ADR 0132's note should list it beside them. `audit.retention` and `audit.otlp` stay machine settings (`Authority::Machine`: user configuration and Operator policy): the Audit log is the user's, one per Goodfetch home, so a project configuration's value would be accepted and never read, which `setting_not_applicable` says instead. Spec #564's table writes "configuration" for the `daemon.*` keys too, which are machine settings as well.
- Switching redaction off lifts ADR 0014's guarantee for logs, traces, HAR files, screenshots and recordings kept as outputs only; secrets still never reach the model, Plans, caches, the Effect journal or observations, so screenshots in observations and vision steps stay masked.
- ADR 0028 lets an Operator policy or a Recipe cap or lock these switches; where nothing locks them, a run can still switch them.
  > Note (agent decision, pending owner review), 2026-10-24, [#614](https://github.com/goodfetch/goodfetch/issues/614): each switch is a boolean `security.*` setting, on by default and settable at every layer: `security.field_encryption`, `security.secure_delete`, `security.resolved_ip_check`, `security.raw_cdp_egress_proxy`, `security.browser_sandbox`, `security.audit_chain` and `security.redaction`. A Recipe caps one by declaring it on, or by exposing it held to `true`; an Operator policy locks it with `[lock]`. A composition registers the keys it reports (`Contribution::with_control`; the engine registers the seven). A new Run whose settings switch one off records one chained `security_switch_turned_off` entry per control, after the Run is created, with details `{setting, value}` and the layer that set it; it logs one warning per control and lists the control in `weakened`. A start that answers an existing Run records nothing again. With `security.audit_chain` off, the Run's entries, from its key reference's use on, are marked `chained: false` and hashed alone (`SHA-256` of 32 zero bytes and the entry's canonical JSON). Verification checks each such entry's place and its own hash, and continues the chain from the entry before it, so an entry of the chain turned unchained breaks the chain at the next chained entry. A failure to record the switch is logged as an error, and the Run goes on. A resumed Run's entries are chained again: unchaining on resume is left to a later ticket.

  > Note (agent decision, pending owner review), 2026-10-28, step 7 review finding 564-5 ([#614](https://github.com/goodfetch/goodfetch/issues/614)): a resume whose settings switch `security.audit_chain` off writes the Run's entries unchained from the resume on, its key-encryption key's use included, and a failed resume chains them again; the entries it wrote while its chain was on stay chained. A start with no Run ID of its own whose settings switch the chain off takes its generated Run ID before its key-encryption key resolves, so that first entry names the Run and is unchained too.

  > Note (agent decision, pending owner review), 2026-10-28, step 7 review finding 564-6 ([#619](https://github.com/goodfetch/goodfetch/issues/619)): a Run's `inputs` and `tags` pass through the `Mask` before run state and the Run index keep them, as every other writer's values do: a start masks each input value and each tag, a tag cut to its 128 characters once masked, so a secret a program passes in either never reaches `run.sqlite`, the Run index or `run.list`. A start again with the same Run ID compares its inputs both masked and as given, and counts an input as different only when it differs both ways, so a value the Mask stopped holding since is no conflict. What was written before the Mask learned a value is not rewritten.
- Later decisions inherit this rule, in particular ADR 0035 and [Adopt site-access decisions](https://github.com/goodfetch/goodfetch/issues/76).
- ADR 0033's Plugin confinement is not one of these switchable controls: no run, Recipe or setting can turn it off. Each run reports which Plugins ran at which network level and, where Operator policy allowed reduced confinement for a first-party Plugin, which parts the host could not provide.
- Third-party patched browser binaries that Goodfetch cannot reproduce are not one of these switchable controls either: the engine refuses them unless Operator policy allows them per digest, and each allowance is recorded in the Audit log and marks the results (ADR 0035).
- TLS verification is not one of these switchable controls: it stays on everywhere except for the per-domain exceptions of ADR 0042, which are pinned and audited. The egress proxy switch covers only its tunnelling of raw CDP traffic, never the relay that carries certificate exceptions or local addresses (ADRs 0042 and 0044). Nothing about the user or their runs leaves the machine unless configured, and there is no telemetry (ADR 0043). RSL joins the Site preferences that are always read (ADR 0045). The erasure operation also removes matching Response cache entries (ADR 0046).
- Never evading a consent wall (ADR 0048), like never evading `payment_required` (ADR 0045), is not one of these switchable compliance controls: a wall is a condition the site set for access, which blocking or hiding would get around. Its wall test, the forced-tier browser sample included, cannot be switched off. It never stops stealth or the Challenge solver, which a wall does not involve. The one exception is the Wall allowance (ADR 0052), which only a person grants, for the domains that person lists; it never covers `payment_required`.
