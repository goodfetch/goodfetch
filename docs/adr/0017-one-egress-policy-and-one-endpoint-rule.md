# One egress policy for every request, one rule for every listening endpoint

The engine sorts outgoing connections into two classes. Addresses a page can reach (start URLs, redirects, discovered links, browser subresources, workers, WebSockets) may not reach private, loopback, link-local, cloud-metadata or IPv4-mapped ranges unless a run allowlists them for tests or an intranet. The check is made on the IP resolved at connect time, so that on a direct connection DNS rebinding cannot slip through. Endpoints the operator configures (sinks, webhooks, Model providers such as Ollama on localhost, vaults, proxies) may use private ranges locally. Goodfetch Cloud switches on a "no private endpoints" policy that forbids it, which is what stops a tenant's webhook URL from reaching the cloud's internal network (Firecrawl's CVE-2025-57818). Every endpoint the engine opens (MCP Streamable HTTP, the JSON-RPC daemon, the Console, the live view, raw CDP) binds to loopback by default, checks `Host` and `Origin`, and requires a per-launch random token; remote exposure needs TLS and a token, and OAuth 2.1 for remote MCP as the MCP specification defines. The engine reaches its own browsers over a pipe, never a debugging port. Decided in [Security and compliance model](https://github.com/goodfetch/goodfetch/issues/73).

## Considered Options

- **Refusing private addresses on redirects only, by host name** (Spider): rejected. It never checks the start URL and does not resolve DNS. Firecrawl shows what slips through: SSRF through redirects (CVE-2024-56800), through webhook URLs (CVE-2025-57818) and through a redirect bypass (CVE-2026-32857).
- **One class for every connection**: rejected. Blocking private ranges for operator endpoints would break local models and local sinks; allowing them for pages would let a page reach cloud metadata.
- **Exposing Chrome's debugging port for raw CDP**: rejected. An open port lets any local process drive the browser and read its cookies; infostealers did exactly that, which is why Chrome 136 stopped allowing the port on the default profile.
- **Endpoints without Origin checks or tokens on loopback**: rejected. MCP Inspector's remote code execution (CVE-2025-49596) and the TypeScript MCP SDK's rebinding protection being off by default (CVE-2025-66414) came from trusting loopback.

## Consequences

- Webhooks follow the Standard Webhooks specification: `webhook-id` carries the delivery ID of ADR 0008, the run epoch is a field of the signed body (the specification signs only the ID, the timestamp and the body), HMAC-SHA256 (`v1`) is the default and ed25519 (`v1a`) an option, several signatures allow secret rotation, receivers reject timestamps more than five minutes off, and the Rust crate and the TypeScript and Python SDKs ship verification helpers.
- A raw CDP client can switch off the engine's interception (ADR 0014), so a Session with raw CDP attached sends its traffic through an engine-owned egress proxy that enforces the SSRF and domain policy at the network layer and only tunnels, leaving the TLS fingerprint unchanged. While a raw client is attached, the engine refuses to type secrets, results are marked unguarded in Provenance, and the Session never goes back to a Session pool by itself, though it can be saved explicitly. The raw CDP token is per Session, short-lived and revocable, and every attach is recorded in the Audit log. An attach opened by a handler gets its own token, bound to the work item's lease (ADR 0003). On a Borrowed browser no egress proxy can be put under the running browser, so the policy is enforced by interception, with each host resolved in the engine and private ranges blocked; the DNS-rebinding gap that leaves is recorded in Provenance (ADR 0056).
  > Amended by [ADR 0089](0089-a-page-is-lent-through-an-endpoint-that-shows-only-its-session-and-collie-joins-other-crawlers-by-borrowing.md): a raw CDP client of a Lent page reaches a browser that shows only that page's Session, with a token for that attach alone, which narrows the per-Session token for every lend; its endpoint refuses new browser contexts (which could carry their own proxy), extensions, ignoring certificate errors and, on a Daemon with accounts and in Goodfetch Cloud, reading files on the browser's machine by path; downloads stay the Run's; and when the attach ends the engine closes the pages the client created and the popups opened from them, leaves popups of the lent page as Pages of the Session, and re-applies the Session's own state.
- Chromium's sandbox stays on: the engine never passes `--no-sandbox` by default, and the official images run as a non-root user with a published seccomp profile. Playwright's image runs as root, which disables the sandbox, and its docs warn against it for untrusted sites.
- When a Session goes through an upstream proxy, the proxy resolves DNS, so the engine checks the host name and any literal IP, resolves the name itself before sending, and refuses a private result. A name that resolves differently for the proxy can still slip through; this matters when the proxy runs on the engine's own host or network, and the docs tell such deployments to block private ranges at the proxy. The local lookup is part of the resolved-IP check, so it is switched off with it.
- The resolved-IP check, the egress proxy and the sandbox can be switched off per run under ADR 0016, and each switch is recorded in the Audit log. Endpoint tokens cannot be switched off. ADR 0031 adds per-person accounts and scoped, expiring program tokens beside them on a shared or exposed Daemon, and a persistent per-user protocol token for a socket-activated Daemon.
- The Console is served by the Daemon or by an Attached engine (ADR 0024), under this rule. The Daemon's JSON-RPC socket carries no HTTP headers, so in place of the `Host` and `Origin` check it closes any connection whose first message is not a `hello` carrying the token (ADR 0024).
- ADR 0033 applies the two classes to Plugins per destination. For a third-party Plugin, an endpoint it names or returns is operator-configured only when it matches a value set in Operator policy or user and project configuration, or a Recipe or run value that Operator policy allows; domains its manifest declares and defaults it ships are checked as addresses a page can reach. A first-party Plugin's endpoints count from any layer, as a built-in Sink's do. A run's private-range allowlist and a switched-off resolved-IP check never apply to traffic the engine carries for a Plugin, except a fetch backend's connection to the target the engine handed it (for a third-party backend, only when Operator policy allows it); link-local and metadata ranges are refused for that traffic; and the per-instance Plugin proxy follows this endpoint rule. At ADR 0033's `direct` level, where the Plugin opens its own sockets, none of this is checked locally on Linux and macOS beyond the configured destinations; on Windows, `direct` in an AppContainer needs the filter broker, which refuses link-local, metadata and other private ranges. Bridge Sinks, which run in a container runtime, get no broker filters on any OS.
- The egress proxy gains a terminating mode for hosts with a certificate exception (ADR 0042) and carries browser Sessions bound to a local address (ADR 0044). Switching off the egress proxy covers only its tunnelling of raw CDP traffic, never those two roles.
- A Filter list URL set through `filter_lists.extra` follows the rule above for Plugin endpoints: it may use a private range only when set in Operator policy or user and project configuration, or by a Recipe or run value that Operator policy allows (ADR 0047).

> Note (agent decision, pending owner review), 2026-10-22, [#621](https://github.com/goodfetch/goodfetch/issues/621): the resolved-address check is `goodfetch-engine`'s `egress::classify` over the table `xtask codegen` writes into `goodfetch-protocol` (`generated/special_purpose.rs`) from IANA's special-purpose registries, now committed beside it in `crates/goodfetch-protocol/iana/` with their date. It fails closed where the registries leave a block unmarked: a terminated block (`192.88.99.0/24`) is refused, and so are IPv4 multicast and every IPv6 address outside global unicast (`2000::/3`), which covers site-local and the deprecated IPv4-compatible form. A local-use NAT64 address (`64:ff9b:1::/48`) is read at each prefix length RFC 6052 allows within it (96, 64, 56, 48) and a Teredo address by both its server's and its client's IPv4 address; the first reading a page may not reach refuses it. A URL whose host carries a zone ID, which the WHATWG parser refuses, is refused as `private_address` naming the address. The engine's HTTP client judges every address of the host before connecting, the `resolve` mapping's included, and races only those, so a name with one private answer is refused and a later rebinding answer is judged on its own connection. Until #622 declares `egress.private_ranges`, a Session lists its ranges only through `Policy::with_private_ranges` (CIDR blocks or single addresses; a metadata address only by its exact address), which the tests that reach the Proving ground's loopback address use.

> Note (agent decision, pending owner review), 2026-10-23, [#631](https://github.com/goodfetch/goodfetch/issues/631): in a browser, every hop of a navigation is judged again. A hop to HTTP is judged at the interception's step 3 as its request leaves, a 3xx's, a refresh's and a script's alike. A hop the browser sends no request for is judged where it shows: a document's 3xx response now always pauses at the interception's response stage, and one whose `Location` names a scheme other than `http`, `https`, `ws` and `wss` is failed with `egress_refused` (`rule: "scheme"`); a navigation the page schedules for its main frame (`Page.frameScheduledNavigation` or `frameRequestedNavigation`) to such a scheme leaves `egress_refused` for the navigation call waiting on the page, or else its next call, except `javascript:` (it runs in the page's own frame, whose origin the policy allowed), `about:` and `blob:` (documents of the page's own, reaching no network). `page.goto` judges its URL's scheme first (`egress::navigation`): HTTP's go on to the interception; `about:blank` loads nothing and is allowed; `javascript:` runs only when the policy allows the main frame's document (its unreachable URL on the browser's error page), else `egress_refused` naming the `javascript:` URL, and answers no response; `file:`, and any other scheme (`data:`, the browser's own `chrome:` pages), is loaded only for the program's own code or the CLI, never for a Client acting for a model, a Recipe's Run or an engine with accounts (none has accounts before area 12), which get `egress_refused` (`rule: "scheme"`, no `setting`); while such a call goes on the main frame's `file:` hops pass step 3 as the call's, and a `file:` subresource of any page stays refused. The browser layer has no resolved-address check until the egress relay ([#634](https://github.com/goodfetch/goodfetch/issues/634)): the SSRF table's redirect cases to a private address run on Chromium under a domain policy that refuses their target until then.

> Note (agent decision, pending owner review), 2026-10-24, [#623](https://github.com/goodfetch/goodfetch/issues/623): the upstream proxy path is built in the engine's own HTTP client (`goodfetch-engine`'s `http_client`, `PageTraffic.proxy`). Before anything goes to the proxy, the engine judges the URL, resolves the host itself (the `resolve` mapping first, then the resolver) and judges every answer as on a direct connection; only then does it send a plain `http://` request to the proxy in absolute form, or open a `CONNECT` tunnel for `https://`. The proxy then resolves the name again itself, so a name it resolves differently is not caught, as this ADR says. The proxy's own address is an Operator-configured endpoint and is not judged. The proxy's answer to the tunnel is read only in `http_client::tunnel`, the translation point ADR 0127 names: a 407 is `proxy_auth_failed`; a 429 and a 502 have their own variants (ADR 0053's ceiling reads them) and are `proxy_unavailable`; a proxy that cannot be reached and any other answer are `proxy_unavailable` too. The egress relay ([#634](https://github.com/goodfetch/goodfetch/issues/634)) chains browser Sessions through an upstream proxy and reuses this path. Until it lands, a browser Session's `proxy.server` is still held by interception alone.

> Note (agent decision, pending owner review), 2026-10-24, [#627](https://github.com/goodfetch/goodfetch/issues/627): the two classes are `goodfetch-protocol`'s `EgressClass`, and every kind of Operator-configured endpoint is a row of its `CONFIGURED_KINDS` table: Model provider, Secret provider, proxy, Notification webhook, OTLP, Plugin index, `cdp_url` and, for ADR 0047, a Clean-up rules source; each is Operator-configured when the Operator policy or user or project configuration sets it, and a `cdp_url` from a Recipe or a run is an address a page can reach unless the Operator policy allows it (ADR 0056, read where `cdp_url` is built). A test holds every module that calls the engine's own HTTP client to a pinned download or one of these kinds. `egress.no_private_endpoints` (boolean, `false`) is set only in an Operator policy; elsewhere it is `setting_locked`. With it off an endpoint reaches any address; with it on every address that is not globally reachable is refused, by the same classification as a page's, with no `egress.private_ranges` exception and a zone ID refused, as `egress_refused` (`rule: "private_address"`, `setting: "egress.no_private_endpoints"`) before any connection. No run's domain policy applies to an endpoint; its URL is refused only for a scheme other than HTTP's. The first endpoint built on the engine's client is the OTLP collector (`goodfetch-engine`'s `otlp`, used by both executables' span and metrics exports in place of ureq): each export judges the collector's addresses again, and a refused export is logged by the exporter while the run goes on. The SSRF case table's `operator_endpoint` family holds the endpoint rows; Notification webhooks and Sink webhooks add their own `kind` when they are built. Rule sources and pinned downloads still connect without this class's check.

> Note (agent decision, pending owner review), 2026-10-25, [#630](https://github.com/goodfetch/goodfetch/issues/630): the endpoint rule is `goodfetch-engine`'s `endpoint` module. It makes every listener's token (`new_token`: 32 bytes of the OS generator, in hex), compares tokens with `subtle`'s constant-time equality, checks an HTTP request's `Host` (an IP address or `localhost`), and records each refusal of the Daemon's socket and WebSocket, an Exposed Daemon, an Attached engine's private endpoint and the ops listener as an `endpoint_authentication_failed` Audit log entry, `{listener, reason}`, actor `engine`, beside its `warn` record under `goodfetch::rpc::refusal`; the Console's refusals keep their sign-in driver's entries. Neither holds a token. A listener keeps no token it no longer takes, so an expired, revoked or out-of-scope token is recorded as `token_wrong`. The endpoint table's rows for them use what each M1 listener has: a token expires with the launch that issued it (the Daemon's `daemon stop`, an ended Attached engine), is revoked when `daemon restart` or the operator's new `ops.token` replaces it, and is scoped elsewhere when it is the same Daemon's ops token on its socket or its protocol token on `/metrics`. A missing `Origin` is accepted on the ops listener with a bearer token and refused (401) when the token comes only as a cookie. The regression tests of CVE-2025-49596 and CVE-2025-66414 run the table's rows that cite them (`advisories`).

> Note (agent decision, pending owner review), 2026-10-25, [#634](https://github.com/goodfetch/goodfetch/issues/634): the egress relay is `goodfetch-page`'s `egress_relay` module. Each browser Session the engine launches gets one while `security.raw_cdp_egress_proxy` is on: a loopback HTTP proxy on port 0 that its browser context takes as `proxyServer` (loopback included), with the Session's own credentials (user `goodfetch`, a 256-bit token), which the interception gives at `Fetch.authRequired`; any other client gets a `407` and no relayed byte, logged under `goodfetch::rpc::refusal` (its Audit log entry and endpoint-table column are [#1593](https://github.com/goodfetch/goodfetch/issues/1593)'s). For each `CONNECT` and absolute-form request the relay judges the host by the domain policy, so WebSockets and WebRTC over TCP are held there too and the proxy auto-config script is passed only with the switch off, then resolves the name itself and judges every answer before connecting to those addresses alone; a refused tunnel gets the relay's `403` with `Proxy-Status: goodfetch-relay; error=destination_ip_prohibited` (or `http_request_denied`), a refused plain request a closed connection with no answer made up, and each refusal is recorded in the Run trace as `page.request_failed` and raised as `egress_refused` by the navigation it failed, or the page's next call. A plain request goes on in origin form with `Connection: close`, so each connection carries one judged host. A site the relay cannot reach itself (no address, a refused or timed-out connection) is answered as a refusal is, and the failure is reported by the browser's own name for it (`net::ERR_NAME_NOT_RESOLVED`, `net::ERR_CONNECTION_REFUSED`), in the navigation's error and the page's `requestfailed` event, as Playwright reports it, never as the relay's answer (`net::ERR_TUNNEL_CONNECTION_FAILED`). A Session's upstream proxy is chained: an HTTP proxy by `CONNECT` (absolute form for plain HTTP) with its credentials sent by the relay, its answers passed to the browser without their body, a SOCKS5 proxy, or the Session's SOCKS5 relay, by a no-credential SOCKS5 `CONNECT`; the proxy is given the name, judged first, as #623's client does. An `https://` proxy is not chained (the relay speaks no TLS to proxies): such a Session, one with the switch off and one on a Borrowed browser are held by interception alone, and Provenance records `egress: interception_only` with the `dns_rebinding` gap; a relayed one records `egress: egress_relay` with the relay's address. Until [#622](https://github.com/goodfetch/goodfetch/issues/622) lets tests list `egress.private_ranges`, the relay does not judge the Run's `network.resolve` mapping's answers, which Chromium took unjudged before (every Proving ground test reaches loopback through it); `localhost`, literal addresses and every name the resolver answers are judged.

> Note (agent decision, pending owner review), 2026-10-25, [#622](https://github.com/goodfetch/goodfetch/issues/622): `egress.private_ranges` (`goodfetch-protocol`'s `egress::private_ranges`, a list, empty by default) takes CIDR ranges, single addresses and host names. A range or address lets any connection of the Run use the addresses it covers; a host name lets that host's own connections (not its subdomains') use any address that is not globally reachable. A cloud-metadata address is reached only through an entry that is that address alone, never through a range or a host name. It is set by the program's own code, configuration and the Operator policy; a Client acting for a model is refused with `setting_locked`, and so is a Recipe unless the Operator policy sets `egress.recipe_private_ranges` (boolean, Operator policy only, `false` by default) to `true` (catalog authority `not_by_model_recipe_allowed_by_operator_policy`). A Run that lists any entry writes one chained `private_addresses_allowed` Audit log entry at its start, `{setting, ranges}`, and its Run report lists the setting in `weakened` (no warning). `security.resolved_ip_check` off makes `judge_addresses` judge nothing for that Run (the engine's client, the egress relay and a Borrowed browser's interception), while ADR 0056's `cdp_url` rules still judge. The egress relay now judges the Run's `network.resolve` mapping's answers as any other, so tests that reach the Proving ground list its mapped host names in `egress.private_ranges`, the check left on, and `localhost` and literal loopback addresses stay refused. Foxhound's HTTP tier (spec [#565](https://github.com/goodfetch/goodfetch/issues/565)'s story 102) judges the mapping's answers the same way: its transports' lookups judge them, a host-name entry opening that host's own connections.
