# The browser driver is direct CDP with the Goodfetch guard, and the guard is its own reference

The engine drives Chromium-family browsers through an in-house Rust CDP client over a pipe and checks every action with the Goodfetch guard: page scripts that require the target to be unique, visible, enabled, stable and not covered, then cancel any event that reaches another element and replay the gesture until the deadline. The guard never let a wrong action through: 390 of 390 cells on Chromium, WebKit and Firefox, under Linux and macOS for the first two and under Linux for Firefox, whose Playwright build does not start on macOS 27 ([cross-engine report](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/cross-engine-2026-10-09.md), [driver contracts](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/browser-driver-contracts-2026-10-08.md)). Its own conformance matrix, not another driver, is the reference the lab gate reads: native Playwright, the previous reference, let a click through on a still-moving target (cross-engine report) and timed out twice at 100 ms of latency, which left the verdict blocked ([quiet-host report](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/quiet-host-2026-10-10.md)). Decided in [Adopt site-access decisions](https://github.com/goodfetch/goodfetch/issues/76).

## Considered Options

- **Playwright as the default driver or as the reference**: rejected. On the same machine guarded CDP takes 21 to 33% longer than Playwright on forms and clicks, but from 20 ms of driver-to-browser latency guarded CDP is 16 to 32% faster, and Playwright is not exact when remote.
- **Stagehand v4's model, a CDP runtime inside a Chrome extension**: rejected. It saves the round trips between a distant SDK and the browser, which the engine and the Browser host (ADR 0022) already avoid by running beside the browser. It needs `--enable-unsafe-extension-debugging`, reaches the browser through a debugging port, which ADR 0017 forbids, and enables `Runtime`. Its click checks nothing and acts on the first match ([Stagehand migration guide](https://github.com/browserbase/stagehand/blob/f261c38/packages/docs/v4/migrations/playwright.mdx)); in the lab, native Stagehand failed every actionability variant but the plain one. Its published "2x faster than Playwright" rests on one 50-action run on a remote browser (1.59x).
- **Chromey or Chromiumoxide**: rejected. Neither can send commands into cross-origin iframes, both trail Chrome by about ten versions, and the guard would bypass their APIs anyway ([Rust CDP client options](https://github.com/goodfetch/goodfetch/issues/67)).

## Consequences

- The client never enables the CDP `Runtime` domain, a known automation signal ([stealth research](https://github.com/goodfetch/goodfetch/issues/64)); the guard runs in an isolated world. The client still needs per-command timeouts, crash and detach handling, out-of-process iframe tracking and reconnect.
- Speed target: one round trip to check and arm, no stability wait for an element with no running animation or transition (the interception listener already cancels a click that lands elsewhere), and input sent as one burst. The guard must stay at 390 of 390 and be no slower than Playwright on the lab's click and form tasks on the same machine. The [V1 benchmark](https://github.com/goodfetch/goodfetch/issues/79) measures it on the reference host; a miss reopens this decision with the numbers.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#700](https://github.com/goodfetch/goodfetch/issues/700): on Chromium the guard runs in a world `Page.createIsolatedWorld` makes in the page's main frame, made again after a navigation, and is called with `Runtime.callFunctionOn` on that world's context, which needs no `Runtime.enable`. One call checks and arms: it observes the target once a frame (or every 20 ms) until it holds, then arms the listener on the window for a pointer action, or focuses the field for a text action, and answers; it waits at most 1 s in the page before it answers, so a navigation or the call's cancellation is seen, and the engine calls it again until `timeout.action`. Stability compares the target's box between two frames only while an animation or a transition that affects it runs; a target a script moves is caught by the listener instead. A second call disarms and says where the gesture landed; an arm whose call was dropped removes itself at the next check or after 10 s. Pointer input is `Input.dispatchMouseEvent` (move, press, release at the box's centre), text is `Input.insertText` over the field's selected text, and keys are `Input.dispatchKeyEvent`, all trusted. The gungraun benchmark `goodfetch-page`'s `check_and_arm` counts the engine's side of the round trip (the command, the CDP connection and the answer's reading); the browser's side is the V1 benchmark's.
  > Note (agent decision, pending owner review), 2026-10-23, [#703](https://github.com/goodfetch/goodfetch/issues/703): a page's console messages and uncaught exceptions, ADR 0085's `console` and `pageerror` events, come only from the `Runtime` domain. The engine enables it on a page once a `page.on` call listens to either, an opt-in exception like those below, and never otherwise, so a program that does not listen keeps the page free of `Runtime`'s side effect; what the browser replays from before that call is passed over. A call on the page sent after such a `page.on` waits until the browser answered its `Runtime.enable`, within that command's limit, so what the call makes the page log is read live, never from the 1,000 messages V8 keeps while `Runtime` is off ([#2224](https://github.com/goodfetch/goodfetch/issues/2224)); the wait is on the browser, never on a Client (ADR 0024).
- The guard can be switched off per run or per call (ADR 0023); actions taken without it are marked unguarded in Provenance.
- Firefox and WebKit run through Playwright's driver process, with the same guard injected, and only when a run asks for that browser. Crawlee offers them through Playwright; Stagehand, Browserbase, Browser Use and agent-browser are Chromium-only. A native WebDriver BiDi path for Firefox can replace Playwright later without changing the API, for stock Firefox only: ADR 0035 keeps Camoufox on Playwright's driver and Juggler, which its isolation depends on.
- The TypeScript and Python SDKs ([SDK binding and distribution strategy](https://github.com/goodfetch/goodfetch/issues/75)) offer Goodfetch's own page API, shaped like Playwright's (`goto`, `locator`, `getByRole`, `click`, `fill`, `evaluate`), which waits through the guard and refuses ambiguous targets. Each Playwright call in the parity list maps to it or is excluded with a reason. Existing Playwright or Puppeteer code attaches through the engine's raw CDP endpoint under ADR 0017's rules; that endpoint must be a WebSocket, because Playwright's `connectOverCDP` cannot attach over a pipe.
  > Amended by [ADR 0089](0089-a-page-is-lent-through-an-endpoint-that-shows-only-its-session-and-collie-joins-other-crawlers-by-borrowing.md): a page is lent to Playwright, Puppeteer or Browser Use through `page.lend()` and per-library helpers, as a Lent page whose endpoint shows only that page's Session. The endpoint stays a WebSocket by choice: since 1.61, Playwright's Node `connectOverCDP` also takes a transport, but Python, Browser Use and engines on another machine need an address, and one path is tested.
- By default on Chromium, the engine's only calls into a page's main world are a consent vendor's own API, called without enabling `Runtime` (ADR 0048); everything else, the guard included, stays in isolated worlds. On Firefox and WebKit, Playwright's only public route into its utility world is a `contentScript` selector engine, which the Site access spec proves; where it cannot, the guard and the runner act from the main world, marked. The opt-in exceptions, each marked, are ADR 0047's page scriptlets, ADR 0035's `js-injection` Fingerprint method and the user's own `evaluate` and init scripts.
  > Amended by [ADR 0121](0121-service-workers-run-under-the-engines-interception-the-back-forward-cache-is-off-locators-reach-closed-shadow-roots-and-a-read-never-scrolls-a-list.md): on WebKit, where Playwright's driver reaches no browser switch for service workers, `browser.service_workers: block` is Playwright's init script that stubs `register`; it is a main-world injection, and the Session is marked in Provenance as the actions above are. On Chromium and Firefox, `block` injects nothing.
- When live hiding hid an action's target, the guard lifts the matching rule for that Session and retries, recording the rule in Provenance; this is never Drift. On Firefox and WebKit, live hiding with `auto` happens only when the guard finds a target covered by an element a rule matches (ADR 0047).
