# Fetch tiers are chosen per route by comparing a sample with the browser

The engine fetches each page through one of four tiers: HTTP; a discovered API, which replays the JSON calls captured while the browser loaded a sample; the browser; and browser-fetch, HTTP sent from inside the Session's browser so that its identity does not change. It chooses per route by fetching a sample both ways and comparing the results with the browser's, and a declared total that no longer matches invalidates the choice. In the lab, the compared sample was exact on 120 of 120 runs and cost 0.004 of the browser's time on a static page, and the discovered API was exact on 120 of 120 and cost 0.008 of the browser's time on GraphQL and infinite scroll ([portal report](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/portal-2026-10-09.md), [quiet-host report](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/quiet-host-2026-10-10.md)). Decided in [Adopt site-access decisions](https://github.com/goodfetch/goodfetch/issues/76).

> Amended by [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md): its "route" is a Label on one domain (ADR 0004's key), which area 6's spec may split by URL path where a Label's samples disagree. A handler gets Collie's page on every tier: every tier but `browser` serves what it can exactly (the document over `http`, `browser_fetch` and `discovered_api`, which also serves network waits from its replayed calls; scripts without layout over `light_browser`, the Lightpanda tier), and a call it cannot serve, a wait for content a static document lacks, or a failed expected page escalates the request to `browser`.

> Amended by [ADR 0103](0103-a-handler-pushes-records-staged-with-its-attempt-into-datasets-its-crawl-declares-and-a-reader-never-slows-the-crawl.md): a sample comparison compares what each attempt staged, before any "Record before commit" Hook: its Records and its enqueues, weighed as area 5's spec says. The browser's attempt, the reference, is the one that commits, whether the two match or not; where the comparison also runs with Filter-list blocking off (ADR 0047), the browser attempt whose blocking setting the route keeps commits. Every other attempt is discarded.

> Amended by [ADR 0118](0118-every-fetch-tier-follows-redirects-as-the-browser-does-fails-a-cut-body-and-resends-only-what-a-site-never-processed.md): a sample whose browser attempt ended on another URL than the other tier's attempt never matches, so a page that redirects by script keeps its Label on the browser on that domain. Every tier follows the same redirects and refresh stubs, so a chain alone never makes two attempts differ.

> Note (agent decision; its sampling rule (a Label on a domain, `fetch.sample.count` samples, exact equality of Records and enqueues, a new sample after `fetch.sample.refresh_after`) accepted by the owner on 2026-11-10 in the grilling of decision G-04 of the consolidated review, Q7, its other parts pending owner review), 2026-10-26, [#768](https://github.com/goodfetch/goodfetch/issues/768): as built in `goodfetch-crawl`'s `tier_choice`. **Weighing:** each Record is its Dataset's name and its data, every string (keys too) in NFC with each run of Unicode whitespace one space and none at either end, compared as RFC 8785 canonical JSON, the two runs' Records as sorted multisets; enqueues are the Frontier identities (`visited`) of the requests each run's staged admissions added, a duplicate not among them, seeds a handler added included; "ended on another URL" compares, by Frontier URL key, the `http` run's document URL after its redirects with the last main-frame document the browser page reached (the browser tier's document reader notes it), and either side naming none leaves the rest to decide. The weighing takes the fields ADR 0047's removal took out as a set of top-level field names left out of both runs' Records; no tier reports any yet, so none is left out. A cheaper run that escalated, failed or skipped differs. **Refresh:** `fetch.sample.refresh_after` is a table `{requests, after}` (milliseconds), 500 and 86,400,000 by default; a choice notes when it was made (wall clock) in the run file, and beside it the requests it served, written at each one, so a resumed crawl goes on counting them (step 7 review finding 579-599-600-5, 2026-10-28). A choice past either bound is sampled again at the next request of its Label on that domain. **Consent wall:** a browser sample that ended `blocked` with `consent_required` keeps its Label on that domain on `browser` for the Run, never sampled again. **Declared total:** `TierChoices::invalidate` samples a Label again at once; no contract declares a total yet, so nothing calls it. `fetch.sample.count` and `fetch.sample.refresh_after` are set for the Run only, like `fetch.tier_race`. The polite scenario's cell ([#2283](https://github.com/goodfetch/goodfetch/issues/2283)) reports the share of its pages that were samples, and the rule is reopened on that figure only (the owner, 2026-11-10, G-04 Q7).

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-29, deep review finding 579-2 and its decision D9 ([#768](https://github.com/goodfetch/goodfetch/issues/768)): a sample's cheaper runs, on `http`, `light_browser` and `discovered_api`, teach the Frontier nothing: no page signature, no `rel=canonical`, no learned rule and none of the `duplicate` endings a rule gives the pending requests it merges, since their attempts are discarded. The browser's run, which commits, teaches nothing either while the browser tier signs no page. Outside samples, a run on a document tier teaches the Frontier once its page passed its Page check, before its handler runs, so a page that fails it or escalates there teaches nothing.

## Considered Options

- **Browser only**: rejected as the default. It is exact but the most expensive tier, by two orders of magnitude on static pages and discoverable APIs.
- **Falling back to the browser when the HTTP page looks empty**: rejected. In the lab this rule declared stale prices and partial pages complete.
- **A light engine as the default** (Lightpanda): rejected. It fails on shadow DOM ([paired light engine](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/light-engine-paired-2026-10-09.md)).

## Consequences

- HTTP transports: reqwest in `standard` and `identified` Sessions; wreq in HTTP-only `stealth` Sessions, with its TLS and HTTP/2 fingerprint matched to the Session's Identity profile (ADR 0035 picks the fingerprints); browser-fetch in any Session that may move to the browser, because a separate client changes the TLS fingerprint at that moment ([identity report](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/identity-2026-10-08.md)). Impit is not shipped: at equal throughput it used about ten times the memory of reqwest, and 1.6 to ten times its CPU per task ([transports](https://github.com/goodfetch/goodfetch/blob/main/rnd/lab/reports/http-transport-2026-10-09.md)).
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-25, [#1608](https://github.com/goodfetch/goodfetch/issues/1608): browser-fetch sends its request as the document load of a page the engine opens with `Target.createTarget`'s `hidden`, which the browser shows nowhere. A shown page loading the response as a text document made Chromium ask the site for `/favicon.ico` after its load event, and that request could leave past the page's interception as the page closed, through the Session's proxy, counted by neither Politeness nor Usage. A hidden page has no icon, so Chromium never asks. The alternatives were weaker: a `Link: rel=icon` header is ignored by Chromium; answering the page with a document of our own (an inline icon) or a non-committing status loses the browser's report of how the body ended (ADR 0118); closing the page before the load event races it.
  > Note (agent decision, pending owner review), 2026-10-25, [#769](https://github.com/goodfetch/goodfetch/issues/769): a Session "may move to the browser" when its crawl request's tier is not forced, that is under `fetch.tier: auto`, whether the attempt is a sample or the comparison chose `http`; a forced `http` keeps reqwest. A tier forced onto `browser_fetch` sends the same way, nothing escalating, and Provenance records `browser_fetch` forced; forcing `discovered_api` is still refused with `capability_unavailable` at the crawl's start, since its replay plan comes only from a browser sample, which a forced tier takes once [#1638](https://github.com/goodfetch/goodfetch/issues/1638) runs one (step 7 review finding 579-599-600-3, 2026-10-28). Its `http` tier, the document, its redirect hops, the robots.txt the attempt reads first (until [#2422](https://github.com/goodfetch/goodfetch/issues/2422) is built, which reads it on the Session's own HTTP transport, by S4 of the owner's note of 2026-11-10 below) and each `page.request` of the served page, sends through Collie's browser-fetch from an engine page of the Session pool's browser context, opened for the hop and closed after, so the cookies and the TLS fingerprint are the Session's on both tiers (pitfall H20). Browser-fetch follows no redirect for the chain (a count of 0), and the chain still takes each hop through the navigation gate, so the engine page's own gate admits at once; it asks for the browser's own content codings, so over plain HTTP it decodes `gzip` and `deflate` only, as Chrome does; the browser hands the body over whole, so `timeout.first_byte` bounds the whole hop on that tier. A Session that never moves keeps no cookies yet; the navigation gate's robots.txt fetch for another origin, which the Run's copy shares, stays on reqwest.

  > - **The other way is a ladder,** as the glossary's Fetch tier reads. A Session has one client for its life: its own HTTP transport or its browser. Under the ladder, a Label's requests on a domain start on a Session's own transport. Where a sample's `http` run differs from the browser's, the same request is sent again from the hop page of the browser's Session: a match moves the Label on that domain to `browser_fetch`, anything else to `browser`. A Label that moves is served by another Session, and nothing is carried, cookies included (ADR 0021). A Session that holds a login (`session.source`) sends from the browser from its first request. For the Access modes, a `stealth` Session keeps browser-fetch from its first request and an `identified` Session stays on its own transport: no Access mode is built yet, so this is the rule for when they are ([#904](https://github.com/goodfetch/goodfetch/issues/904), [#1178](https://github.com/goodfetch/goodfetch/issues/1178)).
  > - **One setting names the three ways,** `fetch.http_from`, the name proposed in Q12 and checked against the glossary by the ladder's spec: `browser`, every hop from the Session's browser, the default until the rule changes it; `learned`, the ladder; `transport`, never from the browser short of rendering. The ladder is built in a spec of its own (Q14), placed after spec #2138 and before [#2176](https://github.com/goodfetch/goodfetch/issues/2176)'s target is read: [#2413](https://github.com/goodfetch/goodfetch/issues/2413); #2176 waits for its tickets #2415 and #2417.   > - **The rule.** `browser` stays the default only while it can carry the bar of the default row (#2176). - The engine sets decompression, redirects and timeouts itself, and a conformance gate checks every transport: the lab found reqwest built without gzip and wreq following no redirects by default.
  > Amended by [ADR 0118](0118-every-fetch-tier-follows-redirects-as-the-browser-does-fails-a-cut-body-and-resends-only-what-a-site-never-processed.md): redirects are followed as the browser follows them, on every tier: Fetch's five redirect statuses with a `Location` that parses to an HTTP(S) URL, with its method and header rules, at most `fetch.redirect.max` (19) times, each hop through the navigation gate. A refresh stub to another URL is one more hop. A cut body fails with `response_truncated`, and a request the site never processed is sent again once, counted nowhere. A sample comparison whose browser attempt ended on another URL than the other tier's never matches.
  > Amended by [ADR 0119](0119-every-fetch-tier-decodes-a-crawls-document-as-the-browser-does-a-label-names-the-content-types-its-handler-takes-and-exports-are-utf-8.md): every tier decodes the documents of a crawl handler's page (the crawl request's and the handler's own navigations') in one order (a BOM, `fetch.encoding` for the request's document, the `Content-Type` charset, the `<meta>` prescan, then UTF-8 for a valid UTF-8 body), and a non-browser tier escalates an undeclared body it would have to guess. Content codings are decoded as Chrome decodes them, and one that fails is `navigation_failed` with `net::ERR_CONTENT_DECODING_FAILED`.
- Discovered APIs are limited to page-number and cursor plans in V1; signed requests and single-use tokens stay in the browser.
  > Note (agent decision, on a default, not read by the owner), 2026-10-26, [#770](https://github.com/goodfetch/goodfetch/issues/770): as built in `goodfetch-fetch-tier`'s `discovered_api` and `goodfetch-crawl`'s sample. **Capture:** a sample's browser run registers a response observer (ADR 0110's) that keeps every `2xx` answer typed as JSON whose whole body parses, up to 4 MiB each; the observer is told no method, so a non-`GET` call is replayed as a `GET`, differs, and keeps its Label on the browser. **Plans:** the calls, a repeated URL counted once, group by endpoint (origin and path, number segments masked); an endpoint called once is replayed as it was; a page number is one query value or path segment counting up by one, replayed until an answer holds no array with an entry; a cursor is one query parameter carrying a string the answer before held at one path of object keys, replayed until an answer holds none or repeats one; an endpoint following none of them leaves no plan, and the Label stays on the browser. A plan learned on one document serves another of its Label: each path segment and query value of a series' first call equal to the sample document's takes the new document's value. **When it runs:** a sample whose `http` run escalated at a network wait (a call `discovered_api` serves and `http` does not; otherwise the two serve the same document) runs on `discovered_api` after its browser run, replaying that run's calls for the same request; the browser's staging is set aside meanwhile and committed, the replay's discarded (ADR 0103). A Label whose samples all matched over `http` or on `discovered_api` moves to `discovered_api` with the last such sample's plan; the cheapest tier serving every sample wins (`http`, then `discovered_api`, then `light_browser`). **What it serves (first build):** the document, as `http`, and `page.wait_for_response` armed before a navigation of the page (`goto`, `reload`, `goBack`, `goForward`), answered from the calls that navigation replays, one call at a time while a wait is armed; a wait none answers, a failed or non-JSON call (a token the site takes once) and a wait with no navigation before its deadline escalate. As in the browser, a wait is armed when called, so a handler arms its waits and reloads; `wait_for_request`, `wait_for_request_finished`, the page's events and kept responses are #1659's. Forcing `discovered_api` stays refused at the crawl's start until a forced tier takes its browser sample.
- Lightpanda is an optional tier, run out of process and downloaded on demand, never bundled, so its AGPL licence stays outside Goodfetch's distribution. It is chosen only when the run's declared capabilities allow it and its sample matches Chrome's; it used 1/8 to 1/20 of Chrome's CPU in the lab.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-26, [#771](https://github.com/goodfetch/goodfetch/issues/771): as built in `goodfetch-fetch-tier`'s `light_browser`. **The Run's capability** is the setting `fetch.light_browser` (Run only, off by default) on a platform Lightpanda builds for (Linux and macOS, x86-64 and arm64; not Windows or musl); forcing `light_browser` without it fails the crawl's start with `capability_unavailable` naming that key. **The build** is a Pinned artifact of Foxhound's, Lightpanda 1.0.2's release executable per platform by its GitHub URL and SHA-256 (`pins.json`); the Browser cache places a pinned URL that names no `.zip` as that single executable, its files' digest the tree of that one file. It is prepared once per engine at the tier's first run, and `browsers install` does not fetch it. **The run** is one `lightpanda fetch --json --dump html` process per attempt (network idle, at most 10 s), telemetry off, every request through a loopback proxy of the engine's (the light-browser bridge, with credentials of its own) that resolves names itself and connects only to addresses the Run's egress policy allows; Lightpanda follows redirects and decodes the document itself, so its Provenance names no encoding. **Its page** is the document the page's scripts left, served as a document tier's is: questions and state waits from its markup; a script of the handler's, a network wait and a navigation escalate under `auto` and fail with `browser_required` when forced, as layout and gestures do, until a live Lightpanda page serves them. **Under `auto`** a Run that allows the tier runs each sample on `http`, `light_browser` and then `browser`; a sample whose `http` run differed but whose light run matched counts as matched on `light_browser`, and a Label (or segment) whose samples all matched moves to `http` when all matched there and to `light_browser` otherwise. The bridge's later hops are not gated per hop, nor its subresources, as the browser tier's navigation hops are.
