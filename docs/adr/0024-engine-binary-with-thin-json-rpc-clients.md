# The engine is a separate binary; SDKs are thin JSON-RPC Clients

The TypeScript and Python SDKs, the CLI, the MCP server and Automan Cloud all reach the engine as Clients of one `automan` binary, over newline-delimited JSON-RPC 2.0 that opens with a `hello` handshake carrying the protocol's `major.minor` version; only the Rust crate links the engine into the user's own program, and it ships the same client. The binary runs either as an **Attached engine**, a child process over stdio that an SDK script starts by default and that stops with it, or as a **Daemon** that several Clients share; an SDK uses the Daemon when one is configured or already running. We chose the binary over in-process bindings (napi-rs, PyO3) for what it does for Clients, not for SQLite: in the prototype, SQLite survived in-process crashes intact, but only the binary re-queued a dead Client's work (in 0.2–0.4 ms), kept other Clients running through the crash, cut p99 commit latency 2–6x at 4–8 processes by grouping their commits, carried full stack traces in both languages, and installed from one `py3-none` wheel on every Python tested (3.9, 3.13 and free-threaded 3.14t) with 13–18 release files against 26–34. Decided in [SDK binding and distribution strategy](https://github.com/Jbmanllr/automan/issues/75), on the evidence of [Prototype: engine binding, native vs RPC](https://github.com/Jbmanllr/automan/issues/74) and [Shipping TypeScript and Python SDKs over a Rust engine](https://github.com/Jbmanllr/automan/issues/63).

## Considered Options

- **In-process native bindings** (napi-rs for Node, PyO3 for Python): rejected. Faster on tiny calls and capable of zero-copy pages, but a dead process leaves its in-flight work stuck as in progress, napi cannot cancel a hung JavaScript handler and passes no JavaScript stack, napi's plain `call_async` aborts the process on a synchronous throw, and PyO3 needs a separate free-threaded wheel without which uv refuses to install and pip downloads a 146 MB Rust toolchain and still fails.
- **Daemon only**: rejected. It forces lifecycle, discovery and Windows work on every one-off script; the Attached engine avoids most of it, as esbuild and Playwright for Python show.
- **Attached engine only**: rejected. It gives up grouped commits across Clients, surviving a crashed Client, the per-install layout of ADR 0002 and a Console that outlives a script.
- **One build per Linux libc** (glibc and musl): rejected. One static musl binary per architecture installed and ran on both through npm and a dual-tagged wheel, halving the Linux files.
- **Named pipes on Windows**: rejected for V1. Python's asyncio reaches them only through an undocumented `ProactorEventLoop` call, while loopback TCP is public in Node, Python and Rust.
- **Inline page bodies**: rejected. Inline JSON cost 2.8–2.9x at 100 KB, 9–10x at 1 MB and 15–17x at 10 MB against passing the page by reference.

## Consequences

- The protocol is the product's main internal contract. An Attached engine runs the exact engine version its SDK ships with; a Daemon or a cloud engine accepts a Client with the same major and the same or an older minor, and refuses anything else with a clean error. The Browser host of ADR 0022 speaks the same protocol with the same handshake, over TLS and a token when reached remotely (ADR 0017).
- Operations are coarse or batched, because a small call costs 1.6–2x as much as in-process (paired ratios of 0.47 in Node and 0.64 in Python; medians of 54 against 26 µs and 120 against 99 µs): little next to fetching and rendering a page, a lot across many tiny calls.
- The Playwright-shaped page API of ADR 0019 is a set of Operation catalog calls over this protocol, so every SDK gets it from the same catalog.
- Page bodies travel as handles backed by files in the run's directory: a Client on the same machine reads the file directly, a remote one streams it through `page.body`.
- Events flow through bounded engine queues with credit-based, batched delivery: when a queue is full, lossless events (records, handler requests) slow the producer and are never dropped, while telemetry (progress, live-view frames) is coalesced. This is on by default in every SDK.
- An Attached engine checkpoints and stops when its stdin closes. If its Client dies without closing it, the engine still goes: the kernel kills it on Linux (`PR_SET_PDEATHSIG`) and Windows (a kill-on-close Job Object), and on macOS it exits through its own kqueue `NOTE_EXIT` watch on the parent. Every browser it starts sits in its own process group or Job Object and dies with it. The engine tells a gone Client apart from a failed handler.
- The Daemon is started on demand by whatever needs it (the Console, the per-install layout, an SDK, the CLI or the MCP server configured to use it) or by `automan daemon start`, and is found through a per-user, per-product-major runtime file, mode `0600`, holding its endpoint, per-launch token, version and PID; a Client that finds a dead PID replaces the file. It stops after 10 idle minutes unless `--keep-alive` is set or `automan daemon install` registers it as a per-user service (launchd agent, systemd user unit, Windows logon task). There is one Daemon per user and per product major (ADR 0030): a Client of that product major whose protocol version the Daemon refuses, under the rule above, restarts it when idle and otherwise fails with an `automan daemon restart` hint.
- A Daemon runs several runs in one process, so a Daemon crash stops all of them; each run can then resume from its own state, in either layout of ADR 0002. A Client crash stops only that Client's work, which the Daemon re-queues.
- The Daemon always runs from a copy in a versioned cache, so `npm update` or `pip install -U` never replaces a running executable, which Windows forbids.
- The Daemon's protocol listens on a Unix socket with `0600` permissions on macOS and Linux and on loopback TCP on Windows; a connection whose first message is not a `hello` carrying the per-launch token is closed. Attached engines use stdio everywhere. The Daemon can also serve the same protocol over an HTTP listener for workflow tools, off until enabled, then loopback and token (ADR 0027). The engine's HTTP endpoints (the Console, MCP Streamable HTTP, raw CDP, the HTTP listener) keep ADR 0017's `Host` and `Origin` check as well.
- The CLI and the MCP server are the engine binary itself: they become Clients of a Daemon when one is running or configured, and otherwise run the engine in their own process; `--attached` and `--daemon` force either.
- The Console's assets are embedded in the binary and served by the Daemon, or by an Attached engine whose script asks for it. `automan console` starts the Daemon of its own product major if needed, opens the browser, and passes the token once in the URL fragment, where it is swapped for an `HttpOnly` cookie. How the Console, which runs in a browser, reads runs and live views from the engine is left to the Console's own design, an open item of the [V1 map](https://github.com/Jbmanllr/automan/issues/61).
- Every SDK offers `workers=N`, with an Attached engine or a Daemon: the SDK starts N handler processes with its language's own mechanism, and they lease work from the same run under ADR 0003. An Attached engine opens a private endpoint, under the same token rule, for its own workers.
- Linux ships one fully static musl binary per architecture, with a bundled allocator (mimalloc) and the engine's own DNS resolver. The cost: names that only corporate NSS setups or `.local` mDNS can resolve do not resolve.
- V1 ships on Linux x64 and arm64 (glibc and musl), macOS arm64 and x64, and Windows x64 and arm64, through npm platform packages in `optionalDependencies` with no install scripts, Automan's own error at first use and an `AUTOMAN_ENGINE_PATH` override; `py3-none` platform wheels on PyPI; crates.io and `cargo install`; signed GitHub Releases; a Homebrew tap; `curl | sh` and PowerShell installers; and an OCI image. In npm, `--omit=optional`, a lockfile made on macOS or an offline install exit 0 and then fail at first use, whether the engine ships as a binary or as an addon, so the first-use error names the cause and the fix. Yarn and pnpm hold back releases younger than 24 hours by default in new projects, which matters for hotfixes; ADR 0030 says how a fix gets through.
- Supported runtimes follow end-of-life dates, not fixed versions: every Node line not past end of life at release (22, 24 and 26 today), Bun and Deno 2, and every CPython not past end of life (3.11 to 3.15 today), with free-threaded builds from 3.14t on. The TypeScript SDK is ESM-only; the Python SDK offers sync and async APIs generated from the Operation catalog (ADR 0011).
- Browsers are pinned builds downloaded into a shared per-user cache and checked by digest: on first use by default with a progress event, by `automan browsers install` for CI and images, or from `AUTOMAN_BROWSERS_PATH` offline. Chrome for Testing is the default. It has no Windows arm64 or musl build, so Windows arm64 runs the win64 build under emulation and musl hosts use their distribution's Chromium, with a message saying so. An installed Chrome can be used by channel or path. Patchright, Camoufox and Lightpanda arrive through the same cache (ADR 0018), and so do Playwright's driver and its Firefox and WebKit builds, fetched only when a run asks for those browsers (ADR 0019); which stealth builds ship is decided in the [Stealth and challenge-solving catalog](https://github.com/Jbmanllr/automan/issues/78).
- The prototype measured only macOS arm64 and Linux arm64 (with a few x64 cells under emulation), Node 20 and 24, Bun installs, and Python 3.9, 3.13 and 3.14t. The conformance suite covers every supported platform and runtime, and the V1 benchmark the Linux reference host.
