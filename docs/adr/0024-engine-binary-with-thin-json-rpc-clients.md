# The engine is a separate binary; SDKs are thin JSON-RPC Clients

The TypeScript and Python SDKs, the CLI, the MCP server and Goodfetch Cloud all reach the engine as Clients of one `goodfetch` binary, over newline-delimited JSON-RPC 2.0 that opens with a `hello` handshake carrying the protocol's `major.minor` version; only the Rust crate links the engine into the user's own program, and it ships the same client. The binary runs either as an **Attached engine**, a child process over stdio that an SDK script starts by default and that stops with it, or as a **Daemon** that several Clients share; an SDK uses the Daemon when one is configured or already running. We chose the binary over in-process bindings (napi-rs, PyO3) for what it does for Clients, not for SQLite: in the prototype, SQLite survived in-process crashes intact, but only the binary re-queued a dead Client's work (in 0.2–0.4 ms), kept other Clients running through the crash, cut p99 commit latency 2–6x at 4–8 processes by grouping their commits, carried full stack traces in both languages, and installed from one `py3-none` wheel on every Python tested (3.9, 3.13 and free-threaded 3.14t) with 13–18 release files against 26–34. Decided in [SDK binding and distribution strategy](https://github.com/goodfetch/goodfetch/issues/75), on the evidence of [Prototype: engine binding, native vs RPC](https://github.com/goodfetch/goodfetch/issues/74) and [Shipping TypeScript and Python SDKs over a Rust engine](https://github.com/goodfetch/goodfetch/issues/63).

Which one a Client starts or reaches, and what `hello` announces, is decided in [Protocol, Operation catalog and SDKs across two products](https://github.com/goodfetch/goodfetch/issues/458).

> Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): both Products speak this one protocol. `hello` also carries the Product a Client needs and its Product version, and the reply the engine's; an engine accepts a Client whose needed Product its own contains, so a Collie engine refuses a Foxhound Client with `not_in_product`. Each Product's Rust SDK crate, `goodfetch-collie` or `goodfetch-foxhound`, links its own engine, and both build on `goodfetch-collie-client`, which links none.

> Note (owner's decisions of 2026-11-10, in the grilling of decision G-01 of the consolidated review, Q4 and Q14, answered "Yes, all four" and "Yes, all ten"), at "only the Rust crate links the engine into the user's own program, and it ships the same client": a typed in-process entry for a Rust program, in place of JSON over the in-memory pair, is neither adopted nor refused. It is decided on a figure: the wire's share of a handled page in Rust (the instructions spent encoding, carrying and decoding messages, on both sides, over the page's instructions), read on the counts benchmark's handled cell once a message is decoded once and an answer encoded once ([#1898](https://github.com/goodfetch/goodfetch/issues/1898)) and a page's fields are read in one call ([ADR 0147](0147-a-pages-fields-are-read-in-one-call-on-every-tier-and-a-push-takes-one-record-or-several.md)). Above 10 % the entry is brought back to the owner as a change to this ADR and to E1's contract (ADR 0140); at or below it, this sentence stands. In either case a Rust program has one API, from the one catalog: no separate native Rust API. The figure is first read with the benchmark's own client; if it lands close to 10 %, whether Rust's client crate and crawl come before the Features step is put to the owner again, with the figure (Q15). How an entry would be built is the session's reading, not the owner's decision, and awaits the owner's reading: if built, it is a second encoding of E1's own dispatch, never a handler beside it (ADR 0140's plug-in rule), so it keeps what a call meets today. It calls each operation's `Handler` with a `CallContext` of its own, which carries the call's cancellation (`crates/goodfetch-engine/src/rpc/connection.rs:1057-1064#CallContext::new`), and so meets the Guard the page contribution folds into its handlers, which gives a Page's Product the first answer (`crates/goodfetch-engine/src/composition.rs:505-519#Contribution::guarded`, `crates/goodfetch-page/src/pages.rs:186-190`), read at `094c96b2d`.

## Considered Options

- **In-process native bindings** (napi-rs for Node, PyO3 for Python): rejected. Faster on tiny calls and capable of zero-copy pages, but a dead process leaves its in-flight work stuck as in progress, napi cannot cancel a hung JavaScript handler and passes no JavaScript stack, napi's plain `call_async` aborts the process on a synchronous throw, and PyO3 needs a separate free-threaded wheel without which uv refuses to install and pip downloads a 146 MB Rust toolchain and still fails.
- **Daemon only**: rejected. It forces lifecycle, discovery and Windows work on every one-off script; the Attached engine avoids most of it, as esbuild and Playwright for Python show.
- **Attached engine only**: rejected. It gives up grouped commits across Clients, surviving a crashed Client, the per-install layout of ADR 0002 and a Console that outlives a script.
- **One build per Linux libc** (glibc and musl): rejected. One static musl binary per architecture installed and ran on both through npm and a dual-tagged wheel, halving the Linux files.
- **Named pipes on Windows**: rejected for V1. Python's asyncio reaches them only through an undocumented `ProactorEventLoop` call, while loopback TCP is public in Node, Python and Rust.
- **Inline page bodies**: rejected. Inline JSON cost 2.8–2.9x at 100 KB, 9–10x at 1 MB and 15–17x at 10 MB against passing the page by reference.

## Consequences

- The protocol is the product's main internal contract. An Attached engine runs the exact engine version its SDK ships with; a Daemon or a cloud engine accepts a Client with the same major and the same or an older minor, and refuses anything else with a clean error. The Browser host of ADR 0022 speaks the same protocol with the same handshake, over TLS and a token when reached remotely (ADR 0017).
  > Amended by [ADR 0066](0066-upgrades-are-tested-from-a-frozen-corpus-and-skew-from-every-released-minor.md): every Attached engine applies the Daemon's rule at `hello`; with the engine its SDK ships the versions are equal, and `GOODFETCH_ENGINE_PATH` is how they can differ.

  > Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): before this rule, an engine checks the Product the Client needs, and refuses one its own Product does not contain with `not_in_product`, in the reply to `hello`. The rule still compares protocol versions, never Product versions.

  > Amended by [ADR 0096](0096-the-browser-host-runs-from-either-products-executable-and-goodfetch-cloud-runs-each-run-on-the-product-it-needs.md): a Browser host does not follow the Daemon's rule: it and the engine that drives it accept each other within one major and settle on the lower of their two minors.
- Operations are coarse or batched, because a small call costs 1.6–2x as much as in-process (paired ratios of 0.47 in Node and 0.64 in Python; medians of 54 against 26 µs and 120 against 99 µs): little next to fetching and rendering a page, a lot across many tiny calls.
  > Note (owner's decisions of 2026-11-10, grilling of G-01, Q2, Q3, Q11 to Q13): a handler's reads and pushes are made coarse too. A page's fields are read in one call, `page.read(fields)`, and one `push` takes one Record or a list ([ADR 0147](0147-a-pages-fields-are-read-in-one-call-on-every-tier-and-a-push-takes-one-record-or-several.md)).
- The Playwright-shaped page API of ADR 0019 is a set of Operation catalog calls over this protocol, so every SDK gets it from the same catalog.
- Page bodies travel as handles backed by files in the run's directory: a Client on the same machine reads the file directly, a remote one streams it through `page.body`.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#216](https://github.com/goodfetch/goodfetch/issues/216)): a body is the file `bodies/<sha256>` in its Run's folder, named by the lowercase hex SHA-256 of its bytes and written whole before it is renamed into place; its handle is `{run_id, body, path, size}`. `page.body {run_id, body}` sends it in `$/chunk {id, offset, data}` notifications of at most 64 KiB in Base64, one per credit granted with `$/credit`, and then answers `{size}`; an unknown Run or body, or an ID that is no digest, fails with `body_not_found`.
- Events flow through bounded engine queues with credit-based, batched delivery: when a queue is full, lossless events (records, handler requests) slow the producer and are never dropped, while telemetry (progress, live-view frames) is coalesced. This is on by default in every SDK.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#215](https://github.com/goodfetch/goodfetch/issues/215)): a handler request is a JSON-RPC request the engine sends the Client on the Connection that started the Run, under an id of the engine's own, and the Client's reply is the handler's answer. The catalog declares each in a section of its own, `handler_requests` (a crawl's `crawl_request.handle`, Foxhound's). The engine never has more in flight than the Run's `crawl.handler.concurrency`, which is how they slow their producer; a failure that names no Error code reads as the handler's own `handler_failed`, and a reply after the attempt's lease ended commits nothing.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#217](https://github.com/goodfetch/goodfetch/issues/217): the engine cancels a handler request whose attempt ended early, at its lease's end, with `$/cancel` naming the request's id, as a Client cancels a call. The request still expects its one answer: a failure, such as `call_cancelled`, changes nothing, and a result is a late commit, refused with `lease_lost`. A request cancelled so no longer counts against `crawl.handler.concurrency`, so a hung handler never holds the slot its retry needs.
  > Amended by [ADR 0103](0103-a-handler-pushes-records-staged-with-its-attempt-into-datasets-its-crawl-declares-and-a-reader-never-slows-the-crawl.md): a crawl's Records are read from run state, where they are already committed, so a reader is a cursor that the engine feeds as its credit allows and the crawl never waits for; handler requests still slow their producer.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#216](https://github.com/goodfetch/goodfetch/issues/216)): a subscription is the call `events.subscribe {after?}`, which stays in flight until its Client cancels it or its Connection ends. The engine sends its events in `$/events {id, events}` batches of at most 256, each event `{position, event, data, dropped?}`, never more than the credits the Client granted the call with `$/credit {id, credits}`; credits are keyed by the streaming call's id, so `page.body` takes them the same way. Each catalog event declares its class, `lossless` or `telemetry`. No producer waits for a subscriber: a subscription whose queue (64 lossless events) is full falls behind, its queued lossless events dropped, and next takes `events.resync`, then the stream; a telemetry event never waits and replaces the unsent one of the same event and scope in each queue, counting the ones it replaced as `dropped`. The Records cursor of ADR 0103 is not on this stream ([#961](https://github.com/goodfetch/goodfetch/issues/961)); the first lossless event is `run.axes_changed`. Changed on 2026-10-21: a subscriber that stops reading falls behind to `events.resync` instead of holding back every Run's lifecycle events, other Clients' included.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, step 7 review (Standards A2): the input a call takes from its Client, such as `run.add_seeds`' `$/seeds` batches, waits in a bounded queue whose room its handler declares: the most its credits let a Client send unanswered (`run.add_seeds`: `SEED_CREDITS` batches and the one that ends the stream). The Connection never waits on it, so a Client's own overflow holds back none of its other calls: one notification past the room fails the call's next read with `invalid_params`, and the call's later input is ignored.
- An Attached engine checkpoints and stops when its stdin closes. If its Client dies without closing it, the engine still goes: the kernel kills it on Linux (`PR_SET_PDEATHSIG`) and Windows (a kill-on-close Job Object), and on macOS it exits through its own kqueue `NOTE_EXIT` watch on the parent. Every browser it starts sits in its own process group or Job Object and dies with it. The engine tells a gone Client apart from a failed handler.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#222](https://github.com/goodfetch/goodfetch/issues/222): on Linux the parent-death signal is `SIGKILL`, so the kernel ends the engine with no Checkpoint, as a power cut would; on macOS the watch stops the engine as the end of its stdin does. On Windows the engine puts itself in a new kill-on-close Job Object, duplicates its handle into its parent and closes its own, so the parent's end closes the job's last handle. Every child process the engine starts goes through its `children` module (Clippy refuses `tokio::process::Command::spawn` elsewhere): a process group of its own with `SIGKILL` as its parent-death signal on Linux, and a kill-on-close Job Object whose only handle the engine holds on Windows; the engine's stop kills each group or the job. On macOS nothing in the kernel ends the children of an engine itself killed with `kill -9`: a browser driven over a pipe ends when the pipe closes (area 5). A handler request whose Connection ended answers `client_gone` (retryable, under the work item's retry policy), never the handler's own `handler_failed`.
- The Daemon is started on demand by whatever needs it (the Console, the per-install layout, an SDK, the CLI or the MCP server configured to use it) or by `goodfetch daemon start`, and is found through a per-user, per-product-major runtime file, mode `0600`, holding its endpoint, per-launch token, version and PID; a Client that finds a dead PID replaces the file. It stops after 10 idle minutes unless `--keep-alive` is set, it holds an enabled Schedule of the active major (ADR 0036), or `goodfetch daemon install` registers it as a per-user service (launchd agent, systemd user unit, Windows logon task). There is one Daemon per user and per product major (ADR 0030): a Client of that product major whose protocol version the Daemon refuses, under the rule above, restarts it when idle and otherwise fails with a `goodfetch daemon restart` hint.
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the Daemon of a major serves both Products and runs its pick, the fullest Product installed for that major at its newest installed version, from the versioned copy, whatever starts it. A Daemon that is not the pick hands over to it once it hosts no live run and no Client but a Console. A Client it refuses by Product or protocol version while it cannot hand over runs, under `engine: auto`, the engine it would run with no Daemon, with a warning, and fails at connect under `engine: daemon`. `daemon install` registers one service per major, which starts the pick.
- A Daemon runs several runs in one process, so a Daemon crash stops all of them; each run can then resume from its own state, in either layout of ADR 0002. A Client crash stops only that Client's work, which the Daemon re-queues.
- The Daemon always runs from a copy in a versioned cache, so `npm update` or `pip install -U` never replaces a running executable, which Windows forbids.
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the copy sits in the Browser cache, pinned by its executable's entry in the list of installed executables, and is deleted only under the cache's clean-up.
- The Daemon's protocol listens on a Unix socket with `0600` permissions on macOS and Linux and on loopback TCP on Windows; a connection whose first message is not a `hello` carrying the per-launch token is closed. Attached engines use stdio everywhere. The Daemon can also serve the same protocol over an HTTP listener for workflow tools, off until enabled, then loopback and token (ADR 0027). The engine's HTTP endpoints (the Console, MCP Streamable HTTP, raw CDP, the HTTP listener) keep ADR 0017's `Host` and `Origin` check as well.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#220](https://github.com/goodfetch/goodfetch/issues/220): the runtime file is `daemon.json` in the per-major folder, `{endpoint: {unix: path} | {tcp: address}, token, version, pid}`, mode `0600`. A Daemon also holds an exclusive lock on `daemon.lock` beside it while it serves, and a Client takes a runtime file whose lock nobody holds for a dead Daemon's, whatever its PID says, so a reused PID never passes for a live Daemon; whatever starts a Daemon holds `daemon-start.lock` until the Daemon it started is ready, so two Clients start one. A socket path longer than the OS takes (macOS's 104 bytes) moves into a `0700` folder of its own in the OS's temporary folder, which the runtime file names. A connection whose first message is not a `hello` with the token is closed without any answer. The per-launch token is 32 bytes of the OS generator, in hex.
  >
  > Note, 2026-11-11 (the owner, grilling of decision G-19 of the consolidated review, Q10: « Yes to all »; the wording is the grilling session's, and the owner did not read it): ADR 0027's note of that day adds two compatible APIs on the HTTP listener, Firecrawl's and Jina Reader's, each off by default.
- The CLI and the MCP server are the engine binary itself: they become Clients of a Daemon when one is running or configured, and otherwise run the engine in their own process; `--attached` and `--daemon` force either.
  > Note (agent decision, on a default, not read by the owner), 2026-10-23, [#1183](https://github.com/goodfetch/goodfetch/issues/1183): each CLI command is a Connection of its own, so a Run a command starts or resumes on the Daemon outlives that Connection: the Daemon does not stop the Runs of a Connection whose `hello` says the form `cli` when it ends, as it does an SDK's. Such a Run still stops with the Daemon, whose idle stop counts Clients, not live Runs. A command whose value outlives it, a value-bound command or an opener, starts the Daemon when none runs; any other asks a Daemon only when one runs. `GOODFETCH_URL` configures a remote Daemon for the CLI as `ws://<IP address or localhost>:<port>`, which the CLI reaches with newline-delimited JSON-RPC, served beside WebSocket on the Exposed Daemon's address (ADR 0049); `wss://` waits for the Daemon's TLS. `--attached` beats `GOODFETCH_URL`, a remote Daemon's refusal ends the command with no fallback, and `GOODFETCH_TOKEN` must hold its token. `config explain` takes `--attached` too, which it already behaves as without `--daemon`.
  > Note (accepted by the owner on 2026-10-28), 2026-10-29, [#1183](https://github.com/goodfetch/goodfetch/issues/1183) (deep review, 608-O1, 608-O2 and 608-O6), amending the note above: the Daemon takes a hold for each CLI Connection whose live Runs outlive it, until they end, so its idle stop counts those Runs as well as Clients and a crawl started from the CLI runs to its end; `daemon status` shows them as live Runs, not as `kept_alive`. A `GOODFETCH_URL` whose address is not loopback is refused with `setting_invalid` before any Connection, until `wss://` lands, as ADR 0049 refuses such a Daemon address, so `GOODFETCH_TOKEN` never travels in clear to another host; a forwarder listens on loopback, as an SSH tunnel does. A command whose value outlives it does not fall back to an Attached engine when the Daemon refuses it by Product or version: it ends with the refusal and its `fix` (ADR 0069). `config explain --daemon` reaches the Daemon as every command under `--daemon` does, so the remote one `GOODFETCH_URL` names wins over the major's.
- The Console's assets are embedded in the binary and served by the Daemon, or by an Attached engine whose script asks for it. `goodfetch console` starts the Daemon of its own product major if needed, opens the browser, and passes the token once in the URL fragment, where it is swapped for an `HttpOnly` cookie. The Console is an ordinary Client of this protocol, carried over a WebSocket on its own origin, and sees every run on the machine through a Run index (ADR 0031), which also adds per-person accounts and scoped tokens beside the per-launch token.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-22, [#817](https://github.com/goodfetch/goodfetch/issues/817): the link is `<console url>#token=<token>`, the token the Daemon's runtime file holds (per-launch, or the persistent one under socket activation). `console` opens the browser on a page of the user's own, `console.html` in the per-major folder, mode `0600` as the runtime file, which goes on to the link, so the token is never in a command line another user's process list shows; `--no-browser` opens nothing and prints the link, `--json` as `ConsoleOpened {url}`. The page posts the token to `POST /sign-in` (its own `Host` and `Origin` only, 1 KiB at most), which answers `204` with the cookie `goodfetch_console_<port>` (`HttpOnly; SameSite=Strict; Path=/`), named by the Console's port because a browser sends a host's cookies to every port and each major has its own; its value is 32 bytes of the OS generator in hex, never the token. The page then replaces its address with one without the fragment, and `GET /session` answers `204` signed in, `401` otherwise. The Console's WebSocket opens at `/protocol` with the Console's own `Host` and `Origin` (`403` otherwise) and a sign-in's cookie (`401` otherwise), and the Daemon serves it as a Connection whose `hello` carries no token. Sign-ins live in the Daemon's memory until the accounts store keeps them ([#826](https://github.com/goodfetch/goodfetch/issues/826)).
- In a Daemon group, the SDKs, the CLI and the Console follow a Group member's redirect of a heavy stream to the Group member that owns the run; after the Error code `run_moved`, a redirected Client reconnects through any Group member and retries once (ADR 0055).
- Every SDK offers `workers=N`, with an Attached engine or a Daemon: the SDK starts N handler processes with its language's own mechanism, and they lease work from the same run under ADR 0003. An Attached engine opens a private endpoint, under the same token rule, for its own workers.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#222](https://github.com/goodfetch/goodfetch/issues/222): an Attached engine started on the OS opens its private endpoint in a `0700` folder of its own in the OS's temporary folder, removed when it stops: a `0600` socket `engine.sock` (loopback TCP on a port the OS chooses on Windows) and the `0600` file `engine.token`, 32 bytes of the OS generator in hex. It tells the Client of its stdio alone, in its `hello` reply's `private_endpoint {address, token_file}`; a Connection there opens with a `hello` carrying the token, or is closed unanswered, as on the Daemon. A handler process joins a crawl with `crawl.serve {run_id}`, which stays in flight until the Run ends (answering its Run report) or the call is cancelled; the engine then sends it `crawl_request.handle` requests too, `crawl.handler.concurrency` at once on each Connection, as ADR 0081 says `workers=N` multiplies. An engine linked in process (the in-memory network) opens none.
- Linux ships one fully static musl binary per architecture, with a bundled allocator (mimalloc) and the engine's own DNS resolver. The cost: names that only corporate NSS setups or `.local` mDNS can resolve do not resolve.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#260](https://github.com/goodfetch/goodfetch/issues/260): the resolver is `hickory-resolver`, reading the system's resolver configuration and hosts file. Such a name fails with `name_not_resolved` (not retryable), whose details name the resolver (`engine` or `system`) and flag a `.local` name; a name whose name servers time out, refuse or fail gives `name_lookup_failed` (retryable). A `.local` name still goes to the configured name servers first, since Kubernetes' cluster DNS serves `cluster.local`; only multicast DNS is never asked. The `resolve` mapping applies before either resolver (ADR 0059).
  > Note (agent decision, as built), 2026-11-06, [#2114](https://github.com/goodfetch/goodfetch/issues/2114): the static musl build compiles its C and C++ code and links with Zig, through cargo-zigbuild, at the versions `ci/musl/toolchain.sh` pins (Zig 0.17.1, cargo-zigbuild 0.24.1); `just musl-toolchain` and the Release suite's musl cells install them (`ci/musl/install.sh`, Zig checked against its SHA-256), and `ci/musl/cargo` runs every musl build: `xtask test-tools` for a `*-linux-musl` target, so `just targets` and `just rss`, and the cells' nextest archive. `musl-tools` has no C++ compiler, which DuckDB and BoringSSL need, and the host's g++ in its place links glibc 2.38 symbols (`__isoc23_strtoull`) the static binary cannot resolve. A musl cross g++ (musl-cross-make) is the alternative, built from source on each host; Zig is one pinned download, free.
  > Note (the owner's decision of 2026-11-07, [#2165](https://github.com/goodfetch/goodfetch/issues/2165); the link is an agent decision, as built), 2026-11-12, [#2202](https://github.com/goodfetch/goodfetch/issues/2202): the static musl executable is a static-PIE with packed relative relocations, so it loads at a randomised base: `ET_DYN`, no interpreter, no `DT_NEEDED`, a `DT_RELR` entry, which musl's start-up applies. Until then it was `ET_EXEC` at a fixed base, without address-space layout randomisation: Zig's `cc` ignores rustc's `-static-pie`, and it refuses `-z pack-relative-relocs`. So `ci/musl/cargo` names `ci/musl/link-cc` as the musl target's linker, which cargo-zigbuild keeps, and that script links each executable twice. Zig's `cc` first links with `-pie`, which makes it pick musl's self-relocating `rcrt1.o` and its runtime archives built position-independent, and prints the command it ran its bundled LLD with (`ZIG_VERBOSE_LINK`); the same command then runs again through `zig ld.lld` with `-z pack-relative-relocs` added. The script takes Zig's argument list from Zig itself, so it copies no path of Zig's cache and no flag of Zig's; the price is the second link, about a second for a release executable, whose link-time optimisation rustc has done before. Every musl executable links this way, whatever its profile: both Products', the test tools' and the tests'. The pinned versions stay. `xtask static-pie` holds each Product's executable of a musl Release cell to those four facts (`ci/release/cell.sh size`). Zig prints its arguments unquoted, so a build folder whose path holds a space fails at the second link. Rejected: staying at a fixed base, since the executable reads hostile content; a static-PIE with unpacked relocations, which costs 5 to 6 MiB of resident memory against 0.5 to 1.5 MiB packed ([#2162](https://github.com/goodfetch/goodfetch/issues/2162)); and copying Zig's LLD arguments into the script, which a Zig update would silently outdate.
- V1 ships on Linux x64 and arm64 (glibc and musl), macOS arm64 and x64, and Windows x64 and arm64, through npm platform packages in `optionalDependencies` with no install scripts, Goodfetch's own error at first use and a `GOODFETCH_ENGINE_PATH` override; `py3-none` platform wheels on PyPI; crates.io and `cargo install`; signed GitHub Releases; a Homebrew tap; `curl | sh` and PowerShell installers; and an OCI image. In npm, `--omit=optional`, a lockfile made on macOS or an offline install exit 0 and then fail at first use, whether the engine ships as a binary or as an addon, so the first-use error names the cause and the fix. pnpm 11 and new Yarn projects hold back releases younger than 24 hours by default, which matters for hotfixes; ADR 0030 says how a fix gets through.

- Supported runtimes follow end-of-life dates, not fixed versions: every Node line not past end of life at release (22, 24 and 26 today), Bun and Deno 2, and every CPython not past end of life (3.11 to 3.15 today), with free-threaded builds from 3.14t on. - Browsers are pinned builds downloaded into a shared per-user cache and checked by digest: on first use by default with a progress event, by `goodfetch browsers install` for CI and images, or from `GOODFETCH_BROWSERS_PATH` offline. Chrome for Testing is the default. - The prototype measured only macOS arm64 and Linux arm64 (with a few x64 cells under emulation), Node 20 and 24, Bun installs, and Python 3.9, 3.13 and 3.14t. The conformance suite covers every supported platform and runtime, and the V1 benchmark the Linux reference host.
- ADR 0039 gives every macOS and Windows executable Goodfetch builds a Platform signature, so every binary channel carries the same signed bytes; an executable Goodfetch did not build that Windows refuses to start fails with a typed error naming Smart App Control.
- ADR 0033 adds browsers declared by a Plugin to this cache (by download URL and digest, allowed per digest), a runtime cache of Node and Python versions for Plugins, a Plugin store of verified OCI artifacts, the `goodfetch plugin-shim` relay inside the same binary, and an elevated `goodfetch plugins setup` that installs the Linux `goodfetch-sandbox` helper with its AppArmor profile and the Windows filter broker for Plugins.
- Browser downloads on first use are among the only connections nobody configures, and the `offline` setting turns them into an error (ADR 0043). The engine's own resolver also serves Sessions bound to a local address on macOS and Windows (ADR 0044).
- `goodfetch browsers install` also fetches the Clean-up rules, which `GOODFETCH_BROWSERS_PATH` also covers, and the part whose licences allow embedding is in the binary (ADR 0047).
- ADR 0051 links V8 into the binary, built from source without JIT, and starts the Script sandbox as a worker mode of the same binary. The Rust crate never links V8: for the Script sandbox and `plugin-shim` it runs the `goodfetch` binary of its exact version, from `GOODFETCH_ENGINE_PATH` or downloaded on first use into the shared cache, pinned and checked by digest.
- ADR 0057 keeps every capability in this one binary, V8 and DuckDB included, and holds every released file to a Size budget that CI enforces.
