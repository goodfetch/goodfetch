# Every parameter is a setting, resolved through layers in which a lower layer can cap, lock or expose a value

At the owner's request, every parameter can be set. That covers retries, timeouts, batching, concurrency and quotas, guarantees, write modes, schema behaviour, failure handling, formats, payloads, Notifications and OAuth. Settings resolve through five layers, lowest first:
1. Built-in defaults: the best-practice values of the catalog decision.
2. An **Operator policy** on the machine or Daemon, which can set, cap or lock values.
3. User and project configuration.
4. A **Recipe** or the developer's code. Every setting the Recipe declares is locked for the Recipe's users unless the developer **exposes** it, optionally with bounds. What the Recipe does not declare, such as the user's own Sinks, Notification channels and credentials, stays the user's to set. A Recipe may expose `session.source` but never sets or locks it (ADR 0056).
   > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): a Recipe declares the Secret placeholders it needs (`secrets.<name>`) and may expose them, but never binds or locks them, as with `session.source`, and the same holds for `session.http_credentials` and for `proxy.server` and the proxy's credentials, which send a Secret reference's value to a destination they name (a Recipe may still set pool kinds); a Client acting for a model sets none of them.
   > Amended by [ADR 0101](0101-a-model-is-named-provider-slash-model-its-capabilities-and-prices-are-declared-and-every-ai-result-carries-its-priced-usage.md): a Recipe never sets a Model provider's `api_key`, `headers` or `base_url` (it names the model it needs with `ai.model`), and a Client acting for a model never does either; the program's own code, configuration and an Operator policy do.
5. The run itself: SDK arguments, CLI flags, environment variables, an Integration's form.
   > Amended by [ADR 0083](0083-a-program-sets-settings-in-one-typed-option-explicit-values-beat-the-environment-and-no-value-is-silently-ignored.md): environment variables carry no setting, only a closed list of deployment variables that fill connection inputs, which an explicit value beats; layer 4's "developer's code" is a Recipe's code, and a program that is not a Recipe sets the run layer; a project file sent to an Exposed Daemon or Goodfetch Cloud keeps layer 3's rank with the run layer's authority.

> Note (agent decision, accepted by the owner on 2026-10-21; [#225](https://github.com/goodfetch/goodfetch/issues/225)): the files and their shape. One major's Operator policy is `<home>/<major>/operator-policy.toml` and its user configuration `<home>/<major>/configuration.toml`, read by both Products (ADR 0098); a project's configuration is `goodfetch.toml`, found from the working folder upward (ADR 0083). Each is TOML: a `version` (`major.minor`, registered in the format registry as `operator-policy` and `user-configuration`, ADR 0066) and its tables of settings nested by key, `[settings]` in every file, and in an Operator policy also `[lock]`, which sets and locks, and `[cap]`, the largest value a higher layer may give a count or a duration. A duration is a whole number of milliseconds, the wire's unit (ADR 0080). An explicit value above a cap is `setting_locked`; a default above it takes the cap; a Run already going takes a tightened cap at its next admission point, the cap then counting as the Operator policy's value. The Operator policy's version, which the run report names, is `sha256:` and the first 16 hex digits of its file's digest. Each key's authority is in the settings schema: `every` layer; `narrowed`, where a Recipe and the run only narrow what the layers below give (a list with no new entry, a count, duration or price no larger); `configuration`, taken only from an Operator policy and user and project configuration, a Recipe's or the run's value being `setting_locked`; `operator_policy`; `machine`, an Operator policy and user configuration only, `setting_not_applicable` anywhere else; `not_by_recipe`; and `fixed`, the honesty guarantees below, which are the keys `delivery.write_ids_and_epochs`, `delivery.report_guarantee_class`, `webhook.signing` and `secrets.by_reference`, locked by the built-in default. A setting whose value weakens a guarantee or switches off a costly control is marked on the run report's `weakened_by`; the Audit log's record of it waits for area 4.

> Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#227](https://github.com/goodfetch/goodfetch/issues/227): an unset key whose `null` means no bound, such as `admission.max_requests_per_minute` or `timeout.run`, is above any cap, so an Operator policy cap bounds it: the Run takes the cap, set by the Operator policy, and a run already going takes it at its next admission point. RT-02's rate cap is that key, named with its area first (ADR 0083); it spaces a Run's admitted requests evenly, the Generic Cell Rate Algorithm with no burst, and a cap of 0 admits nothing.

> Note (agent decision, pending owner review), 2026-10-25, [#1016](https://github.com/goodfetch/goodfetch/issues/1016): an explicit `null` from a layer above an Operator policy cap, which clears the key to no bound, is above the cap too, so it is `setting_locked` naming the cap, as an explicit value past it is; before, the clear was taken and the Run went unbounded. Every key of `crawl.*`, `fetch.*`, `politeness.*` and `site_preferences.*` can be locked, and each that is a count or a duration capped, through these layers (spec #581's story 314).

> Amended by [ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md), 2026-11-04, [#1906](https://github.com/goodfetch/goodfetch/issues/1906): a Run resolves its settings once, when it opens, so a Run already going no longer takes a tightened cap at its next admission point: every change to the Operator policy or the user configuration, a tightened cap included, whether written by `config.policy_write`, `config.user_write` or by hand, reaches the next Run. The notes of #225 and #227 above keep their caps for a Run that opens under them.

> Amended by [ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md), 2026-11-06, as [#1577](https://github.com/goodfetch/goodfetch/issues/1577) built it (agent decisions, pending owner review): more values weaken a guarantee or switch off a costly control, and each is marked on the run report's `weakened`, the field the #225 note calls `weakened_by`: `run_state.durability` at `periodic` or `off` beside `fast` ([#1927](https://github.com/goodfetch/goodfetch/issues/1927)), `frontier.learning: false` ([#1909](https://github.com/goodfetch/goodfetch/issues/1909)), and Foxhound's `provenance.log: false`, `dataset.records: false` and `fetch.block_classification: false` ([#1921](https://github.com/goodfetch/goodfetch/issues/1921)). `config explain` labels each. The Audit log records the last four, `frontier.learning` as `learning_switched_off` and the other three as `feature_switched_off`, each with its value and its default. Each new setting takes the `every` authority, so an Operator policy can lock it or a Recipe can expose it, and so do `run_state.commit_interval`, `extraction.removal_share` ([#1913](https://github.com/goodfetch/goodfetch/issues/1913)) and `site_preferences.mark_robots_txt_ignored` ([#1919](https://github.com/goodfetch/goodfetch/issues/1919)), which weaken nothing.

A higher layer wins only where no lower layer locked the value. In a Daemon group, settings that only make sense on one machine, such as local addresses, TLS files and browser paths, take a *group member* scope applied only by that Group member (ADR 0055).

This extends ADR 0023, under which every costly control can be switched off and the results say so. It adds who may change a value, which a shared Daemon, a published Recipe and a workflow-tool form all need. Apify's input schema, Terraform's variable validation and Helm's values schema validate what users may pass; the lock across layers is Goodfetch's own addition. Decided in [Export connectors and integrations catalog](https://github.com/goodfetch/goodfetch/issues/88).

## Considered Options

- **Settings without locks**, where the last writer wins: rejected. A Recipe's author could not stop its users from removing the delivery guarantee the Recipe depends on, and a team could not cap concurrency on a shared Daemon.
- **Fixed defaults with a few knobs**: rejected by the owner. Every parameter is a setting.

## Consequences

- **One generated schema.** A single settings schema, generated alongside the Operation catalog, produces the SDK types, the CLI flags, the Recipe manifest's exposed inputs, and the n8n, Zapier and Make forms.
- **`goodfetch config explain`** shows each effective value, the layer that set it and the layer that locked it, like `git config --show-origin`. The run report and the Console show the same; which layers the Console may edit is set by ADR 0031.
- **Weakening is recorded.** Any override that weakens a guarantee class or switches off a costly control is recorded in the Audit log and marked on the results it touches (ADR 0023).
- **Some honesty guarantees stay locked whatever the layer**: the delivery ID and epoch on every write, the guarantee class reported per delivery, webhook signing, and Secret references. These join ADR 0016's controls that cost nothing at run time.
- **Changes ADRs 0016 and 0023.** Their "switchable per run" controls can now be capped or locked by an Operator policy or a Recipe; where nothing locks them, the run can still switch them.
- **Per product major.** The Operator policy and the user-level configuration are kept per product major (project configuration lives with the project), and a new major refuses to start on an older major's Operator policy until `goodfetch upgrade-files` has run (ADR 0030).
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): user configuration and the Operator policy of a major serve both Products, and record the lowest minor of their major that can use them. A newer engine raises it when it writes a key its minor added; an older engine refuses them only when that minor is newer than itself.
- **Limits across runs are not settings.** The install, Daemon, person, named token and Client connection Limits live in the Usage ledger, which every major shares; an Operator policy can only cap them for its own major (ADR 0041).
- **Applies beyond Sinks.** The layering covers every engine setting, not only Sinks. Earlier ADRs that call a control "settable" or "switchable" mean settable through these layers.
- Some settings can only be narrowed by the Recipe and run layers. `trusted_cas`, certificate pins and `any` are set only in Operator policy or user and project configuration (ADR 0042). `pay_domains` and `max_price_per_page` are widened only there or, for `pay_domains`, by a person's answer, and the exchange rates and chain RPC endpoints of Paid fetches are set only there (ADR 0045). `consent_domains` is widened only there or by a person's answer (ADR 0048), and so is `wall_domains`, while `wall_refetch_domains` is widened only there, never by an answer, and `wall_denied_domains` is set only in Operator policy, and no lower layer changes it (ADR 0052). Scriptlets of a Filter list from `filter_lists.extra` run only when it is set there (ADR 0047). On a Daemon with accounts, whose user configuration every member's runs share, all of these, scriptlet-carrying Filter lists included, are written only by the operator role, in Operator policy.
  > Amended by [ADR 0101](0101-a-model-is-named-provider-slash-model-its-capabilities-and-prices-are-declared-and-every-ai-result-carries-its-priced-usage.md): the price table's prices, a model's (`ai.providers.<name>.models.<id>.price`) and a metered proxy's, are set only there too, so no Client lowers the price a person's currency Limit is held to.
