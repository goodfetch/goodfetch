# One product version, a minor every four weeks, each Chrome major in a patch, and contracts versioned on their own

Every Goodfetch package carries one version and is released together: the `goodfetch` binary (engine, CLI, MCP server, Browser host and embedded Console), the Rust crate, the npm and PyPI SDKs, the agent skills, the agent-framework adapters (ADR 0011), the sink processes (ADR 0026), the Integration packages that a package registry versions (ADR 0027, such as the n8n node, the Airbyte source and the LangChain and LlamaIndex loaders), the Homebrew formula and the OCI image. Zapier and Make apps follow their platforms' own versioning. Each SDK release already bundles one exact engine (ADR 0024), so separate version numbers would only describe a pairing that is fixed anyway. Formats that outlive a release carry their own `major.minor` version, separate from the product's. `1.0.0` is V1: it ships when the map's completion criteria are met. The public previews before it are `0.y.z`, where any minor may break. From 1.0, a minor ships every four weeks on a fixed calendar. Since Chrome 153 (September 2026), Chrome stable ships a new major every two weeks ([Chrome blog](https://developer.chrome.com/blog/chrome-two-week-start)). Each one reaches Goodfetch in a patch once the conformance suite and the guard pass, so Goodfetch always carries the current Chrome and the stealth material that matches it. Decided in [Release, versioning and documentation policy](https://github.com/goodfetch/goodfetch/issues/100), on the evidence of the [release and versioning research](https://github.com/goodfetch/goodfetch/blob/research/release-and-docs/rnd/research/2026-10-11-release-and-docs/release-versioning-support.md) and the [documentation research](https://github.com/goodfetch/goodfetch/blob/research/release-and-docs/rnd/research/2026-10-11-release-and-docs/documentation.md).

> Amended by [ADR 0090](0090-products-are-named-goodfetch-collie-and-goodfetch-foxhound-and-share-one-product-version.md): both Products, Collie and Foxhound, and the packages people install carry this one version, the Product version, and every release publishes both, so Foxhound X.Y.Z contains Collie X.Y.Z. Each Product has its own packages (`@goodfetch/collie`, `goodfetch-collie` and so on), and "product major" is the Product version's major.

## Considered Options

- **Independent versions per package** (Stagehand with Changesets, Temporal's SDKs): rejected. They let an SDK fix ship without an engine release, but users then need a compatibility matrix. Playwright, Dagger and Biome keep one version, and version skew between a global binary and a local SDK is the recurring pain in Prisma, Turborepo and Biome.
- **A long `1.0.0-alpha`, `beta` and `rc` series for the previews**: rejected. It suits a few weeks before launch, not months of previews. Ruff, uv and esbuild ship 0.x with breaking minors, and Crawlee for Python went from 0.x to a strict-semver 1.0 in September 2025. A short `1.0.0-rc.N` series still precedes 1.0.
- **A slower or unscheduled cadence** (Playwright about every 6 to 8 weeks with no fixed calendar, Deno every 12 weeks, Rust's 6-week trains): rejected. HTTP impersonation tools lag Chrome by 5 to 7 versions ([State of the art in stealth and challenge solving](https://github.com/goodfetch/goodfetch/issues/64)), and keeping the shipped browser and the stealth material current and consistent needs a release at every Chrome major.
- **A minor at every Chrome major**, every two weeks: rejected. It means 26 minors a year, each with a beta week and a benchmark rerun on the reference host. Pinned browser builds are outside semver, so a patch can carry a Chrome major.
- **A Chrome major only in a minor**, skipping every other Chrome: rejected. The pinned Chrome would fall up to one major behind, the lag this cadence is meant to avoid.
- **Backports to older minors of the current major** (Vite backports to N-1 and N-2): rejected. Minors come every four weeks and are non-breaking within a major, so upgrading is the fix.
- **Bypassing the release-age gates**: rejected. Since pnpm 11, every pnpm project, and since Yarn 4.15, every new Yarn project, holds back releases younger than a day by default; pnpm 11 then silently installs the previous version instead of failing. The gates protect users from supply-chain attacks, so a hotfix ships with the steps to let it through the gate.
- **One Daemon per user across majors**, ADR 0024's first rule: rejected. While two majors are supported, a project on 1.x and one on 2.x would keep restarting each other's Daemon. Gradle likewise runs a separate daemon per version.
- **An online update check** (the `gh` CLI, Deno): rejected. It is more accurate than an age notice, but it is a network call from the user's machine, which users of a scraping framework may not want. ADR 0035's browser version check follows the same rule: it reads a release table shipped with Goodfetch, and an online lookup is opt-in.

## Consequences

- **Contract versions.** These formats each carry their own `major.minor`, checked when read:
  - the JSON-RPC protocol (ADR 0024)
    > Amended by [ADR 0096](0096-the-browser-host-runs-from-either-products-executable-and-goodfetch-cloud-runs-each-run-on-the-product-it-needs.md): between an engine and a Browser host, the two sides settle on the lower of their two minors, as the peer protocol's do, so either may be the newer.
  - the plugin protocol, which includes the sink protocol (ADRs 0026 and 0033)
  - the Plugin manifest and lockfile (ADR 0033)
  - run state and Checkpoints (ADR 0002)
  - the Plan file format (ADR 0009)
  - the Recipe manifest
  - the settings schema (ADR 0028)
  - the Schedule file format (ADR 0036)
  - Dataset and Export formats
  - the Usage ledger (ADR 0041), whose major stays frozen across product majors; it is the exception to the rules below, because older engines open its newer versions, which only add
  - the known-certificates store (ADR 0042), which follows the Usage ledger's exception: its major stays frozen across product majors, and older engines open its newer versions, which only add, and a pin row an engine cannot read stops that host; the Response cache (ADR 0046) is kept per product major, and an engine that finds a newer minor of it runs without it
  - the Clean-up rules' manifest (ADR 0047), whose daily channel publishes a set for every format major a supported product major reads; an engine skips a set whose minor it cannot read and uses the newest one it can
  - the per-user Politeness file and the Politeness store's key and script layout (ADR 0053), which follow the Usage ledger's exception: their major stays frozen across product majors, and newer versions only add
  - the peer protocol of a Daemon group (ADR 0055), whose two sides settle on the lower of their two minors, so Group members of one major and different minors work together during a rolling upgrade in any order
  > Note on the owner's decision of 2026-11-01 (spec #1943): the Client relay's protocol joins these contract formats. It is a public contract, stable at the first publish, and nothing is versioned before it (ADR 0066).

  An engine reads every older minor of a format within its major. A newer minor than it knows, such as a Checkpoint written by 1.5 and resumed by 1.4 on another machine, is refused with a message to upgrade, as the protocol handshake refuses a newer Client. A file of an older major is refused with a message naming `goodfetch upgrade-files`, and one of a newer major with a message to upgrade; the two protocols apply the same rule through their handshake. A format's major changes only with a product major. During the `0.y` previews, each `0.y` minor counts as a major for these rules, for the protocol handshake and for the per-major state below, as Cargo treats `0.y` versions. So each preview minor starts its own Daemon and asks for `goodfetch upgrade-files`, a cost accepted for previews. In this ADR, "major" and "minor" alone mean the product's version, not a format's.
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the Run index, the Schedule store, the Saved identity store, user configuration and the Operator policy, which engines of several minors open at once, record the lowest minor of their major that can use them. An older engine opens them unless that minor is newer than itself, and keeps what it does not know. The list of installed executables joins the Usage ledger's family.

  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#226](https://github.com/goodfetch/goodfetch/issues/226): the `0.y` rule applies to a format's own `0.y` versions as well, in every rule's compatibility function and in the handshakes, the Browser host's included, except the Usage ledger family, whose major never changes: a reader at a format's `0.y` refuses `0.(y+1)` as a newer major and `0.(y-1)` as an older one. A file found refused is answered with `format_version_unsupported`; a settings file's refusal moved there from `setting_invalid`.
- **What semver covers from 1.0.** A breaking change requires a new major in any of these:
  - the TypeScript and Python SDKs and the Rust crate's top-level `goodfetch` API
  - the Operation catalog: operation names, inputs, outputs and classes, so MCP tool names and schemas too
  - CLI commands, flags, `--json` output and exit codes
  - setting keys and their meaning
  - the contract formats above
  - webhook Sink and Notification payloads
  - the HTTP listener (ADR 0027)
  - error codes

  > Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): semver covers each Product's catalog. An entry leaving Collie's catalog is breaking for Collie, one joining it from Foxhound's is additive. The Collie client packages (`@goodfetch/collie-client`, `goodfetch-collie-client` on PyPI and crates.io) are released with every version and fall under semver like the SDKs, and the API breakage checks cover them.

  Semver does not cover:
  - Console screens, although the Console's functions stay, such as the reconciliation of uncertain Effects (ADR 0029)
  - human-readable CLI output and log text
  - internal `goodfetch-*` crates, published at `0.0.x` as uv does
  - anything Experimental
  - pinned browser builds and stealth material (fingerprints, impersonation profiles, challenge detectors)
  - AI prompts and the model-facing wording of tool descriptions
  > Amended by [ADR 0132](0132-each-request-may-carry-its-callers-trace-context-across-goodfetchs-own-links-and-the-engines-spans-stay-experimental.md): span names, span fields and the engine's targets in an OpenTelemetry export are Experimental, outside semver like log text, until an ADR promotes them.

  A changed default is breaking only when it weakens a guarantee or a security control. A tuning default, such as a timeout, may change in a minor and is listed in the release notes. Dropping a runtime past its end of life (ADR 0024) or raising the minimum Rust version is announced one minor ahead and happens in a minor, as Pydantic, Vite and Playwright drop Node and Python lines.
  > Amended by [ADR 0082](0082-sdk-schemas-come-from-each-languages-own-schema-types-payloads-are-typed-per-label-and-results-keep-what-the-sdk-does-not-know.md): an SDK widens in a minor the supported major range of a pinned dependency (ADR 0077's G7) it can support in two majors at once, such as Pydantic; a dependency whose types name exactly one major, such as the Rust SDK's `schemars`, serde and serde_json, moves to a new major only in a Goodfetch major; and a range narrows under this rule, once the dropped major is past the end of life upstream declares or, where it declares none, 12 months after its successor's first stable release.
- **Experimental.** From 1.1, a new operation, setting or SDK method may land Experimental. It is marked in the catalog, the docs, the tool description and the generated types, and warns once per process when used. It stays outside semver until promoted, so any minor may change or remove it, like Biome's nursery rules and Ruff's preview mode. Every V1 capability is stable at 1.0, so Experimental never defers V1.
  > Amended by [ADR 0132](0132-each-request-may-carry-its-callers-trace-context-across-goodfetchs-own-links-and-the-engines-spans-stay-experimental.md): span names, span fields and the engine's targets in an OpenTelemetry export are Experimental from 1.0. They are marked in the reference only, never in the catalog or generated types, and nothing warns at run time; they are trace output, not a V1 capability.
  > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): generated types mark it with TSDoc's `@experimental` and a docstring line in Python and rustdoc; no language has a type-level Experimental marker that is not a Cargo feature.
- **Deprecation.** A deprecation lands in a minor. It shows as a warning in the SDKs and on the CLI's stderr, as `deprecated` in the MCP tool schema, and in the release notes, which name the replacement. Removal comes no earlier than the next major and no earlier than six months after the deprecation.
  > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): every deprecated name carries its language's type-level marker (TSDoc `@deprecated`, PEP 702 `@deprecated` with overloads for arguments and values, Rust `#[deprecated]`), rendered from the catalog's deprecation; a plain-data field or a settings `TypedDict` key, which PEP 702 cannot mark, keeps the runtime warning and is listed in the release notes. In MCP, a deprecated tool's description opens with its replacement and its `inputSchema` carries JSON Schema's `deprecated`, since a Tool has no field of its own.
- **Channels.**
  - **Stable:** npm `latest`, PyPI, crates.io, Homebrew, the installers and the OCI `latest` tag.
  - **Beta:** an `x.y.0-rc.N` cut one week before every minor (npm `next`, PyPI `x.y.0rcN`, crates.io `-rc.N`).
  - **Patches:** shipped whenever a fix is ready, on the stable channel, built from the minor's `release/x.y` branch (ADR 0032).
  - **Nightly:** built from `main` to npm `nightly`, GitHub pre-releases, a Goodfetch-hosted Python index on `goodfetch.dev` that lists the pre-releases' wheels (never PyPI, ADR 0057) and an OCI `nightly` tag, but not to crates.io or Homebrew.
  - **Size budget:** a nightly, release candidate or release whose files break a ceiling of ADR 0057 is not published. Each release publishes its binaries' debug symbols beside them, and its notes list every file's size.
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): a release builds, gates, signs and publishes both Products, or neither, and every channel above carries both Products' files. Each Product's executable has its own debug symbols and SBOM, and the notes list each Product's files with their sizes.
- **Browsers and stealth between minors.**
  - **Chrome:** each new Chrome stable major ships in a patch, once it passes the conformance suite and the guard (ADR 0019). A patch may also move the pinned Chrome for Testing build within its major, security point releases included, and update stealth material.
  - **Other browsers:** a patch may move Playwright's Firefox and WebKit builds, Camoufox, Patchright and Lightpanda to a newer build within their own upstream major, security point releases included. A new upstream major of these comes only with a minor.
  - **Clean-up rules:** every patch refreshes them (ADR 0047). What they block, hide or remove is outside semver, as stealth material is, and the release notes name their version.
  - **Release notes:** they always name every browser build.
  - **Supported Chrome:** besides the pinned build, a run may use an installed Chrome. That Chrome is supported on the current stable, beta or dev channel, every stable major released in the last eight weeks, and the current Extended Stable, which keeps an eight-week cycle for enterprises; all are tested against the guard and the conformance suite. A musl host's distribution Chromium follows the same rule.
  - **Best effort:** older builds, Edge and Brave run best effort, with a warning.
- **Majors.** A major ships only once breaking changes have been collected and announced. It comes with a migration guide with before-and-after examples. `goodfetch upgrade-files` upgrades every contract format, like `biome migrate`; the name keeps it apart from the `migrate` signal that moves a run (ADR 0002). Files kept in a project (Plans, Recipe manifests, project configuration) are upgraded in place, where version control keeps the old copy. Per-user and per-install state gets a new major's copy, and the previous major's files are never changed. SDK code relies on the deprecation warnings rather than codemods.
- **Support.**
  - **Previews:** a `0.y` preview is supported until the next `0.y` minor ships.
    > Note (owner's decisions, 2026-11-11, grilling of decision G-18 of the consolidated review: Q1 answered "yes all", Q4, Q5 and Q7 answered "yes to all", and Q9, Q12 and the correction C1, put after an independent check of the grilling's drafts, answered "Yes to all", each on the grilling's recommended option as put; the wording is the grilling session's, and the owner did not read it): a preview is defined by what a user can do (Q1). `0.1.0` holds at least this, a minimum and not a cap: a program holds a `Page` and a `Crawl` in TypeScript, Python and Rust; a crawl runs from a file with no code; the CLI works; and `just compare` reruns (Q4). It goes out once the refactor's last step (spec #1577's closing tickets) and line 1 of Features have both landed, and each later line of Features ends in a preview of its own, unless the owner skips one (Q5, which stands on C1's corrected reason). Between previews, `main` may break without asking the owner each time, on three conditions: the next preview's `upgrade-files` upgrades every file the previous preview wrote; the next preview's release pull request lists every break, and the owner approves that list; a patch of a preview breaks nothing (Q7). From `0.1.0`, the five add-only files (the Usage ledger, the known-certificates store, the per-user Politeness file, the Politeness store's key and script layout, and the list of installed executables) may gain fields but never change or remove one, as their rules above and ADR 0098 already say; the first preview's spec reads each before the publish, as the last chance to change one (Q7, Q12). That spec is cut when line 1 of Features is next, by the agent that cuts line 1's specs, from the grilling's outline (Q9), which is not yet in the repository or the tracker; none of this is built yet.
  - **Current major:** only the latest minor gets patches.
  - **Previous major:** its last minor gets security and data-loss fixes for 12 months after the next major ships, published under npm tags such as `latest-1` so that `latest` never moves back.
  - **Per-major state:** each major runs its own Daemon, with its own runtime file, socket, Console port and HTTP listener port (ADR 0027), so a 1.x and a 2.x project never restart each other's (amends ADR 0024). The Operator policy and user-level settings (ADR 0028) and the per-install layout of ADR 0002 are also kept per major. A new major that finds an Operator policy only for an older major refuses to start and names `goodfetch upgrade-files`, so an operator's caps and locks are never lost silently.
    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#226](https://github.com/goodfetch/goodfetch/issues/226): "refuses to start" is the settings load every Run's start, `config explain` and the `browsers` commands make: when the major's folder holds no Operator policy and the newest older major's does, it fails with `format_version_unsupported` naming `upgrade-files`. The executable itself still starts, so `upgrade-files` and the Daemon's commands run. `goodfetch daemon install` registers one service per major. The browser cache is shared, because its builds are checked by digest.
    > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the per-major state, the Daemon included, is shared by Collie and Foxhound, and the Daemon runs the fullest Product installed for its major.
  - **Shared across majors:** the Usage ledger of ADR 0041 is a contract format whose major stays frozen across product majors. Its versions only add, and each Limit row carries a *must understand* flag, so an older engine refuses runs under a Limit it cannot read rather than ignoring it.
  - **After support ends:** every version that no longer gets fixes is marked deprecated on npm, as Puppeteer does.
  - **Age notice:** a binary more than three months past its own release date prints one line a day. The line says that newer versions carry security fixes and a current Chrome, and gives the upgrade command. It compares dates only, makes no network call, and a setting turns it off. It goes to stderr only, never into `--json` output or a stdio protocol stream (Attached engine or MCP).
    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#226](https://github.com/goodfetch/goodfetch/issues/226): the release build records its release date as `GOODFETCH_RELEASE_DATE` (`YYYY-MM-DD`) at compile time, which the release pipeline (area 1) sets; any other build has none and never prints the notice. "More than three months" is by the calendar, in UTC. The day it was last shown is kept per user in `<home>/age-notice`. The setting is `version.age_notice` (default `true`), set in user configuration or an Operator policy only. Every command but the hidden `daemon launched`, which has no terminal, prints it before running.
  - **Rust:** the crate's minimum supported Rust version is the latest stable minus two releases, tested in CI and raised only in a minor.
- **Hotfixes under release-age gates.**
  - **Advisory:** every security fix ships with a GitHub Security Advisory and a CVE, so `npm audit` and `pnpm audit` find it. `pnpm audit --fix` also adds the exclusion.
  - **Exclusion snippets:** the advisory and the release notes give a copy-paste exclusion for pnpm, Yarn, npm, Bun, Deno and uv. Each is scoped to `goodfetch` and `@goodfetch/*`, so the platform-binary packages are included, and reminds the user to remove it afterwards.
  - **Ungated channels:** the installers, Homebrew, the OCI image and GitHub Releases have no gate and carry the fix at once. With `GOODFETCH_ENGINE_PATH`, a gated npm or PyPI project can run the fixed engine the same day.
- **Security policy.** `SECURITY.md` uses GitHub private vulnerability reporting, as decided in [Security and compliance model](https://github.com/goodfetch/goodfetch/issues/73). Each report is acknowledged within three business days, the fix ships as above, and disclosure is coordinated within 90 days of the report.
- **Release gates.** Any of these blocks a release:
  - **Conformance:** suites green on every supported platform and runtime (ADR 0024). The online conformance against real vendors reports without blocking (ADR 0043), here and wherever a release waits on the conformance suites.
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each suite runs on the smallest Product that carries its contract, and before any publish every file of both Products also runs from its own bytes: each archive's executable prints its version and answers `hello`, and each wheel and npm package installs and starts its engine.
  - **Benchmark, for minors and majors:** ADR 0025's rule, run on the release candidate during its beta week against the previous Goodfetch release. A correctness failure always blocks. A primary metric worse than the previous release by more than its Δ blocks unless the release notes explain it. A blocking result delays that minor; the next minor keeps its own date. A patch runs the correctness oracle only, on a GitHub-hosted Linux runner (ADR 0032), plus the guard when it carries a new Chrome major. Competitor rows are rerun alongside. When a competitor's configuration changed, they wait for ADR 0025's 14-day maintainer review, so they never hold up a release.
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each family runs on the smallest Product that carries it, and startup and binding overhead on each Product's executable; each result names its Product.
    > Note (owner's decision, 2026-11-10, [#2252](https://github.com/goodfetch/goodfetch/issues/2252), Q4): a competitor's row still never holds up a release. One owner checkpoint is added: at a release candidate, each row where a Product is behind a competitor is listed with its gap, its measured cause and the next cut, and the owner accepts the list before the minor is promoted. Until `bench/` runs its campaigns the list is read from `just compare`'s report.
  - **API breakage checks:** cargo-semver-checks for the crate, an API Extractor report for TypeScript, `griffe check` for Python, and a diff of the Operation catalog and settings schema, each against the previous release of the same major. An unannounced break blocks.
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each Product's crate, packages and catalog are checked against the same Product's previous release of the major.
  - **Notice inventory:** ADR 0018's license check.
  - **Supply chain:** signed releases (ADR 0016), and the supply-chain gates of [Security and compliance model](https://github.com/goodfetch/goodfetch/issues/73):
    - trusted publishing with provenance on crates.io, npm and PyPI
    - GitHub artifact attestations and immutable releases
    - a CycloneDX SBOM
    - `cargo-deny` and `cargo-audit` and their npm and Python equivalents
    - Actions pinned by SHA
    - a valid Platform signature on every macOS and Windows executable Goodfetch builds (ADR 0039)
    - OpenSSF Scorecard
  - **Docs:** the docs build, and every example in them runs.
- **Changelog and release notes.** One `CHANGELOG.md`, generated with git-cliff from Conventional Commits, which the product's commits follow from the first preview on. A hand-written page for every minor gives the highlights, the deprecations and their replacements, the browser builds, the contract-format versions and a link to that minor's benchmark results, completed with the competitor rows once they are published.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each release's entries are grouped in two, changes that reach both Products and changes that reach Foxhound only, decided by the paths each commit changes; the notes say when Collie has no change of its own.
- **Documentation.**
  - **Tool and hosting:** a Docusaurus site, chosen for its built-in versioning. Starlight's versioning is still a community plugin, Mintlify is proprietary hosting whose llms.txt covers only the default version, and MkDocs Material has been in maintenance since November 2025. The site is hosted on Vercel as its own project and served at `goodfetch.dev/docs` through a rewrite from the marketing site, which lives in its own repository under the `goodfetch` organization because it is not a released surface. Production always builds `main`'s site, deployed by Goodfetch's CI on each push to `main`. After publishing a stable release or a patch, the release opens a pull request against `main` that replaces that line's frozen docs version (the stable version, or the previous major's copy) with one cut from the release tag's `docs/`, and adds that release's section to `main`'s `CHANGELOG.md` in version order. For `x.y.0` it also adds the minor's release-notes page and `bench/results/<version>/`, and for `x.0.0` it keeps the outgoing stable version as the previous major's frozen copy. Candidates open none. Production redeploys when that pull request merges, so stable content changes only with a release. Previews per pull request come from Vercel's Git integration, with its production deploys turned off. Vercel sets custom headers, so `llms*.txt` is served as `text/markdown` like the `.md` pages, which GitHub Pages cannot do (it serves `.txt` as `text/plain`); it also gives per-pull-request previews and shares one host with the marketing site. Decided in [Release promotion, release branches, vendor conformance and docs hosting](https://github.com/goodfetch/goodfetch/pull/131), on the gaps the [Repository, CI and release spec](https://github.com/goodfetch/goodfetch/issues/130) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/130#issuecomment-6114909646).
  - **Kept versions:** stable (the latest minor), `next` from `main`, and a frozen copy of the last minor of each previous major still supported. Each item carries "Added in" and "Deprecated in" badges generated from the catalog, and a banner marks `next` and old majors.
  - **When docs change:** stable docs change only with a release, because the stable version is a frozen copy that only the release updates (above). Docs ahead of the release are a recurring complaint (browser-use #902, scrapy #5324).
  - **Reference pages:** generated from the Operation catalog and the settings schema, one page per operation and per setting, with TypeScript, Python, Rust, CLI and MCP tabs showing each real signature, as Playwright and Pulumi generate every language from one source. TypeDoc, a Griffe-based Python reference, docs.rs and `clap-markdown` give each language its native reference in addition.
