# The Console is an ordinary Client: one Console per user sees every run through a Run index

The Console reads and acts through the same JSON-RPC protocol and Operation catalog as every other Client (ADRs 0011 and 0024). It carries them over a WebSocket on its own origin, authenticated by the `HttpOnly` cookie of ADR 0024, and fetches large files (page bodies, screenshots, Exports) by handle with plain HTTP `GET`, as a remote Client streams `page.body`. Its `hello` names the surface `console`, which gives the Audit log the surface ADR 0029 records with each reconciliation. One Console per user and per product major (ADR 0030) sees every run of that user and major on the machine:
- **The Run index lists runs.** It is a small per-user, per-major SQLite catalog that every engine, Attached or Daemon, writes when a run starts and when one of its three axes changes. Each row holds the run's ID, its location (a run file, or the run inside the shared database of ADR 0002's per-install layout), Recipe, Lifecycle, Verdict, Completeness, timestamps, a Usage summary, the Schedule, occurrence and trigger that started it (ADR 0036) and, while the run is live, the engine that owns it. In a Daemon group, the Lead Daemon keeps a group Run index fed by every Group member, whose rows name the owning Group member (ADR 0055).
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the Run index and the Console of a major serve both Products, whichever runs the Daemon. Each row records the Product its run needs. A Console a Collie Daemon serves lists a run that needs Foxhound and forwards its live actions, but that run's Foxhound views and the Daemon's own writes to it answer `not_in_product`.
- **The runs stay the truth.** `goodfetch runs reindex` rebuilds the index by scanning the configured run locations, the per-install database and any paths it is given; a run it cannot find stays as a missing row. A row whose file is gone shows as missing; it is never silently dropped. A run discarded on purpose, such as by a Schedule's retention, keeps its row marked *erased*, and reindex leaves it so (ADR 0036).
  > Note (agent decision, accepted by the owner on 2026-10-21; [#219](https://github.com/goodfetch/goodfetch/issues/219)): each Run index row has a `presence`, `present`, `missing` or `erased`. `runs reindex [PATH...] [--json]` reads the per-major `runs` folder, `run_state.location` when user configuration or the Operator policy sets it, and each path given, a Run's folder or a folder of them; a Run found in two places keeps the first. A found Run keeps the owner its row named only while a reader's test finds its writer live. The per-install database is not read: that layout does not exist yet.
  > Note (agent decision, on a default, not read by the owner; [#835](https://github.com/goodfetch/goodfetch/issues/835)): the catalog operation is `run.list` (the `run.*` namespace every Run operation has, ADR 0099), a read on every surface. It answers the Run index's rows, every presence kept, filtered by the engine on each field given (tags, every one; the Recipe, Schedule, occurrence and trigger of the reserved tags, ADR 0036; Product; each axis; start and end as ranges from an included point until an excluded one, compared as instants; a text found, ignoring case, in the Run ID or a tag) and sorted by one key (start by default, newest first; end, Run ID, Recipe, Schedule, occurrence, trigger, Product or an axis), a value a row lacks sorting last in ascending order and ties following in Run ID order. It answers every matching row at once: no page yet. A row's Recipe is its reserved tag `goodfetch.recipe:<name>`, which the Recipe's starter sets ([#1209](https://github.com/goodfetch/goodfetch/issues/1209)), so run state keeps it and `runs reindex` restores it with the other tags; the row gains no column. The Runs screen keeps the filter in the address's query, one parameter per field (`tag` once per tag, `started_from`, `started_until`, `ended_from`, `ended_until`), replaced without a history entry, and follows a live run's axes and status line from `run.axes_changed` and `run.progress`, reading the list again for a run it does not list, an axis change under a filter that names an axis, a resync, or a reconnect.
- **Committed state comes from the run's database.** The Daemon reads any run through SQLite WAL readers, live or not, so the single writer of ADR 0002 holds.
- **Live actions go to the owner.** On a live run it does not own, the Daemon forwards each live action to the owning engine. That covers takeover, confirmation, reconciliation, the event stream and live frames. It reaches an Attached engine through the private endpoint ADR 0024 gives it for its workers: the index records the endpoint, and its token sits in a separate `0600` file. Changes ADR 0024, whose private endpoint served only those workers. In a Daemon group, a Group member forwards to the Group member that owns the run, or redirects heavy streams to it (ADR 0055).
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#222](https://github.com/goodfetch/goodfetch/issues/222): a live Run's index row names its owner as `{daemon: <endpoint>}` (token from the major's runtime file) or `{attached: {address, token_file}}` (an Attached engine's private endpoint, token from that file). Any engine that cannot take the writer lock forwards there, a Daemon included; #219's note that an Attached engine's Runs are never forwarded no longer holds.
- **"Needs you".** The Console's single list of everything waiting for a person (Human pauses, confirmations, uncertain Effects, Plan diffs, runs stopped by a Limit, results to review) covers every run in the index.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#852](https://github.com/goodfetch/goodfetch/issues/852): each source fills two primitives, its items now and when they may have changed (`Changes`); the engine's driver merges them, orders them by `since` then ID, keeps each item's first `since`, publishes every appearance, change and removal as the lossless `needs_you.changed`, folds them into `events.resync`'s new `needs_you`, and answers `needs_you.list` and `needs_you.dismiss` only once every source has tried its first read. `needs_you.list` pages hold 100 items, `after` taking the last page's `next`. An item carries `details`, its kind's own fields (beside spec #592's `{ id, kind, since, run, schedule, summary, actions }`), and its `actions` name catalog operations. `needs_you.dismiss` answers `{dismissed}`, false for an item no longer listed or one only resolving removes; a dismissal is kept in a `needs_you_dismissed` table of the Run index, so every engine of the major hides it across restarts, and forgotten once no source holds the item. The Run index row gains `stop_reason`, from which the `run_stopped_by_storage` source lists each Run a storage stop left stopped; both storage sources read again at each storage sample. A `storage_level` item names its level and its filesystem's first sampled folder, not its free space, which changes with every write.
- **An Attached engine can start the Daemon.** When a Human pause or a Notification needs a link and no Console is running, it starts the Daemon on demand. A script's own Console (ADR 0024) remains for people who want no Daemon.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-27, [#830](https://github.com/goodfetch/goodfetch/issues/830): a script asks for its own Console by starting its Attached engine with `attached-engine --console-address <host:port>` (port 0 takes a free port), the value `console.address` takes for that run: the user configuration's `console.address` is the Daemon's and never reaches an Attached engine. The engine serves its Console build there under the Daemon's headers and sign-in, with a per-launch token, and the stdio `hello` reply alone carries `console_link`, `<url>#token=<token>`; the Console's Connections reach the engine's own Runs and no Daemon, so `daemon.*` and the sign-in operations answer as on any Attached engine. The listener closes with the engine, so nothing listens once the script ends. An SDK crate's linked engine, which carries no Console build, serves none whatever it is given.

Decided in [Console data access](https://github.com/goodfetch/goodfetch/issues/104).

Evidence from the competitor survey made for that ticket:
- Temporal, Prefect and Hatchet serve their UI from the same API as their SDKs. Dagster's GraphQL is "primarily for internal use by the Dagster webserver", and n8n keeps an internal API beside its public one.
- MLflow names its unindexed file store as the usual cause of a slow UI.
- No live-view vendor documents a control lock between automation and a person.

## Considered Options

- **ADR 0027's HTTP listener as the Console's transport**: rejected. It is off by default and built for workflow tools, so the Console would break whenever it is off.
- **A private API for the Console** (REST or GraphQL, as Dagster and n8n have): rejected. It is a second API to keep in step with the catalog, and Goodfetch Cloud would have to copy it.
- **Scanning run directories to list runs** (TensorBoard's log directories): rejected. It gets slower with every run and misses runs stored outside the scanned folder.
- **One Console per engine**: rejected. Two scripts would give two Consoles on two ports, each with its own "Needs you" list.
- **Short-lived signed live-view links in Notifications** (Browserbase, Browserless, Anchor): rejected. A link that grants control sits in chat history and is forwarded with messages.
- **Answering pauses and confirmations with chat-app buttons**: rejected. A Slack or Teams button identifies a chat user, not a Goodfetch person who can verify a passkey.
- **An in-page recorder such as rrweb** (Browserbase's recordings): rejected. It runs in the page's main world, where the page can see it, tamper with it and detect automation; the guard of ADR 0019 stays in an isolated world.

## Consequences

**Where runs live.**
- **Default folder.** Run files and directories go by default to a per-user, per-major data folder, such as `~/.local/share/goodfetch/1/runs/<run-id>/` and its macOS and Windows equivalents. The location is a setting (ADR 0028). Each engine records its runs in the index wherever they are, so a run outside the default folder is still listed.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#215](https://github.com/goodfetch/goodfetch/issues/215)): the per-major folder is `<home>/<major>/`, where `<home>` is `GOODFETCH_HOME` or else the `goodfetch` folder of the OS's data folder, and `<major>` is the Product major, `0.y` during `0.y` previews (ADR 0030). A Run's folder `runs/<run-id>/` holds its state, `run.sqlite`, and the writer's lock file, `run.lock`; the Run index is `<home>/<major>/run-index.sqlite`, whose rows record a folder inside the per-major folder relative to it and any other absolutely.
- **Changes ADR 0002:** the per-run layout gains this default location and the Run index.

**Events and reconnects.**
- **Positions.** Every event carries a position that only goes up. The Console keeps one position per engine and resubscribes from it after a reconnect. When the engine no longer holds that position, it sends a fresh snapshot of the screen's state and continues from there.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#216](https://github.com/goodfetch/goodfetch/issues/216)): positions count from 1 in each engine process, telemetry events included. The engine keeps its last 4,096 lossless events, and `events.subscribe {after}` resumes after any position from the last one it no longer keeps to the last it gave. Any other position, older or ahead of it, starts the subscription with an `events.resync` event at a new position, whose `runs` give the axes of every Run the stream has reported, then the stream. Each engine process names itself with a new `engine_instance` in its `hello` result, and `after` is `{engine_instance, position}`, so a position another engine instance gave, as before a Daemon restart, also starts with `events.resync`. Changed on 2026-10-21: `hello` names the engine instance and `after` carries it, so a Client that reconnects to a restarted Daemon resyncs instead of reading positions it already read.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-30, [#1768](https://github.com/goodfetch/goodfetch/issues/1768), on the note above: `events.resync`'s `runs` give the axes of every **live** Run the stream has reported. A Run leaves them as its end's `run.axes_changed` is published, so a Client that resyncs knows a Run it held as running and finds missing has ended, and reads its axes from `run.list`, the Run index, as the Console's Runs screen already does on each resync. Before, the engine kept the axes of every Run it had ever reported, about 120 bytes a Run for its life, which a Daemon running Run after Run never gave back. The 4,096 kept lossless events stay a window of the last ones: on the Daemon it is full after about 2,000 Runs (two `run.axes_changed` each, about 1.5 KB a Run, so about 3 MB), and holds no more after.
- **No loss.** Lossless events (records, axis changes, "Needs you" items) are never missed across a reconnect.
- **Fallback.** Where a WebSocket cannot be opened, the Console falls back to Server-Sent Events plus `POST`, carrying the same messages.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-24, [#822](https://github.com/goodfetch/goodfetch/issues/822): `GET /protocol/events` (a signed-in read of the Console's own, as `GET /bodies/…`) opens a Connection and answers `text/event-stream`: a first `stream` event whose data names the stream (16 bytes of the OS generator, in hex), then one `message` event per JSON-RPC message the engine sends. `POST /protocol/messages/<stream>` carries the page's waiting messages, one per line, at most 16 MiB, with the Console's own `Origin`, the cookie of the sign-in that opened the stream and that sign-in's `X-CSRF-Token`; it answers `202`, `403` without or with another CSRF token (each refusal in the Audit log), and `404` for a stream that ended or another sign-in's. The page posts one body at a time, so its messages keep their order, and the page leaving ends the Connection. The page opens a WebSocket first; a Connection that ends before the engine sent anything makes the next attempt use the other transport, and the transport of a Connection that carried a message stays in use.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-24, [#822](https://github.com/goodfetch/goodfetch/issues/822): a Connection that sends nothing for 10 s is asked `engine.info` (its `hello` counting as the first question), and one still silent 10 s later counts as stalled and is abandoned as a dropped one is. After a drop the Client sends again each subscription after its last position, and each read and idempotent write waiting for its answer, which also wait for the next Connection when called without one; an Effect fails with `connection_lost`, an `UnavailableError` (ADR 0079), and the operation map `xtask codegen` writes for the Console carries each operation's class for it. A subscription that has read no event resumes from the new Connection's present, since `events.subscribe` names no position to start from.

**Runs that no engine is running.**
- **Taking the writer role.** ADR 0003's epoch cannot be enforced inside the run's own file, so the engine that writes a run holds an exclusive OS lock on a lock file beside it (not on the database itself, which Windows would then close to readers). To write to a run, the Daemon takes that lock and the next run epoch (ADR 0003). If the lock is held, the owner is alive: the Daemon forwards the action to that owner instead. A stale owner recorded in the index never blocks, because a dead process holds no lock.
  > Note (agent decision, accepted by the owner on 2026-10-22; [#219](https://github.com/goodfetch/goodfetch/issues/219)): the first action that takes the writer role is `run.abort` of a Run no engine runs: the engine, of either Product, takes the lock, then the next run epoch (written to the run file before the new writer opens it), then writes the end; resume ([#218](https://github.com/goodfetch/goodfetch/issues/218)) and adopt take the role the same way. A reader tests the lock with a shared lock it releases at once (ADR 0037's consequence), so a writer that finds the lock held first forwards to the owner the Run index names, then retries it 5 times, waiting 32, 65, 129, 258 and 516 ms, each scaled by a jitter from the `Entropy` between three and five quarters, before failing with `run_busy`. A forward to a Daemon reaches the Daemon of the engine's major, with the token of its runtime file, only when that file's endpoint is the one the row names; it calls `run.abort` with `forwarded: true`, which an engine that does not own the Run answers with `run_not_owned` instead of taking the writer role itself, so a stale row can never send an abort round in a loop. A Collie engine refuses with `not_in_product` to take the writer role of a Run that needs Foxhound, before it writes anything (ADR 0098). Corrected 2026-10-21: struck the sentence saying an Attached engine's Runs are never forwarded, which #222's note above overrides.
- **Answers that need no user code** apply at once, such as "it happened" or "leave uncertain". Erasing a Dataset needs no user code either and applies at once.
- **Answers that need handlers.** "It did not happen" and "raise the Limit and resume" resume a Recipe run in the Daemon. They mark an SDK script's run as waiting for its script, which resumes it the next time it resumes that run ID. The Console says so and offers **Copy resume command**.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#887](https://github.com/goodfetch/goodfetch/issues/887): "raise the Limit and resume" answers a `run_stopped_by_limit` item of "Needs you", which the engine lists for each Run the Run index holds stopped by a Limit (stop reason `limit`) while that Limit still holds it: its period has not started again since the stop, and no row of the same scope, Usage kind, currency and period was set again since the stop with something left (a person's raise rewrites the row's `set_at`). Its `details` carry the Limit as `limit_reached` names it, the `amount` the holding row allows, the Product the Run `needs` and, for a Run tagged `goodfetch.recipe:<name>`, its `recipe`; its actions are `usage.raise`, `run.resume` for a Recipe's Run, and `needs_you.dismiss`. The Console raises the Limit with `usage.raise` (the scope, scope ID, Usage kind, currency and period the item names, and the amount the person types, above the one it allows now), then, for a Recipe's Run, calls `run.resume` on the Daemon's Connection; for an SDK script's Run it marks nothing in the engine: the Run stays `stopped` with its stop reason, which any start with its Run ID resumes, and the Console says it waits for its script and offers **Copy resume command** (`<executable> run resume <run-id>`, as the run's page does). The item leaves the list once the Limit no longer holds the Run, read again at each storage sample. Until a Recipe runner registers an engine-side driver (`recipe start`, #1209), a Daemon's `run.resume` of a Recipe's Run drives no Recipe code.
- **A script that ends.** A Human pause pending when the script ends stops with the run.

**The live view.**
- **A channel of its own.** It is a per-Session channel, opened only while someone watches and kept apart from the credit-based event stream. The newest frame wins. A person's input travels on an ordered path where nothing is dropped.
- **Tiers, chosen automatically and each settable:**
  1. **The real window.** When the browser is headful on the person's own desktop, "Take control" can bring that window to the front.
  2. **CDP screencast** everywhere else, the default for headless browsers. It sends JPEG frames sized by `devicePixelRatio` under acknowledgement-based flow control. For remote viewers, the screencast is relayed over WebRTC as video, and falls back to JPEG frames over the WebSocket when WebRTC cannot connect.
  3. **WebRTC H.264.** Where the browser runs headful in a virtual display (Linux containers, the OCI image, a Browser host, Goodfetch Cloud), the engine captures that display at about 25 fps, and falls back to tier 2 when capture fails or WebRTC cannot connect. Steel moved from screencast ("4-12fps, unstable") to this.
     > Amended by [ADR 0130](0130-the-live-views-webrtc-video-is-vp8-encoded-with-libvpx-not-h264.md): every WebRTC video of the Live view, this tier's and tier 2's relay, is VP8 encoded with libvpx; H.264 is declined because it needs a patent licence.
  
  Input goes through CDP (`Input.dispatch*`, `Input.insertText`, `Input.imeSetComposition`).
- **The Session, not one tab.**
  - **Tabs:** it lists the Session's tabs and follows new popups.
  - **Dialogs:** native dialogs and basic-auth prompts become Console dialogs.
  - **Files:** the page's file chooser opens a Console file picker, whose file lands in the run's directory; downloads appear in the drawer.
  - **Clipboard:** paste and copy need an explicit gesture.
  - **Keyboard:** keys carry both `code` and `key`, so non-QWERTY layouts work, and IME composition is forwarded.
  - **Phones:** touch input and a pop-up keyboard field.
- **One holder at a time.**
  - **Watching and control.** Any number of people can watch. "Take control" locks the Session for one person, and automation, already waiting in its Human pause, resumes only after "Hand back" and a passing Page check, or when the pause is resolved.
    > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): a pause a program raised with `page.pause()` ends on a person's "Hand back" as on "Done": when its `until` condition holds, or at once when it has none; otherwise control returns to *waiting*.
  - **Idle holder.** After 2 minutes without input the holder is warned. After 3, control returns to *waiting*, never to automation.
  - **Taking over.** Another person may ask for control, which is granted after 30 s without an answer. An operator can force it.
  - **Timings** are settings.
  - **Audit.** Taking control, handing back and the start and end of input go to the Audit log. Keystrokes never do.
    > Amended by [ADR 0113](0113-a-human-pause-whose-page-closes-raises-call-cancelled-naming-what-closed-and-a-lost-live-view-ends-no-pause.md): each Human pause ended by a person's "Done", "Hand back" or "Decline" (with the person), or by its page or browser closing (`by: "browser"`, no person), also goes to the Audit log; the Live view closes no page a Human pause holds.
  - **Consent prompts.** While a person holds control, the Consent prompt runner's clicks stop, and the person's own answer is recorded as theirs for that Session only; a grant holder's is recorded under the grant (ADR 0048).
- **Embeddable in users' own products**, as Browserbase, Steel, Hyperbrowser and Kernel allow.
  - **The grant.** `liveView.grant(session, mode, ttl, origins)` returns a token scoped to one Session. It is short-lived, single-use for opening the connection, tied to its origins through `frame-ancestors`, and revoked when the Session ends or by `liveView.revoke`.
  - **What a grant allows.** A control grant lets its holder act in the page, for example to complete a login, MFA or CAPTCHA, and the pause then resolves through its Page check. A grant never confirms or reconciles an Effect, for the same reason chat-app buttons cannot: its holder is not a Goodfetch person.
    > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): a grant holder ends a Human pause a program raised with `page.pause()` only through its `until` condition; "Done" and "Decline" are a person's.
  - **View-only is enforced by the engine,** which drops the viewer's input. Browser Use's and Anchor's view-only modes are only drawn in the embedding page.
  - **Limits, audit and Usage.** The number of viewers is a setting, grants are audited, and live-view minutes count as Usage.
  - **Packages.** A `<goodfetch-live-view>` web component and a React wrapper ship with connection, control and Session events.

**Run traces.**
- **What is recorded,** all on the CDP side with nothing injected into the page: the screencast as low-frame-rate video, a DOM snapshot at every action and Effect, the network log as HAR, and console messages. Playwright's trace has the same model. HTTP-tier runs record the network part only.
- **Replay and export.** The run's Timeline replays the trace. It is exported in Playwright's trace format only if a conformance spike proves that format can be produced reliably, since it is undocumented.
- **Masking.** Password fields and values filled from Secret references are masked everywhere, and typed input is masked by default.
- **Retention.**
  - **Kept by default** for runs that are `failed`, `rejected` or `needs-review`, or that had a takeover or an Effect. A takeover is always recorded.
  - **Size cap.** Each run keeps up to 1 GB of trace by default. Past it, the oldest video goes first, while snapshots and the HAR are kept.
    > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): at the `low` storage level a Run trace stops recording video, and at `critical` or when a trace write fails it stops, with the "no trace" mark. "Needs you" also lists a filesystem at `low` or `critical`, with its folder, and a Run stopped by storage.
  - **Erasure.** Traces are erased with their run.
- **Cost.** Traces are a costly control (ADR 0023). Its switch is the trace setting; its mark is "no trace" on the run report and on the Timeline.
- **The main world.** By default, on Chromium, nothing stays in the page, and the engine's only calls there are ADR 0048's calls into a consent vendor's own API. The opt-in exceptions are those ADR 0019 lists, and ADR 0047's on-demand hiding on Firefox and WebKit leaves a visible `<style>` element, marked in Provenance.

**People and tokens.**
- **Changes ADRs 0017 and 0024**, which gave every endpoint one per-launch token.
- **Single user.** On a single-user local Daemon, the OS user who owns it is the person: no login beyond the cookie, and the Audit log records that user and the surface.
- **Shared or exposed Daemon.**
  - **Accounts and roles.** Per-person accounts sign in with passkeys, or optionally OIDC single sign-on, under three roles. A *viewer* reads. A *member* also runs, answers Human pauses, confirms and reconciles. An *operator* also edits the Operator policy and accounts.
  - **Recovery and teams.** Recovery codes and an operator reset cover lost passkeys, and OIDC groups map to roles.
- **Web protections.** Cookies are `SameSite=Strict`, the `POST` fallback carries a CSRF token, and sign-in is rate-limited.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-22, [#826](https://github.com/goodfetch/goodfetch/issues/826): `console.sign_in.rate` (10, Operator policy only) counts every `POST /sign-in` of one address in a sliding minute, whatever its credential, and the next is refused with HTTP 429; the count is kept in memory, so a restart starts it again. A sign-in's CSRF token is an HMAC of its cookie under the Console key, never stored, which `GET /session` answers as `{"csrf_token": "…"}` (only the Console's own origin can read it); every signed-in `POST` carries it in `X-CSRF-Token`, refused with 403 without it or with another. The first such `POST` is `POST /sign-out`, which ends the sign-in and clears the cookie; the Server-Sent Events fallback (#822) checks the same token. Each refusal of the Console's routes and WebSocket is an `endpoint_authentication_failed` entry of the Audit log, `{listener, reason}`.
- **Programs.** Programs use named tokens, each limited to certain operations, Recipes, runs or Datasets, with an expiry, and revocable in Engine & settings. Local Clients that find the Daemon through its runtime file keep using its protocol token: per-launch, or persistent under socket activation (below).
- **Step-up.** On a Daemon with accounts, confirming an Effect (ADR 0014) or reconciling one (ADR 0029) in the Console asks for the person's passkey again. On a single-user Daemon, and in an interactive CLI prompt, the OS user answers as before. Adds to ADRs 0014 and 0029. Raising a Limit asks for it too (ADR 0041).

**Settings** (changes ADR 0028).
- **What the Console edits.** It edits user-level values and a run's own values, and shows every effective value with its layer and lock. It never edits project configuration or Recipe manifests, because those are files under version control.
- **The Operator policy.** The operator role edits it in the Console. The Console writes the file atomically, and only if its digest has not changed since it was read, so a hand edit is never lost.
- **Managed policies and audit.** A policy marked *managed* (deployed by Ansible or MDM) is read-only in the Console. Every change goes to the Audit log with a before-and-after diff.
- **When changes apply.** A tightened cap reaches running runs at their next admission point. Other changes apply to new runs, and each run report names the policy version it ran under.

  > Amended by [ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md), 2026-11-04, [#1906](https://github.com/goodfetch/goodfetch/issues/1906): a Run resolves its settings once, when it opens, so a tightened cap no longer reaches running runs: like every other change, it applies to new runs.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-26, [#874](https://github.com/goodfetch/goodfetch/issues/874): user-level values are written by a third person-only entry beside spec #592's two, `config.user_write(changes)`, which the resolver checks under the Operator policy before the file is replaced, and which records `user_configuration_written` in the Audit log; `config.policy_write` records `operator_policy_written` with the digests before and after and each key's values. The policy's digest is its policy version (`sha256:` and 16 hex digits of its text, of no text when there is no file), and the write holds `operator-policy.lock` beside the file from its digest's check to its rename. `config.explain` marks each key `user_settable` (its authority lets user configuration hold it and nothing locked it) and `fixed_for_run` (ADR 0102's keys fixed for a Run's life: `crawl.scope.*` and `crawl.keep_url_fragment`), from which the Console offers a row's edit. A run's own values in Engine & settings are the run values it explains with, edited row by row; a row a project configuration or a Recipe sets says to edit that file, and a fixed key set by the run says a new run changes it. Roles are not checked yet: a Daemon without accounts has one person, its operator.

  > Note (agent decision, accepted by the owner on 2026-11-08), 2026-11-07, the untangle pass: every person's write of the machine's settings files, `config.policy_write`, `config.user_write` and the "Needs you" answers that write user configuration or the Operator policy, holds `operator-policy.lock` from its first read to its rename and reads the files it checks under it, so a write made elsewhere meanwhile is never lost. Before, only `config.policy_write` held it, and a "Needs you" denial racing a policy write lost one of the two edits.

**Availability.**
- **Idle stop.** A visible Console tab counts as a connected Client, so the Daemon does not stop idle while someone is looking. A hidden tab does not count.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-27, [#830](https://github.com/goodfetch/goodfetch/issues/830): the Console's Client closes its Connection as soon as `document.visibilityState` turns `hidden`, and opens one once the page is visible again, sending its subscriptions after their last position; so a hidden tab is no connected Client and the Daemon's idle count needs no message of its own. While hidden, the page is read-only under its banner.
- **Socket activation.** `goodfetch daemon install` registers launchd or systemd socket activation, so the first connection to the Console or the protocol starts the Daemon. On Windows, the installed logon task keeps the Daemon running. Because a Client may connect before the Daemon has launched and written its runtime file, a socket-activated Daemon uses a persistent per-user protocol token in a `0600` file instead of a per-launch one, rotated by `goodfetch daemon rotate-token`. Changes ADR 0024.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#221](https://github.com/goodfetch/goodfetch/issues/221): the persistent token is `daemon.token` in the per-major folder, 32 bytes of the OS generator in hex, mode `0600`; `daemon-service.json` beside it records the installed service (its service manager, name, socket, the copy it starts and its files), and a Client that finds no running Daemon but a service with a socket connects to that socket with the persistent token. The socket is `daemon.sock` in the per-major folder, or, when that path is too long for the OS, `/tmp/goodfetch-daemon-<digest>/daemon.sock`, in a folder of the user's own, mode `0700`, named by the per-major folder's path. `daemon rotate-token` writes a new token and stops the running Daemon, so every Connection opened with the old token closes, and the next connection starts a Daemon that reads the new one; it refuses where no service with socket activation is installed, since a Daemon's token is then new at each launch. `daemon install` stops a Daemon that runs, since the service's socket takes its place, and `daemon uninstall` stops the service's Daemon, removes the service and its token. A launch agent sets neither `RunAtLoad` nor `KeepAlive`, and the systemd socket unit is the one enabled, with `Accept=no`; an installed service keeps its Daemon from stopping idle, on Windows too.
  > Note (accepted by the owner on 2026-10-28), 2026-10-29, [#1203](https://github.com/goodfetch/goodfetch/issues/1203) (deep review, 608-O3), amending the note above: `daemon rotate-token` no longer refuses where no service with socket activation is installed, since the foreground Daemon (`daemon run`) takes the persistent token too (spec #608); it replaces the persistent token and the HTTP listener's, then stops each running Daemon that takes the persistent token, reached with the old one before it is replaced: the installed service's and a foreground Daemon at `daemon.address`. The old token so stops working at once, as a rotation after a leak needs; a Daemon whose token is new at each launch refuses the old tokens from its next start.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-27, [#830](https://github.com/goodfetch/goodfetch/issues/830): with socket activation the service manager also listens on the Console's address: the systemd socket unit's second `ListenStream=` (passed second, after the protocol's socket) and the launch agent's `Sockets` entry `Console` (`SockNodeName`, `SockServiceName`). `daemon install` reads `console.address` from the machine's layers and, for port 0, records a port free at install time, since the service manager listens before any Daemon reports its port; the service record (`daemon-service.json`, `daemon status`) names it as `console`. The Daemon that service starts serves its Console on the handed-over listener, and binds its own only when none was handed over. A `console.address` that is no `host:port` leaves the Console unactivated, the Daemon then binding it as before.
  > Note (agent decision, as built), 2026-10-30, [#1781](https://github.com/goodfetch/goodfetch/issues/1781), amending the #221 note's socket path: under systemd the service's socket also moves to `/tmp/goodfetch-daemon-<digest>/daemon.sock` when the per-major folder's path holds a byte systemd's C escaping changes (a control or non-ASCII byte, `\`, `"` or `'`). At each reload of its manager, which any program may ask for, systemd writes every listening socket's path escaped and matches it back as written, so such a socket stops listening (systemd 259: "some socket file descriptors have not been opened yet"): Clients are refused, and a first visit to the Console starts a Daemon handed only the Console's socket. launchd keeps no such state, so its socket stays in the per-major folder. `daemon uninstall` removes that folder of its own with the socket.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-11-01, [#1821](https://github.com/goodfetch/goodfetch/issues/1821), amending the #830 note's port 0: `daemon install` no longer binds a port and lets it go, which another program could take before the service manager listened. Under systemd, port 0 takes a port the OS chooses, held by a socket bound with `SO_REUSEPORT` that never listens, until `systemctl --user enable --now` has returned, by which time the socket unit listens; that unit alone says `ReusePort=yes`, so it binds beside the hold, every other program is refused, and another port 0 never lands on the port. systemd refuses a `ListenStream=` on port 0, so it cannot choose the port itself. A named port, the default per-major one or a configured one, never says `ReusePort=yes`: a second listener, a second home's install included, is refused as before, rather than sharing its connections. launchd has no such key and no way found to read back a port it chose, so under launchd port 0 leaves the Console unactivated, the Daemon binding its own port as a `console.address` that is no `host:port` does; a named port is activated as before. Once listening, the unit keeps its port across a reload and a restart of the socket. What it cannot keep is a port another program takes while the socket is stopped, such as before the next login: the unit then fails to start, as one on a named port does, and `daemon install` chooses again.
- **Logins survive restarts.** A per-user Console key in a `0600` file signs Console logins. They expire after 30 idle days and are revocable, and rotating the key signs everyone out. The Console key is separate from the protocol token.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-22, [#826](https://github.com/goodfetch/goodfetch/issues/826): the Console key is `console-key` in Goodfetch home, outside the per-major folders, 32 bytes of the OS generator in hex, mode `0600`. A sign-in's cookie is `<id>.<secret>` from the OS generator; the per-major accounts store (`accounts-store.sqlite`, beside the Operator policy) keeps its identifier, an HMAC of the cookie under the Console key (never the cookie), its person, when it was created and last used, and its wrapping key. `console.rotate_key` writes a new key and empties its major's store, and every other major's sign-ins stop verifying under the new key. `console.sign_in.idle_expiry` (30 days, Operator policy only) counts from the last use, each use (`GET /session`, the WebSocket's handshake) starting it again; the cookie's `Max-Age` is the same and `GET /session` sets it again. The cookie is named `goodfetch_console_<major>`, as the per-major folder, rather than by its port, so a sign-in outlives a restart that moves the Console to another port. On a single-user Daemon each sign-in's Audit log entries name the OS user, from `USER`, `LOGNAME` or `USERNAME` in the Daemon's environment (`os_user` when none is set), and the surface, a new optional `surface` field of an entry: `signed_in`, `sign_in_revoked` and `console_key_rotated`.
- **While disconnected,** the tab stays read-only under a banner and reconnects as above.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-24, [#822](https://github.com/goodfetch/goodfetch/issues/822): the banner (`role="alert"`) shows while the Client is `read_only`, or `reconnecting` after a Connection it had; each screen disables its actions then, and keeps showing what it read.
- **Offline.** Run summaries and metadata are cached in the browser per major. Records are cached only when the person keeps a view offline, encrypted under a key that expires with the Console login. Secret fields are never cached. Sign-out wipes the cache, and Dataset erasures reach it as soon as a tab reconnects. A setting switches caching off.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-25, [#906](https://github.com/goodfetch/goodfetch/issues/906): the cache is the IndexedDB database `goodfetch-console-offline` of the Console's origin, so one per major. Its rows are AES-GCM under a 256-bit cache key the page holds only in memory, as a non-extractable key; each row is named by an HMAC of its kind and identifier under the same key, and a Dataset by an HMAC of its name, so only a row's kind is stored in the clear. IndexedDB keeps the cache key wrapped (XChaCha20-Poly1305, the sign-in's identifier as associated data) under the sign-in's wrapping key, which the accounts store keeps and never sends: `POST /offline-key`, from the Console's own origin with the sign-in's cookie and CSRF token, answers a new key and its wrapped form for `{}`, and unwraps `{"wrapped": "…"}` only for the sign-in it belongs to (`422` for another's, `401` once the sign-in ended, `404` while `console.offline_cache`, a machine setting, is `false`); `GET /session` adds `offline_cache`. A cache whose key no longer unwraps is emptied before a new key is written. "Secret fields are never cached" is kept as an allow-list: a run's Run index row without its status line, its owner's endpoint or any tag but Goodfetch's own `goodfetch.*`, and its page without its status line or Human pauses. A page signed out, or under the setting off, deletes the database, and so does the Console's new Sign out button before it signs out. The page follows the Console's own links without a page load, so a tab whose Daemon stopped still moves between Runs and a run's page, which show the cached copy until the engine answers; a page whose Daemon is stopped cannot be reloaded, since the Console registers no service worker. `forgetDataset` deletes a Dataset's rows for Foxhound's erasures.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-27, [#1219](https://github.com/goodfetch/goodfetch/issues/1219): a person keeps a Dataset view offline with "Keep offline" under the Records grid of a crawl run's Datasets tab, offered only while the page has its cache. The cache keeps one `dataset_view` row per run and Dataset, the row and its Dataset both named by the JSON array `[run ID, Dataset]`, which an erasure passes to `forgetDataset`: the Dataset's name, schema, key and counts, the columns the grid shows, and each Record read so far as its number and the values of those columns alone. A Record's URL, crawl request, commit time and Provenance, and every column the person hid, are never written. Keeping again replaces the row. The Datasets tab opened with no Connection shows the run's kept views, read-only, until the engine answers; a revoked or expired sign-in leaves them unreadable as every other row.

**Records at scale.**
- **Paging.** Records page by key, with filtering, sorting and column selection done in the engine.
  > Note (agent decision, on a default, not read by the owner), 2026-10-26, [#1211](https://github.com/goodfetch/goodfetch/issues/1211): `dataset.page { run_id, dataset, after?, through?, filter?, sort?, columns?, limit? }` answers `{ records, through, next? }`. The key is the sort's field, then the Record's number: `after` is the number of the previous page's last Record, whose sort value the engine reads from that Record, which never changes once committed, and `through` is the last number committed when the first page was read, so Records committed meanwhile never make a page repeat or skip one; a new first page shows them. `filter` holds conditions on top-level fields (`equals` a JSON value, or `contains` a text, case and code points as they are) and `wall` (`with` or `without` the Provenance's `wall` marker); `sort` is one top-level field, ascending or descending, Records that lack it last; `columns` keeps those top-level fields of each value; `limit` is 1 to 1000, 100 by default (`invalid_params` otherwise, or for a field holding `"`). Only the default order by number reads the run file's key; a sort scans the Dataset, which no index serves yet. A crawl run's Datasets come from `dataset.list { run_id }`, beside the spec's entries: each declared Dataset with its schema, key and the committed, dropped and rejected counts the Run report gives. The Console shows them in a Datasets tab of a crawl run's page, not on a route of its own, and reads 500 Records a page.
  > Note (agent decision, accepted by the owner on 2026-11-10 (grilling of G-06, Q19): `dataset.list` is a catalog entry), 2026-10-28, [#1211](https://github.com/goodfetch/goodfetch/issues/1211) (step 7 review, finding 593-608-611-5): `dataset.list` is kept, though spec #593's table of Foxhound's catalog entries does not list it: #1211's fourth criterion asks that a crawl run's Datasets list their schema and committed, dropped and rejected counts, and no entry of the table answers them. The owner confirms it as a catalog entry, to add to the spec's table, or names the read the Datasets tab takes instead.
- **Search across runs** runs on DuckDB inside the engine, reading run files read-only, as ADR 0015 allowed by not using SQLCipher. Each run keeps a SQLite FTS5 index for full-text search.
- **The SQL tab.** The Datasets screen offers a read-only SQL tab over the selected runs. The engine registers the selected runs as DuckDB table functions that read them through `rusqlite` (ADR 0057), with external access off and the configuration locked from the start, so a query reads only those runs. Queries have time and memory limits and secret columns are hidden. The SQL tab is a catalog read, so every surface gets it.

**Reaching the Console remotely.**
- **Links.** Notification links carry no credential. They point to the Console address the person sets, such as an exposed Daemon's TLS address.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-27, [#830](https://github.com/goodfetch/goodfetch/issues/830): `console.public_url` (none by default, user configuration or Operator policy only) is the base of every link the engine builds to the Console: a run's `console_url` (`<base>/runs/<run_id>`) and, once Notifications exist, theirs. Without it the base is the Console's own address. The base loses any query and fragment and its closing `/`, so no link carries the sign-in link's token or a cookie.
- **Remote access** means exposing the Daemon with TLS and passkeys (ADR 0017). The docs give tested setups for Tailscale, Cloudflare Tunnel and a reverse proxy.
- **Out of scope.** A relay through Goodfetch Cloud belongs to the Cloud map.

**Goodfetch Cloud.**
- **One contract.** The Console calls only catalog operations, including `runs.list` over the Run index, and takes its endpoint and authentication as configuration.
- **The gateway.** Goodfetch Cloud gives it a gateway that implements the same operations across its per-run engines (ADR 0001), reading its own index and forwarding live calls as the Daemon does.
- **Testing.** One Console conformance suite runs against a Daemon and a stub gateway.
- **Out of scope.** A hosted Console reaching a local Daemon belongs to the Cloud map.

**Hardening.**
- **Scraped content on its own origin.** Scraped HTML, screenshots and Record previews are served from a separate origin and shown in sandboxed iframes with no cookies, so a hostile page can never act as the Console.
- **Content Security Policy.** The Console runs under a strict policy: its own scripts only, no inline code or `eval`, Trusted Types, embedded assets (stored brotli-compressed, ADR 0057), and no third-party or telemetry calls.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#811](https://github.com/goodfetch/goodfetch/issues/811): the policy is `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; require-trusted-types-for 'script'; trusted-types 'none'; report-uri /csp-report`, the Daemon answering each report at `/csp-report` with 204. `trusted-types 'none'` lets no code create a Trusted Types policy, which nothing in the Console needs yet. Every answer, errors included, carries it with `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin` and `X-Content-Type-Options: nosniff`; `Cache-Control` is `public, max-age=31536000, immutable` for the build's hashed `/assets/` files, `no-cache` for the page and its other files, and `no-store` for any other answer. A busy `console.address` leaves the Daemon serving its Clients: its runtime file and `daemon status` report the Console as `serving` its URL, `failed` with the Error code, message and `fix`, or `absent` (an engine with no Console build), and `daemon start` exits with `console_port_in_use`'s exit code, 12.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-22, [#1188](https://github.com/goodfetch/goodfetch/issues/1188): `console_port_in_use` has no row of its own in ADR 0069's exit-code table, whose `12` is `browser_host_outdated`'s, so `daemon start` exits with the `unavailable` group's, `8`.
- **Headers.**
  - `frame-ancestors 'none'` everywhere except the embed endpoint, for granted origins only;
  - `Referrer-Policy: no-referrer`;
  - COOP and CORP.
- **Checks.** CI checks these headers. The Proving ground (ADR 0025) includes pages that try to escape the content origin.
  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-22, [#896](https://github.com/goodfetch/goodfetch/issues/896): the Console's origin answers a signed-in `GET /bodies/<run_id>/<body>` with the file's bytes as `application/octet-stream` and `Content-Disposition: attachment` (the Client's body fetcher, whose handle is `<run_id>/<body>`), and `GET /content-address/<run_id>/<body>?type=<html|text|png|jpeg|webp>` with `{"url": "…"}`, the file's address on the content origin: `/bodies/<run_id>/<body>?type=…&expires=<Unix seconds>&signature=<hex>`, an HMAC-SHA-256 of the Run, the body, the type and the expiry under a 32-byte key of the OS generator kept in memory, so a Daemon restart ends every address. The content origin answers only such an address, unexpired, and records each refusal (`token_missing`, `token_wrong`, `token_expired`, `host_foreign`, `origin_foreign`) in the Audit log under the listener `content_origin`; it reads no cookie and sets none. Its policy is `sandbox; default-src 'none'; script-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; base-uri 'none'; form-action 'none'; frame-ancestors <the Console's origins>`, with `Referrer-Policy: no-referrer`, `nosniff`, COOP `same-origin`, CORP `same-site` and `Cache-Control: private, no-store`; the Console's own policy gains `frame-src` for that origin alone, a bare `http` or `https` origin (a `console.content_public_url` with a path, query, user or wildcard is refused, leaving the Console without a content origin), and no other directive widens: a file, an image included, shows in the origin's own `sandbox` frame (agent decision, moot: the Console leaves (ADR 0137), 2026-10-23). `console.content_address` has no default port of its own: unset, the content origin listens on the Console's host on a free port, since the Console's port plus one is the next major's Console (7801 + 1 = 7802, ADR 0030); with only `console.content_public_url` set, it shares the Console's listener and answers the requests whose `Host` names that URL's host (ADR 0049). A content origin that cannot listen leaves the Console serving, its content addresses answered with 503. Screenshots and Exports have no handle yet; they join the same routes when their files exist.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, step 7 review finding 591-592-2 ([#826](https://github.com/goodfetch/goodfetch/issues/826)): every Audit entry of a person's action names the person as the sign-in driver's own entries do: the one the Console's sign-in driver signs in where the Daemon serves a Console, else the OS user, both its OS user's name on a single-user install (`USER`, `LOGNAME` or `USERNAME`, else `os_user`). `config.policy_write`, `config.user_write`, the "Needs you" actions and `certs.accept` and `certs.forget` all take it; the known-certificates store still keys its rows by the caller `os_user`, which no entry shows.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, step 7 review finding 591-592-3 ([#874](https://github.com/goodfetch/goodfetch/issues/874)): `config.policy_write` stays an idempotent write, and the engine recognises a write sent again: with a digest the file no longer has, a write whose changes the file already holds, entry for entry, answers as written, with the file's digest and a diff whose values before and after are the same, and records nothing, so a Client that resends it after its Connection dropped tells the person the truth. Any other write against a stale digest is still `policy_conflict`.

  > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-28, step 7 review finding 591-592-5 ([#906](https://github.com/goodfetch/goodfetch/issues/906)): the Console reads `console.offline_cache` from the machine's layers at each `GET /session` and `POST /offline-key`, so switching it off takes effect at the next request with no restart: the page then wipes its cache, and no key is given. Layers that do not read leave it on, its built-in value, with a warning.

  > Note (agent decision, on a default, not read by the owner), 2026-10-28, step 7 review finding 591-592-6 ([#852](https://github.com/goodfetch/goodfetch/issues/852)): "Needs you" orders its items by the time each `since` names, parsed, not by its text, since sources write fractions of a second and offsets differently; then by ID, byte by byte. A `since` that does not parse goes after every one that does. The cursor `needs_you.list` answers keeps its text, `<since> <id>`, and is compared the same way; the Console's store orders the list it holds by the same rule, to the millisecond.
