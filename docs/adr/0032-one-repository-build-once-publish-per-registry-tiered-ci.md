# One repository for every surface, build once and publish per registry, CI in tiers

Every surface released together under ADR 0030 lives in one repository, public from its first release, together with the Proving ground and the benchmark harness. Multi-language projects that release in lockstep keep one repository (Ruff, uv, Biome, Deno and Turborepo around a Rust core; Dagger, which releases every SDK at its engine's version; and Stagehand since v4, which keeps its TypeScript, Python and Go SDKs over one JSON-RPC protocol package). Those split per language lag: Playwright's language ports trail the core by one to three weeks, spider-rs's bindings sit behind its core, and Crawlee JS and Python keep separate version lines. Pydantic merged pydantic-core into its main repository in November 2025. The tree:

```
crates/            Cargo workspace: the public `goodfetch` crate, internal `goodfetch-*` crates, the `goodfetch` binary
crates/sinks/      one crate per sink process (ADR 0026)
console/           the Console app, built and embedded in the binary (ADR 0024)

> Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.

sdks/typescript/   npm `goodfetch` and the generated per-platform packages
sdks/python/       the `py3-none` platform wheels
adapters/          Vercel AI SDK, LangChain/LangGraph (TypeScript and Python), Mastra (ADR 0011)
integrations/      n8n, Airbyte source, LangChain and LlamaIndex loaders, Zapier, Make, Pipedream, Activepieces, Power Automate (ADR 0027)
skills/            agent skills
conformance/       the cross-surface conformance suites, run against the Proving ground (harness: `crates/goodfetch-conformance`)
proving-ground/    seed generator, page server, oracles, and deploy/ for the online copy
bench/             the benchmark harness, competitor adapters, and results/
docs/              the product documentation's content, plus adr/ and agents/
website/           the Docusaurus configuration, theme and release-notes pages
rnd/               frozen R&D record
```

> Amended by [ADR 0070](0070-mcp-adapters-and-integrations-are-tested-through-their-platforms-own-clients-against-a-real-engine.md): the LangChain Dataset loaders live in the LangChain packages under `adapters/` and `integrations/` holds no TypeScript LlamaIndex loader.

> Amended by [ADR 0084](0084-goodfetch-ships-two-products-collie-and-foxhound-from-one-repository-and-foxhound-contains-collie.md): the repository holds two Products, Collie and Foxhound, and `crates/` builds an executable for each, Foxhound's containing Collie's code; the crate and executable names are decided in [How the products are built, and each product's Size budget](https://github.com/goodfetch/goodfetch/issues/454) and [Product names, packages, executables and version line](https://github.com/goodfetch/goodfetch/issues/457). The tree also holds `chromium/`, the Goodfetch Chromium's build inputs and expected results (ADR 0074).

> Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): every crate only Foxhound links lives under `crates/foxhound/`, the sink processes included (`crates/foxhound/sinks/`, no longer `crates/sinks/`), and nothing outside it but `xtask` depends on a crate inside it; the rest of `crates/` may be linked by Collie.

> Amended by [ADR 0090](0090-products-are-named-goodfetch-collie-and-goodfetch-foxhound-and-share-one-product-version.md): the executables are `goodfetch-collie` and `goodfetch-foxhound`, the crates each Product publishes for its users are named `goodfetch-collie` and `goodfetch-foxhound` (`goodfetch-<product>-<part>` for any further one), and internal crates keep `goodfetch-*`. `sdks/typescript/` publishes `@goodfetch/collie` and `@goodfetch/foxhound` with their `@goodfetch/<product>-<platform>-<arch>` packages, and `sdks/python/` the `goodfetch-collie` and `goodfetch-foxhound` wheels; how the SDKs are laid out per Product is decided in [Protocol, Operation catalog and SDKs across two products](https://github.com/goodfetch/goodfetch/issues/458).

> Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): `sdks/typescript/` and `sdks/python/` each hold `collie-client/`, `collie/` and `foxhound/`, the Collie client package and each Product's SDK package; `adapters/` and `integrations/` hold one folder per Product. The pull-request tier checks the declared dependencies of the npm and PyPI packages under `sdks/`, `adapters/` and `integrations/`, as cargo-deny checks the crates.

Releases are **built once and published per registry**: no tool publishes crates.io, npm platform packages, PyPI, Homebrew and an OCI image from one version, so, like uv, Turborepo and Oxc, Goodfetch writes its own publishing jobs. CI runs in tiers, so that the full platform and runtime matrix of ADR 0024 runs before every merge without holding up each pull request. Decided in [Repository layout and CI](https://github.com/goodfetch/goodfetch/issues/107), on the evidence of the [repository layout, CI and release research](https://github.com/goodfetch/goodfetch/blob/research/repo-layout-ci/rnd/research/2026-10-11-repo-layout-ci.md).

## Considered Options

- **A repository per language or per surface** (Playwright, Crawlee, spider-rs, Temporal): rejected. Every one of them shows version lag and parity tickets, and a lockstep release (ADR 0030) would then need pinning files or submodules to hold the versions together.
- **The Proving ground in its own repository**, as web-platform-tests is: rejected. A feature, its conformance test and the page that test needs then change in two coordinated pull requests. Chromium, which imports web-platform-tests, lives with sync conflicts, rate-limit failures and reverts. Playwright, Scrapy, Crawlee and Firecrawl keep their test sites in the product repository.
- **The Proving ground in TypeScript**, a direct move of `rnd/lab/fixtures`: rejected. It must serve millions of seeded pages without becoming the bottleneck, and the online copy deploys more simply as one static binary. The lab's fixtures are about 1,600 lines, so the rewrite is small.
- **The benchmark harness rewritten in Rust**: rejected. It orchestrates competitors written in JavaScript, Python and Rust, does no hot-path work, and its method is the one ADR 0025 adopted.
- **The docs in their own repository** (Deno, Biome, Playwright's website): rejected. Every example runs in CI (ADR 0030), and examples break when docs live apart; Polars moved its docs into the main repository for that reason.
- **dist** (formerly cargo-dist) **for the whole release**: rejected. Its last release was v0.33.0 on 2026-09-11, most recent commits are from Dependabot, and it has no PyPI, crates.io or npm trusted-publishing jobs; uv now maintains by hand the workflow that dist first generated.
- **release-please**: rejected. It has open bugs with linked Cargo and npm versions and with prereleases, which the rc and nightly channels of ADR 0030 need.
- **release-plz**, the tool ADR 0030 named: rejected for the whole release. It versions and publishes Rust crates only, and its `wait_until_published` returns too early during workspace publishes.
- **knope**, which versions Cargo, npm and Python manifests together: rejected. It does not publish, and the release step needs code anyway, to keep the internal crates at `0.0.x` and to generate the per-platform npm packages.
- **Changesets** (Biome): rejected. It versions npm packages only, not Cargo or Python, and its own docs warn that prerelease mistakes are very hard to fix.
- **Postinstall downloads for npm** (dist's and GoReleaser's npm wrappers): rejected. They fail under `--ignore-scripts` and offline; Biome, Turborepo, Deno, Rolldown, Oxc and Rspack all publish per-platform packages, as ADR 0024 already requires.
- **A graph build system** (Nx, moon, Bazel): rejected. It adds a second build system; the native workspaces and the change detection below cover what CI needs.
- **The `rnd/` folder moved to an archive repository**, as Rust and Python keep their proposals: rejected. ADRs, tickets and pull requests link into `rnd/` about 180 times, and single-product repositories such as CockroachDB keep their frozen records in place.

## Consequences

- **Workspaces.** One Cargo workspace, one pnpm workspace (Console, TypeScript SDK, adapters, TypeScript Integrations, harness) and one uv workspace (Python SDK, adapters and Python Integrations), tied together by `just` as the single task runner.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Proving ground.**
  - **Language.** Its seed generator, page server and oracles are written in Rust.
  - **Independence.** It never depends on engine crates, so the oracle stays independent of the tool it judges (ADR 0025). CI enforces the rule.
  - **Moving the lab.** The lab's fixtures and oracles are ported into it.
  - **Release asset.** Each release attaches the Proving ground as a standalone binary and seed, so competitors can rerun the benchmark without the whole repository.
  - **Online copy.** Its deployment code is public in `proving-ground/deploy/`. The challenge vendors' keys sit in a protected GitHub environment, and every deployment needs the owner's approval and starts from a release tag. It is served on a subdomain of `goodfetch.dev` behind Cloudflare, plus a hostname served by Vercel for Vercel BotID (settled on the gaps the [Proving ground and conformance spec](https://github.com/goodfetch/goodfetch/issues/152) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/152#issuecomment-6115242029)).
- **Benchmark harness.** The lab's campaign runner, statistics, verdicts, claims and ledger move to `bench/` in TypeScript, cleaned up rather than rewritten. Each competitor adapter stays in that competitor's own language.
- **Benchmark results.** `bench/results/<version>/` holds the small files: verdicts, summaries, configurations and claims, dated as ClickBench does. Raw data and redacted traces go into release assets, linked by digest; Deno, which keeps its benchmark history in git, carries a side repository of about 3 GB.
- **`rnd/` is frozen in place** when V1 work starts:
  - `rnd/README.md` gets a banner saying it is archived and not maintained.
  - Nothing is edited except broken links, and lab code stays as history after its fixtures and harness move.
  - `pnpm lab ci` runs only when files under `rnd/` change, and is never a required check.
  - `research/*` branches stay unmerged.
- **Conformance harness.** The suites in `conformance/` run in `goodfetch-conformance`, a Rust crate under `crates/` that depends only on `goodfetch-protocol` (STYLE.md's dependency-direction reason: it tests through the interface, never engine internals) and is linked into the binary, so `goodfetch plugins test` runs them (ADR 0033). Cases for the SDKs, the CLI and MCP run in those surfaces' own test runners and write the same result document. The Proving ground depends on neither `goodfetch-conformance` nor `goodfetch-protocol` (settled on the gaps the [Proving ground and conformance spec](https://github.com/goodfetch/goodfetch/issues/152) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/152#issuecomment-6115242029)).
  > Amended by [ADR 0069](0069-sdks-and-the-cli-are-tested-against-a-scripted-engine-and-the-binary-of-the-same-commit.md): for Client conformance cases, the SDK and CLI runners (and MCP's, if it adopts the case list) write a case log, and `goodfetch-conformance`'s writer turns it into the result document; Journeys keep ADR 0063's writers.
  > Amended by [ADR 0068](0068-the-console-is-tested-in-real-browsers-and-served-by-the-real-binary.md): the Console conformance suite in `conformance/console/` runs on Playwright Test and, like the Journeys, writes its own result documents through a Playwright reporter.
  >
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each suite runs against the executable of the smallest Product that carries its contract: Collie's for browser conformance and the Plugin kinds Collie carries, Foxhound's for Sinks and Fetch backends.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Private components.** The public repository holds each Private component's interface, a no-op implementation that keeps the public engine whole, and that interface's conformance suite (ADR 0018). The private repository builds against public `main` every night and against every release candidate, stable release and patch. While that run is red, no release candidate, stable release or patch is published, so the challenge solver cannot silently fall out of a release. Public CI never sees private code or secrets.
- **Release automation.** This settles the item ADR 0030 left to the specs.
  - **Versioning.** An in-house `xtask release`, a small Rust program, sets the product version in every released manifest. It keeps the internal `goodfetch-*` crates at `0.0.x` and leaves the Zapier and Make apps to their platforms' versioning (ADR 0030). It then writes the changelog with git-cliff and opens a release pull request.
  - **Build.** Merging the release pull request builds every target once, with artifact attestations, signatures (ADR 0016) and a CycloneDX SBOM for the archives. Nothing is published if a file breaks a ceiling of the Size budget (ADR 0057).
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each target's job builds both Products' executables, each with its own `cargo build -p` in the same target folder, Collie's first. What both Products use (the sandbox helper, the filter broker, first-party Plugins, the Proving ground asset) is built once, not once per Product, as the Goodfetch Chromium already is (ADR 0074), and each Product's archive has its own SBOM.
    >
    > Amended by [ADR 0108](0108-while-the-repository-is-private-the-release-suite-runs-its-macos-cells-on-the-owners-machine-and-its-hosted-cells-under-a-ceiling.md): for the first release, the repository being public by then, the build publishes nothing until the release pipeline's Release suite run passes on the release commit across the full native matrix, macOS Intel and Windows arm64 included; a private-period run never stands in for it.
  - **Minors and majors.** A release candidate is published to the beta channel first. It is promoted to stable only once its beta week's gates are green: the conformance suites, the benchmark (ADR 0025) and the Private component run. The short `1.0.0-rc.N` series before 1.0 (ADR 0030) goes through the same gates.
    > Amended by [ADR 0067](0067-security-is-tested-per-trust-boundary-with-secret-canaries-and-private-fuzzing.md): the release pipeline reads the Private component run from the private repository with a read-only App, posts no private result on public commits, and also holds promotion while a fuzz crash is open.
  - **Promotion is of a commit, not of bytes** (decided in [Release promotion, release branches, vendor conformance and docs hosting](https://github.com/goodfetch/goodfetch/pull/131), on the gaps the [Repository, CI and release spec](https://github.com/goodfetch/goodfetch/issues/130) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/130#issuecomment-6114909646)). The version is built into the binary and every manifest, and PyPI and crates.io have no tags to hold a final version back, so `x.y.0` is built from the last candidate's commit plus one commit that changes no code, test or build input, which `xtask release` checks. That commit sets the versions and may add the changelog, the minor's release-notes page, which lives in `website/` outside the docs embedded in the binary, and its `bench/results/<version>/` files. The stable build passes the conformance suites, the correctness oracle, the Platform signature gate and the Private component build again on its own bytes; the beta week's benchmark result carries over, since the code is identical. Node.js, CPython, Vite and Playwright rebuild their finals the same way. "Built once" means once per version: every channel of one version carries the same bytes. Rust's alternative, building the final early and testing it from a staging server, was rejected because PyPI and crates.io have no tags to hold a final version back, so the bytes under test could not be on their beta channel, and beta users would test different bytes.
  - **Branches.** `main` carries the next minor and the nightly channel. `xtask release` cuts a protected `release/x.y` branch from `main` and opens `rc.1`'s release pull request against it; every candidate, the stable `x.y.0` and every `x.y.z` patch are built from that branch, Chrome-major patches included, so `main` never carries a release version. Release tags therefore never sit on `main`, so `xtask release` also tags each cut point on `main` (`x.y-branch`) and has git-cliff write each new section from a range: for `rc.1` and `x.y.0`, the range since the previous minor's cut point (`x.(y-1)-branch`, or for `x.0` the cut point of the previous major's last minor), so the stable section replaces the candidates' sections; for a later candidate or a patch, the range since the previous release tag on the branch. A backported fix is listed under its patch and again under the next minor, which also ships it. Fixes land on `main` first and are cherry-picked; `xtask release` lists the commits on `main` whose pull requests carry the backport label and that the branch lacks. The Clean-up rules' pin is not a fix and does not go through `main`: when `xtask release` prepares a patch, it pins the latest set of that release line's daily channel that passed its gate (ADR 0047) directly on `release/x.y`, as it sets the version, while `main` moves its own pin through the nightly build (settled on the gaps the [Repository, CI and release spec](https://github.com/goodfetch/goodfetch/issues/130) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/130#issuecomment-6132949033)). The last `release/x.y` of a previous major stays protected while ADR 0030 supports it, so at most three release branches are live: the current minor's, the next minor's during its beta week, and the previous major's last. Release pull requests target the branch they release from.
  - **Patches.** A patch has no beta week. Before it publishes, it passes the conformance suites, the correctness oracle, the guard when it carries a new Chrome major (ADR 0030), and the Private component build against it. The correctness oracle runs on the Proving ground's local copy in a GitHub-hosted Linux job of the patch pipeline, since correctness does not depend on the host class; the reference host is kept for timing (settled on the gaps the [Proving ground and conformance spec](https://github.com/goodfetch/goodfetch/issues/152) listed, as the [owner settled them](https://github.com/goodfetch/goodfetch/issues/152#issuecomment-6115242029)).
  - **Publishing.** One job per registry: crates.io, npm (platform packages before the root), PyPI, the OCI image with its SBOM, first-party Plugins (sink processes included) as one OCI artifact per platform under one multi-platform image index, at the product's version (ADRs 0026 and 0033), and the GitHub Release, made immutable (ADR 0030).
    > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): every registry job publishes both Products, or the release publishes neither. A re-run finishes a partial publish, the tag is pushed only after both Products' npm packages are published, and the same release updates both formulas of the tap and both Products' installers.
  - **Credentials.** Every registry job publishes through OIDC trusted publishing. npm and crates.io accept a trusted publisher only on a package that already exists, so each new package name, including each new per-platform npm package, is first published once by hand.
  - **Re-runs.** A re-run skips versions already published, and the tag is pushed only after npm succeeds.
  - **Installers.** The `curl | sh` and PowerShell installers are written by hand. Goodfetch's own Homebrew tap is updated by the release job.
- **CI tiers.**
  > Amended by [ADR 0061](0061-three-test-suites-each-run-by-one-just-command-under-a-time-budget.md): the tiers run three suites; the merge queue runs the Release suite, which holds the full matrix below, and `main` reruns nothing after the merge.
  - **Every pull request:**
    - One change-detection job decides what runs; workflow-level path filters are never used on required checks, because a skipped required check stays pending forever.
    - Formatting, lints and unit tests on Linux.
    - Tests of the SDKs and adapters the change touches, on one runtime each.
    - The sink suites against emulators and containers on Linux only, images pinned by digest: RustFS for S3, and LocalStack for the AWS queues and streams (SQS, SNS, Kinesis, Firehose). LocalStack has required an auth token since March 2026. Goodfetch applies for its free open-source licence; if that is refused, the owner approves a paid token like any paid test resource. The token is a CI secret.
      > Amended by [ADR 0076](0076-tests-and-ci-run-on-free-tiers-and-ai-calls-go-through-the-vercel-ai-gateway.md), noted on 2026-10-19 in [#370](https://github.com/goodfetch/goodfetch/issues/370): a paid token is declined: if the free open-source licence is refused, the affected Sinks use free emulators such as MinIO, or wait.
    - Which Sinks run: until the merge queue exists, every Sink's suite, as ADR 0026 requires. Once it exists, a pull request runs only the suites of the Sinks it changes, and the merge queue runs them all before the merge, so every pull request still passes the whole sink suite before it lands. A change to the sink protocol or to code that Sinks share counts as a change to every Sink.
    - The docs build and example runs when docs change.
    - DCO, the notice inventory (ADR 0018), the API breakage checks (ADR 0030), `cargo-deny`, `cargo-audit` and their npm and Python equivalents, a check that every Action is pinned by SHA, and a build on the minimum supported Rust version.
      > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): `cargo-deny` runs workspace-wide, proving that nothing outside `crates/foxhound/` but `xtask` depends on a crate inside it, and once per Product, rooted at its executable crate, on what it ships, with its own bans.
