# Contracts come from Rust types, with one error, cancellation and concurrency model

Every contract the engine speaks is defined once, as Rust types in a `goodfetch-protocol` crate: each operation of the Operation catalog (ADR 0011) is declared there with its class, params, result, events, whether it can be cancelled, its Experimental or deprecated marker and the version it arrived in, and the crate emits a versioned JSON Schema bundle and a catalog file through `schemars`. Both are committed, CI fails when they differ from what the types generate, and every generated surface reads them: the SDKs, the MCP server, the CLI, skills, adapters, reference pages and the release diff of ADR 0030. The settings schema (ADR 0028) and the plugin protocol (ADR 0033) are defined the same way. Around these contracts, the code follows one error model, one cancellation rule, one casing and one concurrency model, so that every area's spec and every implementation session shapes code the same way; the conventions that are easy to reverse live in `STYLE.md`. We chose Rust types over a hand-written IDL because the engine then cannot drift from its schema and the Rust crate reuses the types with no generation step; the closest comparable engines do the same (OpenAI's Codex app-server and Zed's Agent Client Protocol: Rust types, `schemars`, JSON Schema, then generated Python). Decided in [Code design and coding conventions](https://github.com/goodfetch/goodfetch/issues/123).

## Considered Options

- **A hand-written IDL** (OpenRPC, TypeSpec, protobuf): rejected. It is a second language to maintain beside the Rust types the engine needs anyway; OpenRPC's generator is effectively dormant (last release October 2025), and TypeSpec and protobuf target HTTP and gRPC rather than JSON-RPC over stdio and sockets.
- **Direct Rust-to-language exporters** (`ts-rs`, `typeshare`, `specta`): rejected. None covers Python properly (`typeshare` labels Python experimental, `specta` is still a release candidate), so a JSON Schema step is needed anyway.
- **Hosted SDK generators** (Stainless, Speakeasy, Fern): rejected. They target REST over HTTP; Browserbase archived its Stainless-built Python SDK for Stagehand when Stagehand moved to JSON-RPC.
- **`anyhow` everywhere, with messages on the wire**: rejected. Clients would match on message text, and Error codes are under semver (ADR 0030).
- **A cancel operation per domain only, or closing the connection**: rejected. Short calls could not be cancelled, or every other call on the connection would be lost with the one being cancelled.
- **camelCase on the wire** (as MCP, LSP, CDP and Playwright's protocol do): rejected. Every Goodfetch name already decided is snake_case (settings keys such as `solve_challenges`, values such as `proxy_tcp`, the Sink system columns of ADR 0026), so files and the protocol would disagree.
- **TypeScript mirroring snake_case data fields** (Stripe's and OpenAI's SDKs): rejected. `{ wait_until }` breaks the Playwright-shaped page API promised by ADR 0019.
- **Spawning tasks freely and tracking them by hand**: rejected. A page task that outlives its cancelled run keeps writing, against the leases and epochs of ADR 0003.
- **Capabilities as Cargo features** (Spider-rs ships 129 features): rejected. It means several binaries to build, test and sign, and settings could lock or expose code a binary does not contain, against ADR 0028.
  > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): the Products are two executables, Collie's and Foxhound's, made by the crates each links and never by Cargo features; the rejection stands.
- **Generating the SDKs' transport too, or hand-writing whole SDKs**: rejected. Generated transport is hard to make idiomatic and to debug; hand-written SDKs drift from the catalog, against ADR 0011.

## Consequences

- **Errors.** Each crate has its own typed errors (`thiserror`); `anyhow` appears only in `main`, `xtask` and tests. `goodfetch-protocol` holds the one list of **Error codes**: each has a snake_case string, a retryable flag and a JSON-RPC numeric class. Protocol failures use the codes JSON-RPC 2.0 predefines (parse error, invalid request, method not found, invalid params, and internal error only for a failure inside the RPC layer itself, such as a response it cannot encode); every other failure, unexpected ones included, uses a code in the range JSON-RPC 2.0 leaves to servers (−32000 to −32099). The RPC layer is the only place that converts an error for the wire: `{code, message, data: {code: "page_check_failed", retryable, …}}`. Each SDK generates one typed error class per code. Panics are for bugs only, never for input.
  > Amended by [ADR 0132](0132-each-request-may-carry-its-callers-trace-context-across-goodfetchs-own-links-and-the-engines-spans-stay-experimental.md): every request's params may hold `_meta`, the request's Trace context (`traceparent` and `tracestate`). The RPC layer reads and writes it, and its dispatcher opens each received request's span from its catalog entry, so no handler holds request-level tracing code.
- **Changes ADRs 0006 and 0035.** `E_PAGE_CHECK` becomes `page_check_failed` and `E_CHALLENGE` becomes `challenge_unsolved`, so every code reads like `session_reserved`, `hook_failed` or `plugin_crashed`.
- **Cancellation.** A Client cancels a call in flight with a `$/cancel` notification carrying the call's id, the name the plugin protocol already uses (ADR 0033). The engine stops the call at its next cancellation point and answers it with the `cancelled` code; a call that had already finished answers normally. The plugin protocol keeps its own rule, where the engine is the caller: a deadline after which the call is abandoned. Each catalog operation declares whether it can be cancelled. SDKs map `AbortSignal` and asyncio or anyio cancellation to it. An Effect already sent is never treated as undone (ADR 0010). Runs keep their own domain operations for stopping a whole run.
  > Amended by [ADR 0080](0080-sdk-timeouts-nest-waits-arm-when-called-and-a-program-sets-limits-but-never-raises-them.md): the engine answers a cancelled call with `call_cancelled`, renamed because its class `CancelledError` would share its name with Python's `asyncio.CancelledError`. It is an `UnavailableError`, and an SDK raises `CallCancelledError` only when someone other than the caller stopped the call.
- **Casing.** Every contract is snake_case on the wire: the protocol, the plugin protocol, settings, Recipes, Plans, run state, Dataset metadata and system columns, `--json` output and MCP tool arguments; operation names keep their dotted namespaces (`runs.start`). The Python SDK uses wire names as they are. The TypeScript SDK presents camelCase methods, options and result fields through generated mapping that converts only field names the schema declares, never user data (extracted records, headers, metadata maps).
  > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): each entry's canonical name is snake_case words, and an operation is `<namespace>.<member>` with a singular namespace naming the value it acts on (`run.start`, `page.goto`). Each language spells the words by one rule, initialisms from a closed list included (`waitForURL`, `CDPSession` in TypeScript, `CdpSession` in Rust), and escapes keywords by one rule (`continue_` in Python, `r#continue` in Rust).
- **What is generated and what is hand-written.** `xtask codegen` generates, from the committed bundle, the code each SDK takes from the protocol: Python pydantic v2 models (`datamodel-code-generator`) and TypeScript types (`json-schema-to-typescript`), each operation as an async method plus the Python sync method, the event registry, the error classes, doc comments taken from the catalog's descriptions, Experimental and deprecated markers, and the base classes of SDK handlers for each Plugin kind. The generated code is committed and drift-checked in CI. Each language hand-writes its runtime: starting and finding the engine, framing, `hello` and the version check, sockets and WebSocket, request correlation, flow-control credits, resuming events after a reconnect, file-backed bodies, cancellation, and the ergonomic objects (context managers, `await using`, async iterators). The Python sync API runs the async core on its own event-loop thread, because the protocol runs both ways (handler requests and events arrive while a call is pending) and a blocking client would need a reader thread anyway. The Rust crate reuses `goodfetch-protocol` with no generation.
  > Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): each language's Collie client package holds the hand-written runtime, except finding the engine, which each Product's package does, and, in TypeScript and Python, the code generated from Collie's entries; Foxhound's SDK package generates only Foxhound's own entries and builds on that package. Each Rust SDK crate re-exports only its own Product's entries of `goodfetch-protocol`. Each SDK offers the error classes of its Product's Error codes, and a code from outside them arrives as its group's class (ADR 0079).
  > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): the catalog declares each entry's kind, and each language's generator applies one form per kind with no per-entry override. Every public hand-written member is listed in its SDK's manifest with the catalog entry it serves, and the Quick suite checks the list. The Rust SDK reuses `goodfetch-protocol`'s types but generates its members and `blocking` twins the same way.
- **One text per operation.** The catalog's description of an operation is the single source of its MCP tool description, its SDK docstrings and its reference page.
- **Structured concurrency.** The engine runs on Tokio (decided in [Adopt runtime and state decisions](https://github.com/goodfetch/goodfetch/issues/70)). Cancellation tokens form a tree, from the engine process (an Attached engine or the Daemon) to each run, Session and page; each owner waits for its tasks through its own task tracker before it stops, cancelling first. Every Tokio function that starts a task outside an owner's tracker (`spawn` and `spawn_blocking`, free or on a runtime or its handle, and `spawn_local`, free or on a `LocalSet`) is banned outside the module that implements this, by a Clippy rule. State with one owner, such as a run's single SQLite writer (ADR 0002) or a CDP session, is an actor that receives messages rather than a value behind a shared lock. Blocking work runs on tracked blocking threads, or on dedicated threads their owner joins before it stops, never on the async workers. Every public async function documents its cancel safety.

  > Amended by [ADR 0060](0060-distributed-and-crash-behaviour-is-simulated-on-tokio-model-checked-and-faulted-at-io-seams.md): dedicated threads come only from the `tasks` module, which runs their bodies as tasks in the Simulation; spawning a `std::thread` elsewhere is banned.

- **Capabilities are settings, never Cargo features.** Stealth, the Challenge solver, AI and costly controls are in every binary and switched by settings (ADRs 0023, 0028, 0035); Private components stay process Plugins (ADR 0033). Cargo features exist only on the embeddable `goodfetch` crate, only for heavy optional dependencies and test utilities, and are additive; the binary builds one fixed set, and CI checks every combination of `goodfetch`'s features.
  > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): within a Product a capability is a setting, never a Cargo feature, and the Products differ only by the crates their executables link; Foxhound's crates live under `crates/foxhound/`, which nothing outside depends on but the `xtask` build tool. Each Product's executable builds one fixed feature set in its own `cargo build -p`. Cargo features exist only on the published crates through which each Product's SDK embeds its engine, under the same rules, and CI checks every combination of each one's features.
- **Where the other rules live.** Rules a tool can check live in the workspace's lint, format and dependency configuration, which arrive with the first code. The rest live in `STYLE.md` at the root, each with its rationale, and `AGENTS.md` (one per area where useful) lists the commands and the traps and points to it.
