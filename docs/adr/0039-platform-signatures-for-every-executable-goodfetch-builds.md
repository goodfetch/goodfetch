# Platform signatures for every executable Goodfetch builds, under one Goodfetch legal entity

Sigstore signatures and GitHub artifact attestations (ADRs 0016, 0030, 0032) prove which workflow built a file, and Goodfetch's own code checks them, but macOS and Windows never read them. Gatekeeper reads only Apple Developer ID signatures and notarization, and SmartScreen and Smart App Control read only Authenticode. So every executable Goodfetch builds for macOS and Windows also carries a Platform signature: the engine binary, the Windows filter broker (ADR 0033), every executable and library of the Goodfetch-built Chromium (ADR 0035), every first-party Plugin executable, and the Private component, which the private repository signs itself. Smart App Control is why: it checks every executable it runs, downloaded or not, and blocks unsigned code without reputation, and since January 2026 users can turn it on without reinstalling Windows ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [Windows Insider](https://blogs.windows.com/windows-insider/2026/01/27/releasing-windows-11-builds-26100-7701-and-26200-7701-to-the-release-preview-channel/)). On macOS, Gatekeeper checks only quarantined files, which npm, pip, curl and Homebrew formulae do not create, but a GitHub Release archive downloaded in a browser is quarantined ([Apple DTS](https://developer.apple.com/forums/thread/666452)). Deno, uv, ruff, Codex and GitHub CLI sign and notarize on both systems; Biome, Camoufox and Chrome for Testing do not, and their users clear quarantine by hand or click through SmartScreen. A Goodfetch legal entity holds every certificate and is the name users see. Decided in [Platform code signing for binaries and the Goodfetch Chromium](https://github.com/goodfetch/goodfetch/issues/121).

Changes:
- ADR 0024, whose binary channels all carry the Platform-signed bytes, and whose browser and runtime launches gain a typed error when Windows refuses a file Goodfetch did not build.
- ADR 0030, whose supply-chain gates gain the Platform signature check.
- ADR 0032, whose release signs between build and attestation, in jobs that alone reach the `release` environment.
- ADR 0033, whose `goodfetch plugins setup` verifies the helper and the broker before installing them, and whose broker is Platform-signed.
- ADR 0035, whose signed Goodfetch build is Platform-signed and notarized as below, and whose counsel review covers the Private component's Platform signature.
- ADR 0037, whose first `/to-spec` area no longer waits on this ticket.

## Considered Options

- **Sigstore only** (Biome, Camoufox, ungoogled-chromium on Windows): rejected. A stock Windows 11 with Smart App Control enforcing refuses to start the engine, the broker or the browser, and managed Macs and PCs that admit only identified publishers exclude Goodfetch. That fails ADR 0030's production bar.
- **Signing only the engine and the broker** (Bun signs Windows only and leaves macOS ad-hoc): rejected. The stealth browser and first-party Plugins would break under Smart App Control.
- **The owner as an individual publisher** (ungoogled-chromium's notarization runs under a maintainer's personal Developer ID): rejected. The owner's legal name would be printed on every binary, the stealth browser included; Azure Artifact Signing accepts individuals only in the US and Canada ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)); and moving to a company later restarts Windows reputation under a new name.
- **SignPath Foundation's free open-source signing**: rejected. The certificate carries the Foundation's name, not Goodfetch's; its terms forbid features "designed to … circumvent security measures" and require manual approval of each release ([terms](https://signpath.org/terms)), against the autonomous delivery this repository uses.
- **A second legal entity only for the stealth browser**, isolating it if Microsoft or Apple turned against the certificate: rejected as over-engineering. No revocation of a Developer ID for an anti-detect browser has been reported, notarization is an automated malware scan rather than App Review ([Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)), ungoogled-chromium is notarized today, and fingerprint masking in the public framework is Low legal risk ([Legal exposure of stealth and challenge-solving tooling](https://github.com/goodfetch/goodfetch/issues/65)).
- **Leaving the Private component without a Platform signature**, to keep the entity's name off the one component rated Medium to High legal exposure ([Legal exposure of stealth and challenge-solving tooling](https://github.com/goodfetch/goodfetch/issues/65)): rejected. Smart App Control has no exception for a single app ([Microsoft](https://support.microsoft.com/en-us/topic/what-is-smart-app-control-285ea03d-fa88-4d56-882e-6698afdb7003)), so a licensee on Windows would have to turn it off for the whole machine, or, on a managed device, keep a hash rule up to date for every release. The entity grants the licence to vetted customers, so it is already identified as the component's source, and the signature adds little exposure.
- **Signing previews only once the entity exists**, with Sigstore-only `0.x` releases before it: rejected. Previews are public releases (ADR 0030), and a preview that a stock Windows 11 refuses to run tests nothing.
- **Leaving the Goodfetch Chromium unsigned**, as Chrome for Testing and Camoufox are: rejected. It escapes Gatekeeper because the engine's download is not quarantined, but Smart App Control blocks it whatever its origin.
- **An EV (extended validation) certificate** rather than an OV (organization validation) one: rejected. Since 2024 EV no longer skips SmartScreen's reputation check, and Microsoft calls OV "functionally equivalent" ([code-signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)).
- **`rcodesign` on Linux with the key in Azure Key Vault** (uv, ruff and Codex): rejected for one toolchain on a macOS runner. Its custody is stronger, but its last release was in November 2024, and the Chromium bundle needs Chrome's per-helper signing options, which Chromium's own scripts and ungoogled-chromium's notarized pipeline drive through Apple's `codesign` ([parts.py](https://github.com/chromium/chromium/blob/main/chrome/installer/mac/signing/parts.py), [sign_and_package_app.sh](https://github.com/ungoogled-software/ungoogled-chromium-macos/blob/main/sign_and_package_app.sh)). A Developer ID certificate issued since Apple's G2 authority lasts one year ([Apple](https://developer.apple.com/help/account/certificates/replace-developer-id-certificates)), and the release environment below limits who can reach it.
- **Signing on a maintainer's machine**: rejected. It breaks ADR 0032's build-once rule and puts a long-lived key on a laptop.
- **A person approving each release in the signing environment** (SignPath's rule, GitHub CLI's production environment): rejected. ADR 0030's gates already guard every release, and a manual step would hold back the same-day fixes ADR 0030 sends through the ungated channels.
- **Checking the broker's caller by Authenticode** (`WinVerifyTrust`) **instead of, or beside, Sigstore**: rejected. ADR 0033 makes the caller check hygiene, not the boundary; Artifact Signing certificates last 72 hours, so the check would match a subject name through Win32 calls that Microsoft marks "may be altered or unavailable"; and Sigstore keeps one check on all three systems.
- **Re-signing third-party browsers** (Chrome for Testing, Camoufox, Playwright's Firefox and WebKit) so that Smart App Control admits them: rejected. Goodfetch would vouch for bytes it did not build, and their digests would no longer match their publishers'.
- **Switching to an installed, Google-signed Chrome when Windows blocks one of them**: rejected. It would change the browser, its version and its fingerprint under the run without saying so.

## Decision

**The publisher.**
- A Goodfetch legal entity, created before the first public release (the deadline ADR 0034 sets for the trademark filing), enrolls in the Apple Developer Program as an organization (it needs a D-U-N-S number, the free company identifier Apple checks, and its own domain) and in Azure Artifact Signing, which accepts organizations incorporated in the EU, among other listed countries. Its validated legal name is the publisher name in both, and only its Account Holder creates Developer ID certificates.
  > Note (owner's decisions, 2026-11-11, grilling of decision G-18 of the consolidated review: Q3 answered "yes all", and Q11 and the correction C4, put after an independent check of the grilling's drafts, answered "Yes to all", each on the grilling's recommended option as put; the wording is the grilling session's, and the owner did not read it): the first preview's work does not wait for the entity, its two signing accounts, or the trademark search and filing (Q3). The preview's last step is the owner's publish step, which records the entity, the two signing accounts and the trademark search and filing each as declined and the owner's to take up; no agent creates, enables or lists any of them as pending (Q3, C4). The entity's deadline here reads "before the first `1.0.0` candidate" (Q11).
- Every public release carries Platform signatures, the `0.x` previews included, since ADR 0030 makes them public releases. The entity and its accounts are therefore ready before the first public preview.
  > Note (owner's decisions, 2026-11-11, grilling of decision G-18 of the consolidated review: Q2 answered "yes all", and Q11 and the correction C7, put after an independent check of the grilling's drafts, answered "Yes to all", each on the grilling's recommended option as put; the wording is the grilling session's, and the owner did not read it): while the entity's signing accounts do not exist, a `0.y` preview is published with Sigstore signatures only, Windows files included, and the limit is stated where a user installs; Platform signatures are added from the first version built after the accounts exist (Q2, which stands with SmartScreen's warning known, C7). This applies to `0.y` previews only: `1.0.0` and its candidates carry Platform signatures as written above, and the Release gate and the first Consequence below are read as their notes of that day say (Q11). This reverses the rejection of "Signing previews only once the entity exists" above. What that rejection did not weigh, as the question put it: this ADR came before ADR 0076's rule that nothing which bills is created (its rule, not its table, covers the accounts, as [#142](https://github.com/goodfetch/goodfetch/issues/142) says), and together the two allowed no public version of any kind. Whether and when the accounts are opened stays the owner's decision, not made (Q2).

**What carries a Platform signature.**
- **macOS:** the `goodfetch` binary, signed with Developer ID and the hardened runtime, then notarized. It carries no `allow-jit` entitlement, since its embedded V8 always runs without JIT (ADR 0051). A bare Mach-O cannot carry its ticket, so Gatekeeper looks it up online, which matters only for a browser-downloaded archive opened offline for the first time ([Apple](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)). The Goodfetch Chromium `.app` is signed, notarized and stapled, with Chrome's own entitlement scheme: `allow-jit` only on the renderer and GPU helpers, which are signed without library validation, and the full hardened runtime on every other part.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): both Products' executables, each signed with the hardened runtime and no `allow-jit` entitlement, since both embed V8 without JIT; the two executables of a target are notarized in one submission, a ZIP of both.
- **Windows:** `goodfetch.exe`, the filter broker, and every `.exe` and `.dll` of the Goodfetch Chromium, with Authenticode and an RFC 3161 timestamp, since Artifact Signing certificates last 72 hours.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): both Products' `.exe` files, signed by one Artifact Signing call per architecture.
- **Both:** every first-party Plugin executable.
- **The Private component** is not first-party (ADRs 0033 and 0035) and is built by the private repository's own release workflow, so that repository signs it in its own signing job, with its own `release` environment: its own federated credential to the same Artifact Signing account, and its own copy of the Developer ID `.p12` and API key. Counsel reviews this signature together with the component's licence terms (ADR 0035), before the first signed Private component reaches a licensee.
- **Linux:** Sigstore only. Linux has no platform check for a userspace binary that is on by default: Secure Boot and kernel lockdown cover the kernel and its modules, and IMA appraisal and fapolicyd are opt-in ([docs.kernel.org](https://docs.kernel.org/admin-guide/module-signing.html), [ima-doc](https://ima-doc.readthedocs.io/en/latest/ima-configuration.html)). The documentation tells admins who enable them how to add every executable Goodfetch ships (the engine, the `goodfetch-sandbox` helper, the Goodfetch Chromium, first-party Plugins, and for licensees the Private component) to their trust list.
- **Never:** binaries Goodfetch does not build (Chrome for Testing, Camoufox, Playwright's driver and browsers, third-party Plugins, the interpreters in the runtime cache).

**Services.**
- **Windows:** Azure Artifact Signing (Basic tier, 5,000 signatures a month: the engine, the broker and the first-party Plugin executables on two architectures every night, plus about fifteen Chromium files on two architectures per Chrome release and the Private component's builds, which draw on the same account, come to roughly a thousand a month), reached from GitHub Actions through OIDC federation with no stored secret ([pricing](https://azure.microsoft.com/en-us/pricing/details/artifact-signing/), [action](https://github.com/azure/artifact-signing-action)). Its action runs only on Windows x64 runners, which also sign the arm64 files: Authenticode does not depend on the file's architecture, but no Microsoft document says so for these tools, so the release gate on Windows arm64 below is what proves it. If Microsoft refuses the new entity, which a 2024 rule of three years of company history could cause though no current document states it, Goodfetch buys an OV certificate held in a cloud HSM (a hardware key store run by the certificate authority, which CA/Browser Forum rules have required for code signing since 2023: SSL.com eSigner or DigiCert KeyLocker) and signs with Jsign; nothing else changes.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): Collie's executable adds about 60 signing operations a month, two per nightly, on the same account, under the same entity and fees; the release gate below checks every signed file of both Products.
- **macOS:** Apple's `codesign` and `notarytool` on a GitHub-hosted macOS runner, for both the engine and the Chromium. The Developer ID `.p12` and an App Store Connect API key are secrets of the release environment, imported into a temporary keychain for the job, as GitHub CLI does ([deployment.yml](https://github.com/cli/cli/blob/trunk/.github/workflows/deployment.yml)).
  > Amended by [ADR 0141](0141-the-kennel-is-a-tray-tool-of-its-own-workspace-that-reaches-the-daemon-as-an-observing-person-surface-and-is-published-apart-from-the-products.md): the published Kennel's `.app` carries a Platform signature under the Goodfetch entity too: Developer ID, the hardened runtime and notarization, in the Products' release signing. Builds of the Kennel from the repository stay signed ad hoc.
- Each Goodfetch Chromium build for Windows is submitted to Microsoft's security intelligence portal as the software developer when it is signed, so that a false positive is caught early, before it harms the entity's signing identity. The submission runs alongside the release and never waits for Microsoft's answer, which can take days and would hold back the same-day Chrome security patches of ADR 0030. Notarization, by contrast, is part of signing: since every package of a version is released together (ADR 0030), an Apple notary outage holds back the whole release until it passes, which is accepted.

**In `xtask release`** (adds to ADR 0032).
- Signing changes a file's bytes, so the order is fixed: build, then sign and notarize, then compute digests, then attest and Sigstore-sign, then publish every channel. Every binary channel (npm platform packages, PyPI wheels, the OCI image, the first-party Plugin artifacts, the GitHub Release, the installers, the Homebrew tap, the browser cache) carries the same signed bytes, and every digest-based check (attestations, the browser cache of ADR 0024, the broker's caller check) covers them. crates.io ships source, so a `cargo install` build is the user's own and carries no Platform signature.
- Signing runs in its own jobs, after the build jobs, and only those jobs name a `release` GitHub environment. Its deployment rule admits only protected branches: `main`, for the nightly channel, and the `release/x.y` branches of ADR 0032, from which candidates, stable releases and patches are built, the last minor of a supported previous major under ADR 0030 included. No tag is admitted, since the release builds from the merged release pull request and pushes its tag only afterwards (ADR 0032). The Azure federated credential trusts only that environment. A workflow change reaches a protected branch only through the reviewed pull requests and required checks the repository already demands, which is what guards the environment. Build jobs never see signing credentials. No person approves the job; ADR 0030's gates guard the release. The Chromium build of ADR 0035 hands its unsigned bundles to the same signing jobs.
- Every channel that publishes binaries is signed the same way: stable releases, release candidates on the beta channel (stable is then rebuilt from the candidate's commit and signed once for its own version, ADR 0032), patches and the nightly channel, which builds from `main` and so reaches the environment. Nightly signatures count against the Basic tier like the rest; past 5,000 a month each costs 0.005 USD, or the Premium tier applies.
- Signed artifacts are produced once per version. A re-run of the release (ADR 0032) reuses them rather than signing again, since a new signature carries a new timestamp and, with Artifact Signing, a new daily certificate, so the channels would otherwise carry different digests for one version.
- Homebrew keeps Goodfetch as a formula in its own tap, which Homebrew's 2026 Gatekeeper rule for casks does not cover ([Homebrew 5.0.0](https://brew.sh/2025/11/12/homebrew-5.0.0/)).

**Release gate** (adds to ADR 0030's supply-chain gates). The artifacts about to be published are checked on the systems they target, and a missing or invalid Platform signature blocks the release:
- **Windows x64 and arm64:** `signtool verify /pa` on every signed file, which must also carry an RFC 3161 timestamp, since an untimestamped Artifact Signing signature stops being valid after 72 hours.
- **macOS, the engine:** `codesign --verify --strict`, and notarization checked with `codesign --verify --check-notarization -R="notarized"`, since `spctl --assess` rejects a notarized bare binary with "the code is valid but does not seem to be an app".
- **macOS, the Goodfetch Chromium:** `codesign --verify --strict --deep`, `spctl --assess --type execute` and `stapler validate`.

>
> Note (the grilling session's reading, 2026-11-11, same grilling, awaiting the owner's reading), from this ADR's opening paragraph: what a user of a Sigstore-only preview meets. On macOS, an archive downloaded in a browser is refused by Gatekeeper until its quarantine is cleared, while npm, pip, curl and Homebrew installs are not checked. On Windows, an unsigned `.exe` downloaded in a browser meets a SmartScreen warning the user may click through, and with Smart App Control enforcing every Goodfetch executable is refused, whatever its origin. As built, the engine's error is defined for an executable Goodfetch did not build (`crates/goodfetch-protocol/src/executables.rs:20-28#EXECUTABLE_BLOCKED_BY_SMART_APP_CONTROL`); its reader, `crates/goodfetch-engine/src/executables.rs:25-40#blocked_by_smart_app_control`, is called by its tests only; and no hand-written code under `sdks/` reads Windows' refusal codes, the SDKs' generated error classes only mirroring the engine's code (read at `b7ab3b806`).

**Elevated installs** (adds to ADR 0033). `goodfetch plugins setup` verifies the Sigstore attestation of the `goodfetch-sandbox` helper and of the filter broker against the trust root bundled with the engine before installing them, and installs a copy into a path only root or SYSTEM can write. It refuses to install a file that fails. This is the one place where swapping a file would gain root or SYSTEM rights.

**The broker's caller check** stays as ADR 0033 wrote it: a Goodfetch release attestation checked with Sigstore. It holds because attestations cover the signed bytes.

**Executables Windows refuses to start.** When Smart App Control blocks an executable Goodfetch starts but did not build (a browser, a third-party process Plugin, an interpreter from the runtime cache), the start fails with a typed error that names the file and Smart App Control. For a browser it gives the three fixes: the Goodfetch Chromium, an installed Chrome by channel, or turning Smart App Control off. The engine never re-signs such a file and never switches to another browser by itself.

> Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#260](https://github.com/goodfetch/goodfetch/issues/260): the typed error is `executable_blocked_by_smart_app_control` (Refused group, not retryable), whose details give the file. The engine reads it from the start's OS error: `ERROR_SYSTEM_INTEGRITY_POLICY_VIOLATION` (4551) and the code-integrity reputation refusals (4556 to 4559, 4580 to 4582). An App Control for Business policy an administrator sets gives the same codes, so the message names both; the codes for a broken or unsigned policy (4550, 4552 to 4555) refuse no file and keep the start's own failure.

## Consequences

- A Goodfetch company must exist before the first public release, and its Apple and Azure accounts must be validated in time. Validation takes up to about four weeks: the D-U-N-S number takes about five business days, and Artifact Signing's identity check 1 to 20 business days. The owner approves the yearly Apple fee (99 USD), Artifact Signing (9.99 USD a month) and, if needed, the fallback certificate.
  > Note (owner's decision, 2026-11-11, grilling of decision G-18 of the consolidated review: Q11, put after an independent check of the grilling's drafts, answered "Yes to all" on the grilling's recommended option as put; the wording is the grilling session's, and the owner did not read it): "before the first public release" here reads "before the first `1.0.0` candidate". A `0.y` preview is published while the company and its accounts do not exist, and they stay declined and the owner's to take up (the notes under "The publisher." above).
- A Developer ID or Artifact Signing revocation would hit every Goodfetch binary on that system at once. The security intelligence submissions and ADR 0035's wording policy are the mitigations; a second entity is not.
- The browser cache's digests (ADR 0024) and the Plugin store's digests are those of signed files, so a build signed twice, or re-signed after release, is a different artifact.
- The signing credentials exist in two repositories, the public one and the private one, each behind its own environment. If counsel objects to signing the Private component, removing its signing job is the whole technical change, but it brings back the Smart App Control cost above, so it reopens this decision.
- A browser or Plugin built by others may fail to start on Windows hosts with Smart App Control enforcing. Whether Microsoft's reputation already admits Chrome for Testing is unknown, so the conformance suite on Windows reports it rather than assuming it.

Evidence: [platform code signing research](https://github.com/goodfetch/goodfetch/blob/research/platform-code-signing/rnd/research/2026-10-11-platform-code-signing.md) (2026-10-11), from Apple, Microsoft, Homebrew, kernel documentation and peer release workflows, with the main sources cited inline above.
