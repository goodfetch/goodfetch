# Certificate exceptions are per domain, pinned on first use, and reach browsers through the engine's TLS relay

Every tier checks TLS certificates by default. Three settings make exceptions, each scoped to the domains it names: `trusted_cas` (extra certificate authorities), `client_certificates` (mutual TLS) and `accept_invalid_certs` (a certificate that fails verification). An accepted invalid certificate is pinned: its public key is remembered per user, as SSH's `known_hosts` remembers hosts, and a different key stops that host until a person accepts it. Browsers cannot scope these exceptions per host, so the engine's egress relay terminates TLS for the listed hosts and connects upstream with the ClientHello the browser itself sent. ADR 0016 locks every security control that costs nothing at run time; this decision keeps TLS checks locked everywhere except on the domains a user names, because a fully locked check would lose the broken-certificate sites that Crawlee and Scrapy collect without asking (parity row SC-06). Decided in [Network defaults](https://github.com/goodfetch/goodfetch/issues/118).

> Note (agent decision, pending owner review), 2026-10-22, [#625](https://github.com/goodfetch/goodfetch/issues/625): the per-host decision is `goodfetch-engine`'s `tls` module, a rustls verifier the engine's own HTTP client uses for every connection. A `tls.trusted_cas` entry is read as the WHATWG parser reads a host (one trailing dot dropped) and matches that host and its subdomains, as an `egress` domain entry does; its authorities are trusted beside Mozilla's roots, never instead of them, and a host under nested entries trusts the authorities of each. An entry is not checked against the Public Suffix List. A certificate that fails raises `certificate_invalid` (a `PageError`, not retryable) whose `failure` is `expired`, `not_yet_valid`, `unknown_issuer`, `name_mismatch`, `self_signed` (an unknown issuer whose certificate is its own issuer) or `revoked`, and any other refusal of rustls's verifier as its snake_case name; `fix` names `tls.trusted_cas` for an unknown issuer and `tls.accept_invalid_certs` for the rest. An Operator-configured endpoint, such as a pinned download, trusts only its own authorities beside Mozilla's roots. The Proving ground's `certificates` family serves H03's certificates. `tls.trusted_cas` and `tls.accept_invalid_certs` moved into `goodfetch-protocol`'s `tls` module.

> Note (agent decision, pending owner review), 2026-10-22, [#628](https://github.com/goodfetch/goodfetch/issues/628): the known-certificates store is `known-certificates.sqlite` in Goodfetch home, the format `known-certificates` (Usage ledger family, `frozen_major`), one row per person and host holding the SHA-256 of the certificate's DER `SubjectPublicKeyInfo` as 32 bytes, the pin time and the Run; the person is the OS user (`os_user`) until accounts exist. A hash is written `sha256/` and its standard base64, as curl's and Chromium's SPKI pins are. On the engine's own HTTP client, a host whose domain is listed with `null` finishes its handshake whatever its certificate (the handshake signature is still checked against the presented key), then the pin decides before the request is written: no pin and a valid certificate passes with no exception; no pin and an invalid certificate pins on first use and records `certificate_pinned` in the Audit log; the pinned key passes; another key, a row the engine cannot read, or a store it cannot read or write stops the host as a changed key (`certificate_changed` is #629's). A domain listed with a pin or `any` makes no exception until #629. A response fetched under an exception carries its kind (`trust_on_first_use`) and the hash for its Provenance; the host gets no Session cookie, and the Run's Secret-provider driver refuses to resolve for it with `secret_input_refused`, `reason: "invalid_certificate_exception"`, declared here. `certs list` (`certs.list`, all surfaces) lists the caller's pins only, an unreadable row with its host alone.

> Note (agent decision, pending owner review), 2026-10-23, [#629](https://github.com/goodfetch/goodfetch/issues/629): `certificate_changed` is a `RefusedError`, not retryable, whose details carry `host`, `pinned_spki_sha256` (absent for an unreadable row), `presented_spki_sha256` and `fix`. A host it stops stays stopped for the rest of the run, even if it presents its pinned key again, and the key it presented waits beside the pin in the store's `changes` table (one per person and host, the latest kept), which `certs list` shows as `changed_spki_sha256`. `certs.accept` takes the host and that key's hash, and pins it only when it is the change waiting: a person accepts the key they were shown, never one an agent names, and the accepted change is recorded as `certificate_change_accepted` with both hashes, actor the person. `certs.forget` removes the pin and its waiting change. Both are `person_only`: the RPC layer answers `person_required` to every surface but the CLI's and the Console's; the CLI asks at a terminal (`certs accept <host>`, `certs forget <host>`) and refuses them under `--json` or without a terminal. A Recipe has no surface of its own: its code reaches the engine through an SDK, which is refused. `any` lets a host with no pin through with any certificate, pins none and is recorded as `certificate_any_used` once per run and host; a pinned host under `any` passes only with its pin. A pin given as a value of `tls.accept_invalid_certs` still makes no exception (left to the HTTP tiers' tickets).

> Note (agent decision, pending owner review), 2026-10-24, [#626](https://github.com/goodfetch/goodfetch/issues/626): a value of `tls.client_certificates` is a table of `certificate`, the file of the certificate and its chain (PEM or DER), and `key`, the Secret reference of its private key; a key given as a value, or any other field, is refused with `setting_invalid`, whose reason never repeats the value. Every layer sets it, a Recipe and a run included, and a Client acting for a model too, since the key goes only to the domain the entry names. The most specific listed domain of a host gives its certificate. On the engine's own HTTP client the key is resolved through the Run's Secret-provider driver when the first handshake with a host of the domain starts (after the TCP connection, before the TLS handshake), bound to that domain, recorded as `secret_reference_used` with placeholder `tls.client_certificates`, and held for the rest of the run with the certificate, read at the same moment; a reference that gives no value fails the request with the driver's error before any handshake. The Guards' rule on credentials covers client certificates: none goes to a host reached through `tls.accept_invalid_certs`. When a listed host's domain is listed there too, the handshake goes on past the server's certificate only when it verifies and the host has no pin; otherwise the verifier stops the handshake before the client certificate is sent, the exception still decides on the key shown, and the request fails with `certificate_changed` for a changed key or an unreadable pin row, else with `secret_input_refused` (`reason: "invalid_certificate_exception"`). An unusable certificate file or key is `setting_invalid` naming `tls.client_certificates`. Operator-configured endpoints take no client certificate from this setting. The Proving ground's `client-certificate.certificates.test` and `other-client-certificate.certificates.test` require mutual TLS with the seed's client certificate.

> Note (agent decision, pending owner review), 2026-10-25, [#635](https://github.com/goodfetch/goodfetch/issues/635): the relay's terminating mode is `goodfetch-page`'s `egress_relay` (submodules `authority`, `client_hello`, `terminate`). A Run whose `tls.accept_invalid_certs` lists a domain with `null` or `any`, or whose `tls.trusted_cas` lists one, gets one authority when its browser pool opens: an ECDSA P-256 key and certificate made in memory with rcgen, `pathLen` 0, name-constrained to those domains (an address as itself alone); its key is never written, its certificate leaves memory only inside the chains the relay presents, and the Run's Provenance records its key's hash and domains (`relay_authority`). The authority is per Run, not per launch: every browser the Run launches takes the same `--ignore-certificate-errors-spki-list=<base64 SHA-256 of its key>`, so the Sessions' relays, opened before their browser, sign with it; a new Run makes a new one. A domain listed only in `tls.trusted_cas` is terminated too, since a browser cannot trust an authority for some hosts alone. For a tunnel to a host of those domains the relay reads the browser's ClientHello, rebuilds it on BoringSSL (cipher suites with TLS 1.3's order kept, groups and key shares, signature algorithms, ALPN, ALPS protocols and codepoint, certificate compression decoded with Brotli and zlib, OCSP and SCT requests, `record_size_limit`, delegated credentials, GREASE, ECH GREASE, no session ticket when the browser offered none, the extension order through `set_extension_permutation`), lets BoringSSL finish the upstream handshake with a `SSL_CTX_set_custom_verify` callback that keeps the chain, and decides before any byte of the browser's goes up: the engine's per-host decision (`tls::Examiner`, the same webpki verifier the engine's client uses) under the Run's `tls.trusted_cas`, then the Run's exception and pins. A pin that changed stops the host with `certificate_changed` for the rest of the Run; a failure with no exception is `certificate_invalid`; either closes the browser's connection and is raised by the navigation it failed. Only then does the relay finish the browser's handshake with the host's leaf, selecting the protocol the site chose, and copy the bytes both ways. The ALPS payload is empty until area 8 captures the pinned build's, and upstream session tickets are not kept (resuming needs BoringSSL's unsafe `SSL_set_session`): both, and client certificates through the relay, are follow-ups. A host the relay only tunnels whose certificate Chromium refuses (`net::ERR_CERT_*`) raises `certificate_invalid` too: the relay opens a handshake of its own to it, through itself, and names the failure as the engine's decision does, else by the table of Chromium's names (`ERR_CERT_COMMON_NAME_INVALID` is `name_mismatch`, `ERR_CERT_AUTHORITY_INVALID` `unknown_issuer`, `ERR_CERT_REVOKED` `revoked`, any other as its name in text, `date_invalid` among them). The relay records each host it terminated once per Session in Provenance (`tls_terminated`: the relay's address, the host, the exception and the key it presented). The browser adds a Session's cookies itself, so the interception fails a request over TLS to a terminated host that would carry a cookie its host did not set alone with `secret_input_refused` (`reason: "invalid_certificate_exception"`, `placeholder` the cookie's name, `reference: "session.cookies"`) before the request leaves.

> Note (agent decision, pending owner review), 2026-10-24, [#627](https://github.com/goodfetch/goodfetch/issues/627): an Operator-configured endpoint on the engine's own HTTP client verifies its certificate against Mozilla's roots and the authorities `tls.trusted_cas` lists for its own domain, read from the machine's settings at each connection, and takes no exception of `tls.accept_invalid_certs`, whatever that lists for its domain (trust on first use, `any` or a pin): an invalid certificate ends the connection with `certificate_invalid` before anything is sent. Its own client certificate is not built yet; it takes none from `tls.client_certificates`.

Competitors either verify nothing by default or offer one switch for everything:

- Crawlee JS ignores TLS errors by default in its HTTP crawlers (`ignoreSslErrors: true` in 3.x, `ignoreTlsErrors` in 4.0; [http-crawler.ts](https://github.com/apify/crawlee/blob/master/packages/http-crawler/src/internals/http-crawler.ts)). So does Scrapy (`DOWNLOAD_VERIFY_CERTIFICATES=False`, which since 2.16 also skips HTTPS proxy certificates; [security docs](https://docs.scrapy.org/en/latest/topics/security.html)), and so does Firecrawl unless a request sets headers or actions (`skipTlsVerification`; [types.ts](https://github.com/firecrawl/firecrawl/blob/main/apps/api/src/controllers/v2/types.ts)).
- Crawlee Python, Spider, Playwright, Stagehand and Browser Use verify by default and turn verification off for a whole client or browser context. Browser Use's switch also disables web security ([profile.py](https://github.com/browser-use/browser-use/blob/main/browser_use/browser/profile.py)).
- No surveyed tool scopes an exception to a domain, pins what it accepted, or logs that verification was off.

Browsers offer no stable per-host control. Chromium's `--ignore-certificate-errors-spki-list` is browser-wide and skips all verification once any certificate the server sends matches ([ignore_errors_cert_verifier.cc](https://chromium.googlesource.com/chromium/src/+/main/services/network/ignore_errors_cert_verifier.cc)); CDP's per-error decisions (`Security.setOverrideCertificateErrors`, `handleCertificateError`) still work but are deprecated ([protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)). Playwright gives Firefox and WebKit one switch per browser context ([protocol.d.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/webkit/protocol.d.ts)). No browser selects a client certificate except from the OS store (Chromium's `AutoSelectCertificateForUrls` policy). Playwright's `clientCertificates` works through a local proxy that terminates TLS in Node, so the site sees Node's ClientHello, and it turns verification off for the whole browser context ([socksClientCertificatesInterceptor.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/socksClientCertificatesInterceptor.ts), [browser.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/browser.ts)).

## Considered Options

- **TLS checks locked, with extra trusted CAs only**, as ADR 0016's rule for controls with no run-time cost implies: rejected. Sites with expired certificates or missing intermediates would be lost to Goodfetch while Crawlee JS and Scrapy collect them by default.
- **One switch per run** (Spider, Playwright): rejected. A switch flipped for one broken site would expose every Session's credentials and forms to a man in the middle.
- **Accepting any invalid certificate from a listed host**: rejected. It accepts an attacker on that host's path as readily as the broken site; trust on first use stops a later substitution.
- **CDP per-error decisions for Chromium**: rejected. The methods are deprecated, they cover neither client certificates nor Firefox and WebKit, and a second mechanism would still be needed for those.
- **Playwright's approach for client certificates** (terminate TLS in a runtime with its own TLS stack): rejected. The site sees a different fingerprint from the browser's, and the browser stops verifying every other host of the browser context.
- **Upstream fingerprints captured at build time**: rejected. Captures exist only for the Goodfetch Chromium build (ADR 0035), while the relay serves every browser, including ones Goodfetch does not build.
- **Installing CAs or client certificates in the OS store**: rejected. It changes the user's machine for every application and outlives the run.

## Consequences

**Settings.**
- `trusted_cas`, `client_certificates` and `accept_invalid_certs` are maps from a domain (a host name, or a registrable domain as in ADR 0004 with its subdomains) to a value: certificate files or Secret references for the first two (ADR 0015), and for the third a pin, `any`, or nothing (trust on first use). They are settings through ADR 0028's layers, so Operator policy can forbid or lock them.
- `trusted_cas`, a pin and `any` are taken only from Operator policy or user and project configuration, never from a Recipe or a run; on a Daemon with accounts, whose user configuration every member's runs share, only the operator role writes them, in the Operator policy, since each lets a host present a certificate the default roots would refuse. A Recipe or a run can list a domain in `accept_invalid_certs` only for trust on first use, and can set `client_certificates`. **Changes ADR 0028**: these values are settings that the Recipe and run layers cannot set. **Changes ADR 0011:** writing them, and answering `goodfetch certs accept` and `certs forget`, happens only in the Console or an interactive CLI prompt, under ADR 0031's step-up on a Daemon with accounts, or by editing configuration and Operator policy; no MCP tool, code-mode function, SDK method or `--json` CLI operation writes them.
- They apply only to addresses a page can reach (ADR 0017). Endpoints the operator configures (Sinks, Model providers, vaults, proxies, webhooks) take only their own trusted CA and client certificate and never accept an invalid certificate.
- No Plugin can set or widen them (ADR 0033), and a Plugin's own connections never benefit from them.
- **Changes ADR 0016:** TLS verification is a control that cannot be switched off; these per-domain exceptions are the only way around it.

**Pinning invalid certificates.**
- The first invalid certificate accepted for a domain listed without a pin is pinned by the SHA-256 hash of its public key in a per-user known-certificates store, beside the Usage ledger (ADR 0041), kept by the Lead Daemon in a Daemon group (ADR 0055), and recorded in the Audit log.
- A pin is per host name, also under a registrable domain listed with its subdomains. It applies only in runs that list that host's domain in `accept_invalid_certs`; other runs verify the host normally. A pinned host accepts only the pinned key, whatever `trusted_cas` would accept.
- Later connections to that host, in any such run of that user, accept only that key. A different key stops that host with the Error code `certificate_changed`, which carries both hashes. A pin set in configuration that differs from the stored one raises the same error.
- Only a person accepts a changed key, with `goodfetch certs accept` answered in an interactive CLI prompt or in the Console, under ADR 0031's step-up on a Daemon with accounts, as ADR 0029 restricts Reconciliation and ADR 0041 restricts raising a Limit. **Changes ADR 0031**, whose step-up gains accepting a changed key, removing a pin, and writing `trusted_cas`, pins and `any`. On a Daemon with accounts, `certs accept` and `certs forget` are answered by the person whose store holds the pin, never by the operator on another person's behalf. An agent cannot accept one.

  > Note (agent decision, pending owner review), 2026-10-28, step 7 review finding 564-8 ([#628](https://github.com/goodfetch/goodfetch/issues/628)): `certificate_exceptions_used` is recorded once, as a Run ends however it ends, from the engine for that Run, with `{"hosts": [{"host", "kind", "spki_sha256"}]}`: each host the Run reached under a certificate exception, by host name, its `kind` `trust_on_first_use` or `any`, and the key it accepted last. - The value `any` accepts every certificate from that host, for test fixtures that regenerate theirs, records no pin, and is recorded in the Audit log on each run that uses it. It never overrides a stored pin: moving a pinned host to `any` takes a person removing the pin with `goodfetch certs forget`, answered like `certs accept`.
- A pin row an engine cannot read stops that host with `certificate_changed`, so an older engine never treats a pinned host as unpinned.
- `certificate_changed` and `certificate_exception_unsupported` are not retryable (ADR 0038): a person or a configuration change must act first.
- The store partitions per person on a shared Daemon, as ADR 0031's accounts do. Like the Usage ledger, every product major shares it, its format's major stays frozen, and older engines open its newer versions, which only add. **Changes ADR 0030**, whose list of versioned formats gains it.

**Guards.**
- The engine refuses to type a secret into, or send a Session's credentials or cookies to, a host reached through `accept_invalid_certs`, as ADR 0017 refuses with raw CDP attached.
- Each Record fetched under an exception is marked in Provenance with the exception's kind and the certificate hash.
  > Note (agent decision, pending owner review), 2026-10-28, [#679](https://github.com/goodfetch/goodfetch/issues/679), step 7 review finding 563-565-11: a Record a `browser` page gave is marked as an HTTP tier's is. The Session's relay keeps, for each host it terminated, the exception its first connection used, and the crawl reads it for the host of the page's final URL; a host the relay tunnelled, or terminated for its trusted authorities with no exception, gives no mark.
- The Audit log records each run's exceptions, every first pin, every accepted change and every use of `any`.

**HTTP tiers.**
- reqwest runs a rustls certificate verifier that decides per host: the default roots, the domain's trusted CAs, or the domain's pin. rustls chooses a client certificate without knowing the server name, so reqwest keeps one client per client-certificate scope and routes each request by host.
- wreq cannot hand each connection's verification to the caller, but takes a certificate store, a client identity and a verification switch per client ([ClientBuilder](https://docs.rs/wreq/latest/wreq/struct.ClientBuilder.html)). The engine keeps one wreq client per trust scope of a Session and routes each request by host. The emulation profile is the same in every scope, so a site cannot tell them apart. A pin cannot be expressed as a certificate store, so Goodfetch adds per-client custom verification to wreq on top of BoringSSL's (`SSL_CTX_set_custom_verify`), which checks the presented key against the pin during the handshake, before any request is sent. The spec settles whether wreq takes the change upstream or Goodfetch carries it.
  > Note (agent decision, pending owner review), 2026-10-28, [#680](https://github.com/goodfetch/goodfetch/issues/680), step 7 review finding 563-565-3: until wreq's clients present a client identity per client-certificate scope, the wreq transport refuses a request to a host a domain of `tls.client_certificates` covers with `capability_unavailable` (key `tls.client_certificates`, kind `stealth_client_certificate`) before it connects, rather than connect without the certificate. A follow-up owns presenting it.

**The TLS relay for browsers.**
- **Changes ADR 0017:** the engine-owned egress proxy, which only tunnels, gains a terminating mode for hosts with an exception. Hosts without one are tunnelled, and the browser verifies them itself.
- Upstream, the relay applies the domain's rule (trusted CAs, client certificate, pin) and connects through wreq with a ClientHello and HTTP/2 settings rebuilt from those the browser sent it, so the site sees that browser's own fingerprint, whatever the build. The conformance suite compares the JA4 and HTTP/2 fingerprints of the browser and of the relay for every pinned browser on every OS.
  > Amended by [ADR 0124](0124-collies-tls-relay-links-wreqs-boringssl-but-not-wreq-and-forwards-the-browsers-own-http2.md): the relay connects through `btls`, the BoringSSL fork `wreq` uses, not through `wreq`, since Collie carries the relay but not `wreq` (ADR 0088). It rebuilds the ClientHello from the browser's, including the extension order, ALPS, key shares and the browser's ALPN list. It applies the domain's rule in BoringSSL's custom verify callback, then forwards the browser's own HTTP/2 or HTTP/1.1 bytes unchanged instead of rebuilding its HTTP/2 settings.
- Toward the browser, the relay presents certificates from a CA generated at each browser launch, held only in the engine's memory and name-constrained to the listed hosts. How each browser comes to trust it:
  - **Chromium** trusts it through `--ignore-certificate-errors-spki-list` with the CA's key hash. Since a match skips all verification, the key is never written to disk and changes with every launch.
  - **Playwright's Firefox** trusts it through the `Certificates.Install` policy, in a file named by `PLAYWRIGHT_FIREFOX_POLICIES_JSON`, which `playwright.cfg` maps to `browser.policies.alternatePath` ([playwright.cfg](https://github.com/microsoft/playwright/blob/main/browser_patches/firefox/preferences/playwright.cfg)). NSS enforces the name constraints ([pkixbuild.cpp](https://github.com/mozilla-firefox/firefox/blob/main/security/nss/lib/mozpkix/lib/pkixbuild.cpp)). The policy installs asynchronously, so the engine confirms the CA is trusted before the Session's first navigation.
  - **Camoufox and WebKit** are fully relayed. Camoufox reads policies only from its install directory, which sits in the shared browser cache checked by digest at every launch (ADR 0033). WebKit cannot trust an added CA on macOS or Windows, and on Linux only in developer builds. A Session of either with any exception therefore sends every host through the relay, which verifies each one upstream (the default roots for unlisted hosts) and mirrors the browser's ClientHello as above. The browser's certificate switch then covers only its loopback link to the relay.
- Chrome uses no HTTP/3 through a proxy, so listed hosts are reached over HTTP/2, as with any proxied Session.
- **Not switchable.** ADR 0016 and ADR 0017 let a run switch off the egress proxy of raw CDP Sessions. That switch covers only its tunnelling of raw CDP traffic, never the terminating mode: a Session with a certificate exception always goes through the relay.
- A Session with an exception reports which hosts the relay terminated, and the V1 benchmark (ADR 0025) publishes the relay's cost.

**Remote browsers.**
- **Changes ADR 0022:** on a Browser host, the Browser host runs the relay beside its browser and applies the exceptions and pins the engine sends with the Session. A first pin is reported back and recorded in the user's known-certificates store.
- A browser reached only through a third-party CDP endpoint (ADR 0033's Browser backend) cannot be relayed, so a Session there with a certificate exception is refused with the Error code `certificate_exception_unsupported`.
