# A local address is part of a Session's egress, on every OS

A run can send its traffic from chosen local addresses: a list of IP addresses, a network interface by name, or an IPv6 prefix. Each Session binds one address per IP family for its life, exactly as it binds one proxy, so a change of address opens a new Session (ADR 0021). DNS lookups and WebRTC follow the same address, browsers reach it through the engine's egress relay, and, for Sessions without a proxy, a replacement after a block draws from a different network block. Spider and Scrapy let HTTP requests choose their source address, and no browser tool does (parity row SA-25). Decided in [Network defaults](https://github.com/goodfetch/goodfetch/issues/118).

Spider wraps reqwest's `local_address` and `interface`, and its interface option silently does nothing where the OS lacks support ([website.rs](https://github.com/spider-rs/spider/blob/main/spider/src/website.rs)). Scrapy binds per request through `meta["bindaddress"]` or globally through `DOWNLOAD_BIND_ADDRESS` ([docs](https://docs.scrapy.org/en/latest/topics/request-response.html)). Crawlee documents nothing. Chromium has no switch for the source address, so Playwright, Stagehand and Browser Use users resort to a local proxy or network namespaces. reqwest's `interface` works on Linux, Android, Fuchsia, Apple platforms, Solaris and illumos, but not Windows ([ClientBuilder](https://docs.rs/reqwest/latest/reqwest/struct.ClientBuilder.html)). Cloudflare's rate limiting counts "an individual IPv4 address or IPv6 /64 IP range" as one client ([docs](https://developers.cloudflare.com/waf/reference/legacy/old-rate-limiting)).

## Considered Options

- **Excluding local addresses**: rejected. Spider and Scrapy offer them, with a real use: spreading traffic over a server's own addresses without paying for proxies.
- **HTTP tiers only** (Spider, Scrapy): rejected. Sites that need the browser tier would get nothing.
- **Interface names on Unix only, ignored or refused on Windows** (Spider): rejected. Windows can bind by the interface's address with the same effect.
- **A network namespace per browser**: rejected. It would keep HTTP/3, but it works only on Linux and needs privileges, while the relay works on every OS.
- **A custom socket connector with `IP_FREEBIND`**: rejected. Neither reqwest nor wreq lets the caller create the socket, while Linux's `ip_nonlocal_bind` lets their own `local_address` bind any address of the prefix.
- **Random addresses inside the prefix on every rotation** (freebind, the Invidious rotator): rejected. A replacement in the same /64 is the same client to Cloudflare.

## Consequences

**Configuration.**
- **Changes ADR 0021:** `local_addresses` takes a list of addresses, an interface name, or an IPv6 prefix. It sets the source of the Session's outgoing connections: to targets directly, or to its proxy when the Session has one (ADR 0021). Rotation on block moves the local address only for Sessions without a proxy; with a proxy, the proxy's exit is what rotates.
- Interface names are resolved to their addresses on every OS with `netdev` (MIT, maintained, reports gateways). Linux, macOS and illumos also bind the socket to the device (`SO_BINDTODEVICE`, `IP_BOUND_IF`). Windows binds by address, which forces the interface because Windows sends under the strong host model by default ([Cable Guy](https://learn.microsoft.com/en-us/previous-versions/technet-magazine/cc137807(v=msdn.10))); the docs note that the interface needs its own route and that an administrator can change this with `WeakHostSend`.
- An IPv6 prefix covers any address in it on Linux, once the system allows binding addresses not assigned to an interface (`net.ipv6.ip_nonlocal_bind=1`) and routes the prefix locally, as the docs describe. The engine checks both at start. On macOS and Windows, which have no equivalent, a prefix covers only the addresses assigned to the host. Where a prefix yields no usable address, the run is refused with the Error code `local_address_unavailable`. Nothing is ever silently ignored.
- A Session binds one IPv4 and one IPv6 address when the pool has both. A target with no address in a family the Session holds fails with `address_family_unavailable`. Neither it nor `local_address_unavailable` is retryable (ADR 0038): the configuration or the host must change.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#1542](https://github.com/goodfetch/goodfetch/issues/1542)): `address_family_unavailable` is in the Unavailable group, not retryable, with the details `{name, held}`, `held` being `ipv4` or `ipv6`. It is raised when the one family the Session holds has no address and the other family's lookup gave one; a name with no address at all keeps its lookup's code.

**Leaks.**
- DNS queries for a Session with a local address leave from that address through the engine's own resolver (ADR 0024), on every OS.
  > Amended by [ADR 0118](0118-every-fetch-tier-follows-redirects-as-the-browser-does-fails-a-cut-body-and-resends-only-what-a-site-never-processed.md): the engine's resolver keeps each answer for its TTL, a negative answer for its negative TTL and a server failure not at all, and drops an answer whose every address fails to connect. The engine's HTTP transports race the Session's address families under RFC 8305, 250 ms between attempts.
- **Changes ADR 0024:** the engine's own resolver, used on Linux by default, is also used on macOS and Windows for Sessions with a local address.
- Browsers hold WebRTC to `disable_non_proxied_udp` (`--force-webrtc-ip-handling-policy`), so it never reveals the host's other addresses; ADR 0014's interception of WebRTC still applies.
  > Note (agent decision, pending owner review), 2026-10-24, [#632](https://github.com/goodfetch/goodfetch/issues/632): the pinned Chrome for Testing 156 ignores `--force-webrtc-ip-handling-policy` (a page still sent STUN over UDP) and honours `--webrtc-ip-handling-policy=disable_non_proxied_udp`, which every browser the engine launches now passes. No browser-protocol interception sees WebRTC, so the domain policy holds its TCP connections through the browser's proxy resolution instead (ADR 0014's note of the same date).

**Browsers.**
- **Changes ADR 0017:** a browser Session with a local address sends its traffic through the engine's egress relay, bound to that address. The relay tunnels and leaves the TLS fingerprint unchanged; ADR 0042's terminating mode applies only to hosts with a certificate exception.
- **Changes ADR 0016:** the switch that ADRs 0016 and 0017 give over the egress proxy of raw CDP Sessions never removes the binding: a Session with a local address always goes through the relay.
- Chrome uses no HTTP/3 through a proxy ([http_stream_factory_job.cc](https://chromium.googlesource.com/chromium/src/+/main/net/http/http_stream_factory_job.cc)), so such a Session speaks HTTP/2, like any proxied Session.
- **Changes ADR 0022:** a local address belongs to the user's machine, so a Session on a Browser host or a third-party CDP endpoint (ADR 0033) with one is refused with `local_address_unavailable`.
  > Note (agent decision, pending owner review), 2026-10-25, [#638](https://github.com/goodfetch/goodfetch/issues/638): the refusal covers every Session whose browser the engine does not launch on this machine, a Borrowed browser on loopback included, since no relay can be put under a running browser (ADR 0056); its `failure` is `not_launched_here`, and `entry` is the setting's value as written. A Session with local addresses behind an `https://` proxy, which the relay does not chain through yet, is refused the same way with `proxy_not_relayed`, rather than reaching its proxy from an address the OS chooses. The relay resolves through the engine's own resolver from the Session's address and binds each connection, to a site or to the upstream proxy, to its address of the family; a family it holds no address of is never connected to. Each Session's addresses are drawn by its position in the Run, so a Session reopened from run state binds the same ones. The Run's `egress.local_addresses` is the only scope: a Session's own `settings` still refuse the key with `setting_not_applicable`.

**Rotation.**
- When a block retires a Session without a proxy (ADR 0021), its replacement prefers an address outside every /64 (IPv6) or /24 (IPv4) blocked on that domain during the run. When the pool has no other block, it rotates within the block and the run notes it.
- New Sessions with no block involved spread across blocks round-robin. Both block sizes are settings.
  > Note (agent decision, pending owner review), 2026-10-25, [#637](https://github.com/goodfetch/goodfetch/issues/637): `egress.local_addresses` is one value of three forms: a JSON list of addresses, or a string that is an interface's name or, with a `/`, an IPv6 prefix (an IPv4 prefix is `setting_invalid`). A Recipe may expose it but never set it. The Run's start checks it and refuses with `local_address_unavailable` (Unavailable, not retryable, details `{entry, failure, setting}`, `failure` one of `not_held`, `unknown_interface`, `interface_without_address`, `prefix_unusable`): every listed address must be one a socket binds, and an interface's IPv6 link-local addresses do not count. Blocks are taken in address order, each block's addresses in turn on each round; on a prefix the host binds any address of, the n-th Session takes block `n mod blocks` and, in it, the address `round + 1`, never the block's own Subnet-Router address. A name server of a family the Session holds no address of is not asked, so no query leaves from another address. The Run report records both settings in its `settings`, as every effective value. Binding to the interface's device (`SO_BINDTODEVICE`, `IP_BOUND_IF`) is not built yet: an interface binds by its addresses on every OS.
  > Note (agent decision, pending owner review), 2026-10-26, [#682](https://github.com/goodfetch/goodfetch/issues/682): Foxhound's HTTP tiers bind each pool Session's addresses: reqwest binds one address per client, so a Session holding both families keeps a client of each and sends a hop from the family of its host's first answer (IPv4 first), and `wreq` binds both; an interface name now also binds the socket's device on Linux, macOS and illumos (`SO_BINDTODEVICE`, `IP_BOUND_IF`), Windows binding the address alone. A crawl's robots.txt and sitemap fetches send from the rotation's first position, the Run's first Session's. The Session pool keeps each Session's rotation position in run state and, per domain, the blocks (at the sizes in force) of every Session a block retired (`rate_limit`, `ip_block`, `challenge`, `captcha`); a Session opening for a request on that domain takes the next position outside them, looking 1,024 positions ahead, else the next one, and the Run report warns `local_address_rotated_within_block` naming that Session. "With a proxy" is a Run that sets `proxy.server` or `proxy.provider`: the replacement then keeps the retired Session's position and no block is recorded. A Session drawn among those already open (a full pool) keeps its address even in a blocked block.
  > Note (agent decision, pending owner review), 2026-10-30, the deep review's D5, 565-1 and 565-6: "with a proxy" follows the route a Session's requests take, not the Run's settings alone. The HTTP tiers send direct from the Session's addresses even when the Run sets a proxy, and any pool Session may serve on them, so the pool takes none of its Sessions as proxied yet: a block always blocks the blocks of the address the site saw, and the replacement leaves from outside them, until the HTTP tiers send through the proxy. A pool Session's browser context binds its egress relay to the rotation position the pool gave it, so its HTTP and browser requests leave from one address and a replacement's browser requests from outside the blocked blocks; the #638 note's "drawn by its position in the Run" still holds for a program's Sessions. A block met by an attempt whose Session the pool retired while it was in flight (its uses, its age, a full pool) still records that Session's blocks.
- Rotating local addresses on a block carries the legal rating of IP rotation on block ([legal exposure](https://github.com/goodfetch/goodfetch/issues/65)) and follows ADR 0035's placement of it.

**Unchanged.** ADR 0017's resolved-IP check and ADR 0021's `per_ip_concurrency`, which is keyed by the target's IP, apply as before.
