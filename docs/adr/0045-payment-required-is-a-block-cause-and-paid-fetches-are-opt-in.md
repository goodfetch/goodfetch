# Payment Required is a Block cause, and Paid fetches are opt-in, capped and journaled

A site that asks a crawler to pay, with HTTP 402 or a paywall redirect, gets the Block cause `payment_required`. Goodfetch never escalates, rotates or retries past it, because changing identity to avoid a payment gate is the masking the legal research rates medium to high risk. A run can instead pay, from the user's own Cloudflare account or wallet, through Cloudflare's pay-per-crawl headers or x402. It pays only domains the user approved outside the run, under a price cap and a currency Limit reserved before sending, through the Effect journal, so that a resume never pays twice. Goodfetch itself never charges anyone or holds money. This answers pain #6 (`compliance-site-owner-politeness`): site owners who want to be paid rather than merely block. Decided in [Network defaults](https://github.com/goodfetch/goodfetch/issues/118).

> Amended by [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md): Paid fetches are Foxhound's. A Collie run meets a demand for payment as the Block cause `payment_required` and never pays, and `pay_domains` given to a Run on a Collie engine is refused like any other setting Collie does not carry, with `not_in_product` ([ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md)).

Cloudflare Pay per crawl, in private beta since July 2025 ([blog](https://blog.cloudflare.com/introducing-pay-per-crawl/)), answers an unpaid crawler with a 402 and a `crawler-price` header. The crawler retries with `crawler-exact-price`, or sends `crawler-max-price` up front, inside a Web Bot Auth signature that covers the header. A 200 then carries `crawler-charged`, and Cloudflare bills the crawler's registered account as merchant of record ([docs](https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/use-pay-per-crawl-as-ai-owner/crawl-pages/)). x402 has been a Linux Foundation project since 2 April 2026, with the schemes `exact`, `upto`, `batch-settlement` and `auth-capture` ([specs](https://github.com/x402-foundation/x402/tree/main/specs/schemes)). Cloudflare's proposed deferred scheme became `batch-settlement`, whose Cloudflare binding is credit-backed and authenticated by Web Bot Auth ([spec](https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement_cloudflare.md)), and Cloudflare's Monetization Gateway beta charges agents per request over x402 ([blog](https://blog.cloudflare.com/monetization-gateway-beta/)). TollBit, through Fastly, redirects bots to its paywall with a 302 rather than a 402 ([Fastly](https://www.fastly.com/documentation/guides/integrations/non-fastly-services/tollbit/)). Crawlee, Firecrawl, Spider and Scrapy neither recognize a 402 nor pay or sign; Firecrawl's `auto` mode would retry it through a stealth proxy. Browserbase signs requests, but only in its cloud ([signed agents](https://blog.cloudflare.com/signed-agents/)).

## Considered Options

- **Treating a 402 like a 401, 403 or 429** (ADR 0021's escalation, Firecrawl's `auto`): rejected. It changes identity to avoid a payment the site asked for, which is what the *Reddit* case rests on ([legal exposure](https://github.com/goodfetch/goodfetch/issues/65)).
- **Never paying, so a 402 stays a block**: rejected. Pain #6 would get half an answer, and sites that sell access to crawlers would stay closed.
- **Cloudflare's headers only**: rejected. x402 is the open standard that Cloudflare's own newer products use.
- **Paying any domain the crawl reaches, within the currency Limit**: rejected. A broad crawl could spread its currency Limit over sites the user never chose to buy from.
- **Letting a run or a Recipe name the domains it pays**: rejected. An agent could approve its own spending, and a published Recipe could lock in its author's domain, both against the user's wallet.
- **`incomplete` Completeness for a run that left `payment_required` pages**: rejected. A Schedule on a site with one paywalled page would never get a Baseline (ADR 0036), the outcome ADR 0036 rejected for offset-paginated crawls.
- **Fetching exchange rates to compare a price with a Limit in another currency**: rejected. It would be an unconfigured call (ADR 0043) and a price feed the engine does not own (ADR 0001).
- **Cloudflare Pay Per Use** ([blog](https://blog.cloudflare.com/pay-per-use/)): out of the engine's reach. It is an account agreement in which the buyer reports usage, not a request protocol.

## Consequences

**The Block cause.**
- **Changes ADR 0035:** `payment_required` joins the Block causes of its block-detection rules (`challenge`, `captcha`, `rate_limit`, `ip_block`, `decoy`). A 402, or a redirect that the rules match as a paywall (TollBit's), is classed `payment_required`. The quoted price, when the response gives one, is recorded in Provenance.
- **Changes ADR 0021:** `payment_required` never moves a domain up a proxy tier, never retires its Session to rotate, and is never retried unless the run may pay that domain. Rules detect it, never the Decision provider.
- **Changes ADR 0005:** a finished run that left pages in scope at `payment_required` reports Completeness `unverified`, as for offset pagination, and lists those pages. It can therefore become a Schedule's Baseline but cannot soft-delete Records (ADR 0036).
- The Console's "Needs you" view lists the domains that asked for payment with their prices, and offers to add them to `pay_domains` for the next run.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.

**Site preferences.**
- **Changes ADR 0016:** RSL (Really Simple Licensing, a standard since December 2025; [rslstandard.org](https://rslstandard.org/)), declared through robots.txt, joins the Site preferences the engine always reads and records in Provenance, and is honoured under `respect_site_preferences`.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the switch is `site_preferences.respect_use_signals`. It covers RSL and the AI-use signals, while robots.txt has its own setting.

**Who allows paying.**
- `pay_domains` lists the domains a run may pay, matched by registrable domain as in ADR 0004, each with an optional `max_price_per_page`. `*` is accepted only when written explicitly.
- It is taken only from Operator policy, user and project configuration, or a person's answer in the Console or an interactive CLI prompt, as the "Needs you" offer above. On a single-user machine that answer is stored in the user configuration. On a Daemon with accounts, whose user configuration every member's runs share, only the operator role may widen `pay_domains`, raise `max_price_per_page` or write the rates and RPC endpoints below, and these values, the answer included, are stored in the Operator policy. A Recipe or a run can only narrow it, removing domains or lowering caps. **Changes ADR 0028**: `pay_domains` is a setting that the Recipe and run layers can only narrow.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Changes ADR 0011:** widening `pay_domains` or `max_price_per_page`, and writing the rates and RPC endpoints below, is answered only in the Console or an interactive CLI prompt, under ADR 0031's step-up on a Daemon with accounts (**Changes ADR 0031**), or by editing configuration and Operator policy. No MCP tool, code-mode function, SDK method or `--json` CLI operation widens or writes them; a run may still narrow `pay_domains` and `max_price_per_page` through any surface. This follows ADRs 0029 and 0041, which restrict Reconciliation and raising a Limit the same way.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Changes ADR 0014:** `pay_domains` is what ADR 0014 means by a run allowing payments. A payment to a domain outside it is never made, whoever decides it, model or code.
- Paying happens only in a Session whose Access mode is `identified` (ADR 0021). In any other Session the page stays at `payment_required`, with the reason recorded, so `pay_domains` set in configuration never affects `standard` or `stealth` runs.

**Caps and currency.**
- `max_price_per_page`, overall or per `pay_domains` entry, is an amount with a currency (`USD 0.02`). Like `pay_domains`, it is raised only in Operator policy or user and project configuration; a Recipe or a run can only lower it.
- A Paid fetch is made only when a currency Limit applies (ADR 0041) in the quote's currency, or in a currency reached through a fixed rate, such as USDC to USD at 1:1, and the quote is at or below the cap after the same conversion. Otherwise the page stays at `payment_required`, with the reason recorded.
- The Limit that allows paying must be one the run's own Client could not set: a Limit a person set in the Console or an interactive CLI prompt, or a managed policy's. A Limit a Client set for its own work, as ADR 0041 lets it, still caps payments but does not allow them. **Changes ADR 0041:** each Limit row records who set it: a person interactively, a managed policy, or a Client. A Client that lowers a person's Limit adds a row of its own, as for managed rows, so the person's row and the allowance it carries stay. Run and Schedule Limits, which are run parameters rather than ledger rows, cap payments but never allow them.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Changes ADR 0012:** its price table may declare fixed rates between currencies. Rates used for Paid fetches come only from the shipped table, Operator policy, or user and project configuration, never from a Recipe or a run, so a run cannot shrink a quote. The engine fetches no rates.
- **Changes ADR 0041:** a new Usage kind, `paid_fetch`, counts Paid fetches and their amounts by currency. Limit rows that name it carry the must-understand flag, so an older engine refuses rather than overspends.

**Schemes.**
- Cloudflare's `crawler-*` headers; x402 `batch-settlement` with its Cloudflare binding; x402 `exact` and `upto` on EVM networks and Solana.
- x402 is built on `x402-rs` (Apache-2.0), which covers `exact`, and `upto` on EVM, and on `alloy` for EIP-712 and EIP-3009 signing. Goodfetch contributes `upto` on Solana and `batch-settlement` to `x402-rs`.
- Each Paid fetch reads the quote, reserves the worst case against the currency Limit (ADR 0041's reserved costs), journals the payment as an Effect (ADR 0010), sends it, then records what was charged. A Paid fetch is never hedged or coalesced (ADR 0040) and never served from or stored in the Response cache (ADR 0046).
- Every payment goes to the Audit log and is marked on the Record's Provenance with the scheme, the amount and the payee domain.

**Exactly once.**
- Whenever a site declares x402's `payment-identifier` extension, the payment carries an ID derived from the journaled payment, so the site treats a resend as the same payment.
- **The rule.** After a payment is sent, any answer other than success, or no answer, stops further payment for that page until the engine knows the outcome. It never signs a new payment for that page until it has proved, from the chain's finalized state through an RPC endpoint taken only from Operator policy or user and project configuration, that the earlier payload has not settled and can never settle. The local clock never decides expiry.
  - **Settled:** the payment is recorded as made and stays so. The page is requested again only from a site that declared `payment-identifier`. Otherwise, or when that request fails again, the page is listed in "Needs you" as paid but not received, and buying it again is a new Paid fetch that a person confirms. A payment proved settled never goes to Reconciliation, whose "it did not happen" would record it as not made.
  - **Not settled and still able to settle:** only the same payload may be sent again, which cannot be charged twice.
  - **Proved unable to settle:** the payment is recorded as not made, and a new one may follow.
  - **Not provable**, with no RPC endpoint configured, no answer, or a scheme without a proof: an uncertain Effect, never paid again automatically, which only a person reconciles.
- **When a run ends** (`finished`, `stopped` or `failed`; ADR 0029) while a payment is still able to settle or not provable, the payment stays an uncertain Effect and its reservation stays charged at the worst case, as ADR 0041 charges a reservation still open in a run's state, until a proof or a person settles it.
- **Proofs per scheme** are specified with the Site access area. The conformance suite tests them against local chains run as fixtures (Anvil, `solana-test-validator`), and a nightly job checks them on public testnets, one of the jobs ADR 0043 lists as reaching named outside endpoints (**Changes ADR 0032**). They start from EIP-3009's `authorizationState` and `validBefore`, Permit2's `nonceBitmap` and deadline (used by `upto` and by `exact` for tokens without EIP-3009), and, on Solana, a recent blockhash fetched at `finalized` whose `lastValidBlockHeight` the finalized chain has passed, with `upto`'s payment channel settled at closure.
- Cloudflare's headers and the Cloudflare binding of `batch-settlement`, which signs the request's authority, `signature-agent` and `payment-signature` but carries no nonce, have no idempotency key. A payment through either that is interrupted before its response is an uncertain Effect: it is never paid again automatically, the page stays at `payment_required`, and only a person reconciles it.

**Keys.**
- **Changes ADR 0021:** `goodfetch signing-key create` generates the Ed25519 key of an `identified` Session, kept as a Secret reference (ADR 0015), and `goodfetch signing-key directory` (renamed by ADR 0056, which gives `goodfetch identity` to Saved identities) exports the signed key directory for the user to host at `/.well-known/http-message-signatures-directory` on a domain they control, which Cloudflare requires along with registration through its Bot Submission Form ([Web Bot Auth](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/)). Signing uses Cloudflare's `web-bot-auth` crate (Apache-2.0). The engine sends `Signature-Agent` in the string form Cloudflare accepts; both Web Bot Auth drafts are still individual drafts, so the conformance suite tracks the form Cloudflare verifies.
- x402 wallet keys are Secret references too, resolved only at signing.
- Registering with Cloudflare and funding an account or wallet stay with the user; the docs walk through both.
- No cosmetic rule hides or removes an element that contains a section the page declares paid with schema.org's `isAccessibleForFree: false`, nor, outside `wall_domains` (ADR 0052), a paywall vendor's overlay or an element that covers such a section. The scripts that render the paywall vendors' overlays are on the never-block list, so the overlay renders, except on a domain in `wall_domains` (ADR 0052). The paywall is recorded in Provenance, but it is not `payment_required`: that stays a 402 or a paywall redirect, unless ADR 0048's wall test makes an "accept or pay" overlay `consent_required` (ADR 0047).
