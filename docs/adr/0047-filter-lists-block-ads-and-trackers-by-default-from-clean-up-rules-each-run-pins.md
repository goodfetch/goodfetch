# Filter lists block ads and trackers by default, from Clean-up rules that each run pins

Every browser Session blocks ads and trackers by default, in every Access mode. Brave's `adblock-rust` matches each request inside the interception ADR 0014 already runs, and a never-block list keeps challenge, anti-bot, anti-fraud and payment scripts loading whatever the Filter lists say. The same rules remove ads, Consent prompt leftovers and page annoyances from extracted content in every tier. On the live page they hide those elements through a style sheet the site cannot see on Chromium, and only on demand on Firefox and WebKit, where any hiding is visible. The rules come as **Clean-up rules**:
- the part whose licences allow embedding (CC BY-SA, MPL-2.0 and MIT for the rules; Apache-2.0 and MPL-2.0 for the release's stand-ins beside them), precompiled in the binary;
- the full set, a digest-pinned download refreshed in every release;
- an opt-in, signed daily channel.

Each run holds to one version of them for its whole life and names it in its results. Decided in [Built-in page clean-up](https://github.com/goodfetch/goodfetch/issues/119) (parity row SA-17); Consent prompts are handled by ADR 0048.

Competitors split on the default:
- **On by default.** Firecrawl's `blockAds` ([API](https://docs.firecrawl.dev/api-reference/endpoint/scrape)), spider.cloud's `block_ads` and `block_analytics` in browser mode ([API](https://spider.cloud/docs/api)) and Browser Use, which loads uBlock Origin Lite ([profile.py](https://github.com/browser-use/browser-use/blob/main/browser_use/browser/profile.py)).
- **Off.** Steel's `blockAds` ([configuration](https://docs.steel.dev/overview/sessions-api/configuration): "Steel does not block ads by default"), the Spider crate's `block_ads` behind its `adblock` feature ([chrome_common.rs](https://github.com/spider-rs/spider/blob/main/spider/src/features/chrome_common.rs)), Browserbase's `blockAds` ([API](https://docs.browserbase.com/reference/api/create-a-session)), Crawl4AI's `avoid_ads`, and ScrapingBee's `block_ads`.
- **No ad blocking at all.** Crawlee, whose `blockRequests` blocks URL substrings through CDP and does nothing on Firefox or WebKit in its JavaScript version ([docs](https://crawlee.dev/js/api/playwright-crawler/namespace/playwrightUtils)).

The real hazard is that a tracker list blocks the scripts that bot protection needs. EasyPrivacy blocks DataDome, PerimeterX, Akamai's `/akam/` paths, iovation, ThreatMetrix and Forter ([EasyPrivacy](https://easylist.to/easylist/easyprivacy.txt)). Cloudflare documents that ad blockers may block the scripts Turnstile needs, which makes challenges fail ([Turnstile troubleshooting](https://developers.cloudflare.com/turnstile/troubleshooting/challenge-solve-issues/)). uBlock Origin's unbreak list re-allows Turnstile, hCaptcha and reCAPTCHA ([unbreak.txt](https://github.com/uBlockOrigin/uAssets/blob/master/filters/unbreak.txt)), and Spider leaves DataDome and reCAPTCHA unblocked on purpose ([scripts.rs](https://github.com/spider-rs/spider_network_blocker/blob/main/src/scripts.rs)). About 29.5% of internet users run a blocker ([GWI via Backlinko](https://backlinko.com/ad-blockers-users)), so blocking is consistent with `standard`'s ordinary browser (ADR 0021).

## Considered Options

- **Off by default** (Steel, the Spider crate, Browserbase, Crawl4AI, ScrapingBee): rejected. Ads and trackers cost requests, bytes on proxies billed by volume, and noise in screenshots and AI input. A breakage check (below) handles the pages that need them.
- **A browser extension** (uBlock Origin Lite in Browserless and Browser Use): rejected.
  - It is GPLv3, and Playwright loads extensions only into Chromium, so Firefox and WebKit would go without.
  - Browserless documents that it compiles about 69,000 rules on every fresh launch ([launch options](https://docs.browserless.io/baas/launch-options)).
  - Chrome 139's removal of Manifest V2 broke the extensions Browser Use loaded ([browser-use#2724](https://github.com/browser-use/browser-use/issues/2724)).
- **Chromium's own ad filter** (`Page.setAdBlockingEnabled`): rejected. Its rules arrive through Chrome's component updater ([subresource_filter](https://chromium.googlesource.com/chromium/src/+/main/components/subresource_filter/README.md)), which ADR 0043 turns off.
- **URL patterns through `Network.setBlockedURLs`** (Crawlee): rejected as the mechanism. It cannot run filter-list logic, works on Chromium only, and the engine already pauses every request for ADR 0014's policy.
- **Hard-coded domain lists** (Firecrawl's open-source service, Crawl4AI, Steel): rejected. Coverage is thin, and Firecrawl's list blocks the whole of `fbcdn.net` ([api.ts](https://github.com/firecrawl/firecrawl/blob/main/apps/playwright-service-ts/api.ts)).
- **Fetching the lists from their authors at run start** (Ghostery's library, puppeteer-extra, Browser Use): rejected as the default. It is an unpinned call nobody configured (ADR 0043), and launches fail when it fails ([puppeteer-extra#840](https://github.com/berstend/puppeteer-extra/issues/840)); users ask for bundled lists so it works offline ([ghostery/adblocker#3994](https://github.com/ghostery/adblocker/issues/3994)). It stays available as `clean_up.update = upstream`.
- **Downloading the lists while building the binary** (Spider's `adblock_easylist`): rejected. Spider's build fetches them unpinned and silently ships empty lists when the download fails ([build.rs](https://github.com/spider-rs/chromey/blob/main/build.rs)), and GPL lists compiled into the binary risk making it "a larger program" under the GPL.
- **The daily channel on by default**: rejected. One request a day from every install would show Goodfetch each install's address, the census ADR 0043 refuses.
- **Hiding on the live page through page scripts or a `<style>` element**: rejected on Chromium, where the site would see it. Firefox and WebKit can apply invisible user style sheets, but Playwright's driver, through which ADR 0019 runs them, does not expose them, so there hiding happens only on demand. Patching Playwright's drivers for both engines is rejected as over-engineering: a fork to maintain for a need on-demand hiding already covers, on a path ADR 0019 already plans to leave for Firefox.
- **Differential updates for the daily channel** (uBlock Origin's and AdGuard's): rejected as over-engineering. They serve millions of clients hourly; the channel is one opt-in download a day.
- **Non-commercial lists**: excluded by licence. Disconnect's and DuckDuckGo's lists are CC BY-NC-SA ([Disconnect](https://github.com/disconnectme/disconnect-tracking-protection/blob/master/LICENSE), [DuckDuckGo](https://github.com/duckduckgo/tracker-blocklists)), and Steven Black's merged hosts file includes non-commercial sources ([readme](https://github.com/StevenBlack/hosts)). Peter Lowe's list has no formal licence ([site](https://pgl.yoyo.org/adservers/)) and stays out until it has one.

## Consequences

**Matching.**
- **The library.** `adblock` (adblock-rust, MPL-2.0, Brave), unmodified ([repository](https://github.com/brave/adblock-rust)). It handles network rules, cosmetic rules, redirects and uBlock Origin syntax. Brave measured 5.7 µs per request ([blog](https://brave.com/blog/improved-ad-blocker-performance/)), and its FlatBuffers rewrite cut the memory of its default lists by 75%, about 45 MB saved ([blog](https://brave.com/privacy-updates/36-adblock-memory-reduction)).
- **Changes ADR 0018:** the licence allowlist accepts MPL-2.0 for unmodified files, with the notice saying where their source is.
- **Where it runs.**
  - On Chromium, matching runs inside ADR 0014's interception. On Firefox and WebKit, it runs inside Playwright's routing.
  - It covers every request type that interception covers, service workers included.
  - A blocked request fails as `BlockedByClient`, the error a real blocker produces.
- **Redirect rules.** These serve harmless stand-ins through the same interception, so a page calling a blocked script does not break.
  - The stand-ins are DuckDuckGo's tracker surrogates (Apache-2.0, with MPL-2.0 parts; [repository](https://github.com/duckduckgo/tracker-surrogates)), covering Google Analytics, Tag Manager and Publisher Tag, AdSense, Facebook's SDK, Criteo and others, and Mozilla's web-compatibility shims (MPL-2.0; [source](https://searchfox.org/firefox-main/source/browser/extensions/webcompat/shims)).
  - Lists name stand-ins by uBlock Origin's resource names, so Goodfetch keeps an MIT alias table from those names to these files.
  - A redirect rule whose stand-in is missing simply blocks, as `adblock-rust` does when no resource matches ([blocker.rs](https://github.com/brave/adblock-rust/blob/master/src/blocker.rs)).
  - Brave's own `adblock-resources` holds Brave's fixes and a few third-party scripts, not the stand-ins and scriptlets the lists name; Brave assembles those from uBlock Origin's GPL-3.0 files ([brave-core-crx-packager](https://github.com/brave/brave-core-crx-packager)).
- **Memory and threads.** One engine loads each version of the Clean-up rules once, shares it between the runs that hold to it, and unloads it when none does. `adblock`'s default `single-thread` feature is faster and lighter but makes `Engine` neither `Send` nor `Sync`; without it, matching shares a lock per loaded version. The Site access spec measures both at ADR 0040's concurrency and picks one shared engine without the feature, or one engine per worker thread with it.
  > Note (agent decision, as built), 2026-10-23, [#713](https://github.com/goodfetch/goodfetch/issues/713): kept the one shared engine behind an `Arc`. Measured with `adblock` 0.13.3 on the embedded lists (EasyList, EasyPrivacy, Fanboy Annoyance and Brave's unbreak list, 7.8 MB serialized) on the 16-thread reference server, 600 mixed requests per thread: with requests paced as a page sends them (each thread waiting 1 ms between two, 16,000 requests a second at 16 threads), the shared engine matched in 13.2 to 19.4 µs a request against 16.9 to 19.2 µs for one engine per thread, within 10 %, and held 11.8 MB against 182 to 204 MB. Matching flat out, the shared engine serializes on its regex manager's lock, which `adblock` holds for a whole check: 3.4 to 6.1 µs a request at one thread, 21 to 24 µs at 4 and 79 to 130 µs at 16, against 2.8 to 3.6, 3.3 to 4.2 and 6.8 to 8.3 µs per thread's own engine; at 200 µs between requests and 16 threads (80,000 a second) it matched in 20 to 25 µs against 11 µs. A page's interception sends far fewer requests than that, so the per-worker engines' sixteenfold memory buys nothing; a profile showing the lock contended is the signal to revisit it (a small pool of engines, or one per worker as this point allows).

    > Note (agent decision, on a default, not read by the owner), 2026-10-23, [#717](https://github.com/goodfetch/goodfetch/issues/717): the consent-vendor entries are no longer dropped: each joins the never-block list as an entry of kind `consent`, scoped to the line the lists wrote, so the lists keep them and the runner sees every prompt. The cookie sections stay out of Fanboy Annoyance until extraction-side removal (#715) gives them their only use, and the wall test (#718) is done.

**Defaults and the never-block list.**
- **Settings, each settable per run (ADR 0028).**
  - `filter_lists.ads`, `filter_lists.trackers` and `filter_lists.annoyances` are on by default in every Access mode. In browser Sessions they block requests and hide elements; in every tier, HTTP included, they remove elements from extracted content.
  - `filter_lists.first_party_scripts` allows a site's own scripts, as Spider's `allow_first_party_javascript` does.
  - `filter_lists.extra` adds the user's own lists, as files or URLs. A URL is a configured destination (ADR 0043). As ADR 0017 rules for Plugin endpoints, it may use a private range only when set in Operator policy or user and project configuration, or by a Recipe or run value that Operator policy allows; otherwise it is checked as an address a page can reach. The lists it adds are part of the version a run holds to (below). Their scriptlets run only when the list is set in Operator policy or user and project configuration, and on a Daemon with accounts only in Operator policy (**Changes ADR 0028**); a list a Recipe, a run or an agent surface adds contributes network and cosmetic rules only (**Changes ADR 0011**).
- **The never-block list.** Goodfetch maintains it, under MIT. It names:
  - challenge and CAPTCHA providers;
  - anti-bot sensors;
  - anti-fraud and payment scripts.

  It wins over every Filter list, the user's own included, and over `block_resources`, since image challenges need their images. It is tested on the Proving ground's fixtures, and against a real vendor online wherever the online Proving ground or ADR 0035's owner-approved trials include that vendor (ADR 0025).
- **Consent prompts come first.** Whether or not `consent_handling` is on (ADR 0048), the rules aimed at Consent prompts never act before its runner and its wall test.
  - **Which rules.** The EasyList Cookie List, AdGuard's Cookie Notices, and the consent-vendor entries of the other lists (EasyPrivacy's `/sourcepoint.js` and `-didomi.js`, for example).
  - **What they may do.** They never block a request or hide an element on the live page, and their scriptlets never run, since some write acceptance (`set-cookie, cookieconsent_status, allow`). Once the runner and the wall test are done, they only remove leftovers from extracted content.
  - **The consent vendors' prompt scripts.** autoconsent's rules detect prompts by selectors and name no host, so Goodfetch maintains, beside the never-block list, the hosts and paths from which the vendors its vendor rules cover load their prompts. They join the never-block list, scoped to the prompts' scripts, so the vendors' telemetry stays blocked (EasyPrivacy's `||privacy-analytics-proxy.cookiebot.com^`, for example). Site rules' URL patterns never join. The conformance suite tests each entry.
  - **Fanboy Annoyance without its cookie part.** Upstream, Fanboy Annoyance includes the whole EasyList Cookie List, so Goodfetch builds both from the `easylist/easylist` repository's templates, the cookie sections only once. Under `clean_up.update = upstream`, the engine fetches easylist.to's builds. For those and for lists from `filter_lists.extra`, it drops the cookie sections by either marker form (`! *** easylist:easylist_cookie/… ***` in easylist.to's builds, `! easylist_cookie_….txt` in fanboy.co.nz's), and the consent-vendor entries of the other lists, before compiling.
  - **Scriptlets in lists Goodfetch did not build.** Those in such a cookie section are held back like the Consent prompt rules. Any other scriptlet of a list set through `filter_lists.extra` acts for the person who configured that list. What it writes is recorded as their configuration in Provenance and the Audit log, never as the engine's own acceptance.
- **Breakage, caught two ways.**
  - **Changes ADR 0020:** the per-route sample comparison also fetches its sample with blocking off. If the extracted results differ beyond what the rules remove, blocking is off for that route (on `wall_domains`, differences from a Wall's scripts are ignored, ADR 0052), learned as the tier choice is. A route where the paywall detector or the ad-blocker-wall rules see a wall only with blocking off gets blocking off too, learned the same way, so a list that blocks a site's own wall script (an in-house paywall, an ad-block detector) never gets around the wall, except on a domain in `wall_domains` (ADR 0052).
  - A page with no Block cause that fails its Page check, or that shows an ad-blocker wall outside `wall_domains` (ADR 0052), while blocking is on is retried once with blocking off, and blocking is learned off for the domain, keyed as in ADR 0004, only when the retry passes. `challenge` and `captcha` follow the next point, and no other Block cause is retried this way (ADRs 0021, 0045 and 0048).
  - **Changes ADRs 0021 and 0035:** when the interception blocked a request from a challenge's document or frames, the page is retried once with blocking off, at once, before ADR 0035's step 2 waits for the challenge to clear. The blocked request is an event the engine already has. Blocking is learned off for the domain only when the retry clears the challenge; Provenance and the run report then flag the vendor for the user to report, and the maintainers add it to the never-block list and its suite. A challenge that no blocked request touched follows ADR 0035's ladder unchanged.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#716](https://github.com/goodfetch/goodfetch/issues/716): the two retries above, on a Collie page, as built. **What "blocking" means here:** the Filter lists; the never-block list and `browser.block_resources`, the program's own choice, stay. **When:** after a navigation's document is judged by its Page check, while any of its Session's lists is on and its domain is not learned off: a page whose Page check raised `page_check_failed` is retried whether or not the lists blocked anything of it, and a page the Product's Block classification names `challenge` or `captcha` is retried when the lists blocked at least one request of the page during that navigation call; a page with any other Block cause, or that raised `logged_out`, is not. Block classification reaches the page crate as the `goodfetch_page::blocks::BlockClassifier` seam, which Collie's composition fills with its block-detection rules (ADR 0127's rule data), judged on the page's serialized document. **The retry:** the same `goto` again (a `reload`, `go_back` or `go_forward` reloads the document it reached), at once, every request of the page passing step 4 without the lists until the retry is judged; its outcome, response or error, answers the call, and it is neither a Run's retry nor a failure. **Passing:** the retry's Page check passes, or for a challenge its document no longer checks the browser; the vendor flag and the Challenge ladder's wait stay ADR 0035's tickets (#1065). **Learned:** for the first document's domain keyed as ADR 0004 (the registrable domain under the full Public Suffix List, or the address), for every Session of the Run, held in memory while any page of the Run is open; it is not persisted across Runs or resumes, since no learned-state store exists for a Collie Run yet. Requests from a document on that domain skip the lists. **Provenance:** action `blocking_off` with `page_id`, `session_id`, `url`, `domain` and `reason`: `page_check_failed` or `challenge` (with `block`'s `cause` and `rule`) and `learned`, for the retry; `learned` for each later document loaded on a learned-off domain.
- **Provenance.** Each page's Provenance records whether blocking was on, the Clean-up rules it used, how many requests were blocked, and which elements and how much text were removed from extracted content. A removal above a share of the main content, which the Site access spec sets, is flagged, so a rule that removes real content shows.

**Removing and hiding elements.**
- **Changes ADR 0007:** before dom-smoothie, htmd or any AI input, the engine removes from the page's HTML the elements the cosmetic rules match. It walks shadow roots and does this in every tier, so hidden text never leaks into output, as it did in [jina-ai/reader#1138](https://github.com/jina-ai/reader/issues/1138). Raw HTML, WARC, Run traces, the Frontier's link reading (ADR 0007's lol-html pass) and the user's own selectors see the page untouched. On a route whose browser sample showed a consent wall, nothing is removed and the page is `consent_required` in every tier, unless the domain is in `consent_domains` (ADR 0048), or in `wall_domains`, where the page is read as served unless the sample showed the content withheld (ADR 0052).
- **Live page, `live_hiding` (`auto` by default).**
  - **On Chromium**, `auto` hides matched elements through `CSS.createStyleSheet`, in every frame and every new document. That call builds a style sheet with no element in the DOM (its owner is the Document itself) ([style_engine.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/css/style_engine.cc)). `document.styleSheets` is built only from DOM nodes, so the site cannot see the sheet ([style_sheet_collection.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/css/style_sheet_collection.cc)). Computed styles still show the hiding, as they do for any person using a blocker.
  - **Procedural rules.** A style sheet holds only CSS. Cosmetic rules that are not plain CSS (`:has-text`, `:upward`, `:-abp-contains` and the like) hide on the live page only where they translate to CSS, `:has()` included; the rest apply to extracted content only, where the engine evaluates them on the parsed page.
  - **Shadow trees.** These sheets never reach them, so Consent prompts there are handled by ADR 0048's runner.
  - **Cost.** Enabling the CSS domain has a cost, which the benchmark measures. `live_hiding = off` removes it, and Provenance records it.
  - **On Firefox and WebKit,** Playwright offers only `addStyleTag`, a visible `<style>` element. There `auto` hides only on demand: when the guard (ADR 0019) finds an action's target covered by an element a rule matches. `live_hiding = always` hides everywhere, with a warning that the site can see it. Where ADR 0048's route into Playwright's utility world works, that `<style>` is inserted from there; otherwise `addStyleTag` inserts it from the main world, and Provenance marks it.
  - **What else sees the hiding.** **Changes ADR 0019:** when the guard finds that live hiding hid an action's target, it lifts the matching rule for that Session and retries, recording the rule in Provenance; this is never Drift (ADR 0009), so a Plan replayed under newer Clean-up rules needs no Repair. Links inside an element a cosmetic rule matched are left out of ADR 0035's trap-link judgement, so a link inside a hidden ad is not taken for a trap. Before a Plan step's Target fingerprint check (ADR 0009), the engine lifts any live-hiding rule that matches the step's target, so the check sees the target as the site renders it.

Frames in another process (out-of-process iframes) get no sheet until the driver attaches to their targets. **Lifting:** the guard asks, when its check finds the target not visible, which applied rule matches the target or an element holding it whose computed `display` is `none`; it lifts those for the Session, writes every sheet of the Session's pages again and looks at once. A target an element covers is never one a rule hides on Chromium (the covering element is hidden already), so the case the guard lifts is a target inside a hidden element. **Removal:** the document is serialized with every shadow root (`DOM.getOuterHTML`'s `includeShadowDOM`, each root a `<template shadowrootmode>`), and removal applies the hiding rules and the procedural rules it can evaluate (`:has-text` with plain text, `:min-text-length`, `:upward`, after a CSS selector; the others apply nowhere yet) within each root. It exposes each element removed with its rule, list, text length and links. **The share:** the main content's text before removal and after, white space aside, as the extractor finds it; flagged when more than 20 % of it went. **Provenance:** until a Collie result carries Provenance, its entries are lines of the Run trace's `trace/provenance.jsonl`: `live_hiding` (the mode, and whether it applied) for each page, `live_hiding_lifted` (the rule, its list, the operation and its target), and `content_removed` (the elements, the text removed, the share and the flag) for each `page.formats` that removed anything.
    > Note (agent decision, accepted by the owner on 2026-10-28), 2026-10-25, [#784](https://github.com/goodfetch/goodfetch/issues/784): **The matcher in the extractor's context.** `goodfetch-extractor` defines the cosmetic matcher's interface (`CleanUp`, carried by its `Context`) and applies it itself, before the main-content step, the Markdown converter, and the reading of images and media (2026-10-28, D13: they are extracted content), and to nothing else, so a later format that reads the document as it stands (`html.raw`, links, the head) reads the same serialization untouched; `goodfetch-page` implements it with the removal above. **One entry per call:** `content_removed` became `formats`, written for every `page.formats` call, whatever it removed: `clean_up_rules` (the digest of the version the Run holds to, `null` when no Filter list of the page's Session is on), `removed` (empty when nothing matched), `removed_text`, `main_content` (before and after, `null` when nothing was removed or the call asked for no format read from the main content, which then runs no main-content step: owner, 2026-10-28, O28; the formats measure the cleaned document's main content as they read it, so a removal costs one more step, on the document as served, finding 580-6), `share` and `flagged`. Once [#1895](https://github.com/goodfetch/goodfetch/issues/1895) lands, the Filter lists are what keeps a default Session's requests paused, unless the relay's credentials still need a pause ([#2337](https://github.com/goodfetch/goodfetch/issues/2337)).     > - **Live hiding stays `auto` on every document** until that reading (Q6). If the rule brings it back, the proposed cut is a value that hides on demand on Chromium too, at the first look: an action whose target an element a rule matches covers, a screenshot, a read sent to a model, a Live view, a recording.     > - **With `consent.handling: off`, no cosmetic rule acts on the Session's pages** (Q15): nothing is hidden on the live page and nothing is removed from extracted content, and the lists' network blocking stays. A consent wall then stays visible and its text stays in extracted content.
- **Never hidden.** A paywall, a consent wall (ADR 0048) and an ad-blocker wall are never hidden or removed, whatever a list says, except on a domain in `wall_domains` (ADR 0052), where this rule and the never-block entries for paywall vendors' overlay scripts do not apply; elements containing a section the page declares paid stay protected there too. Each is a condition the site set for access. An ad-blocker wall is found by rules written like the paywall detector's; no cosmetic rule hides or removes its elements, the sample comparison catches a list that blocks its script, and it is answered by the retry with blocking off (above), all outside `wall_domains`.
  - **Detecting a paywall.** Rules written like ADR 0035's block detection recognise the overlays of paywall vendors (Piano, Poool, Zephr and others), and a page that marks paid sections with schema.org's `isAccessibleForFree: false`, the markup Google asks publishers to use ([Google](https://developers.google.com/search/docs/appearance/structured-data/paywalled-content)), declares its own.
  - **What follows** (outside `wall_domains`, above). No cosmetic rule hides or removes a paywall vendor's overlay, an element containing a declared paid section, or, on the live page, an element covering one. Provenance records the paywall. The schema.org markup marks the paid content rather than the overlay, so it protects the sections it names and whatever covers them.
  - **Paywall scripts load** (outside `wall_domains`, above). The scripts that render the overlays of the paywall vendors the detector knows (Piano and tinypass, Poool, Zephr, Pelcro, Steady and others) join the never-block list, scoped to those scripts so their analytics stay blocked. Fanboy Annoyance, for example, blocks `||tinypass.com^` and `||piano.io^` on paywalled publishers, which would keep the overlay from rendering at all. The conformance suite has a paywall page per vendor.
  - **Changes ADR 0045:** these rules join its paywall detection. Only a 402 or a paywall redirect is `payment_required`; an overlay leaves the page fetched as the site served it, unless ADR 0048's wall test makes an "accept or pay" overlay `consent_required`.

**Scriptlets and resource types.**
- **Storage scriptlets** (`set-cookie`, `set-local-storage-item`, `set-session-storage-item`, their `trusted-` variants, and `cookie-remover`) are done by the engine before the page's own scripts run: cookies through the browser driver's cookie calls, storage items from an isolated world on Chromium, and on Firefox and WebKit through the route ADR 0048 names. They never touch the cookies or storage of a vendor on the never-block list, such as Akamai's `ak_bmsc`. Those of the Consent prompt lists never run (above).
- **Click scriptlets** (`trusted-click-element`) go through the guard's trusted input, and never click inside a never-block vendor's element.
- **DOM scriptlets** (`remove-class`, `remove-attr`, `set-attr` and the like) change the page's markup where its scripts can see them, so they follow `filter_lists.page_scriptlets` below.
- **Scriptlets that patch the page's JavaScript** (`abort-on-property-read`, `json-prune`, `set-constant` and the like) need the main world.
  - They are off by default.
  - No permissive implementation exists: uBlock Origin's and AdGuard's are GPL-3.0. They come from uBlock Origin's resources, downloaded with the GPL lists and never embedded or compiled into the binary.
  - `filter_lists.page_scriptlets` turns them on, with the warning of ADR 0035's `js-injection` Fingerprint method.
- **`block_resources`** blocks whole types (`image`, `media`, `font`, `stylesheet`). It is empty by default and works through the same interception. In `standard` and `stealth` it warns that the site can see the missing loads, since few people block images or fonts. Finer blocking stays a Hook (ADR 0033).
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): the key is `browser.block_resources`, a `browser.*` Session setting under ADR 0083's rules, set where a Session opens or above it, a crawl's Run included, and applied before every navigation of the Session's pages, so it covers every browser fetch of a crawl; a Label refuses it with `setting_not_applicable`, as every `browser.*` key (ADR 0093).

**What the Clean-up rules hold, and what the release ships beside them.**

The Clean-up rules are rule data: Filter lists, autoconsent's rules, the never-block entries, and the paywall detector's and ad-blocker-wall rules for overlays (ADR 0045's 402 and paywall-redirect rules stay with the release's block detection). The stand-ins, autoconsent's library and uBlock Origin's resources are code, which comes with each release and its downloaded set, never through the daily channel.

**How they arrive.**
- **Embedded.**
  - The embedded part is precompiled at build time with `Engine::serialize` from the binary's own `adblock` version. Serialized, the embedded lists measured 9.06 MB, or 3.67 MB compressed, with `adblock` 0.13.3; they are embedded zstd-compressed and decompressed on load (ADR 0057). autoconsent's rules and library add about 0.1 MB compressed (measured), and the stand-ins are small.
  - The serialized format can change between minor versions of the crate ([docs](https://docs.rs/adblock/latest/adblock/struct.Engine.html)), which is why it is built with the binary's own version.
  - It is loaded on the first page that needs it, never at engine start.
    > Note (agent decision, as built), 2026-11-16, [#2688](https://github.com/goodfetch/goodfetch/issues/2688): still never at engine start, but no longer on the first page's path when the Run's own settings turn a list on: as such a Run starts and records the version it holds to, the Clean-up versions start loading that version's lists on one of the Run's tasks, through its blocking policy, so its first page finds them loaded or loading. Loading them took about 80 ms of the 152 ms between an Attached engine's start and its first request in a warm profile of the extraction cell, half of it verifying the serialized engines. A Run whose settings turn every list off loads none; a Session of it that turns one on loads them on its first page, as before. The three lists load side by side, each on a blocking task of its own, so the Run waits for the slowest list rather than for all three in turn: the first page came 26 ms sooner at the median of 25 trials at 100 pages (0.160 s to 0.134 s, at a host load of 9 to 12). Their transient buffers peak together at 7.9 MB instead of 3.8 MB, but for the memory target of #2165 the Run's peak did not grow: on the shipped musl executable in the extraction cell, the private peak's median of six trials went from 21.9 to 22.0 MiB at 100 pages and from 24.6 to 24.4 MiB at 1,000, and the peak the comparison reports fell from 67.9 to 58.0 MiB and from 70.8 to 60.2 MiB, all of it in resident file-backed pages.
  - Its inputs, like the full set's, are pinned and fetched before CI's network deny starts (ADR 0043); no build script downloads anything.
    > Note (agent decision, as built), 2026-10-23, [#713](https://github.com/goodfetch/goodfetch/issues/713): the embedded part's inputs live as text in the Clean-up crate (`crates/goodfetch-clean-up-rules/rules/` and `stand-ins/`, each pinned in its `third-party.toml`), so the build script compiles them with the binary's own `adblock` and the crate tarball carries them; refreshing them is a change to those files. Each embedded list is its own engine (one per `filter_lists.*` switch, Brave's unbreak list in each), 7.8 MB serialized and 2.9 MB compressed without the cookie sections. The never-block list is a separate small engine checked first, so no `$important` rule or exception of any list reaches it. Until the Consent prompt runner and its wall test exist, the consent-vendor entries are dropped from the embedded lists by an exact-line list (`rules/consent-held-back.txt`) and Fanboy Annoyance is assembled without its `easylist_cookie/` includes. The stand-ins are DuckDuckGo's surrogates, which already carry the Mozilla shims' parts they use; the shims join as files of their own when a list names one. A request blocked while no call waits for it is recorded in the Run trace as `page.request_failed` with `navigation_failed` carrying `net::ERR_BLOCKED_BY_CLIENT`; a route's `fetch` of a request a redirect rule names is blocked, since a stand-in has no response to hand the route.
- **Changes ADR 0018:** the compiled form of the CC BY-SA lists is an adaptation. It carries CC BY-SA in the notice inventory, as Chromium does for the EasyList-derived rules file in its BSD tree ([README.chromium](https://chromium.googlesource.com/chromium/src/+/main/third_party/subresource-filter-ruleset/README.chromium)). The GPL lists are never compiled into the binary or published compiled; the release's downloaded set and the daily channel carry them as text, and each engine compiles them on its own machine.
- **Downloaded.**
  - The full set is pinned by digest in each release and refreshed in every patch release (ADR 0030). Each release also publishes its embedded part, as rule text, as a pinned download, so a run resumed on a machine with another release can fetch it and compile it there. Both are plain HTTPS downloads of the release's assets, as browsers are.
  - It is downloaded on first use by any run, HTTP-only runs included, into the browser cache. A run that starts before the full set is cached holds to the embedded part for its whole life; the download it starts serves later runs.
  - Downloaded sets are compiled once, in a tracked blocking task off the async runtime, and the compiled form is cached by set digest and `adblock` version. Compiled forms, and a run's own `filter_lists.extra` lists, are deleted when the run is reset or discarded, unless another run holds them, as the Response cache does (ADRs 0001 and 0046).
  - **Changes ADR 0024:** `goodfetch browsers install` also fetches the Clean-up rules, and `GOODFETCH_BROWSERS_PATH` covers them.
  - **Changes ADR 0043:** they join the downloads pinned by digest, and `offline` turns their download into `artifact_unavailable_offline` for an explicit `goodfetch rules update`. A run then uses what it has.
- **`clean_up.update`** is one of three values:
  - `release` (default): the set pinned by the release, with the embedded part as fallback;
  - `daily`: the channel below;
  - `upstream`: the Filter lists from their own URLs, at the expiry each declares. autoconsent's rules and the never-block list still come from Goodfetch, and the never-block list still wins. Setting `upstream` makes those URLs configured destinations (ADR 0043), and `offline` turns their fetching off, as it does the channel's.

  `goodfetch rules update` pulls once on demand.
- **The daily channel.**
  - **Built and gated.**
    - A nightly CI job builds it from the upstream lists, autoconsent's latest rules and the never-block list, once per supported release line (ADR 0030), each set keeping only the rules whose snippets that line's library knows.
    - It carries rule data only. autoconsent's library, its main-world snippets and the stand-ins are code, which changes only with Goodfetch releases and their gates (ADR 0030).
    - It publishes only after the never-block, breakage, paywall, ad-blocker-wall and Consent prompt suites pass, on owned fixtures and on the online Proving ground.
    - The paywall detector's and the ad-blocker-wall rules are rule data in the Clean-up rules, so each run holds to its version of them too.
    - Online, each page is judged against the same page with blocking off, so a vendor's own scoring change, which moves both, never holds the channel back; this differs from the release conformance against real vendors, which only reports (ADR 0043).
    - A failed gate publishes nothing and alerts the maintainers.
  - **Published.** It is an OCI artifact in the registry Goodfetch already publishes to, pulled by the Plugin store's code (ADR 0033).
  - **Signed.** It is signed with Sigstore to the workflow's identity and checked with `sigstore-verify` against the bundled trust root, as the Plugin index is.
  - **Kept.** The registry keeps each daily set for as long as the release line that reads it is supported (ADR 0030), so a resumed run or a local reproduction of a Cloud run can still fetch it.
  - **Versioned.** It carries a version and a 14-day expiry. When choosing the version a new run starts with, the engine refuses a set older than the last one it saw (in a Daemon group, the last one the Lead Daemon saw, ADR 0055); a resumed run still uses the version it recorded (below). When the newest set it holds is past its expiry, it falls back, with a warning, to the release set or the embedded part, whichever is newer. A version that `clean_up.version` names explicitly is exempt from both checks, with a warning when it is past its expiry, so a local run can reproduce an older Cloud run.
  - **Fetched.** Once a day per user, as a conditional manifest check (an OCI pull's anonymous token and manifest requests, with blobs fetched only when changed), with no identifier and no cookie, and never when `offline`. Operator policy can lock `clean_up.update`.
  - **Changes ADR 0043:** setting `daily` makes the channel a configured destination.
- **Changes ADRs 0043 and 0032:** the nightly job that builds the channel joins the CI jobs allowed to reach named endpoints: the upstream list URLs, autoconsent's package, the online Proving ground, and the hosts from which the challenges of the vendors protecting it, and the consent vendors it uses, load. Publishing the channel is a publishing job, outside the deny.
- **Changes ADR 0030:** every patch refreshes the Clean-up rules, pinned by `xtask release` on the release branch (ADR 0032). What they block, hide or remove is outside semver, as stealth material is, and the release notes name the version. The Clean-up rules' manifest is a contract format with its own `major.minor`. The channel publishes a set for every format major that a supported product major reads. As with the Response cache, an engine skips a set whose minor it cannot read and uses the newest one it can.

**One version per run.**
- **Choosing.** A run uses the newest valid version available: the daily channel's, then the downloaded release set, then the embedded part. `clean_up.version` pins an exact digest instead. Under `upstream`, the lists fetched from their authors are cached by the digest the engine computes, and that digest is what the run holds to.
- **Changes ADR 0002:** a run records that version's digest in its state at start and holds to it until it ends. A resumed run uses the same digest. A release set or embedded part missing on that machine is fetched as a pinned download. A daily set is fetched only where the channel is configured, or where `clean_up.version` names it, which configures it for that fetch. When neither applies, or the fetch fails, the run uses the newest version available and Provenance records the change.
- **Named in the results.** Provenance names the version and its date, and the Goodfetch release whose code applied it, since the daily channel carries no code. The run report warns when the version is older than 14 days.
- **Changes ADR 0036:** change tracking says when a run and its Baseline used different Clean-up rules, so a difference the rules caused is not reported as a change on the site. A Watch that hashes extracted content holds to the version its comparison point recorded, as a resumed run does; when it cannot get that version, it starts the target and says why. Watches on `ETag`, `Last-Modified` or the raw page do not depend on the rules.
- **Changes ADR 0001:** Goodfetch Cloud, which runs one engine per run, chooses the version and hands its digest to the engine through the protocol, as it hands over saved identities (ADR 0035); the daily check and the anti-rollback state are the cloud's. A local run reproduces it by setting `clean_up.version` to that digest.

The channel tags each version `<line>-format-<format line>` (each `0.y` counting as a major) and `sha256-<hex>`, so a resume or `clean_up.version` pulls the one it names (#208 publishes them so). Two settings name the sources, so a mirror can stand in for them and the executable's tests reach local stand-ins: `clean_up.channel`, the channel's OCI repository `host[:port]/path` (default `ghcr.io/goodfetch/clean-up-rules`), and `clean_up.lists`, the URL of each Filter list `upstream` fetches (default their authors'). Compiled forms are kept in memory only, shared by the Runs that hold the version, so `runs::discard` has no compiled file to delete. Until #207 pins a full release set, `release` holds to the embedded part. The channel's Sigstore check waits for the Plugin store's verifier (ADR 0033).

A fallback in Provenance is `{reason, message}`, `reason` one of `not_a_digest`, `not_here`, `offline`, `timed_out`, `unreachable`, `refused`, `tampered`, `other_digest`, `unreadable`, `past_a_limit`, `not_kept` or `not_loaded`. A Run holds its version's files in the Browser cache while it lives; when they no longer read at its first page, its pages match the embedded part, and Provenance (`recorded`, `fallback`) and the Run report's `clean_up_rules_fallback` warning say so. `clean_up.channel` and `clean_up.lists` take only Operator policy and user and project configuration, as `filter_lists.extra`'s fetching sources would, so a Recipe or a run cannot point the engine's fetches elsewhere. The sources' state is written through a partial file, synced, then renamed.

Provenance's `formats` entry then names the version and what the rules removed, as on the browser tier. A served page has no live hiding and no Consent prompt runner, so only the Filter lists' rules apply there.

**Where it runs.**
- **Browser host** (ADR 0022). Matching, live hiding and ADR 0048's runner run in the Browser host beside the browser, with the digest of the version the run holds to. Goodfetch Cloud hands Browser hosts the compiled form with the digest, so a Session does not recompile the GPL lists. A run's own lists (`filter_lists.extra`, `upstream`) travel to the Browser host as text with the run, and are compiled there.
- **Raw CDP** (ADR 0017). A raw CDP client that switches the interception off also switches blocking off for that Session, and Provenance says so; live hiding and extraction-side removal continue.
- **Third-party CDP browsers** (ADR 0022) are treated as Chromium when the engine controls their interception, and get extraction-side removal only otherwise.
- **Lightpanda** (ADR 0020) gets extraction-side removal, and blocking where its CDP supports request interception. Provenance records which applied.
- **An installed Brave or Edge** (ADR 0030) blocks and hides by itself, outside the never-block list and before the runner. The engine turns that off where the browser allows it. Where it cannot, Provenance records it, and its pages record "no wall test" and keep their prompts in extracted content, as when no browser can start (ADR 0048).

**Proof.**
- **The conformance suite** runs on the Proving ground (ADR 0025), on Chromium, Firefox and WebKit, with cross-origin iframes and shadow DOM. It covers:
  - ad and tracker pages with a known blocked set;
  - challenge and anti-bot pages that must keep working;
  - pages relying on redirect stand-ins;
  - pages whose hidden text must not reach extracted output.
- **Changes ADR 0025:** the matched Goodfetch rows set blocking as each competitor's default does. The benchmark publishes what the clean-up costs and saves in time and bytes, as it does for ADR 0023's controls.
