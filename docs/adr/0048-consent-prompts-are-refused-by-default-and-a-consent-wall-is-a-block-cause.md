# Consent prompts are refused by default, and a consent wall is the Block cause `consent_required`

Every live browser Session answers each Consent prompt by refusing. A prompt that offers no refusal but leaves the content readable is hidden instead. The engine never accepts unless a person approved the domain. A prompt that offers no refusal and covers the content, or asks for payment instead, is a **consent wall**: it gets the Block cause `consent_required` and is never evaded, except on a domain a person put in `wall_domains`, where it is read past without consenting (ADR 0052).

DuckDuckGo's autoconsent recognises the prompts, driven through Goodfetch's own driver in an isolated world, with trusted input, in every frame. Its rules that read or call a consent vendor's own JavaScript run fixed snippets in the page's main world, the engine's only action there by default; every other snippet runs in the isolated world. A prompt no rule recognises goes to the Decision provider when the run has one.

A consent answer is Session state, not an Effect. Decided in [Built-in page clean-up](https://github.com/goodfetch/goodfetch/issues/119) (parity row SA-28). Ads, trackers and the Clean-up rules that carry autoconsent's rules are ADR 0047's.

**Why handle prompts at all.** A prompt left alone is sometimes the only text returned ([firecrawl#78](https://github.com/firecrawl/firecrawl/issues/78), [jina-ai/reader#56](https://github.com/jina-ai/reader/issues/56)). It covers screenshots ([firecrawl#647](https://github.com/firecrawl/firecrawl/issues/647)) and click targets, which the guard of ADR 0019 refuses to click through.

**What the alternatives do to the page.**
- **Hiding without answering** stores nothing, so the prompt returns in every new Session. EasyList documents broken scrolling and dead clicks ([COOKIE_CONSENTS.md](https://github.com/easylist/easylist/blob/master/COOKIE_CONSENTS.md)).
- **Accepting** loads the trackers, and the sites that insist most on it, those with "accept or pay" walls, set 6.4 times more third-party cookies than sites with ordinary banners ([Rasaii et al., IMC 2023](https://arxiv.org/abs/2310.01108)). It is also not consent in GDPR's sense, which is the data subject's own indication of their wishes ([Art. 4(11)](https://gdpr-info.eu/art-4-gdpr/)).
- **Refusing** has a basis: Art. 21(5) lets a person object "by automated means using technical specifications" ([Art. 21](https://gdpr-info.eu/art-21-gdpr/)).
- **Agents left to themselves accept.** Four of eight browser agents chose "accept all" even when an equal "deny" button was there ([Ukani et al.](https://arxiv.org/html/2512.07725v1)).

**Competitors.**
- **On by default:**
  - Apify's Website Content Crawler (`removeCookieWarnings`) and Browser Use, both through "I don't care about cookies" variants, which accept where they have to.
  - Firecrawl (`blockAds`), whose mechanism is closed.
- **Opt-in:**
  - Crawl4AI's `remove_consent_popups`, which clicks "Accept All" first ([async_crawler_strategy.py](https://github.com/unclecode/crawl4ai/blob/main/crawl4ai/async_crawler_strategy.py)).
  - Crawlee 3's `closeCookieModals`. Crawlee 4 removed it ([crawlee#4073](https://github.com/apify/crawlee/pull/4073)), its issue calling the library it wrapped "largely unmaintained" with "licensing problems" ([crawlee#3987](https://github.com/apify/crawlee/issues/3987)), and its guide now points to autoconsent ([guide](https://github.com/apify/crawlee/blob/master/docs/guides/cookie-modals.mdx)).
- **Refuse:** DuckDuckGo's browsers, which then hide ([help](https://duckduckgo.com/duckduckgo-help-pages/company/how-does-duckduckgo-protect-privacy)), and Ghostery's Never-Consent ([autoconsent.js](https://github.com/ghostery/ghostery-extension/blob/main/src/background/never-consent/autoconsent.js)).
- **Nothing:** Stagehand, Browserbase, ScrapingBee and Spider.

## Considered Options

- **Hiding by default** (Brave, [blog](https://brave.com/privacy-updates/21-blocking-cookie-notices/)): rejected as the default, for the reasons above. It stays the fallback for prompts that offer no refusal and leave the content readable.
- **Accepting, or accepting when needed** ("I don't care about cookies" in Apify and Browser Use, Crawl4AI): rejected. No person consents, and agents that do this are the documented privacy failure.
- **Leaving prompts alone** (Stagehand, Browserbase, ScrapingBee, Spider): rejected. It leaves the prompt in the output and in front of the guard.
- **autoconsent's standalone bundle**, as Crawlee 4's guide injects it: rejected.
  - It runs in the main world and writes page globals ([standalone/content.ts](https://github.com/duckduckgo/autoconsent/blob/main/standalone/content.ts)).
  - It uses the `tier2` heuristic, which clicks the only "accept" when there is no refusal.
  - It clicks with `element.click()`, whose events are `isTrusted: false` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted)).
- **"I don't care about cookies" or "I still don't care about cookies"**: rejected. They are GPL-3.0 and accept where they have to.
- **Consent-O-Matic** (MIT, [repository](https://github.com/cavi-au/Consent-O-Matic)) as a second rule source: rejected as over-engineering. A second rule format needs a second runner, for rules that largely overlap autoconsent's larger and more active set, and the Decision provider covers what neither knows. A coverage gap measured by the conformance suite reopens this.
- **The rules of Firefox's Cookie Banner Reduction**: unavailable. The feature shipped only in private windows in Germany ([Firefox 120](https://www.firefox.com/en-US/firefox/120.0/releasenotes/)) and was later turned off everywhere ([bug 1940275](https://bugzilla.mozilla.org/show_bug.cgi?id=1940275)), and its list is archived ([repository](https://github.com/mozilla/cookie-banner-rules-list)).
- **Hiding a consent wall to read what is behind it**: rejected. It gets around the condition the site set for access, and for an "accept or pay" wall the site set consent, or payment, as the price of the content; reading it without either takes the content on terms the site refused.
- **Treating a consent answer as an Effect**: rejected. Repeating the same answer changes nothing. Journaling it would put a Target fingerprint check (ADR 0009) and possible Reconciliation (ADR 0029) on every page for no protection.

## Consequences

**Handling a prompt.**
- **`consent_handling`** is on by default, in every live browser Session and every Access mode, and can be switched off per run. Switching it off stops only the answering: the wall test still runs, a wall is still `consent_required`, the Filter-list rules aimed at Consent prompts still wait (ADR 0047), and Provenance lists the prompts left.

The owner reopened it knowingly (Q8, then Q16), on a fact that question did not show: it presented the bundle's cost as treated once per page created, which holds for its registration only (`crates/goodfetch-page/src/consent.rs:239-249#prepare`), while the bundle is evaluated in every frame of every document with three commands per document (`crates/goodfetch-page/src/consent.rs:365-412#begin`, read at `d06b3d9b8`).
  > - **`consent.handling` takes three values where it took two** (Q11). `answer`, the default, is what on was. `detect` is what off was, unchanged: the runner looks and reports, the wall test runs, the runner clicks and hides nothing. `off` is new: nothing of the runner is registered or started on the Session's pages. [#2434](https://github.com/goodfetch/goodfetch/issues/2434) builds it.
  > - **What `off` gives up, as put to the owner** (Q8, Q15): the engine no longer knows that a page is a consent wall. It reports none, and it returns the page's text as served, what lies behind a wall it did not see included, as a driver with no wall test does. The Run report lists `off` as weakened.
  > - **What `off` keeps** (Q15): no cosmetic rule acts on the Session's pages, on the live page or in extracted content, so no rule hides or removes a wall nobody judged (ADR 0047's note of the same day). Nothing is clicked and nothing is accepted.
  > - **A two-stage injection,** a small detector in every frame and the bundle only where a vendor's marker shows, was put to the owner and not taken now (Q7): as the runner is written it would miss the prompts with no marker, which the heuristic pass finds, and those that appear late. The cuts that change no behaviour come first, and the two-stage design comes back only if the reading is above 10 % after them (Q7).
  >
  > Note (the grilling session's own consequence, 2026-11-10, same grilling, not put as a question; shown to the owner at the second confirmation as a choice the owner may undo, and awaiting the owner's reading): the cuts that change no behaviour have no ticket; the bundle, for one, is not minified (its library and heuristics are each "evaluated as its authors published it", `crates/goodfetch-clean-up-rules/build/consent.rs:1-8`, `:46-118#bundle`, read at `d06b3d9b8`). By the owner's rule of 2026-11-07 they become a ticket when the reading that decides brings the runner back; that ticket reads the page-load cell before and after.
- **The order:**
  1. autoconsent's vendor rules;
  2. its `reject` heuristics, which detect prompts in a dozen languages and recognise refusal buttons in more. autoconsent runs its heuristic only in the top frame and keeps only prompts that have a refusal button, so the engine calls its detection in every frame itself, and a prompt detected without a refusal button goes to step 3 ([heuristic-patterns.ts](https://github.com/duckduckgo/autoconsent/blob/main/lib/heuristic-patterns.ts));
  3. the Decision provider (below);
  4. then either hiding (a prompt with no refusal that leaves the content readable) or `consent_required` (a wall).
- **Hiding** means ADR 0047's: always removed from extracted content, hidden on the live page through the invisible style sheet on Chromium, and on Firefox and WebKit only when the prompt covers an action's target.
- **The Filter lists wait.** The rules of the Filter lists aimed at Consent prompts never block, hide or run scriptlets on the live page, and the consent vendors' prompt scripts are never blocked, so the runner always sees the prompt, and the wall test always sees the wall (ADR 0047).
- **Never delaying a page with no prompt.** The engine waits on a page only once a vendor is detected or a pre-hide rule matches. A prompt that appears later is answered when it appears, and ADR 0047 already keeps its text out of extracted content.
- **In the HTTP tier,** which has no layout, the wall test runs on the route's browser sample (ADR 0020).
  - **Changes ADR 0020:** a route whose browser sample showed a consent wall never moves to a tier that skips it. Its pages are `consent_required` in every tier, unless the domain is in `consent_domains`, or in `wall_domains`, where they are read as served unless the sample showed the content withheld (ADR 0052).
  - On a route whose sample showed a refusable prompt or a notice, ADR 0047 removes the prompt from extracted content.
  - A route whose tier the run forced (ADR 0023), or whose comparison was switched off, still takes one browser sample for the wall test, loaded once with blocking off as well so that ADR 0047's paywall and ad-blocker-wall rules see a wall a list would block, when a browser can start, downloading it on first use (ADR 0024) unless `offline`. This sample cannot be switched off, since a wall is never evaded outside `wall_domains` (ADR 0052), and even there the sample decides whether the content is withheld. When no browser can start, its pages record "no wall test" in Provenance, and their prompts are left in extracted content rather than removed.
  - A server-side consent page, such as Google's `consent.google.com` or Yahoo's `guce`:
    - **with a refusal path,** is answered once through the Session's browser. Browser-fetch keeps the Session's identity (ADR 0020), and later HTTP fetches carry its cookies.
    - **without one,** or when no browser can be started for the Session, is `consent_required`.

**The runner.**
- **Where it comes from.** autoconsent (MPL-2.0, [repository](https://github.com/duckduckgo/autoconsent)): its rules ship in the Clean-up rules, and its library with each release (ADR 0047). Neither is fetched from npm at run time.
- **Where it runs.**
  - On Chromium, in an isolated world in every frame, cross-origin iframes included, through ADR 0019's out-of-process iframe tracking.
  - On Firefox and WebKit, in Playwright's utility world. Playwright's only public route into it is a selector engine registered with `contentScript: true`. The Site access spec proves that route for the runner, the guard and storage writes, including how they report without a main-world binding or polling. Where it cannot, they run in the main world, as the lab's guard did, and Provenance marks it.
  - It is set up again on every new document and every route change of a single-page app.
  - It runs wherever the Session's browser is: in the Browser host for a remote browser (ADR 0022), and on a third-party CDP browser whose isolated worlds and input the engine controls. Lightpanda has no layout for the wall test, but ADR 0020 picks it only when its sample matches the browser's, so a walled route never uses it; on its pages prompts are only removed from extracted content.
- **How it reports to the engine.** Through `Runtime.addBinding`, named with the isolated world's own unique name (`executionContextName`; the `executionContextId` form is deprecated) and added again on every new isolated world, since with `Runtime` off V8 does not carry named bindings to new contexts. Its `bindingCalled` events are sent without `Runtime` being enabled ([v8-runtime-agent-impl.cc](https://chromium.googlesource.com/v8/v8/+/main/src/inspector/v8-runtime-agent-impl.cc)), so nothing polls and nothing appears in the page's own world.
- **How it clicks.**
  - Clicks and keys go through the guard's trusted input on all three browsers, never as untrusted `element.click()` events.
  - autoconsent takes its DOM actions from its public `domActions` field ([web.ts](https://github.com/duckduckgo/autoconsent/blob/main/lib/web.ts)), typed as its `DomActions` class. Goodfetch supplies a subclass that sends clicks to the guard, in its own code under the framework's licence, and autoconsent's files stay unmodified (ADR 0018).
  - Five coded vendors (Admiral, Conversant, Sourcepoint's frame, TikTok and UniConsent) call `element.click()` directly. An isolated world has its own JavaScript prototypes, as Chrome documents for content scripts ([isolated worlds](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#isolated_world)), so the runner replaces `HTMLElement.prototype.click` there, invisibly to the page, and those calls reach the guard too. The conformance suite checks the override on each browser; a vendor is switched off through `disabledCmps` only on a browser where the check fails.
  - Seven snippets click, all through the DOM alone, so they run in the isolated world. Six use `.click()`, which the override sends to the guard. `EVAL_COOKIE_POPUP_CLOSE` dispatches a synthetic click event instead, so the rule that names it (`cookie-popup-close-cookies`) is dropped. A rule is dropped by the snippets it names, not by its own name, both when the channel is built and in the runner, so a newer rule that clicks through a synthetic event, or clicks from the main world, is dropped too. Goodfetch contributes upstream a version that clicks through `domActions`.
  - **Targets the guard refuses.** Many rules click checkbox inputs that styled toggles hide or cover, which the guard refuses (ADR 0019). The runner then clicks the input's label. Failing that, the prompt falls through to the heuristics and the Decision provider, and Provenance records it. The conformance suite measures each vendor's success through the guard.
  - **Pre-hiding and trusted clicks.** autoconsent's pre-hide makes a prompt transparent and lets clicks pass through it, which a trusted click cannot target. The runner lifts the pre-hide from a prompt before its first click on it. The guard's lift-and-retry (ADR 0047) lifts only the rule that hid the target, never pre-hiding for the whole Session.
  - **autoconsent's other page writes.** Its `hide`, `prehide` and `stylesheet` steps would write `<style>` elements into the page. The subclass sends them to ADR 0047's live hiding instead: the invisible sheet on Chromium, and on Firefox and WebKit hiding on demand plus removal from extracted content. Its `setStyle`, `addStyle` and `removeClass` steps (a few rules, mostly lifting a scroll lock the vendor left after a refusal) run from the isolated world, since they only finish a refusal, and Provenance marks them. A `setStyle` that hides the prompt itself, as the `transcend` rule's whole opt-out does, goes to live hiding instead. Evidon's and TrustArc's coded rules build a `<style id="autoconsent-css-rules">` themselves, without `domActions`: they append it empty, then write their rules into it. The runner's isolated world holds the element back from the page, as it overrides `click`, and forwards the text written into it, through a setter override there, to live hiding. The conformance suite checks that no `autoconsent-*` element is ever left in the page.
- **Heuristics.** `reject` only, never `tier1` or `tier2`. A notice with no choice is hidden, never acknowledged.
- **Pre-hiding** (hiding a known prompt before it flashes) uses ADR 0047's live style sheet on Chromium, and is undone before the wall test, so a wall is always judged as the site shows it. ADR 0047's other live hiding starts on a document after the runner's first detection pass and the wall test, so no other cosmetic rule, built-in or added through `filter_lists.extra`, can hide a wall first, and ads are not left visible while autoconsent keeps looking.
- **Detection never stops for good.** autoconsent stops looking after about 20 attempts or a quiet DOM. The runner restarts its detection whenever a DOM mutation matches a rule's detection or pre-hide selectors, or a Consent prompt rule; those mutations are events reported through the binding, so nothing polls. A prompt that appears late on the same document is still answered.
- **The main world.**
  - **Which snippets.** autoconsent's `eval` steps name fixed snippets in its `eval-snippets.ts`. Snippets that read or change only the DOM, cookies, `localStorage` or history, which the isolated world reaches, run there, and most rules use only those: `DOM.resolveNode` accepts the isolated world's context. Goodfetch keeps an MIT table that classes each snippet, checked by the conformance suite. Only the snippets that read or call a page global, such as `__tcfapi` or a vendor's own object, run in the main world. With the five coded vendors that read or call their vendor's API (OneTrust, Cookiebot, consentmanager, Klaro and TrustArc), about 20 rules need it.
  - **How on Chromium.** `DOM.resolveNode`, given no context, resolves in the frame's main world ([resolve_node.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/inspector/resolve_node.cc)), and `Runtime.callFunctionOn` then runs the snippet there. V8 refuses only `compileScript`, `runScript` and two settings calls while `Runtime` is off, never `callFunctionOn`, so `Runtime` stays off, and the snippets leave no global behind.
  - **How on Firefox and WebKit.** Through Playwright's main-world evaluation.
  - **When a main-world call can't be made,** the prompt falls through to the heuristics and the Decision provider, and only then to the wall test.
  - **Changes ADR 0019:** by default, these calls and the TCF read below are the engine's only actions in a page's main world. The opt-in exceptions are ADR 0047's page scriptlets, ADR 0035's `js-injection` Fingerprint method, and the user's own `evaluate` and init scripts, each marked in Provenance. ADR 0047's on-demand hiding on Firefox and WebKit adds a visible `<style>` element, which stays in the page, and on those browsers the runner, the guard and that `<style>` act from the main world wherever the utility-world route of this ADR is not proved; Provenance marks each. **Changes ADR 0031:** its rejection of an in-page recorder stands. This exception covers calls into the consent vendor's own API, not code that stays in the page.

**Prompts no rule recognises.**
- **Which prompts.** Prompts the heuristics detect but no rule can answer.
- **Who is asked.** When the run has a Decision provider, it is asked about them, as about the soft blocks of ADR 0021. Without one, the wall test below decides: a prompt that leaves the content readable is hidden, and any other is a wall.
- **What it may choose.**
  - The engine offers only the prompt's buttons, leaving out any that match autoconsent's accept patterns.
  - The model picks the refusal, "close without answering", or abstains.
  - The prompt's text is wrapped as untrusted page content (ADR 0014).
- **Checking the outcome.**
  - Where the page exposes a TCF consent string, the engine reads it through `__tcfapi` after the click.
  - A consent given by mistake is reported, and the Session's consent cookies are cleared.
  - Elsewhere, Provenance marks the answer `unverified`, since a model alone never judges an outcome (ADR 0013).
- **Accounting.** The call is journaled and counted against Limits (ADR 0012). **Changes ADR 0010:** the click the model chose is a consent answer, not an Effect, so it is recorded in Provenance and the Run trace rather than the Effect journal; the model call stays journaled.

**Consent walls.**
- **The test.** A prompt is a wall when it offers no refusal and either covers the main content or offers payment or a subscription instead.
- **Paywalls too.** An "accept or pay" overlay from a vendor ADR 0047's paywall detector knows is judged as a Consent prompt: the wall test decides, and a wall is `consent_required`.
- **Walls no rule detects.** On a page where the runner found no prompt, an element that the Consent prompt rules of the Filter lists match, and that the runner's detection also takes for a Consent prompt, goes to the wall test, and to the Decision provider, before ADR 0047 removes it from extracted content. An element those rules match that is not a Consent prompt, such as an age gate in their sections, is left in extracted content rather than removed. In the HTTP tier, which has no runner, such an element is kept in extracted content, and Provenance records "no wall test", unless the route's browser sample judged it.
- **Late prompts.** A prompt that appears after live hiding started on its document, on a route change for example, has any live-hiding rule that hides it lifted before detection and the wall test, as ADR 0047 does before a Target fingerprint check.
- **Who decides.** Rules decide. The Decision provider is asked only when they cannot. When it abstains, the prompt is treated as a wall: a notice wrongly blocked costs a page, while a wall wrongly hidden gets around an access condition.
- **Changes ADR 0035:** `consent_required` joins the Block causes. The quoted price of an "accept or pay" wall, when the page gives one, is recorded in Provenance.
- **Changes ADR 0021:** it never moves a domain up a proxy tier, never retires a Session to rotate, and is never retried. On a domain in `consent_domains`, the engine accepts a wall instead of blocking; on one also in `wall_domains`, it reads past first and accepts only when the content is withheld (ADR 0052).
- **Changes ADR 0005:** a finished run that left pages in scope at `consent_required` reports Completeness `unverified` and lists them, as for `payment_required`.
- **Changes ADR 0046:** these responses are never stored in the Response cache, like every Block cause.
- **Changes ADR 0016:** never evading a wall is not one of its switchable compliance controls. It is a condition the site set for access, like ADR 0045's payment gate, and it never stops stealth or the Challenge solver.
- **`consent_domains`** lists the registrable domains (ADR 0004) on which the engine accepts a wall. `*` is accepted only when written explicitly (ADR 0052). A prompt that offers a refusal is still refused there. On such a domain, a wall no rule recognises goes to the Decision provider with its accept buttons offered; without a Decision provider, it stays `consent_required`.
  - **Who widens it.** Only Operator policy, user and project configuration, or a person's answer in the Console or an interactive CLI prompt. On a Daemon with accounts, only the operator role, in Operator policy, as for `pay_domains` (ADR 0045).
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
  - **Changes ADR 0028:** the Recipe and run layers can only narrow it.
  - **Changes ADR 0011:** no agent surface widens it.
  - **Changes ADR 0031:** widening it goes through step-up.
- **`on_consent_wall`.**
  - `report` (default) leaves the page at `consent_required`.
  - `ask` raises a Human pause with a Notification. The person answers for this run, or "always for this domain", which writes `consent_domains` in user configuration. On a Daemon with accounts, only a person with the operator role can give either answer, and "always" is stored in Operator policy, as ADR 0045 does for `pay_domains`.
  - The Console's "Needs you" view lists the domains that showed a wall and offers to add them to `consent_domains`.
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.

**A consent answer is Session state.**
- **Where it lives.** With the Session's cookies and storage, so a saved identity carries it (ADR 0035). A new or resumed Session simply answers again.
- **Acceptances stay in their scope.** The engine records which cookies and storage each answer set. Saving an identity drops those of acceptances that the saving run's `consent_domains` does not cover, such as a person's own click or an "accept for this run" answer, so a later run never inherits them. **Changes ADR 0046:** it also drops the Response cache entries fetched under those acceptances from the saved identity's partition. The same holds for consent cookies written by scriptlets of a list from `filter_lists.extra` (ADR 0047), which saving drops unless the saving run's `consent_domains` covers them. Answers imported from the person's own browser are that person's acceptance and are kept, marked as imported; answers a run gives on a Profile directory used in place or on a Borrowed browser stay there, as the person's own use, marked in Provenance (ADR 0056).

**Global Privacy Control.**
- **The setting.** `gpc` is `auto` by default, which follows the Identity profile. The `Sec-GPC` header and `navigator.globalPrivacyControl` are sent only when the browser the Session presents would send them.
- **Which browsers send it.**
  - Brave and DuckDuckGo send them by default ([GPC](https://globalprivacycontrol.org/)).
  - Firefox sends them in private windows ([Firefox 120](https://www.firefox.com/en-US/firefox/120.0/releasenotes/)).
  - Chrome, Edge and Safari never send them ([browser-compat-data](https://github.com/mdn/browser-compat-data/blob/main/http/headers/Sec-GPC.json)).

  So `auto` never sends them for a stock Chrome identity.
- **Forcing it.** `gpc = on` sends them anyway, with a warning that a signal the presented browser never sends breaks the consistency `standard` keeps (ADR 0021).
  - **Firefox and Camoufox** use their own preference.
  - **Chromium** uses CDP's `Browser.setGlobalPrivacyControl`, which sets the header and `navigator.globalPrivacyControl` together ([browser_handler.cc](https://chromium.googlesource.com/chromium/src/+/main/content/browser/devtools/protocol/browser_handler.cc)). The command needs Chromium's `GlobalPrivacyControlTest` base feature, which by itself exposes `navigator.globalPrivacyControl`, absent from stock Chrome; so Goodfetch launches a browser with it only for a `gpc = on` Session, and the conformance suite checks that the property is absent everywhere else. It is browser-wide, so it applies only to a Session with a browser of its own. Elsewhere, and in a browser Goodfetch did not launch, the header goes through the interception, and the warning also says that the JavaScript property is absent.
  - **The HTTP tier** sends `Sec-GPC` exactly when the Session's browser would, since it presents the same identity.

**Proof.**
- **The conformance suite** runs on the Proving ground (ADR 0025) on all three browsers. Its prompts are modelled on OneTrust, Cookiebot, Didomi, Usercentrics, Sourcepoint, Quantcast, TrustArc, Google's consent page and Axeptio in shadow DOM. It covers:
  - "accept or pay" walls;
  - notices, which must be hidden, against walls, which must be blocked;
  - prompts that appear late or on a route change;
  - prompts in cross-origin iframes;
  - prompts in more than ten languages;
  - server-side consent pages in the HTTP tier;
  - the Live view and recorder scenarios above.
- **Real vendors.** **Changes ADR 0025:** the online Proving ground also carries real consent vendors' prompts, through their free tiers where their terms allow. The owner approves any paid one.
