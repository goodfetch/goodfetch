# A Wall allowance lets a person approve reading past Walls, by generic means only

A **Wall** is an overlay a site draws over its page as the condition for reading the content: a paywall, a consent wall or an ad-blocker wall. ADRs 0045, 0047 and 0048 never get past one. V1 adds an opt-in, the **Wall allowance**: `wall_domains`, a list of registrable domains that only a person approves, as with `pay_domains` and `consent_domains`. On those domains, the engine reads past Walls instead of stopping at them, using only generic means:
- it reads the text the server sent and hides what covers it;
- it lets the Filter lists block a Wall's script;
- on domains a person also lists in `wall_refetch_domains`, when a paywall leaves the served page without its main content, it clears that site's stored data in the same Session and fetches the page once more.

Consent walls are read past without consenting; accepting still needs `consent_domains`. A demand for payment (`payment_required`) is not a Wall and stays as ADR 0045 has it.

Goodfetch's own code never names a paywall vendor, a search crawler or an archive as a way past a Wall. Posing as Googlebot, spoofing a referrer and fetching archived copies stay reachable only through the user's own Hooks, Plugins and Filter lists. The official Plugin index does not list Plugins presented that way. Decided in [Opt-in paywall and consent-wall circumvention](https://github.com/goodfetch/goodfetch/issues/155), on the evidence of [Legal exposure of paywall and consent-wall circumvention](https://github.com/goodfetch/goodfetch/issues/154) ([findings](https://github.com/goodfetch/goodfetch/blob/research/paywall-consent-circumvention/rnd/research/2026-10-12-paywall-consent-circumvention-legal.md)). The refetch, its own approval, its stop and denied domains were settled in [Safeguards for the Wall allowance's fresh-Session reset](https://github.com/goodfetch/goodfetch/issues/193), on the evidence of [Legal exposure of systematic cookie resets at scale](https://github.com/goodfetch/goodfetch/issues/192) ([findings](https://github.com/goodfetch/goodfetch/blob/research/cookie-reset-legal/rnd/research/2026-10-12-cookie-reset-at-scale-legal.md)).

**Why generic, and why public.** The legal research found that risk follows naming, not capability. Every takedown it found hit a tool presented as a way past paywalls:
- one §1201 notice disabled 3,879 GitHub repositories of Bypass Paywalls Clean ([notice](https://github.com/github/dmca/blob/master/2024/08/2024-08-09-news-media-alliance.md));
- 12ft.io's host locked it;
- smry.ai, which used to pose as Googlebot and fetch archives, retreated and now tells users not to use it on hard paywalls.

Reading what was served and letting the Filter lists block a Wall's script rate Low at every level in the public framework and in a user's own Plugin (US, EU and France). Clearing a site's stored data rates Low only as a generic control, such as a Hook a user writes. The refetch does not rate Low: it fires only when a paywall withholds the content, so by function it gets past a metered paywall, whatever the docs call it. The follow-up research rates it Medium for the public framework in all three for that reason: a component made to act on that trigger meets the design test of the anti-circumvention rules. Done systematically by an automated client, it rates Medium for the user and High in Goodfetch Cloud, under *Reddit v. SerpApi*'s reasoning on bulk access and *CoxCom*'s on usage counters. Its safeguards keep it a plain clearing of a site's data: the same IP address and Identity profile, its own approval and lock, and a stop when the site refuses. They do not bring it back to Low; only leaving it to each user's own Hook would. No rating for the public framework or a user reaches High, so it stays. Named means (a vendor list for blocking Wall scripts, a Googlebot or meter-reset preset, an archive fallback) rate Medium to High. A Private component lowers visibility, not exposure: it still provides the tool, and in the EU and France it loses the "other commercial uses" argument (*Nintendo v. PC Box*).

**Competitors.**
- No mainstream scraping framework ships a named feature for blocking Wall scripts, disguising identity or fetching archives.
- Firecrawl treats "paywalls block the actual content" as a successful scrape and does not escalate ([engpicker.ts](https://github.com/firecrawl/firecrawl/blob/main/apps/api/src/lib/engpicker.ts)).
- One third-party Apify actor offers `useGoogleBotHeaders` ([actor](https://apify.com/lukaskrivka/article-extractor-smart)).
- uBlock Origin's uAssets ([readme](https://github.com/uBlockOrigin/uAssets)) and AdGuard ([filter policy](https://adguard.com/kb/general/ad-filtering/filter-policy/)) refuse rules that get past paywalls.
- Accepting consent automatically is common (Apify, Browser Use, Crawl4AI; ADR 0048).

No parity row and none of the 24 ranked pains asks for getting past a paywall (ADR 0037).

## Considered Options

- **Named presets as a Private component** (ADR 0018's usual route for exposed capabilities): rejected. The research rates a Private component no lower than the public framework for blocking Wall scripts (Medium to High), identity disguise (High) and archives (Medium), and it is a second codebase to sign and test. ADR 0018's rule decides where a capability lives once it is built; here the named presets are not built at all, because the generic means already reach every level.
- **Named presets in the public framework**: rejected. This is Bypass Paywalls Clean's profile, and a single notice to GitHub could disable the repository and every fork of it.
- **A per-run switch, like ADR 0016's compliance controls**: rejected. An agent could switch it on for itself, and a published Recipe could ship with it on. A Wall is a condition the site set for access, which is the reason ADRs 0045 and 0048 made their approvals person-only.
- **Letting the allowance cover `payment_required` too**, so the engine escalates, rotates or refetches past a 402 or a paywall redirect: rejected. That is the masking the *Reddit* case rests on ([Legal exposure of stealth and challenge-solving tooling](https://github.com/goodfetch/goodfetch/issues/65)), and a site that asks to be paid already has an answer, the Paid fetch (ADR 0045).
- **The allowance implying acceptance of consent walls**: rejected. Reading past a consent wall gives no consent and loads no trackers. Accepting gives consent in the user's name, which ADR 0048 keeps as a separate approval (`consent_domains`).
- **Unlimited refetches, in any Session**: rejected. Clearing a site's data in a Session logged in to it logs the account out and runs against its terms. Clearing it in an `identified` Session contradicts the identity it signs (ADR 0045). Unlimited refetches can loop.
- **The refetch as part of `wall_domains`**, as first decided: rejected. A person who allows a domain to read past its consent wall would get refetches there without asking for them, and Operator policy could not allow the rest of the allowance while locking off its most exposed means.
- **A new Session for the refetch, keeping the retired one's Access mode, Identity profile and proxy exit**, the research's wording: rejected. Retiring the Session wipes every other site's data in it and goes through the Session pool, the path that rotates proxies. A new Session keeps the exit only where the provider holds a sticky session, as with saved identities (ADR 0035). Clearing one site's data in the same Session keeps the proxy and the Identity profile, which a Session holds for its life (ADR 0021); a pool that rotates per connection is excluded below.
- **Keeping some of the site's data, such as challenge-clearance cookies**, so that the refetch meets fewer Challenges: rejected. Choosing which cookies survive aims the code at the metered paywall's own state and would name challenge vendors. The refetch clears everything the site stored, as a browser's "Clear site data" does, and stops when a Challenge follows.
- **Never completing a Challenge in a Session that cleared the site's data**: rejected. The domain would need a new Session through ADR 0021, which can rotate the proxy the refetch keeps, and the crawl would stall on every site behind a Challenge. Stopping the refetch at the first such Challenge bounds the pairing instead.
- **Leaving the refetch to the user's own Hook**: rejected. It is the only option that brings the public framework back to Low, but every user who wants it would write the same Hook, and no rating for the public framework or a user reaches High.
- **Remembering a stopped refetch across runs**: rejected. A block can be passing, and the lasting answer to a site that objects is a denial in `wall_denied_domains`, which the operator role records with its reason.
- **Naming it `bypass_domains` or `circumvention_domains`**: rejected. The first is the "named" profile the research rates higher; the second is the legal term of art and reads as an admission. The docs describe what the allowance does in plain words.
- **Listing third-party Plugins presented as a way past Walls in the Plugin index when they pass conformance**: rejected. The index is a signed file in Goodfetch's own repository, so listing a Plugin would make Goodfetch its distributor. That reopens, through third parties, the exposure that keeping named means out of Goodfetch's code avoids.

## Consequences

**Who allows it.**
- `wall_domains` lists registrable domains, matched as in ADR 0004. `*` is accepted only when written explicitly. It is empty by default.
- It is taken only from Operator policy, user and project configuration, or a person's answer in the Console or an interactive CLI prompt, as for `pay_domains` (ADR 0045).
  - On a Daemon with accounts, only the operator role widens it, and it is stored in Operator policy.
  - **Changes ADR 0028:** the Recipe and run layers can only narrow it.
  - **Changes ADR 0011:** no MCP tool, code-mode function, SDK method or `--json` CLI operation widens it.
  - **Changes ADR 0031:** on a Daemon with accounts, widening it goes through step-up.
  - Operator policy can lock it empty.
- **`wall_refetch_domains`** lists the domains on which the engine may also refetch (below). It counts only for domains also in `wall_domains`, is empty by default, and follows these rules: registrable domains, `*` only when written explicitly, taken only from Operator policy and user and project configuration, which a person may edit through the Console's settings or the interactive CLI, and never widened by an answer to a Human pause or a "Needs you" item, written only by the operator role on a Daemon with accounts, narrowed only by the Recipe and run layers, widened by no agent surface (ADR 0011), and, on a Daemon with accounts, widened through step-up (ADR 0031). Operator policy can lock it empty separately from `wall_domains`. No Human pause offers it: neither the `ask` pause nor the "Needs you" view adds a domain to it.
- **Denied domains.** Operator policy can hold `wall_denied_domains`: registrable domains, matched as in ADR 0004, each with a required reason, typically a site's objection such as a cease-and-desist. A denied domain gets none of the allowance (reading what was served, blocking a Wall's script, refetching), whatever any layer says, an explicit `*` included, and neither the `ask` pause nor the "Needs you" view offers to add it to `wall_domains` or `wall_refetch_domains`. Only the operator role adds or lifts a denial; on an install without accounts, the user is the operator. No agent surface changes it (ADR 0011); on a Daemon with accounts, changing it goes through step-up (ADR 0031). Each change goes to the Audit log with its reason.
  - **Changes ADRs 0020, 0045, 0047 and 0048:** wherever they treat a domain as in `wall_domains`, a domain in `wall_denied_domains` is not.
  - On a denied domain, `on_wall = ask` raises no pause and acts as `report`, so only ADR 0048's own pause can arise, offering acceptance.
- **A warning at each widening.** The Console, the interactive CLI prompt, and the first configuration load that adds a domain show the person, in plain words, what they take on: copyright in content behind a paywall, the site's terms, and GDPR where consent is later accepted. Widening `wall_refetch_domains` adds that fetching a page again without the site's stored data, on every page the site withholds, exposes the person more than reading what was served; writing `*` there adds that every domain later allowed in `wall_domains`, for one run too, is refetched as well. The warning goes to the Audit log with the approval. There is no confirmation loop.
- **`on_wall`.**
  - `report` (default): a Wall on a domain outside `wall_domains` is handled as ADRs 0047 and 0048 handle it today.
  - `ask`: raises a Human pause with a Notification. The person answers "for this run" or "always for this domain"; the second writes `wall_domains` in user configuration, or, on a Daemon with accounts, in Operator policy, and only a person with the operator role can give either answer there.
  - When a consent wall would raise both this pause and ADR 0048's `on_consent_wall = ask`, the engine raises one Human pause offering both answers: read past it (`wall_domains`) or accept it (`consent_domains`).
  - The Console's "Needs you" view lists the domains that showed a Wall and offers to add them to `wall_domains`.
- **Changes ADR 0016:** never getting past a Wall is still not one of the compliance controls a run switches. The Wall allowance is its only exception, and only a person grants it, for the domains that person lists.

**What the engine does on an allowed domain.** All of it is generic: it acts on any Wall the detection rules of ADRs 0047 and 0048 find, and no part of it is chosen by vendor name.
- **Reading what was served.**
  - The engine keeps the text the server sent.
  - It hides, on the live page, the element that covers the main content, judged by the covering test of ADR 0048's wall test. On Chromium it uses ADR 0047's invisible style sheet; on Firefox and WebKit it hides on demand.
  - It removes that element from extracted content in every tier, and lifts a scroll lock the Wall left, from the isolated world, as ADR 0048 does after a refusal.
  - In the HTTP tier, which has no layout, the route's browser sample decides what covers the main content and whether the served page holds it, as it decides the wall test (ADR 0048).
  - **Changes ADR 0047:** the "never hidden" rule for paywalls, consent walls and ad-blocker walls, and the protection of elements covering a section marked `isAccessibleForFree: false`, do not apply on these domains. Sections the page declares paid are still never removed, since they are the content.
  - **Changes ADR 0045:** on these domains, its rule that no cosmetic rule hides a paywall vendor's overlay or an element covering a declared paid section does not apply, nor does its shielding of paywall vendors' overlay scripts through the never-block list.
- **Letting the Filter lists block a Wall's script.**
  - **Changes ADR 0047:** on these domains, the never-block list's entries for paywall vendors' overlay scripts do not apply. The Filter lists then block them as they do in any browser running uBlock Origin; Fanboy Annoyance already blocks `||piano.io^` and `||tinypass.com^`.
  - **Changes ADRs 0020 and 0047:** the breakage rules that turn blocking off because a Wall appears only with blocking off, or that retry with blocking off because an ad-blocker wall appears, are skipped. An ad-blocker wall is hidden instead.
  - **Changes ADRs 0020 and 0047:** ADR 0047's comparison of the route's sample with blocking off still applies, except that differences caused by requests to scripts of a Wall the rules detected are ignored, so blocking a Wall's script never turns blocking off for the route. Entries for challenge providers, anti-bot sensors, and anti-fraud and payment scripts still win.
  - The consent vendors' prompt scripts keep loading, so a prompt with a refusal is still refused (below).
- **One refetch per page, without the site's stored data**, only on `wall_refetch_domains`.
  - When a paywall leaves the served page without its main content, the Session clears everything stored under that site and fetches the page once more. That is the site's cookies on its registrable domain and, for every origin of that registrable domain, its storage, the browser's cached copies of its responses, Cache Storage and service workers (the kinds of data `Clear-Site-Data: "*"` names), and third-party data kept under it as the top-level site. Other sites' data in the Session stays. Before clearing, the Session admits no new request to that site, closes or navigates away its open pages of that site and ends their connections, so no page writes or sees half-cleared data.
  - It stays in the same Session, so the Access mode, Identity profile and proxy stay the same. It never goes through the Session pool, never retires or rotates a Session, and never counts as a block for ADR 0021's escalation.
  - It never happens when the Session is logged in to that site or is `identified` (ADR 0021). A Session counts as logged in to a site when a login ran there (ADR 0006), when a Page check for that site expects a logged-in page, or when its cookies for that site came from a saved identity (ADR 0035), a session import (ADR 0015) or an import (ADR 0056). A Session on a Profile directory used in place or on a Borrowed browser counts as logged in to every site, since the engine cannot tell which of its cookies are a login (ADR 0056). Nor does it happen when the Session's proxy cannot keep its exit: a pool that gives a new exit per connection, or a provider whose adapter cannot hold a sticky session. A Session with no proxy, a fixed proxy, a sticky session within the lifetime its provider adapter set (ADR 0021), or a local address with no proxy (ADR 0044) keeps its exit. A Session with neither proxy nor local address keeps it only when the refetch leaves from the first fetch's source address; otherwise the refetch does not happen. The engine does not look the exit up, which would send a request outside the run (ADR 0043). Where the refetch does not happen, the page stays as served, with the reason recorded.
  - It happens at most once per page.
  - The Site access spec sets the test for "withholds the content", from the paywall detector and the extracted main content.
  - A consent wall or an ad-blocker wall never triggers it: either one would greet a stateless visitor the same way.
  - **It stops when the site refuses.** Any Block cause in answer to the refetch, such as a rate limit, a Challenge, an `ip_block`, a `decoy` or `payment_required`, or a 401 or 403 status, or a login page, ends refetching on that registrable domain, under every domain key a Recipe gives it (ADR 0004), for the rest of the run: refetches already under way in other Sessions finish, and no new one starts. The page keeps what was first served.
    - **Changes ADRs 0006, 0021, 0035 and 0047:** for a refetch, nothing escalates or rotates, a login page is not a lost Session and goes to no recovery, none of ADR 0035's escalation ladder runs, and ADR 0047's retry with blocking off does not happen. The refusal does not count toward the Session's score in the Session pool, so it never retires the Session by another route.
    - Clearing the site's data also clears the Session's earlier answer to its Consent prompt. A prompt that reappears on the refetch is answered again under ADR 0048: refused, or accepted only where `consent_domains` or a run-scoped answer covers the domain, never by repeating a person's own earlier click; and a consent wall that then withholds the content (`consent_required`) stops refetching like any Block cause.
    - **A Challenge on a later page counts too.** A Challenge met on that site by a Session that cleared the site's data earlier in the run also ends refetching on that registrable domain for the run. That Challenge, on a page the run wants whatever its Wall, is still handled by ADR 0035's escalation ladder. So once a Challenge follows a clearing, no Session clears that site's data again in the run, and the refetch itself never completes a Challenge.
    - A 429 still counts for Politeness, so its backoff and halving apply to the domain (ADR 0053). A 429 or 502 from the proxy itself is a proxy refusal (ADR 0053), not the site's answer, and does not stop refetching.
    - Provenance records the stop. The Console's "Needs you" view lists the domain, and the person can dismiss the item, remove the domain from the layer of `wall_refetch_domains` that lists it (with the operator role on a Daemon with accounts; for a domain covered only by `*`, removal is not offered, and the person can replace `*` with a list in its layer or deny the domain as below), or, with the operator role, a reason and, on a Daemon with accounts, step-up, add it to `wall_denied_domains`.
      > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#862](https://github.com/goodfetch/goodfetch/issues/862): until the Wall allowance's refetch is built, the Run records a stop with `Run::record_refetch_stop(domain, cause)` in a `refetch_stops` table of the Run index (erased with the Run), with the project configuration file the Run's `wall_refetch_domains` came from, if any. "Needs you" lists one `wall_refetch_stopped` item per domain (ID `wall_refetch_stopped:<domain>`, `run` the last Run whose refetch stopped there), read again at each storage sample, with the `layer` that lists the domain and its `file`: the Run's project configuration while that file still sets the key, otherwise user configuration when it sets the key, else the Operator policy; `only_star` says when only `*` covers it there. The item clears once that layer no longer covers the domain or `wall_denied_domains` denies it, and a person may dismiss it. Removal is the person-only `needs_you.remove_refetch_domain({domain, instead_of_star})`, which edits the machine layer (every other byte kept) and, when only `*` covers the domain, requires the list that replaces `*`; it never writes a project file, whose item offers no removal and shows the file. Denial is the person-only `needs_you.deny_wall_domain({domain, reason})`, which appends the domain to the Operator policy's `wall_denied_domains` (its `[lock]` table when that sets the key), creating the file if needed; `wall_denied_domains` stays a list of domains, and the required reason is recorded with it in the Audit log (`wall_domain_denied`) and answered back. A managed Operator policy refuses both writes with `setting_locked`. Not built here: the operator role and step-up on a Daemon with accounts (the accounts and step-up tickets), and the refetch itself.
    - **Changes ADR 0054:** in a Partitioned crawl, the stop reaches every Partition that owns a domain key of that registrable domain, moves with each key when it is handed off, and `runs adopt` carries it too.
    - The stop, the pages already refetched and the Sessions that cleared each site's data are part of the run's Checkpoint, so a resumed run keeps them (ADR 0002). Nothing of the stop carries over to later runs: a denial is the lasting stop.

**Consent walls.**
- A prompt that offers a refusal is still refused (ADR 0048).
- On a domain in `wall_domains`, a consent wall still goes through the wall test. It is then read past as above, without consenting: no acceptance is clicked, and the vendor's trackers stay blocked as for any refused prompt.
- When the consent wall withholds the content, the engine accepts only if the domain is also in `consent_domains`. Otherwise the page stays `consent_required`.
- **Changes ADRs 0047 and 0048:** on a domain in both lists, the engine reads past first and accepts only when the content is withheld, rather than accepting every wall. On a route whose browser sample showed a consent wall, pages on a domain in `wall_domains` are read as served in every tier rather than `consent_required`, unless the sample showed the content withheld.
- **Changes ADR 0048:** `consent_domains` accepts `*` when a person writes it explicitly, as `pay_domains` does. ADR 0048's rule for an Agent's own "accept" click (its change to ADR 0014) still applies: the Agent asks for confirmation on a domain outside `consent_domains`, so under an explicit `*` it no longer asks anywhere. Writing `*` in `consent_domains` therefore shows a plain-language warning saying so, recorded in the Audit log, as widening `wall_domains` does.

**What the allowance never covers.**
- **`payment_required`.** A 402 or a paywall redirect (ADR 0045) is not a Wall. On every domain, the engine never escalates, rotates, refetches or reads past it, and a Paid fetch stays the only way through.
- **Named techniques.** Goodfetch ships no list of Wall scripts to block, no Googlebot, crawler or referrer preset, no preset named or presented as a meter reset (the generic refetch above is the one built-in means, rated above), and no archive or cached-copy fallback. A user's own Hooks, Plugins and Filter lists can do these things through the generic means ADRs 0033 and 0047 already provide. The engine cannot judge a Hook's or Plugin's intent, so these are not limited to `wall_domains`; a user's Filter list, though, gets past a Wall's script only on `wall_domains`: elsewhere the never-block list wins over it for paywall vendors' overlay scripts, and for an in-house paywall or ad-blocker-wall script ADR 0047's breakage rules turn blocking off instead. Consent vendors' prompt scripts are never blocked, on `wall_domains` included. Provenance records what they did as that user's configuration, as ADR 0047 records the scriptlets of a user's own lists, never as the engine's own act.
- **Changes ADR 0033:** the official Plugin index does not list, and delists once found, any Plugin whose name, description or docs present it as a way past Walls, crawler verification or paywalls, or as a source of archived copies of protected pages. Delisting is not revocation: the Plugin's digest and signer do not join the revocation list, which stays for security, so installing it by exact digest, where Operator policy allows it, is unaffected.

**How results are marked.**
- **Provenance** records, for each page:
  - the Wall's kind (`paywall`, `consent_wall`, `ad_blocker_wall`) and its detected vendor;
  - each action taken (`read_served`, `hidden`, `script_blocked`, `refetched_without_site_data`, `refetch_skipped` with its reason, `refetch_stopped` with the Block cause, the 401 or 403 status, or the login page that stopped it, `accepted`, `left`);
  - the reasons of `refetch_skipped`: `logged_in`, `identified`, `exit_not_kept`, `already_refetched`, `stopped_for_domain`;
  - the `wall_domains` entry that allowed it, and the `wall_refetch_domains` entry for a refetch.
- **Records** carry a `wall` marker that Dataset queries and every export format can filter on.
- **Completeness.** A page read past its Wall counts as reached. A page whose Wall still withheld the content keeps today's handling: a consent wall left unaccepted stays `consent_required` and makes the run `unverified` (ADR 0048).
- **The Audit log** records every widening of `wall_domains` and `wall_refetch_domains` with the warning shown, every change to `wall_denied_domains` with its reason, and one entry per run and domain where the allowance was used, not one per page.
- **Changes ADR 0046:** a refetch never reads the Response cache, so it never replays the copy that was withheld. Response cache entries fetched under the allowance are tagged with their domain and served only to runs whose `wall_domains` covers that domain. Entries fetched by a refetch carry a tag of their own and are served only to runs whose `wall_refetch_domains` also covers it, in whichever partition they land: a refetch sends none of the site's cookies, so its response may go to the public partition. No entry fetched under the allowance is served for a domain in `wall_denied_domains`. Saving an identity drops these entries from its partition unless the saving run's settings cover them in the same way, as ADR 0048 does for acceptances.
- **Changes ADR 0036:** change tracking says when a run and its Baseline used different allowances for a domain, or when a page was refetched in one and not in the other, so a difference the allowance caused is not reported as a change on the site.

**How it is described.** The docs, CLI and Console text, setting names, Error codes, Provenance action names and code identifiers describe the refetch as fetching the page again without the site's stored cookies and storage. They never say "meter", "free articles" or "reset the counter", never name a publisher, and never count the articles gained. ADRs and the Proving ground's fixtures keep describing its function plainly. Wording keeps the refetch from being presented as a way past paywalls; it does not change what the refetch does, which the rating above already accounts for.

**Goodfetch Cloud** runs the same contract and can lock `wall_domains` or `wall_refetch_domains` empty through Operator policy (ADR 0001). The research rates every level higher for a hosted service, so whether the cloud offers the allowance at all belongs to the cloud map. For the refetch, rated High there, the research recommends locking it unless a publisher's authorization covers the domain; that is the cloud map's call too.

**Proof.** The conformance suite runs on the Proving ground (ADR 0025) on Chromium, Firefox and WebKit. It covers each Wall kind ADRs 0047 and 0048 test: each paywall vendor, "accept or pay" walls, ad-blocker walls, plus a metered paywall. It checks two things:
- **Outside `wall_domains`:** the behaviour of ADRs 0045, 0047 and 0048 is unchanged.
- **Inside `wall_domains`:**
  - the served content is read and every action is recorded;
  - challenge, anti-bot and payment scripts still load;
  - no refetch happens outside `wall_refetch_domains`, on a Session logged in to that site or `identified`, behind a proxy that cannot keep its exit, for a consent or ad-blocker wall, or twice for a page;
  - a refetch keeps the IP address and Identity profile and leaves other sites' stored data in the Session untouched;
  - any Block cause, a 401 or 403, or a login page in answer to a refetch stops refetching on that domain for the run, without escalating, rotating or running ADR 0035's escalation ladder, and so does a Challenge met later in the run by a Session that cleared the site's data;
  - a refetch clears cookies, storage, cached copies, Cache Storage, service workers and third-party data kept under the site for every origin of its registrable domain, and no other site's;
  - the stop survives a resume, a handoff and `runs adopt`, leaves the Session's score unchanged, and a later Challenge that stops it still goes through ADR 0035's escalation ladder;
  - removing a domain or adding a denial from "Needs you" requires the operator role on a Daemon with accounts, and a denial always requires a reason, and step-up on a Daemon with accounts;
  - a domain in `wall_denied_domains` gets none of the allowance, under an explicit `*` too;
  - consent walls are never accepted without `consent_domains`;
  - a 402 is never got around;
  - cache entries never reach a run without the allowance, refetched entries never reach a run without `wall_refetch_domains`, none is served for a denied domain, and a refetch never reads the Response cache;
  - no Human pause or "Needs you" item offers to add a domain to `wall_refetch_domains`, or a denied domain to `wall_domains`, the Recipe and run layers cannot widen `wall_refetch_domains`, and locking it empty leaves the rest of the allowance working;
  - widening `wall_refetch_domains` and changing `wall_denied_domains` each write an Audit log entry with the warning or the reason.
