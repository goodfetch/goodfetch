# Politeness is shared by every run of a user, and across machines through an optional Politeness store

ADR 0021's per-domain limits (8 requests in flight, `Retry-After`, backoff from 2 s to 60 s, a 429 halving concurrency) lived in each run's own state (ADR 0004). Three runs crawling one site therefore sent it 24 requests at once, and a 429 seen by one run slowed none of the others. Pain #15 (`ops-scale-ratelimit-scheduling`) is this: crawlee#4039 kept hammering a domain despite its backoff, crawlee-python#1437 fell into a "death spiral" of 429s, and a potential user ruled out an engine "because it lacks built-in distributed rate limiting" (hn-102). **Politeness**, the per-domain and per-proxy limits, is now shared by every run of a user on a machine, whichever engine runs it, and across machines through an optional **Politeness store** that speaks the Redis protocol. Decided in [Scaling past one engine](https://github.com/goodfetch/goodfetch/issues/116).

How comparable tools share their limits:
- **Inside one process only:** Crawlee's `sameDomainDelaySecs` and its newer `ThrottlingRequestManager` keep their clocks in an in-memory `Map` ([source](https://github.com/apify/crawlee/blob/master/packages/basic-crawler/src/internals/throttling-request-manager.ts)); Spider, Katana and Colly's `LimitRule` likewise. Every extra crawler multiplies the load on a site.
- **A shared queue but no shared limit:** scrapy-redis, Crawlee's `RequestQueueV2` and Firecrawl's workers share work, not pacing.
- **A shared limit in Redis:** Scrapy Cluster's sliding-window throttle per domain, scoped by IP or spider type ([docs](https://scrapy-cluster.readthedocs.io/en/latest/topics/crawler/controlling.html)), the only off-the-shelf one found. Browserbase enforces account-wide concurrency on its own servers and answers 429 with `retry-after` ([limits](https://docs.browserbase.com/guides/concurrency-rate-limits)).

## Considered Options

- **Politeness per run** (the previous state, and Crawlee's): rejected. A user's own runs gang up on a site.
- **The Daemon as the only authority**: rejected, as ADR 0041 rejected it for Limits. An Attached engine or an engine embedded through the Rust crate never reaches the Daemon and would escape it.
- **Across machines, Goodfetch Cloud only** (as ADR 0041 first placed Limits): rejected. Pain #17 (`selfhost-parity-lockin`) is exactly a capability kept for the hosted service, and hn-103 names Politeness shared across machines as a problem people pay for.
- **Daemons electing an authority among themselves**: rejected. It means building an election and failover for state whose loss only resets pacing.
- **Partitioning alone** (ADR 0054): kept for one crawl, where it makes Politeness exact with no store, but it says nothing about independent crawls that reach the same site.
- **On store loss, failing closed at once or failing open**: rejected. Failing closed at once turns a cache restart into a halt of every run; failing open breaks the very promise the store exists to keep. The degraded mode below keeps runs moving through ordinary outages, and stops admission to shared keys only when an outage outlasts `politeness_degraded_max`, because past that point a crashed engine cannot be told from a cut-off one.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the setting is `politeness.degraded_max`.

## Consequences

**What is shared** (changes ADRs 0004 and 0021).
- **Per domain:** the count of requests in flight, the time before which `Retry-After` or a backoff forbids a request, and the halved concurrency after a 429 with its gradual recovery. The key is the run's domain key (ADR 0004): the registrable domain unless a Recipe overrides it, so runs with the same key share one entry.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the entry also holds the time of the domain's last request start. A run admits a request only once its own `politeness.domain.delay`, or a host's Crawl-delay, has passed since any sharing run's last start there.
- **Per proxy** (adds to ADR 0021). `proxy_concurrency` and `proxy_rate` limit the requests sent through one proxy endpoint and credential, unset by default.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the settings are `politeness.proxy.concurrency` and `politeness.proxy.rate`, in requests per second. Politeness is Foxhound's (ADR 0084); whether Collie carries these limits is [Collie's exact capability set](https://github.com/goodfetch/goodfetch/issues/455)'s.
  > Amended by [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md): Collie carries these limits, the ceiling learned from a proxy's refusals and the per-provider ceiling below, shared the same way. They protect the user's own accounts with the vendors, so they hold a program's own navigation through that proxy or provider too.
  - A 429 or 502 from the proxy itself, not from the site, is a proxy refusal. It is classified as a proxy error, never as a Block cause, so it never triggers ADR 0021's escalation. The engine learns a ceiling from those refusals, halving as on a site's 429, and raises it again gradually after a quiet period; the ceiling can be set by hand.
    > Note (agent decision, as built), 2026-10-23, [#759](https://github.com/goodfetch/goodfetch/issues/759): reqwest, the `http` tier's transport in `standard` and `identified` Sessions, keeps no status of a proxy's answer to `CONNECT`: hyper-util's tunnel error tells a 407 (`ProxyAuthenticationRequired`) from any other refusal (`TunnelRefused`) only by its text, so through reqwest a 429 cannot be told from a 502 there. The proxy limits ticket counts every tunnel refusal alike, or reads the status through a tunnel connector of its own.
    > Amended by [ADR 0127](0127-a-failure-from-a-party-goodfetch-did-not-write-becomes-a-typed-error-in-one-module-per-boundary-and-no-other-code-reads-its-text.md): the refusal is classified only where an engine module sees the proxy's own answer (the transport primitive of a tier that sends HTTP itself, or the egress proxy where it forwards to an upstream proxy). On a browser tier without the egress proxy, Chromium shows a refused tunnel as one network error, and through a proxy to a plain `http://` URL the proxy's answer looks like the site's; area 5's spec decides how each counts.
  - A 407 from the proxy is a credential error: it fails the request with the Error code `proxy_auth_failed` and does not change the ceiling.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#709](https://github.com/goodfetch/goodfetch/issues/709): a Collie page holds each main-frame navigation hop through its Session's proxy, a program's own included, with a Permit under the key `proxy <server> <username>` in the Politeness its Run shares (the per-user file, or with `politeness.sharing = run` one of the Run's own in memory, whose waiters are now woken within the engine); `page.request` and subresources take none. The rule lives in `goodfetch-page`'s `proxy` module, its state in the `proxy_limits` table the page crate adds to the file: the count in flight below the run's own `politeness.proxy.concurrency` and the learned ceiling, and a start only once a second divided by its own `politeness.proxy.rate` (whole requests a second, `0` meaning none) passed since any sharing run's last start. The proxy's own 429 or 502 (Proxy-Status naming an error) and a tunnel it refused (`ERR_TUNNEL_CONNECTION_FAILED`) give the Permit back as a refusal before the navigation's call answers: the ceiling halves from the count in flight, or from itself, at least 1, with no backoff or `Retry-After` hold, and grows back by one per request that ends well after a quiet 10 s, as the domain ceiling does. The settings are declared beside `politeness.sharing` for both Products and fall under area 3's `politeness.` prefix. The per-provider ceiling (A05-49) is not built yet.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-30, [#709](https://github.com/goodfetch/goodfetch/issues/709), the deep review's D18 (599-4): a hosted Proxy provider's Session holds its Permits under `provider <name> <username>`, the provider and the account's username as configuration names it, never the sticky username each Session builds on it, so every Session of one account shares the account's limit, which the vendor's plan sets (ADR 0088); a `proxy.server` Session and a `list` server keep `proxy <server> <username>`.
  > Note (decision of the spec #577 review, on a guarantee, not read by the owner), 2026-10-24: the proxy is the party only where it can have written the answer. Proxy-Status is read only on a response to an `http:` URL the Session's HTTP or HTTPS proxy forwarded itself, and only its last member, the one the intermediary nearest the browser appends (RFC 9209); through a tunnel, a SOCKS proxy or a hop `proxy.bypass` sends around the proxy (matched as Chromium matches its bypass rules), the header is the site's. A hop `proxy.bypass` sends around the proxy takes none of its Permits. The Session's own loopback relay answering `502` for a proxy it cannot reach (its member is named `goodfetch-relay`), and a tunnel it could not open, are the proxy's failure but no refusal: a proxy that is down teaches the ceiling nothing. A refusal halves the ceiling from the count tried at once (those in flight, the refused one included) or from the ceiling when that is lower, and the ceiling grows back only when a request ends well while the ceiling binds, so it never grows while unused and then halves from an inflated value. `politeness.proxy.concurrency` is at least 1: a Session whose proxy opens with `0` fails with `setting_invalid`. A wait for a proxy's room, its interval included, ends when its Run is cancelled.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, step 7 review finding 577-1 of [#1593](https://github.com/goodfetch/goodfetch/issues/1593): through a SOCKS5 proxy a plain `http:` request goes through the Session's own relays (the egress relay, and the loopback relay that authenticates to a proxy with credentials), whose `502` for a proxy they could not use reaches the browser as the document's response. Such a response is the proxy's when its last `Proxy-Status` member is `goodfetch-relay` and the relay recorded that it answered the latest connection itself (the proxy down, the credentials refused, the tunnel refused); a site's own field naming the relay stays the site's, since nothing the site sends sets that record. It raises `proxy_auth_failed` when the proxy refused the credentials, else `proxy_unavailable`.
- **Per cloud-browser provider** (changes ADR 0040). The ceiling learned per provider from a vendor's refusals is shared the same way, since a vendor's plan limits the whole account.
- **What stays per run:** the per-domain queues and their order (ADR 0004), learned escalation and tier choice (ADRs 0020 and 0021), and `per_ip_concurrency`, which is keyed by the target's resolved IP.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the setting is `politeness.ip.concurrency`.

**How settings combine.**
- Each run keeps its own values (ADR 0021, settings per run). A run admits a request to a domain only while the combined count in flight for that key, across every run sharing it, is below the run's own cap. A stricter run therefore waits while a looser one may still go up to its own cap.
- A `Retry-After`, a backoff or a halving seen by any run applies to every run sharing the key.
- Runs waiting on the same busy domain take turns, as ADR 0040 serves runs before domains.
- `politeness_sharing` is a setting per run: `shared` by default (through the Politeness store when one is configured, else on the machine); `per_daemon`, which shares on the machine only and ignores a store; or `run`, which restores per-run Politeness. Anything but `shared` is marked in the run's result (ADR 0023).
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the setting is `politeness.sharing`. Anything but `shared` is also recorded in the Audit log, like every value that presses a site harder than its default.

**On one machine: a per-user Politeness file.**
- Every engine of the user (Attached engines, the Daemon, engines embedded through the Rust crate) takes and returns its *permits*, one per request in flight, in one SQLite transaction on a per-user Politeness file. It lives outside the per-major folders like the Usage ledger (ADR 0041), so every major shares it.
- **No polling.** An engine waiting for a permit registers a wake endpoint (a Unix domain socket on Linux and macOS, a named pipe on Windows); the engine that returns a permit wakes the first waiter in turn. A wait for a `Retry-After` or a backoff is a timer on a known deadline.
- **Nothing to keep.** The file holds no Usage and nothing to resume, so it skips `fsync`. A permit records its run and epoch; an engine reclaims the permits of a run whose writer lock is free or held at a later epoch, as ADR 0041 reclaims slices.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-21, [#239](https://github.com/goodfetch/goodfetch/issues/239): the file is `politeness.sqlite` at the root of Goodfetch home, the format `politeness-file` 0.1 of the Usage ledger's family. The sharing layer is `goodfetch-engine`'s `politeness` module (Collie's): Permits, waiters and their wakes, reclaim. What a key admits is a rule the gate in admission names for its keys; Foxhound's per-domain rule (cap, delay, backoff, `Retry-After` and 429 halving) lives in `goodfetch-frontier`, beside the per-domain queues, and keeps its state in the `domain_limits` table Foxhound's composition adds to the file, so a Collie engine creates and touches none of it. The engine that gives a permit back wakes the waiter of its key whose turn it is, the oldest first, and keeps its room for it 2 s, so a run that did not wait cannot take it first; a waiter woken but still refused by its own stricter cap passes the wake to the next. A wait for room is also tried again after 30 s, only to find a holder that died, whose permits are then reclaimed; a deadline wait is a timer. A 429 halves the key's ceiling, from the count in flight when it had none, and backs the key off; each success after a quiet 10 s raises the ceiling by one. Until the fetch tiers (area 5) classify responses, a 429 reaches the rule as a crawl handler failing with `blocked` for a `rate_limit`, and `politeness.domain.concurrency` and `politeness.domain.delay` are unset by default (ADR 0086's 1 and 1 s arrive with the fetch tiers). `politeness.sharing = per_daemon` shares as `shared` does until a Politeness store exists ([#240](https://github.com/goodfetch/goodfetch/issues/240)); `run` takes permits from a file of the run's own in memory. The per-proxy and per-provider limits wait for area 5's proxies and cloud-browser providers.

**Across machines: the Politeness store.**
- **What it is.** A Valkey or Redis server the user provides, set in user configuration or Operator policy (ADR 0028) with a namespace, so every engine pointing at the same namespace shares Politeness. It holds no run state, so CO-28's exclusion of pluggable live storage (ADR 0037) still stands: nothing is resumed from it, and losing it resets only pacing.
- **Algorithms.** Rates use GCRA, run as a Lua script, so no server module is needed (redis-cell's `CL.THROTTLE` is the reference, [repo](https://github.com/brandur/redis-cell)). Permits are leases with an expiry, renewed while the request lasts. Every key a script touches for one domain or proxy carries the same hash tag, so the script runs on one Redis Cluster slot. A returned permit wakes waiters through pub/sub; a rate wait sleeps until the deadline GCRA returns.
- **Client.** The `redis` crate (BSD-3), async on Tokio with TLS through rustls, Sentinel and Cluster. TLS is required off loopback, and the password is a Secret reference (ADR 0015).
- **Precedence.** With a store configured, the store is the shared state for runs set to `shared`, and the per-user file serves only runs set to `per_daemon`, which count only one another.
- **Goodfetch Cloud** runs the same code against its own Valkey.

**When the store is unreachable.**
- **Heartbeats.** Every engine writes a heartbeat to the store, reporting its longest request timeout, so the live engines sharing a namespace are known. A heartbeat goes stale no later than a permit's lease expires, its record is kept until the store frees its reservation (below), and an engine that exits cleanly deletes its own.
- **Granted shares.** Each heartbeat's acknowledgement carries the engine's degraded share for every key it uses, and the longest request timeout any engine reported for that key. Only the store computes the share, so both sides always hold the same one. The cap shared out is the largest cap any engine's runs reported for that key. The store never lets the shares it has granted add up to more than the cap, except by the minimum of 1 per engine below: a share is the smaller of the cap divided by the live engines and what the cap leaves after every share currently granted to other engines, live or stale, rounded down and at least 1. A share that has to shrink counts at its old size until the engine acknowledges the new one, so a new or growing share waits for the others' next heartbeats.
- **A cut-off engine** keeps the permits it holds until their leases expire, then waits the longest request timeout of its last acknowledgement, so requests other engines admitted before it went stale have ended. It then admits within its last granted share: a run admits a request only while the engine's combined count in flight for that key, across its runs, is below that share scaled by the run's own cap over the largest one. Per-proxy limits are shared out the same way.
- **Engines still connected.** While an engine's heartbeat is stale, the store's script keeps reserved the larger of the share it last granted that engine and the permits it held, so engines that still reach the store admit only the rest of the cap. Requests in flight therefore exceed the cap only by the minimum of 1 per cut-off engine whose share would otherwise have been 0.
- **For a bounded time.** The store cannot tell a crashed engine from a cut-off one, so degraded admission lasts at most `politeness_degraded_max` (10 minutes by default, settable), counted on each side's own clock from the moment the engine sent its last acknowledged heartbeat. The cut-off engine then admits nothing more to shared keys, and the store frees its reservation only once `politeness_degraded_max` plus the longest request timeout the engine reported has passed, so requests it admitted have ended first. From then on, the cut-off engine still admits nothing to shared keys until it reconnects; its runs stay live and resumable. An outage of the whole store longer than that therefore stops admission to shared keys everywhere, which the degraded-period report says.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the setting is `politeness.degraded_max`.
- `Retry-After`, backoff and halving go on locally.
- The degraded period is reported as an event on each affected run's event stream (ADR 0024), a metric on the ops listener (ADR 0050) and a note in each affected run's result. Reconnection is automatic, with backoff; on reconnecting, the engine registers its requests in flight as permits before the store frees its reservation.

**Formats** (changes ADR 0030). The per-user Politeness file and the Politeness store's key and script layout join ADR 0030's contract formats. Both follow the Usage ledger's exception: their major stays frozen across product majors, and newer versions only add, so every supported major shares them.

**Several Daemons in a Daemon group** (ADR 0055) share Politeness through a store. A group of more than one Group member, formed by the Helm chart or by `goodfetch group join`, is refused unless a store is set or its Operator policy sets `politeness_sharing: per_daemon`, which every run's result and the Console then show.
