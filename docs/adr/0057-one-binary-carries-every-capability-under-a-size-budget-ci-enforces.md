# One binary carries every capability, under a size budget CI enforces

The `goodfetch` binary keeps every capability built in, V8 and DuckDB included, and is held to a **Size budget**: a ceiling per released file and an increase check on every pull request, both enforced by CI. V8 and DuckDB are about 80% of the binary (+42.8 MB and +33.0 MB of a 94.9 MB probe), and the projection for V1 is about 95–120 MB raw and 35–45 MB compressed per platform before the engine's own code. That is the research's 105–130 MB (40–50 MB gzip) without the MongoDB and SQL Server libraries (+6.5 MB and +3.7 MB), which ADR 0026 keeps out of the binary as sink processes, at the measured 36% gzip ratio. That is the size of Deno (96 MB, 42 MB compressed) and Bun (89 MB, 42 MB), and it fits every channel. Until now no ADR set a number, so a new dependency had no cost anyone could see, and a channel limit would only show up when a publish failed. Decided in [Binary-size budget per distribution channel](https://github.com/goodfetch/goodfetch/issues/197), from the measurements of [Size limits per distribution channel and the size cost of each binary component](https://github.com/goodfetch/goodfetch/issues/196) ([findings](https://github.com/goodfetch/goodfetch/blob/research/binary-size-budget/rnd/research/2026-10-12-binary-size-limits-and-costs.md)).

> Amended by [ADR 0084](0084-goodfetch-ships-two-products-collie-and-foxhound-from-one-repository-and-foxhound-contains-collie.md): there are two executables, Collie's and Foxhound's, which contains Collie's code. Which capabilities each carries and each one's Size budget are decided in [How the products are built, and each product's Size budget](https://github.com/goodfetch/goodfetch/issues/454) and [Collie's exact capability set](https://github.com/goodfetch/goodfetch/issues/455).

**Which channel limits bind.**
- **PyPI:** 100 MB per file and 10 GB per project, both raised on request; yanking frees nothing ([storage limits](https://docs.pypi.org/project-management/storage-limits/)).
- **crates.io:** 10 MiB per `.crate` upload, with no documented way to raise it ([publish_limits.rs](https://github.com/rust-lang/crates.io/blob/main/src/config/publish_limits.rs)). The binary never ships in a crate (ADRs 0024 and 0051), but the `goodfetch` crate carries what the engine embeds, because ADR 0047 forbids downloads at build time.
- **npm:** no documented limit. Users report a 117.9 MB tarball accepted and 198.7 MB and more refused with `E413` ([npm/cli#4794](https://github.com/npm/cli/issues/4794)); unverified by npm.
- **Everything else** is far above the binary: GitHub Releases under 2 GiB per asset, GHCR 10 GB per layer, Lambda container images 10 GB, Cloud Run none.

**Competitors.** We found no size budget published by Deno, Bun or Node, and their users complain about size ("Why is the Deno 2 binary 136 MB?", [deno#26516](https://github.com/denoland/deno/issues/26516); a Bun issue asking for a smaller build drew 40 reactions, [bun#2541](https://github.com/oven-sh/bun/issues/2541)). Stagehand bundled with Playwright went past Convex's 42.9 MiB function limit ([stagehand#1610](https://github.com/browserbase/stagehand/issues/1610)). Front-end projects fail CI on size with tools such as [`size-limit`](https://github.com/ai/size-limit). What every browser-automation user downloads is the browser: Chrome headless shell is 124 MB compressed and Chrome 198 MB, and that, not the driver, is what breaks Lambda's zip limit.

## Considered Options

- **V8, DuckDB or both downloaded on first use**: rejected. Splitting both saves about 30 MB compressed per platform, about 15% of an install once the browser is counted. It costs a wait before the first script or the first search, an `artifact_unavailable_offline` error under `offline` (ADR 0043) for features that need no network today, two more signed and pinned executables (ADR 0039), and the download failures behind proxies and mirrors that Playwright needed five settings to handle. It would also undo ADR 0051's worker that runs from the same binary.
- **Dropping ICU from V8** (`v8_enable_i18n_support = false`, −10.9 MB): rejected. Scripts lose `Intl`, which ADR 0051 promises and extraction scripts use to read dates and prices in a site's locale, without saying so. LLRT drops it to stay small.
- **ICU stored compressed and decompressed at worker start** (−6 MB on disk): rejected for performance. Every worker would hold its own 10.9 MB copy instead of sharing the binary's pages, about 175 MB at 16 workers. Decompressing once into the per-user cache and handing each worker the file would share it again, but workers have no file access (ADR 0051), so it adds a mechanism for what the binary already gives.
- **`opt-level = "s"` or `"z"`** (−18% or −25% on the probe): rejected for performance. The measured DuckDB query ran about 18% or 90% slower, and AWS's LLRT measured 7% slower on average for `"s"` ([llrt#1811](https://github.com/awslabs/llrt/issues/1811)); ADR 0025's benchmark measures exactly that speed.
- **`panic = "abort"`** (a further −1.5%): rejected. A panicking task would kill the engine and every run in it, where today it fails only that task.
  > Note (owner's decision, 2026-11-10, [#2253](https://github.com/goodfetch/goodfetch/issues/2253), Q4): what follows a panic inside a crawl's attempt is decided. It is caught at the attempt's boundary and ends the attempt as a failed one, through the same end as any other ([#2285](https://github.com/goodfetch/goodfetch/issues/2285)). A panic outside an attempt has no rule yet.
  >
  > Note (owner's decisions, 2026-11-10, grilling of decision G-14 of the consolidated review: Q1 to Q5 answered "Yes, all six", Q7 answered "Yes, all seven", each on the grilling's recommended option as put; the wording is the grilling session's, and the owner did not read it; [ADR 0148](0148-a-panic-ends-what-owned-its-task-the-engine-stops-only-for-a-part-every-run-shares-and-nothing-is-restarted-in-place.md)): a panic outside an attempt now has its rule. It ends what owned its task and only that, and the engine stops only for a part every Run shares, or when a panic interrupted a change of state the engine owns (Q7). The rejection of `panic = "abort"` stands, as Q3 put it: only a panic in a shared part stops the engine, and unwinding is what lets it stop cleanly.
  >
  > Note (the grilling session's own reading, 2026-11-10, same grilling, awaiting the owner's reading): "fails only that task" above holds for a call; for a Run's, a Connection's, a Page's, a Session's or a browser's task it reads "ends only what owned that task", and a part every Run shares stops the engine.
- **UPX compression**: rejected. It does not support macOS, breaks Platform signatures (ADR 0039), keeps the whole image resident and draws antivirus false positives on Windows.
- **Ceilings alone**: rejected. They catch the break, not the drift before it.
- **An increase check alone**: rejected. Small accepted increases add up with no hard stop.
- **Release-profile builds in every CI tier**: rejected. Fat LTO takes about 20 minutes per target. The increase check compares a thin-LTO build with `main`'s thin-LTO build, so it measures growth without the release profile (the two differed by 4.4% on the probe), and the ceilings are checked on the release files themselves.
- **The owner approving every increase**: rejected. It stops autonomous delivery for routine dependency updates; the ceilings, which only the owner moves, remain the hard stop.
- **Nightly wheels on PyPI, pruned by a job**, as DuckDB does (79 `.devN` versions live, 52 GB, [cleanup_pypi.yml](https://github.com/duckdb/duckdb-python/blob/main/.github/workflows/cleanup_pypi.yml)): rejected. PyPI has no API to delete a release ([warehouse#12934](https://github.com/pypi/warehouse/issues/12934) is open), so the job scripts the web forms with the account's password and two-factor secret stored in CI. That breaks the token-free trusted publishing of ADRs 0030 and 0032, and depends on forms PyPI may change.
- **A separate `goodfetch-nightly` PyPI project**, as TensorFlow's `tf-nightly`: rejected. It has the same quota and the same pruning problem, and is one more name to guard.
- **DuckDB's SQLite reader as a pinned download** of the official, signed extension: rejected for distribution. DuckDB loads an extension as a shared library, and the shipped binary cannot: a fully static musl binary's `dlopen` always fails (ADR 0024), and on macOS the hardened runtime of ADR 0039 refuses a library signed by another team; DuckDB says its extensions cannot currently pass that check ([duckdb#16926](https://github.com/duckdb/duckdb/issues/16926)), and the reader failed exactly this way in another signed app ([msgvault#819](https://github.com/kenn-io/msgvault/issues/819)). The `disable-library-validation` entitlement would let any library into the engine and still leaves Linux.
- **DuckDB's SQLite reader linked statically**: rejected for distribution. The `duckdb` crate offers no option for it and refuses extension configs ([build_bundled_cmake.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/libduckdb-sys/build_bundled_cmake.rs)), so it would need a patched build or a self-built libduckdb that nobody else maintains; DuckDB's own build notes warn of symbol collisions on Windows ([sqlite_scanner.cmake](https://github.com/duckdb/duckdb/blob/main/.github/config/extensions/sqlite_scanner.cmake)), and a second SQLite beside `rusqlite`'s is a likely further collision, not verified.

## Consequences

### What stays in the binary

- Every capability stays in the one `goodfetch` binary of ADR 0024: V8 for the Script sandbox (ADR 0051), DuckDB for search and the SQL tab (ADR 0031) and the DuckDB Sink, and the in-binary Sinks of ADR 0026. No capability leaves the binary to meet the Size budget. Browsers, sink processes and Plugins stay downloads, as before, and DuckDB reads run files through table functions the engine registers (below), not through DuckDB's SQLite extension.
  > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): each capability stays in the executable of every Product that carries it. Foxhound's carries all of them; Collie's carries V8 and the Clean-up rules but not DuckDB, the Sinks or impersonated HTTP (`wreq`), as [Collie's exact capability set](https://github.com/goodfetch/goodfetch/issues/455) decided. No capability leaves an executable to meet a Size budget.
  > Amended by [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md): Collie's executable carries V8 and the Script sandbox, but not DuckDB, the in-binary Sinks or `wreq`, which only Foxhound's carries; search across runs, the SQL tab and the DuckDB Sink are Foxhound's.
- **Embedded data is stored compressed.** Every channel already compresses its files, so this saves disk space after install (about 6 MB), not download size; the compressed ceiling below is unaffected.
  - The serialized Clean-up rules with zstd (9.06 MB to 3.67 MB), decompressed when they are loaded, in about 6 ms, then dropped once deserialized. **Changes ADR 0047.**
  - The Console's assets precompressed with brotli (0.99 MB to 0.40 MB for the prototype) and served as they are with `Content-Encoding: br`, so no request compresses anything. It needs a small handler, because `tower-http`'s `precompressed_br` expects the uncompressed file beside the `.br` one. **Changes ADR 0031.**
    > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-21, [#811](https://github.com/goodfetch/goodfetch/issues/811): `xtask console build` (`just console-build`) runs Collie's Console package's `build` script into a folder of its own and writes each file it made, brotli quality 11, into `crates/goodfetch-collie/console-build/`, which no commit holds; it runs nothing when the package's files and the pnpm lockfile did not change since its last build. `build.rs` writes the table of those files, which only `src/main.rs` includes, so `cargo build` of the executable without the build fails with a compile error naming the command, while the library an SDK crate links, and `xtask`, build without it. Every `just` recipe that builds the executable runs it first; `xtask test-tools` builds it, and `xtask perf build` lends the head's build to the base's tree. Foxhound's executable serves no Console until Foxhound's Console build (spec #593).
    > Note (agent decision, moot: the Console leaves (ADR 0137)), 2026-10-26, [#1202](https://github.com/goodfetch/goodfetch/issues/1202): `xtask console build` builds each Product's Console: Collie's as above, and Foxhound's, `console/foxhound/`'s `build` script, into `crates/foxhound/goodfetch-foxhound/console-build/`, which Foxhound's `build.rs` embeds through the same table, so building Foxhound's executable without it fails with the same compile error naming the command. Foxhound's build reads Collie's package too, so a change to either rebuilds it, and its `routes.json` is Collie's routes followed by Foxhound's own. `xtask test-tools` builds both when it builds either executable, and `xtask perf build` lends both.
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no executable embeds a Console build, no Size budget counts one, Foxhound's screens are no workspace package of their own, no release test walks a Console's routes, and no Daemon serves a Console. The Stub gateway stays for the cloud-readiness conformance, without a Console build.
  - The offline docs and the `goodfetch init` templates with zstd, decompressed when read. **Changes ADRs 0030 and 0049.**
- **V8 keeps full ICU, uncompressed in the binary.** ICU is the 10.9 MB of locale data behind `Intl`. Each Script sandbox worker is the `goodfetch` binary itself, so data stored in the binary is shared through the page cache by every worker. ICU stored compressed would need a private decompressed copy in each worker for its whole life, because V8 hands ICU the memory to read its data from ([`udata_setCommonData`](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/udata_8h.html)): about 175 MB at 16 workers, to save 6 MB of disk and almost nothing of download. **Confirms ADR 0051.**

### Release builds

- The release profile uses fat LTO with one codegen unit, `opt-level = 3`, unwinding on panic, and `strip`. Pull-request and merge-queue builds keep thin LTO.
- Each release publishes the debug symbols of every binary beside it (split DWARF or `.dSYM` on Unix, `.pdb` on Windows), Sigstore-signed and attested like the binaries, so a crash backtrace can be read. **Changes ADR 0030.**
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each Product's executable has its own debug symbols per target, named after it.

### The Size budget

| What is measured | Ceiling | Increase threshold per pull request |
|---|---|---|
| Compressed release file per platform: the npm platform package, the wheel and the GitHub Release archive | 60 MB | +1 MB |
| Raw `goodfetch` binary per platform | 160 MB | — |
| `goodfetch` crate tarball (`.crate`) | 8 MiB | — |
| Each OCI image tag (ADR 0049) | none | +3 MB compressed |

> Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): the table is Foxhound's. Collie's ceilings are 50 MB per compressed release file and 120 MB per raw executable, with the same +1 MB threshold, 8 MiB per crate tarball and +3 MB per OCI image tag. Every row of this table, the tiers under "Where CI enforces it" and the rules under "Who moves it" apply to each Product's files, and Collie's ceilings move only by changing ADR 0087.

- Every V1 target of ADR 0024 is measured, and the largest must fit. Static musl Linux is the largest so far for V8 (8–12% above macOS), and DuckDB's own musl build is its largest. V8 was measured from the `v8` crate's prebuilt library; ADR 0051's source build with V8's sandbox on gets its first number from the first merge-queue run.
- The 60 MB ceiling leaves 15–25 MB over the projection, 40 MB under PyPI's per-file limit and about half of what npm is known to accept. The 8 MiB ceiling leaves 2 MiB under crates.io's limit, which has no documented raise. Images get no ceiling because browsers dominate them and their registries allow 10 GB, but an accidental layer still trips the increase check. The crate has no increase threshold: `cargo package` is cheap, so the merge queue checks its ceiling directly.
- Each release's notes list every measured size.

### Where CI enforces it (changes ADR 0032)

- **Every pull request:** a Linux x64 size estimate posted as a comment, which never blocks.
- **Merge queue:** the increase check, per target of the full matrix, comparing each build with `main`'s build of the same profile, and the crate's ceiling. The merge queue also builds the OCI images of ADR 0049, on Linux x64 and arm64, for their increase check. It blocks.
- **Nightly, release candidate, stable release and patch:** the ceilings, measured on the release-profile files of that build before any publish. They block: no nightly, release candidate, stable release or patch over a ceiling is published (**changes ADR 0030**).

### Who moves it

- A pull request that trips the increase check passes when its body has a "Size increase" section with the measured delta per target and its reason, and the fresh review accepts that section explicitly on the pull request's exact head.
  > Amended by [ADR 0133](0133-agent-work-follows-the-matt-pocock-skills-as-written-and-the-fresh-review-is-retired.md): no fresh review exists; the owner accepts the section when merging.
- A ceiling moves only by changing this ADR, with the owner's approval.

### PyPI (changes ADR 0030)

- **Nightly wheels leave PyPI.** They are attached to the nightly GitHub pre-release, which has no total size limit, and listed by a simple repository index (PEP 503, with PEP 691's JSON form) that the nightly job publishes on `goodfetch.dev`. Each file is listed with its SHA-256 and keeps its attestation. The index lists the last 30 nightlies. Users install with `pip install --pre goodfetch --index-url https://goodfetch.dev/nightly/simple --extra-index-url https://pypi.org/simple`, or a uv index pinned to the `goodfetch` package. npm keeps its `nightly` tag, and the OCI image its `nightly` tag: neither has a quota.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): the nightly index lists each Product's wheels on its own project page, and the install line and the uv index name `goodfetch-collie` or `goodfetch-foxhound` (ADR 0090), not `goodfetch`.
- PyTorch ([nightly index](https://download.pytorch.org/whl/nightly/)), JAX ([installation](https://docs.jax.dev/en/latest/installation.html)) and the Scientific Python projects ([SPEC 4](https://scientific-python.org/specs/spec-0004/)) publish nightlies to their own index the same way. uv, ruff, Deno, polars and Playwright publish none to PyPI (their PyPI release lists, read 2026-10-12).
- **The project quota.** About 50 releases a year (a release candidate and a minor every 4 weeks, a patch per Chrome major), six wheels each at about 40 MB, use about 12 GB a year, more than PyPI's 10 GB default. Before the first public release Goodfetch asks for 100 GB through [pypi/support](https://github.com/pypi/support), as DuckDB was granted ([support#6896](https://github.com/pypi/support/issues/6896)). The release job reads the project's usage and warns when it passes 70% of the quota, so the next increase is asked for before a publish can fail.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): `goodfetch-collie` and `goodfetch-foxhound` are two PyPI projects, each under its own 10 GB default. Foxhound's use is this estimate and Collie's about 9 GB a year; the owner asks for 100 GB for each right after its first upload, and the release job warns past 70% of either.

### How DuckDB reads run files (changes ADR 0031)

- Search across runs and the SQL tab do not use DuckDB's SQLite extension, which DuckDB ships only as a shared library fetched on first use. The engine registers its own table functions in DuckDB, through the `duckdb` crate's `vtab` feature, one per run table. Each reads a run file through the same `rusqlite` that writes run state, opened read-only, and hands DuckDB batches of rows.
- Column types come from Goodfetch's own run schema in `goodfetch-protocol`, not from guessing a SQLite file's types. Secret fields of run state (ADR 0015) are not exposed as columns.
- The functions use projection pushdown (`get_column_indices`, so only the queried columns are read) and parallel scans (`set_max_threads`), as DuckDB's extension does.
- DuckDB's external access, extension autoloading and installing are off from the start, so a query reaches only the runs the engine registered. No download is added, and ADR 0043's list is unchanged.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-26, [#1208](https://github.com/goodfetch/goodfetch/issues/1208): the read path is the crate `goodfetch-sql-tab` (glossary term *SQL tab*). Its table functions are `records(run)`, `rejected_records(run)` and `datasets(run)`, each taking a selected run's Run ID, with the columns `goodfetch-protocol`'s `foxhound::sql_tab::RUN_TABLES` declares; a Run ID the query did not select fails at bind with `query_invalid`. DuckDB's `json` extension is linked in statically (the crate's `json` feature, no download): `json_serialize_sql` checks a statement is exactly one `SELECT` or `WITH` before it runs, since `duckdb-rs`'s `prepare` runs every statement before the last and exposes no statement type, and its JSON functions read Records' values. The connection also refuses community extensions and persistent secrets, spills nothing (`max_temp_directory_size` 0), and locks its configuration as it opens. DuckDB's C++ sources build at `opt-level = 3` in the `dev` profile: unoptimized, one test query took minutes.
