# Distributed and crash behaviour is simulated on Tokio, model-checked in TLA+, and faulted at I/O seams

Leases and run epochs (ADR 0003), Checkpoints (ADR 0002), the writer lock (ADR 0031), Daemon groups (ADR 0055), Partitioned crawls (ADR 0054), the Politeness store's degraded shares (ADR 0053), the Usage ledger (ADR 0041) and Sink delivery (ADR 0026) are correct only if they stay correct under crashes, power cuts, partitions, clock skew and unlucky timing. Ordinary tests meet none of these on purpose, and nothing tested ADR 0002's power-cut promise. Each behaviour is therefore tested at every layer that can break it: a **Simulation** of several hosts on turmoil, with no runtime swap; model-based tests in one process with a crash VFS under SQLite; TLA+ models checked by TLC and validated against traces of the code; and real processes under kills, LazyFS and Toxiproxy. Faults enter only at I/O seams, never through failpoints.

No single tool covers Goodfetch: every Rust simulator runs one process, and none carries Chromium, sink processes, Script sandbox workers or SQLite's own C file I/O. Comparable projects layer their tools the same way:
- Amazon's ShardStore pairs reference models with a crash operation, Loom and Shuttle ([SOSP 2021](https://cdn.amazon.science/77/5e/4a7c238f4ce890efdc325df83263/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3-2.pdf)).
- etcd model-checks its Raft library in TLA+ with trace validation ([etcd-io/raft](https://github.com/etcd-io/raft/blob/main/tla/README.md)), and its robustness suite adds failpoints, `kill` and LazyFS.
- SQLite tests crashes through a VFS that drops unsynced writes ([testing](https://sqlite.org/testing.html)).

Decided in [Deterministic simulation and crash testing for leases, fencing, groups and run state](https://github.com/goodfetch/goodfetch/issues/275), answered by the agent on the owner's delegation, on the facts of [Deterministic time, randomness, storage and OS services in a multi-process Tokio system](https://github.com/goodfetch/goodfetch/issues/264) ([findings](https://github.com/goodfetch/goodfetch/blob/research/deterministic-testing/rnd/research/2026-10-13-deterministic-testing.md)) and [Rust test tooling in 2026](https://github.com/goodfetch/goodfetch/issues/263) ([findings](https://github.com/goodfetch/goodfetch/blob/research/rust-test-tooling/rnd/research/2026-10-13-rust-test-tooling.md)). It builds on ADR 0059's `Clock` and `Entropy` and on ADR 0062's test layout and `goodfetch-test-support`. The rules every test follows are in `TESTING.md`.

### The Simulation: turmoil, with no runtime swap

- **turmoil** runs several Goodfetch hosts (Daemons, Group members, engines) in one test process, each on its own paused current-thread Tokio runtime, over simulated TCP, with partitions, latency, message loss, host crashes and restarts. It is pinned to one version, since its main branch is splitting into crates (`turmoil-net`, `turmoil-fs`) and warns that its API will change.
- **One seed drives the whole Simulation.** The test's seed (fixed, overridden by `GOODFETCH_TEST_SEED`, printed when the test starts, ADR 0059; supplied by `goodfetch-test-support`, ADR 0062) is split by `Entropy`'s derivation into one stream for turmoil, one per host's `Entropy`, and one for proptest's generation of the Fault plan, so that seed alone replays every choice. Each host gets `Clock::paused(start)` and `Entropy::seeded(stream)`, ADR 0062's named constructors, which the scenarios' test module opts into as ADR 0062 says.
- **The engine stays on Tokio everywhere:** multi-thread in production, current-thread with the paused clock in tests (ADR 0059), one runtime per host in the Simulation. No crate depends on a replacement runtime.
- **What the code must do:**
  - **Connections the Simulation carries are opened only in a new `transport` module of `goodfetch-engine`.** It sits beside `rpc`, which keeps the protocol server (framing, `hello`, events, credits, WebSocket framing) and takes every connection from `transport`. `transport` listens and connects, and takes the network as a value: the OS, the in-memory transport pair area 3 already exposes, or a test adapter. The network's interface is public because the in-memory pair, which the embeddable `goodfetch` crate uses, is a product adapter; no item is made public for tests (ADR 0062). turmoil's adapter is test code at that seam.
    - **In scope:** stdio of an Attached engine (so the engine tracer's `hello` already arrives through `transport`), the Daemon's Unix socket and Windows named pipe, loopback TCP and the WebSocket listener's sockets, the private endpoint for `workers=N` and forwarded live actions, the ops listener, the peer link, and the Politeness file's wake endpoints.
    - **Out of scope, because the Simulation never runs them:** fetch sockets, opened by area 5's fetch tiers behind ADR 0017's egress checks (local addresses of ADR 0044 included); the CDP connection to a browser process; plugin-protocol pipes to Plugins and sink processes (ADR 0033); and third-party clients that open their own sockets (the Valkey client, object storage, Model providers). Their modules are the only other places allowed to open sockets, each with `#[expect(clippy::disallowed_types, reason = "…")]` naming this ADR.
      > Amended by [ADR 0069](0069-sdks-and-the-cli-are-tested-against-a-scripted-engine-and-the-binary-of-the-same-commit.md): the test-only `goodfetch-scripted-engine`, which the Simulation never runs, may also open its own stdio and sockets and write stdout, each use under an `#[expect]` naming both ADRs.
      > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#172](https://github.com/goodfetch/goodfetch/issues/172): the conformance harness, `goodfetch-conformance`, which the Simulation never runs either, is a Client of the target it starts: its `protocol::target` module opens a Daemon target's Unix socket or loopback TCP connection itself and reads each of the target's streams on a thread that ends with the stream, under `#[expect]`s naming this note, since the harness depends on no engine crate (spec #152).
    - **The lint:** `disallowed-types` lists `std::net::{TcpListener, TcpStream, UdpSocket}`, `std::os::unix::net::{UnixListener, UnixStream, UnixDatagram}`, `tokio::net::{TcpListener, TcpStream, TcpSocket, UdpSocket, UnixListener, UnixStream, UnixDatagram, UnixSocket}` and `tokio::net::windows::named_pipe::{NamedPipeServer, NamedPipeClient}`; `disallowed-methods` lists `tokio::io::stdin`, `tokio::io::stdout` and `std::io::stdin`.
  - **Every thread and every blocking call goes through the `tasks` module, whose blocking policy is a value.**
    - Production and ordinary tests: blocking calls run on tracked blocking threads, and a dedicated thread (the run's SQLite writer actor, for example) is an OS thread its owner joins.
    - The Simulation: blocking calls run inline on the host's runtime, and a dedicated thread's body runs as a task on that runtime, calling its handler inline for each message. `tasks` drives the thread's message loop, so the same handler runs either way. SQLite then takes no simulated time and finishes at a deterministic point.
    - `std::thread::spawn`, `std::thread::Builder::spawn` and `std::thread::scope` join the spawn functions `disallowed-methods` already bans outside `tasks`.
    - The policy's exact shape is decided by the area 3 ticket that first adds blocking work to `tasks`, within these rules.
      > Note (agent decision, as built), 2026-11-06, [#1577](https://github.com/goodfetch/goodfetch/issues/1577) ([ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md)): `tasks` gains a CPU pool policy. `TaskOwner::analysis` runs a page's parse and every read of its document on the owner's tracked blocking threads once it holds one of the pool's permits, which the whole owner tree shares, one per core (`available_parallelism`, else 1), so at most that many analyses run at once, while Tokio's blocking pool would grow to 512 threads. Under `BlockingPolicy::Inline` the analysis runs inline, so the paused benchmarks' counts stay exact, and `BlockingPolicy` stays a `Copy` value ([#1905](https://github.com/goodfetch/goodfetch/issues/1905)). Other blocking work stays on `TaskOwner::blocking`. The run file's kept readers run on `BlockingThreads`, a handle on the owner's tracked blocking threads ([#1923](https://github.com/goodfetch/goodfetch/issues/1923)). The run file's checkpointer is an actor of the writer's owner ([#1922](https://github.com/goodfetch/goodfetch/issues/1922)), and so is the timer that syncs an idle writer at `periodic` ([#1927](https://github.com/goodfetch/goodfetch/issues/1927)). The Politeness file's wake endpoint now does its file work inside the owner's blocking work, since `tokio::fs` ran it on the runtime's own blocking pool even under `Inline`, which let the host's load decide how a paused run's writes were grouped ([#1924](https://github.com/goodfetch/goodfetch/issues/1924)).
  - **The engine never builds its own runtime.** `tokio::runtime::Runtime::new`, `tokio::runtime::Builder::new_current_thread`, `tokio::runtime::Builder::new_multi_thread` and `#[tokio::main]` are allowed only in `main` and test helpers. `tokio::task::block_in_place`, which panics on a current-thread runtime, is in `disallowed-methods`.
    > Amended by [ADR 0071](0071-performance-budgets-are-counted-per-change-and-time-is-measured-on-the-reference-host.md): bench targets (`benches/`) may build a runtime too, through the helper tests use.
    > Amended by [ADR 0081](0081-each-sdk-follows-its-languages-concurrency-model-and-shapes-events-by-meaning.md): the Rust SDK's connection builds a runtime too, through the helper `main` uses: its linked engine's, or its transport's for a Daemon or Goodfetch Cloud; its unit tests over the in-memory transport pair hand it the test helper's paused runtime instead. Engine code still never builds one.
  - **Third-party time hooks read the `Clock`**, such as rustls's `TimeProvider` for certificate expiry. The `tracing` subscriber's timer reads the `Clock` too, so traces carry simulated time and no real timestamps.
  - **The Simulation builds with `--cfg tokio_unstable`**, so turmoil seeds each host's runtime randomness (`select!` order). The shipped binary does not, and neither do the other tests. The scenarios compile only under that cfg (`#[cfg(tokio_unstable)] mod simulation;` in `goodfetch-engine`'s `tests/it/main.rs`), in a nextest archive and CI job of their own with their own rust-cache key. That job runs only the `simulation` module (a nextest filter), so the other engine integration tests never run on a Tokio configuration production does not ship. That job counts against ADR 0061's Pre-merge budget of 15 min per job, and its cache is a Linux pull-request cache, saved by the cache-warming job, within the 10 GB priority of ADR 0061.
    > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): each crate with scenarios, a Foxhound crate included, declares `#[cfg(tokio_unstable)] mod simulation;` in its own `tests/it/main.rs`, and they run in the same job.
- **Scenarios keep an Observation log** (each operation, its answer and each fault, in simulated time) and **invariant checkers** judge it:
  - **Fencing:** no output becomes visible under a stale lease epoch or run epoch, and every committed output is visible exactly once.
  - **One lead:** no two Daemons act as Lead Daemon under overlapping lead epochs, a Schedule fires at most once per occurrence, and one lead grants slices at a time.
  - **Limits:** charged plus outstanding Usage never exceeds a Limit, except the loss ADR 0055 allows after the last Group backup.
  - **Partitions:** every discovered URL lands in exactly one Frontier, and no domain is admitted by two Partitions at once.
  - **Audit log:** every event stays verifiable from the chain's head, checked by the product's own chain verifier through its public interface, which the scenario passes to the checker as a value.
  - **Bounded liveness:** once faults stop, every run finishes or is resumable within a stated simulated time.
  The same checkers judge real-process tests and the conformance suites. Scenarios cover ADR 0055's VM path (majority confirmation, promotion, demotion, `group lead --confirm`), Checkpoint handoff on scale-down, `runs adopt`, a zombie copy writing to a fenced destination, Partition handoff, and clock skew through `jump_wall` on one host. Group scenarios use `politeness_sharing: per_daemon`, since the Politeness store is a real Valkey outside the Simulation.
  > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the key is `politeness.sharing`.
- **Fault plans.** A **Fault plan** lists the faults and Client operations a test applies at named simulated moments. Plans are generated by proptest-state-machine, run by turmoil, and shrunk by proptest when they fail, so a failure is small, readable, and replays after the code changes, where a bare seed replays only on its own commit.
- **Determinism check.** A few seeds run twice, and their Observation logs and `tracing` output must match. A mismatch is a leak of real time, of randomness drawn outside `Entropy` for a choice, or of hash order, fixed at its source.
  - **Security values are not compared.** Keys, tokens, run data keys, the group's certificate authority, certificates and TLS handshakes still come from the OS generator, never seeded (ADR 0059, unchanged). They differ between two runs of one seed, so the Observation log records them redacted, as `STYLE.md` already keeps secrets out of logs. A behaviour that depends on their bytes, such as an order taken from a key, is a determinism bug fixed in the code, never by seeding them.

### TLA+ models with trace validation

- **Five models, checked by TLC**: **run fencing** (leases, run epoch, destination compare-and-set by Guarantee class), **lead epoch** (ADR 0055's confirmation, promotion, demotion and membership change), **Partition handoff** (partition-map epochs, fenced domain handoff), **slices and reclaim**, and **degraded shares** (ADR 0053's shares and reservations over bounded time).
- **Trace validation.** Each transition a model names is a `tracing` event under one dedicated target, carrying the model's variable names as fields. A test subscriber writes them as NDJSON, and TLC checks each TLA+ trace is a behaviour of the model. Only the Simulation's traces are validated: its hosts share one simulated clock, so their events have one order, while traces from several real processes would need a merged order that no clock gives them. etcd's Raft library validates its traces this way, with events compiled in only under a `with_tla` build tag; Goodfetch's events are always compiled in under their target, so no test build is needed.
- **Tool versions are pinned:** the TLA+ tools and the CommunityModules release (whose `CommunityModules-deps.jar` reads NDJSON), as one dated pair. **Unverified:** etcd's `validate.sh` downloads the nightly `tla2tools.jar` and the latest CommunityModules, so it is not known whether the last stable TLA+ tools (1.7.4, 2024-08-05) run this trace validation, or whether 1.8.0, a prerelease of 2026-10-13, is needed. The "Test infrastructure" spec settles the pair.

Corrected 2026-10-22: the owner chose the copy, which the next bullet records.

### Model-based tests in one process

- **proptest-state-machine** checks `run_state`, `lease`, `checkpoint`, delivery and the `ledger` against reference models, on real SQLite in the test's folder and `Clock::paused`. Transitions include handler timeouts (advancing the paused clock), late commits, crashes, power cuts, reopening and resuming. Sinks join through the plugin protocol's in-memory adapter with a test Sink of each Guarantee class.

### Crashes and power cuts

- **A crash VFS** under SQLite, built with `sqlite-plugin` and modelled on SQLite's own crash VFS: it holds writes until a sync, and at a crash point either keeps unsynced writes (a process crash) or drops, tears or reorders them from the seed (a power cut). It then refuses every later I/O of the crashed instance. It also injects I/O errors and a full disk at chosen operations. `run_state`, the Usage ledger and the Politeness file take the VFS name as a value when they open a database; production passes none. It runs on every OS.
- **LazyFS on Linux** under the real binary: the run folder and the Goodfetch home are mounted through it, the engine is killed, LazyFS's cache is cleared, and the run resumes. In default mode every acknowledged commit is present, and in both modes `integrity_check` passes, so fast mode loses commits but never corrupts.
  > Note (agent decision, accepted by the owner on 2026-10-21; [#344](https://github.com/goodfetch/goodfetch/issues/344)): checked first, LazyFS 0.3.1 mounts and clears its cache in a Linux container given `/dev/fuse` and `CAP_SYS_ADMIN`, as a user without root through `fusermount3`, and its own project's CI mounts it on GitHub-hosted `ubuntu-latest` runners (run 32730150342, 2026-08-24); the Release suite's own run waits for Actions. It is built from source archives pinned by SHA-256 (LazyFS and the toml11 and spdlog releases its cache library would otherwise fetch unpinned). `LazyFs::mount` takes the folder alone: the durability mode is the engine's setting, and LazyFS's other modes (page eviction, scripted torn writes) are not needed here. The executable keeps its run folder in the home, so one mount of the home holds both. Ending a mount syncs every file first, so only `clear_cache` loses data.
- **Real process crashes** on every OS (`kill -9`, `TerminateProcess`) of engines, Clients, sink processes and Script sandbox workers, at seeded moments chosen from observed protocol events. The moments come from the test process's own `Entropy`, whose seed `GOODFETCH_TEST_SEED` overrides (ADR 0063).
- macOS's `fullfsync` reaching the drive is invisible to all of these, so a test asserts the pragma is set.

> Note (agent decision, as built), 2026-11-06, [#1577](https://github.com/goodfetch/goodfetch/issues/1577) ([ADR 0138](0138-a-page-is-analysed-once-costly-features-are-settings-and-run-state-commits-in-groups-at-a-chosen-durability-level.md)): the run-state model draws each of the four Durability levels for each case, and after every crash its reopened file holds every acknowledged commit, except what the level may lose to a power cut: recent commits at `fast`, the deferred writes no synced commit covered yet at `full`, and the last `run_state.commit_interval` at `periodic`. `PRAGMA integrity_check` still passes below `off`. At `off` a crash leaves the file's `unclean` mark, or a file a power cut damaged, and the file is discarded, so the Run starts again from nothing ([#1927](https://github.com/goodfetch/goodfetch/issues/1927)). The ledger's model holds that a deferred claim's journal never under-charges a Limit, and the lease's model that only a lease taken by a deferred claim may read pending again after a crash ([#1926](https://github.com/goodfetch/goodfetch/issues/1926)). The LazyFS check above keeps its two modes, `full` and `fast`.

### No failpoints

Faults enter only at I/O seams: the crash VFS for storage, the transport adapters and turmoil for the network, the plugin protocol's in-memory adapter for Sinks and handlers, Toxiproxy and process kills for real binaries. A crash only matters at an I/O boundary, and each one has a seam. A point that cannot be reached this way is I/O that bypasses its seam.

### In-process concurrency: loom

- **loom**, under the custom `--cfg goodfetch_loom`, checks every module that synchronizes threads with its own atomics, `Mutex`, `RwLock` or `Condvar`. Such a module imports them through its crate's `sync` module, which maps to loom under that cfg; `disallowed-types` lists the std atomic, `Mutex`, `RwLock` and `Condvar` types outside `sync` modules, which make the rule checkable. A Goodfetch-specific cfg leaves dependencies that react to `cfg(loom)` unchanged, as crossbeam does with `crossbeam_loom`.
- Actors on Tokio channels are covered by the Simulation, whose hosts run with seeded runtime randomness.
- The `sync` modules' `goodfetch_loom` switch is the only test-only `cfg` in product code. It swaps the primitives of a whole crate at compile time, as loom requires and as Tokio and crossbeam do; no module gains a test branch, so ADR 0062's rule against `#[cfg(test)]` branches holds everywhere else.

> Note (agent decision, as built), 2026-11-14, [#2200](https://github.com/goodfetch/goodfetch/issues/2200): the first module under loom is the engine's CPU pool (`tasks::cpu_pool`), whose own threads now run every Page analysis; it takes `Arc`, `Mutex` and `Condvar` from `goodfetch-engine`'s new `sync` module. `ci/loom.toml` lists each module with its crate and test filter, and `just loom` builds that crate's unit tests under `--cfg goodfetch_loom` in `target/loom/` and runs them at 2 preemptions. The full gate runs it beside the host's steps, as it does TLC and Miri (ADR 0135), and the Release suite on its Linux x64 glibc cell; the nightly-only job at 3 preemptions is not built yet. The runtimes that Collie's executable builds, the Attached engine's, the Daemon's and a command's Connection's, all come from one place, its `runtime` module, sized by `governor.worker_threads` and `governor.blocking_threads`.

### Real-process faults: Toxiproxy and `kind`

- **Toxiproxy** sits between each real engine and the Politeness store, and between real Group members. ADR 0059's `resolve` setting maps each host name to that engine's Toxiproxy listener. `resolve` maps names to addresses, not ports, so each engine's listeners bind the store's and peers' ports on a loopback address of their own: `127.0.0.x` on Linux and Windows, `lo0` aliases on macOS (ADR 0059's extra loopback addresses). So a test can cut off one engine or partition one Group member on any OS. Politeness checks:
  - requests in flight per key stay within the cap plus ADR 0053's minimum of 1 per cut-off engine;
  - degraded admission stops at `politeness_degraded_max`;
    > Amended by [ADR 0086](0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md): the setting is `politeness.degraded_max`.
  - a reconnecting engine registers its requests in flight before the store frees its reservation.
  Valkey's clock stays real, so durations are short settings (ADR 0059).
- **ADR 0055's Kubernetes path** runs on `kind`: deleting and force-deleting the lead's pod, a lead cut off from the API server stopping within the lease period, and promotion by a `lead` change.
- **Sink delivery** crashes the engine at each delivery step through the crash VFS and the in-memory plugin adapter, and kills the sink process and the engine at seeded protocol messages in the real suite. The fencing checker judges by Guarantee class:
  - Fenced: no stale-epoch record is visible.
  - Record-fenced: no stale overwrite.
  - Keyed: no duplicate key.
  - At-least-once: every record is present at least once.

### Where the pieces live

Following ADR 0062's layout:

- **Simulation scenarios** are integration tests of `goodfetch-engine`, in `tests/it/simulation/`, one module per behaviour area (`lead.rs`, `partition_handoff.rs`). turmoil's network adapter lives there too, since it implements `transport`'s public network interface.
  > Amended by [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md): scenarios that need a Foxhound crate (Partition handoff, the crawl's work-item leases, Sink delivery) are integration tests of the Foxhound crate that holds the behaviour, in its `tests/it/simulation/`, under the same `cfg(tokio_unstable)` job, since no crate outside `crates/foxhound/` may depend on one. turmoil's network adapter moves into a test-only crate outside `crates/foxhound/`, which the integration tests of `goodfetch-engine` and of Foxhound's crates take as a dev-dependency.
- **Committed Fault plans** are generated fixtures in a `fixtures/fault_plans/` folder beside the scenario that replays them, each with the `<name>.source.toml` file ADR 0062 requires (generator version, seed, replay command). proptest's regression files are committed where proptest writes them.
- **Model-based tests** are unit tests of `run_state`, `lease`, `checkpoint`, delivery and `ledger`, through each module's interface.
- **loom tests** are unit tests of the module they check, compiled only under `goodfetch_loom`.
- **`goodfetch-test-support`** holds the crash VFS, the Observation log and the invariant checkers, so the Simulation, real-process tests and conformance suites share them. They depend on no Goodfetch crate: the Observation log is plain records (operation, host, epochs, keys, simulated time). It is kept apart from the `tracing` output and the TLA+ traces.
- **TLA+ models** live in `test-support/models/`, one folder per model with its TLC configurations and trace-validation spec.

### Suites

[ADR 0061](0061-three-test-suites-each-run-by-one-just-command-under-a-time-budget.md) defines three suites, Quick, Pre-merge and Release, each containing the one before; the Pre-merge suite runs on Linux and the Release suite on every platform of ADR 0024, in the merge queue, nightly on `main` and for every release. This decision places each check in a suite, and names the nightly-only jobs that explore new seeds. Those jobs are in no suite, and they are not Live checks (ADR 0064). A failure in the deterministic layers (model-based tests, the Simulation, loom, TLC) replays from its seed. A failure in the real-process and Toxiproxy jobs is recorded with its seed and classified by ADR 0064's diagnostic run. They run in the nightly tier once ADR 0032 turns it on, and they repeat tests of normal length with new `GOODFETCH_TEST_SEED` values for the stated time, each test within ADR 0061's 5-minute kill, never one long test.

**Model-based tests are unit tests, so they run in the Quick suite too,** with 16 cases, within its 10-second kill per test. A Pre-merge job of its own reruns them on Linux at 256 cases, selected by a nextest filter. The rerun counts against ADR 0061's Pre-merge budget. Committed regressions replay in both. The count is set per test: these tests take a `ProptestConfig` that `goodfetch-test-support` builds for the suite `just test` runs. The global `PROPTEST_CASES` is never set, so every other property test keeps its count.

A failure in a deterministic nightly-only job is a bug, not flakiness. A real-process or Toxiproxy failure goes through ADR 0064's diagnostic run and, if flaky, its quarantine; the reproduction of Regressions rule 3 is still owed when it does not reproduce. No release candidate is cut while either kind is open. A breached budget is fixed as ADR 0061 says: shard the job, speed up the tests, or move a test to a later suite. Case counts and seeds are never lowered and scenarios never removed to fit.

### Regressions

1. A failing Simulation writes its shrunk Fault plan to a file and prints the command that replays it.
2. The fix commits that plan beside its scenario, with proptest's regression file. Committed plans run in the Pre-merge suite.
3. A failure found by a non-deterministic layer (real processes, LazyFS, Toxiproxy, `kind`) is reproduced at the lowest deterministic layer that shows it, and that reproduction is the regression test. If none can, an issue extends the Simulation, and the failing seed joins the real-process scenario's committed seeds meanwhile.
4. A TLC counterexample becomes a Fault plan as well as a fix to the model or the design. A trace-validation failure is fixed in the code or in a stale model.
5. A test that once found a bug is never removed or weakened while its behaviour is still required; it may be replaced by a test covering the same failure.

## Considered Options

- **madsim:** rejected. It swaps Tokio for `madsim-tokio` and patches crates, so the whole engine rests on a fork whose releases have slowed (last 2025-10-11); RisingWave's simulation outgrew its CI.
- **Shuttle with `shuttle-tokio`:** rejected. Async code needs `tokio = { package = "shuttle-tokio" }` in every crate behind a Cargo feature, which is a runtime swap, and crates that link the real Tokio stay outside it. loom covers small primitives; the Simulation covers actors.
- **A hand-written simulator** (FoundationDB, TigerBeetle): rejected. turmoil already runs Tokio hosts on a simulated network.
- **Antithesis or Hermit:** not adopted. They alone run the real binary with Chromium deterministically, but both are Linux x86-64 only and Antithesis is a paid service with no public price. The layers above cover the rest; the owner can approve Antithesis later as a paid test resource.
- **A `Network` handle** beside `Clock` and `Entropy`: rejected. The transport is already a seam with two adapters (OS sockets and the in-memory pair), so turmoil is a third adapter there, and ADR 0059's two handles stay the only handles.
- **Failpoints** (`fail`, Neon's `testing` builds, etcd's `gofail`): rejected. `fail` is switched by a Cargo feature on the dependency, keeps a global registry, and scatters annotations through product code. A failpoint build of the binary is the test-only build ADRs 0057 and 0059 rule out.
- **Porcupine, Elle, Jepsen:** rejected. Goodfetch's properties are fencing, uniqueness and bounds, not linearizability of a key-value API, so invariant checkers over Observation logs judge them. Jepsen needs a Clojure control node and Linux nodes; Toxiproxy gives real-process partitions on every OS, and `jump_wall` gives clock skew in the Simulation.
- **stateright or P for model checking:** rejected. stateright needs the code written as its actors, and P has no trace-validation precedent found. TLA+ is the established choice and has one in etcd.
- **No model checking:** rejected. A Simulation samples states and rarely reaches a promoted lead meeting a returning one across a membership change; a design flaw survives any number of tests of a correct implementation.
- **`kill -9` alone for crash safety:** rejected. The page cache survives a process crash, so it proves nothing about ADR 0002's power-cut promise.
- **dm-log-writes or dm-flakey; turmoil's `fs` shim:** rejected. Block-level replay needs root and a block device, and ShardStore's block-level variant "has not found additional bugs and is dramatically slower". SQLite's I/O goes through its C VFS, not `std::fs`.
- **Seeds alone as regressions:** rejected. A seed replays only on its own commit; a committed Fault plan stays meaningful after the code changes.

## Consequences

- **[Engine tracer: an Attached engine answers `hello` over stdio](https://github.com/goodfetch/goodfetch/issues/214) builds on plain Tokio.** There is no runtime swap. From its first code, its stdio connection comes from `transport`, it spawns tasks and threads and blocks only through `tasks`, and it leaves runtime construction to `main`.
- **Amends ADR 0038.** Its Structured concurrency allowed blocking work "on dedicated threads their owner joins". Dedicated threads now come only from the `tasks` module, which runs their bodies as tasks in the Simulation, and `std::thread` spawning joins the banned spawn functions. It also adds, for every crate: the `transport` seam with the network as a value, the socket, stdin and runtime-construction bans, and the ban on `block_in_place`. ADR 0037's amendment rule therefore carries them to every area's spec.
- **Amends `STYLE.md`:** its dedicated-thread rule changes as above, these rules join its concurrency and lint rules, and the `goodfetch_loom` cfg joins its custom cfgs. `TESTING.md`'s "Remote but owned" adds the Simulation.
- **Changes area 3's spec** ([Spec: Engine runtime (V1 area 3)](https://github.com/goodfetch/goodfetch/issues/213)):
  - Its scenarios with several processes add Toxiproxy partitions and cut-offs, LazyFS, and seeded kill moments.
  - Its in-memory adapter scenarios move into the Simulation and the model-based tests above.
  - It gains a `transport` module beside `rpc`, which takes its connections from it, and the ops listener's socket comes from `transport` too.
  - `tasks` drives dedicated threads such as `run_state`'s writer actor, and its blocking policy is a value; the ticket that first adds blocking work to `tasks` settles its shape.
  - `run_state`, `ledger` and `politeness` open their databases with a VFS name value.
  - `group`, `partition`, `lease`, `ledger` and `politeness` emit the trace events their TLA+ models name.
- **Adds to ADR 0002:** its power-cut promise is now tested, by the crash VFS on every OS and by LazyFS on Linux.
- **Adds to ADRs 0003, 0026, 0053, 0054 and 0055:** their fencing, delivery, shares, handoff and lead-epoch rules each get a TLA+ model, invariant checkers and, except ADR 0053's store, Simulation scenarios. ADR 0026's sink suite keeps its cases and tiers, and gains crash points per delivery step and a verdict per Guarantee class.
- **The "Test infrastructure" spec** builds the shared pieces: turmoil's transport adapter, the Observation log and invariant checkers, the seed derivation, Fault plans and their file format, the crash VFS, the LazyFS and Toxiproxy setups, the TLC and trace-validation jobs. Three facts are unverified here and are checked there: that `sqlite-plugin` registers a VFS with the SQLite that `rusqlite` bundles, that LazyFS runs on GitHub-hosted Ubuntu runners (else in a container given `/dev/fuse`), and which pinned pair of TLA+ tools and CommunityModules runs trace validation.
- **Amends ADR 0062:** its rule against test-only branches in product code now has one exception, the `sync` modules' `goodfetch_loom` switch, with a one-line note there.
- **Adds to ADR 0062:** its layout gains the places above, and `goodfetch-test-support` gains the crash VFS, the Observation log and the invariant checkers.
- **Amends ADR 0059:** tests gave the network a real local stand-in only; the Simulation now also swaps `transport`'s network for turmoil's adapter. The network stays a value with product adapters, not a third handle, and ADR 0059 carries a one-line note.
- **Adds to ADR 0032:** `test-support/` gains `models/` for the TLA+ models.
- **Builds on ADRs 0061 and 0064:** the suites, budgets and caches are ADR 0061's, and failures of nightly-only jobs are recorded and filed as ADR 0064 says.
- **Delivery order (ADR 0058).** Each check lands with the code it covers. M1 brings the seams, the model-based tests, the crash VFS, LazyFS and the real-process crash tests. The Simulation's group and Partition scenarios, Toxiproxy and `kind` arrive with Daemon groups, Partitioned crawls and the Politeness store in M4.
