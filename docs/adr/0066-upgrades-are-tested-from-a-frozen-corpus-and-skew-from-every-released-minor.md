# Upgrades are tested from a frozen corpus per format version, and skew from every released minor

ADR 0030 promises that an engine reads every older minor of a format within its major and refuses everything else with a message, ADR 0024 that a Daemon serves any Client of its major with the same or an older minor, and ADR 0055 that Group members of different minors work together. Three kinds of test prove these promises together:
- a **Compatibility corpus**: committed files, one set per released version of each contract format, generated by the release that wrote them and then frozen;
- **fabricated versions** for every refusal, generated for every format;
- **released artifacts**, fetched by digest, for every version pair that runs live: every older minor of the major against the current build, Group members upgraded one by one under load, and older engines opening files a newer one wrote.

Nothing is published yet (AGENTS.md), so the corpus holds only the current version of each format until the first `0.y.0` preview freezes the first set.

Comparable projects split the work the same way:
- **Committed files per format version**, run with unit tests: Chromium's `version_N.sql`, Cassandra's legacy SSTables, Kubernetes' objects per release, Temporal's histories.
- **Released binaries** for live skew, rolling upgrades and rollbacks: Kafka, containerd, Kubernetes' skew jobs.
- **Fabricated versions** for refusals: Cargo's lockfile from the future, Playwright's version override.

Docker shows what a wide window does when nothing tests it. Its pull request called the code for old API versions "largely untested", and raising the minimum in 29.0 broke Portainer, Traefik and Testcontainers until 1.40 was restored. Goodfetch's window is the whole major, so every minor in it is tested.

Decided in [Upgrade and version-mismatch testing](https://github.com/goodfetch/goodfetch/issues/287), on the facts of [Upgrade and version-mismatch testing (research)](https://github.com/goodfetch/goodfetch/issues/271) ([findings](https://github.com/goodfetch/goodfetch/blob/research/upgrade-testing/rnd/research/2026-10-13-upgrade-testing.md)). The rules every test follows are in `TESTING.md`. Every check sits in one of the three suites of [Test suites, local commands and time budgets](https://github.com/goodfetch/goodfetch/issues/276) (ADR 0061): Quick, Pre-merge and Release, each containing the one before. The CI tiers that run them (pull request, merge queue, nightly, release pipeline) are that decision's.

## Decision

### The format registry

- **One registry in `goodfetch-protocol`** lists every versioned format: its name, current `major.minor`, schema, and which of ADR 0030's rules it follows (the default rule, the frozen-major family of the Usage ledger, the Response cache's "run without it", the Clean-up rules' "newest readable set"). `xtask codegen` writes it into the committed bundle. Every generated check below reads it, so a new format cannot miss a test.
- **It covers every format an engine reads or a peer speaks.** That is ADR 0030's list, plus the per-major stores a later minor opens: the Run index, the Schedule store and Group backups.
- **One compatibility function per rule** in `goodfetch-protocol` decides each version pair. It is tested against a literal table of cases, and the tests below take their expected outcomes from it.

### The Compatibility corpus

- **Layout.** It lives in a top-level `compat/` folder, keyed by format version, not product version:
  - `compat/<format>/head/` holds the current version;
  - `compat/<format>/<major>.<minor>/` holds each frozen version, with a `SHA256SUMS` file;
  - each frozen version also holds the committed snapshots of what the current reader makes of it.
- **Every version is kept.** The window is the whole major, and the frozen-major formats outlive product majors, so no version is dropped.
- **SQLite-backed formats are stored as SQL text dumps**, rebuilt into a database by the test, as Chromium stores its schemas. Each frozen Checkpoint version also keeps one real Checkpoint file, so its size and digest are checked as well.
- **The protocols' fixtures are recorded transcripts.** For the JSON-RPC protocol, the plugin protocol and the peer protocol, a fixture holds the messages one side sent in a fixed scenario. The test replays them against the current other side.
- **Generated, never hand-written.** `xtask compat write` runs fixed scenarios through the current writers with ADR 0059's fixed `Entropy` seed and test `Clock` start, so its output is byte-stable. The data is synthetic, from the Proving ground's seeded families, and Secrets appear only as Secret references.
- **Whole schema covered.** Every property of a JSON format's schema appears in at least one `head/` document. Every column of a SQLite-backed format holds a non-null value in at least one row.
- **`xtask compat check`** fails when:
  - `head/` differs from what `write` produces;
  - a frozen byte changed;
  - a registered format lacks its `head/` set, or a frozen set for a version a release shipped, as `compat/releases.toml` records it;
  - coverage is incomplete;
  - a format's schema changed while its version still equals its newest frozen version. This catches a format changed without a version bump, the mistake behind Cassandra's two fixture sets for one format (CASSANDRA-15035).
- **Frozen from the release tag.** Every release is built from `release/x.y` (ADR 0032), and `main` may already carry a newer, unreleased version of a format. So when a stable `x.y.0` or a patch ships, the pull request it opens against `main` (ADR 0030) runs `xtask compat freeze --tag <tag>`. It reads each format's `head/` from the release tag, as the docs version is cut from the tag's `docs/`. Every format whose shipped version has no frozen set on `main` yet gets that `head/` copied to `<major>.<minor>/`. Release candidates and nightlies freeze nothing.
- **A frozen file never changes.** When the reading of an old file must change on purpose, only its snapshot changes, in a reviewed pull request whose changelog entry says so, as Kubernetes' `after_roundtrip` files work.
- **Pre-release.** No format changes version before the first publish (AGENTS.md), so `compat/` holds only `head/` sets, regenerated in place with each format change. Each format gets its `head/` set and its refusal cases in the change that creates it, starting with the protocol in [Engine tracer: an Attached engine answers `hello` over stdio](https://github.com/goodfetch/goodfetch/issues/214). The first frozen sets come from the first `0.y.0` preview (M4, ADR 0058).

### What a corpus test checks

- **Golden reads.** Each fixture is read with the current reader, written again with the current writer, and compared with its `insta` snapshot. A SQLite-backed store is migrated, and the test requires the same schema as a freshly created store, as Chromium does, and content equal to its snapshot.
- **Replays, where the format drives work:**
  - a frozen Checkpoint resumes against the Proving ground and finishes with the oracle's result, never repeating an Effect (ADR 0002);
  - a frozen Plan replays without a model against the pages it was recorded on (ADR 0009);
  - a frozen Recipe project runs;
  - a recorded Client transcript replays against the current Daemon, and each response matches its snapshot;
  - a recorded Plugin transcript replays as a scripted Plugin against the current engine.

### `goodfetch upgrade-files`

- `compat/upgrade-paths.toml` lists the majors `upgrade-files` upgrades from: at least the previous major, and during the previews the previous `0.y`.
- Tests generated from that table:
  - every frozen set of each listed source upgrades to a golden result that reads as the current `head/` version;
  - a second run changes nothing;
  - per-user state lands in the new major's folders, and the previous major's files keep their hashes;
  - unrelated project files are untouched;
  - a source not in the table is refused with a message naming the release to upgrade through first, as Cassandra's upgrade graph does;
  - a newer major is refused with a message to upgrade.
- Before the first release the table is empty and only the refusals run.

> Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#226](https://github.com/goodfetch/goodfetch/issues/226): `upgrade-files [--from <major>] [--json]` takes the newest older major Goodfetch home holds when `--from` is not given, and copies its per-major folder (settings files, Run index, run folders; not its Daemon's runtime files) into the executable's major's folder, each file through a temporary file and a rename. A file the new major already holds is kept: one equal to the older major's is reported unchanged, so a second run changes nothing. A source not in the table names the major after it as the release to upgrade through, when that major is older than the executable's. Both refusals answer `upgrade_source_unsupported`. A format whose new major reads its older one differently converts its copy in the release that changes it. The shared stores' generated cases hold an engine of a fabricated Product version, 1.1, to a lowest minor it meets and to a newer one.

### Refusals, from fabricated versions

Generated for each registered format, each with its Error code and message snapshotted:

- **Default rule:**
  - a newer minor is refused with a message to upgrade;
  - an older major is refused with a message naming `goodfetch upgrade-files`;
  - a newer major is refused with a message to upgrade.
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): the Run index, the Schedule store, the Saved identity store, user configuration and the Operator policy refuse a newer minor only when the lowest minor they record is newer than the engine, and the list of installed executables joins the Usage-ledger family.
- **Usage-ledger family** (the Usage ledger, the known-certificates store, the Politeness file and store layout):
  - a newer minor opens;
  - an unknown Limit flagged *must understand* refuses runs with `limit_not_understood` (ADR 0041);
  - an unknown unflagged row is ignored;
  - an unreadable pin row stops its host with `certificate_changed` (ADR 0042).
- **Response cache of a newer minor:** the run goes on without it, reading and writing nothing (ADR 0046).
- **Clean-up rules channel** with sets of several minors: the newest readable set is used (ADR 0047).
- **An Operator policy found only for an older major:** the engine refuses to start and names `upgrade-files` (ADR 0030).
- **Handshakes** (the JSON-RPC protocol, the Browser host, the plugin protocol's range, the peer protocol): a refused version is refused in the reply to `hello`, before any other message, and the connection closes. This replaces a time budget, such as Stagehand's 5 seconds, with a check that cannot flake.
  > Amended by [ADR 0096](0096-the-browser-host-runs-from-either-products-executable-and-goodfetch-cloud-runs-each-run-on-the-product-it-needs.md): between an engine and a Browser host only another major is refused; a fabricated `hello` of a newer or older minor checks that both sides settle on the lower one, and a Session needing more than an older Browser host's minor checks that the engine fails it with `browser_host_outdated` before sending it to the Browser host.

A test fabricates a version by writing the header, or by sending its own `hello`. No build carries a version override (ADR 0059). Each handshake refusal is tested twice:
- in the Quick suite, in process: the handshake code receives the fabricated `hello` over an in-memory transport, and the test checks the reply and that the transport closes;
- in the Pre-merge suite, through the conformance harness, which speaks raw JSON-RPC to a running engine and checks that the reply comes before any other message and that the connection closes.

### Released artifacts

- **The skew matrix.** The latest patch of every released minor of the current major runs against the current build:
  - **Clients:** the TypeScript SDK, the Python SDK, the Rust crate's client, the CLI and the MCP server, against the current Daemon, on Linux with one runtime each. The SDKs also run over stdio, with `GOODFETCH_ENGINE_PATH` pointing at the current binary, the hotfix path of ADR 0030 (see the amendment to ADR 0024 below).
  - **The Console:** a Console page served by an older Daemon keeps working after the current Daemon replaces it on the same Goodfetch home.
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
  - **The Browser host:** older engines against the current Browser host.
    > Amended by [ADR 0096](0096-the-browser-host-runs-from-either-products-executable-and-goodfetch-cloud-runs-each-run-on-the-product-it-needs.md): the Browser host runs in both directions: older engines against the current Browser host, and the current engine against older Browser hosts, which settle on the lower minor.
  - **Plugins:** older first-party Plugins, as OCI artifacts by digest, through the plugin conformance suite against the current engine.

  An SDK and the Attached engine it ships with never skew (ADR 0024); only `GOODFETCH_ENGINE_PATH` pairs an SDK with another engine. The `0.y` previews have no cross-minor skew, because each preview counts as a major (ADR 0030).
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each Product's Clients, SDKs over stdio (through its own engine-path variable) and Console build run against the current executable of the same Product. A Collie Client on a Foxhound engine, which [Protocol, Operation catalog and SDKs across two products](https://github.com/goodfetch/goodfetch/issues/458) admits, has its Product check at `hello` tested for every pair of Products with fabricated `hello`s, as version refusals are; files shared across Products follow [Collie and Foxhound installed on one machine](https://github.com/goodfetch/goodfetch/issues/486).
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **What an old Client runs.** The old release's own Journeys ([ADR 0063](0063-end-to-end-tests-follow-a-catalog-of-numbered-journeys-kept-in-the-repository.md)), checked out at its tag with its own seeds. The old tag's Journey helper runs each variant with the old release's Client against the current binary, given by path. Each variant keeps ADR 0063's fresh start: its own Proving ground and its own Goodfetch home, shared with no other variant, so a Journey that starts, stops or moves the Daemon starts the current one. The Journeys assert what that release promised, and a minor keeps every promise.
  - A Journey that asserts something outside semver (ADR 0030) is fixed on `main`.
  - On an old tag, such a Journey's variant is excluded by its variant ID (`J-NNN@<surface>`) in `compat/skew-exclusions.toml`, with a reason, in a reviewed change.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each old Journey runs against the current executable of its Product.
- **Rolling upgrades.** A three-member Daemon group starts on each older minor of the major and runs under load: a Partitioned crawl, a Schedule and live Limits. Its Group members are upgraded one at a time, once with the Lead Daemon last (the order a StatefulSet's default rolling update gives when the Lead Daemon is pod 0) and once with it first. The test checks ADR 0055's guarantees:
  - no Record lost or duplicated beyond the Sink's Guarantee class;
  - no Limit exceeded;
  - each Schedule occurrence fires once;
  - a named token stays valid;
  - peer links settle on the lower minor.

  It also promotes an upgraded Group member from a Group backup the older minor wrote. Rollbacks:
  - a Group member rolled back before the Lead Daemon upgrades keeps working;
  - a Lead Daemon rolled back after writing newer minors is refused, as ADR 0030 decides.

  The Helm chart runs the same upgrade in `kind`, from the same releases as the group:
  - the older release's chart is installed by digest from `compat/releases.toml`;
  - `helm upgrade` moves it to the current chart, under the same load and checks;
  - `helm test` then runs;
  - any skipped step fails the job.

  During the previews, which have no cross-minor upgrade, the Helm upgrade runs the current chart against itself, as every empty version list does.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): rolling upgrades and the Helm upgrade run on Foxhound, whose load includes a Partitioned crawl; Collie's chart is the same chart with Collie's image (ADR 0049).
- **Older engines and newer files:**
  - each older minor of the major, and the last minor of each supported earlier major, opens the Usage ledger, the known-certificates store and the Politeness file the current engine wrote, enforces what it reads and refuses flagged Limits it cannot;
  - each older minor refuses a current Checkpoint, Plan, settings file and Schedule file with the upgrade message.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): an older Collie opens the formats both Products carry, an older Foxhound Foxhound's own.
  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): each older minor of the major also opens the Run index, the Schedule store, the Saved identity store, user configuration and the Operator policy the current engine wrote, and refuses them only when their lowest minor is newer than itself; the list of installed executables opens as the Usage ledger does. Of settings files, only a project's is still refused.
- **Two majors on one machine.** The previous major's last release and the current build run on one machine:
  - their Daemons never restart each other;
  - only the active major fires Schedules;
  - `schedules activate --major` copies Schedules forward and leaves the older store as it was (ADR 0036);
  - the Usage ledger caps both.

  During the previews this runs from the second `0.y` on.
- **Expected outcomes** come from the compatibility functions, never hard-coded, as Stagehand computes its own.
- **Where artifacts come from.**
  - The release's pull request to `main` appends the release to `compat/releases.toml`: binaries per platform, the npm and PyPI packages, the crate, Plugin artifacts, the Helm chart and the OCI image, each with its SHA-256 digest and attestation bundle.
  - ADR 0032's pinned artifact mirror holds these releases.
  - The entry also records the version of every registered format the release shipped, read from the tag's registry. `xtask compat check` reads it to know which frozen sets must exist.
  - CI fetches the artifacts and Sigstore's trusted root (`gh attestation trusted-root`) before the outbound deny starts, and checks each digest. It then verifies provenance offline with `gh attestation verify --bundle --custom-trusted-root`, since without that flag the command fetches the trusted root over the network. The fetched set is cached by the manifest's hash.
  - One local command fetches the same set; [Test suites, local commands and time budgets](https://github.com/goodfetch/goodfetch/issues/276) names it beside its suite recipes.
- **No silent skip.**
  - A missing or mismatched artifact fails the job. SQLite's `backcompat.test` skips itself without old binaries, and Cargo's `old_cargos.rs` sits `#[ignore]`d.
  - An empty version list runs the current build against itself, as PostgreSQL's upgrade test does by default. Every harness is therefore proven before the first release, and an empty matrix never passes.

### Suites

| Check | Suite |
|---|---|
| Corpus golden reads, fabricated refusals of files and of `hello` in process, compatibility-function tables, `upgrade-files` from fixtures, `xtask compat check` | Quick |
| Corpus replays, handshake refusals through the conformance harness, and `upgrade-files` against the binary | Pre-merge |
| Every test that needs released artifacts: the full skew matrix, rolling upgrades and rollbacks, older engines opening newer files, two majors, the Helm upgrade | Release |

- The Release suite runs in the merge queue, so every merge passes the whole skew matrix. Its rerun on `main` each night and its run on each release candidate's, stable release's and patch's own bytes cover the same checks. Nothing here is a nightly-only job.
- None of these checks is a Live check: every version pair is a fixed, released artifact.
- A new or changed skew harness or generated job takes ADR 0064's 20 stress runs, like any new or changed test.
- **The matrix grows with each minor, and so does its wall time.** About 13 minors ship a year, and each brings about 14 checks: the five Clients, the two SDKs over stdio, the Console, the Browser host, Plugins, the two rolling-upgrade orders with their promotion and rollbacks, the Helm upgrade and the older-engine checks. ADR 0061 runs on the free plan's 20 concurrent jobs, so one job per check would exceed it after two minors. From then on, every added minor adds merge-queue time.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **Few jobs per minor.** The generator groups each older minor's checks into as few jobs as fit ADR 0061's 45-minute job budget: its artifacts are fetched once per job, while every variant still starts its own Daemon, Goodfetch home and Proving ground (ADR 0063). It splits a minor's job only when that job breaches its budget.
- **When the Release suite breaches ADR 0061's merge-queue budget,** the levers are:
  - fewer or faster jobs per minor;
  - more concurrency or larger runners, a paid test resource the owner approves, as ADR 0061 treats the cache limit.

  A minor is never dropped, and no skew check moves out of the merge queue: ADR 0061's "move a test to a later suite" does not apply, since the Release suite has none. Sampling minors or moving skew out of the merge queue reverses this decision and needs a new ADR.

## Considered Options

- **Committed fixtures only:** rejected. They miss live skew, rolling upgrades and an older engine opening a newer file, which ADRs 0041, 0042 and 0053 promise.
- **Released binaries only:** rejected. They are slow, and they never produce the versions that refusals need, such as a newer major.
- **Fixtures keyed by product release, in a sliding window** (Kubernetes keeps four): rejected. ADR 0030 promises every older minor of a major, and the frozen-major formats span majors.
- **Hand-written fixtures:** rejected. They drift from what the writer emits, so every project above generates its fixtures.
- **Binary SQLite fixtures:** rejected, apart from one Checkpoint file per version for its envelope. SQLite's file format has been stable since 3.0.0, and text dumps can be reviewed.
- **Skew only before a release or only nightly:** rejected. A protocol change that breaks an older Client would then land on `main` before anyone sees it; the Release suite runs in the merge queue (ADR 0061).
- **Skew tested on the last release only** (Stagehand) **or on a sample:** rejected. Docker's untested window decayed. The matrix's cost grows with each minor, and Suites names the levers that pay for it without dropping one.
- **chart-testing's `ct install --upgrade` for the Helm upgrade:** rejected. It upgrades from the chart on the git target branch, not from a release, and tests only charts changed against that branch. It passes with "Skipping upgrade test" on a SemVer-breaking version bump, which is any minor bump of a `0.x` chart, or when no previous revision exists.
- **A skew script written today:** rejected. It may call APIs the old Client lacks, and it checks today's expectations, not the old release's promise.
- **A version override in the binary** (Playwright's `PW_VERSION_OVERRIDE`): rejected. ADR 0059 keeps test-only controls out of the shipped binary, and the conformance harness can send any `hello`.
- **A time budget for refusals** (Stagehand's 5 seconds): rejected. "Refused in the reply to `hello`" checks the same thing and cannot flake.
- **Downloading old releases at test time** (containerd, without a checksum): rejected. ADR 0032 denies outbound traffic, so artifacts come from the pinned mirror, checked by digest and attestation.
- **Old-binary tests that skip when binaries are missing:** rejected. A test that passes because nothing ran breaks the no-flaky-test rule.

## Consequences

- **Amends ADR 0024.** Every Attached engine applies the Daemon's rule at `hello`: it accepts an SDK of its major with the same or an older minor, and refuses any other with the same clean error. The engine cannot tell how its SDK found it, so the rule does not depend on it. With the engine its SDK ships, the versions are equal; `GOODFETCH_ENGINE_PATH` (ADR 0030's hotfix path) is how they can differ. ADR 0024 carries a note where it says an Attached engine runs the exact version its SDK ships with.
- **Adds to ADR 0037:** ADR 0066 joins the rows of areas 1, 3, 4, 5, 6, 7, 9, 10 and 13, which build its tooling, its registry and refusals, the formats they own (the known-certificates store, the Clean-up rules manifest, Datasets and Exports, the plugin protocol, Plans, Schedules) and the group and Helm upgrades.
- **Adds to ADR 0030.**
  - **Format versions change only on `main`,** so only a minor or a major ships a new format version, never a patch. When `xtask release` prepares a patch, it compares each format's version and schema in the branch's `head/` with the `x.y.0` tag's and fails on any difference.
  - **A new release gate, Compatibility:** the Release suite's upgrade and skew checks pass on the release's own bytes.
  - **The release's pull request to `main`** also freezes the corpus from the release tag and appends the release, with its artifacts and its format versions, to `compat/releases.toml`.
  - **The format registry** joins the committed bundle.
- **Adds to ADR 0032.**
  - `compat/` joins the repository's top-level folders.
  - The pinned artifact mirror holds Goodfetch's own releases.
  - The Release suite gains the skew matrix, rolling upgrades, older engines, two majors and the Helm upgrade, as ADR 0061 already places tests that need released binaries.
- **Adds to area 1's spec** ([Spec: Repository, CI and release (V1 area 1)](https://github.com/goodfetch/goodfetch/issues/130)):
  - a sixth `xtask` command, `xtask compat`, with `write`, `check` and `freeze`;
  - two new steps in the release pull request: `freeze` from the release tag and the `compat/releases.toml` entry;
  - the patch check of format versions against the `x.y.0` tag;
  - the fetch step under the deny;
  - its tests, through Seam A, with a fixture workspace.
- **Adds to area 3's spec** ([Spec: Engine runtime (V1 area 3)](https://github.com/goodfetch/goodfetch/issues/213)):
  - the format registry and the compatibility functions in `goodfetch-protocol`;
  - the generated refusal cases;
  - the `hello` refusal before any other message.
  - Each area that owns a format adds its `head/` set and its scenarios.
- **Adds to [ADR 0063](0063-end-to-end-tests-follow-a-catalog-of-numbered-journeys-kept-in-the-repository.md):** the Journey helpers accept the engine binary to run, by path, so an old tag's Journeys can run against the current binary. Selecting a tag's variants by surface stays the "Test infrastructure" spec's command.
- **Assumed interfaces of other tickets:**
  - The SDKs' Scripted engine can answer `hello` with any version and Error code ([SDK and CLI test stack](https://github.com/goodfetch/goodfetch/issues/285)).
  - Crash injection can wrap `upgrade-files` and store migrations ([Deterministic simulation and crash testing for leases, fencing, groups and run state](https://github.com/goodfetch/goodfetch/issues/275)).
  - MCP revisions negotiated with external hosts belong to [MCP, framework adapter and Integration test stack](https://github.com/goodfetch/goodfetch/issues/286).
- **The "Test infrastructure" spec** builds:
  - `xtask compat`;
  - the artifact fetcher and verifier;
  - the generated refusal cases;
  - the group upgrade harness;
  - the generator of the Release suite's skew and upgrade jobs from `compat/releases.toml`.
