# SDKs and the CLI are tested against a Scripted engine and the binary of the same commit

Each SDK's hand-written runtime is unit-tested in-process against a **Scripted engine**: a stand-in that plays one script of protocol messages, from one corpus of scripts that a check validates against the committed JSON Schema bundle. Integration tests run the `goodfetch` binary built from the same commit, in both of each SDK's modes: an Attached engine and a Daemon for TypeScript and Python, the engine linked in-process and a Daemon for Rust. Journeys run the shipped binary, so Rust's run with a Daemon only. Process faults the binary can't produce (a refused `hello`, a crash mid-call, garbage on stdout) come from the same scripts played by a Rust executable. Every Client surface implements one declared Client conformance case list in its own runner. Installed packages are tested from a local registry and fresh environments. The CLI is tested through its binary with assert_cmd and insta, every `--json` output is validated against a schema generated from Rust types, and terminal-only behaviour is tested in a pseudo-terminal. Each SDK ships a public testing kit (a Scripted model and a test engine helper), and Goodfetch's own suites use it.

The owner asked for unit, integration and end-to-end tests through public interfaces, with every external dependency replaceable and the shipped artefacts tested. The SDKs are thin JSON-RPC Clients of a separate binary (ADR 0024), their protocol code is generated (ADR 0038), and `--json` output and exit codes are under semver (ADR 0030). Comparable projects do this:
- **Two ways to test an SDK over a separate process, mixed.** Stagehand v4's Python SDK and Pulumi test against a fake that speaks the real protocol, then smoke-test the installed package. Playwright's ports, Temporal and Dagger run a real engine, always pinned or built from the same commit.
- **Parity across languages.** Temporal's `features` runner and Pulumi's language conformance tests drive one shared definition into each language. Stagehand has no shared behaviour suite, but it tests that every registered method has generated models.
- **Installed packages from a local registry.** Playwright and Temporal serve their freshly built npm packages from one; Stagehand and LanceDB install the built wheel into a fresh environment.
- **CLI output in snapshots.** uv wraps assert_cmd with insta filters; Cargo snapshots its help.
- **Testing kits for users.** The Vercel AI SDK ships mock models in `ai/test`, Pydantic AI ships `TestModel`, Temporal ships a test server and Pulumi ships mocks.

Tool facts that decided between options: Vitest's `typecheck` mode is Experimental and its `Assertion` type breaks on TypeScript 7.0.2 (open [#11144](https://github.com/vitest-dev/vitest/issues/11144)); tsd bundles TypeScript 5.9; TSTyche supports TypeScript 7 only in a beta that refuses 7.0; expect-type's own CI type-checks its tests with `tsgo` from `@typescript/native-preview`, pinned to `7.0.0-dev.20260609.1`, a pre-release build of TypeScript 7 rather than a 7.0.x release, so it is the only one of the four tested against the TypeScript 7 compiler at all. anyio's default `anyio_backend` fixture silently drops trio when it isn't installed. insta-cmd had one release in two years. expectrl drives a pseudo-terminal on Linux, macOS and Windows (ConPTY); rexpect is Unix only.

Decided in [SDK and CLI test stack](https://github.com/goodfetch/goodfetch/issues/285) ([grilling record](https://github.com/goodfetch/goodfetch/issues/285#issuecomment-6152351756)), with the agent answering on the owner's delegation, on the facts of [Testing TypeScript and Python SDKs over a separate engine](https://github.com/goodfetch/goodfetch/issues/266) ([findings](https://github.com/goodfetch/goodfetch/blob/research/sdk-testing/rnd/research/2026-10-13-sdk-testing.md)) and [Rust test tooling in 2026](https://github.com/goodfetch/goodfetch/issues/263) ([findings](https://github.com/goodfetch/goodfetch/blob/research/rust-test-tooling/rnd/research/2026-10-13-rust-test-tooling.md)). It builds on ADRs 0061 (suites), 0062 (layout and test support), 0063 (Journeys), 0064 (no retries), 0065 (AI) and 0066 (upgrades). The rules every test follows are in `TESTING.md`.

## Decision

### Levels for an SDK

- **Unit tests** (Quick suite) test each module of the hand-written runtime through its interface, in one process. The engine side is an in-memory transport played by a Scripted engine script.
- **Integration tests** (Pre-merge suite) run the package against the real binary of the same commit, and against the Scripted engine as a separate process for faults the binary can't produce.
- **End-to-end tests** are the SDK variants of Journeys (`sdk-rust`, `sdk-typescript`, `sdk-python`; ADR 0063), against the real binary and the local Proving ground. ADR 0063 never lets a Journey use an engine linked into the test, so `sdk-rust` variants run with a Daemon only; `linked` is a mode of conformance cases and integration tests, never of Journeys.

### The Scripted engine

- **A Scripted engine plays one script:** the messages it expects from the Client and the messages it sends, engine-to-Client handler requests and events included. It fails the test on any message it did not expect and on any step left unused, and records every message.
- **A script can** answer `hello` with any protocol version or refuse it with any Error code, send any response or Error code, stream events under credits, call an SDK handler, stall (the SDK's own short timeout ends the wait), close the connection, write bytes that are not JSON-RPC, or exit with a code. This is the interface [ADR 0066](0066-upgrades-are-tested-from-a-frozen-corpus-and-skew-from-every-released-minor.md) assumes.
- **Scripts live once**, as files in `test-support/fixtures/engine-scripts/`. A Quick-suite check validates every message step of every script against the committed JSON Schema bundle, so a script the engine could never send fails there. Steps that write raw bytes, which are deliberately not JSON-RPC, are the only ones it skips.
- **Matching** is on the method and the canonical JSON of params. Request IDs are correlated by step, never written as literals.
- **The script format** is a Rust type in `goodfetch-test-support`, which holds each message as a plain JSON value, so the crate still depends on no Goodfetch crate (ADR 0062). `xtask codegen` emits its JSON Schema to `test-support/fixtures/engine-scripts/script.schema.json`, committed and drift-checked by `xtask codegen --check` like the bundle.
- **Players:**
  - `@goodfetch/test-support` and the Python `goodfetch-test-support` play a script over an in-memory transport, for unit tests;
  - `goodfetch-test-support` builds a `goodfetch-scripted-engine` executable that plays a script over stdio, a Unix socket or loopback TCP. It is an exception to ADR 0060's closed lists: a test-only executable the Simulation never runs, it opens its own stdio and sockets and writes its own stdout, and each such use carries `#[expect(clippy::disallowed_types, reason = "…")]` or `#[expect(clippy::disallowed_methods, reason = "…")]` naming ADRs 0060 and 0069. The TypeScript and Python SDKs reach it as an Attached engine through `GOODFETCH_ENGINE_PATH`, or as a Daemon through a runtime file in the test's Goodfetch home; the Rust client reaches it as a Daemon only.
    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#362](https://github.com/goodfetch/goodfetch/issues/362): an engine-path variable names an executable, which an SDK starts with its own arguments (`attached-engine`, as Collie's and Foxhound's executables take it), so a script cannot reach the Scripted engine on its command line that way. Started as `goodfetch-scripted-engine attached-engine`, it plays `scripted-engine/script.json` under the `GOODFETCH_HOME` of the environment map and records beside it, in `scripted-engine/record.jsonl`; no variable is added, since an SDK refuses an unknown `GOODFETCH_` variable (ADR 0083). `--script <file> --mode stdio` names a script directly. The JSON-RPC requests an engine sends a Client are not in the catalog yet, so the corpus check validates a `send` request as a JSON-RPC request only, and a `send` notification as one of the catalog's events, named by its event name.
    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#363](https://github.com/goodfetch/goodfetch/issues/363): `--mode socket` publishes the Scripted engine as a Daemon. It listens where ADR 0024 puts a Daemon, a `0600` Unix socket on macOS and Linux and loopback TCP on Windows, not on the Windows named pipe the ticket named, since ADR 0024 rejected named pipes for V1 and [#220](https://github.com/goodfetch/goodfetch/issues/220)'s Daemon, which Clients must find the same way, listens on TCP there. Its runtime file is plain JSON, `{"endpoint": {"unix": <path>} | {"tcp": <address>}, "token", "version", "pid"}`, at `<home>/<major>/daemon.json`, `version` being the Product version whose major names the folder (ADR 0031's note on #215), and the socket is `daemon.sock` beside it, or in a folder of its own under `/tmp` when that path is longer than the OS takes (104 bytes on macOS, which a test's home exceeds); #220 decides the real Daemon's names, and its test that the CLI connects to this file keeps the two in step. The token is `--token` (default `scripted-daemon-token`), matched only by the script's `expect`. A script ending with `exit` leaves the runtime file, as a crashed Daemon does; every other ending removes it and the socket. `--mode tcp` prints `{"address"}` for loopback port 0.
    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#172](https://github.com/goodfetch/goodfetch/issues/172): the conformance harness starts a Daemon target as a Product's `daemon start` starts its Daemon, `<executable> daemon launched`, and reads the runtime file the launched process prints once ready, so the Scripted engine also answers `daemon launched`: it plays `scripted-engine/script.json` under `GOODFETCH_HOME` in socket mode and prints its runtime file in place of `{"address", "runtime_file"}`. A `reply` answers the request the last `expect` of a request matched: an expected notification between them, such as that request's `$/cancel`, leaves it to answer, in every player and in the corpus check, so a script can end a cancelled call with `call_cancelled`.
- **The Rust client** in `goodfetch` keeps area 3's in-memory transport pair for its unit tests and uses `goodfetch-scripted-engine`, as a Daemon, for process faults.

### The real binary

- **SDK integration tests run the `goodfetch` binary built from the same commit.** Never a downloaded release, never a guessed path. The Rust crate's linked mode is the crate itself, of the same commit, so only its Daemon mode starts the binary.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each Product's SDK packages run against their own Product's executable of the same commit, and each runs the Client conformance cases and the completeness checks for its own Product's catalog.
- **The binary and the home reach the SDK through its environment map** (ADR 0062). The TypeScript and Python test-support fixtures build the map from `goodfetch-test-env`'s JSON description, with `GOODFETCH_ENGINE_PATH` and `GOODFETCH_HOME` set, and pass it in the SDK's environment-map option; the SDK starts an Attached engine with exactly that map as the child's environment. In Rust the map is the value given to the settings resolver (ADR 0059). No test sets a variable in its own process, and `vi.stubEnv` and `monkeypatch` stay banned.
- **Each test has its own Goodfetch home** from `goodfetch-test-env` (ADR 0062); a Daemon test starts its own Daemon there.
- **No process outlives its test.** The test-support fixtures record every engine, Daemon and handler process a test starts, and fail the test if one is alive after teardown. Vitest's `hanging-process` reporter runs in CI.

### Client conformance and parity

- **The Client conformance suite** is declared once in `conformance/clients/`. Each case has an ID, the capability it proves, the surfaces it applies to (`sdk-rust`, `sdk-typescript`, `sdk-python`, `cli`, and the MCP surfaces if [MCP, framework adapter and Integration test stack](https://github.com/goodfetch/goodfetch/issues/286) adopts it), and the Proving ground tasks or script it uses.
- **Its capabilities are the hand-written runtime's:** `hello` and the version rule; request correlation; `$/cancel` from `AbortSignal` or anyio cancellation; one error class per Error code; credits and backpressure; event resumption after a reconnect; file-backed bodies read locally and streamed; SDK handlers both ways; `workers=N`; Daemon discovery and dead-PID replacement; the Attached engine stopping with its Client; Experimental and deprecation warnings; the `run_moved` redirect (ADR 0055).
- **Each surface implements every case that applies to it in its own runner**, carrying the case ID the way ADR 0063 carries Journey IDs. Every case runs in both of its surface's modes, as named cases: `attached` and `daemon` for TypeScript, Python and the CLI (whose `--attached` runs the engine in its own process, ADR 0024); `linked` and `daemon` for `sdk-rust`, since only the Rust crate links the engine and it never starts an Attached engine. A capability that exists in one mode only, such as the Attached engine stopping with its Client, declares that mode.
- **A Quick-suite check fails** when a case has no implementation on a surface it applies to, or a test carries an unknown case ID.
- **Generated API completeness**, per SDK, in the Quick suite: every catalog operation has its async method in both SDKs, its sync method in Python and its method on the Rust client; every Error code has its error class; every event has its type; operations ADR 0011 keeps off agent surfaces are absent where they must be.
  > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): the same tests check each SDK's manifest of hand-written members: every catalog entry reaches a public member, a listed member carries its entry's doc text and markers, a line the generator could express fails, and a member with no entry must be spelled from the canonical words and form its line declares, two members of one receiver listed for one entry fail, and a hand-written member's words must be on the same receiver in every SDK that has it unless its line says why.

### Result documents

- **Each runner writes a case log for Client conformance cases**: one JSON Lines entry per case run, with the case ID, the capability, the mode, the platform and runtime, each check's result and the evidence (the oracle's answers, the scripted messages). The entry has no outcome field: the runner never sets an outcome. Its entry type is a Rust type in `goodfetch-protocol`, emitted into the JSON Schema bundle by `xtask codegen`, so `goodfetch-conformance` reads it and every writer is checked against one schema. A Vitest reporter in `@goodfetch/test-support` and a pytest plugin in the Python `goodfetch-test-support` write it; the Rust writer is a module of `goodfetch-conformance`, which `goodfetch`'s tests take under `[dev-dependencies]`, since `goodfetch-test-support` depends on no Goodfetch crate (ADR 0062).
- **`goodfetch-conformance`'s writer turns the case log and the declared case list into area 2's result document**, deriving each capability's outcome through `goodfetch-protocol`'s constructor (ADR 0063's "derived, never set"). A declared case absent from the log leaves its capability `unproved`.
- **Journeys keep ADR 0063's result documents.** Each Journey variant run writes its own `kind = "journey"` document through the Rust constructor or a TypeScript or Python helper tested against the shared outcome vectors; the case log is not used for them.

### Generated code and types

- **Generated code is type-checked by every checker users run:** `tsc` with `skipLibCheck: false`, pyright strict and mypy `--strict`.
- **Encoding and decoding are property-tested**, with hypothesis in Python and fast-check in TypeScript. Values in user-data positions (extracted Records, headers, metadata maps) get arbitrary keys, snake_case, camelCase and `__proto__` among them, and must come back unchanged; declared fields must round-trip between wire and SDK names (ADR 0038).
- **TypeScript type tests** are `*.test-d.ts` files using `expect-type`'s `expectTypeOf` and `@ts-expect-error`, compiled by `tsc --noEmit` against the built `.d.ts` with `skipLibCheck: false`. An unused `@ts-expect-error` is an error.
- **Python type tests** are files under `tests/types/` using `typing.assert_type`, with `# type: ignore[code]` on lines that must fail. pyright strict runs them with `reportUnnecessaryTypeIgnoreComment = "error"`, and mypy runs them with `--strict`, whose `--warn-unused-ignores` reports an unused ignore.

### Python's three APIs

- **The test-support pytest plugin defines `anyio_backend`** over `asyncio` and `trio` explicitly. If trio does not import, the session fails.
- **Every Client conformance case runs three ways:** async on asyncio, async on trio, and through the generated sync API.
- **The sync API's own unit tests** cover its loop thread starting once and stopping at close, its documented error when called inside a running event loop, a handler running while a sync call is pending, `KeyboardInterrupt` cancelling the call in flight, and no thread left after close.
- **Free-threaded builds run the whole suite** with `PYTHON_GIL=0`, and the session fails if `sys._is_gil_enabled()` is true. The sync API's unit tests also run under pytest-run-parallel. The Release suite runs them on every Linux platform (ADRs 0032 and 0061); a nightly-only job runs them on macOS and Windows (ADR 0032's nightly tier).

### TypeScript runtimes

- **Vitest runs the TypeScript SDK's unit, integration and conformance tests on Node**, with the `forks` pool.
- **Smoke scripts** (`sdks/typescript/smoke/*.mjs`) import the installed package and use only `node:assert`. A Vitest test per runtime, script and mode spawns each one and checks its exit code. Area 1's deployment-target smoke runs reuse these scripts.
- **Bun and Deno 2 run them in both modes**, an Attached engine over stdio and a Daemon, since the default mode is the one that spawns a process and Bun's `node:child_process` has known gaps (SDK findings §2.4). There the scripts cover each Client conformance case whose capability depends on the runtime: starting and stopping the Attached engine, framing over stdio and the socket, `$/cancel`, credits, file-backed bodies, SDK handlers and `workers=N`. Each script declares the case IDs it covers, and the spawning Vitest test writes their entries to the case log with the runtime, so the result document records each runtime.
- **The edge runtimes run them against a Daemon only:** `workerd` (Miniflare) for Cloudflare Workers, and Vercel's edge runtime. They cannot start a process, and ADR 0049 makes them Clients of a Daemon. Deno Deploy has no emulator of its own; ADR 0049's row covers it with Deno against a Daemon, which is Deno 2's `daemon` run. So ADR 0024's "every supported runtime" holds for the edge runtimes in the Daemon mode, the only one they support.

### Installed packages

- **npm:** Verdaccio serves the packed root and platform packages with no uplink, under the outbound deny. npm, pnpm, Yarn, Bun and Deno (`npm:` specifier) install them into temporary projects whose path holds a space and a non-ASCII character, then run the smoke scripts, which assert that the installed version is the packed one.
- **Release-age gates:** packages published to Verdaccio in the same job are minutes old, so the gates of pnpm 11 and new Yarn projects (ADR 0024) hold them back. Each manager's install runs with its gate on (the default for pnpm 11 and new Yarn projects, turned on at one day for every other manager that offers a gate) and passes it through ADR 0030's exclusion snippet for that manager. The harness and the release notes read the snippets from one committed source, so the tested text is the published text. One run per manager without the snippet must not install the packed version, which pnpm 11 would otherwise replace silently with an older one. So the npm-side snippets (npm, pnpm, Yarn, Bun and Deno) are tested on every release. ADR 0030's uv snippet is not: the PyPI runs install with `--no-index`, where no release-age gate applies.
- **Optional dependencies and package checks:** an install with `--omit=optional` must fail at first use with Goodfetch's error naming the cause and the fix (ADR 0024). `publint`, `@arethetypeswrong/cli` and the type tests run against the packed tarball.
- **PyPI:** each wheel installs into a fresh environment with `uv pip install --no-index --find-links` and with `pip`, and the package's `tests/integration` runs against it unchanged. Linux runs in a glibc and an Alpine (musl) container.
- **crates.io:** `cargo package` builds the crate, and a temporary consumer project builds and runs against the packaged sources.
  > Amended by [ADR 0094](0094-both-products-are-released-and-signed-together-and-each-test-runs-on-collie-unless-it-needs-foxhound.md): each Product's packages install this way, and one environment per package manager also installs both Products' packages and runs both executables, proving that they collide nowhere (ADR 0090).

### The CLI

- **Tool:** the binary runs under assert_cmd and is snapshotted with insta, through a helper in `goodfetch-test-support` that applies the cleared environment and the shared filters. One snapshot holds stdout, stderr and the exit code of one invocation.
- **`--json`:**
  - every `--json` output is a type in `goodfetch-protocol`, emitted in the JSON Schema bundle. A command generated from an operation outputs that operation's result; hand-written commands (`daemon start`, `config explain`, `usage`) get their own types;
  - each command's test validates stdout against its schema with the `jsonschema` crate, checks that stdout holds exactly that document (or only JSON Lines of the command's declared event type), and snapshots it;
  - a deprecated and an Experimental command run with `--json` still give valid stdout: warnings, hints and the age notice go to stderr only.

    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#1174](https://github.com/goodfetch/goodfetch/issues/1174): a command that fails prints `goodfetch-protocol`'s `CommandFailed`, `{ "error": { code, group, retryable, message, operation, …details } }`, `operation` being the canonical name the command called (`run.finish`); the bundle names it once as `command_failed` beside `outputs`, which lists only the hand-written commands, since a generated command prints its operation's `result`. Its exit code is the code's own row, else its group's row, which `ErrorGroup::exit_code` holds. A generated command's human output is the result's fields one per line, `name: value`, values other than text as JSON, an opener's the new ID alone; a failure prints its message, then `code`, `retryable` and `fix` on lines of their own, on stderr.

    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-22, [#1216](https://github.com/goodfetch/goodfetch/issues/1216): `npx @goodfetch/collie` (ADR 0090's bin) fails as the executable does when it cannot run it: `engine_not_found`, or `setting_invalid` for an empty `GOODFETCH_COLLIE_ENGINE_PATH`, prints `CommandFailed` under `--json` and the message with its `code`, `retryable` and `fix` lines otherwise, and exits with the code's row, else its group's (`8` for `engine_not_found`), from the table `xtask codegen` writes into Collie's TypeScript client package. Since such a failure precedes any call, `CommandFailed`'s `operation` is optional: present whenever the command called an operation, absent only when it failed before calling one.

    > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#1180](https://github.com/goodfetch/goodfetch/issues/1180): a sequence's command requires `--follow` and prints each item the call sends as it arrives: each event of a `$/events` batch (`EventEnvelope`), or the notification's params as one item (`Chunk`), one JSON object per line under `--json`, `name=value` fields on one line otherwise, the call's own `id` left out; the call's final result is not printed, and the command ends when the call does. The CLI grants 64 credits up front and one more per item printed. An interrupt (`SIGINT`) sends a cancellable call's `$/cancel`, waits for the engine's answer and exits `130` without printing the caller's own `call_cancelled`; a second interrupt, or one during a call that cannot be cancelled, exits `130` at once. The engine records each `$/cancel` that stops a call in flight as a dispatch record (`cancel received`), which is how a test sees that the cancellation reached it. A deprecated command's warning and its `--help` share one text: `Deprecated since protocol <since>, and removed no earlier than the next major: <note>`, the note naming the replacement (ADR 0030).

    > Note (agent decision, on a default, not read by the owner), 2026-10-30, [#1512](https://github.com/goodfetch/goodfetch/issues/1512) and [#1513](https://github.com/goodfetch/goodfetch/issues/1513) (deep review, 611-1, 611-3, 611-6, 611-10 and 611-11): without `--follow`, `run records` reads what was committed when it began: it first reads the Dataset's last committed number with `dataset.page` (`limit` 1), then calls `run.records` with that number as its new `through`, which answers once it sent every Record through it, so on a live Run the command ends rather than follow the Run; given `--through`, it calls `run.records` through that number at once. It prints each Record as it arrives and keeps none: under `--json` the array is written as it goes, `[` before the first Record and `]` once the call ended, however it ended, so a failure or an interrupt after the first Record still leaves one JSON array on stdout, the failure going to stderr alone as one `CommandFailed` line, as after `crawl start`'s Run ID. A command that takes a stream from stdin (`run add-seeds`) reads it on a tracked blocking thread into a bounded channel, awaited beside the interrupts, and sends each line as soon as it is read and a credit allows, so an interrupt ends it while stdin stays open; a line that is not UTF-8 ends the stream there and the command fails as a usage error, `2`, naming the line's number. `crawl start` takes no `--datasets` and has its own help, since a code-free crawl declares its one Dataset, `pages`, itself; a seeds file whose seeds would pass the engine's message limit starts the crawl with the URLs given and as many of its seeds as fill half that limit, then sends the others through `run.add_seeds` on the same Connection, a batch per grant of credits. An error whose `id` is null, the engine's answer to a message it could not read (`message_too_large`), ends the command in flight with that error rather than leave it waiting. An optional boolean param's flag takes a value, `--wall true` or `--wall false`, and leaves the param out when absent.
- **Exit codes** come from one table in `goodfetch-protocol` mapping each Error code to an exit code. An in-process unit test (Quick suite) checks that the table maps every Error code. Through the binary (Pre-merge suite), one rstest named case per exit code (ADR 0062) reaches it and checks the code.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-22, [#1188](https://github.com/goodfetch/goodfetch/issues/1188): the table is `goodfetch-protocol`'s `cli::exit_code_table()`, built from each Error code's own `exit_code`, each group's `ErrorGroup::exit_code` and the CLI's other outcomes (`success`, `usage`, `run_stopped`, `verdict_not_verified`, `interrupted`, `terminated`); the catalog file lists it as `exit_codes`, `{name, product, code, description}` by code, whose names are the `exit:` Features, and the executable's `exit_codes` module (`goodfetch-collie`'s `executable::exit_codes`) maps a failure, a Run report or a signal to its row. No exit code has two rows, so `console_port_in_use`, which #811 gave `12`, `browser_host_outdated`'s row, takes its group's, `8`. A command whose operation answers a Run report (`run finish`, `abort`, `pause`, `migrate`) exits by how the Run ended and takes `--require-verified`; a Run that ended `stopped` exits `20` whatever its Verdict, since a stopped Run's Verdict is not its last and a resume goes on with it, and `21` is for a Run that ended otherwise. `SIGTERM` cancels the call in flight as `SIGINT` does and exits `143`; `CTRL_BREAK_EVENT` exits `130`. The cases that reach an Error code's row through the binary play the Scripted engine as a Daemon answering `config explain --daemon` with the code, from the corpus's one script `daemon/cli-call-failed.json`, which each case gives its code and group; the model group's case names a code no entry declares, since no model code is declared yet, which also shows that a code this executable does not know takes its group's row.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-28, [#1183](https://github.com/goodfetch/goodfetch/issues/1183) (step 7 review, findings 593-608-611-1 and -2): a Daemon that refuses a command's `hello` by Product (`not_in_product`) or by protocol version while it cannot hand over ends a command that does not fall back to an Attached engine (under `--daemon`, `config explain --daemon` and every Client the executable's `daemon` commands open) with exit `11`, `protocol_version_unsupported`'s row, whichever code refused it, since the same `daemon restart` in the refusal's `fix` ends both, as #1183 says; the refusal keeps its own code, so this is the one case where a failure exits by a row other than its code's (`exit_codes::DAEMON_REFUSED`). A `not_in_product` answered to a call, not to `hello`, keeps its row, `10`. A Connection to the Daemon that drops before a call is answered fails every command with `connection_lost`, which exits its group's row, `8`, `config explain --daemon` and the `daemon` commands included.
  > Note (accepted by the owner on 2026-10-28), 2026-10-29, [#1183](https://github.com/goodfetch/goodfetch/issues/1183) (deep review, 608-O6 and 563-O4): with neither flag, a Daemon that refuses `hello` by Product or version while it cannot hand over ends a command whose value outlives it (`run start`, `crawl start`) with that refusal and its `fix`, exit `11`, as under `--daemon`; only a command with no value outliving it falls back to an Attached engine, since one would stop the Run it printed the Run ID of. `audit verify` exits `22`, the outcome row `audit_log_not_intact`, for a log or an export that does not verify, as `sha256sum -c` exits non-zero on a mismatch, and prints what it found as before.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-29, [#1183](https://github.com/goodfetch/goodfetch/issues/1183), [#1203](https://github.com/goodfetch/goodfetch/issues/1203) and [#1513](https://github.com/goodfetch/goodfetch/issues/1513) (deep review, 608-1 to 608-7, 611-2, 611-4 and 611-5): every failure prints as `CommandFailed` through the executable's `output::fail` (`goodfetch-collie`'s `executable::output`), the hand-written commands' (`daemon *`, `browser install|clean`, `upgrade-files`, `config explain`, `console`, `usage raise`, `certs`, `audit`) and a failure before any call included, whose `operation` is then absent; only `daemon launched`, `daemon run` and `attached-engine`, whose output is a log or the protocol, still log it. A command that reaches no Daemon (nothing answers where the runtime file or `GOODFETCH_URL` says, a remote Daemon that closes the Connection at `hello` as it does for a token it does not take, or a runtime file that cannot be read) fails with the new Error code `daemon_unreachable`, Unavailable, retryable, exit `8`, with a `fix`; a missing `GOODFETCH_TOKEN`, a `GOODFETCH_URL` that is no `ws://` loopback address and a deployment variable the executable cannot take fail with their setting code (`setting_invalid`, exit `3`) before any engine starts; an Attached engine that closes before it answers is `internal_error`, exit `1`. `upgrade-files --from` naming no major is a usage error, `2`. The published table gives the exit-`11` exception as the description of `protocol_version_unsupported`'s row (`cli::REFUSED_AT_HELLO`), so that no exit code has two rows. A command that answers a Run report exits by the row of the report's `error` when it carries one, and a Run that ended `failed` without one by the `internal` row; `crawl start --follow` does so too. Once `crawl start` printed the Run ID, a later failure goes to stderr alone, as one `CommandFailed` line under `--json`, naming the call in flight (`run.progress.read` or `run.report`), so stdout holds the Run ID alone. `run export --out -` stops `export.stream` with `$/cancel` at the first write standard output refuses: a closed pipe ends the command quietly, `0`, and any other failure exits `14`, `file_write_failed` of side `program` with no path. The Scripted engine's `daemon/cli-crawl-follow-dropped.json` and `daemon/cli-run-export-stopped.json` play those two Daemons.
- **Human output** is snapshotted under `NO_COLOR=1`, a fixed `COLUMNS`, `TERM=dumb` and a fixed locale. The whole command tree's `--help` is one snapshot, rendered in-process from clap's `Command` (Quick suite); one `tests/it` case checks that the binary prints the same text. A unit test calls clap's `Command::debug_assert`.
- **Terminal behaviour is tested in a pseudo-terminal with expectrl:** colour and progress appear only on a terminal, and a person-only prompt (`goodfetch certs accept`, ADR 0042) accepts an answer from a terminal and refuses with its Error code when stdin is not one.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-20, [#367](https://github.com/goodfetch/goodfetch/issues/367): `pty(&env, executable)` runs on expectrl's own pseudo-terminal on Linux and macOS and on ConPTY on Windows, with the test's map, `COLUMNS=100`, `TERM=xterm-256color` and no `NO_COLOR`; it gives one transcript (stdout and stderr share the terminal) and records its command as `cli` does. On Windows it waits for the exit, then closes the pseudo-console while a second handle reads the rest, since ConPTY holds its output open until then. ADR 0073's colour properties are `ColourProperty` cases: "stripped" removes every escape sequence from both runs, so a pseudo-console's own cursor sequences cancel out; colour is an SGR sequence with a parameter other than 0; `--color always` is added after the command's arguments, where clap takes a global flag. The locale cases, `Cli::with_locale` and `Cli::with_time_zone`, take only the shared table's values (its BCP 47 tag, `tr-TR`, sets `LANG=tr_TR.UTF-8`) and set `LANG` and `TZ` in that child's map alone; `LC_ALL` stays unset, so `LANG` governs every category in the cleared map.

  > Note of 2026-10-22 (spec #326's review, SP-1): the Windows sentences above are unverified. The ConPTY path compiles (`cargo check --target x86_64-pc-windows-gnu -p goodfetch-test-support --tests`, on the Linux server), but no Windows or macOS host has run it yet: the Release suite's `windows-x64` cell runs it first, and its `macos-arm64` and `macos-x64` cells on the owner's machine on `main`. `just release-ci` names each cell not green on the commit, so a skipped one shows.
- **Interrupts:** a running Crawl sent `SIGINT` (Unix) or `CTRL_BREAK_EVENT` (Windows) checkpoints and exits with its exit code; a second interrupt stops at once.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-30, [#1513](https://github.com/goodfetch/goodfetch/issues/1513) (deep review, 611-O1 and 611-9): "a second interrupt stops at once" means the command stops, as the #1180 note above says: the second interrupt exits `130` at once, and on a Daemon the Run still stops with its Checkpoint through the first interrupt's `run.stop`, so it stays resumable by its Run ID. The command keeps its signal listeners for its whole run, so an interrupt that arrives while it waits on `run.stop` is not lost. The deep review asked to hold the Run's stop open with a page the Proving ground answers slowly, but a real engine's `run.stop` abandons the attempts in flight and answers within milliseconds, so no page holds it open: the test plays the Daemon on the Scripted engine instead, from `daemon/cli-crawl-follow-stop-held.json`, which holds `run.stop` unanswered, sends the second interrupt once the first one's `run.stop` is in flight, and checks that the command exits `130` within 10 seconds; the first interrupt's own test shows that `run.stop` stops the Run with its Checkpoint.
- **Both modes:** every test of a command that runs the engine has two named cases, `attached` and `daemon`, which must match one snapshot.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#366](https://github.com/goodfetch/goodfetch/issues/366): the CLI helper's `Mode::Daemon` starts the executable's own Daemon in the test's home for that one run (as `daemon launched --keep-alive`, like #342's `Daemon::start`), adds `--daemon`, ADR 0024's forcing flag, after the test's arguments, and stops the Daemon with `daemon stop` once the command ended, failing when it still runs or left its runtime file; `Mode::Attached` adds no flag, since the CLI has no `--attached` yet and a test's home has no Daemon, so the command runs in its own process. `json(type)` names the output's type in the bundle's `$defs` (`SettingsExplanation`), not the command, so the same check serves JSON Lines of an event type (`json_lines`); stdout is snapshotted as the documents pretty-printed. Corrected on 2026-10-22 (spec #326's review, ST-4): that snapshot cannot tell the modes apart by layout, key order or number spelling, so the one snapshot shared by `attached` and `daemon` comes with a test comparing the printed bytes of both modes (`CliJson::printed`).
- **As a Client:** the Scripted engine, run as a Daemon, gives the CLI a refused protocol version (the `goodfetch daemon restart` hint), a dead PID in the runtime file and a connection dropped mid-command.

### The testing kit users get

- **Each SDK ships a testing kit**, public and under semver (ADR 0030): `goodfetch::testing` behind `goodfetch`'s `test-util` feature, the `goodfetch/testing` subpath export, and the `goodfetch.testing` module. This settles what `test-util` holds.
- **It holds:**
  - **a Scripted model** in its SDK-handler form (ADR 0033): registered as the Model provider, it answers call *n* with reply *n* (text, a tool call, structured output, a stream or a provider error), fails on a call beyond its script and on replies left unused, records every request, and reports Usage from its script;
    > Amended by [ADR 0105](0105-a-programs-tests-replay-a-response-recording-in-a-test-engine-that-reaches-no-site.md): a call beyond its replies raises `scripted_model_exhausted`, closing the test engine with replies left raises `scripted_model_unused`, and a retryable error reply is retried as a provider's, taking the next reply. In Rust the kit answers its `model_requests` stream on the connection's own runtime, so the SDK-handler path is the one tested in every SDK.
  - **a test engine helper:** an engine in a temporary Goodfetch home with a cleared environment, `offline` on, the caller's `resolve` map and short durations, removed when the test ends. In TypeScript and Python it is an Attached engine, and the cleared environment is the environment map the helper passes to the SDK; in Rust it is the engine linked in-process, and the cleared environment is the map given to its settings resolver. It needs the `goodfetch` binary only for what the crate always runs from it (ADR 0024).
    > Amended by [ADR 0105](0105-a-programs-tests-replay-a-response-recording-in-a-test-engine-that-reaches-no-site.md): the helper is the value `TestEngine`, with `connection`, `runHandler` and `runHook`. Every Run it starts that names no Response recording replays an empty one, so no request reaches a site unless a Run records; it reads no project file unless the test names one; the hosts its `resolve` setting maps to loopback are allowlisted; and it finds browsers and its Product's executable where the user's other engines do, reading the browser cache of the caller's home without writing to it, through `connect()`'s environment map, which its `env` option replaces. The kit also holds `fakeError`, and in Rust a `fake` constructor on each `#[non_exhaustive]` result type.
- **Goodfetch's SDK suites script models only through this kit** (the scripting ADR 0065 leaves to SDK suites), so the shipped kit is what they test.
- It never holds Goodfetch's own helpers, `Clock::paused` or `Entropy::seeded` (ADR 0062).

## Considered Options

- **The real binary only:** rejected. It can't refuse `hello`, crash mid-call or write garbage on demand without a test-only control, which ADR 0059 rules out, and the Quick suite starts no process.
- **A hand-written fake per SDK** (Stagehand, Pulumi): rejected. Three fakes drift from each other and from the engine; one validated script corpus can't.
- **One Rust fake process only:** rejected. The Quick suite starts no process (ADR 0061), so unit tests need an in-process player.
- **Responses validated by each player at load:** rejected. TypeScript has no generated runtime validators (ADR 0038 types only), so one Rust check over the corpus does it once.
- **One Rust harness driving per-language snippets** (Temporal's `features`, Pulumi): rejected. ADR 0032 already runs SDK cases in each surface's own runner; the declared case list and its check give the parity.
- **Each language writing the conformance result document itself:** rejected. The rule that an unreached capability is `unproved` would be written three times. Journeys differ: ADR 0063 has each runner write its document through helpers tested against shared outcome vectors.
- **One shared Daemon for all SDK tests:** rejected. ADR 0059 gives each test its own Goodfetch home.
- **Vitest's `typecheck` mode, tsd or TSTyche for type tests:** rejected today. The first breaks on TypeScript 7.0.2, tsd is pinned to 5.9, TSTyche's TypeScript 7 support is a beta that refuses 7.0. TSTyche is reconsidered once it supports the pinned TypeScript.
- **pyright alone for Python type tests:** rejected. It leaves unused ignores silent by default; mypy users need the types right too.
- **anyio's default `anyio_backend`:** rejected. It drops trio silently when trio doesn't import.
- **Each runtime's own test runner for Bun and Deno** (Anthropic's ecosystem tests): rejected. Bun's `node:test` is partial and `bun test` is not Vitest; plain scripts spawned from Vitest run the same on every runtime and report through one runner.
- **Installing the npm tarball directly:** rejected. It can't resolve the per-platform packages in `optionalDependencies` the way a registry does for users.
- **hypothesis-jsonschema for property tests:** rejected. Its last release was in February 2024.
- **insta-cmd, trycmd or snapbox for the CLI:** rejected. insta-cmd had one release in two years; trycmd and snapbox add a second snapshot format beside insta.
- **`--json` checked by snapshots only:** rejected. A snapshot shows a change; only a schema from Rust types puts `--json` into ADR 0030's breakage check.
- **rexpect for pseudo-terminal tests:** rejected. It is Unix only.
- **No testing kit for users, or one in Rust only:** rejected. Users of the AI SDK, Pydantic AI, Temporal and Pulumi get one; ADR 0011 promises parity across SDKs.

## Consequences

- **Changes `STYLE.md`.** "mypy checks a small file that exercises the public API" becomes mypy `--strict` over the generated code and the type tests; "a smoke suite of the built package on Bun and Deno 2" becomes smoke scripts of the installed package on Bun, Deno 2 and the edge runtimes. The rules live in `TESTING.md`.
- **Adds to ADR 0038:** every `--json` output is a type in `goodfetch-protocol` emitted in the JSON Schema bundle, and one exit-code table maps Error codes to exit codes. ADR 0037's amendment rule carries this to every area.
- **Adds to ADR 0030:** the testing kits (`goodfetch::testing`, `goodfetch/testing`, `goodfetch.testing`) are public API under semver. The API breakage checks cover them: cargo-semver-checks covers `test-util`'s `goodfetch::testing`, the API Extractor report the `goodfetch/testing` entry point, and `griffe check` the `goodfetch.testing` module. The diff of the Operation catalog and settings schema also diffs the bundle's `--json` output types, those of hand-written commands included. The installed-package runs test the npm-side release-age exclusion snippets on every release, read from the same committed source as the release notes; the uv snippet stays untested.
- **Adds to ADR 0032:** `conformance/clients/` holds the Client conformance case list; Verdaccio serves packed npm packages to the installed-package runs. The merge queue's runtimes, which ADR 0032 and ADR 0061 run on Linux, gain the oldest and newest Node line and CPython on every other platform, and Bun and Deno 2 there too through the smoke scripts. Free-threaded Python stays in the merge queue on every Linux platform, and on macOS and Windows in ADR 0032's nightly tier, as a nightly-only job.
- **Changes ADR 0032's conformance harness:** for Client conformance cases, the SDK and CLI runners (and the MCP runners, if [MCP, framework adapter and Integration test stack](https://github.com/goodfetch/goodfetch/issues/286) adopts the case list) write a case log, and `goodfetch-conformance`'s writer turns it into the result document, so every surface still yields the same result document. Journeys keep ADR 0063's writers. An amendment note marks the sentence.
- **ADR 0024's coverage rule holds for the edge runtimes** in the one mode ADR 0049 gives them, a Daemon; nothing in ADR 0024 changes.
- **Adds to ADR 0062:** the TypeScript and Python SDKs' replaceable environment map, which ADR 0062 left to this decision, carries `GOODFETCH_ENGINE_PATH` and `GOODFETCH_HOME` in tests and becomes an Attached engine's whole environment; `goodfetch-test-support` also builds `goodfetch-scripted-engine` and defines the script format; the two test-support packages hold the in-process players, the TypeScript and Python case-log writers and the `anyio_backend` fixture; `test-support/fixtures/engine-scripts/` holds the corpus.
- **Amends ADR 0060:** `goodfetch-scripted-engine` joins the closed list of places allowed to open sockets and stdio outside `transport`, and is the one writer to stdout beyond `STYLE.md`'s three, each use under an `#[expect]` naming ADRs 0060 and 0069. ADR 0060 carries a one-line note, and `STYLE.md` is edited in place.
- **Adds to ADR 0065:** SDK suites script models through the testing kit's Scripted model.
- **Settles the interface ADR 0066 assumes:** the Scripted engine answers `hello` with any version and Error code.
- **Changes area 1's spec** ([Spec: Repository, CI and release (V1 area 1)](https://github.com/goodfetch/goodfetch/issues/130)): the release jobs' smoke installs gain the local-registry and fresh-environment runs above; the deployment-target smoke runs for edge Clients reuse the SDK smoke scripts; the nightly gains the free-threaded job on macOS and Windows.
- **Changes area 2's spec** ([Spec: Proving ground and conformance (V1 area 2)](https://github.com/goodfetch/goodfetch/issues/152)): the harness builds a Client conformance result document from a case log another runner wrote, deriving the outcomes through `goodfetch-protocol`'s constructor. Assumed by [`goodfetch-conformance` tracer: the harness, the result document and a self-test suite](https://github.com/goodfetch/goodfetch/issues/169).
- **Area 11's spec** (Client surfaces) writes the Client conformance cases, the testing kits, the `--json` types, the exit-code table and the SDKs' environment-map option.
- **Adds to `goodfetch-protocol`:** the case-log entry type, emitted into the bundle; `goodfetch-conformance` gains the Rust case-log writer.
- **ADR 0037's area table lists this ADR** for areas 1 (Repository, CI and release), 2 (Proving ground and conformance) and 11 (Client surfaces).
- **The "Test infrastructure" spec** builds: the script format and its validation check, the three players, `goodfetch-scripted-engine`, the case-log writers and the case-list check, the process-leak check, the CLI helper and its filters, the Verdaccio and fresh-environment install harness, and the matrix jobs.
