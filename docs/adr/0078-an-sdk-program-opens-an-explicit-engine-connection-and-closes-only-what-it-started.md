# An SDK program opens an explicit engine connection and closes only what it started

A program reaches Goodfetch through one value it opens and holds: an engine connection, `Goodfetch`, made by `connect()`. Everything else (Runs, Sessions, Pages, borrows) hangs from it in a tree, and each value closes its children and nothing it did not start. The SDK is a guest in the program: many connections per process, nothing done at import, no signal handler, logs only through the host's logging. Competitors fail here more than anywhere else in their lifecycle: Scrapy's `ReactorNotRestartable` (54 Stack Overflow questions, 228 votes), Browser Use killing a browser it was handed, Playwright's logs that cannot reach Python's `logging` (#6465, +82), and Rust drivers whose `Drop` blocks or panics. Decided in [Entry points and lifecycle](https://github.com/goodfetch/goodfetch/issues/465), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), on the evidence of the [research on competitors' APIs](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/2026-10-14-consumer-api.md) (pain 4; [browser drivers](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/browser-drivers.md) P3, P12 and Rust P1, P7; [crawl frameworks](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/crawl-frameworks.md) §6.1 and §6.18; [AI browser automation](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/ai-browser-automation.md) §2.1, §2.2 and §6 rows 5 and 17) and of the [SDK design guidelines research](https://github.com/goodfetch/goodfetch/blob/research/sdk-design-guidelines/rnd/research/2026-10-14-sdk-design-guidelines.md) (§1.2, §1.5, §3.1, §4.1). Principles are cited by their IDs in [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md). Import paths stay placeholders until [Goodfetch products: Collie and Foxhound as separately installable products](https://github.com/goodfetch/goodfetch/issues/447) settles them.

## Decision

### The entry point

- **One explicit async factory.** TypeScript `await Goodfetch.connect(options?)`, Python `AsyncGoodfetch.connect(...)` and `Goodfetch.connect(...)` (sync), Rust `Goodfetch::connect(options).await`. It starts or finds the engine and finishes `hello` before it returns, so a missing binary or a refused version fails there, never at some later first call (G6). Collie and Foxhound are reached from the connection (`gf.collie`, `gf.foxhound`) with no I/O (G2). The name follows `OpenAI` and `Stagehand` (S3); `Engine` would mislead, since closing it never stops a Daemon, and `Client` is the glossary's whole program. The Python pair follows Stainless's `OpenAI`/`AsyncOpenAI`; how the sync API runs is [Concurrency model per language](https://github.com/goodfetch/goodfetch/issues/468)'s (ADR 0081).
  > Amended by [ADR 0084](0084-goodfetch-ships-two-products-collie-and-foxhound-from-one-repository-and-foxhound-contains-collie.md): Collie and Foxhound are Products installed apart, so a program that installed only Collie has no `gf.foxhound` to reach. Each Product's SDK structure and entry point are decided in [Protocol, Operation catalog and SDKs across two products](https://github.com/goodfetch/goodfetch/issues/458), and the names (`Goodfetch`, `gf.collie`, `gf.foxhound`) in [Product names, packages, executables and version line](https://github.com/goodfetch/goodfetch/issues/457).

  > Amended by [ADR 0090](0090-products-are-named-goodfetch-collie-and-goodfetch-foxhound-and-share-one-product-version.md): the connection is named after its Product, for the reason above: `Collie` from `@goodfetch/collie` in TypeScript, `Collie` and `AsyncCollie` from `goodfetch_collie` in Python, `goodfetch_collie::Collie` in Rust (with `Collie::scope` and `goodfetch_collie::blocking`), and `Foxhound` likewise. `gf.collie` and `gf.foxhound` name nothing; the loggers and `tracing` targets below keep `goodfetch`.

  > Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): the connection is the Product, with no `collie` or `foxhound` property, so `gf.collie.start(…)` becomes `collie.start(…)`. A Foxhound connection carries every member of a Collie connection under the same names, plus its own, and the values below either (Runs, Sessions, Pages, errors) are the same types, from each language's Collie client package. The connection's `engine` value also reports the engine's Product and Product version.
- **Which engine.** An `engine` option: `auto` by default, which follows ADR 0024 (a Daemon when one is configured or running, otherwise an Attached engine; in Rust, the linked engine), or `attached` (TypeScript and Python), `linked` (Rust), `daemon`, or an address with a token for an Exposed Daemon or Goodfetch Cloud. `gf.engine` reports the kind reached, the engine version and the protocol version, and the choice is logged at info (G6). Whether environment variables may set it is [Settings in code](https://github.com/goodfetch/goodfetch/issues/470)'s.
  > Amended by [ADR 0083](0083-a-program-sets-settings-in-one-typed-option-explicit-values-beat-the-environment-and-no-value-is-silently-ignored.md): the environment sets the engine only through `GOODFETCH_URL`, which fills `engine` when the code leaves it at `auto`; the connection's other settings go in its `settings` option.

  > Amended by [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): `gf.engine` also reports the engine's Product and Product version, from the engine's reply to `hello`.

  > Amended by [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md): `auto` also runs the engine it would run with no Daemon, with a warning, when the running Daemon refuses the connection by Product or protocol version and cannot hand over to its major's pick; `daemon` fails at connect.
- **No one-call helper here.** G2 allows a helper that connects, does one task and closes. A verb's own ticket may add one only when a golden scenario shows it earns its place, its docs say it starts an engine, and it is built on `connect()` (S2).

### What a program holds

- **Connection → Run → Session → Page.** The Run is always a value the program opens (`gf.collie.start(…)`, a crawl in Foxhound), never created behind a Page, because Limits, Usage, the Run trace and Checkpoints hang from it (G2, S2). The verbs that start and resume a Run are [The Run in code](https://github.com/goodfetch/goodfetch/issues/478)'s (ADR 0102); whether a Run has a default Session is [Sessions, logins, Human pause and secrets in code](https://github.com/goodfetch/goodfetch/issues/476)'s; pages, contexts and frames as values are [Collie's page API](https://github.com/goodfetch/goodfetch/issues/472)'s (ADR 0085).
  > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): `run.newPage()` opens pages in the Run's default Session, which its first call opens with the Run's settings and every later call shares; `page.session()` reaches it, and a Session of its own opens with `run.newSession({ source })`.
- **`borrow` is called on the Run.** `run.borrow(page)` returns a Goodfetch Page and `run.borrow(browser)` a Session in the browser's default context, both on ADR 0056's `client_browser` source. Closing the returned value, or the Run, ends the borrow; the user's page and browser are never closed (G4). ADR 0056's relay, its refusals and its rules are unchanged. The Rust crate keeps `cdp_url`.

### Closing

- **Every disposable value** has the language's scoped form and a first-class `close()`: `Symbol.asyncDispose` for `await using` in TypeScript (`close()` stays first-class, since Node 22 has no `await using`), `async with` and `with` in Python, `close(&self).await -> Result` in Rust, through `&self` so it works through an `Arc`.
  > Amended by [ADR 0081](0081-each-sdk-follows-its-languages-concurrency-model-and-shapes-events-by-meaning.md): Rust handles are cheap clones of one value, so `close()` on any clone closes the value for every clone. A `Subscription` closes synchronously in TypeScript and Python, since nothing waits, as does a TypeScript iterator's `close()`, and a Rust `EventStream` or blocking `EventIter` closes by being dropped.
- `close()` is idempotent; any other call on a closed value fails with the Error code `closed`. A value never reopens: `connect()` again. Closing a parent closes its children first and waits for them, along ADR 0038's cancellation tree; its deadline is [Time, waits, deadlines, cancellation and budgets](https://github.com/goodfetch/goodfetch/issues/467)'s (ADR 0080).
- **What each `close()` releases:**

  | Value | `close()` |
  |---|---|
  | Page | Closes the tab Goodfetch opened; on a Borrowed browser it never touches the person's tabs (ADR 0056). |
  | Session | Closes its pages and browser context; a browser the engine launched goes back to the governor (ADR 0040); a Borrowed browser is never closed. |
  | Run | A Run no longer `running` only frees the value; the Run stays in the Run index. A `running` one is stopped at its next safe point (an Effect in flight finishes or is reported uncertain, ADRs 0029 and 0036), a Checkpoint is written, and it ends with Lifecycle `stopped` and Completeness `incomplete` as an abort by its Client (ADR 0029), resumable by its ID. It never waits for a crawl to finish. |
  | Connection | Cancels in-flight calls, closes every Run it opened except a detached one, and ends every borrow; then an Attached engine, or Rust's linked engine, checkpoints and stops, and `close()` waits for it, while a Daemon is only disconnected. |

  > Amended by [ADR 0102](0102-a-program-names-its-run-by-an-id-that-a-start-resumes-ends-it-with-a-run-report-and-reads-what-waits-and-why.md): closing a detached Run's value frees only the value and never stops the Run, as the connection's close already leaves a detached Run running; `run.stop()` stops it.

- **A failed close raises** a typed error, never swallowed (G1): in TypeScript it arrives as a `SuppressedError` when `await using` is already unwinding from another error, in Python as a chained exception.
- **A Run belongs to the connection that started it.** When a Client crashes, the engine re-queues its leased work items as soon as it sees the Client gone (ADRs 0003 and 0024); a Run with no Client left to serve its handlers checkpoints and waits for its script (ADR 0031). A Run with no handlers in the program (a Recipe run or a code-free catalog run) may be started detached on a Daemon or Goodfetch Cloud, and then outlives the connection; detaching on an Attached engine, which dies with its connection, is refused with a typed Error code. The option's spelling is The Run in code's.

### A guest in the program (G4)

- **Many connections.** Each `connect()` is independent, with its own settings and, when it starts one, its own Attached engine or, in Rust, its own linked engine; an engine is shared through a Daemon, never through a process-wide instance (G2). `connect()` works again after `close()`. Two connections with their own Attached engines have two resource governors (ADR 0040); two connections to one Daemon share its governor.
- **Nothing at import.** Importing an SDK starts, configures and patches nothing: no logging setup, no event-loop patch, no `nest_asyncio`.
- **Forks.** A connection belongs to the process that opened it; a forked child that uses it gets a typed Error code telling it to connect itself. `workers=N` (ADR 0024) already does so.
- **Notebooks.** The async API runs under a notebook's running loop. Whether the sync API runs inside a running loop is Concurrency model per language's.
- **Signals.** An SDK installs no signal handler and no `atexit` hook. It starts its Attached engine in a process group of its own (`setsid` on macOS and Linux, `CREATE_NEW_PROCESS_GROUP` on Windows), so a terminal's Ctrl+C reaches only the host. A host that unwinds on it, as Python does with `KeyboardInterrupt`, closes the connection, which checkpoints. A Node program that exits at once leaves its Attached engine to ADR 0024's rules, which stop it with the host, and a Rust program that exits at once stops its linked engine with it; either way, Runs resume from their last Checkpoint.

### Logs

- **Python:** loggers under `goodfetch`: `goodfetch.client` for the SDK's runtime and `goodfetch.engine.<area>` for what the engine relays. The SDK adds only a `NullHandler` and never touches handlers, levels or the root logger. Deprecations (ADR 0030) go through `warnings.warn`.
- **TypeScript:** a `logger` option taking `{ debug, info, warn, error }`, which `console`, pino and winston fit; with none, the SDK is silent. Deprecations go through `process.emitWarning`, the host's warning channel.
- **Rust:** `tracing` events under `goodfetch::…` targets; the crate never installs a subscriber.
- **Every SDK:** logger names and targets are part of the SDK API under semver, message text is not. An expected outcome is never logged at error level (G1).
  > Amended by [ADR 0132](0132-each-request-may-carry-its-callers-trace-context-across-goodfetchs-own-links-and-the-engines-spans-stay-experimental.md): the Rust SDK's own `goodfetch::…` targets stay under semver; the engine's targets in an OpenTelemetry export are Experimental. Each SDK passes on its host program's ambient OpenTelemetry context in the request's `_meta`, and runs an SDK handler under the Trace context the engine sent.
- **The engine's logs** reach a Client as log events of its own connection and runs, which area 3's spec already classes as telemetry: coalesced under backpressure with a `dropped` count, never slowing a run. The engine filters them at a level the SDK sets: from the logger's effective level in Python, from `tracing`'s level hint in Rust, and as area 11's spec gives it for the TypeScript `logger` option. The SDK re-emits them under its engine loggers or targets (`goodfetch.engine.*` in Python, `goodfetch::engine::…` in Rust). A Daemon keeps its own log.
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-22, [#257](https://github.com/goodfetch/goodfetch/issues/257): a Client asks for a level with `hello`'s optional `log_level` (`off`, the default, `error`, `warn`, `info`, `debug` or `trace`) and changes it with `connection.set_log_level` (SDK only), from the next log event on, without a new `hello`. The engine sends each Connection every log event of its process at or above that level, whatever the Run, as the notification `$/log {level, target, message, fields?, dropped?}`; each Connection has its own level. A Connection too slow to read them loses the oldest of a buffer of 1,024, and the next one it receives counts them in `dropped`. The engine's `tracing` layer listens only at the most verbose level some Connection asks for.
- **An Attached engine's stderr** is piped, never inherited. An Attached engine started by an SDK sends its logs only as log events, so its stderr carries only ADR 0030's age notice and crash output. The SDK re-emits each stderr line through the host logger at warning level and keeps the last 64 KiB to attach to the error raised when the engine exits unexpectedly (G6).
  > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): an Attached engine also writes JSON lines to the Goodfetch home's log folder when `log.output` is `file` in its configuration, as test support sets it for ADR 0072's exercise audit. Its logs still go as log events, and its stderr is unchanged.

### Rust

- **`Drop` never blocks and never fails** (C-DTOR-FAIL, C-DTOR-BLOCK). On a value not closed, it fires the cancellation tree without waiting, emits a `tracing` warning, and leaves the rest to the engine; Runs resume from their last Checkpoint.
  > Amended by [ADR 0081](0081-each-sdk-follows-its-languages-concurrency-model-and-shapes-events-by-meaning.md): it acts when the last clone of a handle is dropped; dropping an `EventStream` or a blocking `EventIter` is how it closes, with no warning.
- **A scoped helper** `Goodfetch::scope(options, async |gf| { … }).await` opens the connection, lends it to the closure, and closes it on every return and error.
- **Child processes** the crate starts (the `goodfetch` binary for the Script sandbox and `plugin-shim`, ADR 0024) use `kill_on_drop(true)`.

## Considered Options

- **A plain constructor that starts the engine on the first call**, as OpenAI's and httpx's clients do no I/O when built: rejected. It hides when the engine starts and moves a missing binary's error to an arbitrary call; Rust's C-BUILDER also asks for an explicit step when building has side effects.
- **No root object, each Browser or Crawler starting its own engine**, as Crawlee's crawlers and Scrapy's process do: rejected. Two objects get two engines, ADR 0056's relay has no connection to ride on, and Scrapy's process-global reactor is G2's counter-example.
- **One Attached engine shared by every connection of a process**: rejected by G2. It is a process-wide instance; a Daemon shares an engine visibly.
- **An implicit Run behind each Page** (`gf.collie.newPage()`): rejected. Two pages would be two Runs with two sets of Limits and Usage, and there would be two ways to make a Run (S2).
- **`gf.borrow(page)` returning a Page in an implicit Run**: rejected for the same reason. **`gf.borrow(page)` returning a Session source** passed into settings: rejected, two more steps in [Add an AI step to an existing Playwright program](https://github.com/goodfetch/goodfetch/blob/prototype/sdk-api/sdk-api-sketch/scenarios/09-ai-in-playwright-program.md) for no gain in safety.
- **Every Run on a Daemon outliving its connection**: rejected. Runs would wait for scripts that may never return, and an Attached engine and a Daemon would behave differently by surprise. **Never detaching**: rejected, since a short script could not submit a long Recipe run.
- **The Attached engine in the host's process group**, as most drivers leave it: rejected. Ctrl+C kills the engine and its browsers before the host's cleanup runs (chromiumoxide [#251](https://github.com/mattsse/chromiumoxide/issues/251)).
- **Signal handlers in the SDK**, as Crawlee v4 adds a `SIGINT` listener per crawler and Browser Use installs handlers that print: rejected by G4.
- **Inheriting or discarding an Attached engine's stderr**: rejected. Inheriting prints into the host's terminal, and on Ctrl+C left the shell broken (playwright-rs [#59](https://github.com/padamson/playwright-rust/issues/59)); discarding loses the age notice and the crash output chromiumoxide users miss (`LaunchExit` with empty stderr, [#295](https://github.com/mattsse/chromiumoxide/issues/295)).
- **A default console logger in TypeScript**, as Stainless's SDKs log warnings by default: rejected by G4. Stagehand v4 writes to stderr even with `onLog` set ([#3035](https://github.com/browserbase/stagehand/issues/3035)).
- **Blocking cleanup in Rust's `Drop`**: rejected. chromiumoxide's `block_on` in `Drop` panicked ([#137](https://github.com/mattsse/chromiumoxide/issues/137)), thirtyfour's blocks the executor, as its docs warn, and panicked while the runtime shut down ([#268](https://github.com/stevepryde/thirtyfour/issues/268)), and fantoccini's fire-and-forget request is lost when the runtime stops ([#250](https://github.com/jonhoo/fantoccini/issues/250)). Async `Drop` is nightly-only.

## Consequences

- **Changes ADR 0056.** Its SDK relay is spelled `run.borrow(pageOrBrowser)`, on the Run whose Session it serves, instead of `goodfetch.borrow(browserOrPage)`; matrix rows SA-08 and `integ-sdk-llm-runtime` of [ADR 0037](0037-v1-scope-matrix.md) follow.
- **Adds to ADR 0024.** An SDK starts its Attached engine in a process group of its own and pipes its stderr, and that engine sends its logs only as log events. ADR 0030's age notice still goes to stderr only, and the SDK relays it through the host's logging.
- **Error codes.** `closed`, and the codes for a connection used after a fork and for a refused detach, join `goodfetch-protocol`'s list; area 11's spec names the last two.
- **Area 11 (Client surfaces)** builds these rules and lists this ADR. The per-connection log level is a protocol addition its spec makes with area 3's, whose events already class logs as telemetry. Client conformance cases cover the guest rules in every SDK ([TESTING.md](../testing/sdk-and-cli-tests.md#sdks)).
- **The `prototype/sdk-api` sketch** holds this ADR's signatures in `lifecycle` files for each language.
