# SDK timeouts nest in one duration type per language, waits arm when called, and a program sets Limits but never raises them

A program says how long things may take with one `timeout`, a duration in its language's own type, which nests: a call made inside another never outlasts it. Every phase has a finite default held as a setting, and a timeout's error names the setting that set it. App-state waits arm when they are called, so a response cannot slip past its waiter. Cancellation is each language's own (an `AbortSignal`, task cancellation, a dropped future) and always reaches the engine through `$/cancel`. Limits are set in code on a connection and a Run, and only lowered there. Timing is the research's first pain: 53 of the 375 top Playwright and Puppeteer Stack Overflow questions (1,686 votes) are waits, races and sleeps, and "element ready is not app ready" survives auto-waiting ([synthesis §4](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/2026-10-14-consumer-api.md#4-pain-points-merged-ranked-by-evidence-weight), pain 1). The others are close behind: Crawlee's silent hangs, which took years to fix (pain 6); Playwright Python's `timeout` in milliseconds where httpx and asyncio use seconds; Skyvern's minutes, seconds and milliseconds depending on the call; Python cancellation that Playwright calls undefined behaviour (pain 15); and agents whose only cap is a step count (AI pain 13). Decided in [Time, waits, deadlines, cancellation and budgets](https://github.com/goodfetch/goodfetch/issues/467), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), under the principles of ADR 0077 and the error model of ADR 0079.

## Decision

### Timeouts

- **One concept, a duration that nests.** `timeout` is the longest a call, a wait or a phase of a Run may take, counted from its start: a click, a navigation, a crawl handler, a sink write. The engine turns it into an end time that the calls made inside inherit. An action started with 10 s left in its handler gets 10 s, not its own 30 s. A child may end sooner than its parent but never later, which is Azure's rule for cancellation trees. There is no `extendTimeout`: a handler that needs longer gets a longer timeout through its route's setting (S2, G2).
- **A Human pause stops the clock.** Time spent waiting in a Human pause does not count toward any enclosing timeout. How long a pause itself may last is [Sessions, logins, Human pause and secrets in code](https://github.com/goodfetch/goodfetch/issues/476)'s.
  > Amended by [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md): so does a crawl handler's wait for a permit from ADR 0087's navigation gate: it counts toward neither `timeout.navigation` nor `timeout.handler`, and the engine renews the work item's lease meanwhile; the Run's own timeout still applies.
  > Amended by [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): a pause lasts at most `timeout.human_pause`, 24 hours by default, with this ADR's three states; past it, `page.pause()` raises `deadline_exceeded` naming the setting, and a pause the engine raised inside a call ends that call with its own code. In a scheduled run the built-in default does not apply: ADR 0036's pause timeout governs, a value set at any layer also applies, and the first to expire acts.
- **One duration type per language (S1, G3):**
  - TypeScript: a `number` of milliseconds, the one unit throughout the TypeScript SDK, named `timeout` without a unit suffix (Playwright's name and `AbortSignal.timeout(ms)`'s unit, S3).
  - Python: `datetime.timedelta` only. A pasted Playwright `timeout=30_000` is then a type error, where a number would silently mean 30,000 seconds or 30 milliseconds.
  - Rust: `std::time::Duration`. Every call made on a value is a builder that implements `IntoFuture`: `.timeout(d)` or `.no_timeout()`, then `.await`. `ConnectOptions`, which `Goodfetch::connect(options)` takes (ADR 0078), and starting a Run have the same two methods, so `.no_timeout()` is the one spelling of no timeout throughout the crate.
  > Amended by [ADR 0083](0083-a-program-sets-settings-in-one-typed-option-explicit-values-beat-the-environment-and-no-value-is-silently-ignored.md): `.no_timeout()` is the one spelling of no timeout for a call and the option builders; a scope's timeout setting is cleared with `Settings::set(timeout::…, None)`.
- **Three states.**
  - Omitted, the setting's default applies. Python's omitted value is a `not_given` sentinel, as in openai-python.
  - An explicit null means no timeout: `null` in TypeScript, `None` in Python, `.no_timeout()` in Rust. An enclosing timeout still applies.
  - `0`, a negative value or a non-finite number fails with a `ProgramError` whose fix names the null form, because `0` reads as "at once".
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#1180](https://github.com/goodfetch/goodfetch/issues/1180): a call's own timeout is its operation's `timeout` param, in milliseconds or `null` for none, absent for the setting's default; an operation that may wait declares it and a query does not (ADR 0099). The CLI's `--timeout <duration>` is that param: milliseconds (`45000`) or a count with a unit (`250ms`, `45s`, `2m`, `1h`), and `--timeout none` the null form; `0`, a negative or a malformed duration is a usage error (exit `2`) before any engine call, its message naming `--timeout none`. No operation of the catalog takes `timeout` yet, so no command shows the flag until one does.
  > Note (agent decision, on a default, not read by the owner), 2026-10-24, fix 57 of the spec #577 gate: `page.goto` declares its own `timeout`, `timeout.navigation` for that navigation alone, as the waits declare theirs: absent for the setting, `null` for none, a count of milliseconds for that setting at the run layer, which `deadline_exceeded`'s `limit` names, and 0 refused with `invalid_params`; the CLI's `page goto` takes `--timeout` accordingly. A short navigation deadline is then the call's, and opening the page, whose commands wait under the Run's `timeout.navigation` (ADR 0059's note of 2026-10-24), is not bound by it. `page.reload`, `page.go_back` and `page.go_forward` take none yet.
- **Every phase has a finite default**, held as a setting (ADR 0028) that can be set where the Run, Session or page is opened, overridden per call and shown by `goodfetch config explain`:
  - connect: 30 s
  - action, the guard's window (ADR 0019): 30 s
  - navigation: 30 s
  - app-state wait: 30 s
  - crawl handler: 60 s
  - Hook: 10 s
  - sink write: 30 s
  - `close()`: 30 s
  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): an Agent's task is a phase too, `timeout.agent`, 10 minutes, nesting the timeouts of its actions and model calls.

  There is no mutable setter such as Playwright's `page.setDefaultTimeout`, which changes calls elsewhere in the program (G2). The setting names, and whether Foxhound's defaults differ from Collie's, are [Settings in code](https://github.com/goodfetch/goodfetch/issues/470)'s.
  > Amended by [ADR 0083](0083-a-program-sets-settings-in-one-typed-option-explicit-values-beat-the-environment-and-no-value-is-silently-ignored.md): the settings are `timeout.connect`, `timeout.action`, `timeout.navigation`, `timeout.wait`, `timeout.handler`, `timeout.hook`, `timeout.sink_write`, `timeout.close` and `timeout.run`, with the same defaults in Collie and Foxhound.
  > Amended by [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md): `timeout.ai`, 120 s, bounds an AI verb from its call to its return, model calls and a Repair included; the action it performs keeps `timeout.action` inside it.
  > Amended by [ADR 0101](0101-a-model-is-named-provider-slash-model-its-capabilities-and-prices-are-declared-and-every-ai-result-carries-its-priced-usage.md): one attempt of one model request is a phase too, `timeout.model`, 60 s; an attempt past it is retried within the call that made it, inside which it nests.
  > Note (agent decision, on a default, not read by the owner), 2026-11-18, [#2813](https://github.com/goodfetch/goodfetch/issues/2813): bringing a browser up is a phase too, `timeout.launch`, 30 s, Playwright's and Puppeteer's launch timeout: each command of a launch or of a Borrowed browser's connection, and the identity read's page load, wait under it. They waited under `timeout.navigation`, which this ADR and ADR 0059's note of 2026-10-24 give to navigations, opening a page and reading its document or history, so a Run with a short navigation timeout failed `run.new_session` on a loaded machine before any navigation began. Making the Session's browser context stays under `timeout.navigation`, as the first step of opening its pages, which ADR 0059's note gives it.
- **A timeout's error** has one Error code, `deadline_exceeded`, which shares its group's class under ADR 0079's naming rule, whatever the phase: `operation` names the call and `limit` the phase, so per-phase codes would only multiply classes that share one remedy (S2). Its `limit` names that setting, its value and the layer that set it; a call's own argument is that setting at ADR 0028's run layer, and `limit` says so, since that layer also holds CLI flags, environment variables and an Integration's form. Its typed details carry the timeout's value, the elapsed time and what was waited for, and, when an enclosing timeout ended the call, that call's `operation` and `callId`. `observed` holds the last state seen (G6).
  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-21, [#227](https://github.com/goodfetch/goodfetch/issues/227): `deadline_exceeded` is retryable, and its details are `limit` (the setting's `key`, its `value` in milliseconds and its `layer`), `elapsed` in milliseconds and `waited_for` (such as `first_byte` or `navigation`); the engine's `deadline::Deadline` gives every phase that waits under a timeout setting this one answer, which the fetch tiers and the page's driver (area 5) use. The enclosing call's `operation` and `callId`, and `observed`, which this ADR also requires, join these details when nested timeouts and the page's driver land. Corrected 2026-10-21: it listed only `limit`, `elapsed` and `waited_for` as the details, omitting those three.
  > Amended by [ADR 0083](0083-a-program-sets-settings-in-one-typed-option-explicit-values-beat-the-environment-and-no-value-is-silently-ignored.md): the run layer's origins are a call's argument, a `settings` option, a CLI flag or an Integration's form; environment variables carry no setting.
  > Amended by [ADR 0085](0085-collies-page-api-keeps-playwrights-names-strictness-waits-values-cross-as-json-and-unanswered-requests-fall-through.md): a target still ambiguous when its deadline passes raises `target_not_unique`, a `PageError` (ADR 0079's case), not `deadline_exceeded`, since a longer timeout would not fix the locator; its `limit` names the timeout's setting all the same.
  > Amended by [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md): a Success check (`expect`) still false at its timeout, `timeout.wait`, fails with `success_check_failed` (a `PageError`), not `deadline_exceeded`: the timeout bounds how long the condition may take to hold, and the failure is the Success check's answer. Its details carry the timeout's setting and layer, as `deadline_exceeded`'s do.
  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): an Agent's task that reaches its own `timeout.agent` raises no `deadline_exceeded`: the step in flight is cancelled, and the task returns `ended: stopped` with the reason `timeout` naming the setting, since AI work that ends early is a value (ADR 0079). An enclosing call's timeout still ends it with `deadline_exceeded`, naming that call.
- **A timeout fails only its call.** In a crawl, it fails that work item, which is then retried under the crawl's retry policy ([Crawl definition and handler context](https://github.com/goodfetch/goodfetch/issues/477) (ADR 0093)). The Run goes on: no other timeout stops a Run.
- **The Run's own timeout.** Starting a Run takes a `timeout` for the whole Run. It is a setting like the others (ADR 0028), so configuration or a Recipe may set it, with the same three states, but its built-in default is none, because crawls rightly run for hours and Limits cap their cost. On expiry the Run stops with a Checkpoint, `stopped` and `incomplete` (ADR 0029), with the stop reason `timeout`, and it can be resumed; the resumed Run's clock starts afresh. It is not a Limit: elapsed time is not Usage, and "only a person raises it" has no meaning for a clock.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#227](https://github.com/goodfetch/goodfetch/issues/227): the stop reason is `{ "kind": "timeout" }`. The Run's clock starts when its engine starts it, so a resumed Run's starts afresh. A Run its program drives stops at once, since the engine holds nothing in flight for it; a crawl admits nothing new, lets each attempt in flight commit or be abandoned under its lease, then stops. An abort still stops a Run at once, abandoning its attempts under their leases. The Checkpoint written at that stop is [#218](https://github.com/goodfetch/goodfetch/issues/218)'s.

### Waits

- **App state, with Playwright's names where the meaning matches (S3).** The waits are:
  - `waitForURL`, `waitForResponse`, `waitForRequest`, `waitForLoadState`, `waitForFunction` and `locator.waitFor({ state })`, as in Playwright.
  - `waitForRequestFinished`, which waits until a matching request has finished and its body is read.
  - `locator.waitForCount(n | { min, max })`, which returns the count. It has a new name because no Playwright call outside `expect` does this.

  The `networkidle` load state is kept and defined: no request in flight for 500 ms, WebSockets and server-sent events excluded. Each wait takes `timeout`, and in TypeScript `signal`. Python spells them in `snake_case`. Where a host-language predicate runs is [Concurrency model per language](https://github.com/goodfetch/goodfetch/issues/468)'s (ADR 0081).
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#705](https://github.com/goodfetch/goodfetch/issues/705): the waits' operations are `page.wait_for_url`, `page.wait_for_request`, `page.wait_for_response`, `page.wait_for_load_state`, `page.wait_for_function`, `locator.wait_for` and `locator.wait_for_count`, each a waiter under `timeout.wait` whose `deadline_exceeded` names in `waited_for` what it waited for (`url`, `request`, `response`, the load state, `function`, `target_<state>` or `target_count`). `networkidle` comes once the document fired `load` and none of the page's own requests was in flight for 500 ms since, a `data:` or `blob:` URL never counted, and stays until the next document commits. `page.wait_for_url` and `page.wait_for_load_state` pass at once when the page is already there, as Playwright's do. `page.wait_for_function` takes `polling_interval` in milliseconds, about a frame's 16 when absent, which an SDK's `raf` maps to; it is checked from the engine, so it goes on across navigations. `locator.wait_for` waits out several matches like the guard and raises `target_not_unique` when they last to its deadline; `locator.wait_for_count` takes `{ min, max }`, an exact count being both. `waitForEvent` is the SDK's: it is `page.on`, which also listens from when its call arrives, closed after the first event. Each wait, `page.wait_for_request_finished` included, takes its own `timeout` param (corrected 2026-10-24 after the spec #577 review, M21, which found the params refusing one): absent for `timeout.wait`, `null` for none, a count of milliseconds for that setting at the run layer, which `deadline_exceeded`'s `limit` names, and 0 refused with `invalid_params`; the CLI's wait commands take `--timeout` accordingly. A wait in flight is a call on its page: one whose page closes or crashes under it raises `call_cancelled` or `page_crashed`, and a failure a handler left on the page is raised before it waits.
- **Waiters arm when called.** The SDK sends the arming request when the method is called, not when it is awaited, and the engine keeps each page's calls in order. So the response a click triggers can never arrive before its waiter. Each language writes it in its own form:
  - TypeScript, Playwright's promise-first form: `const r = page.waitForResponse(u); await click(); await r`. It is equally safe under `Promise.all`.
  - Python, Playwright's blocks in the async and sync APIs: `async with page.expect_response(u) as info:`, then `await info.value`. The same exists for `expect_request` and `expect_request_finished`.
  - Rust: `page.wait_for_response(u).during(action).await?` arms the waiter, then drives the action, and returns both results. Rust futures do nothing until polled, so a waiter merely joined with its trigger could arm too late. A waiter can also be awaited alone.
- **No fixed sleep.** The page has no sleep verb. A tombstone `waitForTimeout` / `wait_for_timeout` keeps the familiar name, but it cannot type-check, because its parameter is `never`, `Never` or `Infallible`. Its type-level deprecation (TSDoc `@deprecated`, PEP 702, `#[deprecated]`) names the app-state waits and the host's own timer, and in TypeScript and Python, where a program can still reach it past the type checker, it fails at run time with the new Error code `removed`, a `ProgramError`; Rust's takes `Infallible`, so no call to it compiles. It does nothing, so it is not an alias (S2). It gives people and coding agents the pointer at the moment they write the call (T). Puppeteer removed its sleep in 22.0 without one.

### Cancellation

- **Each language's own mechanism, always reaching the engine.**
  - TypeScript: `signal?: AbortSignal` on every cancellable call. An abort rejects with `signal.reason`, as `fetch` does, so `AbortSignal.timeout()` and `AbortSignal.any()` compose natively.
  - Python: cancelling the task (`Task.cancel`, `asyncio.timeout`, anyio's `fail_after`) sends `$/cancel` without waiting for the engine's answer, and `CancelledError` propagates unchanged.
  - Rust: dropping a call's future sends `$/cancel` without blocking, under ADR 0078's `Drop` rule.
- **`call_cancelled` is never the caller's own cancellation.** ADR 0038's answer to a cancelled call is named `call_cancelled`, with the class `CallCancelledError`, because a class `CancelledError` would share its name with Python's `asyncio.CancelledError`, which ADR 0079's naming rule refuses. An SDK never raises it for a cancellation its caller asked for. When someone else stops a call in flight (a person stopping the Run from the Console, another Client, the program closing a parent value), the call fails with `call_cancelled`, an `UnavailableError` that is not retryable: what the call needed is gone, as Playwright's `TargetClosedError` reports that the target page, context or browser has been closed. `observed` says who stopped it, and `fix` follows: resuming the Run when the Run was stopped, or naming the close when the program closed a parent value.
  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): an Agent's task that someone other than the caller stops (a person, another Client, the program closing its page or Run) returns `ended: stopped` with the reason `abort`, keeping its steps and partial answer, instead of raising `call_cancelled`.
  > Amended by [ADR 0113](0113-a-human-pause-whose-page-closes-raises-call-cancelled-naming-what-closed-and-a-lost-live-view-ends-no-pause.md): `call_cancelled` carries `CallCancelledDetails { by, closed, person }`: `by` is `person`, `client`, `program` or `browser`, the last for a page or browser closed in the browser outside every Client; `closed` is the `page`, `session`, `browser`, `run` or `connection` closed or stopped under the call; `person` is whom the stopping Client acts for, when known.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
- **Both apply.** A signal and a timeout both apply, and whichever comes first ends the call. The Run trace records a cancelled call as cancelled. An Effect already sent is never treated as undone (ADR 0010). How the blocking Python client cancels is Concurrency model per language's.

### Limits in code

- **Set on a connection and on a Run.** `connect()` takes `limits` for its Client connection, and starting a Run takes `limits` for that Run (ADR 0041's scopes). They are typed per kind of Usage (model tokens, model calls, browser time, proxy bytes, paid solves, Paid fetches), plus a price in a currency through ADR 0012's price table, a decimal amount with an ISO 4217 code (`Money`), so no float rounding reaches a cap. A Paid fetch Limit set in code only caps: a Paid fetch is made only under a Limit a Client could not set (ADRs 0041, 0045).
  > Agent decision (#1227, 2026-11-18): on the wire, `run.start`'s `limits` is one list of `{ usage_kind, currency?, amount }`, an amount in a currency in millionths of it as `usage.set` takes it; the SDKs type it per kind of Usage and as `Money` (#2830). Each is a Client's Limit with no period on the new Limit scope `run`, which every Run stands in. A list naming one Usage kind and currency twice is `invalid_params`. The values a Run began with are kept apart from its Limits, as a person's raise rewrites those, so a start naming the Run again with them changes nothing; one above the Limit as it stands is `limit_raise_refused`, a `RefusedError`, and the start is refused before the Run opens.
  > Agent decision (#2830, 2026-11-18): `connect()`'s Limits travel as one `usage.set` per Limit on the `connection` scope, with no `scope_id` and no period, sent once `hello` is answered and before `connect()` returns; `hello` takes no Limits. The engine reads an absent `scope_id` on that scope as the caller's own Client connection, so no other connection's Limit can be named, and the wire needs no new field. A Limit the engine refuses closes the new connection and fails `connect()` with that error. The SDK turns a `Money` into millionths of its currency before anything is sent, and an amount it cannot turn exactly fails the call that carries it.
- **Lowered, never raised.** A program may set or lower the Limits that cover its own work; no SDK has an operation that raises one, because only a person raises a Limit (ADR 0041).
- **Reaching a Limit** follows ADR 0079's cases. A call refused because a Limit is already used up fails with `limit_reached`, a `RefusedError`, naming the Limit's kind, scope, value and where it was set. AI work that a Limit stops returns a value whose `ended` is `stopped`, with that Limit by name. Either way the Run ends `stopped` and `incomplete` at its next safe point (ADR 0041), with the stop reason `limit`, and keeps its partial results (ADR 0029). How Usage and cost are reported on results and Runs is [Models, usage and cost in the SDK API](https://github.com/goodfetch/goodfetch/issues/475)'s (ADR 0101).
  > Amended by [ADR 0107](0107-a-runs-model-allowance-refuses-its-model-calls-once-spent-while-the-run-goes-on.md): a Run's model Usage can also be capped without stopping the Run, through a Model allowance (`ai.allowance.price`, `ai.allowance.tokens`, `ai.allowance.calls`), which is not a Limit: once reached, a call that needs a model raises `model_allowance_reached`, a `RefusedError` naming the setting, an Agent's task returns `ended: stopped` with the reason `model_allowance`, and the Run goes on.
- **No step Limit, and no per-call Limit.** A model call already counts every step, and an Agent's own step cap, if it has one, is [The Agent in Collie's SDK API](https://github.com/goodfetch/goodfetch/issues/474)'s. A call is bounded by its timeout and its Run's Limits; to cap one step alone, a program gives it a Run of its own, which is the unit of counting (ADR 0078). No call carries a hidden cap, as HyperAgent's `extract` did with `maxSteps: 2`.
  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): the Agent has one, `agent.max_steps` (20, and `maxSteps` for one task), which is not a Limit: it bounds one task and stops only that task, while the Run goes on.
  > Amended by [ADR 0107](0107-a-runs-model-allowance-refuses-its-model-calls-once-spent-while-the-run-goes-on.md): a call scope for Limits stays declined: scenario 08's Run-wide cut-off is the Model allowance, and a cap on one step alone stays a Run of its own.

## Considered Options

- **An absolute `deadline` parameter**, as gRPC and Trio take: rejected. It is exact, but no browser-automation or crawl leader uses it, and a duration nests just as well once the engine holds the end time (S3, T). **Both a timeout and a deadline**: rejected by S2.
- **`context.extendTimeout()`**, as on Crawlee's master branch for v4: rejected. A handler changing its own timeout is hidden state, and the route's setting already gives a long handler its time.
- **Mutable default setters** (`setDefaultTimeout`, `setDefaultNavigationTimeout`), as in Playwright: rejected by G2. A setter on a page changes calls written elsewhere.
- **`0` meaning no timeout**, as in Playwright and Scrapy's `CLOSESPIDER_TIMEOUT`: rejected. It reads as "at once", and an explicit null says what it means.
- **Python taking a number**, as Playwright Python takes `float` milliseconds or a `timedelta` and httpx takes `float` seconds: rejected. Either unit silently misreads code written for the other; `timedelta` only is what Crawlee for Python takes (`request_handler_timeout=timedelta(minutes=1)`).
- **`Temporal.Duration` or a `timeoutInMs` suffix in TypeScript**: rejected. Temporal is unflagged only from Node 26, and Azure's suffix is unfamiliar where one unit holds throughout the SDK.
- **Clocks running through a Human pause**: rejected. Every human step would need a hand-raised timeout, which AI pain 11 reports.
- **One generic `page.waitFor(condition)`**: rejected. It is smaller, but unfamiliar to Playwright users and to models (S3, T).
- **Keeping `waitForTimeout`**, as Playwright does while marking it discouraged, or **removing it silently**, as Puppeteer 22.0 did: rejected. The first keeps the flaky habit; the second leaves people with no replacement (P37).
- **One callback form everywhere** (`waitForResponse(u, () => click())`, Java's form): rejected by S1. It is uniform but unidiomatic in TypeScript and Python. **The promise-first form in Rust**: rejected, because lazy futures make it unsafe.
- **Azure's `abortSignal` name**: rejected for `signal`, the name of `fetch` and Playwright (S3).
- **A wall-clock Limit kind in ADR 0041**: rejected. Elapsed time is not Usage, and the Usage ledger has nothing to hold. **Reporting a Run's timeout as an abort**: rejected by G6, because the Run trace would not say what stopped it.
- **A "call" scope for Limits**: rejected for now. It amends ADR 0041 and adds a second layer of caps to explain, and a Run of its own already caps one step. **A step Limit**: rejected, because model calls count steps.
- **A timeout failing its whole Run**: rejected. One slow page would end a crawl.
- **One Error code per phase** (`navigation_timeout`, `handler_timeout`, …): rejected. They would share one remedy, and ADR 0079 adds a type only where the remedy differs.
- **Keeping the name `cancelled`** with a different class name in Python alone: rejected, because ADR 0079 forbids a per-language alias (S1). **`call_cancelled` as a `RefusedError`**: rejected. It fits a person stopping a Run, but not a program closing a parent value. **A group of its own**: rejected, because ADR 0079's set of groups is closed under semver.

## Consequences

- **Amends ADR 0079.** Its `cancelled` code is `call_cancelled`, in the `unavailable` group; `limit` says when a call's own argument set it; `timeout` joins the stop reasons of AI work.
- **Amends ADR 0038.** The engine answers a call cancelled through `$/cancel` with the code `call_cancelled`, not `cancelled`.
- **Amends ADR 0029.** A Run's own timeout is a fifth cause of `stopped`, beside a Limit, an abort, the loss of the engine and exhausted resources: such a Run is never `complete`, and it resumes with a fresh clock.
- **Error codes.** `removed` joins `goodfetch-protocol`'s list in the `program` group, ADR 0038's `cancelled` is renamed `call_cancelled` and placed in the `unavailable` group, and every timeout is `deadline_exceeded`, with the details above. `timeout` joins the stop reasons of AI work results and of a Run.
