# A crawl declares its Labels and one handler each, and a handler reads Collie's page on every fetch tier

A program defines a crawl by declaring its Labels, each with exactly one handler, on a value that needs no connection; a Run then carries the crawl out. Every handler receives the same context on every fetch tier: Collie's page over the crawl request's document, which every tier but the browser serves as far as it can exactly, moving the request to the browser only when a call needs one. A crawl request ends in one of ADR 0079's outcomes, and a handler skips or retries it with a call. Competitors fail here in three ways:
- **Switching tiers is a rewrite.** Crawlee's context changes shape with its crawler class, Scrapy reaches a browser through a plugin, a reactor and per-request meta, and Spider-rs through a recompile ([crawl frameworks](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/crawl-frameworks.md) §3.2, §6.5; [synthesis](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/2026-10-14-consumer-api.md) pain 8).
- **Skipping is faked as a failure.** Crawlee v3 skipped a request by setting `noRetry`, throwing, and lowering `requestsFailed` by hand (§6.15).
- **Retry defaults disagree.** Crawlee 3.18.2 retries any handler error three times, and Scrapy 2.19.0 never retries a callback's exception, both read in their source for this decision.

Decided in [Crawl definition and handler context](https://github.com/goodfetch/goodfetch/issues/477), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), first decided by the agent on the owner's delegation and then confirmed by the owner with four changes ([owner confirmation](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6187919342), recorded as [round 12](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6188325918), with a [clarification of R3](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6188913587)), with its [grilling record](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6181133439), [round 7](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6181341593), [round 8](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6181741958), [round 9](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6182018299), [round 10](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6187681403) and [round 11](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6188015778). The handler's page is a Collie page, as [ADR 0088's hand-off](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6188812868) asked, and carries [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md)'s navigation gate. Principles are cited by their IDs in [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md). The page is [ADR 0085](0085-collies-page-api-keeps-playwrights-names-strictness-waits-values-cross-as-json-and-unanswered-requests-fall-through.md)'s; Sessions are [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md)'s and AI verbs [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md)'s, in review when this was decided.

## Decision

### Declaring a crawl

- **A Label for each kind of request, with exactly one handler.** Behind JSON-RPC a callback cannot cross the connection or a Checkpoint, so a request names its handler by a name the engine persists: its Label (ADR 0082). There is no default handler: Crawlee's catches a misspelled label silently, which typed handles make a type error instead (S2, G3).
- **A `Crawl` value holds the declaration,** made with no connection and no I/O, so a module may declare it when it loads (ADR 0078):
  - `new Crawl()` in TypeScript;
  - `AsyncCrawl()` (`async def` handlers) and `Crawl()` (plain functions) in Python, as the client pair;
  - `Crawl::new()` in Rust, and `goodfetch_foxhound::blocking::Crawl` for `Fn + Send + Sync + 'static` handlers (ADR 0081).

  A Run is started from it and resumed with it, since handlers are never persisted.

  > Amended by [ADR 0104](0104-a-crawl-declares-its-hooks-per-stage-in-code-a-hook-returns-its-change-and-a-program-registers-its-own-plugins-by-name.md): a crawl's Hooks in code are declared on the `Crawl` too, one method per stage, and are never persisted either.

- **Two steps per Label: declare it, then attach its handler.**
  - `crawl.label(name, { payload, settings, login })` returns the typed handle `Label<P>`.
  - `crawl.handle(label, handler)` attaches the handler. Python spells it as the decorator `@crawl.handle(label)`, which returns the function unchanged, so a test calls it as it is ([Testing a user's crawl or automation](https://github.com/goodfetch/goodfetch/issues/482)).
    > Amended by [ADR 0105](0105-a-programs-tests-replay-a-response-recording-in-a-test-engine-that-reaches-no-site.md): the decorator still returns the function unchanged, but a test runs a handler through the testing kit's `runHandler`, which runs the one the crawl holds on a saved document and returns how its attempt ended and what it staged.
  - **A login step** (ADRs 0006, 0092) is the `login` option of a Label's declaration (`login=` in Python), or `login` of `new Crawl({ login })` (`AsyncCrawl(login=...)`) for the whole crawl; a Label's own wins for its Sessions. Rust spells them `crawl.login_for(&label, …)` and `crawl.login(…)`.
    > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): a Label's login is the `login` builder method of its `LabelDeclaration`, named after the declaration's `login` option as Rust spells every option, so `crawl.label(LabelDeclaration::<P>::new(name).login(step))`, with no `login_for`; the crawl's own stays `crawl.login(step)`, already the method named after `new Crawl({ login })`'s option.
  - **Why not one step.** One step was tried with tsc 7.0.2: an expression-bodied handler that enqueues to its own Label fails with TS7022, a trap a coding agent writes for pagination, and Rust cannot name a binding inside its own initializer (S1, T).
  - **Rust** declares `crawl.label::<P>(name)`, with the schema `schemars` derives, or `crawl.label_with(name, schema, settings)`.
    > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): one name, `crawl.label`, takes either shape through `impl Into<LabelDeclaration<P>>` (ADR 0099's rule for alternative argument shapes): a bare name, `crawl.label::<P>(name)`, or `crawl.label(LabelDeclaration::<P>::new(name).payload(schema).settings(settings))`, whose builder methods are named after TypeScript's `payload` and `settings` options. `label_with` is gone.
- **Mistakes are typed and early (G3, G6).**
  - A second Label of one name, or a second handler for one Label, fails at once with `label_duplicate`.
  - A Label left without a handler fails the Run's start with `label_unhandled`.
  - A Label the crawl does not declare fails an enqueue with `label_unknown`. A resume whose pending requests name a Label no longer declared is refused with `label_unknown` before any work, beside ADR 0082's schema check.
- **Where handlers run** follows ADR 0081: on the event loop in TypeScript, on the connection's thread pool in Python's sync API, and, in its async API, as tasks in the task group of the Run started from the `Crawl`, since the `Crawl` itself is no value to close. Closing the Run cancels and awaits them. In Rust, `crawl.serve(&run).await` answers the Run's crawl requests with the crawl's handlers inside that future until the Run ends, so handlers may borrow local state and need neither `Send` nor `'static`. Dropping that future is the program's own stop: it sends `$/cancel`, and its leased requests return to pending without counting an attempt (below). `run.crawl_requests()` is the `EventStream` beneath it, for a program that answers requests itself (G8).
  > Amended by [ADR 0102](0102-a-program-names-its-run-by-an-id-that-a-start-resumes-ends-it-with-a-run-report-and-reads-what-waits-and-why.md): `crawl.serve(&run).await`, and the blocking `serve`, return the crawl's Run report once the Run ends.
  > Amended by [ADR 0111](0111-a-rust-crawl-hands-what-it-subscribes-on-its-page-to-serve-which-reads-it-for-the-rest-of-the-attempt.md): `crawl.serve(&run)`, and the blocking `serve`, also read the page streams the crawl's code hands to `ctx.for_each`, for the rest of the attempt.
  > Amended by [ADR 0112](0112-a-rust-crawls-handlers-and-their-futures-are-send-in-axums-form-so-serve-runs-in-a-multi-threaded-server.md): handlers may borrow local state and need not be `'static`, but they are `Send`, and so are the futures they return: a handler, like a login step, is `FnOnce(…) -> Fut + Clone + Send + Sync + 'a` with `Fut: Send`, cloned for each request, so `serve`'s future is `Send` and runs inside an axum handler or a spawned task.

### Seeds and the noun

- **A crawl request** is the noun ADR 0079 left open: one URL a crawl's Frontier admitted, with its Label and Payload, the work item one handler processes (ADR 0003), which ends in one outcome. "Request" is every crawler's word, and prose may keep it. The SDK already has a `Request` type, the page's network request (ADR 0085), so the types are `CrawlRequest<P>` and `CrawlRequestOutcome`, which replaces the placeholder `RequestOutcome` (S3).
- **Seeds are crawl requests:** a URL, a Label, a Payload and the request options of an enqueue, checked as an enqueue is, so a seed the run's domain policy refuses is not added (`domain_policy`).
  - **A sitemap seed.** `sitemap(url, rules)` seeds from a sitemap, `url` being a sitemap or a site's robots.txt, whose `Sitemap:` lines are read. `rules` is an ordered list of URL pattern (matched in the engine, ADR 0081) → Label, as Scrapy's `SitemapSpider` `sitemap_rules` and Crawlee's `SitemapRequestList`: the first rule that matches picks the Label. A sitemap entry carries no Payload, so a rule names a Label without one, a type error otherwise. Nested sitemap indexes are followed. It widens the scope by its own host, like any seed. The seed's own answer, at the start or from `addSeed`, says whether the sitemap was accepted, as an enqueue's does. The engine then reads the sitemap and its indexes once the Run is running, through Politeness and robots.txt, and those fetches run no handler. Each entry is checked as an enqueue is, at depth 0, and an entry matching no rule is not added, with the reason `no_rule`. Entries not added are reported in the Run's report, in the shape [The Run in code](https://github.com/goodfetch/goodfetch/issues/478) gives it. It is the SDK shape of ADR 0037's CO-10.
    > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): an entry is never a seed, and one outside the crawl's scope is not added with `out_of_scope`; the seed widens the scope by the host of the URL the program named, so a robots.txt seed admits its own host's entries from a sitemap on another host that its `Sitemap:` line names (sitemaps.org's cross-submit rule); an entry resolves against its sitemap's URL; the sitemap's own fetches go through the domain policy, not the scope.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-25, [#903](https://github.com/goodfetch/goodfetch/issues/903): on the wire a seed is a request or `{sitemap, rules: [{pattern, label}]}`, `sitemap` naming a sitemap or a URL whose path is `/robots.txt`; a rule's pattern is a glob as `crawl.scope.include` takes one (`pattern_unsupported` at the start), and its Label must take no Payload (`payload_invalid`). The seed's answer is `added` with the ID of its fetch, or `not_added` with `invalid_url`, `unsupported_scheme`, `domain_policy` or `duplicate` (a sitemap the crawl already reads). Each sitemap's fetch is a work item of no Label that waits in its domain's queue, takes a Permit and charges `requests` as a page does, is fetched on the Run's HTTP tier whatever `fetch.tier` says after its origin's robots.txt is read, runs no handler and writes no outcome; a robots.txt seed reads its `Sitemap:` lines from that read, with no second fetch. A nested sitemap is admitted under the domain policy alone, once per URL. An entry no rule matches is `no_rule` before the scope is asked. The Run's report lists each sitemap read with `added`, `not_added` and `not_added_by_reason`, an index's entries being its sitemaps; a sitemap answering 408, 429 or 5xx fails its fetch with `response_unavailable`, retried, any other non-2xx or a file that is no sitemap with `response_not_ok`, which [#909](https://github.com/goodfetch/goodfetch/issues/909) reports.
    > Note (owner's decision of 2026-11-10, grilling of G-06, Q4, option A; the names agent decision, on a default, not read by the owner), 2026-11-11, [#2311](https://github.com/goodfetch/goodfetch/issues/2311): the note above's "A nested sitemap is admitted under the domain policy alone, once per URL" no longer holds. A nested sitemap carries its nesting level, the sitemap or robots.txt the seed names being level 0 and each sitemap an index or a robots.txt names one level deeper than it. It is fetched only on its seed's host, but for the sitemaps a robots.txt seed's own `Sitemap:` lines cross-submit on another host and the sitemaps such a sitemap names on its own host, where sitemaps.org places an index's sitemaps; one elsewhere is kept in the seed's report with `out_of_scope`. One nested deeper than `crawl.max_sitemap_nesting` (5 by default, `null` turns it off) is not fetched, with the new not-added reason `max_sitemap_nesting`. Each nested fetch counts against the crawl's bounds as a page's fetch does, its level as its depth: `crawl.max_depth`, `crawl.max_requests`, `crawl.path_budgets` and the caps on a URL's shape refuse it with their own reason, and it counts among the requests admitted. A refusal by a bound is counted with its setting's, so the Run ends `incomplete` (`unverified` for a cap), and the seed's report keeps the sitemap's URL with the reason. The seed's own fetch is not counted, as before. The run file's `sitemaps` rows gain `nesting` and its `bounds` row `max_sitemap_nesting`.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-25, [#909](https://github.com/goodfetch/goodfetch/issues/909): a sitemap file that opens with gzip's two bytes is decoded whatever its URL or type says, under the Run's `network.max_decompression_ratio` and `network.max_body_size` (ADR 0067), and never past 50 MB; a file past sitemaps.org's 50 MB (52,428,800 bytes) uncompressed or 50,000 URLs, an index's included, is not read at all and fails its fetch with `response_not_ok`, the limit named, rather than read in part; a decompression bomb fails it with `response_limit_exceeded`. The Run's progress and report give `sitemaps` per sitemap seed, replacing the per-sitemap list: `seed`, `read` (its sitemaps read, nested ones included, a robots.txt none), `failed` and `failures` (the first 20 by URL, each with `url`, `code`, `status` when one answered, and `message`), `added`, `not_added` and `not_added_by_reason`, counting only the entries of its sitemaps. A failure's `code` is its fetch's Error code, its skip reason (`robots_txt`), its Block cause, or `domain_policy` for a nested sitemap the domain policy refused; a nested sitemap already read elsewhere is no failure. A content-coded bomb on the HTTP tier is [#681](https://github.com/goodfetch/goodfetch/issues/681)'s.
  - **The start verb.** Its spelling, and resuming, are [The Run in code](https://github.com/goodfetch/goodfetch/issues/478)'s. The sketch uses `foxhound.start(crawl, { seeds: [seed(url, home)] })` on the `Foxhound` connection ([ADR 0090](0090-products-are-named-goodfetch-collie-and-goodfetch-foxhound-and-share-one-product-version.md)) provisionally.
    > Amended by [ADR 0102](0102-a-program-names-its-run-by-an-id-that-a-start-resumes-ends-it-with-a-run-report-and-reads-what-waits-and-why.md): the verb is `foxhound.startCrawl(crawl, { seeds })`, which returns a `CrawlRun` once it is started, and a start whose ID names an existing Run resumes it.
  - **`run.addSeed(url, label, payload?, { method, headers, body, priority, forefront, key })`**, or `run.addSeed(sitemap(url, rules))` (Rust's `run.add(Seed::sitemap(url, rules))`), adds a seed to a running crawl, committed at once (ADR 0037's CO-03), and answers as an enqueue does. The start reports its refused seeds as The Run in code decides. `ctx.run` is bound to its attempt, so `addSeed` called through it inside a handler is staged with the attempt, as an enqueue is.
    > Amended by [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): Rust's is `run.add_seed(seed)`, taking `impl Into<Seed>`: `run.add_seed(Seed::new(url, &label, payload))` or `run.add_seed(Seed::sitemap(url, rules))`, the request options being `Seed`'s builder methods; there is no `run.add`.
    > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-22, [#914](https://github.com/goodfetch/goodfetch/issues/914): `run.add_seed {run_id, seed, attempt?}` answers an `Enqueued`; a seed added through `ctx.run` names its `attempt` (`crawl_request_id`, `lease_epoch`) and fails with `attempt_ended` once that attempt ended. Until [#869](https://github.com/goodfetch/goodfetch/issues/869) stages an attempt's outputs, such a seed is committed at once while its attempt holds its lease, as an enqueue is. `run.add_seeds {run_id}` is a streaming call: the engine grants it 256 credits with `$/credit` (sent by the engine, one seed each), the Client sends `$/seeds {id, seeds, end?}` batches within its credits, the engine commits each batch in one write, answers it in one `$/enqueued {id, answers}` and grants as many credits again, and the call answers `{added, not_added}` once the batch marked `end` is answered; a batch beyond its credits fails it with `invalid_params`. A Run this engine does not run as a live crawl answers `run_not_found` until ADR 0102's `run_ended` is defined. `run.seeds` keeps listing the start's seeds only; a seed added later is answered to its caller. The sitemap form waits for the sitemap seed ([#903](https://github.com/goodfetch/goodfetch/issues/903)).
  - **Seeds define the scope,** so a seed widens it by its host, while a handler's `enqueue` is checked against it. The two get two names because they mean two things, and widening the scope from a handler is the explicit call (S3, G5).

### What a handler receives

- **One `CrawlContext` on every fetch tier** (S2; the pain coverage matrix's K03):
  - `request`: id, the URL the Frontier admitted, the request's own `label` (the handle for pagination), the `payload` typed by its Label's schema, `depth` and `attempt`;
  - `page`: a Collie `Page` (ADR 0085), whose `url` is the final URL and whose `session()` reaches cookies (ADR 0092);
  - `response`: the main document's final `Response`, after redirects, with its status, headers, redirect chain and a body always kept;
  - `tier`: the fetch tier of this attempt;
  - `run`: the crawl's Run, through which [Crawl output in code](https://github.com/goodfetch/goodfetch/issues/479) reaches Datasets and the Key-value store;
    > Amended by [ADR 0103](0103-a-handler-pushes-records-staged-with-its-attempt-into-datasets-its-crawl-declares-and-a-reader-never-slows-the-crawl.md): Records are pushed with `ctx.push(dataset, record)`, a member of the context beside `enqueue`, not through `ctx.run`; `ctx.run` reaches the Key-value store, whose writes through it are staged with the attempt.
  - `enqueue`, `enqueueLinks`, `skip` and `retry`.
    > Amended by [ADR 0110](0110-a-crawl-handler-reads-the-responses-its-labels-settings-kept-from-its-own-navigation.md): the context also has `keptResponse(url)` and `keptResponses(url?)`, which read the responses its Label's `fetch.kept_responses.urls` kept on the request's page from the start of its navigation, with their bodies, so a handler reads what the page loaded while the engine navigated without loading it again.
- **No second way to reach the same thing** (S2, G4): no `log` (the program's own logger), no `session` (`page.session()`), no `sendRequest` (`page.request`, ADR 0085), no selector API beside the page (Parsel- or Cheerio-like), and no `extendTimeout()` (a Label's `timeout.handler`).
  > Amended by [ADR 0147](0147-a-pages-fields-are-read-in-one-call-on-every-tier-and-a-push-takes-one-record-or-several.md) (owner's decisions of 2026-11-10, grilling of G-01 of the consolidated review): a handler reads its page's fields in one call with `ctx.page.read(fields)`, served on every tier and never escalating. No selector API beside the page still holds: `read` is a member of the page and takes the page's own locators.
- **A context belongs to one attempt.** An attempt ends when its handler returns, and early at `skip`, at `retry`, at an escalation, at the handler's timeout, at a lost lease, or when the program closes the Run. A call made after that, such as a TypeScript `enqueue` that was never awaited or a context stored for later, fails too, so a forgotten `await` never silently loses a link (G1). From then on, every call on its context fails with `attempt_ended`, naming why. An attempt whose handler returned commits what it staged; one that ended early discards it (ADR 0003). Catching it changes nothing, since the decision stands. In Python its class derives from `BaseException`, as `asyncio.CancelledError` does, so `except Exception:` lets it through; it still carries its code and group.

### Fetch tiers, per Label, and escalation

- **Collie's page on every tier.** ADR 0020 compares a sample's results fetched both ways, so one handler must run unchanged on every tier. `browser` is the browser tier; every other tier serves what it can exactly and escalates the rest to `browser`:
  - `http` and `browser_fetch` fetch the document without rendering it (`browser_fetch` sends the request from inside the Session's browser, ADR 0020); the engine serves `page` from that document: locators and reads answer from it, and so do reading AI verbs;
  - `discovered_api` fetches the document over HTTP as `http` does, and serves the page's network waits (`waitForResponse`, `waitForRequestFinished`) from the JSON calls it replays;
  - `light_browser`, ADR 0020's optional light engine (Lightpanda), runs the page's scripts without layout, so a wait for scripted content and `evaluate` are served, and a call that needs layout or pixels escalates: a gesture, `boundingBox`, `innerText`, a screenshot. Which calls it serves exactly is area 6's spec. It is used, or forced, only where the run's capabilities allow it (ADR 0020); forcing it where they do not fails when the Run opens with `capability_unavailable` (ADR 0083).
  - `browser` renders the page.

  `page.request` goes through the Session's own HTTP transport on every tier and never escalates. On the document tiers (`http`, `browser_fetch`, `discovered_api`), `goto` and `reload` are served by fetching over the same tier through the navigation gate, and `ctx.page.session().newPage()` opens a page over that tier; on `browser`, the pages a handler opens follow ADR 0085 and carry the gate (ADR 0087).
- **What a tier cannot serve escalates.** On the document tiers such calls include a gesture other than `goto` and `reload`, a popup or new tab (which needs a script or a click), `evaluate`, a network wait no replayed call answers, a screenshot, an acting AI verb or `page.lend()`; on `light_browser`, what needs layout or pixels. Under `fetch.tier: auto`, the first one ends the attempt and runs the request again in the browser. That run is neither a retry nor a failure, and it teaches the tier choice.
  > Amended by [ADR 0110](0110-a-crawl-handler-reads-the-responses-its-labels-settings-kept-from-its-own-navigation.md): on `http` and `browser_fetch`, `keptResponse` and `keptResponses` escalate too, since the page's scripts never ran, and fail with `browser_required` under a forced tier; `discovered_api` serves them from the JSON calls it replays. A Label that keeps responses while forcing `http` or `browser_fetch` fails the Run's start with `setting_not_applicable`.
- **A static document never changes,** so on `http`, `browser_fetch` and `discovered_api` a wait for something it lacks, or a read of one element that would wait for it, escalates too. Waiting for content is thus how a handler states what its page must hold. A JavaScript page fetched over HTTP whose content is missing escalates instead of passing as an empty success. A question (`count()`, `isVisible()`) answers at once and never escalates.
  > Amended by [ADR 0119](0119-every-fetch-tier-decodes-a-crawls-document-as-the-browser-does-a-label-names-the-content-types-its-handler-takes-and-exports-are-utf-8.md): a document that declares no encoding and is not valid UTF-8 can only be guessed, so a non-browser tier escalates it under `fetch.tier: auto`, and fails it with `browser_required` naming `fetch.encoding` and `fetch.tier` under a forced tier. Every tier decodes the document in the same order, and the engine gives the browser that encoding at its interception.
- **Under a forced tier, nothing escalates:** the call fails with `browser_required`, a `ProgramError` naming the Label's `fetch.tier`. For a wait on a static document, its `fix` names both remedies: the tier, or content the page may simply lack.
- **Which calls each tier serves exactly** is area 6's spec, under one rule: a call is served only when its result is exact; otherwise it escalates. "A non-browser tier" below means any tier but `browser`.
- **The unit of the tier choice.** ADR 0020's "route" is a **Label on one domain** (ADR 0004's key), which area 6's spec may split by URL path where a Label's samples disagree; the name avoids a clash with `page.route`. The setting `fetch.tier` takes `auto` (the default) or forces `http`, `discovered_api`, `browser_fetch`, `light_browser` or `browser` at any scope down to a Label. There is no per-request override: requests needing another tier are another kind of request, so another Label, which may share a handler (S2). Provenance records the tier and whether it was forced (ADR 0023).

### Collie inside a handler

- **`ctx.page` is a Collie Page** with its AI verbs: in the browser, the same object as a Collie program's page, as [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md) handed to this ticket, and on every other tier the same type, served from the document. ### A handler's own navigation and Site preferences

- **A handler's navigation that Site preferences refuse** fails, with `site_preferences_refused`, a `RefusedError` whose details name the URL and the reason, and whose `fix` names the setting. That navigation is a `goto`, a click or an acting AI verb that navigates, or a `page.request`: ADR 0086 governs it as a crawl request. The reasons are a crawl request's:
  - `robots_txt` and `crawl_delay` (ADR 0086);
  - `use_signals`, while `site_preferences.respect_use_signals` is on and an AI-use signal refuses the Run's Purpose, since the same URL enqueued would be skipped with it (ADR 0086), and a handler's `goto` must not collect what an enqueue would skip (G3).

  How the refusal surfaces:

  - **When.** What is known before the request is checked before it is sent: robots.txt and its Crawl-delay, and AI-use signals already read for the host, such as TDMRep's well-known file. A signal the response itself carries (aipref's `Content-Usage` header, TDMRep's headers and `<meta>`, RSL's `Link` header) is checked when the response arrives: the call raises then, and the engine leaves the page on a blank document, so a handler that catches the refusal cannot read what it refused (G3). A crawl request whose own response carries such a signal ends `skipped` with `use_signals` before its handler runs.
  - **A refused `page.request`** raises the same way, returns no response, and leaves the page as it was.
  - **A refused navigation that no call waits on,** such as the page's own JavaScript redirect or a popup's first navigation, is aborted at interception by ADR 0087's gate, and the page keeps its document (a popup stays blank). It is a `requestfailed` event whose failure names the Site preference, and the Run trace records it. A waiter armed for that navigation (`waitForURL`, a load-state wait after it, a popup's load) raises `site_preferences_refused`. Nothing else raises, and the request is not skipped: the handler asked for nothing the site refused.

  One code covers every Site-preferences refusal, each with its reason. A Collie program's own navigation is untouched: AI-use signals refuse no call on its page (ADR 0085).

  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-30, deep review 579-3, 579-10, 600-3 and 565-4 (G23): a page a document tier serves answers its handler's navigations and `page.request`s as Collie's page does. Each hop is judged by the Run's egress policy first, its robots.txt included, and a refusal raises `egress_refused` naming the URL, whatever `site_preferences.respect_robots_txt` says; a `page.request` header value holding a CR, an LF or a NUL raises `header_value_invalid`, nothing sent (ADR 0067). The document a navigation reaches is judged by its use signals (ADR 0086's notes for #1595 and #1599), then by the Block classification as the request's own document is: a Challenge or a captcha escalates the page at `blocked` under `auto`, so the attempt runs again in the browser and the domain learns the move (ADR 0035), and raises `blocked` under a forced tier, the page left as it was.

  > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): inside an Agent's task (`page.agent`), a handler navigation's `site_preferences_refused` is a failed action given back to the model, as every refusal inside the task is, not raised from `page.agent`.
- **If it escapes the handler,** the request ends `skipped` with that same reason, not `failed`, since the site asked not to be crawled there. A handler that catches it carries on (G1, G5).
- **A permit's wait** for the gate's per-domain limits, delay and backoff counts against neither `timeout.navigation` nor `timeout.handler`, as time in a Human pause counts against nothing (ADR 0080), and the engine renews the work item's lease meanwhile. Politeness's waits never become failures and retries, each fetching again (G5). The Run's own timeout and its Limits still apply, and the Run's live status names the wait and its setting (The Run in code).

### How a request ends

- **`ctx.skip(message)`** ends the request `skipped`, with the reason `handler` and the message.
- **`ctx.retry(message)`** ends the attempt with `retry_requested`, a `PageError` that is retryable, counted against `crawl.retry.max`. When retries run out, the request ends `failed` with that error.
- **Both unwind the handler.** TypeScript types them `never` and Python `NoReturn`. A Rust handler returns `Err(ctx.skip(…))`, since its handlers return `Result<(), goodfetch_foxhound::Error>`. Skipping is a call, not a thrown failure the program fakes (G1).
  > Amended by [ADR 0109](0109-a-rust-programs-own-code-returns-any-error-as-a-box-error-read-as-the-other-sdks-read-an-exception.md): a Rust handler returns `Result<(), BoxError>`, so `?` on any error of the program ends the attempt with `handler_failed`, while the SDK's own `Error` keeps its code; `ctx.skip()` and `ctx.retry()` return a `BoxError` holding their `Error`, so `return Err(ctx.skip(…))` stays the form, and `CrawlCall::finish` and a login step take `BoxError` too.
- **Retries.**
  - **`crawl.retry.max` is 2,** so three attempts, as Scrapy's `RETRY_TIMES`, the gentler of the two leaders (G5).
  - **What is retried:** an attempt whose error is retryable, such as a navigation timeout raised inside the handler (a `GoodfetchError` keeps its code and retryable flag, ADR 0079), and a handler past `timeout.handler` (ADR 0080).
  - **`handler_failed` is not retried** unless `crawl.retry.handler_failed` is on. A bug fails the same way every time, and each retry fetches the page again (G5).

    > Amended by [ADR 0104](0104-a-crawl-declares-its-hooks-per-stage-in-code-a-hook-returns-its-change-and-a-program-registers-its-own-plugins-by-name.md): `crawl.retry.handler_failed` also governs `hook_failed` for a Hook's own exception, and a crawl request that failed through an SDK handler's own exception (`<kind>_handler_failed`).

  - **A lost lease.** An attempt whose lease ends with no word from the program ends with `handler_lost`, an `UnavailableError` that is retryable (the engine depends on the program to answer), and counts against `crawl.retry.max`, so a request that crashes the program stops after its retries in every language and engine setup:
    - its process ended, its connection dropped, or a signal it does not handle ended it (Node's Ctrl+C, SIGTERM): the engine cannot tell this from a crash, and the docs name the remedy, closing the Run on SIGINT or SIGTERM;
    - its Attached or linked engine died with it: a resume counts each attempt that the Run's committed state shows in flight (the run file, or an imported Checkpoint) as `handler_lost`. The engine commits a lease before it hands the request to the program, so no handler runs on a lease the run file does not hold.
  - **The program's own stop counts nothing,** and the request returns to pending in the Run's committed state: `close()`, which commits after its attempts end, a dropped Rust `serve` future or Run (ADR 0078's `Drop`, which sends `$/cancel`, ADR 0080), or Python's `KeyboardInterrupt` unwinding into `close()`.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-11-18, [#2802](https://github.com/goodfetch/goodfetch/issues/2802): the program gives a leased request back by answering its `crawl_request.handle` with the error `call_cancelled`, details `{"by": "program"}` and no `closed`, not with `$/cancel`: the engine's requests and the Client's share one id space, so a Client's `$/cancel` names only the Client's own calls. The request returns to pending with its attempt uncounted, spends no retry and writes no outcome, and the same Run delivers it again; a `call_cancelled` by the browser, or with `closed` set, stays a counted failure of the attempt. A program that gives a request back every time is given it again each time, with no limit.
  - **A Rust handler's panic** is caught by `serve`, and by the blocking `serve`, and ends that attempt with `handler_failed`, as an exception does in TypeScript and Python: a panic is a bug, not a stop.
    > Amended by [ADR 0109](0109-a-rust-programs-own-code-returns-any-error-as-a-box-error-read-as-the-other-sdks-read-an-exception.md): a crawl Hook's or a login step's panic inside `serve` is caught the same way and is that function's own error (`hook_failed`, or `logged_out`'s cause).
  - **Hooks share the budget.** A Hook's retry and a retryable `hook_failed` (ADR 0033) draw on the same `crawl.retry.max`, so one request never gets two retry budgets.
  - **Not retries:** escalations and sample-comparison runs. A block's escalation by new Session follows ADR 0021.
- **Which responses reach a handler**, as Scrapy's `HttpErrorMiddleware` decides it:
  - a 2xx after redirects reaches the handler;
  - a Block cause ends `blocked` (ADRs 0021, 0045, 0048);
  - a 5xx or a 408 is retried, and fails as `response_unavailable` (a `PageError` that is retryable: the site is failing for now, as ADR 0085's `navigation_failed` is a site never answering) when retries run out; its 502, 503 and 504 also back off the domain (ADR 0086);
  - any other 4xx fails at once with `response_not_ok` (a `PageError`, not retryable);
  - `crawl.handle_statuses` (none by default, settable per Label) lists other statuses whose responses go to the handler, so a link checker reads its 404s, and the error's `fix` names it.
    > Amended by [ADR 0119](0119-every-fetch-tier-decodes-a-crawls-document-as-the-browser-does-a-label-names-the-content-types-its-handler-takes-and-exports-are-utf-8.md): a response that would reach the handler is also checked against the Label's `crawl.content_types` (`text/html` and `application/xhtml+xml` by default), after the status and Block-cause rules; one not listed ends `skipped` with `content_type` before its body is read. For an accepted type that is not an HTML document, `ctx.response` holds the body and the page holds none: a call on that document fails with `response_not_document`, on every tier, and the browser tier starts no download for a navigation; a download the handler's own gesture starts stays ADR 0085's `Download`.
  > Amended by [ADR 0118](0118-every-fetch-tier-follows-redirects-as-the-browser-does-fails-a-cut-body-and-resends-only-what-a-site-never-processed.md): a 3xx is followed only when it is one of Fetch's redirect statuses with a `Location` that parses to an HTTP(S) URL, at most `fetch.redirect.max` (19) times. Past that, the attempt fails with `too_many_redirects` (a `PageError`, not retryable). Any other 3xx fails at once with `response_not_ok`, and a redirect status listed in `crawl.handle_statuses` reaches the handler unfollowed. A cut document fails with `response_truncated` (a `PageError`, retryable) and never reaches the handler, and a transport failure with `navigation_failed`. A request that a `Retry-After` past `politeness.retry_after.max` holds ends `failed` with `response_unavailable`.
- **The skip reasons** (ADR 0079's full list):
  - `out_of_scope`: a redirect leaving the crawl's scope;
  - `domain_policy`: a redirect or a Hook's rewrite to a host the run's domain policy refuses (ADRs 0014, 0017);
  - `duplicate`: a pending request merged by a URL rule learned after its admission (ADR 0005);
    > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): also a request whose redirect reaches a URL whose key the Frontier already admitted for another request; its handler does not run.
  - `robots_txt`, `crawl_delay` and `use_signals` (ADR 0086);
  - `hook`: a before-request Hook (ADR 0033);
  - `handler`: `ctx.skip()`.
    > Amended by [ADR 0107](0107-a-runs-model-allowance-refuses-its-model-calls-once-spent-while-the-run-goes-on.md): `model_allowance`: a `ModelAllowanceReachedError` that escaped the handler, once the Run's Model allowance is reached; the Run is then `incomplete` though it finishes.
    > Amended by [ADR 0119](0119-every-fetch-tier-decodes-a-crawls-document-as-the-browser-does-a-label-names-the-content-types-its-handler-takes-and-exports-are-utf-8.md): `content_type`: a response whose type is not in the Label's `crawl.content_types`, skipped before its body is read, with a message naming the type.

  The `skipped` outcome carries `message`, the handler's or the Hook's own text. Each outcome names its request (id, URL, Label, depth); how a program reads outcomes is The Run in code's.

### Enqueueing, scope and the Frontier

- **`enqueue(url, label, payload?, { method, headers, body, priority, forefront, key })`** adds one request. In TypeScript and Python its Payload argument exists only when the Label has one, and Rust passes `()`, so a missing or wrong Payload is a type error. `method`, `headers` and `body` are Crawlee's `Request` fields and Scrapy's `Request` and `FormRequest`'s: crawling a POST or GraphQL API page by page is common, and it is what the discovered-API tier finds. Whether a non-GET request is an Effect to declare is [Effects a program declares in code](https://github.com/goodfetch/goodfetch/issues/500)'s.
  > Amended by [ADR 0106](0106-a-program-declares-an-effect-as-a-keyed-block-whose-output-the-effect-journal-keeps-judged-by-what-the-engine-sent.md): a crawl request is a read whatever its method: enqueuing it says it is safe to send again (RFC 9110 §9.2.2), so a retry, an escalation, a sample comparison, a lost lease and `retryFailed` send it again. An Effect a handler sends as a request goes through `page.request` inside `ctx.run.effect`, with its `idempotencyKey`.
- **`enqueueLinks(locator, label, payload?, { include, exclude, limit, priority })`** adds every link a Collie locator matches, each `href` resolved against the document's base URL. The locator is the page API's one way to target elements (S2). Two methods, because they return two types.
  - **A Payload per link.** `payload` may be a function of the link (its `href`, its text and its attributes) that returns the Payload, still typed by the Label, or `null` to skip that link. It answers crawlee-python #524 (one `user_data` for all links), as Crawlee's `transformRequestFunction` does; rewriting a URL stays a Hook's.
- **What they return.**
  - An enqueue's result is a value (ADR 0079): added, with its id, or not added, with `duplicate`, `out_of_scope`, `domain_policy`, `max_depth`, `max_requests` or `unsupported_scheme`; a sitemap entry matching no rule is not added with `no_rule`, reported in the Run's report rather than in an answer.
    > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): the reasons also include `invalid_url` (a URL the WHATWG parser refuses) and `max_url_length`, `max_path_segments` and `max_segment_repeats` (the caps on a URL's shape); a handler's `enqueue` resolves a relative URL against the document's base URL, while a seed takes an absolute one.
  - `enqueueLinks` returns the added and not-added URLs: a matched element with no link is reported as `no_link`, and a link its Payload function skipped as `skipped_by_payload`.
  - So "enqueued nothing" says why (G1). A Payload failing its schema still raises `payload_invalid` (ADR 0082).
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-24, [#863](https://github.com/goodfetch/goodfetch/issues/863): the engine side is two calls, since a Payload function runs in the program. `crawl_request.links {run_id, crawl_request_id, lease_epoch, locator}` reads each matched element in document order (`href` as written, `url` resolved as it will be fetched, `text`, `attributes`), and `crawl_request.enqueue_links {…, locator, label, payload? | payloads?, include, exclude, priority}` takes one Payload for every link, or one per element in that order, `null` skipping it; it matches the locator again and answers each element `added`, `not_added` with its reason, `no_link` or `skipped_by_payload`. Every Payload is checked before any link is admitted, so `payload_invalid` adds none; `payloads` of another length than the matches is `invalid_params`. An `href` is a `GET` candidate of its own in the Frontier, its query percent-encoded in the document's encoding (ADR 0120). The engine matches the locator's CSS selector in the document a fetch tier served; on a browser page the call answers `closed` until the browser tier hands pages to handlers, and `limit` waits for a later ticket.
    > Note (agent decision, on a default, not read by the owner), 2026-10-27, [#1601](https://github.com/goodfetch/goodfetch/issues/1601): `crawl_request.enqueue_links` takes `limit`, a count from 0, absent for none. It counts the links added, so a `duplicate` or another link not added uses none of it; once `limit` links are added, each later element whose link the Frontier would judge is not added, with the reason `link_limit`, its link never judged, so no other reason shows. An element without a link stays `no_link`, a link its Payload function skipped `skipped_by_payload` and a trap `trap_link`, since those answers are the element's own. The reason is `link_limit`, not `limit`, so it is not read as one of the Run's Limits.
- **Staging.** A handler's enqueues are outputs staged with its attempt and committed with it (ADR 0003), so a failed or escalated attempt leaves no stray links.
  > Amended by [ADR 0106](0106-a-program-declares-an-effect-as-a-keyed-block-whose-output-the-effect-journal-keeps-judged-by-what-the-engine-sent.md): while a declared Effect's body runs in an attempt, a call that stages an output with that attempt (an enqueue, a seed, a Record, a Key-value store write) fails with `effect_staging_refused`, since a re-run that finds the Effect in the Effect journal does not run the body again.
  > Note (agent decision, accepted by the owner on 2026-10-28), 2026-10-25, [#869](https://github.com/goodfetch/goodfetch/issues/869): an attempt's enqueues, `enqueueLinks` links and seeds added through `ctx.run` stay in the engine's memory with the attempt and reach the run file only in the write that commits its Records and its work item's success, so a crash between the two leaves the Frontier as the last commit left it. Each is answered as the Frontier will admit it, after the attempt's own earlier ones, and the position its added request takes, its ID, is reserved at once (table `work_item_positions`), so the commit gives it the ID its answer named; a discarded attempt leaves a gap among the IDs, and a request another attempt's commit added meanwhile is not added twice, its ID named in the commit's outcome (note of 2026-10-29). A Key-value store write through `ctx.run` names its attempt with `attempt {crawl_request_id, lease_epoch}` on `key_value_store.set` and `.delete`, and `.get` and `.get_bytes` through it read what it staged first; on a Run with no crawl, `attempt` is `invalid_params`. Outside a crawl's handler it answers `invalid_params`.

  > Note (owner's decision O25 of 2026-10-28 for the outcome; the rest agent decision, on a default, not read by the owner), 2026-10-29, deep review findings 581-1 and 581-2 ([#869](https://github.com/goodfetch/goodfetch/issues/869), [#768](https://github.com/goodfetch/goodfetch/issues/768)): each staged enqueue, `enqueueLinks` call or seed runs its admission once, on the run file inside a savepoint it rolls back, against what the attempt's earlier admissions did, which the engine keeps in memory beside the attempt: the identities they visited, plain and learned, with their requests, their counts against `crawl.max_requests` and each path budget, the seeds that widened the scope and the sitemaps they added. The commit still admits each again, in order, on the run file. A request the commit does not add, because another attempt's commit added it meanwhile or a rule learned since refuses it, is listed in the `succeeded` outcome's `not_added`, with the ID its staging answered, its URL, the reason and, for a `duplicate`, the request it duplicates (`duplicate_of`), so a program that kept the ID finds what became of it (owner, 2026-10-28, O25 (a)). The Frontier identities a sample comparison weighs (ADR 0103) come from the same record, for every attempt, with no read of the visited set. An attempt stages at most `crawl.max_staged_enqueues` admissions, 10,000 by default; one more fails with `staging_full`, naming the setting in `limit`, and stages nothing.
- **The Frontier.** Its identity for a request is the method, the URL after its rules and a hash of the body, whatever the Label, as Crawlee's `useExtendedUniqueKey` (amends ADR 0005's URL-only identity). `key` replaces that identity, a declared canonicalization that always wins. `priority` and `forefront` are ADR 0005's.

- **Hooks keep cross-cutting policy,** such as a header on every request, and URL rewrites (ADR 0033).

- **Scope is crawl-wide, checked on every enqueue and every redirect.**
  - `crawl.scope.strategy`: `same_hostname` by default (Crawlee's default; Scrapy allows every host when `allowed_domains` is unset), or `same_domain`, `same_origin` or `all`.
  - `crawl.scope.include` and `crawl.scope.exclude`: URL patterns matched in the engine (ADR 0081). Besides the strategy, a URL must match an `include` pattern when there are any, and no `exclude` pattern; they never replace the strategy, as Crawlee v4 learned.
  - **Measured against every seed,** with hosts compared after the Frontier's fixed URL rules, so `www.` is no other host (ADR 0005). `include` and `exclude` on `enqueueLinks` only narrow.
    > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): hosts are compared as the WHATWG parser leaves them, and the scope ignores one leading `www.` label as a rule of its own, since the identity merges `www.` only on evidence; under `same_origin`, a seed's `http` origin also admits its host's `https` origin.
  - **Bounds.** `crawl.max_depth` (seeds at 0) and `crawl.max_requests` (requests admitted) have no default. Reaching either refuses further enqueues with its reason and ends the Run `incomplete` (ADR 0005).
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-22, [#843](https://github.com/goodfetch/goodfetch/issues/843): an enqueue is one level deeper than the request whose attempt added it, and one past `crawl.max_depth` is not added with `max_depth`; `crawl.max_requests` counts every request the Frontier admitted, seeds included, and refuses the next with `max_requests`. The bounds are checked after the scope and the identity check, so a `duplicate` or an `out_of_scope` URL stays what it is and is never counted as cut, and before the URL caps. Their values are recorded in the run file when the Run begins and again when it resumes, so a resume's settings apply from then on and every admission point, a seed added to a running crawl included, reads the same ones; the count of requests admitted and each setting's count of refusals live there too. A finished Run's report lists in `completeness_reasons`, in ADR 0102's reason shape, one `{code, message}` per setting that refused something, coded by the setting (`crawl.max_depth`), its message giving the count, beside any other reason its driver gives (ADR 0118's `response_unavailable`); its Completeness is the worst they give, `incomplete` (a bound) before `unverified` (a cap). The wording of every reason, and the reasons of other causes, are #1010's.
  - **No transform function:** rewriting is a Hook's.

  > Note (agent decision, accepted by the owner on 2026-10-22), 2026-10-22, [#840](https://github.com/goodfetch/goodfetch/issues/840): `crawl.scope.include` and `crawl.scope.exclude` take globs as Playwright reads them, through the engine's one URL matcher, matched against the URL as the WHATWG parser serializes it; a pattern the matcher cannot read fails `crawl.start` with `pattern_unsupported` before the Run begins, and a regular-expression form waits for area 11's mapping of each language's patterns. A seed is never `out_of_scope`, and only a seed the Frontier adds widens the scope. `same_domain` compares registrable domains under the full Public Suffix List, private entries included, never `crawl.domain_keys`; an address is its own domain. ### Settings and the Label scope

- **A Label is a settings scope** between the Run and its requests. It takes:
  - every setting a page takes (ADRs 0083, 0085, 0091), such as `timeout.action`, `timeout.navigation`, `timeout.wait` and `locator.test_id_attribute`;
  - `timeout.handler`, `fetch.tier`, `crawl.retry.*`, `crawl.handle_statuses` and `crawl.handler.concurrency`;

    > Amended by [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): an enclosing `timeout.handler` that ends an Agent's task first fails it with `deadline_exceeded` naming that call (ADR 0080), so a Label that runs an Agent sets a longer `timeout.handler`.

  - every `session.*` key and `secrets.*` (ADR 0092), with a `login` step as an option of its declaration.

    > Amended by [ADR 0104](0104-a-crawl-declares-its-hooks-per-stage-in-code-a-hook-returns-its-change-and-a-program-registers-its-own-plugins-by-name.md): a Label also takes `timeout.hook`, for the Hooks on its requests.

- **Sessions per Label.** A Label that sets what a Session holds (`session.source`, `session.http_credentials`, `secrets.*` or a `login` step) gets Sessions from a pool of its own; Labels that set none share the Run's pool. So one crawl mixes anonymous and logged-in pages, as Scrapling routes requests to declared sessions with `sid=`, without a second Run that would split its Limits and Completeness. `session.page_check` and `session.recovery.human_pause` judge the Label's pages in whichever pool serves them, so a Page check per Label splits nothing.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-25, [#773](https://github.com/goodfetch/goodfetch/issues/773): a Label takes `session.source` beside `fetch.tier`; `session.http_credentials`, `secrets.*` and a `login` step give a Label its own pool by the same rule once they exist as Label keys, and until then are refused with `setting_not_applicable`. A Label's pool opens its Sessions from its own `session.source`, `null` opening each fresh whatever the Run's; the Run's pool opens them from the Run's. A pool's Sessions are named `session-<n>` in the Run's pool and `<label>.session-<n>` in a Label's, each pool keeping `session.pool.max_size` Sessions of its own, while a domain's proxy tier and its move to the browser tier are the crawl's, whichever pool met the block. On the browser tier each handler's page opens in its pool Session's own browser context (no longer the Run's default Session), which the pool retires once the Session is retired and no attempt holds it. A resumed crawl keeps its pool Sessions, but their browser contexts open again, without their cookies, at their next page, which their `revalidate` flag already marks.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-14, [#2418](https://github.com/goodfetch/goodfetch/issues/2418): a pool whose Sessions hold a login, a Label's from its own `session.source` or `login`, the Run's from the Run's `session.source`, sends its HTTP from the browser whatever `fetch.http_from` says, and an explicit `transport` on it fails the start with `setting_locked`; a login pool's site files are read by a transport Session of the Run's pool. HTTP credentials and secrets give a Label its own pool but hold no login. ADR 0020's note of the same day has the rule.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-18, [#2850](https://github.com/goodfetch/goodfetch/issues/2850): the `limit` naming a Label's own `session.source` or `login`, as `setting_locked` carries it, gives the run-layer origin `settings`, as the Run's does: a Label's values come from its declaration's `settings`, a scope's `settings` option (ADR 0083).
- **What a Label refuses**, with `setting_not_applicable`: the Session's identity (`browser.*`, `proxy.*`, `network.*`), which takes the Run's values in every pool, and Politeness, Site preferences, scope and Run-wide keys. The TypeScript and Python types leave them out, and Rust refuses them when the Run starts (G3).
- **Politeness per Label is declined:** two Labels on one domain share its slot and delay with every run of the user (ADR 0053). A per-domain override, as Scrapy's `DOWNLOAD_SLOTS`, would be keyed by domain, and none is added.
- **A page failing its `expectedPage`** (`session.page_check`) on a non-browser tier escalates under `fetch.tier: auto`, as a wait for missing content does. On the browser tier, or under a forced tier, it fails with `page_check_failed` (ADR 0006). A login page is a lost session on every tier.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-25, [#774](https://github.com/goodfetch/goodfetch/issues/774): a Label sets `session.page_check` in its `settings` beside `fetch.tier`, read whole; its pages are judged by it in place of the Run's, and a Label setting none is judged by the Run's. On a non-browser tier the document is judged before the handler is given it, only where its markup alone decides as the browser would: the URL against a glob or a regular expression, and an element a CSS selector finds in the markup. An `XPath` expression or a body text, read from the rendered document, or a pattern or selector the tier cannot read, leaves the page unjudged, which escalates under `auto` like a failed expected page and fails with `browser_required` under a forced tier. A failed expected page escalates under `auto` without running the handler on the cheaper tier; Provenance names `session.page_check` as the escalation's `call`. Under a forced tier it fails with `page_check_failed`, and a login page fails with `logged_out` on every tier. On the browser tier the Label's check judges every page the attempt opens, through the page's value; a navigation that fails it fails the attempt with `page_check_failed` before the handler runs, so no `fetch_tier` entry is written for that browser page.
- **`crawl.handler.concurrency` is 16 by default** (Scrapy's `CONCURRENT_REQUESTS`): the engine never leases more requests to the program at once (ADR 0081). Set on a Label, it also caps that Label's handlers, within the Run's.

## Considered Options

- **Per-request callbacks** (Scrapy, Scrapling): rejected. A function cannot cross the connection or a Checkpoint, so it needs a registry of names, which a Label already is. **One handler that switches on the Label** (Spider-rs): rejected; every program writes its own router, with no Payload typed per kind.
- **A default handler** (Crawlee's `addDefaultHandler`): rejected. It catches unlabelled seeds and misspelled labels alike; seeds name their Label, and typed handles catch misspellings.
- **Declaring a Label and its handler in one call:** rejected for the TS7022 trap and Rust's ordering, above. **Handlers registered on the Run after it starts:** rejected; a request can arrive before its handler. **A crawl class to subclass** (Scrapy's `Spider`): rejected; inheritance as configuration, and a method name doubling as a persisted name.
- **A context whose shape changes with the tier** (classic Crawlee): rejected; it is the rewrite users complain of (§3.2). **A selector API beside the page:** rejected by S2. **A restricted context type** (Crawlee's adaptive crawler): rejected; a third shape to learn, when the page API already reads a static document.
- **Failing instead of escalating** when an HTTP-tier handler touches the browser: rejected while the engine chose the tier, since its guess is no bug of the program's; kept when the program forced the tier. **Loading the browser mid-handler and carrying on:** rejected; one attempt would read two documents.
- **A tier per request** (Scrapling's `sid=`, scrapy-playwright's meta): rejected by S2; a Label is a kind of request. **Tiers chosen at build time** (Spider-rs's Cargo features): rejected by ADR 0038's rule that a capability is a setting.
- **Retrying `handler_failed` by default** (Crawlee): rejected by G5. **Never retrying any handler error** (Scrapy): rejected; a retryable code raised inside, such as a navigation timeout, deserves the retry it signals. **`RetryRequestError` with no cap** (Crawlee): rejected; `ctx.retry()` counts against `crawl.retry.max`.
- **Skip and retry as return values:** rejected; a helper deep inside a handler could not use them. **A flag set, then a return** (Crawlee v3): rejected; forgetting either half is silent.
- **Every non-2xx reaching the handler:** rejected; a 404 would pass as a handled page unless every handler checked. **Retrying 4xx:** rejected by G5.
- **A selector string for `enqueueLinks`** (Crawlee): rejected by S2; the locator is the page API's one way to target elements. **Patterns replacing the scope strategy** (Crawlee v3): rejected; Crawlee v4 reversed it. **Scope relative to the current page** (Crawlee): rejected; a redirect to another host would carry the crawl there. **Scrapy's open default** (every host): rejected by G5.
- **Queue additions written through at once** (Crawlee v4's default): rejected for a handler's enqueues; staging them with the attempt keeps a failed attempt's links out, as ADR 0003 stages every output.
- **Politeness per Label:** rejected; it belongs to the site, and per-Label values would be ignored (G3) or a way to press a site harder (G5).
- **`Request` in a crawl namespace** for the noun: rejected; one name with two meanings in one SDK (S3). **Visit, task or work item:** rejected as unfamiliar.
- **Run-wide Sessions only:** rejected; a crawl mixing anonymous and logged-in pages would need two Runs, splitting its Limits, Usage and Completeness. **A Session named per enqueue** (Scrapling's `sid=`): rejected by S2; the Label already names the kind of request. **Every Session setting splitting the pool:** rejected; a Page check per Label would give each Label its own logins.
- **Failing a failed expected page on every tier:** rejected; a JavaScript page fetched over HTTP would fail where the browser passes.
- **One code, retryable or not by status:** rejected; ADR 0079 gives each code one flag. **A site's 5xx as an `UnavailableError`:** rejected; ADR 0079 keeps that group for what Goodfetch depends on, and ADR 0085 makes a site that never answers a `PageError`.
- **AI-use signals leaving a handler's navigation alone,** as a Collie page's: rejected; the navigation is a crawl request (ADR 0086), and a handler's `goto` would collect what the same URL enqueued skips. **A code of its own for a use-signal refusal:** rejected by S2; one Site-preferences code carries its reason.
- **A Rust handler's panic as the program's stop:** rejected; a panicking handler would re-run forever where the same bug in TypeScript or Python ends `handler_failed`. **An unhandled signal counting nothing:** rejected; the engine cannot tell it from a crash, which must count.
- **Plans keyed by the Label on a domain:** withdrawn in round 10; ADR 0091 keys them by call, with one variant per page layout.
- **A permit's wait counting against the timeouts:** rejected by G5; a busy domain would turn into `deadline_exceeded` and retries, each fetching again. **Skipping the request when the page's own script is refused a navigation:** rejected; the handler asked for nothing the site refused.
- **A dropped `serve` future counting as a lost lease:** rejected; it is the program's own cancellation, which the engine hears through `$/cancel`, and a Rust service that stops on a shutdown signal would use a retry per leased request at each restart.
- **A failed-request handler** (Crawlee's `failedRequestHandler`): rejected, on the owner's condition that The Run in code offers a live, filterable sequence of outcomes (only `failed` and `blocked`, as they happen, in ADR 0081's iterator shape), which covers that callback's real-time use; ADR 0102's draft ([PR #521](https://github.com/goodfetch/goodfetch/pull/521)) offers `run.outcomes({ kinds, labels })`. A failed request is an outcome value (ADR 0079), and a callback would be a second channel for the same fact (S2). A Hook stage before a retry stays a Hook question.
  > Amended by [ADR 0102](0102-a-program-names-its-run-by-an-id-that-a-start-resumes-ends-it-with-a-run-report-and-reads-what-waits-and-why.md): the sequence is `run.outcomes({ kinds, labels, after })`, read from the Run's committed state as each outcome commits and filtered in the engine; `after: "now"` starts it at the next commit.
- **Crawl requests that are only GET,** with headers and bodies left to Hooks (this ADR's first draft): reversed by the owner. Crawling a POST or GraphQL API is common, Crawlee and Scrapy take a method and a body per request, and a Hook would have to rebuild per request what the program knew at enqueue.
- **One Payload for every link of `enqueueLinks`** (this ADR's first draft): reversed by the owner; per-link data then needed a loop of `enqueue`, crawlee-python #524's complaint.
- **A re-run after a lost lease that never counts:** rejected; a request that crashes the program would re-run forever. **One that always counts:** rejected; a clean stop would use up retries.

## Consequences

- **Amends ADR 0020.** Its route is a Label on one domain; a program forces a tier per Label with `fetch.tier`; a call only a browser serves, a wait for missing content and a failed `expectedPage` on a non-browser tier escalate the request; `tier_race` is `fetch.tier_race`.
- **Amends ADR 0040**, whose `tier_race` is `fetch.tier_race`.
- **Amends ADR 0033**, whose Hook retries and retried `hook_failed` draw on `crawl.retry.max`.
- **Amends ADR 0005**, whose Frontier identity for a request is its method, its URL after the rules and a hash of its body.
- **Amends ADR 0006.** A page failing its expected page on a non-browser tier, under `fetch.tier: auto`, escalates to the browser instead of stopping the work item.
- **Amends ADR 0023**, whose per-run or per-call switch of the sample comparison is also set per Label: `fetch.tier` forces a tier at any scope down to a Label.
- **Amends ADR 0079.**
  - The noun is crawl request, and the type is `CrawlRequestOutcome`, which names its request.
  - The skip reasons are listed, and `skipped` carries a message.
  - `handler_failed` is not retried unless `crawl.retry.handler_failed` is on.
  - In Rust, a handler's panic, caught by `serve`, ends its attempt with `handler_failed`.
  - `skip()` and `retry()` end a handler's attempt.
  - In Python, `AttemptEndedError` derives from `BaseException` rather than `GoodfetchError`, the one class outside the hierarchy, as `asyncio.CancelledError` is outside `Exception`.
    > Note (agent decision, on a default, not read by the owner), 2026-11-19, [#3021](https://github.com/goodfetch/goodfetch/issues/3021): the fields every error carries live on `BaseGoodfetchError(BaseException)`, hand-written in Collie's Python client package and not exported. `GoodfetchError` extends it and `Exception`, as `ExceptionGroup` extends `BaseExceptionGroup`, and `AttemptEndedError` extends it alone. The SDK's own relays, a call's reply, a sequence, a listener and the sync client's private loop, catch `BaseGoodfetchError`, so the end reaches the code that made the call; a program catches `GoodfetchError` or `AttemptEndedError`.
