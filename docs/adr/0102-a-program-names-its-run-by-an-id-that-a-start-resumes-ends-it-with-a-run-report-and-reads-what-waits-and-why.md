# A program names its Run by an ID that a start resumes, ends it with a Run report, and reads what waits and why

ADR 0078 makes the Run a value the program opens, and ADR 0002 makes it resumable from its committed state, but nothing said how a program starts one, resumes it, follows it, ends it or reads what it did. This is where the leaders fail most visibly ([synthesis](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/2026-10-14-consumer-api.md) pains 6 and 10, [crawl frameworks](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/crawl-frameworks.md) §6.3 and §6.4):
- **A Run is inferred from a storage folder.** "The second time the code is run it does not work" ([crawlee#1602](https://github.com/apify/crawlee/issues/1602)). Crawlee 3.18.2 purges its default queue on a second `run()`, crawlee-python 1.10.4 still does, and a user spent two days on a restart with `purgeOnStart: false` that seemed to do nothing until a maintainer showed it resumed ([crawlee#3315](https://github.com/apify/crawlee/issues/3315)). Its maintainers write that "people are still asking about the storages, purging, resuming" ([#1782](https://github.com/apify/crawlee/issues/1782)).
- **Resuming and retrying are fragile.** Resuming a Scrapy `JOBDIR` job is "only supported when the spider is paused by stopping it cleanly" ([jobs.rst](https://github.com/scrapy/scrapy/blob/2.19.0/docs/topics/jobs.rst#L104-L107)). Re-running a crawl's failed requests has been asked of Crawlee since 2022 ([crawlee#1363](https://github.com/apify/crawlee/issues/1363), open), and Firecrawl's v2 API has no resume and no retry.
- **Status is counts with no reasons.** Crawlee logs "Crawled N pages, F failed requests, desired concurrency C" every 10 s, and Scrapy "Crawled N pages (at R pages/min)" every 60 s. Neither says why a request waits, and Crawlee hung silently for years ([#505](https://github.com/apify/crawlee/issues/505), [#1829](https://github.com/apify/crawlee/issues/1829)).

Crawlee 4, unreleased, now keeps the same request manager across repeated `run()` calls and warns when a run processes nothing; Scrapy 2.19 adds a `/status` endpoint so its MCP server can say why a crawl is slow. Decided in [The Run in code](https://github.com/goodfetch/goodfetch/issues/478), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), every answer decided by the agent on the owner's delegation, with its [grilling record](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6181744417), [round 5](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6181977614), [round 6](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6187864261), [round 7](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6188091534), [round 8](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6189565195), [round 9](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6189958305), [round 10](https://github.com/goodfetch/goodfetch/issues/478#issuecomment-6190148240) and round 11 with its clarifications. [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md)'s owner-confirmed changes ([R1 to R5](https://github.com/goodfetch/goodfetch/issues/477#issuecomment-6187919342)) are taken as they stand. Principles are cited by their IDs in [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md). It builds on these decisions:
- [ADR 0091](0091-collies-ai-verbs-live-on-the-page-replay-from-a-plan-file-the-run-names-and-expect-runs-a-success-check.md): the Plan file a start takes, and the `PlanReport` the report carries;
- [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md): the Human pauses progress shows;
- [ADR 0093](0093-a-crawl-declares-its-labels-and-one-handler-each-and-a-handler-reads-collies-page-on-every-fetch-tier.md): the crawl declaration a crawl's start takes;
- [ADR 0095](0095-both-products-speak-one-protocol-from-one-catalog-marked-by-product-and-their-sdks-share-collies-client-packages.md): the connections that carry these verbs;
- [ADR 0099](0099-every-surface-spells-each-catalog-name-by-its-own-rule-shapes-come-from-declared-kinds-and-call-is-the-way-down.md): the rule for reads on a handle in each language, and the catalog's names;
- [ADR 0100](0100-collies-agent-is-one-bounded-call-on-a-page-judged-by-the-programs-success-check-and-replayed-whole-from-the-plan.md): an Agent's task in the Run's Verdict and Plan;
- [ADR 0101](0101-a-model-is-named-provider-slash-model-its-capabilities-and-prices-are-declared-and-every-ai-result-carries-its-priced-usage.md): the `RunUsage` the report carries, and its applied Limits;
- [ADR 0103](0103-a-handler-pushes-records-staged-with-its-attempt-into-datasets-its-crawl-declares-and-a-reader-never-slows-the-crawl.md): the Records, Sinks and Exports the report counts and a view reads;
- [ADR 0104](0104-a-crawl-declares-its-hooks-per-stage-in-code-a-hook-returns-its-change-and-a-program-registers-its-own-plugins-by-name.md): the observe-only stages a program watches through the Run's own values.

## Decision

### Starting a Run

- **Two verbs, which return once the Run is started, never at its end:**
  - `collie.start(options?)` returns a `Run`. A Foxhound connection carries it under the same name (ADR 0095).
  - `foxhound.startCrawl(crawl, options)` returns a `CrawlRun`, whose handlers run from then on. It is Firecrawl's `start_crawl` (S3). A crawl cannot share Collie's `start` on one connection: one name would have two return types (S2), and Rust has no overloading.
- **Their options:** `id` (below), `settings` (ADR 0083), `timeout` and `limits` (ADR 0080) and `plan` (ADR 0091); a crawl adds `seeds`, at least one.
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): the option is `runId` (`run_id` in Python and Rust), whose doc comment opens with the rule below; `run.id` keeps its name.
- **Per language:** Python's `start(id=…)` and `start_crawl(crawl, seeds=[…], id=…)`; Rust's `collie.start().id("…")` and `fox.start_crawl(&crawl, seeds).id("…")`, `IntoFuture` builders (ADR 0080). `start` and `startCrawl` are two members of the shared Connection, as ADR 0099 requires of Collie's Run start and Foxhound's crawl start: `start` is `run.start`'s member, and `startCrawl` the crawl start's. Reads on a handle, such as `run.startedAs`, follow ADR 0099's rule: a method in TypeScript (`run.startedAs()`), a property in Python, a method in Rust.
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): Python's `start(run_id=…)` and `start_crawl(crawl, seeds=[…], run_id=…)`, Rust's `.run_id("…")`.
- They call the catalog's run operations, whose CLI and MCP spellings ADR 0099 derives from their canonical names and whose CLI commands are area 11's: `start` calls ADR 0036's start operation, `run.start`, then the resume operation when the Run it returns is interrupted (below); `startCrawl` calls the crawl start, `crawl.start` as ADR 0095 names it, whose entry area 3's spec writes.

### The Run's ID

- **A program may name its Run** with `id`; otherwise the engine generates one. `run.id` is always set, and every error raised in the Run carries it (ADR 0079). An ID names one Run in the Run index for good (ADR 0031): a Run is never inferred from a storage folder.
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): with `runId`.
- **Its characters** are area 3's spec, since the ID also names the Run's folder (ADR 0036). One the spec refuses fails with `run_id_invalid`.
- **The ID is the program's idempotency key,** as Stripe's are. A start calls ADR 0036's start operation (`run.start`, ADR 0099's singular namespace), which is unchanged: it returns the Run of a matching ID, live or ended, and refuses a mismatch, as the Daemon's scheduler relies on after a restart. The SDK's start then acts on that Run, as this table says. It resumes an interrupted Run through the catalog's resume operation, and refuses one that another writer holds, since the program would have to drive it or serve its handlers:

  | The Run of that ID | The start |
  |---|---|
  | none | begins it: `run.startedAs` is `new` |
  | interrupted: no live writer after a crash; `stopped` by a close, an abort, its timeout, the engine's loss or exhausted resources; waiting for its script (ADR 0031); or `failed` | resumes it from its committed state, the run file on this machine or an imported Checkpoint, at the next run epoch (ADRs 0002, 0003): `resumed` |
  | `stopped` by a Limit still used up: no person has raised it, and the period of a Limit that counts per period has not reset | raises `limit_reached` (ADR 0041), which names the Limit's scope and the scope's ID and when its period resets, and whose `fix` names the Console, where a person raises the Limit and the Run waits for its script (ADR 0031) |
  | ended `finished` | returns it as it is, with no handler called: `ended`. Only `retryFailed` reopens it (below) |
  | live, with a writer: another program, or this one | raises `run_in_use` |
  | started with other inputs, or by another caller | raises `run_conflict`, listing each difference |
  | listed in the Run index, its state missing or unreadable | raises `run_state_unavailable`, and never starts afresh under that ID |

  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
  > Note (agent decision, not read by the owner), 2026-11-18, [#1544](https://github.com/goodfetch/goodfetch/issues/1544): the engine's `run.start` and `crawl.start` apply this table themselves, rather than returning the Run as it is for the SDK to act on, so every surface (an SDK, the CLI, MCP, a Schedule) gets the same answer. An interrupted Run resumes through `run.resume`'s path within the start, which answers `resumed`; a finished one answers `ended` with the Run as it ended; `existing` leaves `startedAs` (pre-release). A Run this engine writes raises `run_in_use` with its folder, as one another engine writes does through the writer lock, and `run.resume` answers it the same. A Run listed in the Run index and not erased whose run file is gone raises `run_state_unavailable`; a start with no Run ID reads no index row. This supersedes the #218 note's `existing` for a Run live in the engine or finished. A start under the ID of a Run a Limit stopped is refused with `limit_reached` while a Limit that holds it has nothing left, as a new Run's start is, and resumes the Run once a person raised the Limit or its period started again; with the Console gone (ADR 0137), its details carry no `fix`. The caller is the OS user on every surface the engine has yet, so `run_conflict` names `caller` once a Daemon with accounts gives callers that differ.

- **The caller** is who the connection acts for (ADR 0031): the OS user on a single-user install, the person on a Daemon with accounts, a named token acting for the person who created it. A per-launch protocol token never counts, so a Daemon restart changes no caller. Another caller's ID is taken, so a start under it raises `run_conflict` naming `caller`.

- **What one ID gives.** A program run again under its ID carries on where it stopped, which is how Scrapy's `JOBDIR`, Crawlee 4's repeated `run()` and Scrapling's `crawldir` behave (S3), with the name written in the code rather than found on disk (G2). A crash loop under one ID keeps one set of Limits and one Usage (G5). A Collie program run again under its ID finds its Sessions and its Effect journal, so an order placed before a crash is checked, never placed again (ADRs 0002, 0010, G5).
- **No restart and no purge.** Crawling again is a new Run, under a new ID or none; the old one stays in the Run index (S2). Recurring Runs are ADR 0036's Schedules.
- **Logged** through the host's logging (ADR 0078): a resume at info, a start that found its Run ended at warning.

### Resuming

- **The inputs must match,** or the start raises `run_conflict`:
  - the Product and the kind of Run, a crawl or a Collie Run;
  - a crawl's seeds, after the Frontier's URL rules (ADR 0005), a sitemap seed (ADR 0093's R3) compared by its URL and its rules;
  - the Plan file's path and its stable identity (ADR 0091), never its version, which a promotion changes;
  - the Response recording a start names, compared as the Plan file is ([ADR 0105](0105-a-programs-tests-replay-a-response-recording-in-a-test-engine-that-reaches-no-site.md)).

  A crawl's declaration is checked as ADR 0093 says: pending requests of a Label no longer declared raise `label_unknown`, a changed Payload schema follows ADR 0082, and a new Label is accepted. Handler code is the program's own and may change.
- **What may change:**
  - `timeout`: the resumed Run's own, on a fresh clock (ADR 0080).
  - `limits`: a value equal to the one the program gave when the Run began changes nothing, so a person's raise stands; any other value at or below the Limit as it stands lowers it; a value above it raises `limit_raise_refused`, since only a person raises a Limit (ADR 0041).
  - `settings`: a value changed since the Run began applies from the resume on and is recorded in the Run trace with its layer, and one pressing a site harder is recorded as ADR 0086 says. A key the settings schema marks as fixed for a Run's life raises `setting_not_applicable`, whose `fix` names a new Run. The fixed keys are those that decide the Run's scope or what its committed results mean, `crawl.scope.*` at least; area 3's spec lists them.
    > Amended by [ADR 0107](0107-a-runs-model-allowance-refuses-its-model-calls-once-spent-while-the-run-goes-on.md): a raised Model allowance (`ai.allowance.*`) opens a new cut-off from the resume on, so a reached allowance is reached no longer; the requests skipped with `model_allowance` before it stay skipped, as every skip does.
    > Amended by [ADR 0120](0120-the-frontier-parses-urls-as-browsers-do-fixes-only-safe-rules-learns-the-rest-on-evidence-and-caps-a-urls-shape.md): `crawl.keep_url_fragment` is one of the keys fixed for a Run's life, since the keys of the requests already admitted would no longer match.
- **Requests in flight.** A resume counts each attempt that the Run's committed state shows in flight, in the run file or an imported Checkpoint, as `handler_lost` against `crawl.retry.max`; a request that the program's own stop returned to pending (`close()`, `stop()`, a dropped Rust `serve` future, `$/cancel`) counts none (ADR 0093).
  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-18, [#2801](https://github.com/goodfetch/goodfetch/issues/2801): on the wire, a Client answers an engine's request that its program dropped unanswered, such as a Rust `HandlerCall` dropped, with `call_cancelled` (JSON-RPC class -32006, not retryable) whose details are `by: program` and no `closed`, and the engine reads that answer as the program's own stop of that request ([#2802](https://github.com/goodfetch/goodfetch/issues/2802)). A request of a method no stream of the Client serves is answered with the protocol's method error, `method_not_found` (-32601).
- **Each seed's answer.** A seed is checked as an enqueue is (ADR 0093), so one the run's domain policy refuses, a duplicate or one with an unsupported scheme is not added. `run.seeds` lists each seed's `Enqueued` answer, read with no round trip; on a resume, the answers given when the Run began. A seed is one request among many, so its refusal never raises (ADR 0079). A start whose seeds were all refused still starts, and its Run finishes at once unless `crawl.keep_alive` holds it. A sitemap seed is answered once its first sitemap is admitted; its sitemaps are read while the Run works, so what they add is in the progress and the report (below).

### Following a Run

- **`run.progress()`** is ADR 0081's telemetry sequence (an `EventStream` in Rust) of `RunProgress`. It subscribes when called, and its first value is the Run's progress at once. Each later value is the latest after a change, coalesced under load (ADR 0024), and the last one says how the Run ended. There is no separate one-shot read (S2): a program reads one value and leaves the loop.
- **`RunProgress`**, for every Run:
  - `lifecycle`, and `writer`: `live`, or `none` when nothing works the Run, as after a crash, until a start with its ID resumes it;
  - `epoch`: the run epoch (ADR 0003), which a resume or a migration to another machine advances, and `checkpointAt`: when the last Checkpoint was written, or none;
  - `pauses`: each Human pause waiting (ADR 0092), with its Session and page, its `reason`, its `until` as text, whether the program or the engine raised it (and for the engine, the step: a login recovery or the Challenge ladder), since when, and its `deadline`: the first of `timeout.human_pause` and, in a scheduled run, ADR 0036's pause timeout, or none when it waits without limit. A pause beginning or ending is a change, so it gives a new value; the Run trace records both, and ADR 0027's Notification and the Console's "Needs you" reach the person. Its time counts toward no timeout, the Run's own included, while its Usage counts toward Limits (ADR 0092);
    > Amended by [ADR 0113](0113-a-human-pause-whose-page-closes-raises-call-cancelled-naming-what-closed-and-a-lost-live-view-ends-no-pause.md): the Run trace records how each pause ended: its condition, a person's "Done" or "Hand back", a "Decline", its timeout, the program's own cancel, or stopped with `call_cancelled`'s `by` and `closed`.
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
  - `message`: the program's own status line, set with `run.setProgressMessage(text)` and shown in the Console, as Crawlee's `setStatusMessage` sets one (ADR 0037's RT-15).
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
- **`CrawlRunProgress`** adds:
  - `requests`: the crawl's requests pending, being fetched, being handled and in a Human pause, and the ended ones by kind, skip reason, Error code and Block cause;
  - `waiting`: why due requests are held, one group per reason, each with its count, the domains it holds with when each is next admitted (a fixed number of domains per reason, the rest counted), and the setting behind the wait, with its value and layer, as ADR 0079's `limit` names one. The reasons are `domain_concurrency` and `domain_delay` (ADR 0086), `crawl_delay`, `backoff` (a 429, 502, 503, 504, or a connection refused or timed out), `robots_txt` (not served yet), `handler_concurrency` (`crawl.handler.concurrency` handlers already running), `governor` (ADR 0040's governor admitting nothing new), `session` (waiting for a Session of the pool, such as one logging in) and `human_pause`. A reason a newer engine sends is kept (G3);
    > Amended by [ADR 0118](0118-every-fetch-tier-follows-redirects-as-the-browser-does-fails-a-cut-body-and-resends-only-what-a-site-never-processed.md): `backoff` also covers a `Retry-After`'s wait, with `politeness.retry_after.max` as its setting when the site's time is the longer.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-26, [#766](https://github.com/goodfetch/goodfetch/issues/766): `backoff` also covers a site's HTTP/2 `ENHANCE_YOUR_CALM`, which backs off its domain as a 503 does (ADR 0118), and never a proxy's own answer: a forward proxy's 429 or 502 naming its own error in `Proxy-Status`, or a tunnel it refused, lowers that proxy's ceiling and holds no domain (ADR 0053). The protocol's description of the `backoff` reason names both.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-10-29, deep review findings 213-4 and 213-10 ([#1547](https://github.com/goodfetch/goodfetch/issues/1547)): `waiting` also names `politeness_file`, a domain held because ADR 0053's shared Politeness file refused its take, such as one busy past its timeout, until the Run tries it again; before, such a domain showed under `domain_concurrency`. A crawl's admission keeps each reason's requests and domains counted as its queues change, so a progress value costs the domains that changed since the last one and the 10 it names, not a walk of every domain: the domains named are the first 10 by name.
    > Note (agent decision, on a guarantee, not read by the owner), 2026-11-23, [#1762](https://github.com/goodfetch/goodfetch/issues/1762): `waiting` also names `rate_cap`, the due requests no domain holds while a handler is free and the governor admits, held by the Run's rate cap, `admission.max_requests_per_minute` (ADR 0028's note of 2026-10-21), with the cap as its `setting` and each domain's `next_admitted_at` the cap's next admission, or none for a cap of 0, which admits nothing; before, such a request showed as pending with no reason. `handler_concurrency` and `governor` come first, since a request they hold would not go at the cap's moment either.
  - `inFlight`: each request being fetched or handled, with its phase, tier, attempt and start time, a short list since concurrency bounds it. One being handled carries `waiting` while its handler's own navigation or fetch waits for a permit, which counts against no timeout (ADR 0093): the reason and the setting behind it, as a wait group has them;
  - `sitemaps`: per sitemap seed (ADR 0093's R3), the sitemaps read, each sitemap it could not read with its URL and why (a fetch failure with its status, robots.txt, a document it could not parse; a fixed number, the rest counted), the entries added, and the entries not added counted by reason, `no_rule` and an enqueue's other reasons (ADR 0093), never listed one by one, since a sitemap holds up to 50,000;
  - `idle`: true while `crawl.keep_alive` holds the Run `running` with an empty Frontier and nothing in flight, until `addSeed` gives it work;
  - `concurrency`: the handlers running against `crawl.handler.concurrency`, and the governor's level (normal, pressure or critical), its open pages against the allowance and what set that allowance: a cgroup, a Job object, `memory_allowance` or half of physical memory (ADR 0040). The research's autoscaling pain ([crawl frameworks](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/crawl-frameworks.md) §6.13) becomes a stated reason.
    > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): a Run's progress also carries `storage`, the worst storage level among the filesystems it writes to, with that filesystem's folder and free space.
- **No event per stage** (ADR 0104's observe-only stages). Each shows in a value the Run already has: its start in the start's return (`startedAs`), a Checkpoint in `checkpointAt` and the report's `checkpoint`, a migration as a new `epoch`, a Limit reached and a stop in the last progress value and the report's `stopReason`, a request ending, ADR 0104's `request_ended`, as an outcome. A second channel for the same facts would break S2.
- **No periodic status line.** No SDK logs one, as Crawlee's every 10 s and Scrapy's every 60 s: `progress()` and the Console replace it, and a program logs progress values at the rate it wants (G4). The engine's logs of state changes, such as a Run resuming or a domain backing off, reach the host's logging as ADR 0078 says, and the CLI's own output is the CLI's design.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-23, [#1547](https://github.com/goodfetch/goodfetch/issues/1547): on the wire, `run.progress` is a cancellable read, as #1545 made `run.outcomes` one: without `after` it answers the Run's progress at once; given `after`, the `position` of the value the reader last read, it waits for a change and answers the latest value, so the values in between coalesce; the SDK's sequence calls it again with `after` until a value whose `last` is true, which says how the Run ended (`lifecycle`, `stop_reason`, `writer: none`) or that no engine this one reaches works it. Positions start in the run epoch's own range, so they go up across a resume, and a value read from committed state sits after every live value of its epoch. A value carries its own time, `at`. `checkpointAt` is known only to the engine that wrote the Checkpoint: a value read from run state has none. The `run.progress` event carries each value as the engine holds it, without the parts an area reads from committed state when a value is read (a crawl's `requests`). A view's `report()` is `run.report`, which waits for a live Run's end and raises `run_interrupted` (`UnavailableError`, not retryable, its `fix` naming a start with the Run's ID) for a Run with no live writer that has not ended. A read of a Run another engine works (`run.progress`, `run.report`, the Key-value store's `get`, `run.outcomes` and `run.failed_requests`) is forwarded to the owner the Run index names, as #219 forwards an abort, when a reader's test finds the writer lock held; when that owner does not answer, the read goes on from committed state, and `run.report` reads the run file again every second until the Run ended or its writer is gone. The Run trace's and Records' reads take the same path when their tickets (#1048, #961) add them. A crawl's `waiting` groups carry `reason`, `count`, at most 10 `domains` (each with `next_admitted_at`, none while a domain waits for a request in flight to end), `more_domains` and `setting`, a `SettingLimit` as `deadline_exceeded`'s `limit`; the reason is a string, so a reason a newer engine sends is kept. `inFlight` lists each attempt with `phase` (`fetching`, then `handling`), `tier`, `attempt` and `started_at`, and `concurrency` names `handlers`, `handler_concurrency` (per serving Connection), the governor's `level`, `open_pages`, `page_allowance` and `allowance_set_by`. A Human pause shows `session` and `page` by their IDs and `raised_by` as `{ by: program }` or `{ by: engine, step }`.

### Ending a Run

- **`run.finish()`** lets the Run finish, ends it `finished`, closes its Sessions and pages, and returns its Run report, a `RunReport` (a crawl's `CrawlRunReport`):
  - a Collie Run finishes at once, since its program says it is done;
  - a crawl finishes once its Frontier is empty and nothing is in flight;
  - a detached Run (below) finishes when the engine ends it.

  If something stops the Run first (a Limit, its timeout, a person, the engine), `finish()` returns the report saying `stopped`: an expected outcome (ADRs 0029, 0079). A Run that ends `failed` makes `finish()` and `stop()` raise the error that failed it, as ADR 0079 has a failed ending of AI work raise.
- **Its wait** has no timeout of its own by default: the Run's own `timeout` bounds it (ADR 0080). A `timeout` or `signal` given to `finish()`, a cancelled task or a dropped future ends only the wait, and the Run goes on.
- **`run.stop()`** stops the Run at its next safe point with a Checkpoint, `stopped` and `incomplete` as an abort by its program (ADR 0029), and returns its report; the Run stays resumable by its ID. It stops a Run as `close()` does, so its wait is bounded by `timeout.close` (ADR 0080), or by a `timeout` given to it. Past that, it raises `deadline_exceeded` naming the setting, and the Run still stops at its next safe point, so a shutdown never hangs silently on a handler that does not return (G6).
- **`close()` is ADR 0078's, unchanged.** A scope left without `finish()` therefore stops the Run: honest, since the program never said it was done (G1).
- **A Collie Run its program finishes is `complete`:** the program defines its scope and says it reached its end. A crawl's Completeness stays ADR 0005's. Its Verdict follows ADR 0091: a Run whose program called `act` or `observe` is `verified` only when an `expect` evaluated after the last such call passed, and one whose only AI steps are `extract` is judged by Grounding.
- **Promotion** (ADR 0091). A Run that `finish()` ends `finished` and `verified` has its new Plan versions written to its Plan file on the program's machine before `finish()` returns; otherwise they stay pending with the Run in the Run index, for a person in "Needs you". A stopped Run promotes nothing. The report's `plan` says which.
  > Amended by [ADR 0116](0116-a-saved-file-is-written-whole-or-not-at-all-and-a-failed-write-says-whether-its-path-or-its-storage-failed.md): when the write of the Plan file, or of a recording Run's Response recording (ADR 0105), fails, the call that ends the Run (`finish()`, `stop()`, `close()`, Rust's `serve`) raises `path_not_writable` or `file_write_failed` once the Run has ended, unless the Run itself ended `failed`, whose error it raises instead. The Run's ending is unchanged, its report keeps a `RunWarning` whose code is the Error code and whose message names the path, read with `openRun(id).report()`, and the new Plan versions stay pending with the Run for a person.
- **Keep-alive crawls** (ADR 0037's RT-12): with `crawl.keep_alive`, `false` by default, a crawl's Run stays `running` with an empty Frontier, waiting for `addSeed`, until `finish()` lets it end once drained. While it waits, its progress says `idle`, and its idle time counts toward the Run's own `timeout`; `stop()`, `close()`, a person or a Limit stop it as any Run.
- **Rust:** `crawl.serve(&run).await` returns the crawl's report once the Run ends, since serving is what lets a crawl finish; `goodfetch::blocking`'s `serve` does too. `run.finish()` exists as well, for Collie Runs and to end a keep-alive crawl from another future while `serve` runs (S1).

### The Run report

- **A Run report** is what a Run states about itself when it ends. **Run report** joins `GLOSSARY.md`, uniting the "run report" of ADRs 0026, 0028, 0031 and 0033 and the "run's result" of ADRs 0041, 0049, 0053 and 0086. `finish()` and `stop()` return it, `serve` in Rust, and a view (below) reads it later.
- **What it holds:**
  - the three axes (ADR 0029): `lifecycle` (`finished` or `stopped`), `stopReason` (a Limit, with its name, its scope and the scope's ID, and when its period resets; `timeout`, `abort` with who stopped it, `engine_lost` or `resources`), `verdict` and `completeness`, each with the reasons it is not `verified` or not `complete`. The Verdict is the Run's, reading every check the Run relies on, each AI task's Success check included; its reasons name each AI task that is not `verified`, an Agent's included, by its `callId`, as the task's own result gives its Verdict (ADR 0100);
    > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): `resources` carries `resource` (`memory` or `storage`) and, for storage, the folder. When even the commit that records a storage stop fails, the Run is left interrupted and the call waiting on it raises `resources_exhausted`.
  - `usage`: the final `RunUsage` of ADR 0101, its uncapped mark included (ADR 0041). Each applied Limit in it names its scope's kind and the scope's ID (the Run, a Client connection, a Schedule, a named token, a person, the Daemon, the install, a Partitioned crawl) and, for a Limit that counts per day, week or month, its period: the unit, the IANA time zone and `resetsAt` (ADR 0041);
  - `weakened`: every setting that weakened a safeguard for this Run (ADR 0028), with its key, value, layer and origin, whether a costly control switched off (ADR 0023; the Run trace's "no trace" mark, ADR 0031) or a value pressing a site harder (ADR 0086);
  - `plan`: ADR 0091's `PlanReport` (the Plan file, or none, the version used, its status and the steps changed), on every Run, a crawl's included, in which each Agent task is one entry (ADR 0100);
  - `policyVersion`: the Operator policy version it ran under (ADR 0031);
  - `settings`: each effective value with the layer that set it and the one that locked it, as `explainSettings()` returns them (ADR 0028); a Sink inherited by a Collie Run, which carries no Sinks (ADR 0088), shows there as inactive (ADR 0103);
  - `plugins`: each Plugin that ran, at which network level, and the parts of reduced confinement the host could not provide (ADRs 0016, 0033);
  - `warnings`, each with a code and a message: a `stealth` choice (ADR 0035), Clean-up rules older than 14 days (ADR 0047), throttled CPU (ADR 0049), a degraded Politeness store (ADR 0053), a Plugin's reported quantity above its declared maximum and figures that come from a Plugin (ADR 0033). Area 3's spec lists the codes, and a newer engine's are kept (G3);
    > Amended by [ADR 0116](0116-a-saved-file-is-written-whole-or-not-at-all-and-a-failed-write-says-whether-its-path-or-its-storage-failed.md): a failed write of the Plan file or the Response recording at the Run's end adds a warning whose code is `path_not_writable` or `file_write_failed`.
    > Amended by [ADR 0122](0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md): a Run that met the `low` storage level carries the warning `storage_low`, naming the folder, the free space and what was shed, and a periodic Checkpoint whose write failed adds a `file_write_failed` warning.
  - `recording`: what the Run did with the Response recording its start named, or none (ADR 0105);
  - `checkpoint`: the last Checkpoint written, or none;
  - `nothingDone` (G1): none, or `already_ended` (the start found the Run ended), `no_seed_handled` (no seed reached a handler: each was refused when added or skipped when fetched, counted by an enqueue's reason or a skip reason) or `nothing_pending` (a resume or a retry found nothing left);
  - `consoleUrl`: the Run's page in the Console, where its Run trace replays, when the engine knows a Console address (ADR 0031), or none;
    > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console, so what this says of the Console ends; the rest stands.
  - `startedAt` and `endedAt`.
  > Amended by [ADR 0106](0106-a-program-declares-an-effect-as-a-keyed-block-whose-output-the-effect-journal-keeps-judged-by-what-the-engine-sent.md): it also holds `uncertainEffects`, each Effect the Run left uncertain (a declared Effect or an AI action), with its Effect journal entry, key or instruction, crawl request, reason, first command sent and since when, until a person reconciles it (ADR 0029).
- **Points in time.** Every point in time the Run carries is the language's own type, as ADR 0092 has it (a `Date`, a time-zone-aware `datetime` in UTC, a `SystemTime`): `startedAt` and `endedAt`, an outcome's `endedAt`, a pause's `since` and `deadline`, when a held domain is next admitted, an in-flight request's start, a Checkpoint's time, `checkpointAt`, `nothingDone`'s `endedAt`, a period's `resetsAt` and a progress value's own. ### Retrying failed requests

- **`run.retryFailed({ blocked? })`** re-admits, in the same Run and its Datasets, every request that ended `failed`, and with `blocked: true` those that ended `blocked`. A skip is a decision (robots.txt, scope, a handler's `skip`), never re-admitted.
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): `run.failedRequests({ blocked? })`, on a crawl's Run and its `CrawlRunView`, reads from committed state the requests whose latest outcome is `failed` (with `blocked: true`, also `blocked`), exactly what `retryFailed` with the same option would re-admit; `outcomes()`'s doc comment opens by calling it a log of endings, not current state.
- Each re-admitted request keeps its ID, Label, Payload and depth. Its attempts go on counting, with a fresh `crawl.retry.max`.
- It returns how many it re-admitted; 0 says there was nothing to retry (G1).
- On an ended Run, it returns the Run to `running`, its Verdict and Completeness given anew when it ends, as ADR 0029's "it did not happen" already reopens a Run. Its Usage counts in the same Run, under its Limits (G5). A new Run seeded from the failures would have left the first one `incomplete` for good, with two Datasets to merge.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-27, [#1005](https://github.com/goodfetch/goodfetch/issues/1005): the catalog's operation is `run.retry_failed {run_id, blocked?, settings?, project?}`, answering `{readmitted}`. On a crawl this engine runs, the requests join its work at once, its delivery woken as `run.add_seed` wakes it. On an ended Run with something to retry, the engine takes its writer role under the Run's event `RetryFailed`, as a resume does, with `settings` and `project` read as `run.resume` reads them; the re-admission commits under that writer, and the crawl's driver starts again with the calling Connection as its server, so a program calls it from the Connection that serves the crawl's handlers. With nothing to retry it answers 0 and leaves the Run as it is, never reopened. A Run whose state says `running` with no writer here fails with `run_interrupted`, since a resume takes its writer role first. The fresh `crawl.retry.max` counts from the attempts a work item had when re-admitted (`work_items.retried_from`), so its attempts go on counting in its outcomes while its budget starts again; an attempt a resume finds in flight is judged against the same budget.
  > Note (agent decision, on a guarantee, not read by the owner), 2026-10-29, deep review findings 581-3 to 581-6 ([#1005](https://github.com/goodfetch/goodfetch/issues/1005), [#914](https://github.com/goodfetch/goodfetch/issues/914)): a crawl about to end closes its intake in a job of its Run state's writer that looks once more for a pending work item, and `run.retry_failed`, `run.add_seed` and `run.add_seeds` check that intake in their own writer jobs. A re-admission or a seed committed before the crawl's last look is delivered, the crawl going on; after it, a re-admission waits for the Run's end and re-admits as on an ended Run, and a seed fails with `run_not_found`. An attempt a resume finds in flight with no retry left ends as an attempt does: its `handler_lost` error and a `failed` outcome at the resume's time, so `run.outcomes`, `run.failed_requests`, `run.retry_failed` and the report agree. `run.retry_failed` is an Effect, never sent again after a lost Connection. The `requests` counts are kept in the run file as each outcome commits, and a re-admission takes back its request's latest outcome, so a request counts once, by its latest outcome while ended and as pending once re-admitted; a progress read reads those counts, not the outcomes.

### Checkpoints

- **`run.checkpoint()`** writes a Checkpoint now, where the engine keeps the Run's Checkpoints: the Run's own folder (ADR 0031), or wherever Goodfetch Cloud stores them (ADR 0002). It returns a `Checkpoint` with its location, size, digest, run epoch, journal position and time, as ADR 0002 reports them, and `saveAs(path)` or `stream()` copies it to the program's machine, as ADR 0103's Export does. There is no path option in the SDK, since a path on the engine's machine would break on a Daemon or Goodfetch Cloud; the catalog's checkpoint operation keeps ADR 0002's location the caller gives, which Goodfetch Cloud uses to store Checkpoints wherever it likes.
  > Amended by [ADR 0116](0116-a-saved-file-is-written-whole-or-not-at-all-and-a-failed-write-says-whether-its-path-or-its-storage-failed.md): `run.checkpoint()` returns its `Checkpoint` only once the file is complete, and fails with `file_write_failed` (an `UnavailableError`, side `engine`, not retryable) when the engine cannot write it. `saveAs` writes whole or not at all, through a hidden temporary file renamed over the path, and raises `path_not_writable` or `file_write_failed`, as an Export's does.
  > Note (agent decision, as built), 2026-11-23, [#2348](https://github.com/goodfetch/goodfetch/issues/2348): `run.checkpoint`'s `location` is marked `catalog_only` in its schema, so the generated SDK members take no path while the catalog keeps it; `xtask codegen` refuses the mark on a required parameter. `run.migrate` keeps its `location` in the SDKs, in `RunMigrateParams` of its own.
- **`checkpoint.interval`** is ADR 0002's periodic interval, none by default locally.
  > Note (agent decision, accepted by the owner on 2026-10-21), 2026-10-21, [#218](https://github.com/goodfetch/goodfetch/issues/218): the catalog's resume operation is `run.resume`, answering `RunStarted` with `started_as: resumed`, and `existing` for a Run live in the engine or finished. A Run's report carries `checkpoint`, the last Checkpoint the engine that ended it wrote, which a report read back from run state does not hold. Pause is `run.pause`, stop reason `pause`, and migration `run.migrate`, stop reason `migrate`. A Run's lifecycle events are `run.checkpointing` (run epoch), `run.migrating`, `run.aborting` (`by`) and `run.stopping` (`cause`), lossless. A Run bound to its machine records the machine's identity, a random value kept in the Goodfetch home's `machine-id` file, so another home stands for another machine.
- **On the same machine** a Run resumes from its run file and needs no Checkpoint. To resume elsewhere, the catalog's run import (ADR 0002) registers the Checkpoint, and a start with its ID resumes it, except a run that ADR 0056 binds to its machine. Session secrets stay encrypted in it (ADR 0015).

A CI job keeps it as an artifact of a failed run; a person replays it in the Console at `consoleUrl`.

### Reading a Run the program does not hold

- **`collie.openRun(id)` returns a `RunView`, and `foxhound.openCrawlRun(id)` a `CrawlRunView`;** a Foxhound connection carries both (ADR 0095). Python's are `open_run` and `open_crawl_run`, Rust's the same. They serve a program that holds only an ID: an export of yesterday's crawl, a monitoring program following a detached Run, another program's live Run. Temporal's `getHandle(id)` plays this part.
- **A view only reads:** `progress()`; `trace()`; `report()`, at once for an ended Run and at its end for a live one, which it never ends; the Key-value store's reads, on every Run (ADR 0103); and for a crawl, `outcomes()` and ADR 0103's `records(dataset)`, `rejectedRecords(dataset)` and `export(dataset, …)`. The Dataset handles come from the program's own crawl declaration, so these reads are typed (ADR 0082).
  > Amended by [ADR 0117](0117-what-coding-agents-misread-is-reshaped-an-ai-result-holds-its-answer-in-how-it-ended-resource-types-are-blocked-by-a-setting-and-a-start-names-its-run-id.md): and for a crawl, `failedRequests()`.
- **It takes no writer lock** (ADR 0031) and gives the Run no work, so it never resumes an interrupted Run, which a start with the ID would. Closing it frees only the view. An ID the Run index does not list raises `run_not_found`.
- **An interrupted Run** has no live writer and has not ended, so a view's sequences (`progress()`, `outcomes()`, and ADR 0103's `records()` and `rejectedRecords()`) end after what is committed, and `report()` raises `run_interrupted`, whose `fix` names a start with the Run's ID. Waiting would hang until some program came back (G6).
- **Detaching.** The option is `detached: true` (Python `detached=True`, Rust `.detached()`). It exists only on the starts of Runs with no handlers in the program, a Recipe's run or a code-free catalog run (ADR 0036's targets), whose verbs come from the catalog; area 11's spec spells the start of an Agent task as a code-free run. `collie.start` and `startCrawl` never take it, since the program drives a Collie Run and serves a crawl's handlers; the TypeScript and Python types leave it out (G3). Closing a detached Run's value frees only the value and never stops the Run, `finish()` waits for its end, and `stop()` stops it. A refusal on an Attached engine keeps ADR 0078's code, which area 11's spec names.
  > Note (agent decision, not read by the owner), 2026-11-23, [#3179](https://github.com/goodfetch/goodfetch/issues/3179): on the wire, `crawl.start` also takes `detached`, for a code-free crawl, as ADR 0104 reads one: a crawl whose `extraction` the engine runs and that has no Hook in the program, started on a Daemon, outlives its Connection. Any other detached start fails with `detach_unsupported` (`ProgramError`, not retryable), its details naming the key that kept the Run from detaching (`extraction`, `hooks`, or `engine` on an engine that ends with its Connection) and the `fix`. `foxhound crawl start --detached` is generated from it. The SDKs do not send it yet: the TypeScript and Python `startCrawl` leave it out (G3), and the Rust SDK's crawl sends `detached: false`.

### Error codes

| Code | Group | Retryable | When |
|---|---|---|---|
| `run_id_invalid` | `ProgramError` | no | An ID the engine refuses |
| `run_conflict` | `ProgramError` | no | The ID names a Run started with other inputs, or by another caller; the details list each difference |
| `run_ended` | `ProgramError` | no | A call that would give an ended Run new work, such as `newPage()` or `addSeed()` on a Run that `startedAs` `ended`; its `fix` names a new ID, and `retryFailed` on a crawl's Run |
| `run_not_found` | `ProgramError` | no | `openRun` or `openCrawlRun` with an ID the Run index does not list |
| `run_in_use` | `RefusedError` | yes | The Run's writer's lock is held, by another program or this one (ADR 0031); another program may end, and the details name the owner, so a program that holds the Run itself sees that retrying cannot help |
| `limit_raise_refused` | `RefusedError` | no | A resume gave a Limit above the Limit as it stands |
| `run_state_unavailable` | `UnavailableError` | no | The Run index lists the Run, but its state is `missing` or `damaged`; the details give the path |
| `run_interrupted` | `UnavailableError` | no | A view's `report()` on a Run with no live writer that has not ended |

> Note (agent decision, on a guarantee, not read by the owner), 2026-10-23, [#697](https://github.com/goodfetch/goodfetch/issues/697): `run_ended` is raised by `run.new_page` and `run.new_session` for a Run whose committed state says it ended `finished`; a Run `stopped` or `failed` is interrupted, and new work on it raises `run_not_found` until a start resumes it.

> Note (agent decision, as built), 2026-10-28, step 7 review finding 213-misc-2 ([#1547](https://github.com/goodfetch/goodfetch/issues/1547)): `key_value_store.keys` reads committed run state and is not forwarded to the owning engine, while `get` and `get_bytes` are: the owner's forwarding answers one reply, and `keys` streams its keys under credits, which a forward would have to relay. Every write but an attempt's staged one commits at once, and staged keys are visible only within their attempt, so committed state lists what the owner would. Forwarding it needs a streaming read through the Forwarder.

> Note (agent decision, accepted by the owner on 2026-10-21; [#219](https://github.com/goodfetch/goodfetch/issues/219)): two codes join this table for the writer lock of ADR 0031. `run_busy` (`RefusedError`, retryable) answers an action that takes a Run's writer role, `run.abort` of a Run whose engine died, when the lock stayed held through every retry and the owner the Run index names did not take the action. `run_not_owned` (`RefusedError`, not retryable) answers a forwarded action that reached an engine that does not own the Run. A start of a Run another writer holds still answers as this table says.

## Considered Options

- **Refusing a start whose ID names an open Run, with a separate `resume(id)`** (the default of Temporal's Conflict Policy, `FAIL`): rejected. Every crash-safe program would look the ID up and branch, the program of golden scenario 07 among them (T). **A conflict policy option** (`ifExists: "resume"`, Temporal's `USE_EXISTING`): rejected, a second way to resume (S2). **A start that always begins and a `resume` that always continues:** rejected, since the program would have to know which run it is.
- **Inferring the Run from a storage folder,** as Crawlee's queues and Scrapy's `JOBDIR`: rejected, the pain itself (G2). **Starting afresh under an ID whose Run finished,** as Temporal's default Reuse Policy (Allow Duplicate) does for a closed workflow and Scrapling forgets a completed crawl: rejected. An ID names one Run in the Run index, and an idempotency key replays its first answer; Temporal's `start` gives an existing ID two meanings under one verb (S3).
- **A name kept apart from the Run ID,** as Temporal's workflow ID and run ID: rejected. A second identifier for the "run it again" a new ID already says (S2).
- **`foxhound.start(crawl, …)`**: rejected, beside Collie's `start` on the same connection (above). **`crawl.start(foxhound, …)`**, Crawlee's `crawler.run()`: rejected; the declaration ADR 0093 keeps free of I/O would start Runs, and an agent completing `foxhound.` would not find it (T). **`foxhound.crawl(…)`**: rejected; Firecrawl's `crawl` waits for the end (S3).
- **A start that resolves at the Run's end,** as Crawlee's `run()`: rejected; no `addSeed`, progress or early stop while it runs. **A wait verb per Product** (`finish` for Collie, `wait` for crawls): rejected, two concepts for one end. **`close()` ending a Collie Run `finished` when the program returns normally:** rejected; TypeScript's disposal cannot tell a return from a throw, and S1 asks for one rule.
- **Amending ADR 0036's start operation** (`run.start`) to resume and refuse: rejected; the scheduler relies on it after a restart, and the SDK's start composes it with the resume operation instead.
- **Log lines only for progress,** as Crawlee and Scrapy: rejected, since a program cannot read them (G6). **A periodic status line from the SDK** beside `progress()`: rejected; the host decides what it logs and how often (G4). **A progress callback:** rejected; ADR 0081 shapes a sequence read to its end as an iterator. **A one-shot status read beside the sequence:** rejected (S2).
- **Outcomes as a lossless event stream that slows an unread Run** (ADR 0081's rule): rejected; a forgotten iterator would stall a crawl (G4, G5), and outcomes are committed state that a reader can page. **Counts only:** rejected; scenario 07 must list the failed URLs.
- **Retrying failures in a new Run:** rejected (above). **A failed-request callback** (Crawlee's `failedRequestHandler`): rejected by ADR 0093; a failed request is an outcome value.
- **Opening a past Run by starting its ID:** rejected; it needs the declaration and the seeds, and would resume an interrupted Run, which a reader must never do. **Only the catalog's reads:** rejected; no typed Records and no Export. **A view's `report()` that waits on an interrupted Run:** rejected; it would hang silently (G6).
- **A lossless sequence of Human pauses beside `progress()`,** or a callback per pause: rejected. The progress already holds each pause, which lasts as long as a person takes, and the person is reached by ADR 0027's Notification, not by the program (S2); ADR 0081 shapes a sequence as an iterator.
- **A lossless `events()` sequence of the Run's stages** (ADR 0104's observe-only stages): rejected; progress, outcomes and the report already state each (S2).
- **A typed iterator over the Run trace's entries,** as Temporal's `fetchHistory()` returns a workflow's history: rejected. The trace is a recording for a person, a program's values have their own channels (S2), and typing it would fix a format ADR 0031 leaves open. **Nothing in code:** rejected; a CI job could not keep the trace of a failed run (G6).
- **A Checkpoint path on the engine's machine:** rejected, as ADR 0103 rejects one for Exports; it breaks on a Daemon or Goodfetch Cloud.
- **Raising when a seed is refused:** rejected; a seed is one request among many (ADR 0079).

## Consequences

- **Amends ADR 0029.** A finished crawl's Run also returns to `running` when its program retries its failed requests, its Verdict and Completeness given anew when it ends; and a Collie Run its program finishes is `complete`. Notes sit under the Lifecycle and Completeness items.
- **Amends ADR 0078.** Closing a detached Run's value frees only the value and never stops the Run, as the connection's own close already leaves it running. A note sits under the close table.
- **Amends ADR 0081.** A sequence read from a Run's committed state, as `outcomes()`, never slows its Run; the rule that an unread lossless sequence slows its Run covers what the engine must deliver. A note sits under the iterators item.
- **Amends ADR 0083.** The settings schema also marks, per setting, whether a resume may change it; `crawl.keep_alive` and `checkpoint.interval` join it; and `setting_not_applicable` also refuses a key fixed for a Run's life given on a resume. Notes sit under its refusals table and its settings-schema consequence.
- **Amends ADR 0103.** On a Run with no live writer, a view's `records()` and `rejectedRecords()` end after the last committed Record instead of waiting for the Run to end. A note sits under its "When it ends" item.
- **Amends ADR 0093.** The start verb is `foxhound.startCrawl(crawl, { seeds })`, in place of the sketch's provisional `foxhound.start`; Rust's `crawl.serve(&run)` returns the crawl's Run report once the Run ends; and the live sequence the owner's R4 asks for is `run.outcomes({ kinds, labels, after })`. Notes sit under its start verb, its item on where handlers run, and its rejected failed-request handler.
- **Adds to ADR 0041:** a resume that gives a Limit above the Limit as it stands fails with `limit_raise_refused`, and a person's raise stands against the value the program began with.
- **Builds on ADR 0036, unchanged:** the SDK's start calls `run.start`, then resumes an interrupted Run through the resume operation or refuses one with a live writer.
- **Adds to ADR 0079:** a `CrawlRequestOutcome` carries `endedAt`, and a Run that ends `failed` makes `finish()` and `stop()` raise, as a failed ending of AI work does.
- **Adds to ADR 0080:** `finish()`'s wait has no timeout of its own, the Run's `timeout` bounding it; `stop()`'s wait is bounded by `timeout.close`, as `close()`'s is.
- **Builds on ADR 0002, unchanged:** the catalog's checkpoint operation keeps the location its caller gives; only the SDK's `checkpoint()` leaves it to the engine and copies the Checkpoint to the program's machine.
