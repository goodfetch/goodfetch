# A program declares an Effect as a keyed block whose output the Effect journal keeps, judged by what the engine sent

ADR 0010 journals every action an AI decides and lets user code "opt in by declaring Effects"; this decides how. A program wraps the code that performs an Effect in `run.effect(key, body)`. The value the body returns is kept in the Run's Effect journal, so a retried crawl handler or a Collie program started again with its Run's ID gets that value back instead of performing the Effect again. The engine judges a body that did not return by what it sent for it: nothing sent means not performed, something sent means uncertain until a person reconciles it (ADR 0029), unless the program declared the body repeatable. None of the browser drivers, AI browser tools and crawlers the research surveyed lets a program declare one: Crawlee retries a failed handler three times, so a form submitted before the failure is submitted again, and Stagehand warns that a failed `act()` may already have acted ([crawl frameworks](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/crawl-frameworks.md) §6.14; [AI browser automation](https://github.com/goodfetch/goodfetch/blob/research/consumer-api/rnd/research/research_notes/Consumer%20API%20of%20competitors/ai-browser-automation.md) §2.1). The leaders of this problem are durable-execution frameworks, whose blocks (AWS's `context.step`, Restate's `ctx.run`, Inngest's `step.run`, Cloudflare's `step.do`, Temporal's Activities) keep a block's result and return it on replay. Decided in [Effects a program declares in code](https://github.com/goodfetch/goodfetch/issues/500), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), every question by the agent on the owner's delegation; the grilling record ([rounds 1–4](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6187495124), [round 5](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6188094314), [round 6](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6190079286), [round 7](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6190262494), [round 8](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6190354025), [round 9](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6190979650), [round 10](https://github.com/goodfetch/goodfetch/issues/500#issuecomment-6191167631)) cites their documentation, re-read on 2026-10-15. Principles are cited by their IDs in [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md).

## Decision

### What is declared

- **Only what the program declares.** A program's own calls (`locator.click()`, `page.request.post()`) are Effects only inside a declaration, as ADR 0010 says. What the engine journals by itself is unchanged: every action an AI decides (ADR 0010), a Plugin's Effect-class calls (ADR 0033), Paid fetches (ADR 0045), and a code-mode program's actions by position (ADR 0051). Undeclared calls run again whenever handler or program code runs again, under ADR 0003's at-least-once delivery, and the docs say so. Classing every click and non-GET request as an Effect, as ADR 0033 does for Plugins, would make discovery clicks, which ADR 0037's CO-06 says are not Effects, and GraphQL reads sent as POST into Effects, and a re-run after a crash would stop on dozens of uncertain clicks (G1, S2).
- **A crawl request is a read, whatever its method.** ADR 0093 lets `enqueue`, seeds and `addSeed` carry a `method`, `headers` and a `body`, so that a crawl reads a POST or GraphQL API page by page. Enqueuing a request is the program's statement that it is safe to send again: RFC 9110 (§9.2.2) lets a client repeat a POST automatically when it "knows (through design or configuration) that the request is safe for that resource", and Crawlee and Scrapy retry a request whatever its method. A crawl request is therefore fetched at least once (ADR 0003), and sent again on a retry, an escalation, a sample comparison, a re-run after a lost lease and `retryFailed`; it is still never hedged or coalesced unless its method is GET or HEAD (ADR 0040). An Effect that a handler must send as a request goes through `page.request` inside a declaration, which carries an `idempotencyKey` (G5, S2).
- **A block, not an option on a call.** The body may be one click, one request or several actions, and it returns what the program needs afterwards, such as the order number on the confirmation page. On a re-run the page is not where the Effect left it, so the Effect journal returns that value instead (S2, S3).
- **No confirmation.** A declared Effect is the program's own decision, so it never asks for ADR 0014's confirmation, which stays for Effects an AI decides.

### The declaration

- **`run.effect(key, body, options)`** on every Run, crawl Runs included. In a crawl handler it is `ctx.run.effect(…)`: ADR 0093 binds `ctx.run` to the attempt, so the declaration knows its crawl request with no extra argument (G2). The Run holds the Effect journal (ADR 0002); a page does not, since an Effect may span two pages and a re-run opens new ones. `effect` is the glossary's term, where `step` already means a Plan step or an Agent step and "side effect" is an _Avoid_ term (S3).
- **The Effect key** names one Effect, chosen by the program and required: a non-empty string of at most 255 Unicode code points, refused otherwise with `effect_key_invalid`. Its namespace is the crawl request in a handler or in a Hook's context (ADR 0104), whose call belongs to its request's attempt, and the Run elsewhere, so one key on two requests names two Effects. Within one attempt (one run of a handler, or one start of a Collie program), declaring a key again while its body runs, or after this attempt got its answer, raises `effect_key_reused`, so a loop that left its varying part out of the key fails instead of silently placing one order (G1, G3). On a Run whose browser is borrowed (ADR 0056), as every Run that joins another crawler through `run.borrow(page)` is, that crawler retries its handlers as new calls in the same Run (ADR 0089), where a retry cannot be told from a loop: a key declared again after its answer returns that answer, `journal` or `reconciled`, and only a declaration while its body runs raises `effect_key_reused`; the docs tell such a program to put the crawler's request key in the Effect key, such as Crawlee's `request.uniqueKey`. Across attempts of one namespace, such as a sample comparison's two runs of one crawl request, a declaration waits until a body still running under its key is judged, within its own handler's timeout; a re-run after a lost lease never overlaps, since a handler past its lease sends nothing more (ADR 0003). Matching by position, as AWS, Restate, Temporal and ADR 0051 do, was rejected: a handler re-run on another tier takes other branches, a resumed program may have changed (ADR 0102), and one conditional Effect shifts every later one.
- **`repeatable`**, `false` by default, declares the body safe to run again. There is no separate verifier that tells whether an Effect happened: a body that first looks for its Effect, as Cloudflare's own charging example does, is exactly a repeatable one, and returns the output it finds. Not repeatable is the default, the reverse of AWS's `AtLeastOncePerRetry`, because the engine never redoes an Effect it cannot vouch for (ADR 0010, G5).
- **The body receives an `Effect`** with its `key` and an `idempotencyKey`: an opaque string, the same on every attempt and resume of this Effect on any machine, different in every Run and every install. It is derived from a secret the Run creates when it begins and keeps in its state, so a Checkpoint carries it, and it reveals neither the Run's ID nor the key, as Stripe advises for idempotency keys. A program sends it as a site's `Idempotency-Key` header or to its own service, which makes the body repeatable, as Temporal recommends with its Workflow Run and Activity IDs. A redo after a person's "it did not happen" keeps it, so a site that did receive the first request drops the second.
- **The body's value** is JSON (ADR 0082's `JsonValue`; `Serialize + DeserializeOwned` in Rust), or nothing. The Effect journal keeps it up to `effect.output.max_size`, 64 KiB by default as `crawl.payload.max_size`, set on a connection or a Run, and marked `collie` in the settings schema (ADR 0095), since both Products carry declarations. A value that is not JSON or is too large is a body that did not return a value the Effect journal keeps: it raises `effect_output_invalid` when nothing was sent, and `effect_uncertain` with `effect_output_invalid` as its cause after a send. The output is masked like everything the Effect journal keeps, as the engine masks every Secret value it resolved in what a call returns (ADR 0092), so a Secret's value never stays in it (ADRs 0014, 0015).
- **What it returns:** an `EffectResult` whose `source` says where the answer came from (G1), as an AI step's `step: "journal"` does (ADR 0091):
  - `performed`: the body ran now, with its `output` and `performedAt`;
  - `journal`: the Effect journal already held it from an earlier attempt or start, so the body did not run, with the `output` it returned then and `performedAt`;
  - `reconciled`: a person answered "it happened" (ADR 0029), so the body did not run and no output is known, with `reconciledBy` and `reconciledAt`;
  - a source a newer engine sends is kept (ADR 0079).

  Only `performed` and `journal` carry an output, so each language's type makes the program handle its absence (G3).

### How a body is judged

- **The window.** A declaration writes the Effect's entry in the Effect journal before its body starts. Until the body returns, every command that may change a page or a site is attributed to it: a guarded action's first input, a navigation, a `page.request`, a page function, an AI `act`'s action. Reads and waits never count. In a handler the attempt's commands count; elsewhere, the Run's commands outside any attempt. The first such command marks the entry sent in the Effect journal before it goes out. A `fill` counts, since autosave and search-as-you-type send requests on input and the engine cannot tell which input does: a program prepares the page before the declaration, and the body holds the action that commits the Effect and the reads of its result.
- **When the engine cannot see every command,** a body counts as sent from its start: while a page of its attempt (or of the Run, outside a handler) has a raw CDP attach open (ADR 0003) or is lent to another library with `page.lend()` (ADR 0089), or while the Run's browser is borrowed and other code drives it too (ADR 0056), as with `run.borrow(page)` (G5).
- **Done:** the body returned a value the Effect journal keeps. It never runs again under that key.
- **Not performed:** the body did not return and nothing was sent. The entry is dropped and the error propagates unchanged, with its own retryable flag, so a button that was never found is an ordinary failure, retried as usual.
- **Uncertain:** the body did not return after something was sent. Unless the Effect is repeatable, a body that threw makes the call raise `effect_uncertain` with the original as its cause, and every later declaration of that key raises it at once, without running the body, until a person reconciles it. A repeatable Effect lets the original error propagate and runs its body again at its next declaration.
- **A body cut short** by a cancellation (Python's `CancelledError` or `KeyboardInterrupt`, a TypeScript abort, a Rust future dropped), by its attempt's end (ADR 0093's `attempt_ended`), or by a crash, a lost lease or a dropped connection, is judged by the same rule, and the original propagates unchanged, as ADRs 0080 and 0093 have it: the host's structured concurrency and `except Exception:` keep working (G4). The judgment is recorded when the body is cut short, or when its attempt or Run ends, and the key's next declaration acts on it.
- **What the engine cannot see.** The program's own I/O inside a body, through its own HTTP client, is invisible to the Effect journal: a body whose Effect goes through it declares itself repeatable and makes itself safe to repeat, which `idempotencyKey` is for (G1).
- **Nesting and concurrency** are allowed for different keys. Each Effect is judged on its own, and concurrent bodies in one attempt share their windows, which can only make a judgment more cautious.

### Re-runs

- **A crawl handler** runs again for the same crawl request on a retry, an escalation, a sample comparison (ADR 0020), a lost lease (`handler_lost`, ADR 0093) and `retryFailed`, which keeps the request's ID (ADR 0102): a done Effect returns `journal`, an uncertain one raises `effect_uncertain`. An attempt's Records, enqueues and seeds are staged, committed when its handler returns and discarded when it ends early (ADRs 0003, 0093), but an Effect's entry is committed at once, since the site has received it.
- **Nothing is staged inside a body.** A re-run that gets `journal` does not run the body again, so an output the body staged with an attempt that then ended early would be lost for good. While a body runs in an attempt, a call that stages an output with that attempt (an `enqueue`, a Record's `ctx.push`, and an `addSeed` or a Key-value store write through `ctx.run`, as ADRs 0093 and 0103 stage them) fails with `effect_staging_refused`, a `ProgramError` whose `fix` says to stage it after the declaration, from the output the body returned. Concurrent code of the same attempt counts, as the window does. The leaders draw the same line: inside `ctx.run`, Restate's docs say "you cannot use the Restate context", and an AWS durable function's `StepContext` exposes no durable operations (G1, S3). Outside an attempt, where nothing is staged, a body's outputs are committed at once and kept.
- **Escalation inside a body.** A call the tier cannot serve escalates before it sends anything (ADR 0093), so an Effect whose first command needs the browser is not performed, and runs in the browser. A body that sends a `page.request` and then needs the browser is cut after a send, and is uncertain unless repeatable; a Label whose Effects need the browser sets `fetch.tier: browser`.
- **An uncaught `effect_uncertain`** ends the crawl request `failed` with that error, which is not retryable, so ADR 0079's four outcomes stay as they are. The Run's Verdict is `needs-review` until a person reconciles the Effect (ADR 0029). After "it happened", the request stays `failed` until the program's `retryFailed`, whose re-run gets `reconciled` and does the handler's remaining work; the docs and the Console say so.
  > Amended by [ADR 0137](0137-the-console-leaves-both-products-and-the-engine-and-the-owners-monitoring-tool-is-designed-apart.md): no Product carries a Console. The engine behaviour this ADR describes stands and the Console's part does not; a Client reaches it.
- **A Collie program started again with its Run's ID** (ADR 0102) runs from its top, and each declaration finds its entry by key, so an order placed before a crash returns `journal` with its number. A program that starts without an `id` gets a new Run on each start, so its Effects are found only within that Run; the docs tell a program that declares Effects to name its Run. On a Run that `startedAs` `ended`, a key the Effect journal holds returns from it and any other raises `run_ended`.
- **An Effect journal that may lack entries.** A resume from a Checkpoint after which the Run may have gone on, because it was written while the Run was running or is older than the Run's latest run epoch, may lack the entries written after it (ADR 0002). For the rest of the Run, in each namespace that may lack them (a crawl request that Checkpoint did not hold ended, and the Run's own, on a Collie Run or a crawl Run), a key the Effect journal lacks is uncertain unless repeatable, and a person's "it did not happen" releases that key. A program narrows the gap by writing a Checkpoint after an Effect (ADR 0102's `run.checkpoint()`).

### Reporting and reconciling

- **`effect_uncertain`** (a `PageError`, not retryable, ADR 0091's) covers declared Effects too. Its details name the Effect journal entry, the key or an AI action's instruction, the crawl request, why it is uncertain (`failed_after_send`, `interrupted` or `journal_incomplete`), the first command sent, rendered in the caller's language (ADR 0079), and since when.
- **The Run report** (ADR 0102) lists each Effect left uncertain as `uncertainEffects`, with those details, besides its Verdict reason (G6).
- **Only a person reconciles** (ADR 0029). After "it happened", the next declaration returns `reconciled`. After "it did not happen", the entry is dropped and the next declaration performs the Effect: a crawl request is re-admitted as `retryFailed` re-admits one, and the program's Run waits for its script (ADR 0031) until a start with its ID.

### Agent tools

ADR 0100 left to this ticket whether an Agent tool takes a function that tells whether its Effect already happened. It does not, for the reasons a declaration takes none. A tool that is not read-only keeps ADR 0100's rule that a raise leaves its Effect uncertain, and gains the declaration's two answers (G5, S2):
- **`repeatable`**, `false` by default: a raise from the tool still ends the task as ADR 0100 says, but leaves no uncertain Effect, so a replay of the task or a later task may call the tool again. TypeScript's `agentTool({ …, readOnly, repeatable, category, run })`, Python's `@agent_tool(…, repeatable=True)` and Rust's `AgentTool::new(…).repeatable()`.
- **The call's `idempotencyKey`,** derived from the tool call's own Effect journal entry, so a replay of that call (ADR 0100) gets the same key: on TypeScript's `call` (`call.idempotencyKey`, beside `page` and `signal`), and on an `AgentToolCall` with `idempotency_key` that a Python tool takes as an optional third parameter and a Rust tool as its third argument. OpenAI Agents' `ToolContext`, Pydantic AI's `RunContext` and the AI SDK's `execute` options hand a tool its call's ID the same way (S3).

### The catalog and tests

- **Two catalog operations,** `effect.open` and `effect.close`, carry a declaration: the first writes the entry and answers `perform` or the journal's answer, the second records the output or how the body ended. Only the SDKs call them, behind `run.effect`, which ADR 0099's manifest lists against both; like ADR 0029's answer about an uncertain Effect, they are generated for no MCP tool, Framework adapter or CLI command, since an Effect an agent decides is journaled by the engine itself (ADR 0010). Both are marked `collie` (ADR 0095).
- **A replayed response counts as sent.** A command a Response recording answers (ADR 0105) is judged as if the site had received it, so a test meets the same judgment a live Run does (G5).
- **`runHandler` takes the Effect journal's prior answers** (ADR 0105): `effects`, a map from Effect key to `journal` with an output, `reconciled`, or `uncertain` with its reason, so a handler test reaches each path in its one attempt. Its `AttemptResult` lists `effects`: each declaration with its key, how it was answered (`performed`, `journal`, `reconciled`, `uncertain` or `not_performed`) and whether its body sent anything.
- **`engine.reconcile(runId, key, answer)`** on the test engine stands for a person's answer, `happened` or `did_not_happen` (ADR 0029), so a Collie program's test reaches `reconciled` and a redo; starting the program again under its Run's ID on the same test engine reaches `journal`. It exists only in the testing kit: no agent surface gives a person's answer (ADR 0029).

### Each language's form

- **No `timeout` or `signal`** on `run.effect`: the body's own calls carry theirs (ADR 0080), and the declaration's own catalog calls are short writes under the default call timeout.
- **TypeScript:** `await run.effect("order-1234", async (effect) => { … }, { repeatable })` returns `EffectResult<T>`, a union narrowed by `source`.
- **Python:** `await run.effect("order-1234", place, repeatable=False)`, where `place(effect)` returns an awaitable JSON value, on `AsyncRun` and `AsyncCrawlRun`, and the same, synchronous, on `Run` and `CrawlRun`. `EffectResult[T]` is `EffectDone[T] | EffectReconciled | EffectSourceUnknown`. There is no `with` form: a context manager cannot skip its own body (S1).
- **Rust:** `run.effect("order-1234", async |effect| { … }).repeatable().await?`, an `IntoFuture` builder as ADR 0080 has them. The body is `AsyncFnOnce(&Effect) -> Result<T, E>`, runs in the awaiting task, may borrow and needs no `Send` (ADR 0081). It is generic in its error, `E: From<Error> + Into<Box<dyn std::error::Error + Send + Sync>>`, where `Error` is the SDK's, from `goodfetch-collie-client`, which `goodfetch_collie` and `goodfetch_foxhound` re-export (ADR 0095); that `Error` itself or `anyhow::Error` fits, so the declaration returns `Result<EffectResult<T>, E>`: the body's own error unchanged, an SDK error converted into `E`, and `effect_uncertain` with the original as its `source()` (S1). `EffectResult<T>` is a `#[non_exhaustive]` enum with `output()`.
  > Amended by [ADR 0112](0112-a-rust-crawls-handlers-and-their-futures-are-send-in-axums-form-so-serve-runs-in-a-multi-threaded-server.md): the body is `FnOnce(Effect) -> Fut + Send + 'a` with `Fut: Send`, given `Effect` by value, and `T` and `E` are `Send`, so the declaration's future is `Send` and a handler or a server's future that declares an Effect stays `Send`. It may still borrow.

### Error codes

| Code | Group | Product (ADR 0095) | When |
|---|---|---|---|
| `effect_key_invalid` | `ProgramError` | `collie` | An empty key, or one longer than 255 code points |
| `effect_key_reused` | `ProgramError` | `collie` | A key declared again in one attempt while its body runs, or after it got its answer |
| `effect_output_invalid` | `ProgramError` | `collie` | The body's value is not JSON or is larger than `effect.output.max_size`, when nothing was sent; after a send, the cause of `effect_uncertain` |
| `effect_staging_refused` | `ProgramError` | `foxhound` | A call that stages an output with an attempt while a body runs in it |
| `effect_uncertain` | `PageError` | `collie` | ADR 0091's code, extended to declared Effects above |

## Considered Options

- **The engine classes the page API itself,** as ADR 0033 does for Plugins: rejected. Discovery clicks, "load more" buttons and GraphQL reads sent as POST would become Effects, a re-run after a crash would stop on every one of them, and ADR 0010 rejected forcing the Effect journal on user code. ADR 0051's positional Effect journal works for code mode because a corrected program replays against the same live page.
- **Classing `page.request` by its HTTP method:** rejected for the same GraphQL reads, and as a second rule beside the declaration (S2).
- **An option on the call** (`click({ effect })`, `post(url, { effect })`): rejected. On a skip the page is not where the Effect left it, so the program's next line fails; an Effect of several actions cannot be declared; and a response would have to be journaled whole. **Both forms:** rejected by S2.
- **Matching by position,** as AWS's durable functions, Restate, Temporal and ADR 0051: rejected, since handler code may change, branch by tier and run Effects conditionally. **A counter per name,** as Inngest: rejected, since it is a position within the name.
- **A separate `verify` function,** run only on an uncertain re-run: rejected. It must answer "happened, with this output" or "did not happen", which has no clean type in Python, where `None` is also JSON; it is a second way to make an Effect safe (S2); and no leader has one (S3).
- **Repeatable by default,** as AWS's `AtLeastOncePerRetry`: rejected by ADR 0010 and G5.
- **Wrapping a cancellation or an attempt's end in `effect_uncertain`:** rejected by G4 and ADRs 0080 and 0093. Python's `asyncio.timeout` and task groups depend on seeing `CancelledError`, and an `Exception` subclass would let `except Exception:` swallow a Ctrl+C.
- **Counting only clicks, key presses and requests in the window:** rejected. A `fill` can reach a site through the page's own scripts, which the engine cannot tell apart.
- **Listing raw CDP, lent pages and shared browsers with the program's own I/O,** as things for the program to make repeatable: rejected by G5. The engine knows when it cannot see every command, so it counts the body as sent.
- **Judging only whether the body completed,** as Restate and Temporal do: rejected. Either a button that was never found leaves an uncertain Effect for a person, or a body cut after its click runs again.
- **Treating every body that did not return as uncertain,** so that the program's own I/O is covered too: rejected. Every ordinary failure inside a body, before anything was sent, would need a person; the program's own I/O is made safe by `repeatable` and `idempotencyKey` instead.
- **The Run's ID as the idempotency key,** or a random one per attempt: rejected. The first may say something about the user and collides across installs, and the second changes on every attempt.
- **A fifth crawl request outcome, `uncertain`:** rejected. ADR 0079's outcomes stay closed; `failed` with `effect_uncertain` and the `needs-review` Verdict say it.
- **"It happened" re-admitting the request,** as "it did not happen" does: rejected. ADR 0029's "it happened" resumes nothing, and a person's answer would start work the program never asked for; `retryFailed` is the one way to re-run failed requests (S2).
- **A Rust body returning only the SDK's `Error`,** with a Rust-only code wrapping the program's own error, as ADR 0079's `listener_failed` is TypeScript and Python only: rejected by S1. A body's error would reach a crawl handler under another code in Rust than in the other SDKs.
- **Writing a Checkpoint before every Effect,** so no entry is lost with a machine: rejected. A Checkpoint is a whole copy of the run state (ADR 0002); a program that needs it calls `run.checkpoint()` after its Effects.
- **A crawl request whose method is not idempotent as an Effect by default,** as HTTP clients retry only idempotent methods by default (urllib3's `Retry`; Go's `net/http`, which also retries a request carrying an `Idempotency-Key` header): rejected. It would leave every POST or GraphQL read that R1 of ADR 0093 exists for uncertain after a timeout, waiting for a person, and class requests by method, which this ADR rejects for `page.request` (S2). An HTTP client does not know what its caller sends; an enqueue says what the program sends.
- **An option on `enqueue` that makes a crawl request an Effect:** rejected. It is a second way to declare one (S2), and the Frontier fetches the request outside any body, so a skipped fetch would leave its handler with no response to read.
- **Committing what a body stages with its Effect's entry:** rejected. Concurrent code of the attempt would commit with it and then again on the attempt's retry. **Leaving it to the docs:** rejected by G1, since the loss is silent.
- **`effect_key_reused` after an answer on a borrowed browser too:** rejected. Every retry of the other crawler would fail where the Effect journal holds the answer it needs.
- **An Agent tool's idempotency key from its name and input:** rejected. Two calls the model decided with the same input are two Effects (ADR 0010).

## Consequences

- **Adds to ADR 0010.** User code declares Effects with `run.effect`, and an Effect "declares itself repeatable" with `repeatable`. For a declared Effect, one "that has no way to verify whether it already happened" is one whose body ended after a send and that is not repeatable.
- **Adds to ADR 0029.** For a declared Effect, "it did not happen" re-admits a crawl request as `retryFailed` does (ADR 0102), and leaves the program's Run waiting for its script (ADR 0031), a Collie Run included, which has no work items. "It happened" makes the next declaration return `reconciled`, and leaves a crawl request `failed` until `retryFailed`.
- **Adds to ADR 0002.** A resume from a Checkpoint after which the Run may have gone on marks the namespaces whose entries it may lack, as above.
- **Adds to ADRs 0040 and 0046.** A request sent while a body runs belongs to its Effect: it is never hedged or coalesced, nor served from or stored in the Response cache; a work item declares an Effect, in ADR 0040's words, from its first declaration on.
- **Adds to ADR 0083.** `effect.output.max_size` joins the settings schema, set on a connection or a Run.
- **Amends ADR 0091.** Its `effect_uncertain` also covers declared Effects, with the details above.
- **Amends ADR 0102.** Its Run report also holds `uncertainEffects`; a note sits under "What it holds". Its hand-off is answered: a resume, a crash's restart and `retryFailed` re-run program code, and each declaration there finds its Effect by key, as above.
- **Amends ADR 0100.** An Agent tool that is not read-only may be `repeatable`, and a raise from it then leaves no uncertain Effect, so a replay or a later task may call it again; its call carries an `idempotencyKey`, a third parameter in Python and Rust (above).
- **Amends ADR 0093.** Its open question is answered: a crawl request is a read whatever its method, and a call that stages an output fails with `effect_staging_refused` while a body runs in its attempt.
- **Amends ADR 0103.** A Record, an enqueue, a seed or a Key-value store write staged while a body runs in the attempt fails with `effect_staging_refused`. A note sits under its "Staged with the attempt".
- **ADR 0095's marks.** The four new codes and `effect.output.max_size` carry the Products in the table above.
- **Amends ADR 0104.** A Hook context's `run` also declares Effects, in its crawl request's namespace, and a Hook call counts in its request's attempt; a crawl request is a read whatever its method. Notes sit under its contexts and its rule on the method and the body.
- **Amends ADR 0089.** On a Run that borrows another crawler's pages, a key declared again after its answer returns that answer, since the crawler's retries reach the Run as new calls.
