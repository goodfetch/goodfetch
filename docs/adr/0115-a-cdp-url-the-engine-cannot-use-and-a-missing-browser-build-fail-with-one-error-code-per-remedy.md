# A `cdp_url` the engine cannot use and a missing browser build fail with one Error code per remedy

Opening a Session on a `cdp_url` (ADR 0056's Session source for any browser reached by its CDP address) fails with one of four codes, one per remedy: `cdp_url_unreachable` when nothing answers, `cdp_url_not_browser` when something answers that is not a browser speaking CDP, `cdp_url_unauthorized` when the browser's service refuses the credentials sent, and `cdp_url_not_allowed` when ADR 0056's address rules refuse the address. A browser build the engine needs and does not have fails with `browser_not_installed` when the engine cannot fetch it, ADR 0043's `artifact_unavailable_offline` when `offline` forbids fetching it, and `artifact_download_failed` when fetching it failed. The `cdp_url` codes and a browser build's are raised by the call that opens the Session or launches the browser, never by `connect()`; for the other pinned downloads, the two artifact codes come from the call or command that first needs the artifact. Golden scenario 09's Rust program, which borrows a browser by its CDP address, had no code for its failure point "The browser cannot be attached to", and ADR 0098 described a missing build's error without a code. The leaders throw one untyped error with different text for every case: Playwright's `connectOverCDP` gives the socket's `ECONNREFUSED` or "This does not look like a DevTools server, try connecting via ws://" ([chromium.ts](https://github.com/microsoft/playwright/blob/5ad202df4f/packages/playwright-core/src/server/chromium/chromium.ts#L459-L476)), and its launch gives "Executable doesn't exist at …" with the install command ([registry/index.ts](https://github.com/microsoft/playwright/blob/5ad202df4f/packages/playwright-core/src/server/registry/index.ts#L516-L556)); Puppeteer rethrows "Failed to fetch browser webSocket URL from …" for a refusal and a wrong answer alike ([BrowserConnector.ts](https://github.com/puppeteer/puppeteer/blob/10c43c1b91/packages/puppeteer-core/src/common/BrowserConnector.ts#L196-L221)) and "Could not find Chrome (ver. …)" for a missing build ([BrowserLauncher.ts](https://github.com/puppeteer/puppeteer/blob/10c43c1b91/packages/puppeteer-core/src/node/BrowserLauncher.ts#L663-L679)); Browser Use raises a `RuntimeError` ([session.py](https://github.com/browser-use/browser-use/blob/c75e8476e2/browser_use/browser/session.py#L2026)); Crawlee wraps every launch failure in one `BrowserLaunchError` ([browser-plugin.ts](https://github.com/apify/crawlee/blob/c69d2898ae/packages/browser-pool/src/abstract-classes/browser-plugin.ts#L236-L295)); and chromiumoxide's `CdpError` leaves the caller matching tungstenite's and `std::io`'s variants ([error.rs](https://github.com/mattsse/chromiumoxide/blob/afcc3a4313/src/error.rs#L21-L67)). It answers pain rows P20 (the Rust crate's `cdp_url`) and P24 (the missing browser) of the [pain coverage matrix](https://github.com/goodfetch/goodfetch/blob/prototype/sdk-api/sdk-api-sketch/pain-coverage.md). Decided in [Error codes for an unreachable cdp_url and a missing browser build](https://github.com/goodfetch/goodfetch/issues/534), on the map [The SDK API of Collie and Foxhound](https://github.com/goodfetch/goodfetch/issues/461), by the agent on the owner's delegation; each question, its options and the field evidence are in the ticket's [grilling record](https://github.com/goodfetch/goodfetch/issues/534#issuecomment-6194719954). It builds on [ADR 0056](0056-a-login-is-brought-in-through-one-session-source-read-by-the-browser-that-owns-it.md), [ADR 0079](0079-failures-raise-grouped-typed-errors-and-expected-outcomes-are-values.md), [ADR 0092](0092-sessions-open-from-their-source-page-pause-waits-for-a-person-and-a-secret-is-a-placeholder-bound-to-domains.md) (confirmed by the owner: a Session opens from its source) and [ADR 0098](0098-both-products-share-one-goodfetch-home-and-one-daemon-per-major-run-by-the-fullest-product-installed.md), under the principles of [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md).

## Decision

### One code per remedy

- **The rule.** ADR 0079 puts each Error code in exactly one group, named for its remedy, and adds a type only where the remedy differs. A `cdp_url` that cannot be used has four remedies (start the browser or correct the address and retry; point to a browser; fix the credentials; ask the operator), and a missing build three (install it; lift `offline`; retry the download), so each gets its own code, and the sub-cases that share a remedy are a field of one code, as `secret_unavailable`'s `failure` says which provider failed (ADR 0092). One code with a reason would put three of the four `cdp_url` cases in the wrong group and give them the wrong `retryable` flag (G6); one code per sub-case would multiply classes that share a remedy, which ADR 0080 refused for timeouts (S2). ADR 0101 split a Model provider's failures the same way: `model_unavailable` (`UnavailableError`, retryable) and `model_unauthorized` (`RefusedError`, not retryable).
- **Every code carries ADR 0079's fields:** the operation, the address or the build as its target, what was observed, and a `fix` naming the setting, the command or the action that would change the outcome (G6). No message ever shows a header's value or a Secret's value (ADR 0015).

### A `cdp_url` the engine cannot use

| Group | Code | Retryable | When | `fix` |
|---|---|---|---|---|
| `UnavailableError` | `cdp_url_unreachable` | yes | Nothing at the address answered. Its `failure` is `name_not_resolved`, `connection_refused`, `connection_reset` or `tls_failed` | Start the browser with remote debugging on that port, or correct the address |
| `ProgramError` | `cdp_url_not_browser` | no | Something answered, but no browser speaks CDP there. Its `observed` says what answered: an HTTP status and content type, a WebSocket that refused the upgrade, a CDP target that is not a browser (`page`, `node`, `worker`), or a product the engine does not drive | Give the browser's endpoint, `http://host:port` or `ws://…/devtools/browser/<id>`; when the same host serves `/json/version`, the browser address found there |
| `RefusedError` | `cdp_url_unauthorized` | no | The address answered 401 or 403 to the HTTP request or the WebSocket upgrade. Its details name the header names sent and their Secret references | Check the Secret references in `headers` |
| `RefusedError` | `cdp_url_not_allowed` | no | ADR 0056's address rules refused the address before any connection: a private range from a value that is not operator-configured, or loopback from a Client acting for a model, a Recipe or an Integration, or on an Exposed Daemon. Its details name the rule and the settings layer that gave the address | Set the address in Operator policy or in user or project configuration, or give a public address |

> Note (accepted by the owner on 2026-10-28, the deep review's O8): a `cdp_url` in the project configuration a Client acting for a model sends is the model's (ADR 0056's #633 note), so `cdp_url_not_allowed`'s fix no longer offers project configuration: "set the address in Operator policy or in user configuration, or give a public address".

- **Each code's details** also carry the address, without its query string and with any credentials in it removed, and the settings layer that gave it (ADR 0083).
- **What stays as it was.** An address that does not answer before the opening call's timeout raises `deadline_exceeded` (ADR 0080) with the address as its target. A Secret reference in `headers` that resolves to nothing raises `secret_unavailable` (ADR 0092). A second Run borrowing the same browser raises `browser_borrowed`, and a Firefox or WebKit page given to `run.borrow()` raises `borrow_requires_cdp` (ADR 0056).
- **No waiting for the address.** A refused connection fails at once, never retried until the timeout: a wrong port is diagnosed immediately with its address (G6), the program that starts its own browser knows when it is ready (G2), and no leader waits (S3). Scenario 09's Rust program keeps its own wait for the port.
- **A Borrowed browser lost after its Session opened** keeps ADR 0056's rules; this ADR covers only opening.

### A missing browser build

| Group | Code | Retryable | When | `fix` |
|---|---|---|---|---|
| `UnavailableError` | `browser_not_installed` | no | The build a Session needs is not in the Browser cache and the engine cannot write that cache, such as an image's read-only `GOODFETCH_BROWSERS_PATH`; or a browser named by channel or path (ADR 0024) is not there | The install command of the Product's executable for that build (`goodfetch-collie browsers install …`, `goodfetch-foxhound browsers install …`, ADR 0090), run where the cache is writable, such as the image's build; or the browser of that channel to install, or the path to correct |
| `RefusedError` | `artifact_unavailable_offline` (ADR 0043) | no | The `offline` setting refused a pinned download; its `limit` names `offline`, its value and the layer that set it (ADR 0079). Under `offline`, a build absent from a cache the engine cannot write raises this code, not `browser_not_installed`, since `offline` is checked first; its `fix` then also names installing the build where the cache is writable, since lifting `offline` alone would not fetch it into that cache | The same install command, run beforehand, or `offline` lifted where it was set |
| `UnavailableError` | `artifact_download_failed` | yes | A pinned download on first use failed after the engine's own attempts. Its `failure` is `network`, `http_status` (with the status) or `digest_mismatch` | Retry, or install beforehand with `browsers install` or point `GOODFETCH_BROWSERS_PATH` at a prepared cache |

- **Their details** name the artifact: for a browser build, the browser, its build ID, and the Product and Product version that pin it (ADR 0098), with the cache's path; for a channel or path, what was looked for and where. `artifact_download_failed` also names the host it came from, never a full URL with a query.
- **"Artifact", not "browser", for the download codes.** The same pinned-download path fetches Lightpanda, Camoufox, Playwright's driver, the Clean-up rules and the Rust crate's engine executable (ADRs 0024, 0047, 0051, 0098), and ADR 0043 already names them artifacts; one code per remedy serves them all (S2). `artifact_download_failed` is not ADR 0085's `download_failed`, a page's download.
- **A browser that is installed but fails to start** (missing system libraries, a crash at start) is not a missing build; its code is area 3's. Crawlee's one `BrowserLaunchError` for both hides which (G6).

### Which call raises them

- **For the `cdp_url` codes and a browser build, the call that opens the Session or launches the browser, never `connect()`.** A connection may never open a browser, and a Session's source may be set per Session (ADR 0092), so `connect()` checks neither (G1); ADR 0078's rule that `connect()` fails early covers the engine and `hello` only. The calls are:
  - `run.newSession({ source })` (Python `new_session(source=...)`, Rust `run.new_session().source(..)`);
  - the first `run.newPage()` of a default Session, which opens it with the `session.source` set at the Run or connection (ADR 0092);
  - in a crawl, the Session pool opening a Session for a request, and a request escalating to the browser tier under `fetch.tier: auto` (ADR 0093): that crawl request's attempt fails with the error, and the request is retried under `crawl.retry.max` only when its code is retryable (ADR 0079), otherwise ending `failed`.
- **No check at a Run's start.** A crawl under `fetch.tier: auto` may never escalate, and refusing its start for a build it might not need would fail a crawl that works (G1). Every request a missing build failed is in the Run report and `run.outcomes()` (ADR 0102), and `retryFailed()` re-admits them once the build is installed.
- **A first-use download is unchanged:** it runs with ADR 0024's progress event, inside the opening call.
- **Other pinned downloads.** For an artifact that is not a browser build, `artifact_unavailable_offline` and `artifact_download_failed` come from the call or command that first needs it, when ADR 0043 lists that download: the Script sandbox or `plugin-shim` first needing the Rust crate's engine executable (ADR 0051), `plugins test` the Proving ground, `plugins add` a Plugin's runtime, a run choosing the Lightpanda tier (ADR 0020). Their details name the artifact and what pins it: a Product version, or for a Plugin's runtime the installed Plugins that use it (ADR 0098).

## Considered Options

- **One code per failure with a reason field** (`cdp_url_failed { reason }`, `browser_missing { reason }`), as the leaders' one error with different messages: rejected. ADR 0079's groups are per code, and three of the four `cdp_url` cases and two of the three build cases would sit in a group whose remedy is wrong for them, with a wrong `retryable` flag (G6).
- **One code per sub-case** (refused, reset, name not resolved, TLS failure, 401, 403): rejected. They share one remedy each, and ADR 0080 refused per-phase timeout codes for the same reason (S2). reqwest also keeps one connect failure, asked with `is_connect()` ([error.rs](https://github.com/seanmonstar/reqwest/blob/2230ed3945/src/error.rs#L156-L172)).
- **Waiting for a `cdp_url` to answer** until the opening call's timeout, so scenario 09's Rust program could drop its own wait for the port: rejected. A wrong port would then fail only after the timeout, as `deadline_exceeded`, instead of at once with its address (G6), and no leader waits (S3).
- **`cdp_url_not_browser` as a `RefusedError` or an `UnavailableError`**: rejected. Nothing refused and nothing is down: the program or its settings point to the wrong thing, which ADR 0079 puts under `ProgramError`.
- **Reusing `borrow_requires_cdp` for an address with no CDP**: rejected. It is `run.borrow()`'s refusal of a Firefox or WebKit page (ADR 0056), whose remedy is to borrow a Chromium page; a `cdp_url` with no CDP is a wrong address, whose remedy is the browser's endpoint.
- **One launch-failure code for a missing build and a browser that fails to start**, as Crawlee's `BrowserLaunchError`: rejected (G6). **A new code for `offline`**: rejected; ADR 0043 already names `artifact_unavailable_offline`, which only needed its group.
- **Checking `cdp_url` and the browser builds at `connect()` or at a Run's start**: rejected, as above (G1).

## Consequences

- **Amends ADR 0056.** Opening a Session on a `cdp_url` fails with `cdp_url_unreachable`, `cdp_url_not_browser`, `cdp_url_unauthorized` or `cdp_url_not_allowed`, the last for its address rules. A note sits under "Which `cdp_url` addresses are allowed".
- **Amends ADR 0098.** A missing build's error is `browser_not_installed`, or `artifact_unavailable_offline` under `offline`, or `artifact_download_failed` when its download fails, each with the details and `fix` its section asks for; its "No Error code is added" no longer holds. Notes sit under "Each Product asks for exactly the builds its version pins" and under its settings and commands.
- **Amends ADR 0043.** `artifact_unavailable_offline` is a `RefusedError` whose `limit` names `offline`; a failed pinned download is `artifact_download_failed`. A note sits under its `offline` setting.
- **Adds to ADR 0079.** The new codes join `goodfetch-protocol`'s list in their groups. A note sits under its Error codes consequence.
- **Adds to ADR 0092.** The calls that open a Session from its source raise these codes; nothing it decided changes, so no note is added there.
- **Error codes.** `cdp_url_unreachable` and `artifact_download_failed` join `goodfetch-protocol` in the `unavailable` group, retryable; `browser_not_installed` in the `unavailable` group, not retryable; `cdp_url_not_browser` in the `program` group; `cdp_url_unauthorized`, `cdp_url_not_allowed` and `artifact_unavailable_offline` in the `refused` group, not retryable, through `xtask codegen`'s naming checks (ADRs 0079, 0099): `CDPURLUnreachableError`, `CDPURLNotBrowserError`, `CDPURLUnauthorizedError`, `CDPURLNotAllowedError`, `BrowserNotInstalledError`, `ArtifactUnavailableOfflineError` and `ArtifactDownloadFailedError` in TypeScript and Python. They are Collie's codes, since Collie opens Sessions and launches browsers (ADR 0088).
- **`GLOSSARY.md`** is unchanged: Borrowed browser, Session source and Browser cache already name what these codes describe.
- **`TESTING.md`** gains the connection and provisioning error cases.
- **Area 3 (Engine runtime)** builds the build checks, the download's `failure` and the launch failure's own code. **Area 5 (Site access)** builds the `cdp_url` probe that tells the four cases apart. **Area 11 (Client surfaces)** builds the classes and their details per language. Each lists this ADR.
- **ADR 0037's matrix:** browser provisioning (SDK-08) and attaching to a running or remote browser (SA-08) cite this ADR; no status changes.
- **The `prototype/sdk-api` sketch** holds the codes, their classes and their details in the `results` and `sessions` files for each language; golden scenario 09's failure point 4 is typed for Rust with `cdp_url_unreachable`, and the pain coverage matrix's P20 and P24 cite this ADR.
