# Collie's TLS relay links wreq's BoringSSL but not wreq, and forwards the browser's own HTTP/2

Collie's executable links BoringSSL for one purpose: the TLS relay that ADR 0042 builds for certificate exceptions in browser Sessions. It links BoringSSL through `btls`, `btls-sys` and `tokio-btls`, the BoringSSL fork that `wreq` itself uses, at `wreq`'s version, and no crate in Collie but the relay's and these three may depend on them. `wreq` stays banned from Collie, since the impersonated HTTP fetch tiers stay Foxhound's (ADR 0088). Upstream, the relay sends a ClientHello rebuilt from the one the browser sent it, offering the browser's own ALPN list. It then forwards the browser's own HTTP/2 (or HTTP/1.1) bytes unchanged, so it links no HTTP stack.

ADR 0042 built the relay "through wreq", ADR 0088 gave the relay to Collie, and ADR 0087 banned "`wreq` and its BoringSSL" from Collie's executable without weighing the relay. The three could not all hold. Primary sources show:
- **rustls cannot replace BoringSSL here.** It sends its own ClientHello: no GREASE, no ALPS, no extension permutation, and only its providers' ciphers and groups. The lab measured reqwest's rustls fingerprint as distinct from every browser's ([TLS fingerprint report](../../rnd/lab/reports/tls-fingerprint-2026-10-08.md)).
- **Cloudflare's `boring` alone cannot mirror every pinned browser.** Read in its published source (5.3.0), it sets ciphers, curves, signature algorithms, ALPN, GREASE, random extension permutation, certificate compression, OCSP and SCTs. It cannot set a fixed extension order (Firefox, Camoufox, Safari), the key shares sent, `record_size_limit` or delegated credentials (Firefox), or keep a TLS 1.3 cipher order as given. ALPS is reachable only through raw FFI. `btls` 0.5.6, "a hard fork of boring" by `wreq`'s author ([README](https://github.com/0x676e67/btls)), exposes all of these. Its `btls-sys` patches BoringSSL to add `SSL_CTX_set_extension_order`, `SSL_CTX_set_record_size_limit`, `SSL_CTX_set_delegated_credentials` and `SSL_CTX_set_preserve_tls13_cipher_list`.
- **One build cannot hold both.** `boring-sys` and `btls-sys` both declare `links = "boringssl"`, and Cargo "requires that there is at most one package per `links` value" ([build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html#the-links-manifest-key)). Foxhound links Collie's code and `wreq`, so a relay on `boring` would make Foxhound's build fail to resolve.
- **Upstream `h2` cannot rebuild a browser's HTTP/2 settings.** `h2` 0.4.20 sets SETTINGS values only. `wreq`'s fork `http2` adds `settings_order`, `headers_pseudo_order` and `priorities`. Forwarding the browser's own frames reproduces all of these exactly and needs neither crate.
- **The size fits, and linking `wreq` instead would save little code and cost more.** A probe for this decision measured BoringSSL through `btls` at +1.43 MB raw and +0.70 MB compressed, and `wreq` with no optional feature at +3.30 MB raw and +1.49 MB compressed (below). So BoringSSL is under half of a bare `wreq`, and a quarter of the +5.49 MB that ADR 0088 cites for `wreq` with every emulation profile ([binary-size research](https://github.com/goodfetch/goodfetch/blob/research/binary-size-budget/rnd/research/2026-10-12-binary-size-limits-and-costs.md) §3.1). Not linking `wreq` saves Collie about 1.9 MB raw and 0.8 MB compressed. That is small, but `wreq` would not even do the relay's job: its TLS connector is private (`pub(super) mod conn`), so it offers an HTTP client, never a TLS stream whose bytes the relay could forward, and it has no verify callback for a pin (ADR 0042). What the relay would write itself is the setting of each ClientHello value on `btls`, which `wreq`'s connector does in about 860 lines from a fixed set of options rather than from each ClientHello. The relay must parse each browser's ClientHello either way.

Decided in [Collie's TLS relay needs BoringSSL, which ADR 0087 bans from Collie](https://github.com/goodfetch/goodfetch/issues/566), first by an agent, then confirmed by the owner in a grilling on 2026-10-16: the relay stays in Collie, links BoringSSL through `btls` with `wreq` still banned, forwards the browser's own HTTP bytes, stays in Collie's Rust SDK crate with no Cargo feature, and leaves the ALPS payload and session resumption to area 4's spec. Each question, its options and the sources are in the ticket's [grilling record](https://github.com/goodfetch/goodfetch/issues/566#issuecomment-6211932547) and the owner's answers. It builds on [ADR 0042](0042-certificate-exceptions-per-domain-pinned-and-relayed-to-browsers.md), [ADR 0087](0087-each-product-is-an-executable-crate-that-links-only-its-crates-and-has-its-own-size-budget.md) and [ADR 0088](0088-collie-carries-every-capability-except-those-only-many-pages-need.md), decided in [#454](https://github.com/goodfetch/goodfetch/issues/454) and [#455](https://github.com/goodfetch/goodfetch/issues/455), and follows G5 of [ADR 0077](0077-the-sdk-api-follows-eight-guarantees-and-four-ranked-shape-rules.md): a certificate exception weakens nothing else. The Session keeps its TLS and HTTP/2 fingerprint toward the site, and the browser still verifies every other host.

## Decision

### What Collie links

- **BoringSSL, through `btls`, `btls-sys` and `tokio-btls`, for the TLS relay only.** Outside these three, the relay's crate is the only crate in Collie that depends on them. Their version is the one `wreq` uses, so the workspace builds one BoringSSL and Foxhound links it once.
- **Not `wreq`, nor the crates that exist for it:** its dependencies `wreq-proto`, `wreq-rt` and `http2`, and its companion `wreq-util`. The HTTP and discovered-API fetch tiers and impersonated HTTP stay Foxhound's (ADR 0088). Collie sends a Session's HTTP only from inside the Session's browser.
- **A version bump of `wreq` that moves `btls` moves the relay's dependency in the same pull request.** The `links` rule leaves no other way to build.

### How the relay connects upstream

- **The ClientHello.** For each connection, the relay reads the browser's ClientHello before answering it, and sets the same values on its upstream connection through `btls`: cipher list (TLS 1.3 order kept), groups and the key shares sent, signature algorithms, ALPN, ALPS and its codepoint, certificate compression, OCSP and SCT requests, `record_size_limit` and delegated credentials when present, GREASE, and ECH GREASE (`set_enable_ech_grease`). It sets the extension order the browser used, through `set_extension_permutation`. GREASE values are drawn fresh, as each browser draws its own.
- **The socket.** The relay opens the upstream connection itself, through the Session's proxy (ADR 0021) and from its local address (ADR 0044), as it already does when it only tunnels.
- **The domain's rule.** The relay applies the trusted CAs, client certificate and pin (ADR 0042) through `btls`'s connector and its custom verify callback (`SSL_CTX_set_custom_verify`). The callback runs the same per-host decision as the engine's rustls verifier, so one implementation decides for both.
- **HTTP/2 and HTTP/1.1.** The relay finishes the browser's handshake with the protocol the site chose, then copies the decrypted bytes both ways. The site sees the browser's own SETTINGS, WINDOW_UPDATE, PRIORITY frames, pseudo-header order and HPACK use. The relay links no HTTP stack, and needs none: the rule, the pin and ADR 0017's address check all apply per connection.
- **The arbiter is ADR 0042's conformance comparison.** It compares the JA4 and HTTP/2 fingerprints of the browser and of the relay, for every pinned browser on every OS, now through Collie's executable. When a browser sends something BoringSSL cannot reproduce, that comparison fails, and the relay's spec or a later decision must deal with it. It is never waived. What JA4 and the HTTP/2 comparison do not see is area 4's spec to settle: the ALPS payload, which reaches the relay only after its upstream handshake, and session resumption.

### Size

- **Measured, BoringSSL adds about +1.4 MB raw and +0.7 MB compressed to Collie.** The probe ran on 2026-10-16, on macOS arm64 with Rust 1.93.0, `lto = "thin"` and `strip = true`, as ADR 0087's research did. Its baseline was `tokio` 1.53.3 with `serde_json`. Each variant was called on input from `argv`, so the linker kept its code:

  | Variant | Raw | gzip -9 | Added raw | Added compressed |
  |---|---|---|---|---|
  | Baseline | 0.59 MB | 0.27 MB | — | — |
  | `btls` + `tokio-btls` 0.5.6: a connector with every setter above, a handshake and a read | 2.02 MB | 0.97 MB | +1.43 MB | +0.70 MB |
  | `wreq` 6.0.0-rc.31, `default-features = false`, `tokio-rt`: a client and a GET | 3.89 MB | 1.76 MB | +3.30 MB | +1.49 MB |
  | Both | 3.94 MB | 1.78 MB | +3.35 MB | +1.51 MB |

  The last row shows the BoringSSL is shared, so in Foxhound the relay adds almost nothing.
- **No ceiling moves.** After the relay and its own code, Collie's projection leaves about 12–19 MB compressed and 26–46 MB raw (with musl, as ADR 0087 counts its 13–20 MB and 27–47 MB) for the engine's own code, under its 50 MB and 120 MB ceilings.
- **The relay's pull request may stay under the +1 MB increase check.** If its own code pushes it over, it passes as ADR 0057 says: with a "Size increase" section, giving the measured delta per target, that the fresh review accepts on its exact head.
  > Amended by [ADR 0133](0133-agent-work-follows-the-matt-pocock-skills-as-written-and-the-fresh-review-is-retired.md): no fresh review exists; the owner accepts the section when merging.
- **`btls-sys`'s 5.16 MB `.crate` is its own crate.** It counts against crates.io's limit, not against the 8 MiB ceiling for `goodfetch-collie`'s tarball (ADR 0087).

## Considered Options

- **rustls in the relay:** rejected. The site would see a Rust TLS fingerprint instead of the browser's, which breaks ADR 0042 and changes a Session's identity whenever it has a certificate exception (ADR 0088).
- **A Foxhound-only relay:** rejected. It breaks ADR 0088. Collie would lose certificate exceptions in browser Sessions (parity row SC-06), and a Browser host run from Collie's executable would lose its relay (ADR 0096).
- **Linking `wreq` in Collie for the relay only,** with the impersonated HTTP fetch tiers kept Foxhound's by a ban on Foxhound's fetch-tier crates and a check that only the relay's crate uses `wreq`: rejected, on equal terms with the decision.
  - **What it would save:** the relay's own setting of each ClientHello value on `btls`. That is a few dozen calls on `btls`, which `wreq`'s connector makes in about 860 lines from options set per client, not per connection. The ClientHello parser is needed either way.
  - **What it would cost:** +1.9 MB raw and +0.8 MB compressed more in Collie (measured above).
  - **What it would break:** `wreq`'s TLS connector is private, so the relay could only re-send each request through `wreq`'s HTTP client. It would have to terminate and translate the browser's HTTP: HTTP/2 streams and priorities, WebSocket upgrades over HTTP/1.1 and HTTP/2, streaming bodies, informational responses and trailers. The site would then see `wreq`'s rebuild of the browser's HTTP/2 frames instead of the frames themselves. The pin would still wait on the verify callback that ADR 0042 must add to `wreq`.
  - **The verdict:** a small saving of reimplementation for more code, more size and less fidelity.
- **Cloudflare's `boring`/`boring-sys`,** as area 4's draft spec proposed: rejected. It cannot mirror Firefox's, Camoufox's or WebKit's ClientHello, all of which the relay must send for a fully relayed Session (ADR 0042). Its `boring-sys` cannot share a build with `wreq`'s `btls-sys`.
- **Goodfetch's own BoringSSL patches:** rejected. They would be a third fork to keep current, beside `btls`, which Foxhound already depends on.
- **Rebuilding the HTTP/2 frames with `http2`:** rejected. It would put a second fork in Collie, and a rebuild only approaches what forwarding reproduces.
- **Upstream `h2`:** rejected. It cannot set the order of SETTINGS or of pseudo-headers, nor send PRIORITY frames.

## Consequences

- **Amends ADR 0087.** Collie's parts gain the relay's BoringSSL (+1.4 MB raw, +0.7 MB compressed), and its headroom shrinks as above; a note sits at "The headroom absorbs the engine's own code". Collie's ban list keeps `wreq` and the crates that exist for it. `btls`, `btls-sys` and `tokio-btls` are each a deny entry whose `wrappers` list its allowed direct parents: `tokio-btls` the relay's crate; `btls` the relay's crate and `tokio-btls`; `btls-sys` `btls`, and the relay's crate only if it calls the FFI itself, so no other crate reaches BoringSSL. cargo-deny checks every direct parent of a denied crate against its `wrappers`, which "allows specific crates to have a direct dependency on the banned crate but denies all transitive dependencies on it" ([bans config](https://embarkstudios.github.io/cargo-deny/checks/bans/cfg.html)). A note sits at the ban list.
- **Amends ADR 0088.** Collie's ban list keeps out `wreq` but not its BoringSSL, which the relay links. A note sits at "Collie's `cargo-deny` ban list".
- **Amends ADR 0042.** The relay connects upstream through `btls`, not through `wreq`. It rebuilds the ClientHello from the browser's, and forwards the browser's own HTTP/2 frames instead of rebuilding them. A note sits at the relay's upstream item. ADR 0042's change to `wreq` for pins stays: it is for Foxhound's HTTP tiers.
- **Building Collie's engine from source now needs CMake, a C and C++ compiler, libclang and git,** which `btls-sys`'s build script uses. It costs most for programs that embed the Rust SDK crate (ADR 0024), which did not need them before. `cargo install goodfetch-collie --locked --features executable` (ADR 0094) already needs libclang for V8. Building Foxhound already needs all of them, through `wreq`. The Rust SDK's install docs list them.
- **Collie's Rust SDK crate keeps the relay.** An engine embedded in a Rust program launches browser Sessions that can have certificate exceptions, so the relay is not put behind a Cargo feature as ADR 0094 put V8 behind `executable`. V8 could go there because the embedded engine runs the Script sandbox from the engine executable (ADR 0051). Keeping a capability out of an engine by a feature is what ADR 0038 refuses.
- **ADR 0037.** SC-06 cites this ADR. Areas 1 and 4 list it.
- **Areas.**
  - Area 1 (Repository, CI and release) builds the ban list and its `wrappers`, and the Size budget check that records the relay's increase.
  - Area 4 (Security and egress) builds the relay's upstream connection: ClientHello mirroring through `btls`, the domain's rule in the custom verify callback, and the forwarding of the browser's HTTP bytes.
- **Glossary.** No term changes.

> Note (agent decision, as built), 2026-10-25, [#635](https://github.com/goodfetch/goodfetch/issues/635): the relay's crate is `goodfetch-page`, whose `egress_relay` module the Rust SDK crate links with no Cargo feature, so Collie's bans (`ci/deny/collie.toml`) list `goodfetch-page` as the wrapper of `tokio-btls`, and `goodfetch-page` and `tokio-btls` as those of `btls`; the relay calls no FFI, so `btls-sys` keeps `btls` alone. `ci/proofs/` holds a stand-in `goodfetch-page` taking `tokio-btls`, which the bans allow, beside one that does not. BoringSSL links libstdc++, so the DHAT benchmarks of the crates that link the relay set `GLIBCXX_TUNABLES=glibcxx.eh_pool.obj_count=0`: libstdc++'s emergency exception pool, allocated as the loader starts the process, otherwise leaves frames DHAT names with no location, which gungraun cannot read.

> Note (agent decision, as built), 2026-10-26, [#636](https://github.com/goodfetch/goodfetch/issues/636): two more BoringSSL calls go through `btls-sys`, each a function-level `#[expect(unsafe_code)]` with a `// SAFETY:` comment, as the M1 Core run's fix-queue 74 did for `SSL_CTX_set1_requested_trust_anchors`; `foreign-types` 0.5.0, at `btls`'s version, gives their pointers. `SSL_add_application_settings` and `SSL_get0_peer_application_settings` (`egress_relay::application_settings`): `btls` sends ALPS with an empty payload only and reads none, and the relay sends the pinned build's captured payload, which `pin-chrome-for-testing alps` reads with the same module's `capture_application_settings` (Chrome for Testing 156 sends an empty one for `h2`). `SSL_set_session` (`terminate::resume`): `btls`'s `set_session` asks for a session of the same `SslContext`, while each upstream connection builds its own context from the browser's ClientHello; BoringSSL ties a client session to no context, only to the X.509 method every context of the library shares, and offers none its settings cannot resume. A Session's relay keeps the latest upstream session of each host, at most 64, and drops them with the Session; a resumed connection's chain is the one its session kept, which the Run's decision reads again before any byte of the browser's goes up.
