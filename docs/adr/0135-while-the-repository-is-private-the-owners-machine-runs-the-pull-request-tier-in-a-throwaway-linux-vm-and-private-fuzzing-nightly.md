# While the repository is private, the owner's machine runs the pull-request tier in a throwaway Linux VM, and private fuzzing nightly

While the repository is private, ADR 0108's self-hosted runner on the owner's machine (Apple M3 Max) also runs the pull-request tier: every job of the tier runs there, and each job's build and tests run inside a Linux VM that Lima creates for that job and destroys after it. The VM runs an x86-64 userland through Rosetta for Linux, so the tier's Linux x64 checks keep their platform. Its build cache is a folder on the machine that only a `main` job writes. Private fuzzing runs there too, nightly on `main`'s head, in the same kind of VM. Nothing falls back to GitHub-hosted runners. The hosted jobs left (the ingest of test results and the checks run by hand) take at most 240 of the 400 included minutes a month that ADRs 0064 and 0108 leave, each line under a budget of its own.

ADR 0108 holds 600 of the account's 2,000 included minutes a month for the manual-dispatch Release runs, beside ADR 0064's 1,000 for test health, and leaves at most 400 for every other hosted job of the account. Two consumers had no budget. The pull-request tier (ADR 0061: `just quick all`, then the Pre-merge suite on Linux) runs on every push of every pull request, and agents open many. Private fuzzing (ADRs 0067 and 0076) needs about 1,800 minutes a month for its nightly `batch` of 3,600 s alone, before 600 s of `code-change` after every push. The cache-warming job on every push to `main` (ADR 0061), the ingest workflow after every finished run (ADR 0064) and the checks run by hand, such as ADR 0065's Live checks and ADR 0043's online conformance, draw on the same remainder. Without a payment method, an account that runs out is blocked, not billed, so pull requests would stop getting checks.

Facts this rests on, checked on 2026-10-18:

- **Pull-request volume:** 183 pull requests were opened in the 30 days before 2026-10-18 (`gh pr list`), before any code exists. At 10 hosted minutes a pull request, that is about 1,800 minutes a month, more than four times what is left.
- **Minutes are rounded per job** ([Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)): each job's minutes and partial minutes are rounded up to the nearest whole minute, so a hosted job that runs for seconds after every pull-request run costs a minute each time.
- **Self-hosted runners are free today** ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)): "GitHub Actions usage is free for self-hosted runners". The $0.002-a-minute charge for self-hosted runners in private repositories was postponed, not cancelled, with no new date (ADR 0108's facts).
- **Pre-job and post-job scripts** ([run scripts](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts)): the scripts see the job's default variables and the full event payload at `GITHUB_EVENT_PATH`, run as the runner's service user, block the job while they run and have no timeout setting. The docs do not say whether the post-job script runs when a job is cancelled.
- **A queued job fails after 24 hours** on a self-hosted runner (ADR 0108's facts).
- **Lima** ([multi-architecture](https://lima-vm.io/docs/config/multi-arch/)) is free and open source. On an Apple silicon Mac its VMs run Linux arm64 natively. "Running a VM with a foreign architecture is extremely slow"; x86-64 programs run faster in an arm64 VM through "Rosetta for Linux", which is "available for VZ instances on ARM hosts".
- **Rosetta's end is announced.** Apple: "Rosetta is available for any Mac with Apple silicon using macOS 27 or earlier"; from macOS 28 it serves only certain older games (ADR 0108's facts). Whether Rosetta for Linux in a VM outlives macOS 27 was not found.
- **Actions run where the runner runs.** `actions/checkout`, `Swatinem/rust-cache` and `actions/upload-artifact` run on the macOS host, not in the VM, and rust-cache's key includes the runner's OS and architecture ([rust-cache](https://github.com/Swatinem/rust-cache)).

Decided by the owner on 2026-10-17 in [Fit the pull-request tier, private fuzzing and other hosted jobs in the included minutes left](https://github.com/goodfetch/goodfetch/issues/545): the owner's machine runs the pull-request tier, in a throwaway Linux VM, and private fuzzing runs nightly on merged `main` there. On 2026-10-18 the owner settled the rest:

- the VM tool is Lima; the machine never sleeps while on power; a check that failed because the runner was offline is re-run with `gh run rerun` once it is back; and nothing falls back to GitHub-hosted runners;
- the VM runs an x86-64 userland under Rosetta for Linux, re-pinning a check to Linux arm64 only where Rosetta fails it;
- the build cache is a folder on the machine, written only by a `main` job there and read-only to pull-request VMs;
- the pull-request tier keeps ADR 0061's time budgets, measured on the machine from each job's start;
- ADR 0072's in-diff mutation job runs on the machine;
- runs that ran only on the machine reach the results store through one daily hosted ingest job.

This ADR records those and settles what they and earlier ADRs imply. It builds on ADRs 0032, 0061, 0064, 0067, 0071, 0072, 0076 and 0108.

> Amended on 2026-10-22 (owner decision of 2026-10-22, with agent decisions as built where marked): the local gate is incremental, and a gate verdict may combine a full run on an ancestor head with an incremental run on the pull request's head. Every `just pre-merge all` records each step's result, pass or fail, by step, head, tree and time, with a fingerprint of the host and its tools (the kernel, the system's packages, the runtimes, the test runners, the container engines and the toolchain), in the gate worktree's `target/gate-runs/`, which is never committed and which `just merge` keeps between gates; one gate run at a time holds it. A step's result is recorded once the whole step has ended, and only while the planned head is still checked out on a clean tree; otherwise the run records nothing more and fails. A run on a head that descends from a recorded head plans from the nearest one (`xtask gate plan`). It reuses a step's green result when the change since the head the result ran on reaches neither the step by `xtask affected` nor, by the evidence of what each workspace member read, the members the step tests. By `xtask affected`: `just perf` when that change selects no `perf` job, the visual projects no `visual` job, TLC no `tlc` job, the tests only Linux decides no Pre-merge job, and the MSRV build and Miri no crate. The Quick suite, the Pre-merge suite with its exercise audit, and the stress run are judged per workspace member (a crate, a pnpm or a uv package), plus the tests no member owns, such as `console/screens.spec.ts`, which rerun whenever any member does. `xtask affected` reaches every package of an ecosystem when the change reaches a package that every run of its runner loads (one the root Vitest or Playwright config imports, or a pytest plugin), follows the workspace imports a package's files make whether or not its manifest declares them, and reaches the crate that embeds the Console's build (ADR 0057). The evidence is checked apart from that graph, and a member it reaches reruns with its dependants: Cargo's dep-info and the build scripts' `rerun-if-changed` paths, for every file a crate's last build read, `include_str!` targets among them; Vitest's `--changed` and Playwright's `--only-changed` listings since the head, which follow each test's own module graph; and a string literal in a member's files naming a changed file that no member owns, as a test that reads `TESTING.md` at run time does. Missing or unreadable evidence (no dep-info for one of a crate's test targets, a listing that fails) reruns the member, and a member the listings alone name reruns the visual job too when it owns a visual test. The plan's log names each member the evidence reaches beyond `xtask affected`'s selection. The stress run repeats only the pull request's new and changed tests of the members it reruns, plus every test whose file the change since the earlier run changed. Every run reruns the checks that judge the whole change: sign-offs, commit messages, `just lint` (with its codegen, compat, Feature, Client and Journey checks), advisories, secrets in commits and the notices, and also, as an agent decision, the feature combinations, the fuzz-target check, the proofs, the Journey task lists and the Feature and Client listing checks. A red result is never reused, a step with no result runs, and so does a result older than a day or from another host fingerprint. A change to the gate's own inputs reruns every step in full: the justfile, `ci/`, `.config/` (nextest's settings), `.cargo/`, the root Cargo, pnpm and uv manifests and lockfiles, `rust-toolchain.toml`, and, as an agent decision, `xtask`, which runs most steps and makes the choice itself, and the files tests of several members read at run time: the Proving ground's `pages/` and `fixtures/`, `test-support/fixtures/`, `chromium/` and Collie's browser pins (`crates/goodfetch-collie/src/pins.json`). A moved base (the merge base with `origin/main`) reruns perf and the stress run. The run's log names, for each step, whether it reran and, when reused, the head it ran on and the run that carried it, and the merge commit names the reused run. A working tree with uncommitted changes reuses and records nothing, and `GOODFETCH_GATE_FULL=1` reruns everything. A run with `GOODFETCH_TEST_SELECTION`, `GOODFETCH_TEST_ENGINE` or `GOODFETCH_ORDER_SEED` set fails before any step, and the other variables that change how the steps run (`CI`, `GOODFETCH_*`, `NEXTEST_*`, `CARGO_*`, `RUST*`, `UV_*`, `NODE_*`) join the host fingerprint, so a result counts only for a run in the same environment. Known limits, accepted as agent decisions: a test that reads at run time a file another member owns, through neither an import nor a build input, is seen by none of the evidence; it reruns only through a declared dependency or `runs` edge (today every such read, of `goodfetch-protocol`'s generated bundle, has one), and the shared data such reads use are gate inputs, above. Dep-info is required for each of a crate's test targets by name, and a library's plain build and its test build share that name, so an `include_str!` only the test build has is seen only once a test build ran; the gate's own worktree keeps the previous gate's test builds, and the literal scan sees such a path too. Vitest, Playwright and pytest order their tests by the head's seed (TESTING.md, Before merge), so every run reruns them in the head's order, over every workspace member, reused or not, and with every test those runners have, as a full run does (`just test <suite> --shuffled-all <crates>`, and the stress run within every pnpm and uv member and the unowned tests); nextest runs each test in its own process, so only a crate's result is reused (owner decision of 2026-10-22, F8 option B). A reused crate's result therefore counts only together with that rerun, green in the head's order, and the incremental verdict matches a full run's in test order too; the differences from a full run that remain are the known limits above and the one below. One more difference from a full run on the head remains: a part builds its crates with `-p`, whose dependency features unify over fewer members than `--workspace`, which the always-rerun feature combinations and the rule that a capability is a setting, not a Cargo feature, keep from changing behaviour. A reused perf result was judged against the acceptance its own run read (ADR 0134); while no figure fails (ADR 0134, as amended on 2026-10-22), that changes no verdict, and this note is revisited before figures gate again (agent decision).

> Amended on 2026-10-28 (owner decision of 2026-10-28, adopting option 7 of the test-gate audit; the backstop as first drafted on 2026-10-23 in #1591): the incremental gate has a backstop. `just gate-backstop`, daily from the gate host's cron, runs `just pre-merge all` in full (`GOODFETCH_GATE_FULL=1`) on `main`'s head (during M1, the milestone branch's, where `just merge` lands) in a gate worktree of its own (`.claude/worktrees/gate-backstop`), then compares that run with each incremental run in `just merge`'s records on the same tree, the merge's gated head (`xtask gate compare`). A result that run reused and the full run found red is a selection miss, recorded in `~/gate-backstop/misses.txt` with the run and the head it reused from, and fails the backstop: each one is a defect of the selection to fix. A reused result the full run has no result for, because it stopped at a red step, is reported as unchecked. One line a day goes to `~/gate-backstop/results.txt`. Daily, because a result is reused for a day at most, so a miss is found before the results it rests on expire. In a worktree of its own, at low priority, so it never holds `just merge`'s worktree, at the cost of a second gate build on the disk (about 25 GB): it starts only when its build leaves the 60 GB the server keeps free (85 GB free before its first build, 65 GB after), and a day it skips is listed as skipped and fails; its full record stays in its own worktree, and `just merge` plans only from its own runs. > Amended on 2026-11-09 (owner decision of 2026-11-09, « Oui, avec F4 », on [#2090](https://github.com/goodfetch/goodfetch/issues/2090)'s F4 and [#2233](https://github.com/goodfetch/goodfetch/issues/2233), taken once the backstop's first green run, on a8d28bf3f, lifted #2090's hold on wider reuse): a gate reruns less, and no check weakens. First, a change to a path the gate's own files name reaches only the steps that read it, by a map in `xtask gate plan`. A change to an xtask test file reruns `xtask` in the steps run per member and the Linux step. A `ci/` file only some steps run reaches those steps, and a `ci/` file only the checks that rerun in every run read, or no gate step runs, reaches none. Any path the map does not name still reruns every step, and `xtask/src/` stays a full input, since it decides the plan. A test that reads a changed `ci/` file still reaches its member by evidence, and evidence that reaches `xtask` adds the Linux step instead of widening as a crate's would, since `xtask` has no dependant and no benchmark. A test reads the real `justfile` and scripts and fails when a step's recipe or script names a mapped path the map does not give it. It sees paths written from the repository's root; it does not see a script's relative reference to its sibling, nor a file a step reads from xtask's own code, so the map's entries for what such reads reach rest on reading them by hand. A new file in a folder the map names reaches what that folder's entry says, not every step. Second, a red stress run no longer costs the members it did not fail their clean passes. A crate the run left short of its counts, with no failing test, keeps each selected test's earned passes in `<head>.earned`, beside the record. A member that keeps them reruns, and each of its tests runs what its 20 or 200 still owes; the total is never lowered. They hold by the rule a green result holds by, the same code: the member's inputs identical since the head the earliest pass ran on, the same host fingerprint, the same base when the base bears on the step, and within `MAX_AGE` of the start of the stress run that gave the first one, which is no later than that pass and which a result that counted them keeps as its own age; the selection checks that age again when it reads the file, later than the plan. A failing test takes its member's earned passes. > | Sign-offs and subjects (`dco`, `commit-messages`) | each commit | whichever runs first: the pre-push hook for pushed commits, `just merge` for the commits it makes | Each records the commits it judged green and judges only the rest. |

> | The Pre-merge suite per member, browser tests and Linux-only tests included | a batch or spec pull request's tree | the hosted tier, sharded | `just merge` reuses it. The local Pre-merge run beside batch-check and the one in `just preflight` end. A member's Quick suite unit counts as covered by its Pre-merge unit. |
> | The full gate's other steps: feature combinations, fuzz-target check, proofs, MSRV, Miri, loom, TLC, the Kennel, feature tests, visual tests, the Windows build under Wine | a spec pull request's tree | the hosted tier | `just merge` reuses them. |
> | `perf` (counted and timed rows, `just counts`) and the stress run | a spec pull request's tree | the gate host: `just preflight` or `just merge`, whichever runs first | Each writes the shared record, and the other reuses it on the same tree. |
> | Release suite cells | a `main` commit, on every platform | the Release suite dispatch | The Linux x64 cell reuses hosted Pre-merge units of the same tree and the same test set. |
> | Nightly fuzzing | `main` | the gate host's cron (private, ADR 0067) | None. |
> | Everything a fork's pull request reaches | the fork's head | the hosted tier, once approved | `just merge` never reads a fork's records. > - **How `just merge` reads hosted records.** Through GitHub's API, it accepts a run only when the run is the repository's own pull-request workflow, its event is `pull_request`, its head repository is this repository, and its head commit is the gated head or a first-parent ancestor of it. An accepted record counts as an earlier run, under the same rules as the gate's own records, only when its image digest is the one the gated tree pins. A fork's runs are never read. A required status check was rejected: a check run gives one conclusion per job, not the units the plan reuses; it cannot tell a fork's or another workflow's check of the same name apart without these provenance checks; and rulesets are the owner's setting.
> - **Waiting, cancelling, falling back.** The gate first runs the units it owns. For each hosted-owned unit with a hosted run in progress on the gated head, it waits up to ADR 0061's job cap of 30 minutes from the run's start. When the cap passes, or the run is queued past it, cancelled or missing, the gate cancels any run still going on that head and runs the uncovered units itself, so a unit runs on one layer only; where the gate host's token cannot cancel a run, the gate waits for the run to end instead, and never runs the unit beside it. A red hosted unit on the gated head ends the gate red and names the job, and is never retried away (ADR 0064). The gate's log says, for each unit, whether it ran here or reused a local or hosted record, and which run. The hosted run on the merge of `main`'s tip that the gate pushes plans from the batch head's hosted record, so it runs only the units that merge reaches. `just merge` stays the only way to merge, and the lock, the merge of `main`'s tip and the closing-issues check stay its own: when Actions is down, disabled or out of free concurrency, the gate runs every unit itself, so the hosted tier speeds the gate up and never gates it.
> - **`just batch-check` retires,** and with it the batch's local Pre-merge run beside it: the batch pull request's hosted run covers all their checks, a superset of their selections. A batch is assembled, pushed with its pull request opened, which starts the hosted run, and then gated by `just merge`.
> - **`just preflight` keeps only the gate host's units,** the stress run and `just counts` (perf's counted rows), and writes them to the shared record, so the full gate reuses them on the same tree. Its floor guard and Pre-merge suite leave it: the gate runs the first in seconds, and the hosted tier owns the second.
> - **The pre-push hook,** for a push to a branch with an open pull request to `main` that the hosted tier serves, judges the pushed commits only and leaves `just quick` to the hosted run; every other push keeps today's rule, `just quick` unless a green run holds the pushed head. `dco` and `commit-messages` record each commit they judged green and judge only the rest; the gate always judges the merge commit it makes.
> - **A member's Quick suite is covered by its Pre-merge suite.** Where a member's Pre-merge unit runs or is reused on a tree, the plan marks its Quick unit as covered by it, once a test shows that the member's Pre-merge selection holds every Quick test of the member. The full gate then no longer runs the Quick suite and the Pre-merge suite, which contains it, on one tree.
> - **`just quick` records its runs in the shared record** (as built: `quick-runs`, one line a run), green or red, on a clean checkout, by the layer that ran it, `quick` or `pre-push` (the hook's run), in place of the green trees each worktree's hook read before (`goodfetch-quick-green`, whose stamps are dropped). Its unit is `just quick` with its form and the merge base of the head with the change's base, so a run of `just quick all`, or one against another base, holds none of the others. A run is held when the latest run of its unit on the same tree, host fingerprint and step variables is green, within a day, and lint's reads of the day and GitHub still read as green, as the plan reads them for a reused lint; a held run runs only the checks of the change's commits, which read more than the tree. The recorded result is that of the steps after those checks, since a red commit is mended by a rewrite that keeps the tree. The step runner's variables (`ci/keep-going.sh`'s) and the launcher's base and layer are left out of the fingerprint, so the hook and the run it starts read one key. The gate's quick form records nothing yet: its reuse of `just quick` comes with the hosted form ([#3377](https://github.com/goodfetch/goodfetch/issues/3377)).
> - **The duplicate-run check,** `just duplicate-runs` (`xtask gate duplicates`), reads every run in the shared record and fails, naming both layers, on each unit a run ran, not reused, on a tree where an earlier run on the same host had recorded it green within a day. A rerun after a red result is none, nor one past a day or under another host fingerprint, which no plan reuses across, nor a rerun of the commit checks or the audit, whose verdicts read the commits and the advisories as well as the tree. A plan on a head replaces that head's record, so a rerun on the same head is out of its sight.
> - **What stays on the gate host:** timed and counted readings (`perf`, `just counts`, `just compare`), since hosted runners share hardware; the stress run; and the private nightly fuzzing (ADR 0067). The quick-gate and full-gate rules above, and what each step checks, do not change.

### Availability, and how a queued or failed check is noticed

- **A job waits in GitHub's queue while the runner is offline, and fails after 24 hours there.** The machine is set never to sleep while on power ([#1562](https://github.com/goodfetch/goodfetch/issues/1562)), so the runner is offline only when the machine is off or loses its network.
- **A check that failed because the runner was offline is re-run once the runner is back,** with `gh run rerun <run-id> --failed`. Such a job never reached a runner: it has no runner name in `gh run view <run-id> --json jobs`. A job that reached the runner and failed, whether the pre-job script refused it or a test failed, is an ordinary failure and is never re-run (ADR 0064).
  > Amended on 2026-10-19 (owner decision of 2026-10-19): a job with no `Test` steps whose figures are deterministic, `perf` and, where it gates, `size`, may be re-run after the owner's acceptance comment. It is no retry, since nothing flaky is masked; "all green" still refuses a run whose earlier attempt failed a `Test` step.
- **No job falls back to GitHub-hosted runners.**
- **The merging agent reads the checks before every merge** with `gh pr checks <number>`. It never merges while "all green" is pending or failed. When a check is pending and `gh api repos/goodfetch/goodfetch/actions/runners` shows the `owner-machine` runner offline, it tells the owner that the check is waiting for the machine. When a check failed because the runner was offline, it re-runs it once that call shows the runner online.
- **The owner is notified by GitHub's own Actions notifications,** on by default, which report a failed run to the account that triggered it; agents push and dispatch under the owner's account. A queued check shows as pending on its pull request, and the merging agent reports it as above. Nothing else is set up, and nothing costs money.
- **A nightly fuzzing run that failed because the runner was offline is re-run the same way,** or left to the next night's run, which covers the same `main`.

### The hosted jobs that still draw on the included minutes

Every line is counted in ADR 0108's Linux-equivalent minutes, from the job durations the ingest records, as ADRs 0064 and 0108 count theirs.

- **The ingest of each finished run that had a hosted job** stays as ADR 0064 has it, so the ceilings' counts stay current. A workflow whose jobs all run on the owner's machine, the pull-request tier first among them, is left out of its trigger: one hosted ingest job after each pull-request run would cost a minute each time, 183 minutes or more a month on its own.
- **The daily ingest job** copies those workflows' finished runs of the past day into the results store, in one scheduled hosted job with a 2-minute timeout. Flaky tests in pull-request runs are then detected a day later, which nothing gates on.
- **The checks run by hand** are dispatched through their recipes, which read this line's count for the month from the results store before dispatching, locally and with no runner. A dispatch whose estimate would take the line past 90 is refused with the minutes needed and the date the month turns.
- **A line past its budget opens an issue.** The daily test-health job, which already reads the month's counts, opens or updates one `needs-triage` issue per line that has passed its budget, as a budget breach does (ADR 0061). The fix is to shorten its jobs or move work to the owner's machine. Nothing is bought.

### When things change

- **If GitHub announces a date for the self-hosted charge in private repositories,** this design is revisited before that date: the agent that finds the announcement opens a `needs-triage` issue that links this ADR. The pull-request tier would not fit the included minutes even at one third of a Linux minute, and the charge is never paid (ADR 0076).
- **If Rosetta for Linux ends,** the checks it serves move to Linux arm64 in the VM, as above.
- **Once the repository is public,** the pull-request tier leaves the owner's machine, as above. Fuzzing stays.
  > Note (2026-11-22): the owner made the repository public on 2026-11-22. The pull-request tier never left the gate host for the owner's machine (the amendments of 2026-10-19 and 2026-10-22); its move to GitHub-hosted runners is triggered, not yet done, and tracked by the hosted-CI spec ([#3373](https://github.com/goodfetch/goodfetch/issues/3373)). Fuzzing stays.

## Considered Options

- **The pull-request tier and fuzzing on GitHub-hosted runners, with per-run caps and a reduced fuzzing schedule:** rejected. With 183 pull requests a month, the pull-request tier alone passes the 400 minutes left, and nightly fuzzing alone needs about 1,800.
- **Paid minutes, or a payment method with a spending limit:** declined while there is no revenue (ADR 0076).
- **Making the repository public now:** declined by the owner for now (ADR 0108); reopening it is the owner's call alone.
  > Note (owner's decision, 2026-11-22): reopened by the owner, who made the repository public that day (the note of 2026-11-22 under Decision).
- **The pull-request tier directly on the macOS host:** rejected by the owner's decision of a throwaway Linux VM. Nothing a job left behind would be cleared before the next job or a timing, and the Pre-merge suite's platform is Linux.
- **A fallback to GitHub-hosted runners while the machine is offline:** declined by the owner on 2026-10-18. A day of queued checks would spend the month's minutes, and a re-run once the runner is back costs nothing.
- **Native Linux arm64 in the VM, with the Linux x64 checks re-pinned to arm64 while private:** not chosen by the owner on 2026-10-18, except check by check where Rosetta fails. Reference screenshots and counted figures recorded on arm64 would be recorded again on x64 once the tier is hosted, and ClusterFuzzLite's arm64 support was not confirmed.
- **The Linux x64 checks on hosted Linux x64 runners:** rejected. Run on every pull request, they would not fit the 400 minutes.
- **The cache-warming job on GitHub-hosted runners, restored on the host and handed to the VM:** not chosen by the owner on 2026-10-18. It would cost included minutes, a download per job and room in GitHub's 10 GB, where a folder on the machine costs none.
- **No build cache:** rejected. Every job would build its dependencies from scratch, against the 20-minute "all green" budget.
- **Suspending the tier's time budgets, or new budgets for the owner's machine:** not chosen by the owner on 2026-10-18. ADR 0061's budgets keep guarding test speed; measuring from each job's start keeps the machine's queue out of them.
- **The in-diff mutation job kept hosted under ADR 0064's ceiling:** not chosen by the owner on 2026-10-18. It would stop after about nine runs a month.
- **Ingesting the owner's-machine runs in the daily test-health job, or on the owner's machine:** not chosen by the owner on 2026-10-18. The first takes room ADR 0064's ceiling does not have; the second would put the results store's token on the runner, which holds no secret (ADR 0108).
- **Fuzzing in the main repository's workflows, on its runner instance:** rejected. Their logs would become public with the repository, which ADR 0067's containment forbids.
- **One runner registered on the organization, serving both repositories:** rejected. ADR 0108 registers the runner on the repository only, so that no other repository of the organization reaches the machine.

## Consequences

- **Amends ADR 0108:** its allowlist gains the pull-request tier's and the cache-warming job's entries, squared with ADRs 0032 and 0071 above, and its "one runner instance" becomes two instances that never run jobs at once, the second serving the private fuzzing repository. One-line notes sit at its allowlist rule and its single-instance rule.
- **Amends ADR 0061:** while the repository is private, the pull-request tier runs on the owner's machine in a Linux VM with an x86-64 userland, never on GitHub-hosted runners; its budgets are measured there from each job's start; and the cache-warming job runs there, writing a cache folder on the machine. One-line notes sit at its tier table, its budgets and its cache-warming job.
- **Amends ADR 0064:** while the repository is private, the ingest after each run covers only workflows with a hosted job, and a daily hosted job ingests the rest. A one-line note sits at its ingest workflow.
- **Amends ADR 0067:** fuzzing runs nightly only, on the owner's machine in a VM, through a runner instance of the private fuzzing repository; push fuzzing and continuous builds do not run. A one-line note sits at where it runs.
- **Amends ADR 0072:** while the repository is private, the in-diff mutation job runs on the owner's machine, without the four-shard cap or the 550-minute threshold. A one-line note sits at its in-diff job.
- **Amends ADR 0076:** the owner's machine also runs the pull-request tier while private, and private fuzzing, instead of fuzzing within the included minutes. One-line notes sit at its CI rule and at the fuzzing row of its table.
- **Amends ADR 0032's rule, which ADR 0071 restates:** the machine that stands in for the reference host runs pull-request code, in a VM recreated for each job and never during a timing. A one-line note sits at ADR 0032's release-candidate benchmark.
