# While the repository is private, the owner's machine runs the pull-request tier in a throwaway Linux VM, and private fuzzing nightly

While the repository is private, ADR 0108's self-hosted runner on the owner's machine (Apple M3 Max) also runs the pull-request tier: every job of the tier runs there, and each job's build and tests run inside a Linux VM that Lima creates for that job and destroys after it. The VM runs an x86-64 userland through Rosetta for Linux, so the tier's Linux x64 checks keep their platform. Its build cache is a folder on the machine that only a `main` job writes. Private fuzzing runs there too, nightly on `main`'s head, in the same kind of VM. Nothing falls back to GitHub-hosted runners. The hosted jobs left (the ingest of test results and the checks run by hand) take at most 240 of the 400 included minutes a month that ADRs 0064 and 0108 leave, each line under a budget of its own.

ADR 0108 holds 600 of the account's 2,000 included minutes a month for the manual-dispatch Release runs, beside ADR 0064's 1,000 for test health, and leaves at most 400 for every other hosted job of the account. Two consumers had no budget. The pull-request tier (ADR 0061: `just quick all`, then the Pre-merge suite on Linux) runs on every push of every pull request, and agents open many. Private fuzzing (ADRs 0067 and 0076) needs about 1,800 minutes a month for its nightly `batch` of 3,600 s alone, before 600 s of `code-change` after every push. The cache-warming job on every push to `main` (ADR 0061), the ingest workflow after every finished run (ADR 0064) and the checks run by hand, such as ADR 0065's Live checks and ADR 0043's online conformance, draw on the same remainder. Without a payment method, an account that runs out is blocked, not billed, so pull requests would stop getting checks.

Facts this rests on, checked on 2026-10-18:

- **Pull-request volume:** 183 pull requests were opened in the 30 days before 2026-10-18 (`gh pr list`), before any code exists. At 10 hosted minutes a pull request, that is about 1,800 minutes a month, more than four times what is left.
- **Minutes are rounded per job** ([Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)): each job's minutes and partial minutes are rounded up to the nearest whole minute, so a hosted job that runs for seconds after every pull-request run costs a minute each time.
- **Self-hosted runners are free today** ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)): "GitHub Actions usage is free for self-hosted runners". The $0.002-a-minute charge for self-hosted runners in private repositories was postponed, not cancelled, with no new date (ADR 0108's facts).
- **Pre-job and post-job scripts** ([run scripts](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts)): the scripts see the job's default variables and the full event payload at `GITHUB_EVENT_PATH`, run as the runner's service user, block the job while they run and have no timeout setting. The docs do not say whether the post-job script runs when a job is cancelled.
- **A queued job fails after 24 hours** on a self-hosted runner (ADR 0108's facts).
- **Lima** ([multi-architecture](https://lima-vm.io/docs/config/multi-arch/)) is free and open source. On an Apple silicon Mac its VMs run Linux arm64 natively. "Running a VM with a foreign architecture is extremely slow"; x86-64 programs run faster in an arm64 VM through "Rosetta for Linux", which is "available for VZ instances on ARM hosts".
- **Rosetta's end is announced.** Apple: "Rosetta is available for any Mac with Apple silicon using macOS 27 or earlier"; from macOS 28 it serves only certain older games (ADR 0108's facts). Whether Rosetta for Linux in a VM outlives macOS 27 was not found.
- **Actions run where the runner runs.** `actions/checkout`, `Swatinem/rust-cache` and `actions/upload-artifact` run on the macOS host, not in the VM, and rust-cache's key includes the runner's OS and architecture ([rust-cache](https://github.com/Swatinem/rust-cache)).

Decided by the owner on 2026-10-17 in [Fit the pull-request tier, private fuzzing and other hosted jobs in the included minutes left](https://github.com/goodfetch/goodfetch/issues/545): the owner's machine runs the pull-request tier, in a throwaway Linux VM, and private fuzzing runs nightly on merged `main` there. On 2026-10-18 the owner settled the rest:

- the VM tool is Lima; the machine never sleeps while on power; a check that failed because the runner was offline is re-run with `gh run rerun` once it is back; and nothing falls back to GitHub-hosted runners;
- the VM runs an x86-64 userland under Rosetta for Linux, re-pinning a check to Linux arm64 only where Rosetta fails it;
- the build cache is a folder on the machine, written only by a `main` job there and read-only to pull-request VMs;
- the pull-request tier keeps ADR 0061's time budgets, measured on the machine from each job's start;
- ADR 0072's in-diff mutation job runs on the machine;
- runs that ran only on the machine reach the results store through one daily hosted ingest job.

This ADR records those and settles what they and earlier ADRs imply. It builds on ADRs 0032, 0061, 0064, 0067, 0071, 0072, 0076 and 0108.

> Amended on 2026-10-22 (owner decision of 2026-10-22, with agent decisions as built where marked): the local gate is incremental, and a gate verdict may combine a full run on an ancestor head with an incremental run on the pull request's head. Every `just pre-merge all` records each step's result, pass or fail, by step, head, tree and time, with a fingerprint of the host and its tools (the kernel, the system's packages, the runtimes, the test runners, the container engines and the toolchain), in the gate worktree's `target/gate-runs/`, which is never committed and which `just merge` keeps between gates; one gate run at a time holds it. A step's result is recorded once the whole step has ended, and only while the planned head is still checked out on a clean tree; otherwise the run records nothing more and fails. A run on a head that descends from a recorded head plans from the nearest one (`xtask gate plan`). It reuses a step's green result when the change since the head the result ran on reaches neither the step by `xtask affected` nor, by the evidence of what each workspace member read, the members the step tests. By `xtask affected`: `just perf` when that change selects no `perf` job, the visual projects no `visual` job, TLC no `tlc` job, the tests only Linux decides no Pre-merge job, and the MSRV build and Miri no crate. The Quick suite, the Pre-merge suite with its exercise audit, and the stress run are judged per workspace member (a crate, a pnpm or a uv package), plus the tests no member owns, such as `console/screens.spec.ts`, which rerun whenever any member does. `xtask affected` reaches every package of an ecosystem when the change reaches a package that every run of its runner loads (one the root Vitest or Playwright config imports, or a pytest plugin), follows the workspace imports a package's files make whether or not its manifest declares them, and reaches the crate that embeds the Console's build (ADR 0057). The evidence is checked apart from that graph, and a member it reaches reruns with its dependants: Cargo's dep-info and the build scripts' `rerun-if-changed` paths, for every file a crate's last build read, `include_str!` targets among them; Vitest's `--changed` and Playwright's `--only-changed` listings since the head, which follow each test's own module graph; and a string literal in a member's files naming a changed file that no member owns, as a test that reads `TESTING.md` at run time does. Missing or unreadable evidence (no dep-info for one of a crate's test targets, a listing that fails) reruns the member, and a member the listings alone name reruns the visual job too when it owns a visual test. The plan's log names each member the evidence reaches beyond `xtask affected`'s selection. The stress run repeats only the pull request's new and changed tests of the members it reruns, plus every test whose file the change since the earlier run changed. Every run reruns the checks that judge the whole change: sign-offs, commit messages, `just lint` (with its codegen, compat, Feature, Client and Journey checks), advisories, secrets in commits and the notices, and also, as an agent decision, the feature combinations, the fuzz-target check, the proofs, the Journey task lists and the Feature and Client listing checks. A red result is never reused, a step with no result runs, and so does a result older than a day or from another host fingerprint. A change to the gate's own inputs reruns every step in full: the justfile, `ci/`, `.config/` (nextest's settings), `.cargo/`, the root Cargo, pnpm and uv manifests and lockfiles, `rust-toolchain.toml`, and, as an agent decision, `xtask`, which runs most steps and makes the choice itself, and the files tests of several members read at run time: the Proving ground's `pages/` and `fixtures/`, `test-support/fixtures/`, `chromium/` and Collie's browser pins (`crates/goodfetch-collie/src/pins.json`). A moved base (the merge base with `origin/main`) reruns perf and the stress run. The run's log names, for each step, whether it reran and, when reused, the head it ran on and the run that carried it, and the merge commit names the reused run. A working tree with uncommitted changes reuses and records nothing, and `GOODFETCH_GATE_FULL=1` reruns everything. A run with `GOODFETCH_TEST_SELECTION`, `GOODFETCH_TEST_ENGINE` or `GOODFETCH_ORDER_SEED` set fails before any step, and the other variables that change how the steps run (`CI`, `GOODFETCH_*`, `NEXTEST_*`, `CARGO_*`, `RUST*`, `UV_*`, `NODE_*`) join the host fingerprint, so a result counts only for a run in the same environment. Known limits, accepted as agent decisions: a test that reads at run time a file another member owns, through neither an import nor a build input, is seen by none of the evidence; it reruns only through a declared dependency or `runs` edge (today every such read, of `goodfetch-protocol`'s generated bundle, has one), and the shared data such reads use are gate inputs, above. Dep-info is required for each of a crate's test targets by name, and a library's plain build and its test build share that name, so an `include_str!` only the test build has is seen only once a test build ran; the gate's own worktree keeps the previous gate's test builds, and the literal scan sees such a path too. Vitest, Playwright and pytest order their tests by the head's seed (TESTING.md, Before merge), so every run reruns them in the head's order, over every workspace member, reused or not, and with every test those runners have, as a full run does (`just test <suite> --shuffled-all <crates>`, and the stress run within every pnpm and uv member and the unowned tests); nextest runs each test in its own process, so only a crate's result is reused (owner decision of 2026-10-22, F8 option B). A reused crate's result therefore counts only together with that rerun, green in the head's order, and the incremental verdict matches a full run's in test order too; the differences from a full run that remain are the known limits above and the one below. One more difference from a full run on the head remains: a part builds its crates with `-p`, whose dependency features unify over fewer members than `--workspace`, which the always-rerun feature combinations and the rule that a capability is a setting, not a Cargo feature, keep from changing behaviour. A reused perf result was judged against the acceptance its own run read (ADR 0134); while no figure fails (ADR 0134, as amended on 2026-10-22), that changes no verdict, and this note is revisited before figures gate again (agent decision).

> Amended on 2026-10-28 (owner decision of 2026-10-28, adopting option 7 of the test-gate audit; the backstop as first drafted on 2026-10-23 in #1591): the incremental gate has a backstop. `just gate-backstop`, daily from the gate host's cron, runs `just pre-merge all` in full (`GOODFETCH_GATE_FULL=1`) on `main`'s head (during M1, the milestone branch's, where `just merge` lands) in a gate worktree of its own (`.claude/worktrees/gate-backstop`), then compares that run with each incremental run in `just merge`'s records on the same tree, the merge's gated head (`xtask gate compare`). A result that run reused and the full run found red is a selection miss, recorded in `~/gate-backstop/misses.txt` with the run and the head it reused from, and fails the backstop: each one is a defect of the selection to fix. A reused result the full run has no result for, because it stopped at a red step, is reported as unchecked. One line a day goes to `~/gate-backstop/results.txt`. Daily, because a result is reused for a day at most, so a miss is found before the results it rests on expire. In a worktree of its own, at low priority, so it never holds `just merge`'s worktree, at the cost of a second gate build on the disk (about 25 GB): it starts only when its build leaves the 60 GB the server keeps free (85 GB free before its first build, 65 GB after), and a day it skips is listed as skipped and fails; its full record stays in its own worktree, and `just merge` plans only from its own runs. > Amended on 2026-11-09 (owner decision of 2026-11-09, « Oui, avec F4 », on [#2090](https://github.com/goodfetch/goodfetch/issues/2090)'s F4 and [#2233](https://github.com/goodfetch/goodfetch/issues/2233), taken once the backstop's first green run, on a8d28bf3f, lifted #2090's hold on wider reuse): a gate reruns less, and no check weakens. First, a change to a path the gate's own files name reaches only the steps that read it, by a map in `xtask gate plan`. A change to an xtask test file reruns `xtask` in the steps run per member and the Linux step. A `ci/` file only some steps run reaches those steps, and a `ci/` file only the checks that rerun in every run read, or no gate step runs, reaches none. Any path the map does not name still reruns every step, and `xtask/src/` stays a full input, since it decides the plan. A test that reads a changed `ci/` file still reaches its member by evidence, and evidence that reaches `xtask` adds the Linux step instead of widening as a crate's would, since `xtask` has no dependant and no benchmark. A test reads the real `justfile` and scripts and fails when a step's recipe or script names a mapped path the map does not give it. It sees paths written from the repository's root; it does not see a script's relative reference to its sibling, nor a file a step reads from xtask's own code, so the map's entries for what such reads reach rest on reading them by hand. A new file in a folder the map names reaches what that folder's entry says, not every step. Second, a red stress run no longer costs the members it did not fail their clean passes. A crate the run left short of its counts, with no failing test, keeps each selected test's earned passes in `<head>.earned`, beside the record. A member that keeps them reruns, and each of its tests runs what its 20 or 200 still owes; the total is never lowered. They hold by the rule a green result holds by, the same code: the member's inputs identical since the head the earliest pass ran on, the same host fingerprint, the same base when the base bears on the step, and within `MAX_AGE` of the start of the stress run that gave the first one, which is no later than that pass and which a result that counted them keeps as its own age; the selection checks that age again when it reads the file, later than the plan. A failing test takes its member's earned passes. What a quick merge skips runs on the next finished spec's full gate, whose stress run still starts from the head of the last full gate (the note of 2026-11-11 on #2455), and meanwhile in the post-merge test-health run (`TESTING.md`, After merge). The backstop's switch (`ci/gate-backstop.state`) and the merge cap are unchanged.

> Note (as built on 2026-11-14, [#2619](https://github.com/goodfetch/goodfetch/issues/2619), an agent decision the owner did not read; the post-merge run itself is the owner's, approved with the rule above after the same retrospective): the post-merge run, `just counts` and the Pre-merge suite over what `main` gained on quick gates, builds in `just merge`'s worktree, and each gate that held its lock starts it as it ends, unless it was told to stop. Its first design, a cron line every 20 minutes and a build in the backstop's worktree, ran once: that second build took 36 GB, which kept its disk under the run's own floor. After a merge, `main`'s tree is the tree the gate just built, since a head holds its base's tip, so in the gate's worktree the run compiles only what its suites need beyond the gate's build; started by the gate, it has the gate's environment, so Cargo takes the gate's units for its own. What this ADR says of that worktree holds: one run at a time is in it, because the run takes the backstop's lock, marks it and only then reads the gate's, and a gate takes its own before it reads the backstop's, stops a run it finds and waits until that run's lock is gone, which goes once every process of the suites' session has ended; only a gate holds the gate's lock, records in `target/gate-runs/` or sweeps. The plan's evidence of what a member read is then of a build of `main`, an ancestor of every head a later gate tests, as it is after any quick gate's build. The run's results are reused by no gate. It lists a range it could not check in `~/test-health/results.txt`, once for a commit and a reason, and a run that ends on its setup reads `fail` there and leaves its range to the next run.

> Note (owner's decision, 2026-11-11, answering the chief of staff's question f, put as "An edit to ADR 0037's matrix gets the quick gate, not the docs gate (`xtask affected` counts the matrix as an input of `xtask codegen`, which builds `features/inventory.json`)", with "yes" recommended; the owner's answer: « Yes X10, yes a–i »; the wording is the chief of staff's, and the owner did not read this note): a change to ADR 0037's matrix, `docs/adr/0037-v1-scope-matrix.md`, takes the quick gate and not the docs gate, since `xtask codegen` builds `features/inventory.json` from it and `xtask codegen --check` runs in `just lint`, which the quick gate runs and the docs gate does not (`justfile:158`). The rule is decided; [#2476](https://github.com/goodfetch/goodfetch/issues/2476) builds it, by having `xtask affected` count the matrix as an input of `xtask codegen`. `xtask affected` does not do it today (read at `83090c63f`): the matrix is Markdown under `docs/`, so `is_document` takes it for a document (`xtask/src/affected/selection.rs:115-135`), and `literal_readers` counts xtask's string naming such a path only when the string climbs out of xtask through `../` (`xtask/src/affected/readers.rs:72-76`, `names` at `:421-436`), which `MATRIX`'s does not (`xtask/src/features/files.rs:33`, read by `features::row` and through it by `xtask codegen`, `xtask/src/codegen.rs:368-371`). A change of the matrix alone therefore gets `gate=docs` (`Selection::gate`, `xtask/src/affected/selection.rs:618-629`), whose `just lint-documents` runs `xtask register check` and `xtask features check` and no `xtask codegen --check` (`justfile:71-84`).

> Note (as built on 2026-11-13, [#2090](https://github.com/goodfetch/goodfetch/issues/2090)'s F7, under the owner's approval of 2026-11-04 above): four of the checks that every run reran give a result that follows from the tree and the host: `just lint`, the feature combinations, the fuzz-target check and the proofs. A run on the same tree as a recorded green result of one of them now reuses that result, by the rules any reused result keeps: the same host fingerprint, within a day, and never a red one. A run on another tree reruns them, whatever the change. Four things make the reused result the one a run now would give. First, the host fingerprint also covers the tools the steps run that the system's packages do not hold (`just`, typos, zizmor, actionlint, gitleaks, OSV-Scanner, cargo-deny, cargo-shear, cargo-hakari, cargo-hack, cargo-fuzz, cargo-audit and cargo-insta, each by its version), the toolchains rustup holds, each with its components, the Python of the project's environment (`.venv/pyvenv.cfg`), which pyright and mypy judge the tree for and no file of the tree pins, and the two ignore files Git reads outside the tree, the repository's `info/exclude` and the user's, which lint's check of `.gitignore` reads. A step whose tool or pinned toolchain is missing lists itself as skipped and passes outside CI (`ci/tool.sh`, `ci/fuzz-check.sh`), so its green result holds only on a host that still lacks it, and the proofs' Miri fails on a toolchain without its `miri` component. The first gate after this change finds another fingerprint and reruns every step once, as after any change to `xtask/src/`. Second, lint's `uv lock --check` runs offline: a lock that matches the manifests reads no index, but one that does not is resolved again, and that resolution asked the index (measured with uv 0.9.28: no connection for a current lock, 320 for a stale one, none offline, the same exit status each way). Third, lint reads two things besides the tree and the host, and `xtask gate plan` reads both again, only for a green lint it would otherwise reuse, and reruns lint when one no longer reads as a green lint found it, or cannot be read: the day, which the register check compares each Exception's expiry with (ADR 0140), taken from the plan's own time; and GitHub, where the quarantine check reads that each quarantined test's issue is open and labelled `flaky-test` (ADR 0064), read with lint's token. Fourth, with a GitHub token in the run's environment (`GH_TOKEN`, `GITHUB_TOKEN` or `ZIZMOR_GITHUB_TOKEN`), lint's zizmor also runs its online audits, which the plan cannot read again: such a run never reuses lint. The gate host's runs hold no such token. The proofs' zizmor fixture gives the same finding online and offline (run both ways with zizmor 1.30.1). What the fingerprint still does not cover is what it did not cover for the results reused before: a tool's own environment variables outside the names `just _gate-plan` lists, the rest of the user's Cargo and Git configuration, and the packages installed under `node_modules` and the Python environment, which follow their lockfiles. A reused step also leaves out of the gate's closing list the parts it skipped on this host for a missing tool, as a reused perf, Linux or visual step already did: the fingerprint keeps the verdict, since a tool that was missing is still missing, and only the line is lost.

> Note (as built on 2026-11-13, [#2090](https://github.com/goodfetch/goodfetch/issues/2090)'s F5 and F7): two more changes to the gate, neither of which changes what a step checks. First, the host fingerprint leaves out `NEXTEST_TEST_THREADS` and `CARGO_BUILD_JOBS`. The full gate removes both from its environment before its plan and before any step (F1), so no result is recorded under them and no step of a planned run reads them; a plan made by hand in a shell that caps them now has the gate's fingerprint. A test reads `ci/pre-merge.sh` and fails if the fingerprint leaves out a variable the script does not remove. Second, TLC and Miri start beside the host's steps, with perf, the Linux-only tests and the visual tests, instead of after the stress run. Each runs the command it ran, builds and writes in folders no other step reads (`target/tlc/<model>/<config>`, `target/miri/`; the proofs' Miri fixture builds in `target/proofs/`), has no time limit of its own, and gives a verdict that follows from the tree and its pinned tools (the TLA+ tools by SHA-256, Miri's nightly by date), so the load beside it cannot change it. What they share with the host's steps, they read or wait for. Cargo's package cache and the lock on the build folder `xtask` is built in make a step wait, never fail, and every step builds `xtask` with the same command. Miri's recipe reads `ci/miri.toml` through `uv run --frozen` in the project's environment, beside lint's `uv run` steps: `just merge` syncs that environment before the gate (`just fetch`), so neither changes it, and uv locks it. Miri and the proofs' Miri fixture share Miri's sysroot (`~/.cache/miri`): in a full run the proofs start minutes after Miri has built or found it. One case is not settled: were the sysroot removed by hand between two gates on one tree, with lint, the feature combinations and the fuzz-target check reused and both Miri and the proofs rerun, the two could build it at once, and whether cargo-miri guards that is not verified; a step would go red, and no wrong green can come of it. The Kennel's check stays where it was, after the suites: `kennel/scripts/check.sh` builds the scripted engine and Collie into the build folder the suites' test tools are in, with the features of its own build, so beside the suites either could replace an executable under the other's tests. The time this can save is what TLC and Miri took on the host's path, 14 to 39 s and 108 to 198 s in the gates of 2026-11-12 and 2026-11-13, and only in a gate whose host steps end after perf; no gate has measured it yet.

### The pull-request tier on the owner's machine

- **Every job of the pull-request tier runs on the owner's machine,** through ADR 0108's runner: the Quick job, the Pre-merge jobs, "all green", the Chromium build gate's check and the lab job. ADR 0072's in-diff mutation job runs there too; the test V8 build already does (ADR 0067). A step that builds or runs the repository's code runs inside a Linux VM that Lima starts for the job and destroys when the job ends. A job that builds and runs nothing of the repository's, such as the Chromium build gate's placeholder check, needs no VM.
- **The VM is recreated for every job,** from a base image pinned by digest. It holds no secret and has only the job's `contents: read` token. No host folder it can write survives the job, except the job's own workspace, which the runner cleans at start and end; the cache folder below is read-only to it. The pre-job script destroys any VM an earlier job left behind before it admits the next job, since a cancelled job may skip the post-job script.
  > Amended on 2026-10-19 (owner decision of 2026-10-19): a named job may also pass read-only scopes into the VM: `issues: read` for the quarantine-list check ([#315](https://github.com/goodfetch/goodfetch/issues/315)), `pull-requests: read` for the `perf` job and the Release suite's Linux jobs ([#319](https://github.com/goodfetch/goodfetch/issues/319)), and `actions: read` for "all green". Never a write scope and never a secret; each job's `permissions` hold exactly what it needs.
- **The VM runs an x86-64 userland through Rosetta for Linux.** Lima starts a VZ VM, Linux arm64, with Rosetta for Linux on, and the tier's toolchains, tools and images are their Linux x86-64 builds. So the checks pinned to Linux x64 keep their platform: visual tests in the pinned Playwright image (ADR 0073), the count snapshots, `xtask perf` and benchmark admission (ADR 0071), the size estimate (ADR 0057), `cargo fuzz check` (ADR 0067) and the in-diff mutation job (ADR 0072). The tier matches what it becomes on hosted Linux x64 runners once the repository is public.
- **A check that Rosetta fails is re-pinned to Linux arm64 alone, while private.** [#132](https://github.com/goodfetch/goodfetch/issues/132) proves the setup with a quick trial: Callgrind, the pinned Playwright image and `cargo fuzz check` under Rosetta. A check that fails there runs natively on Linux arm64 in the VM, one check at a time, and the ticket that finds it amends the ADR that pins it, with a one-line note.
- **Rosetta may end with macOS 27.** If Rosetta for Linux stops working on the owner's machine before the repository is public, every check falls back to Linux arm64 in the VM as above. That is decided with macOS x64 support in [#546](https://github.com/goodfetch/goodfetch/issues/546), before the machine moves to macOS 28.
- **The build cache is a folder on the owner's machine.** The cache-warming job runs on the machine, in a VM, after each push to `main`, one run at a time, a newer waiting run replacing an older one. It builds the tier's dependencies, tests and benchmark targets without running them, as ADR 0061 has it, and is the only job that mounts the cache folder writable. Pull-request VMs mount it read-only and copy what they need, so no pull request writes what another job reads. GitHub's cache is not used by the tier. Hosted Linux jobs, such as test health and the coverage job, restore the Linux caches that manual-dispatch Release runs on `main` save (ADR 0061).
- **The allowlist admits pull-request jobs only from branches of this repository.** Its pull-request entry is the tier's jobs, on the `pull_request` event; the cache-warming job's entry is a `push` to `refs/heads/main`. The pre-job script reads the event payload and fails a pull-request job before its first step unless the pull request's head repository is this repository. A pull request from a fork never runs a step on the machine (ADR 0076), and the list still admits no other job.
  > Amended on 2026-10-19 (owner decision of 2026-10-19): the list also admits `update-screenshots.yml`, dispatched from a branch other than `main`, and `diagnostic.yml#rerun-owner-machine`, both on `owner-machine`. The repository is private, only the owner pushes branches, and forks are refused.
- **Write access is still the boundary.** A pull request runs its workflow file from its own branch, so its steps outside the VM run whatever the branch asks, as the runner's standard user. Only those with write access can push a branch: the owner, and agents acting for the owner. They can already push to `main`, which has no branch protection while private (ADR 0108). The VM keeps the build and the tests, and anything they leave, from outliving the job.
- **This squares the entry with ADRs 0032 and 0071,** which keep pull-request code off the machine that times the benchmark and the Performance series. The machine runs one job at a time, so no pull-request job runs during a timing. Nothing a pull-request job builds or leaves survives its VM, and timings run on the macOS host, outside any VM.
- **Its time budgets are ADR 0061's, measured on the owner's machine from each job's start.** ADR 0061 measures them on GitHub-hosted runs, and none exist while this holds. Each job's p50 runs from the job's start, and "all green" from the first job's start, so time spent waiting for the machine is not counted. Breaches open issues as ADR 0061 says.
- **The in-diff mutation job keeps ADR 0072's rules but not its minute limits.** It uses no included minutes there, so the four-shard cap and the 550-minute threshold no longer apply to it; its shards keep to the 15-minute job budget.
- **Once the repository is public,** standard hosted minutes are free, and the pull-request tier goes back to GitHub-hosted Linux runners. Its allowlist entries are removed, and the cache-warming job, the in-diff mutation job and the ingest go back to ADR 0061's, ADR 0072's and ADR 0064's rules.

### Private fuzzing on the owner's machine

- **A second runner instance on the machine serves the private fuzzing repository.** A runner is registered on one repository, never on the organization (ADR 0108), and ADR 0067 keeps fuzzing's logs and results in that repository, so the main repository's runner cannot run it. The instance runs as its own standard macOS user, as a launchd service, with the label `owner-machine` and the same pre-job script. Its allowlist copy admits only that repository's nightly `schedule` on its default branch.
- **The machine still runs one job at a time.** The two instances' pre-job scripts share one lock on the machine, so a job on one instance waits until the other instance's job ends. No job overlaps a timing, as ADR 0108's single instance ensured.
- **Fuzzing runs nightly on `main`'s head, in a VM recreated for the job,** running ClusterFuzzLite's x86-64 images through Rosetta for Linux. It builds the fuzz targets, runs `batch` for 3,600 s, then `prune` and `coverage`. Push fuzzing (600 s of `code-change` after every push) and the continuous builds it needs do not run; the next night's `batch` covers each day's pushes.
- **ADR 0067's containment holds.** The job that builds and runs the targets holds no secret and a token with no permissions. A later job stores the results with the fuzzing repository's own token, on the same machine, after the VM is gone. Crashes, corpora, coverage and logs stay in that repository.
- **It stays on the owner's machine after the main repository is public,** since the fuzzing repository stays private. OSS-Fuzz replaces its `batch` run once Goodfetch qualifies (ADR 0067).

### Availability, and how a queued or failed check is noticed

- **A job waits in GitHub's queue while the runner is offline, and fails after 24 hours there.** The machine is set never to sleep while on power ([#1562](https://github.com/goodfetch/goodfetch/issues/1562)), so the runner is offline only when the machine is off or loses its network.
- **A check that failed because the runner was offline is re-run once the runner is back,** with `gh run rerun <run-id> --failed`. Such a job never reached a runner: it has no runner name in `gh run view <run-id> --json jobs`. A job that reached the runner and failed, whether the pre-job script refused it or a test failed, is an ordinary failure and is never re-run (ADR 0064).
  > Amended on 2026-10-19 (owner decision of 2026-10-19): a job with no `Test` steps whose figures are deterministic, `perf` and, where it gates, `size`, may be re-run after the owner's acceptance comment. It is no retry, since nothing flaky is masked; "all green" still refuses a run whose earlier attempt failed a `Test` step.
- **No job falls back to GitHub-hosted runners.**
- **The merging agent reads the checks before every merge** with `gh pr checks <number>`. It never merges while "all green" is pending or failed. When a check is pending and `gh api repos/goodfetch/goodfetch/actions/runners` shows the `owner-machine` runner offline, it tells the owner that the check is waiting for the machine. When a check failed because the runner was offline, it re-runs it once that call shows the runner online.
- **The owner is notified by GitHub's own Actions notifications,** on by default, which report a failed run to the account that triggered it; agents push and dispatch under the owner's account. A queued check shows as pending on its pull request, and the merging agent reports it as above. Nothing else is set up, and nothing costs money.
- **A nightly fuzzing run that failed because the runner was offline is re-run the same way,** or left to the next night's run, which covers the same `main`.

### The hosted jobs that still draw on the included minutes

Every line is counted in ADR 0108's Linux-equivalent minutes, from the job durations the ingest records, as ADRs 0064 and 0108 count theirs.

- **The ingest of each finished run that had a hosted job** stays as ADR 0064 has it, so the ceilings' counts stay current. A workflow whose jobs all run on the owner's machine, the pull-request tier first among them, is left out of its trigger: one hosted ingest job after each pull-request run would cost a minute each time, 183 minutes or more a month on its own.
- **The daily ingest job** copies those workflows' finished runs of the past day into the results store, in one scheduled hosted job with a 2-minute timeout. Flaky tests in pull-request runs are then detected a day later, which nothing gates on.
- **The checks run by hand** are dispatched through their recipes, which read this line's count for the month from the results store before dispatching, locally and with no runner. A dispatch whose estimate would take the line past 90 is refused with the minutes needed and the date the month turns.
- **A line past its budget opens an issue.** The daily test-health job, which already reads the month's counts, opens or updates one `needs-triage` issue per line that has passed its budget, as a budget breach does (ADR 0061). The fix is to shorten its jobs or move work to the owner's machine. Nothing is bought.

### When things change

- **If GitHub announces a date for the self-hosted charge in private repositories,** this design is revisited before that date: the agent that finds the announcement opens a `needs-triage` issue that links this ADR. The pull-request tier would not fit the included minutes even at one third of a Linux minute, and the charge is never paid (ADR 0076).
- **If Rosetta for Linux ends,** the checks it serves move to Linux arm64 in the VM, as above.
- **Once the repository is public,** the pull-request tier leaves the owner's machine, as above. Fuzzing stays.

## Considered Options

- **The pull-request tier and fuzzing on GitHub-hosted runners, with per-run caps and a reduced fuzzing schedule:** rejected. With 183 pull requests a month, the pull-request tier alone passes the 400 minutes left, and nightly fuzzing alone needs about 1,800.
- **Paid minutes, or a payment method with a spending limit:** declined while there is no revenue (ADR 0076).
- **Making the repository public now:** declined by the owner for now (ADR 0108); reopening it is the owner's call alone.
- **The pull-request tier directly on the macOS host:** rejected by the owner's decision of a throwaway Linux VM. Nothing a job left behind would be cleared before the next job or a timing, and the Pre-merge suite's platform is Linux.
- **A fallback to GitHub-hosted runners while the machine is offline:** declined by the owner on 2026-10-18. A day of queued checks would spend the month's minutes, and a re-run once the runner is back costs nothing.
- **Native Linux arm64 in the VM, with the Linux x64 checks re-pinned to arm64 while private:** not chosen by the owner on 2026-10-18, except check by check where Rosetta fails. Reference screenshots and counted figures recorded on arm64 would be recorded again on x64 once the tier is hosted, and ClusterFuzzLite's arm64 support was not confirmed.
- **The Linux x64 checks on hosted Linux x64 runners:** rejected. Run on every pull request, they would not fit the 400 minutes.
- **The cache-warming job on GitHub-hosted runners, restored on the host and handed to the VM:** not chosen by the owner on 2026-10-18. It would cost included minutes, a download per job and room in GitHub's 10 GB, where a folder on the machine costs none.
- **No build cache:** rejected. Every job would build its dependencies from scratch, against the 20-minute "all green" budget.
- **Suspending the tier's time budgets, or new budgets for the owner's machine:** not chosen by the owner on 2026-10-18. ADR 0061's budgets keep guarding test speed; measuring from each job's start keeps the machine's queue out of them.
- **The in-diff mutation job kept hosted under ADR 0064's ceiling:** not chosen by the owner on 2026-10-18. It would stop after about nine runs a month.
- **Ingesting the owner's-machine runs in the daily test-health job, or on the owner's machine:** not chosen by the owner on 2026-10-18. The first takes room ADR 0064's ceiling does not have; the second would put the results store's token on the runner, which holds no secret (ADR 0108).
- **Fuzzing in the main repository's workflows, on its runner instance:** rejected. Their logs would become public with the repository, which ADR 0067's containment forbids.
- **One runner registered on the organization, serving both repositories:** rejected. ADR 0108 registers the runner on the repository only, so that no other repository of the organization reaches the machine.
