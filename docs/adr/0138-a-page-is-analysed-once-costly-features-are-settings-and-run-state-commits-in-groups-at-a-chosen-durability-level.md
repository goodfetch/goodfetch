# A page is analysed once, a costly feature is a setting that removes its work, and run state commits in groups at a Durability level the crawl chooses

Every page a crawl fetches is parsed once, in one **Page analysis**, whose readers run in a fixed order on one tree and leave one immutable result that every later module reads. A reader runs only when the request or the Run's settings demand it. Work that depends only on a Run's inputs is built when the Run starts. Every costly per-page feature is a setting, and switching it off removes its work as well as its effect. Run state commits each attempt in two transactions, which the single writer groups across pages under one sync, at one of four **Durability levels** (`full`, the default, `fast`, `periodic` and `off`). Structural counts become ceilings that fail a change. This is the spec of the optimization pass ([#1577](https://github.com/goodfetch/goodfetch/issues/1577)), decided with the owner in a grilling session on 2026-10-31.

> Amended by [ADR 0142](0142-a-runs-state-lives-in-memory-its-run-file-is-written-in-batches-and-a-clean-stop-writes-everything.md): memory holds a Run's state and the run file is written in Run-state batches. Each Durability level becomes a preset of the batch settings: `full`, `fast` and `periodic` keep their meaning, `off` writes the same batches as `batch`, never synced, and `batch` is the new default.

On 2026-10-30 the owner found Foxhound's comparison with Spider unacceptable. They decided that every comparison runs each tool with the same features and the same settings, in a five-scenario matrix against Spider, Crawlee and Scrapy, with every metric (the comments on #1577). The profile of the code-free 1,000-page crawl at 16 requests at once (tip `0fd15a3a7`, summarized on #1577 on 2026-10-31, its key figures checked against the raw outputs and the code) shows that the gap is structural. Each layer redoes the work another layer already did:

| Setting | Foxhound | Spider 2.53.9 |
|---|---|---|
| Default (`run_state.durability: full`, robots.txt obeyed) | 11.6 s | 0.09 s |
| Like for like (`fast`, robots.txt not obeyed) | 3.0–3.5 s | 0.09 s |

Foxhound runs 32 times Spider's instructions and makes 329 system calls per page against 12. The measured causes, in order:

1. **The cosmetic clean-up runs on every page, even with `formats: {}`.** It compiles about 614 CSS selectors per page, twice: 48.9 % of instructions, and `Matcher::new` alone is 33 %. `measured_formats` calls `clean_up.remove` before it reads the request.
2. **About 8 run-state commits per page, about 1.1 writes each,** each awaited before the page goes on. In `full` that is 7.5 fsyncs per page and 71 % of the wall time. In `fast` the single writer is the serial resource, and only about 1.7 of 16 cores are used. `RunState::read` goes through `write`.
3. **Write amplification:** 142 KB of WAL, 34 KB of savepoint journal spilled to `$TMPDIR` and 8 KB of checkpoints per page, for 462 bytes served. The `run` row's `journal_position`, rewritten on every commit, is 22.8 % of WAL frames.
4. **SQL is prepared again on every call:** 135 times per page, 14.9 %.
5. **Datasets parse their JSON again and build a JSON Schema validator for every page,** inside the writer: about 6 %.
6. **Readability runs for the Page signature** on the untouched document, while formats run it on the cleaned one: 8.6 %.
7. **8 HTML parses per page.** Modules pass HTML as strings: the clean-up serializes its result and the next step parses it again.
8. **RSS is mostly allocator retention:** a live heap of 14.7 MB against an RSS of about 208 MiB, of which 110 MiB is pages mimalloc keeps and 57–67 MiB is the executable's own pages. The workspace builds mimalloc v3, whose purge delay is 1,000 ms (10 ms in v2).

ADR 0002 already promised "many operations grouped per commit by the single writer". The code does not keep that promise, because each page awaits its writes one after another.

The owner asked for « évidemment les meilleures pratiques », taking inspiration from the best crawl frameworks to arrange the architecture. They also asked that the features that slow a crawl, such as persistence after a crash, Politeness and reading robots.txt, « doivent être sous flag (l'user doit pouvoir ne pas les utiliser pour maximum performances) », and that Foxhound offer checkpoint or batch protection against crashes, as competitors do.

How proven crawlers shape this work. Each was checked against its primary source on 2026-10-31.

- **One parse, shared by every reader.**
  - Nutch's `HtmlParser` builds one `DocumentFragment` and hands it to every `HtmlParseFilter` ([HtmlParser](https://github.com/apache/nutch/blob/master/src/plugin/parse-html/src/java/org/apache/nutch/parse/html/HtmlParser.java), [HtmlParseFilter](https://github.com/apache/nutch/blob/master/src/java/org/apache/nutch/parse/HtmlParseFilter.java)).
  - StormCrawler's `JSoupParserBolt` parses once ([2.x](https://github.com/DigitalPebble/storm-crawler/blob/2.10/core/src/main/java/com/digitalpebble/stormcrawler/bolt/JSoupParserBolt.java)).
  - Scrapy caches `response.selector` in `_cached_selector` ([text.py](https://github.com/scrapy/scrapy/blob/master/scrapy/http/response/text.py)).
  - Heritrix passes one `CrawlURI` through its processor chains, but finds links with regular expressions and builds no tree ([ExtractorHTML](https://github.com/internetarchive/heritrix3/blob/master/modules/src/main/java/org/archive/modules/extractor/ExtractorHTML.java)).
  - Crawlee 3.18.2 parses each body twice, once with htmlparser2 and once with `cheerio.load`; only its development branch parses once ([3.18.2](https://github.com/apify/crawlee/blob/96ed398b26954f0e7818cc862f33ff4bb706c84b/packages/cheerio-crawler/src/internals/cheerio-crawler.ts)).
  - Spider reads each body in one streaming lol_html pass with precompiled selectors.
- **The shape of the pipeline.**
  - Heritrix's `ToeThread`, Scrapy, Crawlee and Spider carry a page from start to end in one worker or task.
  - StormCrawler splits the work into Storm bolts that can run on different machines. It serves continuous low-latency crawling, such as Common Crawl's [CC-NEWS](https://commoncrawl.org/news-crawl). Its fetcher's internal queues are unbounded by default (`fetcher.max.queue.size: -1`, [crawler-default.yaml](https://github.com/apache/stormcrawler/blob/main/core/src/main/resources/crawler-default.yaml)).
- **Durability.** No surveyed crawler syncs run state.
  - Scrapy's `JOBDIR` pickles each request when it is queued, writes its queue index and `spider.state` only on a clean close, never syncs, and its documentation warns that an unclean shutdown can corrupt it ([jobs](https://docs.scrapy.org/en/latest/topics/jobs.html), [scheduler.py](https://github.com/scrapy/scrapy/blob/master/scrapy/core/scheduler.py)).
  - Crawlee persists its state every 60 s with a plain `writeFile` and purges its storage on start by default ([Configuration](https://crawlee.dev/js/api/core/class/Configuration)).
  - Heritrix's checkpoints are off by default, and its BDB JE databases are non-transactional and deferred-write ([CheckpointService](https://github.com/internetarchive/heritrix3/blob/master/engine/src/main/java/org/archive/crawler/framework/CheckpointService.java), [BdbModule](https://github.com/internetarchive/heritrix3/blob/master/commons/src/main/java/org/archive/bdb/BdbModule.java)).
  - Databases group syncs instead: in LevelDB's writer queue and RocksDB's write group, the writer at the head of the queue writes everything queued behind it ([db_impl.cc](https://github.com/google/leveldb/blob/main/db/db_impl.cc), [Pipelined Write](https://github.com/facebook/rocksdb/wiki/Pipelined-Write)), and PostgreSQL's leading backend flushes for its group.
- **SQLite and the parsers.**
  - With `temp_store=MEMORY`, statement journals, the ones savepoints use, never touch the disk ([tempfiles](https://www.sqlite.org/tempfiles.html), [global.c](https://github.com/sqlite/sqlite/blob/master/src/global.c)). Automatic checkpoints are `PASSIVE` ([pragma](https://www.sqlite.org/pragma.html#pragma_wal_autocheckpoint)).
  - rusqlite's `prepare_cached` keeps an LRU cache of 16 statements by default ([docs](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html)).
  - A `dom_query` `Document` is never `Sync`, and its `atomic` feature makes it `Send` ([docs](https://docs.rs/dom_query/latest/dom_query/struct.Document.html)): one tree has one owner at a time.

## Decision

### The Page analysis

- **A fetched page is parsed once, in one Page analysis.** The body, read once into `Bytes` (ADR 0134), is parsed on the CPU pool (below). Every module that reads a page is a reader of the Page analysis, and the readers run in this order on the one tree:
  1. the readers that see the page untouched, as ADR 0007 requires: links, `rel=canonical`, `meta refresh`, `<base href>`, the program's own selectors and XPath, and `html.raw`;
  2. the cosmetic clean-up, which removes its elements **in place on the same tree**, never on a copy or a re-serialized string;
  3. the readers of the cleaned page: the main content, the Page signature and the formats.

  > Note (agent decision, as built), 2026-11-01, from reading the code at `85083c57b` for [#1577](https://github.com/goodfetch/goodfetch/issues/1577): the tree passes four states, and one step consumes it. It starts untouched, the clean-up removes in place, then composing the shadow roots rewrites it (only when the page holds one), and dom-smoothie takes the `Document` by value and leaves only its article. So the readers of the whole cleaned page (`html.cleaned`, tables, metadata, contacts, images, media, full Markdown) read before the main content, and the tree is copied (`Document::clone`, no parse) only when the demand plan has a reader after a step that consumes it: the main content's fallback that removes landmarks, or `fit`. At most 1 copy per page, a new register row `F1.tree_copies`. A format's string (`html.raw`, `html.cleaned`, `html.main`) is serialized once, only when asked. Markdown reads the tree too: htmd's only entry that does not parse takes an rcdom tree, so the main content's tree is walked into one with no parse, and `scraper`'s readers move to `dom_query`. F1's crate (ADR 0140, open question 1) is `goodfetch-extractor`, which Collie and Foxhound both use and which stays pure: its caller runs it on the CPU pool, and Foxhound passes its own readers of the untouched page in, built once per Run.
- **Its result is immutable and shared.** The Page analysis returns one `Send + Sync` value shared by `Arc`: links, canonical, title, main content's text, Page signature, formats and fields. The Frontier, Datasets, learning and the writer read only that value. The tree ends with the Page analysis, unless a handler on a document tier needs it; no module receives a page's HTML as a string to parse.

  > Amended on 2026-11-01 ([the sweep of ADR 0140](https://github.com/goodfetch/goodfetch/blob/claude/festive-curie-bc4545/rnd/research/2026-11-01-shared-paths-ticket-sweep/proposal.md), D3, decided by the orchestrator under the owner's « fait tout ce que tu peux faire seul », open to their review; #767, #1097, #1473, #1474): **a document tier keeps the tree for its handler's life.** A handler's calls (`content`, `formats`, Locator reads, questions and waits) arrive after the analysis, one task per call, with selectors nobody knew in advance, so they read the attempt's kept tree, with its one owner on the CPU pool, and count in F1: no parse per call, selectors from the engine's cache. The kept tree stays untouched, since a program's selectors see the page untouched (ADR 0007); the clean-up and the main content run once, on a copy, and their result is kept for the attempt. Only a Label that declares a handler keeps one, and `dom_query`'s `atomic` feature, off today, makes it `Send`.

- **Extractors read the tree.** ([the sweep of ADR 0140](https://github.com/goodfetch/goodfetch/blob/claude/festive-curie-bc4545/rnd/research/2026-11-01-shared-paths-ticket-sweep/proposal.md), D4, same authority; #788, #814.) Neither built-in Extractor costs a second parse: dom-smoothie through `Readability::with_document`, rs-trafilatura through a document entry patched into its vendored fork (#1634, which also moves it to this workspace's `dom_query`). An Extractor Plugin crosses a process boundary, so it gets a counted allowance, only when chosen: 1 serialization and 1 parse of its answer (`F1.plugin_serializations`, `F1.plugin_answer_parses`).
- **The browser tier takes the same path,** from the DOM's serialization.

  > Note (agent decision, as built), 2026-11-01: on the browser tier and in Collie, this covers formats, each read from a new `GetOuterHTML` because the DOM moves, so the unit there is one serialization read, and each counts one parse. Links, fields and Block markers stay read in the live page, as a person sees it, and the browser tier learns nothing, as today (`browser_run` never calls the Page signature).

### Work runs only when something asks for it

- **A demand plan, computed before the Page analysis.** A pure function of the request (formats, fields, Datasets) and the Run's settings (`follow`, `frontier.learning`, the tier) gives the set of readers to run. Each reader declares what it produces and needs. A result several readers share, such as the main content, is computed once. A table test holds, for each combination, that no reader outside the plan runs. For example, `formats: {}` with learning off runs neither the clean-up nor readability.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-05, [#1909](https://github.com/goodfetch/goodfetch/issues/1909): the demand plan is `goodfetch-extractor`'s `Plan::of(&Demand)`, over the formats and `frontier.learning` for now; the fields, Datasets, `follow` and the tier join it with the tickets that move their readers onto the Page analysis. `page.formats` runs the clean-up, and writes its Provenance line, only for a format read from the cleaned page. `frontier.learning: false` is recorded in the Audit log as its own kind, `learning_switched_off`, with its value and default, rather than as `security_switch_turned_off`, since learning is no security control; the report lists it in `weakened` and adds the warning `learning_off`. The navigation gate says whether it reads a document's body (`reads_document_body`), and the page takes none from the browser for a gate that does not, as Foxhound's while the Run does not honour AI-use signals (the audit #1884's C5-4).

  > Note (agent decision, as built), 2026-11-05, [#1910](https://github.com/goodfetch/goodfetch/issues/1910): the readers of the untouched page are Foxhound's `goodfetch-fetch-tier` module `untouched`, since they read the Frontier's trap-link markup and the Page check, which `goodfetch-extractor` must not depend on. `UntouchedReaders` is built once per Run for each Label (its Page check, else the Run's) from an `UntouchedDemand`: a code-free crawl's links and fields, the Page check and `frontier.learning`, every selector compiled then. A crawl request's own document is decoded and parsed once, on the CPU pool, and read there in this order: its refresh directive, `<base>`, AI-use signals, links, fields, Page check with its robots `meta`, `rel=canonical`, then the Page signature, whose main-content step consumes the tree (`goodfetch_extractor::page_signature_of`); the result stays with the served page, and `links`, `field_elements`, `judge` and `signature` answer from it. A redirect chain's HTML hop is read on its own tree: a refresh directive it follows ends the read there, so only the document the chain ends on is read whole. The refresh directive is read from the decoded document, as the browser reads it, rather than from the body read as UTF-8; a body whose type sniffs as no document is still read whole for it. The Page signature is read with the document, before the Page check and a sample's discard, since the tree cannot wait for them (`dom_query`'s tree is not `Send` until #1918's `atomic`). A selector the Run did not ask for (a handler's `crawl_request.links`, a handler's own navigation) still parses its page for its call, under X1, until #1918 keeps the tree.

- **No tree when none is needed.** When no reader in the plan needs a tree (no format, no field, learning off), the Page analysis reads links, canonical, refresh and `<base>` in one streaming lol_html pass with precompiled selectors, as ADR 0007 already adopted lol-html for and as Spider does.

  > Note (agent decision, as built), 2026-11-01: the streaming path reads the same links as the tree does, trap-link judgement included, which needs each link's ancestors and the page's `aria-controls`: the pass keeps a stack of open elements and judges at its end. A reader it cannot serve puts the page on the tree, by the demand plan, never with a weaker answer. A test holds that both paths give the same links on the corpus. lol_html parses its selectors once (`Cow::Borrowed`), and builds its program per rewriter inside the library, which the instructions figure measures. A tree reader uses a kept `Matcher`, never `select("…")`, which compiles on each call.

  > Note (agent decision, as built), 2026-11-05, [#1911](https://github.com/goodfetch/goodfetch/issues/1911): the streaming pass is `goodfetch-extractor`'s `Streaming` with `StreamSelector`s parsed once per Run on `F1.selector_compilations`, and Foxhound's `UntouchedReaders` uses it when the Run's readers need no tree: no Page signature (`frontier.learning: false`, so `rel=canonical`, which only learning reads, stays on the tree), CSS fields, and every selector one lol-html reads. It serves `<base>`, the refresh directive, links with their trap-link judgement (each link's ancestors from the pass's own stack, `aria-controls` judged at the pass's end), the fields' first elements, the Page check's CSS and the robots `meta`. A document is put on the tree when its markup names an AI-use signal, or when the pass cannot vouch that HTML's tree construction builds what its stack holds: no `<!doctype html>`, an implied `<html>`, `<head>` or `<body>`, an end tag that closes no element or more than one, a start tag that closes or moves an element (an open `<p>`, `<li>`, `<dd>`, heading or `<a>`, a table's implied section or foster-parented content), `<noscript>` (the tree parses it as markup, lol-html as text), `<template>`, `<select>`, HTML or a match inside SVG or MathML, a NUL, or an undecoded value a selector compares. The corpus tests (`stream::tests`, `untouched::tests`) hold that both paths read the same. Formats still parse their own tree (#1914 joins them, and then turns the stream off when a format is asked).
- **The Page signature reads the cleaned page's main content,** the same main content the formats read: one readability run per page, and a signature that a consent prompt or a paywall overlay cannot make the same on every page of a site. This amends ADR 0005's note of #851.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-01: it is the main content of the Run's chosen Extractor with its fallback, as formats read it; today it hard-codes dom-smoothie with no fallback. **ADR 0047's share** measures the main content before the rules, a second readability run on every page they touch, so by default the share becomes an estimate with no second run: the text removed over that text plus the main content left. It is an upper bound of the true share, so it can flag more and never misses one. `extraction.removal_share: exact` restores the measure at the cost of 1 copy and 1 readability run, a counted allowance when chosen.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-05, [#1913](https://github.com/goodfetch/goodfetch/issues/1913): as built. **The interface:** `Extractor::main_content` takes the page's tree, which it consumes, and answers the main content's HTML and text (`Found`); dom-smoothie reads it through `Readability::with_document`, so it parses nothing of its own, and rs-trafilatura reads the tree's serialization until its fork's document entry (#1916). **The step's fallback** reads the text outside the landmarks on the tree before the step, removing nothing, so the Page signature copies nothing; the formats copy the tree once (`F1.tree_copies`, counted by `CountedWork::copy_tree`) for the fallback's HTML, which removes the landmarks, and read the clean-up's own tree when composing the shadow roots left the cleaned page as it was, so a read of the main content after the rules parses the page once. **The Page signature** reads the main content of the Run's chosen Extractor (the Label's `content.extractor`, else the Run's), with that fallback: a page the step finds nothing in is signed by its text outside its landmarks, no longer by its title alone. **The share:** `extraction.removal_share`, `estimate` (the default) or `exact`, read from the Run's resolved settings; the estimate is written as the share of a main content "before" of the text left plus the text removed, so Provenance's `main_content.before` is that sum, and each `formats` entry names its measure in `share_measure`. `exact` parses the page as served once more, as before, and counts its step on `F1.share_readability_runs`, not `F1.readability_runs`; a copy of the untouched tree would need the composed tree the browser tier's ticket (#1917) builds.
  >
  > Note (agent decision, as built), 2026-11-05, [#1916](https://github.com/goodfetch/goodfetch/issues/1916): as built. The fork is carried in the repository, `vendor/rs-trafilatura` at `0.2.2+goodfetch.1`, through the workspace's `[patch.crates-io]`, as `vendor/wreq` is (ADR 0042's note of #680); its document entry, `extract_document_with_options`, takes the caller's `dom_query::Document` and runs what `extract_with_options` runs after its parse, and its backup of the document before cleaning copies the tree instead of parsing its serialization again. Moving it to this workspace's `dom_query` 0.28 meant carrying the two crates it hands that tree to, `html-cleaning` 0.3.0 and `quick_html2md` 0.2.1, beside it for their `dom_query` requirement alone, so `dom_query` 0.24 and the html5ever 0.36, selectors 0.33 and tendril 0.4 it brought leave the build. ### Run invariants are built once

- **Nothing that depends only on a Run's inputs is computed per page:**
  - Compiled selectors live in a bounded cache of the engine, keyed by the selector's text and the Clean-up rules' digest (a Run holds to one version, ADR 0047).

    > Note (agent decision of #1912, as built), 2026-11-05: the cache rides on `CountedWork`, the value the engine already hands every owner, so no owner's interface grows a second dependency and a test's engine keeps a cache of its own. It is moka's concurrent cache, which `hickory-resolver` already links with the same feature, so a lookup takes no lock around a page's others. It keeps 16,384 selectors (B1's default Filter lists compile 613 a Run), and 1,024 regular expressions and 1,024 globs; one over a bound evicts, by moka's `TinyLFU`, rather than grows. A selector of the Clean-up rules is keyed by the rules' digest, every other selector by its text alone. A selector the engine's own code matches on every page (the main-content step's, a handler's markup waits') is compiled into the cache as the crawl starts, with the untouched page's readers, so no page compiles it; a selector only a handler names compiles at its first use and is read from the cache after.

    > Note (agent decision of #1784, as built), 2026-11-05: loaded Filter lists are held at the engine's scope too, keyed by their version's digest: besides the versions live Runs hold, the engine keeps the two it used last (`KEPT_VERSIONS`, `goodfetch-page/src/clean_up_versions.rs`), so the next Run on one of them compiles nothing; two covers a switch of version and the embedded part a fallback holds beside a fetched one. Measured in release on this server: one load of the embedded lists takes 34 to 64 ms and adds 12 MiB of resident memory, so the bound keeps at most about 24 MiB once no Run holds them. A page's cosmetic resources (`PageRules::of`, adblock's `url_cosmetic_resources`) are read once a page by the clean-up, and only when a format reads the cleaned page (#1909): 0 a page on B1, which asks no format, and 22 to 96 µs a page in release when a format does (about 22 ms over the 1,000-page crawl), so the read is accepted; the soak profile's 2.5 ms (#1765's review) is not what an optimized build pays, and this probe's figure is the one recorded. Live hiding's reads per refresh are X34's C4-4. The delivery loop reads the Run's settings once, as the Run opens (crawl policy, Session pool bounds, whether it is proxied, the longest wait): no lease, admission or settlement reads them again; `lease_to_servers` still runs once a loop turn, where it batches every admission the governor gives, and F2.transactions stays at its register figure.

  - A crawl's Dataset declarations are parsed, and their validators compiled, when the crawl starts.
  - Settings, the Operator policy and user configuration are resolved once per Run.
  - Provenance's file and the Run index are opened once per Run.
  - Every SQLite connection keeps its prepared statements: `prepare_cached`, with a capacity that holds every statement the connection runs.

    > Note (agent decision, as built), 2026-11-01: this turns on rusqlite's `cache` feature in the workspace and lifts `hashlink`'s ban in `ci/deny/collie.toml`, since Collie's engine runs the same connections. A setting cannot do it: a statement cache is not a capability.

### Every costly per-page feature is a setting

- **Each per-page step is either needed for the result or a feature.**
  - **Needed:** fetching, decoding, reading links when the crawl follows them, the exact duplicate check and the attempt's outcome.
  - **Features:** durability, robots.txt, Politeness, learning and the Page signature, the clean-up, formats, Provenance and Datasets.
- **Each feature is one setting per value** (ADR 0086's rule), and switching it off is recorded in the Audit log and marked on the results it touches, as ADR 0023 already decides for every costly control (and ADR 0028 for a weakened guarantee). When a feature is off, the demand plan schedules none of its readers, admission does not consult it, and nothing of it is written.
- **The spec's deliverables:**
  - the inventory of every per-page step, with its class, the setting that switches it off and its measured cost;
  - the documented **maximum-throughput** combination, which is scenario 1 of the comparison matrix.

    > Note (agent decision, on a guarantee, not read by the owner but for what lowers the Verdict, decided by the owner on 2026-11-10 (grilling of G-06, Q3; the note under ADR 0029:13)), 2026-11-05, [#1921](https://github.com/goodfetch/goodfetch/issues/1921): the inventory and the combination are in `docs/throughput.md`. The three features that had no off state get one setting each, on by default and `weakens` when false: `provenance.log` (the Run trace's Provenance log; each Record keeps its own Provenance), `dataset.records` (no Record is validated, encoded or committed, a code-free crawl reads no format or field for one, and a Record named for an undeclared Dataset is still refused) and `fetch.block_classification` (no document is read by the Block classification rules). Each is Foxhound's, so a Collie run logs its Provenance as before. A Run that switches one off is recorded in the Audit log as one shared kind, `feature_switched_off`, with the key, its value and its default, rather than one kind per feature; its report carries `provenance_off`, `records_off` or `block_classification_off`, and each succeeded request's outcome says `records_off` as its `nothing_committed`. The Block classification's work is counted by a new row, `F1.block_classifications`, at most 1 per page. Scenario 1's Foxhound cell runs the combination; the durable and extraction cells keep `dataset.records` on, since their figures read the Records.
- **`frontier.learning`,** true by default, is new. False switches off learned rules, the Page signature and readability; the fixed rules and the exact duplicate check stay. The run report says no rule was learned.
- **Politeness and robots.txt switched off cost nothing.**
  - With `site_preferences.respect_robots_txt: false`, robots.txt is never fetched, read or stored.

    > Amended on 2026-11-01 ([the sweep of ADR 0140](https://github.com/goodfetch/goodfetch/blob/claude/festive-curie-bc4545/rnd/research/2026-11-01-shared-paths-ticket-sweep/proposal.md), D8, same authority as D3; #684, #1649): the Provenance mark `robots_txt: "ignored"` needs robots.txt read, so it becomes its own setting, `site_preferences.mark_robots_txt_ignored`, false by default. With it on, each origin's one copy is read and each page costs one match. The Audit log and the run report still record `respect_robots_txt: false`. `follow: sitemap` reads robots.txt for its `Sitemap` lines because the crawl asked for that, and matches no rule in it.
  - With a delay of 0 and no per-domain limit, admission does not consult the Politeness store.

Its per-domain queues back its domains off themselves by the same rule over state they keep in memory: the backoff under `politeness.backoff.*`, a `Retry-After` (the crawl refuses one further away than the Run waits, as before), and a 429's halving of the count in flight.
  - The backoff on 429, 503 and `Retry-After` stays a separate feature with its own setting.
  - An Operator policy can still lock any of these values (ADR 0086).

### Durability levels

- **`run_state.durability` takes four values.** Each is a Durability level:

| Level | When run state commits | After a process crash | After a power cut | SQLite |
|---|---|---|---|---|
| `full` (default) | each attempt's outcome, grouped across pages, synced before anything is told outside | only attempts in flight are lost | only attempts in flight are lost | WAL; the claim commits without a sync of its own, the outcome with one |
| `fast` | as `full`, without a sync | only attempts in flight are lost | recent commits may roll back, without corruption | WAL, `synchronous=NORMAL` |
| `periodic` | as `fast`, with one synced commit every `run_state.commit_interval` (5 s by default) | only attempts in flight are lost | the Run resumes at the last synced commit and redoes at most one interval, without corruption | WAL, `synchronous=NORMAL`, `FULL` for the interval's group |
| `off` | grouped, never synced | the Run starts again from nothing | as after a process crash | WAL, `synchronous=OFF`, checkpoints never synced either |

> Note (agent decision, on a guarantee, not read by the owner), 2026-11-01: `periodic` was first decided as one long open transaction, which reading `run_state` rules out. It acknowledges a write before its commit, which the writer's contract, its model test and ADR 0122 forbid; a read-only connection misses acknowledged writes, so the idle check could spin; a stale writer's transaction blocks a takeover's `BEGIN IMMEDIATE` past SQLite's busy timeout; and a failed commit would roll back an interval of acknowledged work. A commit that syncs covers every frame before it, so one synced commit every interval gives the same bound with none of these, and a process crash loses less. It writes more WAL than one long transaction; scenario 2 measures it.

- **Two transactions per attempt.** The **claim**, before the fetch, admits the request and takes its Lease. The **outcome**, after it, commits learning, enqueued links, the Lease's commit, the settlement, the charge and the Records in one atomic transaction, as ADR 0103 already wants of a Record ("staged with the attempt and commits once with it"). No page is ever half written.

  > Note (agent decision, as built), 2026-11-01: a transaction here is one job on the writer, whatever group it commits in. The claim is one job that takes the charge's journal, the Lease and the Session draw, whose Label comes from the Lease, from the delivery loop that holds the pool. Three things stay jobs of their own, which their outcome divides by (ADR 0140): a followed redirect's check-and-set, whose answer can skip the page; a handler's `learn`, which must commit before the handler runs (ADR 0005); and a program's enqueue, whose IDs go back to it. A code-free attempt absorbs `learn` in its outcome, in a nested savepoint that keeps today's tolerance of its failure, and an attempt that fails still commits what it learned. A new link is keyed at admission, so `set_keys` leaves. A domain's hold or backoff journal joins the next group.
  > Note (2026-11-10): since [ADR 0142](0142-a-runs-state-lives-in-memory-its-run-file-is-written-in-batches-and-a-clean-stop-writes-everything.md), a handler's `learn` no longer commits before the handler runs: learning's evidence is written behind, and a rule is learned at most one batch later (the owner's decision of 2026-11-10 on [#2169](https://github.com/goodfetch/goodfetch/issues/2169)).
- **The single writer groups transactions across pages, without a timer.** While one sync runs, the writer takes everything queued and commits it in one transaction with one sync, as LevelDB's writer queue does. Each page keeps its own savepoint, so one page's failing write rolls back alone.
- **What `full` guarantees.** Everything the engine tells the outside has been synced before it is told: a readable Record, an outcome, `run.finish`'s answer and a Checkpoint. A claim lost to a power cut costs one more fetch, never an acknowledgement. In SQLite's WAL, the outcome's sync covers every frame written before it, so a claim committed without its own sync becomes durable with the next outcome.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-01: what is told is what ADR 0002 acknowledges. `run.progress`'s in-flight counts, a handler's request, its enqueue answers and a Provenance line go out earlier, as today, and promise nothing. **A claim's lost charge:** a power cut can lose the journal of a charge for a fetch that happened, and the ledger's reclaim would then under-charge. So after an unclean end, the reclaim counts the journal plus the requests that were in flight at `full`, and the whole Slice at any lower level: it can over-charge a Limit, never under-charge one, and the run report says so.
- **What holds at every level:**
  - An Effect's journal entry commits before the Effect at every level, synced except at `off` (ADRs 0003 and 0010). An Effect never happens twice after a resume.
  - A clean stop (`run.pause`, an abort, a migration) writes a consistent Checkpoint. A paused Run resumes even at `off`.
  - Run state stays in a file at `off`, so ADR 0134's 8 heap bytes per URL in the Frontier still hold.
  - An `off` run file carries an "unclean" mark. Opened after a crash, it is discarded and the Run starts again.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-05, [#1927](https://github.com/goodfetch/goodfetch/issues/1927): `periodic` keeps `full`'s two writer connections: a group commits on the `NORMAL` one until `run_state.commit_interval` (5 s, a Duration setting) has passed since the last synced commit, read on the Clock at each group, then on the `FULL` one, which covers every frame before it; a timer task of the writer's owner sends a tick every interval, and a tick that finds a commit unsynced syncs an empty group, so an idle writer loses at most one interval too. The writer's last write syncs. Charges deferred below `full` declare nothing, as the reclaim charges those Slices whole. At `off` the mark is a one-row table, `unclean`, set in the schema's commit at `synchronous=FULL` before the writer's connection turns `OFF`, and cleared by the writer's last write (the end record a pause, an abort or a finish writes), which syncs. **Checkpoints at `off` sync, unlike the table above:** an unsynced checkpoint lets the next commit write over WAL frames whose pages are not on disk yet, so even a clean stop could leave a damaged file without its mark; synced, they cost one sync of the WAL and one of the file per 16 MB of WAL. A Checkpoint never holds the mark, since it holds one commit's whole state. The engine reads the mark when a Run it does not run is started or resumed, and also counts a damaged run file as unclean when the Run's level is `off`: under the Run's writer lock, so another engine's live Run is refused as held, it overwrites the data key when the file still opens, as a discard does, erases the run file (from the install database in that layout) and every other entry of the run folder but its lock. A resume then finds no Run; a start starts it again from nothing. The per-install layout keeps `off`: each write of a run file is one transaction of the install database, so a damaged run file never damages it. `Durability::named` answers no level for a value that names none. No Effect journal exists yet (#1550): its write keeps `RunState::write`'s default, which syncs at `full` only, so #1550 adds the sync `fast` and `periodic` need.
- **The default stays `full`** (ADRs 0002 and 0077's G5). The pass measures `full` against `fast` after grouping; if the gap stays large, the write-up says so, and the owner reopens the default at the owner test.
- **`fast`, `periodic` and `off` weaken a guarantee.** The run report's `weakened` and `config explain` label them (ADR 0028), as `fast` is labelled today.

### Run-file settings

- **`temp_store=MEMORY`.** Savepoint journals never spill to `$TMPDIR`.
- **One savepoint per transaction of a page** (its claim, its outcome), not one per write.
- **`journal_position` is written once per group commit,** and counts group commits. That still matches ADR 0002's note of #218: "the number of commits the run file holds".
- **No checkpoint runs on the writer.** Automatic checkpoints are off on the writer's connection. A checkpointer on its own connection, on a `tasks` thread, runs a `PASSIVE` checkpoint when the WAL passes 16 MB, and a `TRUNCATE` one on a clean stop.

  > Note (agent decision, on a guarantee, not read by the owner), 2026-11-06, [#2117](https://github.com/goodfetch/goodfetch/issues/2117): the run file's own syncs fold into the commits it acknowledges (the owner's call of 2026-11-06: cut them, keep the measure). **A clean stop runs no `TRUNCATE` checkpoint:** its last write commits synced at every level, `fast`'s included, and no connection of the writer, nor the read of the "unclean" mark, copies the WAL into the file as it closes (`SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE`), so the stop syncs the WAL once rather than the WAL and the file again. A Run that ended leaves its WAL beside its file, at most the checkpointer's 16 MB; SQLite reads both, a Checkpoint is still one self-contained file, a discard still truncates the WAL before it erases, and anything that copies a run file's raw bytes takes its `-wal` too. **A new run file's opening commits its tables and format unsynced** below `off` (`synchronous=OFF` for that one commit, the WAL's header with it): nothing is told of it, and the Run's start, a synced commit, covers it; at `off` the commit that sets the mark still syncs. **A new SQLite file switches to WAL at `synchronous=NORMAL`** (`sqlite_wal::enter`, every store): its rollback journal holds no page to put back, so it syncs once instead of twice, and the file is still synced. **A crawl's start declares the bound of its deferred charges** in its own synced commit (`Syncing::Declaring`), rather than its first claim's group syncing to declare it; a Collie Run, whose charges all sync, declares none, so its reclaim adds nothing. **The seeds' keying and the intake's close are deferred writes:** neither answer is told outside, and the next synced commit, an outcome or the Run's end, covers them.
- `page_size` stays 4,096, and the writer's page cache 512 KiB (ADR 0134's note of #1571).

### Reads leave the writer

- **The writer only writes.** It stays the single actor of ADR 0002 and `STYLE.md`.
- **Reads go through a small, bounded group of kept read-only connections** on the owner's blocking threads, as ADRs 0031 and 0103 already read, though today each read opens its own.
- **A read that must see a given write** waits for the writer's commit count to reach that write's commit, then opens its read transaction.
- **The Frontier's hot state is not read back:** its per-domain queues, already bounded at 64, stay in memory.

### The pipeline

- **One task per page carries the page from claim to outcome.** It holds the Lease, the deadline, cancellation (ADR 0038) and the outcome, as Heritrix, Scrapy, Crawlee and Spider do.

  > Note (agent decision, as built), 2026-11-01: the delivery loop issues the claims, which batch naturally; the page's task then carries it from its fetch to its outcome.
- **Two shared, bounded resources** take the staged model's strengths (sizing each step on its own, and batching) without splitting an attempt across queues:
  - **A CPU pool** sized to the cores runs every Page analysis. It is a policy of `tasks` (ADR 0060), not Tokio's blocking pool, which grows to 512 threads.
    > Note (owner's decision, 2026-11-10, [#2200](https://github.com/goodfetch/goodfetch/issues/2200)): until #2200 lands the code differs from this bullet. The CPU pool is a count of permits, one per core, and an analysis that holds one runs on a thread of Tokio's blocking pool (`crates/goodfetch-engine/src/tasks.rs:147-166`, `:321-328`). #2200 gives Page analyses threads of the CPU pool's own, so that the cap on blocking threads it adds, 4 by default, does not limit them.

  - **The writer** groups commits (above).
- **A page being analysed holds no network slot.** The slot among the requests in flight is given back once the fetch ends (ADR 0004 counts only requests in flight), and the analysis waits for the CPU pool.

  > Note (agent decision, as built), 2026-11-04, [#1905](https://github.com/goodfetch/goodfetch/issues/1905): the place among the requests in flight is the attempt's HTTP admission from the Resource governor (ADR 0040), which ADR 0004's global cap became. A tier race's or an escalation's browser run after that fetch holds the browser page the governor gives it, not an HTTP admission. `TaskOwner::analysis` serves the document's parse and every read of a served or browser page's document (formats, links, fields, Page signature, Page check, Block classification, the gate's use signals and a redirect hop's refresh stub); other blocking work stays on `TaskOwner::blocking`. The pool's permits are `available_parallelism`'s count, one when the OS cannot tell.
- **Every channel is bounded** (`STYLE.md`).

  - per-page work that depends only on the Run.

## Considered Options

- **Cache each module's own result and keep the modules as they are:** rejected. These are local patches over the model that produced 8 parses, and the next spec's module would parse again.
- **Share the tree itself between asynchronous modules:** rejected. A `dom_query` `Document` is never `Sync`, so sharing it needs a `Mutex`, which `STYLE.md` bars around shared state.
- **One streaming lol_html pass for everything:** rejected. Readability needs a tree (ADR 0007 rejected lol-html for main content), and lol_html matches no sibling combinators. It stays the path when nothing needs a tree.
- **Laziness on first access only, with no demand plan:** rejected. What runs then depends on call order, and one stray call brings a cost back unseen.
- **The Page signature on the untouched page, as today:** rejected. It costs a second readability run per page whenever a format is asked, and an overlay rich in text can sign every page of a site alike and merge distinct pages.
- **A cheaper signature without readability:** rejected. It is weaker evidence, and it would redo #851's thresholds.
- **Grouping commits alone, keeping about 8 awaited writes per page:** rejected. Each page's latency would stay 8 round trips through the writer.
- **Asynchronous durability, with writes acknowledged before their sync and only outside acknowledgements gated on a durability watermark:** rejected for now. It gives the outside the same guarantee as two transactions with grouping, but its code and its Simulation tests (ADR 0060) are much heavier.
- **`periodic` as one long open transaction:** rejected, for the reasons in the note under the table of Durability levels.
- **Weakening `full` to periodic checkpoints,** as Heritrix and Scrapy do: rejected. It breaks ADR 0002's guarantee. `periodic` offers it as a choice instead.
- **`periodic` as the default:** rejected. It would align with competitors at the price of up to 5 s of work lost on a power cut, against ADR 0077's G5.
- **`off` with an in-memory journal or no journal:** rejected. Without WAL, readers cannot read while the writer writes, and without a journal a savepoint cannot roll back.
- **Syncing the claim at `full`:** rejected. It protects nothing the outside is ever told, and it costs one more sync per page at low concurrency.
- **One `performance: max` switch:** rejected. It contradicts ADR 0086's one setting per value, hides what is weakened, and cannot switch off a single feature.
- **A staged pipeline, in the manner of StormCrawler or SEDA:** rejected. Inside one process it splits each attempt, with its Lease and its cancellation, across queues, and adds queues to bound and handoffs to pay for. Scaling past one engine is already ADR 0054's partition by domain, which also keeps a domain's Politeness on one engine.
- **Changing the allocator now:** rejected. The measurement used glibc's allocator, which no Linux build ships, and most of the retention comes from churn this ADR removes.
- **Only ADR 0134's byte and instruction ceilings, without structural counts:** rejected. A second parse costs about 5 %, under a 1.10× ceiling, so it would pass unseen twice.
- **Several ADRs, one each for the analysis, durability and settings:** rejected. The decisions depend on one another: the signature on learning, the claim's sync on the levels and on grouping.

## Consequences

- **The optimization pass ([#1577](https://github.com/goodfetch/goodfetch/issues/1577)) takes this ADR as its one spec,** through `/to-spec`, run as one whole spec (ADR 0136) once [#1583](https://github.com/goodfetch/goodfetch/pull/1583) has merged. Its pull request records before-and-after figures for every metric of the owner's matrix and sets the ceilings (ADR 0134). Fixes 1–6 of the profile were estimated to bring instructions to 30–35 % of today; no figure is promised here, and a missed target is written up as ADR 0134 says.
- **Amends ADR 0002:** the four Durability levels, two transactions per attempt, commits grouped across pages, `journal_position` per group commit and checkpoints off the writer.
- **Amends ADR 0005** (the note of #851): the Page signature reads the cleaned page's main content, and `frontier.learning` switches learning off.
- **Amends ADR 0007:** one Page analysis per page, the clean-up in place on the same tree, and the streaming path when nothing needs a tree.
- **Amends ADR 0134:** the structural counts as ceilings, the scenario the Spider target is read on, the matrix's Foxhound cells and the rule for the 2× ceiling.
- **Notes on ADRs 0023** (its table gains the Durability levels, `frontier.learning` and the Page signature), **0028** (`periodic`, `off` and `frontier.learning: false` join `weakened_by`), **0060** (a CPU pool policy in `tasks`), **0086** (switched off means no work; `site_preferences.mark_robots_txt_ignored`) **and 0103** (at `periodic`, a Record a reader saw can be lost to a power cut, which `weakened` labels).
- **`STYLE.md`** gains the rule above. **`TESTING.md`** gains the structural counts beside the absolute ceilings.
- **`GLOSSARY.md` gains two terms,** added with this ADR:
  - **Page analysis:** the one step in which a fetched page is parsed and read by every reader its crawl needs, leaving one result that every later step shares. _Avoid_: parse step, pipeline stage, page processing.
  - **Durability level:** what a run's state survives: a process crash, a power cut, both or neither, chosen per run as `full`, `fast`, `periodic` or `off`. _Avoid_: persistence mode, sync mode, fsync mode.
- **Contracts change in place.** The new values of `run_state.durability`, and the settings `run_state.commit_interval`, `frontier.learning`, `extraction.removal_share` and `site_preferences.mark_robots_txt_ignored`, are added to `goodfetch-protocol`'s types and regenerated with `xtask codegen`. Nothing is published, so no format changes version (ADR 0066).
- **Out of scope: continuous crawling.** A Run that never ends, per-URL revisit dates, a revisit policy and feed discovery, which StormCrawler serves, are decided in ADR 0139, from their own grilling session. This ADR's one task per page with shared pools does not block them.

> Note (agent decision, on a guarantee, not read by the owner), 2026-11-06, [#1930](https://github.com/goodfetch/goodfetch/issues/1930): what [#1577](https://github.com/goodfetch/goodfetch/issues/1577) built, where it differs from the decision above or from its notes. The notes of each ticket above hold the rest, and ADRs 0002, 0005, 0007, 0023, 0028, 0060, 0086, 0103, 0134 and 0140 carry their own notes of #1577.
> - **The Page analysis is three modules, not one.** `goodfetch-extractor` holds the demand plan, the streaming pass, the formats on one tree, the main-content step and the Page signature; Foxhound's readers of the untouched page are `goodfetch-fetch-tier`'s `untouched`, whose `Read` stays with the served page for every later step; a handler's kept tree is `goodfetch-page`'s `kept_tree` (ADR 0140's open question 1). No single `Arc` value gathers a page's results. The demand plan (`Plan::of`) covers the formats and `frontier.learning`; the untouched readers are chosen apart, by `UntouchedDemand`, built once per Run for each Label from a code-free crawl's links and fields, the Page check, `frontier.learning` and whether a handler reads the page.
> - **The Page signature reads the page as served, not the cleaned page.** It reads the main content of the Run's chosen Extractor, with its fallback, as the last reader of the untouched tree, since its step consumes the tree: one parse and one readability run per page. The clean-up runs only for a format read from the cleaned page, so the Clean-up rules' removals take no part in the signature, and the main content it reads is not always the one the formats read.
> - **One parse per page is met except for one case.** A code-free crawl that asks for a format parses its page once more than its untouched readers did, since only a handler's page keeps its tree: Exception X1 of the Quality register holds that gap.
> - **The structural counts are ADR 0140's Quality register rows,** read by `just counts` on the counts benchmark B1 from the gate's spec (#1837), at implementer done and the merge gate, and exposed as the ops listener's `goodfetch.counted_work`, not a test of `crawl::in_memory_pages`. Statement preparations are counted per page a crawl adds, since the once-only preparations of a Run's start and end are no page's (ADR 0140's note of #1907). On `origin/spec/1577` at this note: 1 parse a page (0 on the streaming path), 0.077 selector compilations a page (a handler's own selector, compiled once at its first use), 1 readability run, 0 file opens and 0 preparations a page; 3.385 transactions and 2.385 syncs an attempt in the worst cell, a handler's (1.539 and 1.539 at 16 requests at once), still above 2 and 1 under Exception X4; 2 configuration reads a Run under Exception X5, the engine's own read as it starts being the second (#1885). Bytes allocated per page stay 234.45 times the body's under Exception X3, for #1931.
> - **`full` keeps two writer connections.** A group that needs no sync commits on a second connection at `synchronous=NORMAL`, since switching the pragma per group would prepare its statements again (ADR 0140's note of #1926). The charges a deferred claim journals are bounded: once 64 are owed, the next group syncs, and the bound is declared in the run file (`run.deferred_charges`). After an unclean end the ledger's reclaim charges up to that bound at `full`, and each Slice whole below it; the resumed Run's warning `limit_may_be_over_charged` states it.
> - **A read that must see its own write waits for nothing.** A write is answered once its commit counts, so a read on the kept read-only connections that follows it sees it. A Run that another engine writes is read with one connection per read, since a kept connection would stop that writer from folding its WAL into the file as its last connection ([#1923](https://github.com/goodfetch/goodfetch/issues/1923)).
> - **A Durability level is not an Audit log entry.** `fast`, `periodic` and `off` are labelled in the run report's `weakened` and in `config explain`, as `fast` was. The features switched off are recorded in the Audit log: `frontier.learning` as `learning_switched_off`, and `provenance.log`, `dataset.records` and `fetch.block_classification` as `feature_switched_off`.
> - **Durability levels cover run state only.** The Audit log and the Usage ledger keep `synchronous=FULL` at every level, with one sync per grouped append and none at a connection's close ([#2110](https://github.com/goodfetch/goodfetch/issues/2110)).
> - **Memory.** mimalloc's purge delay is 0, set in `goodfetch-collie`'s `executable::allocator` before any thread starts, for both Products, rather than through `MIMALLOC_PURGE_DELAY`, which would reach the browsers the engine starts ([#1928](https://github.com/goodfetch/goodfetch/issues/1928)). The targets measure the static musl executable, built with cargo-zigbuild, and its own resident pages apart ([#2114](https://github.com/goodfetch/goodfetch/issues/2114)). `dom_query`'s `atomic` feature is on, with dom-smoothie carried in `vendor/dom_smoothie` for it ([#2109](https://github.com/goodfetch/goodfetch/issues/2109)).
