# A panic ends what owned its task, the engine stops only for a part every Run shares, and nothing is restarted in place

When a task of the engine panics outside a crawl's attempt, what owned that task ends, and only that: a call is answered with an error, a Connection ends, a Run fails, a Page, a Session or a browser closes. The engine stops only when the task was a part every Run shares. Nothing that panicked is restarted in place. Decided by the owner on 2026-11-10 in the grilling of decision G-14 of the consolidated review: Q1 to Q6 answered "Yes, all six", Q7 to Q13 "Yes, all seven", Q14 to Q16 "Yes to all, confirmed", and, after an independent check of the grilling's drafts, Qa to Qd "Yes, all four", each answer accepting the recommendation as put. The wording is the grilling session's; the owner did not read it.

ADR 0057 kept unwinding so that a panic "fails only that task", and ADR 0038 gave every task an owner. Neither said what follows:

- **A task's panic reaches no one.** An owner starts a task and keeps no handle that would report its panic, so the task stops and nothing reacts.
- **A call is never answered.** The task that serves a call answers it only once its handler returns; a handler that panics leaves the call in flight, and its program waits.
- **A crawl whose driver panicked is not ended by the crawl.** The driver is one of its Run's tasks, and only the delivery module it runs ends the crawl from inside the crawl crate, so the Run stays `running` until something outside ends it, such as an abort or a stop through the Runs' registry.
- **The engine stays up without its Runs' registry.** The registry is one task of the engine's owner; once it is gone, a call on a Run answers that the engine's Runs have stopped.
- **State a panic interrupted is read on.** Every production place that takes a `std::sync` lock a panic interrupted reads on past it: 53 places in seven crates. The crash-report writer does the same with the engine's masks, so a report written after a panic broke off a change of the masks is masked from the list as the panic left it.

Inside a crawl's attempt the owner decided on 2026-11-10 that a panic ends the attempt as a failed one ([#2253](https://github.com/goodfetch/goodfetch/issues/2253) Q4, [#2285](https://github.com/goodfetch/goodfetch/issues/2285)). This ADR decides every other case. It fills ADR 0057's silence and builds on ADRs 0038, 0128, 0145 and 0146. [Spec #2425](https://github.com/goodfetch/goodfetch/issues/2425) builds it.

## Decision

### What ends (the owner's decisions)

- **A call** whose task panicked is answered with `engine_panicked`; its in-flight place is freed; its Connection, its Run and its Page go on (Q1).
- **A Connection** whose own task panicked ends as when its Client goes away: its calls are cancelled, its Runs follow the rule for a lost Connection, and the Client sees `connection_lost`. Its own tasks are three: the one that serves it and reads its Client's messages, its writer and its log forwarder (Q4, Qc). An Attached engine, whose one Connection is its program, ends with it (Q4).
- **A Run** whose own task panicked ends `failed` with `engine_panicked`. What it committed stays, and a start with its Run ID resumes it, as for any failed Run (ADRs 0029 and 0102); the engine and its other Runs go on. When what panicked is its run file's writer, its end cannot be written: the Run is left as after a crash, with no live writer and no end, and a start with its ID resumes it too (Q2).
- **A Page** closes and the Run trace records it; **a Session** closes with its Pages; **a browser** is treated as crashed, through the path a real crash takes: its Sessions are told and its Pages raise `page_crashed`. Every later call on a Page or a Session closed this way raises `engine_panicked`; the Pages of a browser treated as crashed raise `page_crashed`, as for a lost browser, and the Run trace names `engine_panicked` with `ended: browser`. The Run goes on, and in a crawl the attempt using that Page fails and is retried under the Run's retry rule. Until each has its own owner ([ADR 0146](0146-a-session-a-page-and-a-browser-each-have-one-owner-a-page-has-one-reader-of-its-events-and-one-module-of-the-page-crate-names-cdp.md), spec [#2256](https://github.com/goodfetch/goodfetch/issues/2256)), its tasks are its Run's, so such a panic fails the Run (Q5).
- **Work an attempt starts on its Run is the attempt's** (Q11): the task that keeps its Lease alive while its handler waits for a Politeness Permit, the browser side of a tier race, and the one that receives a handler's answer after the attempt's Lease has ended. A panic in one of the first two ends the attempt; a panic in the third ends nothing, since the attempt is over: the late answer is discarded and the crash report written.
- **A panicked attempt is retried by a line of its own in the crawl's retry rule,** under a setting on by default, as `crawl.retry.handler_failed` governs a handler's own failure (Qb). The setting's proposed name is `crawl.retry.engine_panicked`; [#2285](https://github.com/goodfetch/goodfetch/issues/2285) builds it, and the retry rule's own cap, `crawl.retry.max` (ADR 0093), bounds it.
  > Note (agent decision, as built), 2026-11-12, [#2285](https://github.com/goodfetch/goodfetch/issues/2285): the setting is `crawl.retry.engine_panicked`, a boolean, `true` by default, set at any level and read once for the Run as `crawl.retry.handler_failed` is. An attempt's watch, made as its work item is leased, catches the unwind of the attempt and of the two tasks it starts that end it, and ends the attempt with `engine_panicked`, `ended: attempt`, through the attempt's own end, so each holding is given back where it already is; what the attempt met of its site before the panic is dropped, so its domain neither backs off nor learns from it. The reading of a late answer is caught in its own task, counted and logged. Each panic is counted in `goodfetch.engine.panics` with `ended: attempt`.
- **The engine stops when the task belonged to no Run and no Connection** (Q3, Qd). It logs why and exits 1, and every Run stays resumable. While the Runs' registry runs, a Daemon drains as on a requested drain, each live Run stopping at a safe point; an Attached engine, which has no drain, stops its Runs as it does when its program goes away, each resumable by its ID, and their report says the engine stopped on a bug rather than that their Client aborted them. When the Runs' registry is what panicked, no drain is possible: the engine stops at once, and the next start reconciles as after a crash.
- **State a panic interrupted mid-change is never used again,** with no exception: whatever owns it ends as if its own task had panicked (Q7, Qa). A call that panics while it changes shared state takes that state's owner down with it: the engine for the engine's list of Secret values to hide, a Page for state one Page owns. When the engine's masks were interrupted, a crash report written afterwards has its text withheld (Qa).
- **Nothing is restarted in place** (Q6). The only restarts are the two that rebuild from what was written: a start with the Run's ID, and a new engine process. The engine resumes no Run by itself under this rule: a Run a panic failed waits for a start with its ID, like any failed Run (Q12).

### What a person sees (the owner's decisions)

- **One Error code, `engine_panicked`,** in the Internal group, raised wherever a panic ended something, and also the code of a panicked attempt (Q8). It is not retryable for a program's call (Q8, Qb). Its details: `ended` (`call`, `attempt`, `page`, `session`, `browser`, `run`, `connection` or `engine`), the ID of what ended when it has one, and the crash report's file name. The panic's own text never travels in the error; it stays in the crash report.
- **Through what exists, plus one counter** (Q9): the Run report, `failed`, with `finish()` and `stop()` raising the error; a Run trace entry when a Page, a Session or a browser is closed this way; the existing "Run failed" Notification, with no new event; the crash report and an error log line, which the error's details name; exit code 1 for a Daemon or a CLI command, and `engine_exited` with that code for a program on an Attached engine; a Run the engine stopped while stopping itself is `stopped`, as by any drain, and its report carries a warning with this Error code; one new counter on the ops endpoint, of panics by what ended. Nothing goes to the Audit log.
- **No Shared path gains counted work** (Q10). Answering a panicked call adds no decode, encode, copy or allocation to a call that does not panic; no row is added, no cap is raised and no owner module moves (ADR 0140). If the watch cannot fit under `E1.instructions`' 0.5 %, it comes back to the owner as a register change.
- **A test produces a panic through something a test can already hand the engine,** never through a switch built into a Product: an extra operation whose handler panics, a registered Run driver that panics, and, for a Connection, a Page or a shared part, a test of that crate that starts a panicking task on the owner in question (Q13).

### How it is built (spec #2425's mechanism, the grilling session's, not put to the owner and awaiting the owner's reading)

- **The `tasks` module tells an owner's parent when one of the owner's tasks panicked,** and the parent ends the owner through an end that already exists. An owner never stops itself from one of its own tasks, since stopping waits for them. The owner was told, with Qc, that this mechanism is the grilling session's and not the owner's decision.
- **A call and the task that serves a Connection are watched where they are started,** because each is started on an owner wider than what it belongs to: a call on its Connection's, the serving task on the Daemon's list of Connections.
  > Note (agent decision, as built), 2026-11-12, [#2426](https://github.com/goodfetch/goodfetch/issues/2426): a call's watch catches the unwind inside the task the call already has, in the `rpc` module, and answers through the call's own failure line, so its in-flight place is given back as for any call that ended. `crash_report` in the details is the report's file name, absent when the process records no panics (an engine linked into a program that did not ask for crash reports) or when the report could not be written; the panic hook hands the name to the watch on the panicking thread, and a panic in a handler's blocking work, caught on its blocking thread and resumed in the call, carries its name with it, since resuming runs no hook. A call's `id` is absent: its answer already carries the call's id. The counter is `goodfetch.engine.panics`, Experimental, labelled `ended`; this ticket counts `call` only, and each later ticket of spec #2425 counts what it ends.
- **A `sync` module in each crate that takes a lock carries the rule on interrupted state, so no call site decides.** Today only `goodfetch-counted-work` has a `sync` module, and it holds an atomic; lock sites name `std::sync` under an `expect` of `clippy::disallowed_types`, so [#2430](https://github.com/goodfetch/goodfetch/issues/2430) adds these modules.
- **The engine's transition table gains the event of a shared part's panic** (ADR 0128).

## Considered Options

- **The engine stops on any panic,** as Materialize and TiKV do: rejected (Q1 to Q5). A bug in one read would end every Run of a Daemon; ADR 0057 kept unwinding against exactly that.
- **Carry on without the part,** as today and as Spider does for a page task: rejected (Q3). ADR 0128 already refuses "a warning that carries on": the object is then in a state no one designed.
- **Restart the task in place,** as an Erlang supervisor does: rejected (Q2, Q3, Q6). An Erlang process shares no memory and restarts from scratch; a task here would restart on what the panic left. The restart from scratch exists: a resume from what was written.
- **Read on past a lock a panic interrupted, each place giving its reason,** or the crash-report writer alone: rejected (Q7, Qa). Where the reason holds, the lock is never found interrupted and the rule costs nothing; where it does not, only the rule finds out. A report masked from a half-updated list could hold a Secret value in clear.
- **`engine_panicked` marked retryable,** so that the crawl's rule retries a panicked attempt unchanged: rejected (Qb). It would tell a program that repeating a call that panicked is safe.
- **A panicked attempt never retried:** rejected (Qb).
- **One Error code per thing that ended, or the existing `internal`:** rejected (Q8). The remedy is the same every time.
- **An engine that resumes a failed Run by itself:** not decided here (Q12). It would apply as much to a Run whose engine crashed or whose machine rebooted, so it is a capability of its own, to be placed with schedules in the order of Features.

## Consequences

- **ADR 0057:** its note of 2026-11-10 ends "A panic outside an attempt has no rule yet"; a note now points here. The rejection of `panic = "abort"` stands: unwinding is what lets a call be answered and the engine stop cleanly. "Fails only that task" holds for a call; for the rest it reads "ends only what owned that task" (the grilling session's reading, as in that ADR's note).
- **ADR 0038:** the tree of owners is also the tree of what ends together when a task panics (the grilling session's reading, as in that ADR's note).
- **ADR 0079:** the Internal group gains `engine_panicked`.
- **ADR 0128:** the engine's table gains the event of a shared part's panic.
- **ADR 0146:** a Page's, a Session's and a browser's owner each end alone on a panic of their task; [#2263](https://github.com/goodfetch/goodfetch/issues/2263), [#2273](https://github.com/goodfetch/goodfetch/issues/2273) and [#2276](https://github.com/goodfetch/goodfetch/issues/2276) carry it.
- **ADR 0140:** no change.
- **`STYLE.md`** gains two rules, each with the ticket that enforces it: with [#2427](https://github.com/goodfetch/goodfetch/issues/2427), "an owner's parent is told when one of its tasks panics, and nothing is restarted in place" (its first half is spec #2425's mechanism, above, awaiting the owner's reading; its second is Q6); with [#2430](https://github.com/goodfetch/goodfetch/issues/2430), "never read on past a lock a panic interrupted" (Q7, Qa). Until #2430 lands, 53 production places in seven crates still read on past an interrupted lock (`Existing code`, below).
- **The catalog** gains `engine_panicked` ([#2426](https://github.com/goodfetch/goodfetch/issues/2426)) and the setting for the retry of a panicked attempt (#2285). Nothing is published, so no format changes version (ADR 0066).
- **Not reached:** an abort, a stack overflow and a panic while unwinding end the process; the next start reconciles.
- **Glossary.** No term changes.
