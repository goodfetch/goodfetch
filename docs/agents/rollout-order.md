# How work is picked

Work follows the ticket graph (owner, 2026-11-23: « Il faut que ce soit implémenté comme implement spec de Matt Pocock et que ça suive le graphe des tickets, sans bloqueur, sans milestone », [ADR 0136](../adr/0136-each-implement-spec-run-is-one-whole-spec-and-milestones-are-ticket-metadata-and-owner-checkpoints.md)'s note of that day). The order of steps this file held until then, the order of Features' lines and the holds this file alone kept ended that day; this file's `git log` has them. This file holds no status: the tracker does.

**What holds a ticket back.** Beyond the [Frontier](issue-tracker.md#delivery-milestones)'s labels and assignee, two things:

- **An open blocked-by link.** Every "before" that code or a measurement requires is a native blocked-by link on the ticket that waits. A wait a run finds that the tracker does not show becomes one the same hour (the [Implementation loop](issue-tracker.md#implementation-loop)), so the next pick sees it.
- **A file in work.** Two writers never edit one file at the same time: a run or relay starts only when the tickets it takes share no file with a run or relay in progress, and the agent that starts it says which files it checked.

A milestone, a line of Features, or a file that an open ticket names but no one is editing holds nothing. The one exception is the owner's scope: the specs kept ready below wait until the owner names one into the work.

**What goes first.** A ticket is startable when it is on the Frontier and no file in work holds it. Among the startable work, the spec or ticket whose startable tickets unblock the most open tickets goes first: the open tickets reachable from them through blocking links, counted transitively. Each run stays one `/implement-spec` of a whole spec, and a slot that frees takes the next pick at once; `TESTING.md`'s [Checks by role](../testing/checks-by-role.md) sets how many slots run.

Every "before" or "after" a line states is one that code requires, and its tickets' blocked-by links hold it. This repository holds the Products alone: Goodfetch Cloud is built in another repository, and no line below concerns it. Every capability stays in V1 (ADR 0037). **How a line is cut,** in this order:

1. The agent that will write the line's spec re-reads every compared tool ([ADR 0037's "Compared tools" table](../adr/0037-v1-scope-matrix.md#compared-tools)) from the version recorded there to its latest release, records the new version and date, and adds every capability no row holds as a row `open`, under one grilling ticket to the owner. The spec is written once the owner has answered that ticket. A row becomes `excluded` only in a pull request that quotes the owner's words and links where they were said (owner, 2026-11-11, grilling of G-19, Q33).
2. The spec is written from the line's outcomes and every open ticket they wait on that no refactor spec holds. Tickets keep their numbers and their text and change parent; a ticket the line does not need stays where it is.
3. A line cut in several specs is cut by crate or folder, so that no two of its specs name the same file in their `Existing code` lists and they run side by side; a file two of them would need goes to one of them, or to a first spec the others wait for in the tracker (ADR 0136's note of 2026-11-12).
4. The spec carries its `Existing code` list, read at that day's `main` (ADR 0144).
5. Its draft lists, in one table, every note of the ADRs it touches that is marked "not read by the owner", and the owner's approval of the spec is the owner's reading of those notes (owner, 2026-11-10, grilling of G-06, Q8). Each line of the table says what a user sees because of its note, and each note is then marked accepted or amended.
6. The spec is ready to run when none of its tickets waits on an open ticket outside it. A spec of the old cut closes when its last open ticket has moved or closed.
