# Order of work

The order of runs the owner adopted on 2026-11-01 and amended in later grillings (see this file's `git log` for each change). Each refactor spec runs right after the tickets its performance criterion is measured with. An issue written before 2026-11-11 may cite an older step number; the spec number it names decides.

**Status lives in the tracker.** This file holds only what is still to run and the order between it. A ticket, relay or step that closes leaves this file in the change that closes it, or in the next change to this file; a "waits for" whose blocker has closed goes with it.

**What a step is.** Each run goes as `issue-tracker.md`'s [Implementation loop](issue-tracker.md#implementation-loop) says:

- **A step that names a spec** is one `/implement-spec` run of it: every open ticket of that spec, whatever its milestone.
- **A step that names tickets** (steps 7, 9 and 15) is a relay of `/implement` on those tickets alone. It is no `/implement-spec` run, so it cuts no spec into scoped runs. Each of its tickets is built on a branch from `main` and reaches `main` through a pull request that closes it; none lands on a spec's integration branch; ready ones merge together, by `AGENTS.md`'s Merging.
- **#1838 has one `/implement-spec` run, step 14,** with every ticket still open then; step 9 takes its CDP tickets by relay. Step 14 starts `spec/1838` afresh from `main`: the `spec/1838` branch of 2026-11-06 is superseded.
- **#2165 has one `/implement-spec` run, step 13,** with every ticket still open then.

**Where the order is held.** This file picks the next run. The tracker's native dependencies hold each "before" that code or a measurement requires, and each step names them, so a run started out of turn still takes no ticket too early. When this file and the tracker differ, correct the wrong one in the same change. An order this file gives that no code or measurement requires is said to be held here only.

**Runs side by side.** Runs and relays go side by side as the [Implementation loop](issue-tracker.md#implementation-loop) says. This list's order is the priority when slots are short: the earlier step takes the free slot. The tracker's dependencies hold every "before", and an order this file alone holds still holds: what it places later waits as written, though the tracker would let it start, but for the slot the next paragraph fills. A run or relay starts beside another only when the tickets the two take share no file, and the agent that starts it says which files it checked. This file lists no specs that may pair: the Features specs are cut when their line is next, so a list would go stale.

**A slot is not left empty** (ADR 0136's note of 2026-11-12). When no step from 4 to 15 and no relay named above can fill a slot, Features' work (step 16) takes it, in the order of its lines. It takes a cut spec of the earliest line that has one ready to run. Before a line is cut, a relay of `/implement` takes tickets of that line that carry `ready-for-agent` and have no open blocker. Either starts only when its tickets share no file with a run or relay in progress, and none with a file that an open ticket of steps 4 to 15 names: the refactor rewrites those files, and work built on them before it is built twice. The agent that starts it says which files it checked. Steps 4 to 15 keep their order among themselves, every dependency of the tracker holds, and an earlier step takes the next slot that frees.

    **How a line is cut,** in this order:

    1. The agent that will write the line's spec re-reads every compared tool ([ADR 0037's "Compared tools" table](../adr/0037-v1-scope-matrix.md#compared-tools)) from the version recorded there to its latest release, records the new version and date, and adds every capability no row holds as a row `open`, under one grilling ticket to the owner. The spec is written once the owner has answered that ticket. A row becomes `excluded` only in a pull request that quotes the owner's words and links where they were said (owner, 2026-11-11, grilling of G-19, Q33).
    2. When the line is next, its spec is written from the line's outcomes and every open ticket they wait on that no earlier step closes. Tickets keep their numbers and their text and change parent; a ticket the line does not need stays where it is.
    3. A line cut in several specs is cut by crate or folder, so that no two of its specs name the same file in their `Existing code` lists and they run side by side; a file two of them would need goes to one of them, or to a first spec the others wait for in the tracker (ADR 0136's note of 2026-11-12).
    4. The spec carries its `Existing code` list, read at that day's `main` (ADR 0144).
    5. Its draft lists, in one table, every note of the ADRs it touches that is marked "not read by the owner", and the owner's approval of the spec is the owner's reading of those notes (owner, 2026-11-10, grilling of G-06, Q8). Each line of the table says what a user sees because of its note, and each note is then marked accepted or amended.
    6. The spec is ready to run when none of its tickets waits on an open ticket outside it. A spec of the old cut closes when its last open ticket has moved or closed.

    **Where nothing orders two capabilities,** the one a compared tool ships in its open-source code comes first. The compared tools are the 22 of [ADR 0037's "Compared tools" table](../adr/0037-v1-scope-matrix.md#compared-tools) (owner, 2026-11-11, grilling of G-19, Q2 and Q28).
