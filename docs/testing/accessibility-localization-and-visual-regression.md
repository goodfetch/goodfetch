## Accessibility, localization and visual regression

Decided in [ADR 0073](../adr/0073-accessibility-meets-wcag-2-2-aa-the-console-ships-ready-to-translate-and-screenshots-compare-in-one-pinned-image.md). The runners are those of [Browser tests and the docs site](browser-tests-and-the-docs-site.md). Two product decisions in it await the owner's confirmation: V1 ships in English, ready to translate, and the docs publish an accessibility statement.

### Accessibility

- **The target is WCAG 2.2 AA** for the docs site and the Live view packages' own controls. The remote page inside the Live view is third-party content; the Live view's controls, name and announcements are not.
- **Use the shared Playwright fixture: it runs axe with the tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` and `best-practice` at the end of every served test.** Call `expectAccessible(page)` at each state worth checking on the way (an open dialog, drawer or menu). The docs pass runs axe on every `sitemap.xml` page of `next`, light and dark.
- **The audit runs axe with every rule of those tags on**, at the end of each served test that passed, on every open page but `about:blank`, and fails the test with `axe_violations`. Its "incomplete" results are attached to the report as `axe-incomplete` (the page's URL and each result's rule, help and elements) and never fail. axe waits on the page's timers, so the end-of-test audit resumes a `page.clock` the test installed; a test that paused it resumes or runs it before calling `expectAccessible`.
- **Never disable an axe rule in a test.**
- **Check keyboard access with the shared helpers:** Tab and Shift+Tab reach every element with an interactive role, focus never falls to `body`, Escape closes each overlay and returns focus to its trigger, and the ordered accessible names are a snapshot. At each stop, the element must look different focused and unfocused, and must not be entirely covered.
  - `keyboardWalk(page)` and `focusChecks(page)`, from `@goodfetch/test-support/playwright`, check these rules; each walk starts at the page's top and ends when focus leaves the page. `keyboardWalk` tabs forward, opens each overlay a stop declares (`aria-haspopup` or `popovertarget`) with Enter, or ArrowDown on a combobox, presses Escape there, and tabs back; it gives each stop's `{ role, name }` in Tab order for the snapshot. It fails with `focus_trapped` when Tab comes back to a stop before focus leaves the page, `focus_lost` when focus falls to the body, `focus_unreachable` when Tab or Shift+Tab never reaches a visible, enabled element with an interactive role (a composite widget's options, items, tabs and radio buttons count through their widget), `overlay_not_opened` and `focus_not_returned`. `focusChecks` fails with `focus_obscured` when no point of a 5 × 5 `elementsFromPoint` grid over the part of a stop inside the viewport shows it on top, `focus_not_visible_unstable` when that area changes while the stop stays unfocused (an animation that never ends there would pass for a ring), and `focus_not_visible` when the stop, with 8 CSS pixels around it for its ring, looks the same focused and unfocused.
  - On WebKit, a walk presses Alt+Tab, since WebKit's Tab skips links and buttons as macOS does, and `focusChecks` takes its screenshots through the known-issue tolerance of the style element Playwright adds before every WebKit screenshot, which the production CSP refuses, so it checks focus visibility there too.
- **Check reflow, text spacing and motion with the shared helpers:**
  - at 320 × 256 CSS pixels there is no horizontal page scroll, except inside data tables and code blocks with their own scroll container. `reflow(page)`, from `@goodfetch/test-support/playwright`, lays the page out at that size, fails with `horizontal_scroll` when the page or an element of it scrolls sideways, unless the element is a table or code block (`table`, role `table`, `grid` or `treegrid`, `pre`, `code`) or its only child is one, and gives the page back its viewport;
  - with WCAG's text-spacing values and at 200% text, in the `component` project, no text is clipped without a way to read it in full. `clippedText(locator)`, from `@goodfetch/test-support/vitest-browser`, fails with `text_clipped` when an ancestor whose `overflow` hides or clips cuts off text under the locator; text an ancestor lets the reader scroll to passes, as does visually hidden text (a box at most 1 CSS pixel wide or high). `textSpacing()` applies the style sheet until the test ends. It doubles the root's font size, so a size in `px` does not grow;
    _Why:_ a page under the production CSP refuses an injected style sheet, so a served test cannot take it, and Playwright has no option for either;
  - under `reducedMotion: 'reduce'`, `document.getAnimations()` holds no running animation after an action. `noRunningAnimations(page)`, from `@goodfetch/test-support/playwright`, reads them two frames after the call and fails with `animations_running`, or with `reduced_motion_off` on a page that does not prefer reduced motion.
- **Every drag has a single-pointer alternative,** and its test performs the action through it.
- **Test announcements with `@guidepup/virtual-screen-reader`** in the `component` project: live regions, route titles and Live view control changes. Assert names and roles in the spoken log. `virtualScreenReader(container)`, from `@goodfetch/test-support/vitest-browser`, starts one over the container until the test ends.
- **The Live view's escape key always returns focus to the page that embeds it** while a person holds control; a served test proves it and that every other key reaches the remote page.
- **The CLI's colour never carries information alone:** in a pseudo-terminal, the coloured output with ANSI sequences stripped equals the `NO_COLOR=1` output. `NO_COLOR` set to any non-empty value disables colour, an empty one does not, and `--color always` overrides it. The shared CLI helper fails any `tests/it` case whose piped output holds an escape byte (0x1B).
- **Real screen readers run as the Live check `screen-reader`** (Guidepup, NVDA on Windows and VoiceOver on macOS), nightly, owned by area 12, blocking nothing directly; before each release candidate while the nightly tier is off.

### Localization

- **V1 ships in English.**
- **Render data inside `translate="no"`:** URLs, names, IDs, page text and every value from the engine.
  _Why:_ browser translation then leaves data alone, and a test can tell data from interface text.
- **Take locale and time zone cases from the shared table in test support** (`en-US`, `de-DE`, `fr-FR`, `tr-TR`, `ar-EG`, `hi-IN`, `ja-JP`; `UTC`, `America/St_Johns`, `Asia/Kathmandu`, `Pacific/Chatham`, `Australia/Lord_Howe`, and the DST gap and overlap days of `Europe/Paris` and `America/New_York`). Period Limits and Schedules use it for their zone cases.
- **The elsewhere project** reruns served tests with `locale: 'tr-TR'` and `timezoneId: 'Asia/Kathmandu'` (Release).
- **A translation project** adds a page script that wraps every new text node in `<font>`, as page translators do; served tests must pass with no uncaught error (Release). The Release suite's `translation` project sets the served fixture's `translationEmulation` option, whose context adds the script (`emulateTranslation(context)`) to every page from the document's start. It leaves text under `translate="no"` alone, as translators do.
- **The CLI's human output reads no locale:** the snapshot commands give the same bytes under `LANG` and `LC_ALL` set to `tr_TR.UTF-8`, two `TZ` values print the same instant, and `--json` is UTC.
- **Engine results never depend on the host's locale or time zone** unless a setting names a zone. The Release suite reruns the engine's integration tests and the Journeys on Linux and macOS with `TZ=Pacific/Chatham` and `LANG=tr_TR.UTF-8`.
- **The shared Unicode record** (bidi text with marks, NFC and NFD forms, a ZWJ emoji sequence, an astral character, a zero-width joiner, a BOM, a tab and a newline in a field) round-trips byte for byte through every Sink conformance case and every Export format.
- **The Proving ground's encodings and language families** cover the encodings and scripts ADR 0073 lists; their oracle holds the expected text in UTF-8.
- **Keyboard layouts and IME:** a served Chromium test drives the Live view with AZERTY, QWERTZ and dead-key pairs and a CDP `Input.imeSetComposition`, and compares a Proving ground page's record of events with literal expected events.

### Visual regression

- **Compare a Reference screenshot only inside the pinned Playwright image, on Linux x86-64.** Visual tests are the `visual` projects of Vitest and Playwright, and nothing else schedules them. Name a visual test file `*.visual.test.ts[x]` (Vitest) or `*.visual.spec.ts` (Playwright). The image is pinned by the digest of its Linux x86-64 manifest in `ci/visual/image.toml`, whose Playwright version is the pnpm catalog's; both runner configs define their `visual` project only inside it (`ci/visual/run.sh`), so the other projects and every host leave visual tests out. The pull-request tier runs them in the `visual` job.
  _Why:_ rendering differs by OS, architecture and font stack.
- **The shared visual config gives both `visual` projects:** `visualConfig` from `@goodfetch/test-support/visual-config`, which `playwright.config.ts` and `vitest.config.ts` spread. It gives each project only when `GOODFETCH_VISUAL_IMAGE` names `ci/visual/image.toml`'s digest, refuses another image with `visual_image_not_pinned`, sets `updateSnapshots: 'none'` (Playwright) and `update: 'none'` (Vitest, inside the image) so no suite writes a Reference screenshot, even a missing one, and fixes Vitest's locale, time zone, scale, motion and 1280 × 800 viewport with its animations disabled and caret hidden.
- **Never set a tolerance in a test.** Zero mismatched pixels at the default per-pixel threshold. `test-support/typescript/src/visual-config.ts` is the one file that sets a comparison's tolerance: `xtask screenshots check` (Quick) fails on `maxDiffPixels`, `maxDiffPixelRatio`, `allowedMismatchedPixels` or `allowedMismatchedPixelRatio` in the code of any other JavaScript or TypeScript file, and on a `threshold` key of a comparison's options (`toHaveScreenshot`, `toMatchScreenshot`, `toMatchSnapshot`, `comparatorOptions`), or any `threshold` in a visual test file, so options in a variable do not hide it; it reads fixture modules a test may import too, outside its own cases (`xtask/tests/it/fixtures/`) and `rnd/`.
- **Make the screen deterministic:** in Playwright, compare through the shared helper, `screenshot(page, name)` from `@goodfetch/test-support/screenshot`. It refuses a page that lacks a fixed setting with an `UnsettledScreenshotError` (`screenshot_unsettled`) whose `settings` name each one: the fixed instant (`page.clock.setFixedTime`), `locale: 'en-US'`, `timezoneId: 'UTC'`, the project's viewport (a test never sets its own), `deviceScaleFactor: 1` and `reducedMotion: 'reduce'`. It then awaits `document.fonts.ready` and compares with animations disabled and the caret hidden, masking only the Live view's frames (`<goodfetch-live-view>`). In Vitest, fix the instant with fake timers. Use builder data with literal defaults.
- **Make hover, focus and pressed states with real `userEvent` input** in `.test.tsx` files, never a pseudo-states addon.
- **A Reference screenshot is neither a fixture nor a snapshot** in the sense of [Fixtures and data files](fixtures-and-data-files.md) and [Snapshots](snapshots.md): their size limit, their `.source.toml` and "CI never writes a snapshot" do not apply; its own rules below do.
- **Keep Reference screenshots beside their tests,** named without the platform, each at most 512 KiB (`xtask screenshots check`, Quick). Clip a larger one to the region the test is about. No Git LFS. A run of every visual project fails on a Reference screenshot no test read: each visual run records the references it reads under `target/visual/read/` (Vitest's config and the Playwright helper do), and `xtask screenshots orphans` fails on any other file in a `__screenshots__/` or `-snapshots/` folder, so a Playwright screenshot taken without the helper shows up as an orphan.
- **Update Reference screenshots only through the `update-screenshots` workflow** on the pull request's branch (`gh workflow run update-screenshots.yml --ref <branch>`), then `just screenshots-fetch <run>`, and commit them with your own sign-off, naming the run in the commit message. The workflow is the only writer and is not a suite job, so no suite writes one. `just screenshots-fetch` refuses a run whose image digest is not the pinned one or whose commit is not the branch's head, and any file outside a reference folder. Never commit a Reference screenshot rendered outside the pinned image.
- **The gate runs its visual step only when the change reaches it:** when a visual test, a Reference screenshot, `playwright.config.ts` or `vitest.config.ts`, the pinned image or its scripts (`ci/visual/`, `ci/vm/visual.sh`), or a package a visual test is in or depends on changes, and for any change outside every package, as for every selectable step.
- **The first pull request after the owner's machine joins as the runner ([#1562](https://github.com/goodfetch/goodfetch/issues/1562)) bootstraps the fixture's Reference screenshot.** No reference is committed before then, since none may be rendered outside the pinned image, so until one lands only a pull request that selects the `visual` job fails: that pull request runs the `update-screenshots` workflow on its branch, then `just screenshots-fetch <run>`, and commits the fixture's References (`fixture-page-visual.png`, and Firefox's and WebKit's `-visual-firefox` and `-visual-webkit` ones) with the run named.
- **Locally, `just` runs the visual projects in the same image through Docker or Podman;** with neither, the step fails with an error naming the fix. On an arm64 host the image runs under emulation: `just visual-repeatability` names it (Docker Desktop on Apple Silicon runs it through Rosetta for Linux, the translator of CI's VM, ADR 0135) and, once the `update-screenshots` workflow wrote every committed Reference (the commit that last changed each names its run, `ci/visual/ci-references.sh`), compares every visual case with the committed References. If they differ, local visual runs on such hosts dispatch the visual job to CI and follow it, like `just release-ci` (ADR 0073); until the first References land, that comparison waits.
- **What is screenshotted:** the docs' page templates, light and dark, desktop and phone, and test support's fixture pages.
- **A browser joins the `visual` projects only once its screenshots repeat in the pinned image.** `just visual-repeatability [browser,…]` measures it, through Docker or Podman on a copy of HEAD: every Playwright visual case runs 20 times (ADR 0064's count) on each browser against a Reference the measurement writes first in the copy, and it prints each browser's verdict with each case's runs. Record them in `REPEATABILITY` in `test-support/typescript/src/visual-config.ts`, the runs the verdict rests on included. Chromium's project is `visual`, in every suite; each other browser that repeats has its own, `visual-firefox` and `visual-webkit`, in the Release suite only (`GOODFETCH_TEST_SUITE=release`, which the Release suite's visual job and the `update-screenshots` workflow set). A browser whose screenshots do not repeat stays out, its served tests and axe keep running, and an issue owned by area 12 tracks it until 20 runs repeat. Never add a tolerance instead. Chromium, Firefox and WebKit all repeated every run (`REPEATABILITY`; [ADR 0073](../adr/0073-accessibility-meets-wcag-2-2-aa-the-console-ships-ready-to-translate-and-screenshots-compare-in-one-pinned-image.md)'s note on #389). After that, a screenshot test that stops repeating is a Flaky test like any other ([Flaky tests and Live checks](flaky-tests-and-live-checks.md)): quarantined, never removed.
- **No hosted visual service:** declined while there is no revenue (ADR 0076); screenshots compare in the pinned image.

### Manual tests

Only these stay manual, on each minor's release candidate, recorded on the release pull request:

| Manual test | What a person does |
|---|---|
| Screen-reader pass | NVDA with Firefox and Chrome on Windows, VoiceOver with Safari on macOS and iOS, TalkBack with Chrome on Android, over some docs pages and the CLI's common commands |
| Keyboard, zoom and contrast pass | Keyboard only, 400% zoom, the OS magnifier, a Windows contrast theme and speech input on changed docs pages, in Chrome, Firefox and Safari |
| Real IMEs and layouts | Japanese, Chinese Pinyin and Korean IMEs, AZERTY and a dead-key layout, in the Live view, on macOS and Windows |
| Browser translation | Chrome's and Safari's page translation over the docs' main pages |
| WCAG review of new pages | Names and instructions, error suggestions, consistent help, redundant entry, sensory-only cues; the accessibility statement kept current |
