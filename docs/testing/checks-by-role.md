## Checks by role

Which checks each role runs, and when (the owner's decision of 2026-11-05). Orchestrator briefs, `implement-spec` runs and relays of `/implement` point here and list no checks of their own; where a brief or a skill asks for more, this section wins.

| Role | Runs | Does not run |
|---|---|---|
| Implementer of a ticket | While editing: `tdd`'s red-green cycles and the tests of the modules it touches, by name, and the steps of `just quick` its change reaches, by name (`just quick-steps`, [Commands](suites-commands-and-time-budgets.md#commands)). Done, once, on the tree it reports: `just quick`, which reads the change against the integration branch's tip when that branch is the branch's upstream (its base, below), and the [Quality register](../../TESTING.md#quality-register)'s rows whose Runs at is implementer done, for the Shared paths it touched ([Rules](../../TESTING.md#rules)). | `just pre-merge`, `just stress`, `just perf`, `just linux`, `just visual`, a per-merge smoke run, a build, database, Journey, end-to-end or benchmark suite, `just counts` before the change or for a family the change does not touch, unless its spec names one for implementer done. |
| Merger of a ticket into an integration branch | The merge. The pre-push hook is its only check: the sign-offs and subjects of the pushed commits, and `just quick` unless the merge leaves a tree it already passed on. | Any other lint, suite, `just counts` or smoke run. |
| The pull request to `main` that finishes a spec, from its integration branch `spec/<n>`: none of the spec's sub-issues stays open once it merges (the owner's rule of 2026-11-13, ADR 0135) | `just preflight` on its head in its own worktree, then `just merge <number>`, once on its head: the gate `xtask affected` picks: for a change a test reads, the full gate (the Pre-merge suite with `perf` and every family of `just counts`, the stress run, the visual tests and the Linux-only tests). A `spec/<n>` pull request that leaves a sub-issue open is any other pull request below, and `just merge` says why it took the quick gate. | |
| Any other pull request to `main`, during the refactor (the owner's decision of 2026-11-10 and rule of 2026-11-14, [ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md); the owner ends it) | `just merge <number>`, once on its head: the docs gate for documents alone, else the quick gate (sign-offs, commit messages, the floor guard, secrets in commits, advisories, notices, `just lint`, the Quick suite, the Journey task lists), even when a test reads the change. Only a finished spec's pull request takes the full gate (the owner's rule of 2026-11-14, « FULL GATE seulement en fermant une spec entière », ADR 0135): no count of quick merges, no `--full` option and not the pull request that pins the reference build (#2281). | For a change a test reads: the Pre-merge suite, `perf`, the stress run, the visual tests, the Linux-only tests, and the full gate's other steps (TLC, the Kennel's checks, the MSRV build, Miri, loom, the Windows build under Wine, the feature combinations, the fuzz-target check, the proofs, the Feature and Client listing checks). They run on the next full gate, a finished spec's pull request's, over the whole workspace; its stress run compares its head with the head of the last full gate, so the tests such a merge adds or changes run their 20 times there ([Before merge](flaky-tests-and-live-checks.md#before-merge)); its `perf` compares with `main`, which by then holds the change, so `perf`'s comparison with the base does not see what it moved. |
| `main` | The backstop, `just gate-backstop`, daily from the gate host's cron while it is switched on (`ci/gate-backstop.state`; off since 2026-11-10, [Commands](suites-commands-and-time-budgets.md#commands)), and the cron jobs of [After merge](flaky-tests-and-live-checks.md#after-merge); the nightly fuzzing, `just fuzz-nightly`, from the gate host's cron by the entry in `ci/fuzz-nightly.crontab` (#2454, [Fuzzing](security.md#fuzzing)); the Release suite on dispatch. | |

- **One `just quick` reports every failure.** Its steps, the lints' own included, all run even after one failed, and its summary names each failed step and its log ([Commands](suites-commands-and-time-budgets.md#commands)), so a ticket needs one fix round for all its defects, then one `just quick` on the fixed tree.
- **No check runs twice on one tree,** whoever ran it first: the agent, the pre-push hook or the merger. `ci/quick.sh` records each tree a green `just quick` passed on a clean checkout in the repository's common folder (`goodfetch-quick-green`, which every worktree shares), and `.githooks/pre-push` runs no `just quick` for a push of recorded trees. A recorded tree says nothing of the messages of the commits that hold it, since a reworded commit keeps its tree: the hook judges the sign-offs (`just dco`) and the subjects (`just commit-messages`) of the pushed commits on every push, and refuses the push on a red one before `just quick` runs. Such a commit is only mended by rewriting it, and a gate that ran on it then reuses nothing, as the full gate of #2481 showed on 2026-11-11. After an edit, run again only what the edit can reach.
- **An unchanged check runs again once, and only after a diagnosed environment fault** (a full disk, a killed process, a timing failure on a loaded host), in a free slot, not under the same load: never to see whether a failure goes away ([No retries](flaky-tests-and-live-checks.md#no-retries)).
- **`just quick` reads the change against its base:** the commit the push's remote ref holds when the pre-push hook runs it and the push only adds the branch's own commits to it, else the branch's upstream off `main` when it is another branch (a ticket's integration branch), else `origin/main`. A ticket's quick gate covers its own change, not the integration branch's whole diff with `main`. After a rebase, or a merge of the branch's own base, the remote ref's commit is no base, since the change would hold every file the base gained: the hook says so in one line and `just quick` reads the branch against its own base (`ci/change-base.sh`).
- **The branch's own remote copy is never that base.** After `git push -u` a branch's upstream is the branch of its name on the remote, which holds its head: against it nothing changed, so no test would run and the tree would still be recorded green. `just quick` reads such a branch against `origin/main` and says so; when the branch goes into an integration branch, name that branch in `GOODFETCH_QUICK_BASE`.
- **One heavy suite at a time per machine** (a build, database, end-to-end, benchmark or Pre-merge run). **Implementers on one machine:** start with 3, and add one at a time while the load stays under the core count, memory does not swap, the disk has room for another build, and no check has failed on timing or queued behind a heavy suite since the last look; when the load passes the core count, memory swaps or a check fails on timing, leave the next finished implementer unreplaced (the owner's decision of 2026-11-05). Wait for a run through its completion notice, never through a `pgrep` or `sleep` loop.
- **A run has one implementer, which holds both ticket roles** (the owner's decision of 2026-11-11, [ADR 0133](../adr/0133-agent-work-follows-the-matt-pocock-skills-as-written-and-the-fresh-review-is-retired.md)'s second note of that day; [the Implementation loop](../agents/issue-tracker.md#implementation-loop)). It builds the spec's tickets one after another on `spec/<n>`, in one slot worktree, and at the end of each it runs the first row's checks on the ticket's commit, then pushes, which stands for the second row's merge. On `spec/<n>` the upstream is the branch's own remote copy, so each ticket's `just quick` is given the last pushed tip as its base, `GOODFETCH_QUICK_BASE=origin/spec/<n>`, and runs before the push: without that base it reads the whole spec so far against `origin/main`. The limit above counts one implementer for each run and each relay.

_Why:_ on the gate host, in M1 and spec #1577's run up to 2026-11-05, Pre-merge runs by implementers took about 1,749 minutes, the hook's `just quick` on trees that had already passed 162 pushes and 2,598 minutes, and `just counts` before and after each ticket over every family 139 runs and 1,375 minutes. The merge gate of the pull request to `main` still runs each of them once.
