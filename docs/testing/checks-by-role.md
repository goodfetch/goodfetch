## Checks by role

Which checks each role runs, and when ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s note of 2026-11-21). Orchestrator briefs, `implement-spec` runs and relays of `/implement` point here and list no checks of their own; where a brief or a skill asks for more, this section wins. ADR 0135's amendment of 2026-11-22 ([#3373](https://github.com/goodfetch/goodfetch/issues/3373)) gives each check one owning layer, hosted or local, so that each runs once per tree; the rows below hold until the batch flow moves to the hosted tier ([#3381](https://github.com/goodfetch/goodfetch/issues/3381)), which changes them.

| Role | Runs | Does not run |
|---|---|---|
| Implementer of a ticket | While editing: `tdd`'s red-green cycles and the tests of the modules it touches, by name, and the steps of `just quick` its change reaches, by name (`just quick-steps`, [Commands](suites-commands-and-time-budgets.md#commands)). Done: those tests and steps green on the tree it reports, then the push. In a run, a ticket ends with no `just quick` of its own: the batch's `just batch-check` runs `just quick` once, on the combined tree of every pull request it holds (the owner's decision of 2026-11-23, ADR 0135's note of that day). A relay of `/implement`, whose pull request no batch holds, ends with `just quick`, which reads the change against the integration branch's tip when that branch is the branch's upstream (its base, below), and the [Quality register](../../TESTING.md#quality-register)'s rows whose Runs at is implementer done, for the Shared paths it touched ([Rules](../../TESTING.md#rules)). | In a run: `just quick`, `just counts` and `just compare`. In both: `just pre-merge`, `just stress`, `just perf`, `just linux`, `just visual`, a per-merge smoke run, a build, database, Journey, end-to-end or benchmark suite, `just counts` before the change or for a family the change does not touch, unless its spec names one for implementer done. In a run, `just counts` and `just compare` run once at the spec's end: every family of `just counts` in the full gate of the pull request that finishes the spec, and `just compare`, where the spec measures against other tools, once on its last ticket's tree, in the quiet share. |
| Merger of a ticket into an integration branch | The merge. The pre-push hook is its only check: the sign-offs and subjects of the pushed commits, and `just quick` unless the merge leaves a tree it already passed on or the push goes to `spec/<n>`, whose batch runs it; such a push runs the floor guard and the module check instead (the last row's rule below). | Any other lint, suite, `just counts` or smoke run. |
| The pull request to `main` that finishes a spec, from its integration branch `spec/<n>`: none of the spec's sub-issues stays open once it merges (ADR 0135's note of 2026-11-13) | `just preflight` on its head in its own worktree, then `just merge <number>`, once on its head: the gate `xtask affected` picks: for a change a test reads, the full gate (the Pre-merge suite with `perf` and every family of `just counts`, the stress run, the visual tests and the Linux-only tests). A `spec/<n>` pull request that leaves a sub-issue open is any other pull request below, and `just merge` says why it took the quick gate. | |
| Any other pull request to `main`, during the refactor ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendment of 2026-11-10 on the quick gate and note of 2026-11-14; the owner ends it) | `just merge <number>`, once on its head: the docs gate for documents alone, else the quick gate (sign-offs, commit messages, the floor guard, secrets in commits, advisories, notices, `just lint`, the Quick suite, the Journey task lists, and xtask's codegen tests when the change reaches what only they check), even when a test reads the change. Only a finished spec's pull request takes the full gate (ADR 0135's note of 2026-11-14): no count of quick merges, no `--full` option and not the pull request that pins the reference build (#2281). | For a change a test reads: the Pre-merge suite, `perf`, the stress run, the visual tests, the Linux-only tests, and the full gate's other steps (TLC, the Kennel's checks, the MSRV build, Miri, loom, the Windows build under Wine, the feature combinations, the fuzz-target check, the proofs, the Feature and Client listing checks). They run on the next full gate, a finished spec's pull request's, over the whole workspace; its stress run compares its head with the head of the last full gate, so the tests such a merge adds or changes run their 20 times there ([Before merge](flaky-tests-and-live-checks.md#before-merge)); its `perf` compares with `main`, which by then holds the change, so `perf`'s comparison with the base does not see what it moved. |
| `main` | The backstop, `just gate-backstop`, daily from the gate host's cron while it is switched on (`ci/gate-backstop.state`; off by ADR 0135's amendment of 2026-11-10 on the backstop's switch, [Commands](suites-commands-and-time-budgets.md#commands)), and the cron jobs of [After merge](flaky-tests-and-live-checks.md#after-merge); the nightly fuzzing, `just fuzz-nightly`, from the gate host's cron by the entry in `ci/fuzz-nightly.crontab` (#2454, [Fuzzing](security.md#fuzzing)); the Release suite on dispatch. | |

- **One `just quick` reports every failure.** Its steps, the lints' own included, all run even after one failed, and its summary names each failed step and its log ([Commands](suites-commands-and-time-budgets.md#commands)), so a ticket needs one fix round for all its defects, then one `just quick` on the fixed tree.
- **No check runs twice on one tree,** whoever ran it first: the agent, the pre-push hook or the merger. `ci/quick.sh` records each run of `just quick` on a clean checkout, green or red, in the gate's records every worktree shares (`quick-runs`, in the folder `ci/gate-records.sh` prints), by the layer that ran it: `pre-push` when the pre-push hook started it, else `quick`. Its result is that of the steps after the commit checks, since a red commit is mended by a rewrite that keeps the tree. A run whose key a green run already holds runs the checks of the change's commits alone, no lint and no suite, and `.githooks/pre-push` runs no `just quick` for a push whose heads such runs hold (`just _quick-held`), nor for a push to `spec/<n>`, whose batch runs it, nor for a push of a `batch/…` branch the hosted tier serves, with an open pull request to `main` while the pull-request workflow is active: the hosted run that push starts runs the Quick suite, and `just merge` reuses its units ([#3377](https://github.com/goodfetch/goodfetch/issues/3377)). The key is the tree, the form (`changed` or `all`), the merge base with the change's base, the host fingerprint and the variables a step reads, as the gate's (the step runner's own and the launcher's are not among them), within a day, and lint's other reads, the day and GitHub, read again as the gate reads them. A run on uncommitted changes is neither held nor recorded. A held run says nothing of the messages of the commits that hold it, since a reworded commit keeps its tree: the hook judges the sign-offs (`just dco`) and the subjects (`just commit-messages`) of the pushed commits on every push, and refuses the push on a red one before `just quick` runs. Such a commit is only mended by rewriting it, and a gate that ran on it then reuses nothing (ADR 0135's note of 2026-11-21). Both checks record each commit they judged green in the gate's records (`judged-commits`, in the folder `ci/gate-records.sh` prints), keyed by the commit and the check's rules, so `just quick`, `just batch-check` and `just merge` judge only the commits no layer judged green before, the gate's own merge of `main`'s tip among them, and say which they did not judge again (`note[judged-green-before]`). A red verdict is never kept (ADR 0135's amendment of 2026-11-22). The full gate runs no Quick suite of its own: its Pre-merge suite holds every Quick test. `just duplicate-runs` reads the gate's records and fails, naming both layers, on each unit a run ran on a tree where an earlier run had recorded it green ([Commands](suites-commands-and-time-budgets.md#commands)). After an edit, run again only what the edit can reach.
- **An unchanged check runs again once, and only after a diagnosed environment fault** (a full disk, a killed process, a timing failure on a loaded host), in a free slot, not under the same load: never to see whether a failure goes away ([No retries](flaky-tests-and-live-checks.md#no-retries)).
- **`just quick` reads the change against its base:** the commit the push's remote ref holds when the pre-push hook runs it and the push only adds the branch's own commits to it, else the branch's upstream off `main` when it is another branch (a ticket's integration branch), else `origin/main`. A ticket's quick gate covers its own change, not the integration branch's whole diff with `main`. After a rebase, or a merge of the branch's own base, the remote ref's commit is no base, since the change would hold every file the base gained: the hook says so in one line and `just quick` reads the branch against its own base (`ci/change-base.sh`).
- **The branch's own remote copy is never that base.** After `git push -u` a branch's upstream is the branch of its name on the remote, which holds its head: against it nothing changed, so no test would run and the run would still record its tree green. `just quick` reads such a branch against `origin/main` and says so; when the branch goes into an integration branch, name that branch in `GOODFETCH_QUICK_BASE`.
- **One heavy suite at a time per machine** (a build, database, end-to-end, benchmark or Pre-merge run), except that a batch's Pre-merge run goes alongside its `just batch-check`. **Implementers on one machine:** up to 6 run, whatever the load; the machine bounds their work instead. Their cargo builds and test runs share one job budget for the whole machine, about 20 jobs on the gate host: a build waits for a free job, and running tests count against the budget. The main checkout, the gate and the batch worktrees stay outside it. Start an implementer while memory does not swap and the disk has room for another build. A check that fails on timing reruns once, the failed tests only; a second timing failure within the hour lowers the budget by 4, never under 12. A timed run goes in the quiet share: while a measurement holds the machine, the measuring slot runs on 4 cores of its own and every other implementer on the rest (ADR 0135's note of 2026-11-21 on the job budget). Wait for a run through its completion notice, never through a `pgrep` or `sleep` loop.
- **A run has one implementer, which holds both ticket roles** ([ADR 0133](../adr/0133-agent-work-follows-the-matt-pocock-skills-as-written-and-the-fresh-review-is-retired.md)'s second note of 2026-11-11; [the Implementation loop](../agents/issue-tracker.md#implementation-loop)). It builds the spec's tickets one after another on `spec/<n>`, in one slot worktree, and at the end of each it runs the first row's checks on the ticket's commit, then pushes, which stands for the second row's merge. A push to `spec/<n>` judges the pushed commits' sign-offs and subjects, runs the static steps that take seconds, the floor guard over what each pushed head adds to `origin/main` (`just floor-guard origin/main <head>`) and, when the checkout's head is pushed, the module check (`xtask modules`), refuses the push on a red one, and runs no `just quick` (`.githooks/pre-push`): a miss of either would otherwise first show in a red `just batch-check`, whose rerun holds up the whole batch. Clippy stays in the batch: warm, over one touched crate, it took 24 seconds for xtask and 35 for `goodfetch-engine` (2026-11-23). The batch that holds the spec's pull request runs it once, against `origin/main`, on the combined tree that merges, so that tree passes every step each ticket's own `just quick` ran, and a red step is fixed on the spec's branch before the batch is built again. The limit above counts one implementer for each run and each relay.

_Why:_ Pre-merge runs by implementers, the hook's `just quick` on trees that had already passed and `just counts` before and after each ticket took the gate host thousands of minutes (ADR 0135's note of 2026-11-21 has the figures). A ticket's own `just quick` then still took 23 minutes of its 145, and `just counts` and `just compare` 13 more, on 11-22, while the batch's checks and its gate ran the same steps again on the combined tree (ADR 0135's note of 2026-11-23). The merge gate of the pull request to `main` still runs each of them once.
