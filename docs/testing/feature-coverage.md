## Feature coverage

Decided in [ADR 0072](../adr/0072-every-feature-in-a-generated-inventory-has-a-passing-test-and-code-coverage-and-mutants-are-signals.md). Coverage means every Feature has a passing test, never a percentage. Suites are those of [Suites, commands and time budgets](suites-commands-and-time-budgets.md); quarantine is that of [Flaky tests and Live checks](flaky-tests-and-live-checks.md).

### The Feature inventory

- **Never edit `features/inventory.json` by hand.** `xtask codegen` generates it from ADR 0037's matrix, `features/stories/`, `features/rows.toml`, `features/areas.toml` and the contracts the code defines, and `xtask codegen --check` fails on drift.
- **Every generator reads source files or Rust types in process.**
- **Write a Feature as `<kind>:<id>`.** Declared kinds: `row:` (an ADR 0037 matrix row that is not `excluded`) and `story:<area>-<n>` (a spec's user story). Generated kinds: `operation:`, `error:`, `event:`, `setting:`, `command:`, `exit:`, `format:`, `plugin-kind:`, `block-cause:`, `sink:`, `mcp-profile:`, `skill:`, `adapter:` and `integration:`.
- **A contract you add is a Feature in the same pull request,** and that pull request adds a test that declares it. The Quick suite fails until it does.
- **Never renumber or reuse a story ID.** A new story takes its spec's next number; a removed one stays with `status = "retired"` and a `reason`.
- **Give every declared Feature a milestone**, and every generated Feature an owning area through `features/areas.toml`.

### Declaring what a test proves

- **Declare a Feature only when the test asserts its outcome**, never one the test merely passes through.
- **Declare it in the runner's own idiom**, never by a file or name pattern:
  - Rust: `/// Covers: operation:run.start, error:run_not_found` on the test function, or `//! Covers: …` on a test module for every test in it; a long list wraps onto the doc lines below, each holding Feature IDs only, up to prose, a blank doc line or another attribute; on an rstest table, a `/// Covers:` line between `#[rstest]` or one `#[case]` and the next declares for the case below it only, as rstest gives that case the attributes written there, so each case declares the row it reaches; a `/// Covers:` line on a `fn` inside `prop_state_machine!` or `proptest!` declares for the test it expands to, and one inside any other macro fails the scan, which cannot read that macro's tests;
  - Vitest: the Feature ID as a tag, on the test or its `describe`, as written (Vitest's tag names accept `:` and `.`); `vitest.config.ts` declares every ID of the inventory through test support's `readFeatureIds`, with `strictTags` on, so an unknown one fails the run;
  - pytest: `@pytest.mark.covers("<feature id>")` or a module's `pytestmark`, under `strict_markers`;
  - Playwright Test: an annotation `{ type: "covers", description: "<feature id>" }` per Feature, on the test or its `describe`; `playwright.config.ts` passes the inventory's IDs, and test support's `test` fails a test whose annotation names an unknown one;
  - Journeys, conformance cases (each `cases.toml` under `conformance/`) and Client conformance cases (`conformance/clients/`): their `covers` list. A retired Journey declares nothing.
- **`xtask features scan` reads every declaration with its level**, from where the test sits: a `journeys` folder below `tests/` and a Journey's `covers` are `journey`; `conformance/` is `conformance`; `src/` and `tests/unit/` are `unit`; any other `tests/` folder is `integration`. Rust's lines, the Journeys and the conformance cases are read from source; the Vitest tags, Playwright annotations and pytest markers from the runners' listings (`xtask journeys listings`), which start processes, so the check reads them only in the Pre-merge suite.
- **A test that drives the protocol and declares an `operation:`, `error:`, `event:`, `command:` or `exit:` Feature must reach it.** The exercise audit reads `rpc`'s dispatch records and the engine's outcome records (the engine's structured log for the binary, the test `tracing` subscriber for in-process tests over the in-memory transport) and test support's command record, and fails a declaring test that never called the operation, received the Error code or event, ran the command or saw the exit code. An outcome record (target `goodfetch::run::outcome`, `Run::record_outcome`) names an Error code a Run recorded and no reply carries, such as a work item's `handler_lost`, so a test that asserts one from the run file reaches it. Under `just test pre-merge` or `release`, each test nextest runs leaves its exercise record in `target/test-records/`; `just features-audit` reads the tests that nextest's JUnit file shows ran (`target/nextest/ci/junit.xml` under the workspace, even where `CARGO_TARGET_DIR` puts the build elsewhere, as in CI's VM), and fails when tests left records but no JUnit file names them; the suites run it as a gate ([The checks](#the-checks)). `just features-audit all` judges every declaring test, run or not, for a local look. A declaring test with no record fails, as does one whose record never shows its Feature, and any test whose record holds a command whose arguments named no `command:` Feature (`command-unmatched`); only a test whose record holds no dispatch record at all, or a unit test that left no record, may declare the `error:` or `event:` it asserts itself. A test above the unit level must leave a record, and a test whose record shows it dispatched is judged on every declaration, unit test or not. An in-process test reaches the record through its crate's helper that serves the engine on the in-memory transport (`goodfetch-engine`'s `attached_with`, `goodfetch-crawl`'s `crawl`), which installs the test subscriber unless the test installed its own. The engine's log is lossy (ADR 0122), so a killed engine loses the lines its writer's thread had not written yet, the dispatch records among them: a test's Client of an engine that does not exit by itself records the calls it read answered in the test's answer record (`goodfetch_test_support::AnsweredCalls`: `sent` and `read` on each message, `record_in(env.folder())` once the engine is killed or left to teardown), which teardown copies into the exercise record after the command record. Collie's and Foxhound's `Attached` helpers do it; any other Client that kills an engine does it too, or reaches what it declares on an engine that exits as it should. `env.exercise_lines()` gives the lines teardown will copy, as they stand (#1779).
- **A test that never reaches `rpc` may declare the `error:` or `event:` Feature it asserts,** but must assert the Error code or the event itself: a unit test of a module's own error, or a `tests/it` test of a module that binds a socket, such as the Browser cache's downloads against a loopback stand-in. The audit can't see it, so it is a review standard. A declaration the audit finds unreached is fixed by reaching it, or by moving or removing it, never by widening this rule. A test of a command the executable answers without `rpc`, such as `runs reindex`, never declares an `operation:` of the same name.

### What counts as tested

- **Every Feature is tested, excepted or untested.** The gates fail only on untested Features.
- **A Feature is tested** when, on `main`'s latest Release suite run (while the repository is private, `main`'s latest commit whose cells have all run, across dispatches: [ADR 0108](../adr/0108-while-the-repository-is-private-the-release-suite-runs-its-macos-cells-on-the-owners-machine-and-its-hosted-cells-under-a-ceiling.md)), at least one test declares it, every declaring test ran and passed in every configuration it runs in, none is quarantined, every declaring Journey's variants of reached milestones are `proved`, and every declaring conformance case's capability is `proved`.
- **A story with `journey = true` also needs a proved variant of a Journey that covers it,** and every story needs a declaring test above the unit level ([Which stories need a Journey](which-stories-need-a-journey.md)).
- **Test a Feature once.** The per-surface completeness and conformance of [SDK and CLI tests](sdk-and-cli-tests.md) and of the surface ADRs, and a Journey's variants, prove each surface.
- **Once, not once per Product.** The inventory records the Products that carry each Feature, from ADR 0087's generated table of Foxhound's names, and `xtask features report` gives each Product's view.
- **A quarantined test leaves every Feature it declares untested** until its fix merges.

### Exceptions

- **List a Feature no pinned test can prove in `features/exceptions.toml`;** it is then excepted, never tested. Give it its `evidence` (`manual`, `live`, `check` or `none`), a `reason` and a `link` to the owner-test step, Live check, CI job or place where it is tested.
- **Never except a Feature a pinned test can reach.** The release pull request lists every exception, and the owner test lists the `manual` ones as manual steps.

### The checks

| Check | Suite or gate | Fails when |
|---|---|---|
| Feature check | Quick, over Rust's, the Journeys' and the conformance cases' declarations (a generated Feature none declares is only noted); Pre-merge, `just features-tests`, over every runner's | the inventory is stale, a declaration names an unknown or retired Feature, a generated Feature has neither a declaring test nor an exception, a non-excluded matrix row has no milestone, a generated Feature has no area or two, or an exception is incomplete or names a Feature a test also declares |
| Exercise audit | Pre-merge (tests that ran), Release (each cell's tests that ran: all but the quarantined ones and those the cell cannot run) | a declaring test never reached its Feature |
| Milestone gate | the owner test (ADR 0058) | a generated Feature, or a declared Feature due at the milestone, is untested (neither tested nor excepted) |
| Release gate | `xtask release` | a Feature present in the release is untested (neither tested nor excepted) |

- **Run `just features`** to see what the changed packages declare and miss, `just features-tests` for the check over every runner's declarations, and `just features-audit` after `just test pre-merge` for the exercise audit of the Rust tests that ran.
- **The suites run the exercise audit as a gate, the justfile's `exercise_audit` verdict:** `just pre-merge` and CI's `pre-merge` job, `just release` and each Release cell, each over the tests its nextest run ran, so a quarantined test (ADR 0064) or one a cell cannot run, which leaves no record, never fails it; a finding fails the suite. `just pre-merge` runs it after a red nextest run too: the Pre-merge suite still runs the doctests then and fails with 100 when they passed, the audit runs on that 100, and when it passes the incremental gate records green each crate that passed in full but those holding insta snapshots, whose unreferenced snapshots cargo-insta judges only once every test passed (the test-gate audit's option 4b). The step stays red. `just features-audit <scope> report` lists the findings and fails nothing, for a local look.

### The report

- **`xtask features report --milestone <M> --store <store> --listings <folder> --out <folder>`** writes `features.json`, for agents, and `features.html`: each active Feature tested, untested by cause, excepted by evidence kind or planned at milestone `M`'s gate, with its declaring tests and their outcomes, and each Product's view by area and by due milestone. Its `gate` and its last line give the milestone gate's state: ready only when the store holds a Release run of `main` and no Feature due at `M` is untested on it, with the untested Features' IDs. It fails no gate. The daily test-health job builds it at the gate of the next owner test, writes its lines to the job summary and attaches both files to its run.
- **Due:** a generated Feature at every gate; a declared one at its milestone; a story with `journey = true` at the later of its milestone and the earliest milestone of a variant of a Journey that covers it (ADR 0075). A declared Feature not due yet, or with no milestone, is planned.
- **Results:** `main`'s latest Release run is the newest commit of `main` on which every cell of the Release matrix has a test run in the store, across dispatches (a commit some of whose cells have not run is not read, ADR 0108); each test's newest run per configuration on it counts, and a skipped or inconclusive one is not run. A Journey's declaration stands for its variants due at the gate, each as the Journey report judges it from the result documents the run kept: `proved` passes, `failed` and `rejected` fail, `unproved` is not run, and one a quarantined test carries is quarantined. A conformance case's declaration counts as the `conformance` documents the run's cells kept give the case (`<suite> <case id>`), the worst across cells, and is not run when none holds it; the conformance suites' tests keep theirs as `conformance-<suite>-<product>-<mode>.json` in `GOODFETCH_TEST_RESULT_DOCUMENTS`, and each part of a suite run in parts as `conformance-<suite>-<product>-<mode>-<part>.json`.
- **Causes, the first that holds:** `no-test`; `failed`, `quarantined` or `not-run` for a declaring test that is no Journey variant; `no-test-above-unit-level` for a story; `no-covering-journey` for a flagged story with no proved covering variant; then `failed`, `quarantined` or `not-run` for a declaring Journey's variant.

### Code coverage and mutation testing

- **Never gate on a percentage:** no `--fail-under-*`, no coverage or mutation score in any check, badge or pull request, and no coverage service. The Quality register's `coverage.project` ratchet opens an issue on a fall and fails nothing.
- **The coverage job runs in no suite** on Linux x64, weekly (nightly once the nightly tier is on): cargo-llvm-cov over nextest and over every run of the instrumented binary through `show-env`, Vitest's `v8` provider on Node and in Browser Mode, coverage.py with branches. While the repository is private, it has a 60-minute timeout and runs only while the month's count toward the ceiling of [Flaky tests and Live checks](flaky-tests-and-live-checks.md) is below 550 minutes; a skip says so in its job summary. Its results never decide a Feature's status: its step is no test step, and its JUnit files carry the runtime `instrumented`, a configuration of their own in the results store. It attaches its three reports to the run as `coverage-report` (`.github/workflows/coverage.yml`), and its `compare` job, which holds the issue token and runs none of the product, compares them with the [Quality register](../../TESTING.md#quality-register).
- **Run `just coverage`** for the Pre-merge suite's tests of what changed (`just coverage all` for the whole workspace, as the job runs): every workspace crate is built for coverage into a target folder of its own, test support's map passes `LLVM_PROFILE_FILE` to every executable a test starts, and the reports go to `target/coverage/rust/`, `vitest/` and `python/`, written even when a test fails: every runner still runs after another one fails (`GOODFETCH_TEST_KEEP_GOING`, which `just coverage` sets for `just test`), the Rust report leaves out a profile llvm-profdata cannot read and names it, and the run ends by listing its failed tests.
- **Read coverage for gaps.** A function no test executes that hides a behaviour with no Feature gets a story, a Feature or a test.
- **Every pull request that changes Rust code runs cargo-mutants `--in-diff`** with nextest on Linux x64, sharded within the 15-minute job budget, in a job that never fails on a survivor and is not part of "all green". While the repository is private, it runs on the owner's machine with the pull-request tier, using no included minutes, so neither the four-shard cap nor the 550-minute threshold applies to it ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)). The `affected` job counts the change's mutants and gives the `mutants` job one shard per 4 (`ci/mutants.sh`); each shard writes its surviving mutants to its job summary and attaches its report as `mutants-<k>`. Run `just mutants` for every mutant of your branch's committed Rust changes at once: it writes each mutant into the working tree and takes it out again. Neither mutates what `xtask codegen` writes: `.cargo/mutants.toml` excludes every `generated/` folder and `generated.rs` (ADR 0099).
- **List each surviving mutant of your changed code in the Evidence section,** with the test that now kills it or why it stays (an equivalent mutant; caught only by a doctest, by a Journey in another runner, or by another OS's test).
- **Full mutation runs are weekly once the nightly tier is on:** cargo-mutants over the workspace, and `just mutants-sdks` over the SDKs' hand-written runtimes on Linux: StrykerJS with its Vitest runner on the TypeScript SDK (`sdks/typescript/stryker.config.mjs`), and mutmut on each Python SDK package (its `pyproject.toml`'s `[tool.mutmut]`). A surviving mutant fails neither run. Neither mutates what `xtask codegen` writes: both configs leave out every `generated/` folder (ADR 0099). Both reach the programs a test starts, which run the mutant and count what they cover for that test: a Node program started through test support's process record, and a Python program started with the runner's environment or test support's `test_env` map (`--mutation-children`). Both skip the tests on the quarantine list, as `just test` does. StrykerJS 10.1.0 fixed [stryker-js#6210](https://github.com/stryker-mutator/stryker-js/issues/6210), so an in-diff pull-request job for the TypeScript SDK comes next (#3192).
