## Flaky tests and Live checks

Decided in [ADR 0064](../adr/0064-tests-are-never-retried-and-unpinned-checks-run-as-live-checks.md). The Quick, Pre-merge and Release suites and the CI tiers are those of [ADR 0061](../adr/0061-three-test-suites-each-run-by-one-just-command-under-a-time-budget.md).

### What is a test

- **A test pins every input:** commit, Proving ground seed, `Entropy` seed, browser build, images by digest, recorded model exchanges. A **flaky test** passes and fails with the same inputs.
- **A check with an input that moves without a commit is a Live check.** It never goes in a suite.
  _Why:_ a vendor's change or outage is then never mistaken for a broken change.

### No retries

- **Runners keep zero retries with every lock on:** nextest `retries = 0` and `flaky-result = "fail"` in every profile, with no per-test override; Vitest `retry: 0` with no per-test `retry`; Playwright `retries: 0` and `failOnFlakyTests: true`; no pytest rerun plugin and no `flaky` marker.
- **No workflow step retries a test:** no retry action, no shell loop, no `continue-on-error` on a test step.
- **No test loops until it passes.** Wait on a condition with a deadline (auto-waiting, `expect.poll`, a CDP event, a state you can name); never repeat the action under test until it succeeds.
- **The no-retry check in the Quick suite (`xtask no-retry`) refuses all of the above**, and the flags and variables that undo them (nextest `--retries`, `--flaky-result`, `NEXTEST_RETRIES`, `NEXTEST_FLAKY_RESULT`; Vitest `--retry`; Playwright `--retries`; Chromium's `--test-launcher-retry-limit` other than 0, a gtest run without it, and `--num-retries`; wptrunner's `--retry-unexpected` above 0, `--rerun` above 1 and `--repeat-until-unexpected`; typ's `--retry-limit` and `--isolated-script-test-launcher-retry-limit` other than 0, `--retry-only-retry-on-failure-tests`, and a `RetryOnFailure` expectation). Downloads before the deny of ADR 0043 may retry: they test nothing.
- **Re-run a failed job only when no test step failed in it** (lost runner, failed download). The "all green" job fails when an earlier attempt of its run had a failed test step. **Name every step that runs a suite or a test runner starting with `Test`** (`Test: just test quick`, `Test: Miri on opted-in unsafe code`): that prefix is how "all green" tells a test step, and `xtask no-retry` refuses a step that runs a runner, `just test`, `just repeat` or `just miri` under another name.
- **Never assert elapsed real time, a rate or a duration.** Those are measurements.

### Before merge

- **Every new or changed test runs 20 times in the pull request**, and one failure fails it. New: absent from the base commit's listing, so a renamed test too. Changed: its file changed, plus the tests Vitest's `--changed` and Playwright's `--only-changed` reach through their imports. The run is sharded to fit the budget, with the Pre-merge job's shards (one while that job is one); the count is never lowered, and nothing skips it. A red run stops at the end of its first red iteration, since one failure has already failed it: a green run still runs every iteration. A test still on the quarantine list is not run, as in every suite.
- **Taking a test off the quarantine list takes 200 passing runs** in that pull request.
- **The stress run is `just stress [base]`**, the Pre-merge job's `Test: just stress` step. `xtask stress select` compares each runner's listing at the head (`cargo nextest list --message-format json`, `vitest list --json --staticParse=false`, which loads each file so that each `test.for` and `test.each` case is listed under the name it runs as (so the listings get the suite and test tool manifest variables `just repeat` runs with), `playwright test --list --reporter=json`, `pytest --collect-only -q`) with the base's. The cache-warming job saves the four listings of each `main` commit in the build cache (`xtask stress listings`, under the target folder's `stress-listings/<commit>/`); a base with none is listed from a checkout of it in the same job, which installs the base's own npm packages and Python environment from its lockfiles (`pnpm install --frozen-lockfile --prefer-offline` and `uv sync --frozen --all-extras`, from the package store and uv cache `just fetch` filled), so its Vitest and Playwright configs and its pytest tests import its own workspace packages, not the head's. Each count's runs go through `just repeat --until-red` (a parameterized pytest case by the node ID of each of its runs, `test_x[a-1-20]` …, which pytest-repeat names), and their JUnit files to `target/junit/repeat-<count>/`, which the ingest reads as run that many times. A test the base's listing holds and the head's does not fails the selection before any test runs, unless a `Quality-change` trailer of the change names its ID ([Floor](../../TESTING.md#floor)); its finding and each trailer's note go to stderr, since stdout is the selection.
- **A full gate's stress run covers the tests merged since the last full gate** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendment of 2026-11-10). A change a test reads that merged on the quick gate had no stress run, and `main` holds it by the next full gate, so that gate's stress run compares its head with the head of the last full gate instead of its own base: the nearest head `main` holds whose record in `just merge`'s `target/gate-runs/` shows that its stress run passed, each workspace member green. `xtask gate plan` prints it as `stress.base`, and `ci/pre-merge.sh` hands it to `just stress` as `base`, in a full run and in a narrowed one. The tests such merges added or changed then run their 20 times there, a test they took off the quarantine list its 200, and a test they deleted fails the selection unless a `Quality-change` trailer of a commit since that head names it: the deleting pull request's, or the gated one's. A full gate whose stress run was red, or stopped before it ended, is passed over for the one before it, and a record on a head of the gated pull request itself moves nothing: its own tests are new since its base. The base stays the change's, and the selection is as before, with no such record, when no test reads what `main` gained since that head (`xtask affected`'s `gate=docs` or `gate=quick` for it, so the base's saved listings still serve), and for a run on `main` itself, as the backstop's. `perf`'s comparison with the base still does not see what a quick merge moved.
- **Tests run in random order, seed printed:** pytest-randomly (`-p randomly --randomly-seed`), Vitest `sequence.shuffle` with `sequence.seed`, Playwright `--shuffle` with `fullyParallel`, each runner's arguments printed by `ci/order-arguments.sh`, which every recipe and Release cell passes and xtask's order-seed tests run twice on one seed and once on another; nextest runs each test in its own process. The seed is the first 8 bytes of the tree hash under test, read as an unsigned integer, as `ci/order-seed.sh` prints it, in every run but the constrained test-health run, which takes a fresh one; Vitest takes its low 53 bits, the most its shuffle can count up from. Pass it back as `GOODFETCH_ORDER_SEED` to reproduce an order.
- **Vitest resets shared state:** `restoreMocks`, `unstubEnvs` and `unstubGlobals` are on, only as a safety net: `vi.stubEnv` and `vi.stubGlobal` stay banned ([Writing a test](writing-a-test.md)).
- **Leaks and hangs fail:** nextest's leaky result is `fail`, every test has its suite's hang timeout, and the constrained test-health run runs Vitest with `detectAsyncLeaks`.
  - **`just` runs nextest with `NEXTEST_DOUBLE_SPAWN=0`;** export it too when you run `cargo nextest` yourself on macOS.
    _Why:_ on macOS under load, a test that started no process failed as leaky when nextest started it through its double-spawn stub: its output pipes stayed open past the 200 ms leak timeout after it exited, even with one test at a time. Started directly, it never did. On Linux the stub made no difference: there, such tests failed as leaky only with many tests at once on a CPU-starved host, as often with the stub as without, and never with one test at a time. The stub only guards against a hang when Ctrl-Z stops the runner, so the setting costs nothing on either platform.
  - **The gate host runs a nextest built from [nextest-rs/nextest#3686](https://github.com/nextest-rs/nextest/pull/3686),** installed as `~/.cargo/bin/cargo-nextest` by `cargo install --locked --git https://github.com/nextest-rs/nextest --rev 3b1f99691c0da30eae70d6bd748f6f6723d4c832 cargo-nextest` (it reports itself as 0.9.150). The stock release stays beside it as `~/.cargo/bin/cargo-nextest.0.9.149`: to go back, copy that file over `~/.cargo/bin/cargo-nextest`. Issue 2776 stays open until the gate host runs the first nextest release that includes #3686. The CI image and the host-tools action keep their pinned release: the Linux gate runs nextest on the host, not in the image, and hosted runners share their machine with no other build.
    _Why:_ on Linux, nextest 0.9.149 holds no lock while it starts a test. A `posix_spawn` child that nextest clones for one test while another test's capture pipes are open keeps their write ends until its own `execve`. When the other agents' builds starve nextest of CPU, that child can wait more than the 200 ms leak timeout, and the other test fails as leaky. A wrapper that logged every holder of a test's pipes still open 50 ms after the test exited caught 8 such tests in the extractor, page and crawl crates: each holder was `cargo-nextest` or a child it had cloned before its `execve`, never the test's own process. With 32 busy loops, each started by `setsid` in a Linux session of its own, stock 0.9.149 failed 25 distinct tests as leaky in three runs of the unit tests of the seven crates in #2776. With the build from #3686, which holds one lock across the pipes' creation and the spawn, none failed as leaky in 15 such runs, and each run took within 13% of the stock build's time under the same load. The same 32 loops in a single Linux session left stock 0.9.149 with no leaky test, because the scheduler gives all of one Linux session's processes one share of the CPU. No test of #2776 holds its own output: traced with `strace -f`, 15 of its 16 leaky tests start no process, and the 16th, the engine's preamble case, starts only the sandbox probe, whose standard streams are null and which it waits for.
  - **The leak timeout stays 200 ms.** On Linux, at the mutation run's settings (nice 10, four tests at once, host load up to about 50), every test of `just mutants`' baseline closed its output within 5 ms of exiting, a 40-fold margin, and six whole baselines had no leaky failure. A leaky failure there is a real leak: name the process that holds the test's output before you raise the timeout.

### After merge

- **Every runner writes JUnit XML in every tier and attempt, pass or fail.** An ingest workflow, which runs none of the product, copies it to the results store: the `test-results` repository beside the main one (private until it is public), one compressed file per run attempt, with a record per test run (test ID, runner, suite, tier, job, OS, architecture, runtime, shard, commit, tree hash, run, attempt, outcome, duration, order and `Entropy` seeds). Nothing is pruned. While the repository is private, the ingest runs after each run of a workflow with a hosted job only, and one daily hosted ingest job copies the runs that ran only on the owner's machine, such as the pull-request tier's ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)), so their flaky tests are found a day later.
- **The store's files and their records** (`xtask results ingest`, `.github/workflows/results.yml`): `runs/<year>/<month>/<run>-<attempt>.tar.gz`, by the month the attempt started, holding `run.json`, `test-runs.jsonl`, `jobs.jsonl` (each job's labels, runner OS and duration) and `junit/<artifact>/…` as written. An artifact belongs to an attempt when it was uploaded after the attempt started. A test's ID is its runner's (the quarantine list's), its runner comes from the JUnit file's name (`nextest-ci.xml`, `vitest-node24.xml`), and the file's suffix after a Vitest, Playwright or pytest runner joins the artifact's runtime. **Every job that uploads JUnit runs `ci/junit-context.sh` first**, pass or fail: it writes `context.json` beside the JUnit files with the commit and tree the job tested, which each test run is recorded under (a run's head may be another commit), the job's ID, the order seed (`ci/order-seed.sh`), the `Entropy` seed (`GOODFETCH_ENTROPY_SEED`) and, after `just repeat <count>`, the count, without which the ingest refuses the artifact. A job whose tests ran different counts of times, as the stress run's 20 and 200, puts each count's JUnit files in a `repeat-<count>/` folder instead. Only hosted jobs hold the store's token, the Actions secret `TEST_RESULTS_TOKEN`: the ingest, the test-health jobs, the diagnostic run's `select` job and the Release suite's `budgets` job. It is a fine-grained token on the `test-results` repository: the jobs that only read the store need Contents: Read, and only the ingest, which pushes, needs Contents: Read and write. Nothing falls back to `github.token`, which cannot read another private repository. It never reaches the owner's machine.
- **Allure Report 3 shows the history,** built from the store by the daily test-health job (`xtask results allure`, then `allure generate`): each test's latest result per configuration, and one history point per run attempt with its status and duration.
- **A test is flaky when** it passed and failed on the same tree hash and configuration, or when a diagnostic run passes it at least once: 20 more runs at the same commit and on the same OS, after a failure in the merge queue, a manual-dispatch Release run, the nightly tier or a test-health run. A diagnostic run never changes a verdict. The scan (`xtask results scan`, after each ingest) finds both, since a diagnostic run's results share the failed run's tree and configuration, and keeps one issue per flaky test, found again by a marker line in its body. `.github/workflows/diagnostic.yml` runs each failed test (at most 20 a run) in a job of its own, through `just repeat 20 --test <runner>=<test ID>`.
- **Test health runs from M1 on, even while the repository is private, with no paid resource:**
  - the **daily test-health job** (scheduled, Linux, `main`'s head, 15-minute timeout) runs the 10 oldest quarantined tests 50 times each, then the scan and the Allure report; `just reports <store>` lists every runner's tests and writes the [Feature report](feature-coverage.md#the-report) and the Journey report into the results store under `reports/<date>/`, and is off while ADR 0135 keeps the workflow off (below);
  - the **constrained test-health run** (weekly and after each manual-dispatch Release run, Linux, 120-minute timeout) runs the Pre-merge suite with half the runner's CPU and memory, a fresh order seed and `detectAsyncLeaks`;
  - these and the diagnostic runs share a ceiling of 1,000 included minutes a month, counted in the Linux-equivalent minutes of [Suites, commands and time budgets](suites-commands-and-time-budgets.md). A diagnostic run of a cell on the owner's machine runs there and counts nothing. At the ceiling, constrained and then diagnostic runs are skipped until the month ends: `xtask results ceiling`, run before each, counts the month's jobs of `test-health.yml` and `diagnostic.yml` from the store (each job's minutes rounded up) and admits a constrained run only while its 120 minutes fit, and a diagnostic run while the 10 minutes of each of its hosted jobs do (`--jobs`); a skip goes to the job summary. The coverage job of [Feature coverage](feature-coverage.md) counts toward it too, and starts only while the month's count is below 550 minutes, so a run that starts just below can pass 550 by up to its 60-minute timeout; the in-diff mutation job runs on the owner's machine while the repository is private (ADR 0135), so it counts nothing and never stops.
  - Once the nightly tier is on, both run every night with no ceiling.
- **While GitHub Actions runs the Release suite alone** (the owner's decision of 2026-10-21 in [ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md), which disables every other workflow), each suite above runs where this list says, and the owner's approval of 2026-11-04 to fix every gap the test-gate audit found ([#2090](https://github.com/goodfetch/goodfetch/issues/2090)) keeps the rest off until Actions or the nightly tier is back:
  - **the constrained test-health run** runs only by hand, within its 120 minutes, in the backstop's gate worktree: `just test-health constrained` (`ci/test-health/scheduled.sh`). The gate host's cron ran it weekly until the owner's decision of 2026-11-19 in ADR 0135. Its egress deny stays the hosted job's alone;
  - **ADR 0072's mutation testing** is written for the same cron, daily, within 150 minutes, and its entry in `ci/test-health.crontab` stays uninstalled since 2026-11-13: `just test-health mutants`, `just mutants` over the Rust `main` changed in the last 24 hours. A surviving mutant fails nothing; the report is kept in `~/test-health/<day>-mutants/`. The in-diff job of a pull request runs nowhere: `just merge` does not run it. Either run skips while `just merge`'s gate runs, with `<run>=skipped (the merge gate is running)` in `~/test-health/results.txt`, as it skips when the disk lacks room, its build's or the 5 GB its tests' folders need where `TMPDIR` is (#2664). The 5 GB is a measured peak with room to spare: a browser-backed test's folder links the pinned Chrome for Testing build rather than copying it, from Playwright's files or, where the system refuses that link (root's `/ms-playwright` on the gate host), from one copy laid out in `TMPDIR` (`goodfetch-chrome-for-testing-<build>-<platform>`, 421 MB, kept for later runs), so a failed test's kept folder holds about 4 MB instead of 400 (#2664). Measured on 2026-11-15 on the gate host, at a load of 9 to 17, by sampling `du -sb` of a fresh `TMPDIR` each second through a filtered run (`cargo nextest run -p goodfetch-foxhound -E 'binary(it) & test(/^(fetch_tiers|decoding|discovered_api|content_types|browser|browser_fetch|light_browser)::/)'`, 53 tests, 40 of them failed and kept their folders): a peak of 596 MB, the build's copy included. A lock whose holder ended stops neither. A gate started during a run waits for it to end, saying so on its output;
  - **nothing runs after a quick merge**: what a quick merge skips, `just counts` and the Pre-merge suite included, runs on the next full gate, a finished spec's pull request's (the owner's decision of 2026-11-18 in ADR 0135, which removed the post-merge run each gate started as it ended);
  - **the coverage job** is off (`coverage.yml` is disabled); `just coverage` still runs by hand, and nothing compares the Quality register's Project coverage row;
  - **the ingest and the flaky-test scan** are off (`results.yml`, `test-health.yml` and `diagnostic.yml` are disabled), so no run reaches the results store, no `flaky-test` issue opens, and no diagnostic run follows a failure;
  - **the daily reports** are off: `just reports <store>` runs from no cron (neither the gate host's crontab nor `ci/test-health.crontab` holds it), and the `test-results` store it writes into does not exist, so no Feature or Journey report is written; it runs by hand once the store exists;
  - **quarantine** is enforced but fed by nothing: `xtask quarantine check` still refuses a bad entry and every suite skips the listed tests, but no scan finds a flaky test to list, and the daily 50 runs of the oldest entries do not run;
  - **CodeQL** is off, as it is until the repository is public ([Other rules](security.md#other-rules)): running the CodeQL CLI on a private repository needs a paid GitHub Code Security licence, declined while Goodfetch has no revenue ([ADR 0076](../adr/0076-tests-and-ci-run-on-free-tiers-and-ai-calls-go-through-the-vercel-ai-gateway.md)).

### A flaky test found after merge

1. CI opens (or reopens) one `flaky-test` issue for it, a sub-issue of the spec that owns the test, in the milestone of that spec's ticket that added it ([ADR 0136](../adr/0136-each-implement-spec-run-is-one-whole-spec-and-milestones-are-ticket-metadata-and-owner-checkpoints.md)). Until [#1719](https://github.com/goodfetch/goodfetch/issues/1719), `xtask issues` still files it in the earliest open milestone with an open issue.
2. The same day, add the test to the quarantine list with its issue, in a pull request of its own. The quarantine, not the fix, keeps the gates green: the fix waits its turn and never goes ahead of Features' work ([the rollout order](../agents/rollout-order.md)).
3. If the test or the code it covers changed in the last 7 days, you may also revert that change: revert the product code, and the tests stay quarantined.
4. Fix the cause. A longer timeout alone, a sleep or a retry is not a fix. A race or leak in the product is fixed in the product, and the test stays as it was.
5. The fix takes the test off the list after 200 passing runs; the issue closes when it merges.

- **A flaky or timing fix's acceptance asks for three things:** the cause named and removed, one normal run of the test, then the gate, whose stress run gives a test leaving the list its 200 runs. No issue asks for runs under artificial load (`stress-ng`, busy loops) or a count of runs in a row: `just load-proofs <issue>` refuses such an acceptance criterion or task-list item, before the issue takes `ready-for-agent` and before a run or relay takes it (owner, 2026-11-18, « Tu ne fais plus ça »).

- **The quarantine list is one file in the repository**, `quarantine.toml` at the root (upstream Chromium tests the Chromium build gate excludes are not on it: see [Goodfetch Chromium's expected results](goodfetch-chromium.md#expected-results)). Each entry has a test ID, its open `flaky-test` issue and a date; the Quick suite's check (`xtask quarantine check`) refuses an entry without an open issue or naming a test that no longer exists. Every suite command skips the listed tests through its runner's own filter (`xtask quarantine exclude`). An entry is a `[[test]]` table:
  - `runner`: `nextest`, `vitest`, `playwright` or `pytest`;
  - `id`: the test's ID as its runner lists it: nextest's `<binary ID> <test name>` (`goodfetch-engine::it dispatch::route_waits`), Vitest's full name with its suites joined by ` > `, Playwright's file, suites and title joined by ` › `, pytest's node ID. nextest skips by name, so a name that is part of another test's name is refused;
  - `issue`: the number of its open `flaky-test` issue;
  - `date`: the day it was quarantined (`2026-10-18`).
- **Quarantined tests still run** 50 times a day in the daily test-health job (the 10 oldest entries), into the results store: `just repeat 50 --quarantined 10`.
- **A quarantined test blocks** (unlike an upstream exclusion of [Goodfetch Chromium's expected results](goodfetch-chromium.md#expected-results)) its milestone's gate, every release (`xtask release` refuses while the list is not empty), and counts its feature as untested.
- **A flaky test is never removed or weakened to make a suite pass:** quarantine it, fix it, or replace it with a test covering the same behaviour (for example by moving its unpinned part to a Live check).

### Live checks

- **Each Live check has an owning area and a placement** listed in ADRs 0064 and 0065 (the live-model checks): real SaaS Sinks, installed Chrome's stable, beta and dev channels (pinned majors are tests), public testnets, the Clean-up rules' daily gate, the online conformance, the benchmark, the Performance series (ADR 0071), the Cloud Run deploy, live-model evaluations, Scorecard; and, from ADR 0070, the newest MCP conformance suite, Inspector and SDK clients, each agent framework's newest releases, the n8n scanner on the published node, and real Integration platform accounts; and fuzzing (ADR 0067); and, from ADR 0068, the docs site's `docs-external-links` (nightly, or before each release candidate while the nightly tier is off) and `docs-deploy-smoke` (after each production deploy), which block nothing directly ([Browser tests and the docs site](browser-tests-and-the-docs-site.md)); and, from ADR 0073, `screen-reader` (nightly, or before each release candidate while the nightly tier is off), blocking nothing directly; and, from ADR 0074, the Chromium patch preview and the Chromium build currency, owned by area 8, which block nothing directly ([Goodfetch Chromium](goodfetch-chromium.md)); and, from ADR 0089, `lend-libraries-newest` and `crawler-examples-newest`, owned by area 11 (nightly, or before each release candidate while the nightly tier is off), which block nothing directly ([SDKs](sdk-and-cli-tests.md#sdks)); and, from [ADR 0097](../adr/0097-one-docs-site-renders-each-products-section-from-one-source-and-neither-product-leads-with-access.md), `migration-guides-current`, owned by area 11 (nightly, or before each release candidate while the nightly tier is off), which fails when a migration guide's competitor has a newer major, or a newer minor at `0.y`, or a newer patch at `0.0.z`, than the one pinned (a pin its manifest marks as held is checked within its own major, or its minor at `0.y` and its patch at `0.0.z`, and fails when its reason lapses), and blocks nothing directly.
- **Security advisories:** the gate's `just audit` checks every lockfile the repository holds offline (not the lock a server `just compare` installs with `cargo install --locked` ships inside its crate, fastCRW's) against the snapshot `ci/advisories.toml` pins, so only a commit moves its verdict; the newest RustSec, npm and PyPI advisories are the live advisory audit's, `just audit-live`, daily on `main` (from the server's cron while the hosted workflows are off), which blocks nothing directly (ADR 0064's note of 2026-10-22).
- **Outcomes are pass, fail or inconclusive.** Inconclusive means the external side was unavailable; it never counts as a pass.
- **Results go to the results store** under the `live` tier, except fuzzing's, which stay private ([Security](security.md#fuzzing)). A Live check writes JUnit like a test, and a skipped test case is its inconclusive result. Declare each Live check with its owning area in `ci/live-checks.toml`; the scan names the area in the issue's title and fails on an undeclared one.
- **A fail, or three inconclusive runs in a row, opens or updates one `live-check` issue**, a sub-issue of the spec that owns the Live check, in the milestone of that spec's ticket that added it (ADR 0136; until #1719, `xtask issues` still files it in the earliest open milestone with an open issue). If its cause is not stated within two business days, the next minor is not promoted until it is. Patches are not held, and the online conformance never blocks (ADR 0043). Fuzzing opens no `live-check` issue: its crashes stay private and block the next minor until fixed ([Security](security.md#fuzzing)).
- **A `live-check` issue closes** once its cause is written down and either fixed or attributed to an external party with a linked upstream report, so an explained vendor outage never holds a milestone gate.
- **A measurement declares its trials, threshold and statistic before it runs,** and every trial counts. A failed trial is never replaced.
