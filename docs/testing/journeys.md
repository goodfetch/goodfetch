## Journeys

Decided in [ADR 0063](../adr/0063-end-to-end-tests-follow-a-catalog-of-numbered-journeys-kept-in-the-repository.md). A Journey is a goal a person reaches through Goodfetch's public surfaces; Journeys are the end-to-end tests.

### The catalog

- **One Journey per file, `journeys/J-NNN.toml`**, validated by `journeys/journey.schema.json`, which `xtask codegen` emits. Unknown fields fail.
- **A new Journey takes the number in `journeys/catalog.toml`** and increments it in the same pull request. If another pull request merged the same number first, take the next one.
- **Never change an ID on `main`, and never reuse one.**
- **Never change a Journey's `goal` under its ID.** Fix wording, steps, data or surfaces freely; for a different goal, set `status = "retired"` with `reason` and `replaced_by`, keep the file, and add a new Journey.
- **Write `goal` with RFC 2119 words**, readable as a specification without the code.
- **Write steps declaratively** ("export the Dataset as CSV"), never as clicks or flags, so the wording survives a change of implementation. Pin a step with `on` only when the goal needs that surface; give `manual` a reason only when no automated check can do it.
- **List every surface on which a person can reach the goal**, each with the milestone by which it must be proved, never earlier than the surface ships.
- **Name the Journey's `product`:** `collie` when Collie carries every step, `foxhound` otherwise. Its surfaces are that Product's.
- **A Collie Journey with a `cli` surface also runs as `J-NNN@foxhound-cli`:** the same test, given Foxhound's executable, in the same suites. It is the only variant that names a Product.
  _Why:_ it shows end to end that Foxhound's executable keeps Collie's behaviour, where the other containment checks show only that Collie's definitions are there.
- **Fill `covers` with Feature IDs** (`row:CO-18` for an ADR 0037 row; every kind is in [Feature coverage](feature-coverage.md)).
- **Keep a Journey to its goal.** Edge cases, Error codes and limits go to unit, integration and conformance tests.

### Data and isolation

- **Each Journey that uses Proving ground pages has its own `seed`.** Never share one between Journeys. A Journey that touches no page has none. `GOODFETCH_TEST_SEED` never overrides a Journey's seed.
- **Pin each Proving ground task a Journey names with its `digest`** from the task list. The digest ignores the port of every URL, wherever it appears in a string value (an absolute link inside a Markdown body included), so the same seed gives the same digest on every run.
- **Commit the task list of each seed the catalog uses with `just journeys-tasks`**, which writes the Proving ground's `tasks --seed N` to `journeys/tasks/seed-<N>.json` and removes the list of a seed no Journey uses. `xtask journeys check` reads those lists, so the Quick suite starts no Proving ground; `just journeys-tasks --check`, in the Pre-merge suite, fails on a committed list that differs from the Proving ground's, is missing, or is of an unused seed. Never edit a list by hand.
- **Each variant run starts from scratch:** its own Proving ground on port 0 with the Journey's seed, its own Goodfetch home and cleared environment, `resolve` mapping the Proving ground's hosts to loopback, and its certificate authority trusted through the per-domain exception.
- **An AI Journey names the Fake model as its Model provider:** its variant's Proving ground serves it, and the setup steps point the Model provider setting at it through a public surface ([ADR 0065](../adr/0065-ai-features-are-tested-without-live-models-and-measured-by-oracle-graded-evaluations.md)). A Journey that covers an `AI-` row or an area 9 story is an AI Journey: its first step names the Fake model and runs on every variant's own surface, neither pinned to one surface nor left to a person, so that no variant can reach a real provider. Never the Scripted model, never a live model.
- **Build the starting state through public surfaces** in the first steps. Never copy in a run file, database or home folder, except an older-format file for an upgrade Journey.
- **Run against the local copy only.** Online results stay conformance reports.
- **Drive the shipped artefacts**: the Products' executables and the SDK packages built from the commit, never an engine linked into the test. An `sdk-rust` variant drives its Product's shipped executable through the crate's client, as a Daemon, never the engine the crate can link ([ADR 0069](../adr/0069-sdks-and-the-cli-are-tested-against-a-scripted-engine-and-the-binary-of-the-same-commit.md)).
- **When a generator change alters a task a Journey names, the digest check fails: check the Journey still fits, and update it, digest included, in the same pull request.** Task ordinals are append-only within a family; never reuse one.

### Tests and results

- **Carry the variant, its Journey's ID and its surface, where the runner selects by them:**
  - nextest: a module `j002` (the ID lowercased, hyphen dropped) in the test's path, and the test named after the surface with `_` for `-`: `journeys::j002::cli`, `journeys::j002::foxhound_cli`;
  - Vitest: the tags `J-002` and `sdk-typescript`, which `vitest.config.ts` declares from the catalog's files and the surfaces Vitest runs, `strictTags` on;
  - pytest: `@pytest.mark.journey(id="J-002", surface="sdk-python")`, registered, `strict_markers` on; keywords, since `-m` matches only those;
  _Why:_ one Journey file holds several variants, such as `cli` and `foxhound-cli` in one executable crate, so the ID alone cannot select one.
- **Put a surface's Journey tests in a `journeys` folder of the package that ships it**, one file per Journey: `tests/it/journeys/j002.rs` in Rust, `tests/journeys/J-002.test.ts` in TypeScript, `tests/journeys/test_j002.py` in Python.
- **Start a variant's Proving ground, home and environment through test support** (`goodfetch-test-support`, or `goodfetch-test-env` through the `test-support/` packages), and drive the shipped binary.
- **A Rust variant (`cli`, `foxhound-cli`, `sdk-rust`, `http-listener`) is written with `JourneyRun`**, which takes the executable of the Journey's Product as a value: `env!("CARGO_BIN_EXE_goodfetch-collie")` or `-foxhound` in that Product's executable crate, the test tool manifest's entry (`tools()?.path(Tool::Collie)` or `Tool::Foxhound`) in its Rust crate's `sdk-rust` variants, Foxhound's manifest entry for a Collie Journey's `foxhound-cli` variant (Collie's executable crate takes no Foxhound crate), and any path for a skew run. When `GOODFETCH_TEST_ENGINE` is set, `JourneyRun` drives that executable in place of the one passed, and a `cli` variant written without `JourneyRun` takes its executable through `journey_engine(env!("CARGO_BIN_EXE_goodfetch-collie"))`, which returns the variable's path when it is set and the built executable otherwise, so a skew run reaches every variant.
  - Call `step` for each step, with the file's exact wording and in its order. A `manual` step is recorded `manual` without being called. A step called out of order, twice or with another wording is recorded `failed` without running; after the first failure no body runs, every later step and check is `not_reached` and no result goes to the oracle. At `finish`, each step never called is recorded `not_reached` after those called, so a skipped step fails the variant and every reader refuses its document.
  - Call `check` for each check that names no task, and `expect_task(check, &json!({ "status": …, "records": … }))` with the tool's result for each check that names a task, by the check's wording: the helper submits it to the variant's Proving ground's oracle for the check's task, records the answer, and records the check `passed` only when the answer is `verified`. Each such check is judged on its own submission, so two checks naming one task (two Crawls of one site) take two submissions, and the document holds the task once per check, each with its answer.
  - A check whose `surfaces` lists some variants' surfaces belongs to those variants only, as an SDK package's install checks belong to J-002's `sdk-*` variants: the helpers neither run nor record it in another variant, and the reader expects it only in those variants' documents (`foxhound-cli` takes `cli`'s). `journeys check` fails a check scoped to a surface the Journey has no variant on, or naming a task the Journey does not pin.
  - A step pinned `on` another surface drives that surface in its body, through that surface's own helper: the CLI through `run.command()` in any variant.
- **A TypeScript variant (`sdk-typescript`) is written with `@goodfetch/test-support`'s `journey`**, by the same rules as `JourneyRun`: `step`, `check` and `expectTask` are awaited one at a time, and the CLI runs through `run.command(args)`. It drives the executable the test tool manifest names for the Journey's Product, so `just journeys --engine` reaches it through the manifest.
  - Each run writes its document as `<id>@<surface>.json` in the test's own folder, which `Finished::path()` names, and also in the folder `GOODFETCH_TEST_RESULT_DOCUMENTS` names: `just test` sets it to `target/result-documents/`, and each Release cell (`ci/release/cell.sh`) to `target/junit/result-documents/`, so the results store keeps its documents with its JUnit files. Read a run's document from `path()`: in the shared folder, another test running the same variant (the helper's own tests do) may write after it.
- **A Python variant (`sdk-python`) is written with `goodfetch-test-support`'s `journey`**, by the same rules as `JourneyRun`: `step`, `check` and `expect_task` are awaited one at a time, and the CLI runs through `run.command(args)`. It drives the executable the test tool manifest names for the Journey's Product, as the TypeScript helper does.
- **Journey tests run with their package's integration tests**: in the Pre-merge suite when the package is touched, and in the Release suite.
- **One test per variant.**
- **Each variant run writes one result document with `kind = "journey"`.** Never set its outcome by hand: derive it from the steps, the checks and the oracle's answers, through the Rust constructor (`goodfetch_protocol::result_document::JourneyDocument::new`) or a helper that passes the shared outcome vectors: `@goodfetch/test-support`'s `writeJourneyDocument` or `goodfetch-test-support`'s `write_journey_document`. A step not reached, or any Proving ground task not `verified`, fails the variant, and so does an error that failed the variant's test outside its steps and checks: test support's `ResultDocumentReporter` writes the errors of a Playwright test that did not pass into the facts' `test_errors`, so a page error or an accessibility violation found at teardown (`failOnErrors`, `axe`) leaves the variant `failed`, never `proved`. Readers load documents through `goodfetch_protocol::result_document::read`, which recomputes the outcome and rejects a document that disagrees, then pass each `journey` document with its typed Journey to `read_journey_document`, the only way to a `JourneyDocument` from stored bytes, which rejects one whose steps, checks and named Proving ground tasks are not exactly its Journey's, in order, or that records a step `manual` the Journey does not mark manual (or the reverse). The shared outcome vectors, the comparison's among them, are in `test-support/fixtures/outcome-vectors/`.
- **Run chosen variants with `just journeys`:** `--id J-002`, `--surface cli`, `--milestone M1`, `--area 3` and `--product collie`, each repeatable (values of one flag add variants, different flags intersect), and `--exclude J-002@cli`, repeatable, which removes one variant. It runs `xtask journeys select`'s filters, one per runner, through `just test pre-merge`, after naming each chosen variant no test carries (from the runners' listings), and fails when none of them has a test rather than run none and pass. `--engine <path>` runs them against that executable, through `GOODFETCH_TEST_ENGINE`, which `JourneyRun` and `journey_engine` read and the test tool manifest's `collie` and `foxhound` entries take; `--tag <tag> --engine <path>` runs the tag's own Journey tests and helpers, from a temporary worktree it removes, against it (ADR 0066). The runners of `mcp-*`, `skills`, `adapter-*` and `integration-*` variants are named by their own tickets; until then `select` lists those variants as skipped.
- **See each variant's outcome on `main` with `xtask journeys report --store <results store>`** (ADRs 0063 and 0094): every variant of an active Journey, by milestone, area and Product (`foxhound-cli` under Foxhound), from the result documents `main`'s latest Release run kept, each loaded through `goodfetch-protocol`'s reader. A variant is `proved` or `failed` as its documents give across the Release cells (`failed` when any is), `rejected` when the reader refuses one of them, never `proved` then, and `unproved` when the run kept none. With `--listings <folder>` (the runners' listings), a variant whose test ran in a Release cell that kept no document of it, as when the test panicked before `finish`, is `failed`. `--out <folder>` also writes `journeys.json` and `journeys.md`. `just reports` writes it beside the Feature report.
- **The catalog check fails** on a file that does not parse, an ID that differs from its file name, repeats or is not below the next free number, a Proving ground task missing from the task list for the seed or whose digest differs, a test naming a retired or unknown Journey or an unlisted surface (`foxhound-cli` counts as listed only on a Collie Journey that lists `cli`, with `cli`'s first milestone), two tests for one variant, a Journey test that carries no single variant, a variant milestone earlier than its surface, an AI Journey whose first step does not set up the Fake model on every variant, or a retired Journey without a reason. The rules on tests read the runners' listings, so they run in the Pre-merge suite (`just journeys-tests`, which also notes each variant no test carries yet); the others run in the Quick suite.

### Owner tests

- **List an owner test's "Journeys to try" from the catalog:** every variant of its milestone, by ID and title, with its manual steps, plus the milestone's `manual` exceptions of [Feature coverage](feature-coverage.md). `xtask journeys report --owner-test M1` prints it, both Products' Journeys in one list, each `manual` exception whose Feature is due at the milestone after them; paste it into the owner test's issue, never write it by hand. The daily test-health job attaches it as `journeys-to-try.md`.
- **An owner test is ready only when every automated variant of its milestone is `proved` on `main`,** and no Feature due at its milestone is untested ([Feature coverage](feature-coverage.md)).
- **A finding on a goal no Journey covers adds a Journey.**
- **An owner test installs both Products' executables** from a local build, and its list holds the Journeys of both Products.
