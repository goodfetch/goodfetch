## Performance budgets

Decided in [ADR 0071](../adr/0071-performance-budgets-are-counted-per-change-and-time-is-measured-on-the-reference-host.md) and [ADR 0134](../adr/0134-absolute-ceilings-and-performance-targets-join-the-per-change-budget-and-m1-ends-with-an-optimization-pass.md).

### What gates a change

- **Only counted figures fail a change:** instructions and heap metrics per benchmark, protocol and render counts per scenario, and bundle bytes. No check on a GitHub-hosted runner compares a duration with a threshold.
  _Why:_ shared runners vary by about 2.7% in wall time, and instruction counts of one binary on one machine repeat exactly.
- **No test asserts elapsed time, a rate or a duration.** Time is measured only by the Performance series and the benchmark, both Live checks.
- **Until M1's optimization pass, the counted figures inform and fail nothing,** a dated waiver of the [Quality register](../../TESTING.md#exceptions) (X20) ([ADR 0134](../adr/0134-absolute-ceilings-and-performance-targets-join-the-per-change-budget-and-m1-ends-with-an-optimization-pass.md), as amended on 2026-10-22). `xtask perf` lists each figure past its threshold or over its ceiling, with its change or value, as a `note[performance-change]` or `note[over-ceiling]` line in the gate's log, and no pull request needs a "Performance change" section or acceptance comment. A broken measurement still fails: a benchmark that fails its admission, or a ceiling whose figure the head lost. The switch is the constant `GATING` in `xtask/src/perf/budget.rs`; the optimization pass's pull request sets it back to `Enforced`, and the acceptance and ceiling rules below gate from then on.

### Benchmarks

- **Benchmarks live in the crate's `benches/`:** `scenarios.rs` holds the scenario functions, `instructions.rs` runs them under gungraun's Callgrind with mimalloc as the global allocator, `heap.rs` under gungraun's DHAT with the system allocator, and `wall.rs` under criterion for the Performance series. Scenarios that cross crates (startup, a protocol round trip) live in the binary crate.
  _Why:_ DHAT counts allocations by replacing `malloc`, which mimalloc never calls.
- **A benchmark measures one pinned scenario:** inputs from a literal, a fixture or a seed; no network, no sleep, no work whose amount depends on timing.
- **A bench target builds what it needs the way tests do:** a paused current-thread runtime through the helper tests use, `Clock::paused` and `Entropy::seeded` from the start time and seed `goodfetch-test-support` supplies (it supplies the values, never the handles), and the `tasks` module's inline blocking policy, so no thread waits on another. Its root opts in once with `#![expect(clippy::disallowed_methods, reason = "benchmark harness, ADR 0071")]`.
- **A scenario that times a crate's own private code compiles its pure modules in through `#[path]`,** each module that does no I/O and holds no task, such as the page crate's guard check, its guard world's call and the interception's steps; no `pub` item is added for a benchmark, as none is for a test (ADR 0071's note of 2026-10-24). The one exception is the fetch tiers' test seam, `FetchTiers::serving`, since the crawl path no pure module carries crosses several crates (ADR 0134's note of 2026-10-27).
  _Why:_ the scenario then builds the very command the engine sends, and the crate's interface stays what its callers use.
- **A new or changed benchmark runs 20 times on one build in its pull request.** Every gated figure must spread less than 0.5%, or the benchmark is fixed before it gates.
- **Changing what a benchmark measures gives it a new ID.** A benchmark with no base is reported, never gated.
- **Benchmarks build with the `bench` profile** (release settings, thin LTO, `debug = "line-tables-only"`) on the Linux gnu targets. Valgrind and gungraun's runner come with the pinned CI image on Linux x86-64, the only platform ADR 0135's image has; the Linux arm64 Release cells install them on their runner (`ci/host/perf-tools.sh`).
- **The `perf` job is one job while every selected bench target fits it;** it becomes a matrix over `bench-targets`, sharded by bench target within the Pre-merge budget, once they do not.

### The comparison with the base

- **`xtask perf` measures the base and the head in the same job, on the same runner:** on a pull request, the merge commit against its first parent, the base branch's head, so the head adds exactly the pull request's change; the group's base in the merge queue. Never a stored figure from another machine.
- **The gate trips at +5%** on instructions, total allocations, total bytes or bytes at the global maximum of any benchmark, and at **+5 kB brotli** on any size-limit entry. No entry exists yet: `.size-limit.json` comes with the entries of the TypeScript packages ([ADR 0071](../adr/0071-performance-budgets-are-counted-per-change-and-time-is-measured-on-the-reference-host.md); #1415 owns the list), and until then `xtask perf` measures no size.
- **Once the budget gates again, a tripped pull request passes only with a "Performance change" section** in its body, listing each tripped figure with its measured change and reason, accepted explicitly by the owner when merging ([ADR 0133](../adr/0133-agent-work-follows-the-matt-pocock-skills-as-written-and-the-fresh-review-is-retired.md)).
  - Each line names the figure as the table does, with a change at least the measured one: `- goodfetch-frontier/instructions::admission::admit/one_heavy_domain_and_a_thousand_small instructions: +5.10%, <reason>`, or `- size-limit/<entry> brotli: +6.20 kB, <reason>`.
  - The owner accepts with a comment saying "Performance change accepted" and naming the head SHA, then re-runs the `perf` job with `gh run rerun <run-id> --job <job-id>`. Its steps are not test steps and its figures repeat exactly, so the re-run measures the same change and is no retry: nothing flaky is masked ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md), as amended on 2026-10-19). The same holds for `size` where it gates. "all green" still refuses a run whose earlier attempt failed a `Test` step.
  - No section passes a ceiling ([Ceilings](#ceilings)).
- **Run `just perf` before pushing a change to code a benchmark covers.** It uses CI's thresholds; off Linux it runs in the CI image through a container engine, or lists itself as skipped.
- **The figures reach the results store** as `perf-figures.json` in the job's JUnit artifact, beside gungraun's and size-limit's reports. The daily test-health job's drift check reads them from there: `main`'s latest per platform against the last release's.

### Absolute ceilings

- **`xtask perf` also checks absolute ceilings,** in the same job as the comparison with the base. A "Performance change" section never passes a change over one; only the owner moves a ceiling. Until M1's optimization pass, a figure over one is noted and fails nothing ([What gates a change](#what-gates-a-change)).
- **The fixed ceilings:** at most **8 heap bytes per URL in the Frontier** at 100,000 URLs (DHAT's bytes at the global maximum, less the same scenario with no URL, over the URL count), and at most **twice its body's bytes allocated per crawled page**, in a crawl fed by an in-memory fixture (DHAT's total bytes of the crawl over the total body bytes its fixture records as `body-bytes` in its `.source.toml`).
- **ADR 0138's structural counts are ceilings beside these,** per page of that crawl, each a row of [Counted work](../../TESTING.md#counted-work) that `just counts` fails one count over, from the pull request that measured it and whatever `GATING` says: HTML parses at most 1, and 0 on the streaming path (`F1.parses`); selector compilations 0 (`F1.selector_compilations`); SQL statement preparations 0 (`F2.prepares`); run-file transactions at most 2 at `full` and `fast` (`F2.transactions`); syncs at most 1 at `full`, at any concurrency (`F2.syncs`); file opens 0 (`F1.file_opens`); and configuration reads 1 per Run (`F2.configuration_reads`). A Today figure above its ceiling stands only under its [Exception](../../TESTING.md#exceptions).
- **The crawl fed by an in-memory fixture is `goodfetch-foxhound`'s `heap::crawl::in_memory_pages`:** a code-free crawl, on an engine composed as the crawl's tests compose it, of an index and twelve pages of about 1 kB to 1 MB, served from memory through the fetch tiers' test seam, `FetchTiers::serving`, which sends every Run's HTTP hops with the transport it is given. Each page goes through admission, the fetch, parsing, link discovery (`follow: scope`) and extraction to a Record. Its bodies are borrowed from a static fixture, so serving them allocates nothing, and DHAT counts the whole process, as the Frontier's benchmark does. The integration test `in_memory_crawl` runs the same scenario and checks that the site sends exactly the `body-bytes` its `benches/pages.source.toml` records.
- **The tuned ceilings:** instructions, allocations and bytes allocated per dispatched JSON-RPC message, each at 1.10 times its figure after M1's optimization pass, approved by the owner.
- **The ceilings are constants of `xtask perf`** that cite ADR 0134, like the thresholds, each keyed by the benchmark IDs or size-limit entries whose figures it reads.
- **A ceiling starts when its benchmark first runs, and never lapses:** once the base or the head measures a benchmark a ceiling reads, the head must have every figure the ceiling reads, so renaming or removing a benchmark fails rather than dropping its ceiling.
- **The summary lists every ceiling beside the comparison table:** its head figure, derived ones shown rounded up, and its verdict. One whose benchmarks neither side measured is listed as not run yet. The check itself compares exact counts.

### The fixed reference build

- **`xtask perf` also holds every counted figure to at most 1.10 times a pinned reference build** (`drift.reference`, [ADR 0140](../adr/0140-every-shared-per-unit-path-has-one-owner-module-a-cost-contract-of-counted-work-and-a-benchmark.md)), so that steps under +5 % cannot add up unseen. `ci/perf-reference.toml` names the build's commit or tag: #1577's tuned build, then each release tag. Its `[[accepted]]` entries name each figure an ADR 0140 note the owner approved accepts over 1.10, held instead to the value the entry gives (with the 0.5 % of a figure read under Valgrind); an entry whose figure is back within 1.10 fails until it is removed, and a release's pin starts the list again.
- **It is measured in the same job, on the same runner,** in a worktree and target folder of its own: the selected bench targets it has, and size-limit when it has a `.size-limit.json`. Moving the pin selects every bench target.
- **A figure over 1.10 times its reference fails, naming it,** whatever `GATING` says and whatever a pull request's "Performance change" section accepts: only an ADR amendment the owner approves passes it. A figure the reference does not hold is listed as new since it. A reference holding none of the head's figures compared nothing, and fails.
- **With no revision pinned, the check reports that it has not run yet.** A missing `ci/perf-reference.toml` fails `xtask perf build`: the file is the gate's switch.

### Performance targets

- **A Performance target is measured on the owner's machine and never fails a change.** Startup to `hello` at most 10 ms (median); an idle Attached engine at most 8 MiB and an idle Daemon at most 16 MiB of resident memory, for each Product; the 1,000-page HTTP crawl at most 32 MiB at its peak, and at least as many pages per second as Spider in the same `just compare` run's scenario 1 (ADR 0138); the HTTP crawl's peak at 100, 1,000 and 10,000 pages, 16 in flight, at most Spider's at the same size, each size's row held to the tighter of that bar and 32 MiB (spec #2165). Collie has two targets on the Collie scenario's tasks: with the Guard on, no slower than Playwright (ADR 0019); with the Guard off, no slower than the fastest tool whose click does not check ([ADR 0019](../adr/0019-direct-cdp-driver-with-the-guard-as-reference.md)'s note of 2026-11-10 on G-08, Q4); #2282 builds the scenario and #2440 its Guard-off row. The owner closes both on a write-up, and neither fails anything.
- **`just targets` writes the targets report:** each target, its measured figure and, for a miss, the gap with the optimization pass's write-up from `ci/performance-target-gaps.toml`, in `target/targets/report.md`. It measures each Product's release build: startup to `hello` with hyperfine (10 warm-up runs, then the median of 100), the peaks of the idle Attached engine, the idle Daemon and the crawls of 100, 1,000 and 10,000 pages with the resident-memory check's scenarios (median of 5 runs each), and takes from the latest `just compare` report the crawl's pages per second, on scenario 1, and Spider's median peak at each size and 16 in flight, from its sizes cell; each crawl's peak is held to the tighter of that and 32 MiB, and to 32 MiB alone where the report has no Spider peak at its size. A figure with no measurement yet is listed as not measured. Each milestone's owner test links it under Reports, with `just compare`'s report, labelled `local-controlled`.
- **The release build `just targets` and `just compare` measure is profile-guided on Linux** ([ADR 0057](../adr/0057-one-binary-carries-every-capability-under-a-size-budget-ci-enforces.md)'s note of 2026-11-14). `just targets` first runs `xtask pgo check`, which fails when a Product's executable does not start `.text` with the committed order file's functions in its order, as the link map `ci/musl/link-cc` writes beside it places them. It also fails when the order file names a crate under an identity the build links it under no more, or when the build holds less than 80% of the order file's symbols, section names left out, and it notes that share. `just pgo-refresh` retrains the committed profile and order file under `ci/pgo/<target>/`: an instrumented build runs scenario 1's crawl at 100, 1,000 (three times) and 10,000 pages, scenario 4's at 1,000, the resident-memory check's `crawl-1000` and Collie's row of five Collie exercises, then the pages that `crawl-1000` and scenario 1 touch in the executable widen the order; it needs `sudo -n`, to set the kernel's fault-around to one page while it maps them. The map is read every 20 ms, so the order of the code the profile does not count and of the data depends on timing: run the refresh at any load, then `just pgo-refresh --order-only` in a quiet window, which maps the pages again and writes the order on the guided build the refresh recorded, which it keeps in its own target folder, `target/pgo/guided-target`, where the release builds that follow, guided by the committed files, do not overwrite it, and refuses when that build, its profile or its hot order changed since. `just pgo-validate` times the guided build against a plain one on scenario 1 and on each Product's held-out workload, the crawl-like scenario at 1,000 pages and Collie's pages opened one after another, 9 trials of each by default, in turn: run it in a quiet window, and put both figures of each in the pull request that commits a refreshed profile.

### Counts as snapshots

- **Protocol counts are snapshots:** for each named scenario of a surface, the requests sent, the answers and events received, and their bytes after the shared redactions. Rust against the real binary in `tests/it`; TypeScript and Python against the Scripted engine of ADR 0069 in unit tests.

  _Why:_ for an agent, bytes are context.

### Ceilings

- **Resident memory stays under its ceiling per OS** for an Attached engine idle after `hello`, an idle Daemon, and a 1,000-page HTTP crawl of the local Proving ground. The check runs in the Release suite.
- **`just rss [scenario…]` runs the check on this host:** each scenario on each executable it runs on (`idle-attached-engine` and `idle-daemon` on both Products; on Foxhound, `crawl-100`, `crawl-1000` and `crawl-10000`, the HTTP crawl of that many pages at 16 in flight, and the same three with `governor.huge_pages` on, `crawl-100-huge-pages` and the others, which run on Linux alone, where the setting changes the allocator), each run after its executable is dropped from the page cache (Linux alone), each peak against its ceiling in `ci/rss-ceilings.toml` and its Performance target. Until the owner commits that file, it reports and gates nothing. `just rss-propose` proposes the file's lines from 20 runs. `xtask rss measure --page-cache cached` reads each executable into the page cache before each run instead, for the figure of a start soon after another; the ceilings stay the dropped figures.
- **Each Product's executable has its own startup benchmarks and its own ceilings** for an idle Attached engine and an idle Daemon; the 1,000-page crawl runs on Foxhound's.
- **Resident-memory ceilings are measured on the tuned build,** after M1's optimization pass. A ceiling may sit above its target.

### Memory at scale

- **The Frontier at scale:** one process enqueues 100,000 synthetic URLs, then 1,000,000, with no network, at the default Durability level, `batch`, once at `run_state.memory.budget: 0` and once at a 1 MiB budget (ADR 0142). Peak resident memory at 1,000,000 is at most 1.5 times its peak at 100,000. It is `goodfetch-frontier`'s `at_scale` test: the Frontier's admission in the test's own process, against a run file on disk opened as a crawl's is, memory holding the visits each batch has not written and, within the budget, those it has, read with `goodfetch-test-support`'s `peak_resident_bytes`; outside the Release suite, on 10,000 and then 100,000 URLs. It also checks the duplicate check is exact: every distinct URL added, a visited one a `duplicate`.
- **The Daemon soak:** one Daemon runs 20 consecutive 1,000-page Proving ground crawls. Its resident memory after the 20th is within 10% of its value after the 3rd. If the 20 crawls take more than about two minutes, lower the pages per crawl, never the crawl count. It is `goodfetch-foxhound`'s `soak` test: 40 code-free HTTP crawls of 300 of `scale.test`'s items each, up to 8 in flight, on one Daemon of Foxhound's executable, its Runs' stores on a memory file system; a least-squares line through the Daemon's live heap after each of crawls 26 to 40, once it is warm, climbs at most 32 KiB a crawl, a bound over thirteen times clean runs' measured climb and under a third of a planted leak of 110 KB a Run's (#1734, ADR 0134's note). The live heap is `daemon.status`'s `heap`: the bytes the Daemon's allocations hold, as its executable's global allocator, mimalloc wrapped in `goodfetch_engine::heap::Counting`, counts them, without the pages mimalloc keeps once freed, whose swings failed the private-memory checks this replaced on clean runs. The Daemon's private resident memory, read with `goodfetch-test-support`'s `private_resident_bytes_of` (`RssAnon` on Linux, the physical footprint on macOS, the private working set on Windows), is printed beside the heap when the check fails; the same in every suite.
- **An engine ending Run after Run keeps nothing of each:** `goodfetch-engine`'s `heap` test runs one engine in its own process over the in-memory network, on the paused runtime with its blocking work inline, so each Run allocates the same; the test binary's global allocator is the executables' `Counting`, around the system's. It sets the engine's window of kept lossless events to 16, so the window is full within the 40 Runs of its warm-up (the Daemon's 4,096 fill after about 2,000 Runs, past the soak's reach), then ends 100 more bare Runs, and a least-squares line through the live heap after each climbs at most 16 bytes a Run (#1768, ADR 0134's note).
- **The Daemon soak pins the resource governor's memory allowance far above the expected peak,** so it does not measure load shedding (ADR 0040); the Frontier at scale starts no engine, so no governor runs.
  _Why:_ a ratio gives one verdict on any machine, and both fit the five-minute cap per test.
