## SDK and CLI tests

Decided in [ADR 0069](../adr/0069-sdks-and-the-cli-are-tested-against-a-scripted-engine-and-the-binary-of-the-same-commit.md).

### SDKs

- **Unit tests run against the Scripted engine in-process**, through an in-memory transport; integration tests and Journeys run the Product's executable built from the same commit. `sdk-rust` Journeys run with a Daemon only; `linked` is never a Journey mode.
  _Why:_ the binary can't fabricate a refused `hello` or a crash mid-call, and a fake alone passes where the engine fails.
- **Scripts live only in `test-support/fixtures/engine-scripts/`**, never inline in a test. Every message step in them must validate against the committed JSON Schema bundle; only raw-byte steps, deliberately not JSON-RPC, are skipped.
  _Why:_ one validated corpus keeps the stand-in true to the engine for every SDK at once.
- **Pass the Product's engine-path variable and `GOODFETCH_HOME` in the SDK's environment-map option**, as the test-support fixtures build it from `goodfetch-test-env`. Never set them in the test's own process; an Attached engine gets exactly that map as its environment.
- **Process faults use `goodfetch-scripted-engine`**, reached as an Attached engine through the Product's engine-path variable (TypeScript and Python) or as a Daemon through a runtime file in the test's Goodfetch home (every SDK). No build of either Product carries a fault switch. In TypeScript, test support's `scriptedEngineEnv(testEnv, product, script, home?)` builds the environment map, installing the corpus's script as `scripted-engine/script.json` under the home it names, `scriptedEngineClientMethods(home)` reads back the methods of the Client's messages the engine read, and `scriptedEngineEnvironment(home)` the environment an Attached one was started with; Python's `scripted_engine_env`, `scripted_engine_client_methods`, `scripted_engine_environment` and `until_scripted_engine_read` are their twins, the last also reading a Daemon that `start_scripted_daemon(..., recorded=True)` started. A Client conformance case tagged `attached` runs on it or on the Product's executable, never on the in-memory player.
- **No process outlives its test:** the test-support fixtures fail a test that leaves an engine, Daemon or handler process alive after teardown.
- **Each Product's SDK packages run against their own Product's executable**, and each implements every Client conformance case and passes the completeness checks for its own Product's catalog.
- **Every Client conformance case in `conformance/clients/` is implemented on every surface it lists**, carries its case ID, and runs in both of its surface's modes: named cases `attached` and `daemon` in TypeScript, Python and the CLI, `linked` and `daemon` in Rust, which links the engine and starts no Attached engine. A Quick-suite check fails on a missing implementation or an unknown ID.
  - Each case in `conformance/clients/cases.toml` lists its `surfaces` (`cli`, `sdk-rust`, `sdk-typescript`, `sdk-python`) and, for a capability that exists in some modes only, its `modes`: one list for every surface, or a table giving a surface modes of its own (`modes = { sdk-rust = ["daemon"] }`), where a surface the table leaves out takes every mode it has.
  - A `cli` test carries its case the way a nextest Journey test carries its variant: a module `client_conformance::<case>` (the ID with `_` for `-`) in its path, and the test, or its rstest case, named after the mode: `client_conformance::hello_refused::refuses::case_1_attached`. It sits in the executable crate of its case's Product, which is Collie unless the case says `product = "foxhound"` because Collie's executable lacks what it needs: a test runs once, on Collie's executable when it carries everything the test needs (ADR 0094). A test of Foxhound's crate may also carry a Collie case, but only a test of Collie's implements it.
  - An `sdk-typescript` test carries its case as the Vitest tag `client_case/<id>` and its mode as the tag `attached` or `daemon`, both declared from the case list, so `strictTags` refuses an unknown case. It sits in a TypeScript SDK package under `sdks/typescript/`.
  - An `sdk-python` test carries its case and mode as the marker `client_case(id="<id>", mode="attached")` (or `"daemon"`), by keyword, one marker per case and mode it runs; the plugin refuses at collection a marker with no such mode or a case the case list does not declare. It sits in a Python SDK package under `sdks/python/`. Under `@three_ways`, each way runs the case and writes its own entry.
  - `xtask clients check` (in `just lint`) fails on a case missing on a listed surface in one of its modes (on `cli`, from its Product's executable crate), a test carrying an unknown case, a test of Collie's executable crate carrying a Foxhound case, a `product` other than `collie` or `foxhound`, a case on a surface or in a mode the case does not list, or no mode (or, in Vitest, two), a case giving modes of their own to a surface it does not list, and when the case list is missing. A test behind a `cfg` (on it or an enclosing module, `cfg(test)` aside) or `#[ignore]`d implements nothing, since it may never run, nor does a skipped or todo Vitest test or a pytest test behind `skip` or `skipif`: the one exception is a test behind the `cfg` of the one platform its case lists in `platforms`, such as `platforms = ["unix"]` for a case whose Windows half has no test yet. It reads the `sdk-typescript` and `sdk-python` tests from Vitest's and pytest's listings, so those surfaces are checked in the Pre-merge suite (`just clients-tests`) and only noted in the Quick suite. It reads `sdk-rust` from the sources of `goodfetch-collie`, `goodfetch-foxhound` and `goodfetch-collie-client`, unit tests included, in every suite: a Rust test carries a case and its mode by a `ClientCaseRun::start(folder, "<case>", RustMode::Linked)` (or `RustMode::Daemon`) call in its own body, with both written literally, and the check fails on such a call whose case or mode is not a literal; a call in a helper carries nothing.
- **For Client conformance cases, each runner writes a case log; only `goodfetch-conformance`'s writer turns it into a result document**, deriving each outcome through `goodfetch-protocol`'s constructor. A log entry never carries an outcome. A declared case missing from the log is `unproved`. In TypeScript the writer is the Vitest reporter `CaseLogReporter` ([Shared helpers](shared-helpers.md)): one entry per case a test that ran carries, with the checks the test recorded through `clientCase` and a last check, `the test passed`, so a test that fails outside its checks fails its case; a skipped test writes none. In Python the writer is the plugin's `--case-log` ([Shared helpers](shared-helpers.md)), with the same entries and the checks a test recorded through `client_case`; a test skipped in any phase writes none. In Rust the writer is `goodfetch-conformance`'s `ClientCaseRun` ([Shared helpers](shared-helpers.md)), into `target/case-logs/nextest.jsonl`, with the same entries and the checks a test recorded through its `check`; the tests of `goodfetch-collie`, `goodfetch-foxhound` and `goodfetch-collie-client` write theirs, taking the folder from `goodfetch-test-support`'s `case_logs()`. `goodfetch-conformance write <case list> <header> <case log> <document>` turns a log into its document. Journeys write their own documents ([Journeys](journeys.md)). The entry type is in `goodfetch-protocol` and its schema in the bundle; the script format's schema is `test-support/fixtures/engine-scripts/script.schema.json`. Both come from `xtask codegen`.
- **Lifecycle conformance cases** ([ADR 0078](../adr/0078-an-sdk-program-opens-an-explicit-engine-connection-and-closes-only-what-it-started.md)) run in every SDK: two connections at once in one process, a second `connect()` after `close()`, `closed` on a call after `close()`, nothing written to stdout or stderr by the SDK, no signal handler or event-loop patch after import or `connect()`, Ctrl+C reaching only the test's own process, a Borrowed page left open after its borrow ends, and an Attached engine's unexpected exit raising an error that carries its stderr tail.
  _Why:_ they are the failure points of the golden scenarios "Run a crawl inside a web service" and "Add an AI step to an existing Playwright program", and the lifecycle failures competitors shipped (ADR 0078).
- **Error and outcome conformance cases** ([ADR 0079](../adr/0079-failures-raise-grouped-typed-errors-and-expected-outcomes-are-values.md)) run in every SDK against the Scripted engine: each Error code raises its class under its group; a code the SDK does not know raises its group's class with the code kept; unknown outcome kinds, Block causes, skip reasons and Verdicts are kept, and an unknown Verdict is never `verified`; after a dropped connection an in-flight read is re-sent, while an in-flight Effect raises `UnavailableError` and is never re-sent; each SDK declares its language in `hello` and shows the target the engine rendered; and no error or call log carries a Secret canary's value. The engine's target renderer is tested once per SDK language in the Quick suite, and a Quick-suite check fails when codegen would emit a class name that shadows a built-in of any SDK language.
  _Why:_ they are the failure points of the golden scenarios "Extract a typed object with a chosen model", "Crawl two page types into a Dataset" and "Reach a goal from one instruction, with limits and a verdict", and the false successes and stringly errors competitors shipped (ADR 0079).
- **Trace context conformance cases** ([ADR 0132](../adr/0132-each-request-may-carry-its-callers-trace-context-across-goodfetchs-own-links-and-the-engines-spans-stay-experimental.md)) run in every SDK against the Scripted engine: a call inside an active OpenTelemetry span sends its `traceparent` and `tracestate` in `_meta`, a call outside one or without the OpenTelemetry API sends none, Baggage is never sent, and an SDK handler runs under the Trace context the engine's request carries. The engine's side runs through an in-process OTLP collector: the receiver rules, both span kinds, the run's root with its link, propagation over each link of the protocols in that link's tests, and no `traceparent`, `tracestate` or `baggage` header in what the Proving ground, the Fake model, each Sink's container and an `httpmock` webhook endpoint receive.
  _Why:_ a header that reached a site would mark the request as automated, and a Trace context dropped at one link splits the caller's OpenTelemetry trace (ADR 0132).
- **Time conformance cases** ([ADR 0080](../adr/0080-sdk-timeouts-nest-waits-arm-when-called-and-a-program-sets-limits-but-never-raises-them.md)) run in every SDK: an inner call ended by its outer timeout and naming it, `0` refused, the null form meaning no timeout, a response that arrives before its waiter is awaited still caught, a signal, a cancelled task or a dropped future reaching the scripted engine as `$/cancel` and stopping its work, a call stopped by another Client failing with `call_cancelled` while the caller's own cancellation never raises it, a Human pause not counted, a Limit reached ending the Run `stopped` and `incomplete`, and the sleep tombstone failing with `removed` in TypeScript and Python, and Rust's failing to compile (a compile-fail test).
  _Why:_ they are the failure points of the golden scenarios "Fill a dependent form and read the results" and "Run a crawl inside a web service", and the timing, hang and cancellation failures competitors shipped (ADR 0080).
- **Concurrency conformance cases** ([ADR 0081](../adr/0081-each-sdk-follows-its-languages-concurrency-model-and-shapes-events-by-meaning.md)) run in every SDK: Python's sync API inside a running ipykernel loop and from several threads at once; Python's async API under asyncio and under Trio, and a call from another loop failing at once; Ctrl+C during a sync call reaching the scripted engine as `$/cancel`; a listener's exception raising `listener_failed` once, on its value's next call; a `Subscription` and an iterator unsubscribing on close, on leaving the loop and on release; an unread lossless iterator slowing its producer; a regular expression with look-around refused at the call, and `\d` and `\w` matching as in the pattern's own language; the async Python client starting an Attached engine under asyncio's selector loop on Windows, with no event-loop policy set; and in Rust, handles checked `Clone + Send + Sync + 'static` at compile time, a `Crawl` checked `Send + Sync` and its `serve` future `Send` at compile time, a handler that declares an Effect keeping that future `Send`, a crawl served from a task spawned on a multi-threaded Tokio runtime with handlers that borrow and handlers that own their captures, a handler that holds an `Rc` across an `.await` failing to compile (a compile-fail test, [ADR 0112](../adr/0112-a-rust-crawls-handlers-and-their-futures-are-send-in-axums-form-so-serve-runs-in-a-multi-threaded-server.md)), the crate's futures run on a single-threaded executor, each Product's `blocking` module (`goodfetch_collie::blocking`, `goodfetch_foxhound::blocking`) used inside an async runtime without panicking, and an async connection closed and dropped inside a running Tokio runtime without panicking.
  _Why:_ they are the failure points of the golden scenario "Run a crawl inside a web service", and the concurrency failures competitors shipped (ADR 0081).
- **Typed data conformance cases** ([ADR 0082](../adr/0082-sdk-schemas-come-from-each-languages-own-schema-types-payloads-are-typed-per-label-and-results-keep-what-the-sdk-does-not-know.md)) run in every SDK against the Scripted engine: a schema in the language's idiom and a hand-written JSON Schema both reach the engine as the same JSON Schema; a candidate a native rule rejects is retried with that rule's message; a validator that throws stops the call with `schema_validator_failed` in TypeScript and Python, while in Rust a `Deserialize` error is retried and a panic unwinds in the caller; a non-JSON value is refused with its field path and never stringified; a wrong or oversized Payload fails its enqueue with `payload_invalid`; a resume after a Payload's JSON Schema changed is refused with `payload_schema_changed` before any work, while a Payload only a changed native rule rejects fails its own request with `payload_invalid`, never retried; a native rejection outside extraction fails its call without a retry; a result field or value the SDK does not know is kept and nothing raises.

### CLI

- **The binary runs under assert_cmd and is snapshotted with insta**, through `goodfetch-test-support`'s helper. One snapshot holds stdout, stderr and the exit code.
  - `cli(&env, executable).args([…]).env(name, value).run()` (with `.stdin(text)` for what it reads on standard input, empty otherwise) runs the executable the test gives, by path (its own crate's `env!("CARGO_BIN_EXE_goodfetch-collie")` or `…-foxhound`), in the test's folder with the cleared map (whose `LANG=C.UTF-8` and `TZ=UTC` are the fixed locale and zone unless the test named others) plus `NO_COLOR=1`, `COLUMNS=100` and `TERM=dumb`. It returns a `CliOutput` (`exit`, `stdout`, `stderr`), which `assert_cli_snapshot!(output)` (or with a name, or an inline `@"…"`) snapshots as one value under the shared filters. It fails with `CliError::EscapeByte` when piped stdout or stderr holds `0x1B`, and with `CliError::NotUtf8` on bytes that are not UTF-8.
  - `--json` runs: `cli(&env, executable).args([…, "--json"]).json("SettingsExplanation")` runs the command as `run()` does, then checks that stdout holds exactly one JSON document, valid against that type of the committed bundle's `$defs` (read as a file, so the test names the type and test support stays on values); `.json_lines("EventEnvelope")` checks that each line of stdout is one document of the command's declared event type. They fail with `CliError::SchemaViolated` (each violation, and the line among JSON Lines), `CliError::SecondDocument`, `CliError::NotJson` (a stray line, a blank line or no document) and, before anything starts, `CliError::SchemaUnknown`. The `CliJson` they give holds the `documents` and an `output` whose stdout is those documents pretty-printed, for `assert_cli_snapshot!`; that leaves out stdout's layout, key order and number spelling, so a test running one command in several modes also compares `printed`, stdout as the command printed it, across them.
  - Both modes: `.mode(Mode::Daemon)` starts the executable's Daemon in the test's home (`Daemon::start_program`), adds `--daemon` after the arguments, runs the command, then stops the Daemon and fails with `CliError::Daemon` when it still runs or left its runtime file; `.mode(Mode::Attached)` adds `--attached`, so even a command whose value outlives it, which reaches the Daemon by default, runs in the executable's own process and starts none. With no mode, the arguments run as given, on the engine the executable chooses: a test of a value-bound command or an opener that is about something else passes `--attached` or a mode, or it starts a Daemon. Each command that runs the engine has one rstest case per mode, `#[case::attached(Mode::Attached)]` and `#[case::daemon(Mode::Daemon)]`, snapshotted under one name (`assert_cli_snapshot!("config_explain_json", checked.output.without_dispatch_records())`, or one inline snapshot). The engine's dispatch records, which an Attached engine writes on the command's stderr at the level `TestEnv` sets and a Daemon in its own log, are the one difference between the modes, and no shared filter of `assert_cli_snapshot!` drops them: `CliOutput::without_dispatch_records` leaves them out of what both snapshot. A test that compares only the documents needs no such call, and a test of the records themselves keeps them.
  - `pty(&env, executable)`, with the same `.arg`, `.args` and `.env`, runs the executable on a pseudo-terminal under expectrl (ConPTY on Windows) with the test's map, `COLUMNS=100`, `TERM=xterm-256color` and no `NO_COLOR`. `.run()` gives a `PtyOutput` (`exit`, `text`: the one transcript, `\r\n` line ends and escape sequences included); `.spawn()` gives a `PtyRun` whose `expect(text)` waits for a prompt, failing with `PtyError::NotShown` when the executable ends or 60 seconds pass first, whose `send_line(answer)` types the answer, and whose `finish()` reads to the end. `PtyOutput::stripped()` drops the escape sequences and `\r`; `has_colour()` finds an SGR sequence other than a reset. A pseudo-terminal run never refuses an escape byte, and records its command as `cli` does.
  - The colour properties of [Accessibility](accessibility-localization-and-visual-regression.md) are `ColourProperty` cases any command can run: `ColourProperty::StrippedColourEqualsNoColor.check(&env, executable, &args)` fails with `ColourError::ColourCarriesInformation`, `EmptyNoColorKeepsColour` with `ColourError::EmptyNoColorTurnsColourOff`, and `ColorAlwaysOverridesNoColor` (which adds `--color always` after the arguments) with `ColourError::ColorAlwaysIgnored`. Write one rstest named case per property.
  - The locale cases: `cli(&env, executable).with_locale("tr-TR").with_time_zone("Asia/Kathmandu")` sets `LANG=tr_TR.UTF-8` and `TZ` in that child's map only; a value outside the shared table fails the run, before it starts, with `CliError::LocaleUnknown` or `CliError::TimeZoneUnknown`.
  - Each run appends `{"target": "goodfetch::test::command", "fields": {"command": …, "exit_code": …}}` to the test's command record, `commands.jsonl` in its folder, which teardown copies into its exercise record ([Feature coverage](feature-coverage.md)). The command is the longest run of the arguments whose names, joined by dots, are a `command:` Feature of `features/inventory.json` (`browser install --json` is `browser.install`); arguments that name none are recorded as `unmatched`, which the exercise audit reports. A test that starts the executable itself, such as an Attached engine's, calls `record_command(&env, &["attached-engine"], status.code())` once it exited; a handle kept beyond a borrow of its `TestEnv`, such as `daemon run`'s foreground Daemon across a Journey's steps, keeps the test's folder and calls `record_command_in(&folder, …)`.
- **Every `--json` test validates stdout against the command's schema** from the bundle, checks that stdout holds nothing else, and snapshots it, through `cli(…).json(type)` or `.json_lines(event type)`.
  _Why:_ `--json` is under semver (ADR 0030), and only a schema puts it in the breakage check.
- **Warnings, hints, deprecations and the age notice never reach stdout.**
- **Every exit code in `goodfetch-protocol`'s table has a test through the binary**, one rstest named case per exit code, in `tests/it`. An in-process unit test checks that the table maps every Error code. A case that needs an Error code the engine cannot be made to raise plays the corpus's `daemon/cli-call-failed.json` with that code and its group's class in its reply, the Scripted engine run as a Daemon answering `config explain --daemon`.
- **Test a command both executables carry through Collie's.** Foxhound's `--help` snapshot and the containment checks of [Which Product's executable a test runs](levels-and-layout.md#which-products-executable-a-test-runs) show it unchanged there.
- **Human output is snapshotted under `NO_COLOR=1`, a fixed `COLUMNS`, `TERM=dumb` and a fixed locale.** The `--help` tree is one snapshot rendered in-process from clap's `Command`; one `tests/it` case checks the binary prints the same. A unit test calls clap's `Command::debug_assert`.
- **Terminal-only behaviour is tested in a pseudo-terminal with expectrl,** through `pty`: colour, progress, and person-only prompts, which must refuse when stdin is not a terminal.
- **Interrupts are tested through the binary:** a running Crawl sent `SIGINT` (Unix) or `CTRL_BREAK_EVENT` (Windows) checkpoints and exits with its exit code; a second interrupt ends the command at once, exit `130`, while on a Daemon the Run still stops with its Checkpoint through the first interrupt's `run.stop` (ADR 0069's #1180 note): its test plays the Daemon on the Scripted engine, which holds that `run.stop` unanswered, sends the second interrupt once it is in flight, and checks that the command exits `130` within 10 seconds. Test support's `Process::interrupt()` sends a spawned executable `SIGINT` (Unix), and `Process::terminate()` `SIGTERM`, which exits `143`. A cancellable command's interrupt shows in the engine's dispatch records as `cancel received`, before its call's `call_cancelled`.
- **A command that runs the engine is tested in both modes**, as rstest cases `attached` and `daemon` through `cli(…).mode(mode)`, against one snapshot.
- **Daemon log cases** ([ADR 0122](../adr/0122-a-run-stops-resumably-before-its-disk-fills-and-a-daemons-logs-rotate-at-a-bounded-size.md)): `daemon run` writes JSON lines to stdout and no log file; a Daemon started by `daemon start` writes them to the Goodfetch home's log folder, rotating at `log.file.max_size` and keeping `log.file.max_files`, so a test that sets both small and logs past them finds that many files, each at most the size plus one line; a crawl of 1,000 requests at the default level writes no line per request; on a full filesystem the Daemon keeps serving, and once space returns the next line says how many were dropped; `log.output: stdout` on an Attached engine fails with `setting_not_applicable`, and with `log.output: file` it writes the JSON lines ADR 0072's exercise audit reads into the test's Goodfetch home.
  _Why:_ they are the pitfall catalog's row O10, debug-level logs and files that never rotate on long runs (ADR 0122).
- **Client faults** (a refused protocol version, a dead PID, a dropped connection) come from the Scripted engine run as a Daemon.
- **What only Foxhound carries is refused through Collie's executable,** table-driven from the generated list of Foxhound's names: each operation over the protocol, each setting key as a `settings` value, each CLI command with its exit code, enabling each Plugin kind and Hook stage, and each value Foxhound adds to a type both Products share (a Limit scope, a Usage kind, a Notification event) where a program or a Recipe sets it answer `not_in_product`, with one message snapshot per kind. A configuration file holding a Foxhound key or such a value loads, and `config explain` lists it as Foxhound's (ADRs 0087 and 0095).
- **A Recipe is held to the Product its manifest names, on both engines** (ADR 0096). `init` writes the Product of the executable that ran it. Collie refuses a Recipe that names Foxhound with `not_in_product` before its run starts. A Foxhound-only operation, Plugin kind or Hook stage from a Recipe that names Collie answers `not_in_product` on both engines, its `fix` saying to name Foxhound in the manifest, and on a person's own Collie engine also to run it with Foxhound. On Foxhound's engine, the same call on that run from a Client answers the same, the Client's connection and other calls still succeed, and a crawl setting key on that run answers `setting_not_applicable`.
