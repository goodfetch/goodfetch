## Shared helpers

- **Rust helpers live in `goodfetch-test-support`** (`crates/goodfetch-test-support`, `publish = false`): the per-test folder, `GOODFETCH_HOME` and cleared environment, the printed seed, unique names, reported addresses, the Proving ground started from a seed, commands with the cleared environment, and the shared snapshot redactions and filters.
  - A test starts with `TestEnv::new()`: its folder (kept and listed as `goodfetch-test-folder-kept=<path>` when the test fails), `home()`, the cleared `env()` map, `seed()` (printed as `goodfetch-test-seed=<n>`), `start_time()` (2026-01-05T09:00:00Z), `unique_name(prefix)` and `suite()`; `.with_variable(name, value)` adds a variable to the map every child gets. `TestEnv::in_memory()` makes the same setup with its folder on a memory file system (`/dev/shm` on Linux, the temporary folder elsewhere), for an in-process test of a store whose cases each write a store of their own: on a busy disk every sync and new file waits for the other writers' data, which can push such tests past the Quick suite's kill ([ADR 0062](../adr/0062-tests-sit-beside-their-code-and-share-one-test-support-written-once.md)'s note of 2026-11-21). The Daemon soak is the one engine test on it: its HTTP crawls start no browser, and a busy disk slows its Runs' stores past its time cap (ADR 0062's note of 2026-11-21). Any other test that starts a browser or an engine keeps `new()`, whose copies would sit in memory. A failed in-memory test's folder is kept on disk, copied to the temporary folder under its own name and listed there, and removed from memory, where every kept folder would hold RAM until someone deleted it; a test killed on its timeout runs no teardown, so the next in-memory setup moves each folder whose process is gone (its name carries the process ID) and lists it as `goodfetch-test-folder-moved=<path>`. Its home starts with a user configuration holding `TEST_SETTINGS` and the test's `log.level`, so every engine process writes its JSON log (`log.output = "file"`), and the Resource governor judges the engine's own memory alone (`governor.host_memory = false`), since the host's pressure comes from whatever runs beside the test and, once critical, sheds the Run's browsers (#2115, #2116); `user_configuration(settings)` writes it again with the test's own settings after them, each default left out whose key the settings set; `log_level(filter)` sets `log.level` in the file as it is, whoever wrote it (`info` keeps the trace lines, which carry their instant, out of two pseudo-terminal runs a colour property compares; `trace` makes any log line on stdout fail a `StrictStdout` test). It starts children through `command(&env, program)` or `env.spawn(…)`, and its teardown fails the test when one is still alive. Its user configuration turns on the JSON log of every engine the test starts, into the home's `logs/` folder (ADR 0122), and under `just test pre-merge` or `release` its teardown copies those lines, its command record ([CLI](sdk-and-cli-tests.md#cli)) and its answer record ([Feature coverage](feature-coverage.md)) into the test's exercise record, which the exercise audit reads; an in-process test that installs `goodfetch_test_support::subscriber` gets its dispatch and outcome records there too ([Feature coverage](feature-coverage.md)). Under `just coverage` the map also passes on `LLVM_PROFILE_FILE`, so each instrumented executable writes its coverage profile.
  - **Every test has a crash-dump folder**, `crash_dump_folder()` (`<home>/crash-dumps`), which the map names in Chromium's own `BREAKPAD_DUMP_LOCATION` (`CRASH_DUMP_VARIABLE`), so every browser a test launches writes its crash dumps there. Teardown fails the test when the folder or a subfolder holds any file but the `settings.dat` Chromium's crash reporter keeps at its root whenever it runs, with a `CrashDumps` payload listing each one, and keeps the folder ([ADR 0074](../adr/0074-the-goodfetch-chromium-is-gated-where-it-is-built-against-a-control-build-of-the-same-revision.md)). `goodfetch-test-env` exits non-zero at teardown for the same reason, which the Vitest fixtures report as `teardown_failed`.
  - **Tests find the commit's executables through the test tool manifest**, `tools()`: `just test` builds each one the workspace has (both Products', the Proving ground's, `goodfetch-test-env`, `goodfetch-scripted-engine` and `goodfetch-conformance`, whose `read <file>` loads a result document through `goodfetch-protocol`'s reader, and `read <file> --journey <Journey file>` also compares a `journey` document with its Journey) with the tests' Cargo profile, through `xtask test-tools build`, and puts the manifest's path in `GOODFETCH_TEST_TOOLS` (a script reads one entry with `xtask test-tools path <tool> --manifest <file>`, which fails on an entry it does not know) and the suite in `GOODFETCH_TEST_SUITE`. Run outside `just test`, a test that needs one fails, naming `just test`.
  - **A test is refused tools older than their sources.** Beside the manifest, `xtask test-tools build` writes its input record, `<manifest>.inputs.json`: the tree the tools were built from, and the size and modification time of each source Cargo compiled into them. The sources are the files each executable's dep-info names inside the workspace (Rust sources, included files, what build scripts watch, a watched folder with every file under it), with `Cargo.lock`, `Cargo.toml`, `rust-toolchain.toml`, `.cargo/config.toml` and the manifests of the packages they are in. The build fails when a source changed while it ran. `tools()` compares the record with the tree at a process's first use of a tool, and `goodfetch-test-env` does when a Vitest, Playwright or pytest test starts it: tools built before a merge, a `git switch` or an edit fail the test with `ToolsError::Stale`, which names the first changed source, and tools built from another tree with `ToolsError::OtherTree`; both name the command, `just _test-tools`. The check adds about 4 ms to a test process that uses a tool (one read of the record and one `stat` a source; [ADR 0062](../adr/0062-tests-sit-beside-their-code-and-share-one-test-support-written-once.md)'s note of 2026-11-21 has the measurement), and starts no process.
    - What it does not see: a commit alone (Git's own files and the target folder are no sources); a file put back with its size and time, as for Cargo; another tree's tools under Vitest, Playwright or pytest, where `goodfetch-test-env` is itself one of those tools and compares the record with the tree it was built from.
    - A manifest with no record is read as it is: one a test writes for stand-in programs, one `manifestWithEngine` derives, and the copy `ci/mutants.sh` gives its tests, since each mutant changes a source on purpose. The Kennel's tests read the manifest with a reader of their own, after `kennel/scripts/check.sh` built it.
  - **These rebuild the tools before they run a test:** `just test` (so `just test-affected`, `just pre-merge`, `just release`, `just journeys`, `just merge`'s gates and `just coverage`), `just repeat`, `just stress`, `just snapshots`, `just asan`, `just warm`, `just journeys-tasks` and `just mutants`; `just rss`, `just rss-propose`, `just compare`, `just targets`, the Kennel's `scripts/check.sh` and the Release suite's cells build manifests of their own. A bare `cargo nextest run` or `cargo test`, `cargo insta` and a runner started by hand rebuild none: after a merge, a `git switch` or an edit of a crate a tool is built from, run `just _test-tools` first, which builds nothing when nothing changed.
  - **A test that drives Proving ground pages starts its own Proving ground**, `ProvingGround::start(&env, seed)`: the tool manifest's Proving ground runs `serve` on port 0 of loopback under the test's environment, its process joins the test's record, and it stops when the value drops: interrupted with `SIGINT`, as `stop()` does, so it ends its connections and undoes any network shaping, and killed only when it outlasts its 10 s deadline. `stop()` answers its exit status. A binary that prints no first line within `PROVING_GROUND_DEADLINE` (30 s) fails with `ProvingGroundError::Line`. `description()` holds its `address`, `version` and `seed`, `resolve` (every host name it serves, mapped to the address's IP, for the `resolve` setting), `ca` (its certificate authority's PEM file in the test's folder) and `fixtures`: the forward `proxies` by name with their `proxy_credentials`, the `dns` fixture, the watched `target` and `connections`, the connection record's URL. `url(host, path)` gives a page's URL on the bound port, `start_url(id)` the start URL of a task of its task list, such as `actionability/2`, and `judge(id, status)` the oracle's verdict on that task as a tool reports it (`success` or `failure`), from the Effects its pages recorded. `ProvingGround::start_program(&env, path, seed, deadline)` starts another executable, such as an old tag's. A test that starts `serve` itself, such as the Proving ground's own, takes its command line from `serve_arguments(seed, address, network_profile)`, and a test that compares a URL the engine answers takes its path with `path_of(url)`.
  - **A test counts the requests a site received through `ReceivedRequests`**, never the observations' raw `requests` list: `proving_ground.received_requests()`, or `ReceivedRequests::of(&observations)` for observations read once. `of_the_case()` leaves out `OWN_TARGETS`, the robots.txt the engine reads of each loaded document's origin, which nothing a case calls waits for ([ADR 0086](../adr/0086-a-crawl-obeys-robots-txt-and-sends-one-request-at-a-time-per-domain-by-default-and-pressing-harder-is-recorded.md)), and the icon Chromium asks a site for on its own. `every()` keeps them, for a claim about all a site saw (an exact list, "nothing more", each request's headers, a robots.txt test); where order matters, its count comes after a named state, `goodfetch-test-client`'s `robots_txt_read(&env, run_id)`, which returns once the Run's Provenance records a robots.txt reading, so the read's request has reached the site. The conformance harness's `ProvingGround::received_requests()` gives its cases the same. `xtask received-requests`, in `just lint`, refuses any other read of the list in a file under `crates/` that reads the observations. A test whose record is too large to read whole, such as the Daemon soak's 12,000 requests, counts one host's requests of the case with `proving_ground.requests_of_the_case(host)` (`GET /requests-of-the-case`), which leaves out the same `OWN_TARGETS`.
    _Why:_ both land before or after any count a test takes, so a count over every request is a race under load ([ADR 0064](../adr/0064-tests-are-never-retried-and-unpinned-checks-run-as-live-checks.md)); five counts failed that way.
  - **A test reads where the Proving ground's DNS fixture was asked from through `ProvingGround::dns_query_sources(&observations, name)`**: the source address of each query for `name`, in arrival order.
  - **A test that makes one request lose a race on its way to a site names a proxy in front as its Session's**, `proxy_in_front(upstream, hold)`: a forward proxy on loopback before the Proving ground's proxy `upstream`, which calls `hold` with each connection's first line before handing it on.
  - **A test that launches a browser takes its Browser cache from `browser_cache(&env)`**: a cache in the test's folder that holds the Chrome for Testing build Collie pins (`CHROME_FOR_TESTING_BUILD`), laid out as a prepared copy holds it, its files hard links to the same build Playwright installs for the repository's own browser tests (`PLAYWRIGHT_BROWSERS_PATH`, else Playwright's default folder), so no test downloads a browser; where the system refuses those links, as Linux's `protected_hardlinks` does for another user's files and any system does across file systems, they link one copy of the build laid out beside the tests' folders, `goodfetch-chrome-for-testing-<build>-<platform>`: the first test that needs it lays it out whole, under a lock and a name of its own, and renames it in place, every later test links it, and a test that finds it removed lays it out again, so a test's folder holds no bytes of the build of its own (#2664, #2306), and a file is copied only where neither link can be made; the test passes its root to the engine as `GOODFETCH_BROWSERS_PATH` (`BROWSERS_PATH_VARIABLE`). A build Playwright has not installed fails with `BrowserCacheError::NotInstalled`, naming `pnpm exec playwright install chromium`. A test that searches every file of the Goodfetch home, such as the reset gate, takes `browser_cache_in_home(&env)` instead: the same build in the home's own Browser cache (`<home>/browsers`, where an engine without `GOODFETCH_BROWSERS_PATH` keeps it), so the search takes in the cache as a person's home holds it, and sets `egress.offline = true`, so a build the engine cannot find fails at once with `artifact_unavailable_offline` rather than downloading some 150 MB within a call's deadline (fix-queue 124).
  - **A test of `browser clean` lays out a stand-in build with `lay_out_browser_entry(root, build, used_at)`**: its placeholder files, lock and `entry.json`, installed and last used at `used_at`, in the Browser cache at `root`.
  - **A test that needs a Daemon starts the one of its own home**, `Daemon::start(&env, Product::Collie)` (`Product::Foxhound` for a test that needs Foxhound, ADR 0094): the tool manifest's executable of that Product runs `daemon launched --keep-alive` under the test's environment, so it is the test's own child, joins its record and never stops for idleness. It reads back the runtime file the Daemon prints once ready from `<home>/<major>/daemon.json`; `description()` holds its `socket` (the Unix socket's path, or the loopback TCP address on Windows) and `token`. `stop(&env)` runs the executable's `daemon stop` and fails with `DaemonError::StillRunning` or `DaemonError::RuntimeFileLeft` when the process did not end or a runtime file is left in the home; dropping a value the test did not stop runs the same `daemon stop`, so the Daemon ends its Runs and its children before it exits, and kills it only when that fails or outlasts the deadline. A Daemon that exits before it is ready fails with `DaemonError::Exited`, its own message on stderr. `goodfetch-test-env --daemon` (Collie's) or `--daemon=foxhound` starts one, describes it under `daemon`, stops it when its stdin closes and exits non-zero when that stop fails.
  - **A Rust Journey variant runs through `JourneyRun`** ([Journeys](journeys.md#tests-and-results)): `JourneyRun::start(id, surface, engine, ResultDocument::journey)` reads `journeys/<id>.toml` as plain values, refuses a surface the Journey does not list (`JourneyRunError::UnlistedSurface`; `foxhound-cli` counts only on a Collie Journey that lists `cli`), starts the variant's `TestEnv` and, when the file has a `[proving_ground]` table, its Proving ground on the Journey's own seed, and records the Product and version the executable's `--version` reports. `run.step(wording, |run| …)`, `run.check(wording, |run| …)` and `run.expect_task(check, &submission)` record the outcomes; a body fails when it panics or returns an `Err`. `run.command()` is the executable's command line under the variant's environment, `run.env()`, `run.engine()` and `run.proving_ground()` the rest; `run.surface_package(name, version)` names an `sdk-rust` variant's crate. `run.finish()` hands the facts to the constructor, writes its document and returns a `Finished` whose `assert_proved()` fails the test with a `VariantNotProved` unless the document says `proved` and nothing failed. A run dropped without `finish` fails the test with an `UnfinishedJourneyRun`. `JourneyRun::start_file(path, …)` runs a Journey file outside the catalog, for test support's own tests.
  - **A crash or fault test records an Observation log**, `ObservationLog::for_test(&env)`: plain `Record`s of a host, an optional simulated time and an `Operation` (`Fence`, `Write`, `Commit` and `Visible` for delivery; `Limit`, `Reserve` and `Settle` for Usage; `Fault`; or the test's own `Other`). Values are `ValueDigest`s and security values `Redacted`. When the test fails, the log is written as NDJSON to `observation-log.ndjson` in the kept folder, listed as `goodfetch-observation-log=<path>`. `fencing(&log, class)` judges delivery by Guarantee class and `limits(&log, allowed_loss)` judges Usage; each returns the first `Violation` with the records that show it. `kill_at(&process, &moment, &mut log)` kills a process started through `env.spawn` at a `Moment` (the n-th protocol message whose JSON-RPC `method` is the event), drawn by `Moment::drawn(env.seed(), events, occurrences)`, and records the kill. A moment drawn among requests the test leaves unanswered needs them all in flight at once whatever the machine: the home's governor holds that many HTTP admissions at pressure (Foxhound's `in_flight_whatever_the_machine`), as one sized by a loaded machine's memory admits only its floor of 1.
  - **A test that reads an Attached engine's or the stdio MCP server's stdout reads it through `StrictStdout`**, with the child's logging at `trace` and its stderr piped: `StrictStdout::of(&process)` for a child of `env.spawn`, `StrictStdout::from_output(&output)` for one run by `command(&env, program)`. It yields each newline-delimited JSON-RPC 2.0 message (request, notification or reply) as a plain JSON value, and any other line fails the test, naming the line and showing its bytes escaped with the child's stderr: a log line, an ANSI escape, a byte-order mark, bytes that are not UTF-8, a truncated message, a partial line at the end of stdout, or JSON that is not a JSON-RPC message, a batch included. Iterating panics with a `StrictStdoutError`; `try_next()` returns it; each line waits at most `MESSAGE_DEADLINE` (10 s), or what `within(deadline)` sets. `is_quiet_for(quiet)` says whether the child writes nothing for a short duration the test sets, such as while a call that no credit lets through must stay unanswered; a line written meanwhile is kept for the next read. It proves only an absence, so a test uses it after a state that makes the absence the product's, never to wait for something to happen.
  - **A process fault an SDK or the CLI must handle comes from `goodfetch-scripted-engine`** ([ADR 0069](../adr/0069-sdks-and-the-cli-are-tested-against-a-scripted-engine-and-the-binary-of-the-same-commit.md)), playing a script of `test-support/fixtures/engine-scripts/` (`engine_script(name)`), whose format is `Script`: a `description` and `steps`, each one of `expect` (a method and its params, matched on their canonical JSON), `reply` (a `result` or the wire's `error` object, sent with the ID of the request the last `expect` of a request matched; an expected notification between them, such as that request's `$/cancel`, leaves it to answer), `send` (a `request` to a Client's handler or a `notification` such as an event), `await_reply`, `stall`, `close`, `raw` (text that is not JSON-RPC) and `exit` (a code, and a `stderr` of `line` and `times`, written that many times to its stderr just before it exits, as a crash prints its output). An SDK reaches it as an Attached engine: its Product's engine-path variable in the environment map names the executable, which the SDK starts as `attached-engine`, and the test copies the script to `ATTACHED_SCRIPT` (`scripted-engine/script.json`) under the map's `GOODFETCH_HOME`; `--script <file> --mode stdio [--record <file>]` names one directly. The CLI and an SDK reach it as a Daemon through `--mode socket`: it writes the Daemon's runtime file, `RuntimeFile` (`endpoint`, `token`, `version`, `pid`), at `RuntimeFile::path(home, version)`, `<home>/<major>/daemon.json` under the map's `GOODFETCH_HOME`, mode `0600`, and listens on a `0600` Unix socket beside it (in its own folder under `/tmp` when that path is too long for the OS, as on macOS, which the test's `TestEnv` removes at teardown when a killed engine left it) or on loopback TCP on Windows (ADR 0024), and holds the Daemon's serving lock, `DAEMON_SERVING_LOCK` (`daemon.lock`) beside the file, until it exits, as a live Daemon does: a Client takes a runtime file whose lock nobody holds for a dead Daemon's. `--token` (default `SCRIPTED_DAEMON_TOKEN`) and `--product-version` (default this commit's) fill the file; the token check is the script's own `expect` of a `hello` carrying it. It prints `{"address", "runtime_file"}` once a Client can find it, which `reported_address` reads, and removes the file and the socket when the play ends, unless the script ends with `exit`, which leaves them as a crashed Daemon does (`daemon/dead-pid.json`). Started as `daemon launched`, as a Product's `daemon start` starts its Daemon, it plays `ATTACHED_SCRIPT` in socket mode and prints the runtime file itself once ready, as a launched Daemon does; the conformance harness starts a Daemon target this way. `--mode tcp` listens on loopback port 0 and prints `{"address"}`. In both, the one Client is accepted when a step first reads or writes. `--mode http` plays a Daemon's HTTP listener (ADRs 0027 and 0070) on loopback port 0 and prints `{"address", "token"}`: each request posts one JSON-RPC message, played only behind `--token` as its bearer token (any other request is answered `401` with `WWW-Authenticate: Bearer` and never played), and is answered once the play reads its next message or ends, with every line the play wrote since it, or `202` when it wrote none for a notification; a request still unanswered when the play ends gets no answer, as from a Daemon that dropped it. The Client keeps one connection for the play, accepted when the play first reads. It records every message it read and wrote, one JSON line each, at `ATTACHED_RECORD` beside the script, and on a message no step expects, one that is not a JSON-RPC 2.0 message (no `"jsonrpc": "2.0"`, or both `result` and `error`), or a step left unused it exits 1 with `goodfetch-scripted-engine: <code>: <reason>` on stderr, `<code>` being `unexpected_message`, `unused_step` or `nothing_to_answer`, or `publish_failed` or `listen_failed` when it cannot start listening; a failed play keeps its own code even when removing its runtime file fails too. A test matches the code. A Quick-suite test of `goodfetch-test-support` validates every message step of the corpus against the committed bundle and catalog, and refuses a method that neither the catalog nor the connection has (the Client's `hello`, `$/cancel` and `$/credit`, the engine's `$/events` and `$/chunk`) and an Error code the catalog does not define; `raw` steps are skipped, and a `send` request is checked as a JSON-RPC request only, until the catalog declares the requests an engine sends a Client.
  - **A test of run state crashes SQLite through the crash VFS**, `CrashVfs::register(name, seed)` (name from `env.unique_name`, seed from `env.seed()`): the code under test opens its database with `vfs.name()` as its VFS value. `vfs.crash(CrashKind::Process | CrashKind::PowerCut)` crashes the instance and returns the `Crash`, which says what `Landed` of each file's unsynced writes; `vfs.fail_at(index, IoFault::Error | IoFault::Full)` injects a fault at the operation numbered `index` (`vfs.operations()` is the next one's). `after_crash(&vfs, path)` opens the database again and fails with `AfterCrashError::Damaged` unless `PRAGMA integrity_check` passes; the test checks its acknowledged commits on the connection it returns. Files live in memory, so the database's path is a name, not a file in the test's folder. `unique_name` counts per `TestEnv`, so a model-based test that registers a VFS in each case adds the case's own folder name to it.
  - **A test of a store's failing disk damages its file with `damage_table(path, table)`**: the pages at the root of the table and of its indexes overwritten with bytes that are no B-tree page, the WAL first copied in, so SQLite meets them as it meets an I/O error. `wal_of(path)` is where the file's write-ahead log is.
  - **A test that power-cuts a real executable mounts its folders through LazyFS** (Linux), `LazyFs::mount(dir)`, in a setup made with `TestEnv::for_lazyfs()`: its folder is in `/tmp`, or in the folder `GOODFETCH_LAZYFS_FOLDER` names, whatever `TMPDIR` says, because the operating system refuses a user's FUSE mount outside some folders (Ubuntu's AppArmor profile of `fusermount3` allows `$HOME`, `/mnt`, `/run/user/<uid>`, `/media` and `/tmp`), and such a refusal fails with `LazyFsError::MountRefused`, which says so. The folder keeps its path, its files seen through the pinned LazyFS build that `GOODFETCH_LAZYFS` names, whose cache holds every write until it is synced. After the kill, `clear_cache()` drops what was never synced and returns once LazyFS says so; dropping the value ends the mount, syncing every file first as a clean shutdown would, and a second `mount` of the folder is the remount after the reboot. A mount that cannot be made, or a LazyFS that is not set, fails with a `LazyFsError` carrying LazyFS's output, never a skip. `just lazyfs-test` fetches LazyFS's pinned source archives (`test-support/lazyfs/sources.toml`, each checked against its SHA-256 by `xtask lazyfs fetch` before the deny), builds them (`xtask lazyfs build`, needing cmake, a C++17 compiler and FUSE 3) and runs the `lazyfs::` tests, which nextest's profiles otherwise leave out.
  - **A test that fills a size-capped filesystem runs its executable over a tmpfs** (Linux; the Storage conformance cases and the Daemon log cases, ADR 0122): `tmpfs_mounted(&env, folder, size, program)`, or `tmpfs_mounted_home(&env, size, program)` over the Goodfetch home with its `logs` folder kept on the test's own disk, is a command that mounts it in a user and mount namespace of the started process (`ci/os-services.sh setup`'s `unshare`), failing at once, naming the restriction, when that `unshare` cannot map the test's user to root. `read_only_mounted(&env, folder, program)` mounts a read-only one the same way. The test reaches the filesystem through `inside_mount(pid, path)`, fills it to a given room with `fill_filesystem(pid, folder, room)` and frees it with `free_filesystem(&filler)`.
  - **A test that searches what `tracing` wrote for a value no log line may hold runs its work under `logged(work)`**: every level, without colour, beside the work's answer.
  - **A SQLite format's corpus writer dumps its store with `sql_dump(&connection)`**: every table's schema and rows, then its indexes, as SQL text that `xtask compat` reads, byte-stable (tables and indexes in name order, rows in `rowid` order).
  - **A layer's SSRF runner applies the one table** ([Egress and hostile input](security.md#egress-and-hostile-input)): `SsrfTable::committed()` reads `test-support/fixtures/ssrf/cases.toml`, whose JSON Schema `xtask codegen` commits, and `run_cases(cases, public, layer)` calls the layer once per `SsrfCase` (its URL, route, scripted lookups, redirect, fetches, domain policy and target, a target written `public` being the layer's public stand-in `public`), compares the `Outcome` (the typed refusal, and the addresses connections reached, from the Proving ground's connection record end to end) with the case's expected refusal, and fails with every case the layer let through. `ScriptedResolver::new(case.script(public))` answers a case's lookups in order, `public` being the layer's public stand-in; a lookup beyond the script or of another name panics with a `LookupFailure`, again when the resolver drops if the code under test swallowed it. A Quick-suite test fails when a block of the committed IANA registries that is not globally reachable has no case, and parsing fails on a case of an unknown family. Collie's runners take their cases through `Runner::committed(layer, file!(), "<test function>")`, which gives each the cases of the families its entry in `test-support/fixtures/ssrf/layers.toml` names, and run them with `Runner::run(controls, public, layer)`, which also runs its positive controls (each must be let through and reach its target) and fails when it has none.
  - **A layer's hostile-input runner applies the family tables** ([Egress and hostile input](security.md#egress-and-hostile-input)): `HostileTables::committed()` reads `test-support/fixtures/hostile/` (`header_values`, `secret_redirects`, `paths`, `schema_refs` and `limits`), whose JSON Schemas `xtask codegen` commits. Each `HostileCase` gives its `input`, the `expected` typed error, matched on its Error code, and `served_by`: the Proving ground task whose page serves it end to end, a page `waiting_on_owner` or a `missing_page`, or `program_input`. A case with no expected error fails the parse, and a Pre-merge test fails on a page the Proving ground has no task for. A path case runs on the OSes its `os` names, `cases_here()` on the running one. A missing uv or pip fails with `ToolMissing`, no engine with `ContainerEngineMissing` and an image not pulled with `ImageMissing`, never a skip. Its tests are `tests/integration/test_install.py`, which the Release suite alone collects.
