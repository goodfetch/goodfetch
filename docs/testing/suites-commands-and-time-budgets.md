## Suites, commands and time budgets

Decided in [ADR 0061](../adr/0061-three-test-suites-each-run-by-one-just-command-under-a-time-budget.md), with the private-period matrix in [ADR 0108](../adr/0108-while-the-repository-is-private-the-release-suite-runs-its-macos-cells-on-the-owners-machine-and-its-hosted-cells-under-a-ceiling.md) and the private-period pull-request tier and hosted budgets in [ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md).

### The three suites

Each suite runs everything the suite before it runs.

| Suite | What it adds | Command | Runs in CI |
|---|---|---|---|
| Quick | Format and lint checks; in-process tests of what changed (Rust unit tests in `src/`, never `tests/it`); the committed format fixtures; `xtask codegen --check`, `xtask wording` (ADR 0097), `xtask journeys check` (ADR 0063), `xtask clients check` (ADR 0069) and `xtask affected`'s own tests | `just quick` (`just quick all` for everything) | First job of every pull request, over the whole workspace |
| Pre-merge | The `tests/it` of every touched crate and its dependants; conformance on the local Proving ground; touched Sinks against their containers (every Sink until the merge queue exists, ADR 0032); touched SDKs, adapters and Integrations on one runtime; the browser tests on Chromium; docs examples; ADR 0032's static checks; the Journey task lists' drift check, `just journeys-tasks --check`, and the rule on each Journey variant's tests, `just journeys-tests` (ADR 0063), the Feature check over every runner's declarations, `just features-tests` (ADR 0072), and the Client conformance case-list check over Vitest's listing, `just clients-tests` (ADR 0069) | `just pre-merge` (`just pre-merge all`) | Every pull request, on Linux |
| Release | Everything, for every package, on the full matrix of ADR 0024; deployment-target smoke runs; tests that need released binaries | `just release` (this host's cell), `just release-ci` (the whole matrix on CI) | Merge queue, nightly, every release |

- **A Quick-suite test starts no process, browser or container and binds no socket.** Anything that does is a `tests/it` test, or its runner's equivalent.
  _Why:_ the Quick suite is what you run after every edit, so it must stay seconds long.
- **The Chromium build gate holds pinned tests in no suite** ([Goodfetch Chromium](goodfetch-chromium.md)), because they need the build's source tree. Like the test V8 build job ([Security](security.md#confinement)), it is its own required check beside "all green".
- **Checks that are non-deterministic by nature are in no suite**: real SaaS Sinks, live models, the online Proving ground, real vendors, Chrome's beta and dev channels, the benchmark, the Performance series. They keep their own tiers.
- **The Release suite gates every merge**, through the merge queue. Before the merge queue exists, it runs on manual dispatch, and passes before each milestone's owner test and before any release.
  _Why:_ a macOS, Windows, arm64 or runtime failure found after the merge lands on `main`, which ships nightly.
- **While the repository is private, a manual-dispatch Release run is a smaller matrix** ([ADR 0108](../adr/0108-while-the-repository-is-private-the-release-suite-runs-its-macos-cells-on-the-owners-machine-and-its-hosted-cells-under-a-ceiling.md)):
  - Linux x64 and arm64 (glibc and musl) and Windows x64 run on GitHub-hosted runners;
  - macOS arm64, and macOS x64 under Rosetta 2 (labelled `macos-x64 (Rosetta 2)`), run on the owner's machine;
  - native macOS Intel and Windows arm64 first run once the repository is public: the first release's build publishes nothing until the release pipeline's Release run passes on the full native matrix, while GitHub still offers an Intel macOS image (fall 2027 at the latest). Rosetta 2 serves the macOS x64 cell only while the owner's machine runs macOS 27 or earlier; macOS x64 support past either date is decided in [#546](https://github.com/goodfetch/goodfetch/issues/546).

  The owner's-machine cells run only on `main`, so no pull request or fork reaches that machine through the Release suite; with no branch protection while private, write access is the boundary. A passing run is every one of those cells green on one commit of `main`, from one or more dispatches (`just release-ci` takes a commit of `main`, its head by default, and `main`'s workflow refuses any other). A cell held back by the ceiling, timed out in the queue or failed with no failed test step may run again; a cell with a failed test step leaves the commit red (ADR 0064). The workflow is `.github/workflows/release-suite.yml`: its first job runs `xtask release-suite plan`, and `xtask release-suite verdict --commit <sha>` says whether every cell is green on a commit across its dispatches, as `just release-ci` prints after each run, on any branch, naming each cell that is not green, a skipped one included. The cells are `linux-x64-gnu`, `linux-x64-musl`, `linux-arm64-gnu`, `linux-arm64-musl`, `windows-x64`, `macos-arm64` (with the visual projects beside it, in the pinned image in the owner's machine's VM) and `macos-x64`; the runtimes follow [SDK and CLI tests](sdk-and-cli-tests.md#where-they-run): every line on `linux-x64-gnu`, the oldest and newest elsewhere, free-threaded CPython on every Linux cell. Each cell installs its set of `ci/runtimes.toml` (`release-linux-x64-gnu`, `release-linux` or `release-other`) through `.github/actions/host-tools`.
  _Why:_ the full matrix on hosted runners costs about 1,350 of the 2,000 included minutes a run, nearly three quarters of it macOS.
- **While the repository is private, the pull-request tier is the local gate, `just merge`, on the Hetzner server the owner rents** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendments of 2026-10-19, 2026-10-21 and 2026-10-22). GitHub Actions runs the Release suite alone: every other workflow, the pull-request tier's included, is disabled in the repository's settings. `just merge` runs `just pre-merge` natively on the server, without a VM: the host steps, `just perf` under Valgrind and the tests only Linux decides on the server itself, and the visual projects in the pinned Playwright image under rootless Podman. The tier's checks that no gate step runs, and the test-health jobs, run from the server's cron or nowhere ([After merge](flaky-tests-and-live-checks.md#after-merge)). ADR 0135's first design, the tier on the owner's machine in a Lima VM recreated for each job, from branches of this repository only, is what the two rules below describe; it applies again only if the owner's machine takes the tier back. Once the repository is public, the tier goes back to hosted Linux runners.
- **Run the VM's userland as Linux x86-64, under Rosetta for Linux.** The VM is a Lima VZ VM, Linux arm64 with Rosetta for Linux on, and the tier's toolchains, tools and images are their x86-64 builds, so the checks pinned to Linux x64 (visual tests, count snapshots, `xtask perf`, the size estimate, `cargo fuzz check`, the in-diff mutation job) keep their platform. A check that fails under Rosetta runs natively on Linux arm64 while private, alone, with a note in the ADR that pins it. If Rosetta for Linux ends with macOS 27, every check moves to Linux arm64 ([#546](https://github.com/goodfetch/goodfetch/issues/546) decides it).
  _Why:_ 183 pull requests were opened in the 30 days before 2026-10-18, and at 10 hosted minutes each the tier alone would take more than four times the minutes left.
- **When a check waits for the owner's machine, say so and wait.** A job queues while the runner is offline and fails after 24 hours; the machine never sleeps on power. Before merging, read `gh pr checks <number>`, and never merge while "all green" is pending or failed. If a check is pending and `gh api repos/goodfetch/goodfetch/actions/runners` shows the `owner-machine` runner offline, tell the owner. A failed job with no runner name in `gh run view <run-id> --json jobs` never reached the runner: re-run it with `gh run rerun <run-id> --failed` once the runner is online. A job that reached the runner and failed is an ordinary failure, never re-run, except a job with no `Test` steps whose figures are deterministic, re-run once the owner accepts its change (`perf`, and `size` where it gates). The owner gets GitHub's default Actions notifications of failed runs.
- **Keep the hosted jobs of manual-dispatch Release runs under 600 included minutes a month.** The organization's private repositories share the account's 2,000, so at most 400 are left for every other hosted job, which ADR 0135 budgets: the ingest after each run with a hosted job, 90; one daily ingest job for the runs that ran only on the owner's machine, 60; and the checks run by hand (ADR 0065's Live checks, ADR 0043's online conformance), 90, whose recipes refuse a dispatch that would pass it. That is 240; the other 160 stay unallocated. A line past its budget opens or updates a `needs-triage` issue from the daily test-health job. Count in Linux-equivalent minutes: Linux 1, Linux arm64 1, Windows 2, macOS 11. The workflow's first job reads the month's count and estimates the run from its cells' last recorded durations (270 before any is recorded). If the run would pass 600, no hosted cell starts: the summary names the minutes needed and the date the month turns, the run fails, and no diagnostic run follows. A dispatch off `main` starts its hosted cells only if a run on `main` still fits after it. A run whose own estimate passes 600 still starts as the month's first Release run on `main` whose hosted cells start, and opens a `needs-triage` issue, like a budget breach.

### Commands

- **Run `just quick` before every push, once.** `just hooks` installs an opt-in pre-push hook that does it, unless a green `just quick` already passed on the pushed tree ([Checks by role](checks-by-role.md)). With the hook on, the push is that run: run it by hand only when your role's done check asks for it, and the hook then does not run it again on that tree. On every push the hook first judges the pushed commits' sign-offs and subjects ([Checks by role](checks-by-role.md)). It starts with the compiler cache's coverage (`just compiler-cache`, [Compiler cache](#compiler-cache)), then the checks of the change's commits, as the gate's forms start: their sign-offs (`just dco`), their subjects (`just commit-messages`), the floor guard (`just floor-guard`) and the scan for secrets (`just commit-leaks`), which take seconds and which the gate would otherwise first run at merge, all over the change's own commits since its base below (on a push the hook's own check of the sign-offs and subjects comes first, a second of reading commits), then the checks the change's own gate runs at merge, from `xtask affected`'s `gate=` line as `just merge` picks its form (`ci/quick.sh`): for a change of documents alone (`gate=docs`) `just lint-documents`, as the docs gate runs it, and no code lint or suite; for any other change the licence allowlist (`just notices`), `just lint` and the Quick suite over what changed, read against the change's base: the commit the push's remote ref holds, else the branch's upstream off `main` when it is another branch, never its own remote copy, else `origin/main` ([Checks by role](checks-by-role.md)). `just quick all` runs the allowlist, every lint and the whole Quick suite, whatever changed. Every step runs even after one failed, the steps of `just lint`, `just lint-documents` and `just fmt-check` included (`ci/keep-going.sh`), and the run ends with a summary naming each failed step and its log under `target/steps/`, then fails; a step that needs an earlier one's output (Clippy the lockfile check, the `xtask` checks xtask's build) is skipped and named when that one failed. The Quick suite runs after a red lint too, since a lint failure leaves the tests' results as meaningful, so one run shows every lint and test failure of a change. Only a failed `xtask affected` ends the run early: without its `gate=` line the tier cannot tell which checks the change takes. A tree is recorded green only when every step passed.
  _Why:_ when a red line ended the recipe, each run showed one defect, and implementers ran `just quick` 3 to 7 times a ticket (the 2026-11-06 retro).
- **`just test <suite> [packages]`** runs one suite's tests without lints. CI jobs call it, and so can you.
- **`just repeat <count> --test <runner>=<test ID>`** runs a test `count` times whatever each run's result, as a diagnostic run does; `--quarantined <n>` takes the quarantine list's n oldest entries, and `--tests-file <file>` a file of `<runner>=<test ID>` lines, as the stress run hands it its selection. A runner whose arguments would pass the operating system's limits (Linux's 128 KiB for one argument, `getconf ARG_MAX` for all) runs in batches, each with the same counts and its part of the tests, each batch's JUnit file kept as `<runner>.<batch>.xml`. Every run counts, so it is no retry. With `--until-red`, given first, as the stress run gives it, the run stops at the end of its first red iteration: nextest runs one iteration a command (`--stress-count=1`, since nextest's `--max-fail` ends a stress run in the middle of an iteration), each iteration's JUnit file kept as `<runner>.<batch>.<iteration>.xml`, and after a red one no later iteration, runner or count runs. A selected LazyFS power cut (`lazyfs::`) runs past nextest's default filter where `GOODFETCH_LAZYFS` names a LazyFS build, and fails the run elsewhere rather than being dropped: a Linux host that runs the local gate builds LazyFS once (`just lazyfs-build` prints the executable's path), keeps that `bin/` folder outside the gate's checkout, whose `target/lazyfs/` each gate clears, and exports `GOODFETCH_LAZYFS` to it.
- **`just stress [base]`** runs the stress run of [Before merge](flaky-tests-and-live-checks.md#before-merge) against `base`, the merge base with `origin/main` by default. `just merge`'s full gate gives the head of the last full gate as `base` when a test reads what merged since, so the tests the quick merges since then added or changed run too, and the deleted tests and their trailers are read from that head (`xtask gate plan`'s `stress.base`, [Before merge](flaky-tests-and-live-checks.md#before-merge)). The incremental local gate narrows it, `just stress "<base>" <since> <earned file> "" <workspace member>…`, `base` empty for the change's own: only the new and changed tests of the workspace members the change since an earlier gate run's head reaches, plus each test whose file that change changed; Vitest, Playwright and pytest keep every one of their new and changed tests, so they run in the head's order as in a full run ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)). A nextest test of a crate with no failing test keeps its earned passes, the clean passes a red stress run gave it, and each later run gives it what its 20 or 200 still owes, while the crate's inputs, the host fingerprint and the base are the same, within a day of the start of the run that gave the first one; `xtask gate plan` writes them to `target/gate-runs/<head>.earned`, and says in its plan who keeps them. Any failure takes its crate's earned passes, and a red run its nextest files do not account for takes every crate's: nextest exiting other than 100, its status for a failed test run, or 100 with no failing test in its files, as a run cancelled during its tests can end.
- **`just preflight [base]`** runs, on HEAD, what the full gate most often went red on, before `just merge` of the pull request that finishes a spec, which takes it, in that pull request's own worktree: the floor guard against `origin/main` (`just floor-guard origin/main`), the Pre-merge suite over the change since the merge base with `origin/main` (`just test-affected pre-merge`), the stress run against the head of the last full gate that passed, the second parent of the newest merge on `origin/main`'s first-parent line whose message holds `` Merged on the local gate: `just pre-merge all` ``, as the full gate's own (`just stress <base>`; `base` gives another), and `just counts`. Every step runs even after one failed, and the run ends with the summary of `ci/keep-going.sh`. It takes no gate lock, so it runs while a gate runs, at its cost in load.
  _Why:_ six of nine full gates went red on defects the branch could show without the gate's lock: deleted tests without a `Quality-change` trailer, Pre-merge suite failures, stress flakes and register rows (the 2026-11-13 retro).
- **`just gate-backstop [ref]`** is the incremental gate's backstop ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)), daily from the gate host's cron on `main`'s head, where `just merge` lands, from the main checkout, by the entry in `ci/gate-backstop.crontab`: `just pre-merge all` in full (`GOODFETCH_GATE_FULL=1`) in a gate worktree of its own, then each result an incremental run of `just merge` on the same tree reused and the full run found red, a selection miss, listed in `~/gate-backstop/misses.txt` and failing the backstop; a suspect crate of a red per-member step reruns alone to confirm it. Each crate whose stress result in any merge since the backstop's last green run counted earned passes, whatever that merge's tree, is stressed again at its whole counts against that merge's base, whatever the full run found, since the full run's own stress run selects nothing on `main`'s head; a red is a miss, as is a stress run that cannot run, a merged run's record that cannot be read, a full gate's merge whose record is gone, and `just merge`'s whole records folder gone with commits merged since. With no green run yet, only the folder is judged. A day with a miss, a failure or a skip is no green run, so the next day reaches the same merges. A test renamed since runs at its new name; a test or crate gone since has nothing left to stress, and the selection notes it in the run's log. A run is the `ci/` of the commit it tests, whichever script started it. Its cron entry names `GOODFETCH_LAZYFS`; without a LazyFS build a run on Linux lists itself as skipped before any step. Fix a same-tree miss in the gate's selection or evidence, with a test that plants it. A re-stress miss first needs reading, since that run covers every later merge's tests too: it may be a bad reuse, or a flake in another merge's test, which ADR 0064 quarantines or fixes where that test lives. When nothing can clear a miss, a base that can never run again or a record gone for good, the owner stresses by hand what can still run, then runs `GOODFETCH_GATE_BACKSTOP_SINCE=<commit> just gate-backstop` once: it starts from that commit, which `main` must hold, instead of the last green run, must still pass in full, and ends its `results.txt` line with `since=<commit>`. Nobody edits `results.txt`. **The backstop has a switch and is off since 2026-11-10** (the owner's decision, ADR 0135): `ci/gate-backstop.state` holds `on` or `off`, and only the owner changes it. A run reads the one of the commit it tests: switched off, it starts nothing, takes no lock, writes no line and ends well, so its cron entry may stay. While it is off, nothing runs the full gate on `main`, compares it with the results `just merge` reused, stresses earned passes again, sweeps the tracker's `ready-for-agent` issues or sweeps the worktree the test-health runs share; the merge cap below counts nothing. The rest of this entry is what it does once switched on. A backstop that finds `just merge`'s gate running waits for it before its full run, and reads the free disk it needs once the gate has ended (below). After its day's line, green or red, it sweeps the tracker (`just existing-code-sweep --apply`, ADR 0144): each open `ready-for-agent` issue whose `Existing code` list no longer holds on `main` gets `needs-triage` and one comment and loses `ready-for-agent` (docs/agents/triage-labels.md), and a sweep that fails only warns. Then, still holding its worktree's lock, it sweeps that worktree's `target/` (`just sweep-target`, twice): every profile but `ci-test` keeps each build unit a build read in the last two days, which its own run and the mutation run do daily, and `ci-test`, which the weekly constrained test-health run alone builds, each unit one read in the last fifteen, so a run that skipped once finds its build as it left it; a day that skips or a run that is stopped sweeps nothing, and a sweep that fails only warns.
- **A red step ends no form of `just pre-merge`** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendment of 2026-11-10). Every other step still runs, the steps beside the host's to their own end; each step of the full gate records its result, so the next gate on a descendant head reuses the green ones the fix does not reach; and `ci/pre-merge.sh` ends by naming every red step with its exit status, `error: the gate is red: <n> steps failed, and every other step ran`, then one line a step; the list of what the host skipped and, under `just merge`, the kept-results line and the sweep's follow it in the log. It fails with the first red step's status, and any red still means no merge. So a pull request meets all its reds in one gate: fix them together, then start one gate. A red gate holds its lock as long as a green one. Since the gate goes on, the steps after a red one clear or write over its result files (the stress run removes nextest's JUnit files, each suite writes the other runners' anew), so the gate copies them, as they are when a red step of the host's that it records ends, to `target/red-steps/<step>/`; the steps beside and the quick and docs forms get no folder. A fault of the gate itself still ends it where it is and stops the steps beside: the OS services' setup failing, a step list or plan the script cannot read, a result that cannot be recorded, or a stop.
- **`just linux` and `just visual` run, on a host that is not Linux, what only the Pre-merge suite's Linux job checks:** the tests only Linux decides (`tc netem`, the Secret Service, the IPv6 Happy Eyeballs check, the extra loopback addresses) in the CI image with every Linux OS service, and the visual projects in the pinned Playwright image, each through Docker or Podman. Without either, `just linux` is listed as skipped and `just visual` fails, as ADR 0073 has it; `just screenshots-update` writes Reference screenshots in that image while GitHub Actions is off. `just pre-merge` runs them beside its host steps, with `just perf`, and runs `just stress` after its tests. A test that only Linux decides joins `ci/linux.sh`'s selection.
- **A change of documents alone takes the docs gate** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendment of 2026-11-04). `xtask affected` prints `gate=docs` when it would print `gate=quick` and every changed path is Markdown at the top level or under `docs/`, `website/` or `rnd/`; any other path, a file no test reads included, keeps the quick gate, and no change at all does too. ADR 0037's matrix, `docs/adr/0037-v1-scope-matrix.md`, keeps the quick gate as well: `xtask codegen` builds `features/inventory.json` from it, and only `just lint` runs `xtask codegen --check` (ADR 0135's note of 2026-11-11, #2476). `just merge` then runs `just pre-merge docs`: the sign-offs, the commit messages, the floor guard and the secrets in commits, then `just lint-documents`, the checks of `just lint` that read documents: formatting, typos, `xtask register check`, `xtask features check`, `xtask wording`, `xtask journeys check` and `ci/repository-files.sh`. The code lints, the advisories, the notices and every suite do not run. A document a test reads in part counts as documents alone when the change leaves those parts as they were: `xtask affected` reads a changed Markdown file's base and head versions and splits each into parts, a part running from its heading line to the next heading of its level or above. A workspace member whose code names the document and, in string literals, some of its heading lines (`"## Quality register"`, `"### Time budgets"`) reads those parts alone, and is selected only when one of them changed; a member that names the document and none of its headings reads it whole. A change to `TESTING.md`'s Quality register also runs perf, since `xtask counts` holds the counted rows to its limits. So a prose edit of `TESTING.md` takes the docs gate, and an edit of its register, its Time budgets or its Cloud-readiness list the full gate. A test that reads a part finds it by its heading line, which its code names.
- **`just merge` refuses once 10 merges have landed on `main` since the backstop's last green run** (`ci/merge-cap.sh`, ADR 0135's amendment of 2026-11-04). A green run is a line of `~/gate-backstop/results.txt` (`GOODFETCH_GATE_BACKSTOP_LOG`) with `gate=pass misses=0`; the cap counts the first-parent commits of `origin/main` since the latest green run whose commit `main` holds, and each merge prints the count. 10 is twice the most merges `main` took in a day since the local gate began (5, on 2026-11-03): with the backstop daily, one red or skipped run leaves a day of merges, and a second stops them until the backstop runs green again. Until the backstop's first green run the cap counts nothing, blocks no merge and says so; when green runs exist but `main` holds none of their commits, it refuses. Only the owner overrides it, with `just merge <number> --past-cap`, which the merge commit records. While `main` holds the backstop's switch as `off` (`ci/gate-backstop.state`), no green run comes, so the cap counts nothing, blocks no merge and says so on each merge; a word other than `on` or `off` there refuses the merge.
- **`just merge` refuses to start a gate under 30 GB free on the file system of the gate's `target/`** (`GOODFETCH_GATE_MIN_FREE_GB`; #1822), which can be another disk than the checkout's, and names it. That variable is the launcher's alone: the host fingerprint leaves it out, so a gate started under another floor still reuses earlier results. On Linux it refuses a full gate, before any step, unless `GOODFETCH_LAZYFS` names an executable LazyFS build (`just lazyfs-build`), because the stress run, after the whole Pre-merge suite, refuses a selected `lazyfs::` test without one, and which tests it selects takes a build to find. No other variable is a prerequisite: `just pre-merge` sets up the OS services and their variables itself, and no step refuses an unset `TMPDIR`. A failing gate's log and its JUnit files are kept for 30 days in the common Git folder's `goodfetch-gate-failures/<time>-pr<number>-<head>/`, which no checkout's clean, worktree removal or sweep of the temporary folder reaches; the issue of a flaky candidate links that folder (#2087). Its `red-steps/<step>/` holds the JUnit files of each red step the host ran and recorded, as that step left them, which are the ones to read for a red Quick or Pre-merge suite: the files at the folder's top are what the last steps wrote. Its `steps/<run>/` holds each step's own log of a run that keeps going (`just quick`'s under `steps/quick/`), which that run's summary names under the worktree's `target/steps/`: read them here, since the next gate checks its own head out there. After every gate, still holding the gate's lock, `just merge` runs `xtask sweep-target` on the gate's `target/` (`just sweep-target`): it removes each build unit whose fingerprint no build has read since the day before the gate started, with its files, and keeps whole every unit a build read, which the next gate reuses. A sweep of the merge gate's `target/` runs only under its lock, never during a gate.
- **`just merge` outlives the shell that starts it** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendment of 2026-11-08). The command starts the gate again in a session of its own, with its output in the common Git folder's `goodfetch-gate-logs/<time>-pr<number>-<caller>.log`, kept for 30 days, and follows that log: it prints the gate's output on its standard output and ends with the gate's exit status. Stopping the command or closing its output stops nothing: the gate still merges, and its log says how it ended. To stop the gate, signal the process the command names, which `.claude/worktrees/merge-gate.lock/pid` also holds: SIGTERM stops its steps, skips the sweep and releases the lock, and the command, if it still runs, ends with 143. The gate's steps start with no signal ignored, as under a foreground command.
- **`just merge`'s gate waits for the run in the backstop's worktree, a test-health run or the backstop's own, and the backstop waits for a running gate** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)'s amendments of 2026-11-08 and 2026-11-10), so no two of them run their suites on the host at once. The gate first reads the pull request and refuses at once, holding nothing, one it cannot merge: closed, a draft, past the merge cap or in conflict with its base's tip. A head without that tip is not refused: once it holds its lock and any wait has ended, the gate merges the tip into it, pushes the merge commit to the pull request's branch without force and gates and merges that commit (ADR 0135's amendment of 2026-11-17). Then, holding its lock, it prints that it waits and for which process, and starts when that run ends: a constrained or mutation run's 120 or 150 minutes and its setup at most; for the backstop, with no limit, its whole run, which is the full run, the comparison, the suspects' reruns, the re-stress and the sweeps. A gate that waited reads the pull request again, so it judges the head, the base and the merge cap as they are once the wait has ended. A test-health run marks the backstop's lock it holds with a `test-health` file. A backstop that finds a gate running holds its worktree, names that gate in its lock's `waits-for` file, says so in its log and starts its full run when the gate ends, however long that takes; it never skips its day for a gate, and tests the head it read when it started, so what that gate merged is the next day's. The gate it named does not wait for it in turn, and any gate started later does, since the backstop was there first. Each takes its own lock before it reads the other's, so of the two starting together at least one sees the other; a backstop that sees the gate lets it go first, and a gate the backstop did not see waits for the backstop. A backstop that finds its own worktree held, by a test-health run or by a backstop still waiting, lists its day as `gate=skipped (the backstop's worktree is busy: process <n>)`. A lock names when its holder started (`started`) beside its process (`pid`): a lock whose holder ended holds up neither side, and neither does one whose process number another process has since taken, so a run that died leaves nothing to wait for. Only two start readings that differ make a lock stale: a start that cannot be read leaves the lock judged by its process alone, since a live lock read as stale would let two suites run together unseen, where a dead one read as live makes a caller wait in plain sight. A stop ends the suites before the lock goes: SIGTERM, SIGHUP or SIGINT to the gate or to the backstop stops its steps, waits for them and then releases its lock, and a stopped backstop writes no line for its day. SIGKILL runs no trap: the suites of a gate or backstop killed that way run on with no lock held, so never stop either with it; if one was, end the `just pre-merge` it left before anything else starts.
- **`just counts`** prints each counted row's figure and fails over its limit, and `just counts --valgrind` each row read under Valgrind ([Quality register](../../TESTING.md#quality-register)). B1's `F2.prepares` and `F3.prepares` and B3's `E2.log_prepares`, `E2.prepares` and `E3.prepares` need Valgrind, for Callgrind's count of statement preparations, B1's `F3.counted_work_constructions` for its count of `CountedWork`'s constructor, and B1's `E1.handled_page_wire_share` for its count of instructions beneath the wire's functions.

A change to `kennel/` selects no other job; `just lint` checks the Kennel's formatting, lockfile and `cargo-deny` rules on every change, and that its manifest keeps the root's lints, `rust-version` and versions of the dependencies both declare (`xtask kennel-manifest`), and `just audit` its advisories. On a host other than macOS, such as the display-less Linux gate, it tests the non-graphical crate and type-checks the graphical one for macOS (`aarch64-apple-darwin`) and, on Linux, for the host, whose Tray runs on GTK 3; each type-check is listed as skipped without its Rust target or, on Linux, the development files of GTK 3 and libdbus (`libgtk-3-dev`, `libdbus-1-dev`), and fails in CI.

Locally it diffs the working tree, uncommitted changes included, against the merge base with `origin/main`, or with the revision `--since` names, as `just quick` gives it its change's base. Rust selects the changed crates and every crate that depends on them (`crates=`), so dependants run too. A crate whose tests run another crate's executable through the test tool manifest names that crate in `[package.metadata.goodfetch] runs`, and a pnpm or uv package names it in its `package.json`'s `goodfetch.runs` or its `pyproject.toml`'s `[tool.goodfetch] runs`. ### Time budgets

Budgets are the median (p50) of a job's last 20 runs in its own tier, on GitHub-hosted runners with warm caches: pull-request runs for Quick and Pre-merge; merge-queue runs (manual-dispatch runs while the repository is private), nightly and release runs for Release. Cells on the owner's machine are labelled with it and kept out of the budgets; they keep the 90-minute job cap. While the pull-request tier runs on the owner's machine, its Quick and Pre-merge budgets are measured on its runs there, labelled with the machine: each job from its start, and "all green" from the first job's start, so waiting for the machine is not counted ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)).

| Suite | Where | Budget | Hard cap |
|---|---|---|---|
| Quick | Locally, one crate changed, incremental build | ≤ 60 s (guidance) | none |
| Quick | CI, whole workspace | tests ≤ 2 min, job ≤ 10 min | 20 min |
| Pre-merge | Pull request | "all green" ≤ 20 min, each job ≤ 15 min | 30 min per job |
| Release | Merge queue | ≤ 60 min per group, each job ≤ 45 min | 90 min per job, 120 min for the queue |
| Release | Nightly and release pipelines | each job ≤ 3 h | 5 h per job |

- **The pre-push tier (T1), `just quick` through `.githooks/pre-push`, measured 2,232 s (37 minutes)** once, on 2026-11-04 on the gate host, for the change that added its floor guard and commit scan: a change to xtask, `ci/` and the justfile, so its `just lint` ran a front-end build since removed (ADR 0137) and the workspace Clippy, and its Quick suite built and ran 5,872 tests (16 s of tests). The host's load ran from 10 to 55 under other runs, and waits on a build folder shared with other worktrees count in it. The floor guard and the commit scan take seconds of it. It is far past the 60-second guidance above, which holds for one crate changed on an idle host; no limit is set for it. On 2026-11-05 its parts were measured (`.claude/handoff/wiki/t1-speed-diagnosis.md`): a 12-minute wait for a `load-guard` slot at a load of 3 to 16; on a warm build folder about 5.5 minutes of its own work; on a new worktree's build folder over 40 minutes, most of it DuckDB's C++ built again for lint's Clippy and for `xtask compat check`. A change of documents alone now runs only the docs gate's checks. The Quick suite now builds only the libraries and executables whose tests it runs: for a change to `goodfetch-foxhound` its build took 4 s instead of 14 to 17 s (2026-11-05, warm build folder, load 11 to 13), with the same tests listed.
- **While the repository is private, the hosted Release cells' hard caps are past 90 minutes** (ADR 0061's agent decision of 2026-10-23): `linux-x64-gnu` 300, `linux-arm64-gnu` 210, `windows-x64` 150 and the musl cells 120, as one 2-vCPU job holds each cell's build, tests and, on the gnu cells, both benchmark builds. A cap stops a hang; the budget above is unchanged.
- **Per-test caps stop hangs, never measure speed.** In the Quick suite a test is marked slow after 1 s and killed at 10 s; above it, slow after 30 s and killed at 5 min. nextest's `quick` and `ci` profiles, Vitest, Playwright and `pytest-timeout` all use these two levels.
- **A suite that outgrows the kill runs in parts, never under a longer cap** (ADR 0064). The page suite runs as one nextest test per Feature group, `page::the_page_suite_proves_<group>_against_collies_attached_engine`, each on a Proving ground copy and an engine of its own, through `ProtocolSuite::with_capabilities`; `page::the_page_suites_parts_take_each_of_its_capabilities_once` checks that the parts take every capability of `conformance/page/cases.toml` once, so a new capability joins a part, or a new part, in the change that declares it. A part that comes near the kill on a loaded host splits along its capabilities into parts of their own, as the clean-up part did into `clean_up_blocking` (the Filter lists, the never-block entries and `browser.block_resources`), `clean_up_blocking_off` and `clean_up_hiding`. Each part's `Covers:` line names the Features its cases cover that its run reaches, as the exercise audit reads them, and each keeps its own document.
- **No run fails for being slow within its cap.**
  _Why:_ benchmark suites on shared runners vary by about 2.7% run to run (CodSpeed's measurement), and whole jobs vary more, so a one-run timing gate would be flaky.
- **A breached budget opens an issue** through the budget check, run nightly and at the end of every manual-dispatch Release run (its `budgets` job), labelled `needs-triage`. Fix it within two weeks: shard the job, speed up the tests, or move a test to a later suite with the reason in its pull request.
  - The check is `xtask budgets`. It reads each job's last 20 successful runs in its own tier from the results store, and each suite's "all green" or group time from its runs' first attempts; it compares their median with this table, and opens or updates one issue per breached suite or job, listing the 20 durations. A tier with no row here, or a row without the budget it needs, is noted as `missing-budget`. Its tests read this table, so rewording it fails them.
  - It never fails a run. While the repository is private, it runs as the last job of each manual-dispatch Release run (`release-suite.yml`'s `budgets`); it moves to the nightly tier once that is on. A run whose last job ends before its first starts is left out of a whole-run median and noted as `negative-span`.
  - The Quick suite's "tests ≤ 2 min" is not checked: the store keeps no step timings.
- **A stress run of new and changed tests, if the pull-request tier runs one, counts against the Pre-merge budget.** Shard it to fit; never lower its run count to meet a budget.

### Sharding, caching and reports

- **Shards are deterministic:** nextest archives once per target and splits with `--partition hash:m/n`; Vitest and Playwright use `--shard`; pytest uses `pytest-xdist` inside one job. Never split by recorded timings.
- **While the repository is private, each Release cell is one job holding one shard** (`ci/release/cell.sh`): it archives the target's tests once and runs `--partition hash:1/1`. A second job per cell would spend setup minutes under ADR 0108's ceiling and pass the archive through the account's 500 MB of Actions storage. A cell that breaches its 45-minute budget is split into a build job and shard jobs named `<cell> shard <k>/<n>`, which the ceiling's estimate and the verdict count as that cell's.
- **The tests of the pinned Chrome for Testing build run on the cells that have it.** Chrome for Testing has no build for Linux arm64 or musl, where Collie launches the distribution's Chromium (ADR 0024), so `.config/nextest.toml`'s `ci` profile leaves those tests out on `linux-arm64-gnu`, `linux-arm64-musl` and `linux-x64-musl`, by name, with the reason: each launches the build from `browser_cache`'s Browser cache, or reads which build launches or whether a browser is installed. No test yet launches a distribution's Chromium on those cells.
- **Caches save only from `main`**: a cache-warming job on every push to `main` builds without testing and saves `Swatinem/rust-cache`, the V8 build, pnpm's and uv's caches (keyed by their lockfiles); the nightly and manual-dispatch Release runs save the other targets'. The merge queue saves none, since pull requests can't restore its caches. Chromium, images and released binaries are cached by digest.
- **The warming job shares the pull-request jobs' rust-cache `shared-key` and profiles.** Linux pull-request caches take priority within GitHub's 10 GB; a larger cache is declined while there is no revenue (ADR 0076), so fit within it.
- **Past 9 GB, the least recently used caches that are not the pull-request tier's Linux caches are deleted until the total fits** (`xtask evict-caches`, through GitHub's cache interface), so the priority holds before GitHub's own eviction. The pull-request tier's cache keys start with `pull-request-`, or with `v0-rust-pull-request` for rust-cache under a `shared-key` starting with `pull-request`, and a Linux one names `Linux` as rust-cache and `runner.os` write it. While the repository is private, the eviction runs at the end of each Release run on `main` (its `caches` job), since those runs save the GitHub caches and the warming job's token holds no write scope on the owner's machine.
- **While the repository is private, the build cache is a folder on the owner's machine** ([ADR 0135](../adr/0135-while-the-repository-is-private-the-owners-machine-runs-the-pull-request-tier-in-a-throwaway-linux-vm-and-private-fuzzing-nightly.md)). The cache-warming job runs there in a VM after each push to `main`, one run at a time, and is the only job that mounts the folder writable; pull-request VMs mount it read-only and copy what they need. The tier uses no GitHub cache. Hosted Linux jobs, such as test health and the coverage job, restore the Linux caches that manual-dispatch Release runs on `main` save.
- **Size reports are saved by tree.** Every merge-queue run, and while private every manual-dispatch Release run on `main`, uploads each target's report of both Products (`xtask size`, the thin-LTO `ci` profile) as the artifact `size-report-<tree>-<target>`, kept 90 days, where `<tree>` is the tested commit's tree. A run that needs `main`'s report asks for it by name: `gh api 'repos/goodfetch/goodfetch/actions/artifacts?name=size-report-<tree>-<target>'` with `main`'s head's tree. A `main` whose head no Release run tested has no report: the estimate and the increase check then report each file as "no baseline" and gate nothing on growth, as a benchmark with no base is reported and never gated (ADR 0071); the increase check still fails a crate tarball over its ceiling.
- **A musl cell checks how its executables are linked.** After the size report, `ci/release/cell.sh size` runs `xtask static-pie` on the same manifest: on a `*-linux-musl` cell each Product must have its `ci` executable there, and each must be a static-PIE with packed relative relocations (`ET_DYN`, no interpreter, no `DT_NEEDED`, a `DT_RELR` entry), which `ci/musl/link-cc` links for every profile (ADR 0024). The other cells' executables are not read.
- **CI test builds use the `ci-test` Cargo profile** (`test` with `debug = "line-tables-only"`, and the dependencies at `opt-level = 1`: the Proving ground's tests run 4.5 times as fast, for twice the dependencies' build time; debug assertions and overflow checks stay on).
- **CI's Linux builds link with mold and its Windows builds run on a Dev Drive**; local builds keep the default linker and disk. Hosted jobs get both from the host-tools action (`rui314/setup-mold` and `samypr100/setup-dev-drive`, pinned by SHA, the workspace's `target` a junction to the Dev Drive), and the owner's machine's VM jobs get mold from the CI image, at the version `ci/tool-versions.sh` holds equal. Each sets `-Clink-arg=-fuse-ld=mold` for its target, since Rust's own default on x86-64 Linux, rust-lld, ignores the system linker.
- **Every run writes JUnit XML**, local or CI. Every CI job uploads it, pass or fail, as `junit-<suite>-<tier>-<os>-<arch>[-<runtime>]-<shard>`.
- **Every test job writes its failed tests to its summary page**, pass or fail: `ci/junit-summary.sh` (with `vm` in the owner's machine's VM) runs `xtask junit-summary` after `ci/junit-context.sh`. The page lists each failed test of `target/junit/` with its failure's first 15 lines and the `goodfetch-test-seed=<n>` lines it printed, or says that none failed. A JUnit file it cannot read is listed and fails the step, never skipped. pytest writes each failed test's captured output into its JUnit file (`junit_logging`), where the seed line is.
  _Why:_ a contributor reads the failure and the seed that replays it without opening the logs (ADR 0061).

### Compiler cache

A host that builds in several checkouts shares one sccache across them, so a fresh checkout reuses the C and C++ objects of DuckDB (`libduckdb-sys`) and BoringSSL (`btls-sys`) that another checkout compiled, instead of compiling them again. Dev builds still compile both from source, with the shipped flags; only the objects come from the cache.

- **C and C++ go through sccache wherever Rust does.** The `cc` crate compiles DuckDB through the Rust compiler wrapper (`RUSTC_WRAPPER`) when it is sccache; `.cargo/config.toml`'s `[env]` gives CMake, and so BoringSSL, the same rule through `ci/compiler-launcher.sh`. Without sccache the compiler runs itself.
- **sccache keys hold absolute paths**, and DuckDB's sources sit under `target/`, so a checkout hits another's objects only when sccache's server lists both checkouts' folders in its base directories (`basedirs` in `~/.config/sccache/config`, read once when the server starts). A listed parent folder does not cover a checkout below it: sccache strips the longest listed prefix, and the rest of the path stays in the key.
- **On a host with several worktrees, build in a fixed set of them.** The list names the main checkout, the gate's `.claude/worktrees/merge-gate` and `.claude/worktrees/gate-backstop` (`ci/gate-worktree.sh`), and a pool of slot worktrees, `.claude/worktrees/slot-1` to `slot-6`. A task claims a free slot, checks its branch out there and keeps the slot's `target/`, then releases the slot; a worktree named after its task misses every C/C++ object. After changing the list, restart the server once while no build runs (`sccache --stop-server`; the next build, or `sccache --start-server`, starts it).
- **`just compiler-cache` guards the setup**, first in `just quick` and in `just merge` before any build: where the Rust compiler wrapper is sccache, it reports a gap when sccache's base directories do not list the checkout or a CMake launcher variable bypasses sccache, with the fix. It fails only on a host that opts in with `COMPILER_CACHE_REQUIRED=1`: the shared build server's agent shells, and `just merge`, which sets it for the gate. On any other machine a gap is a note, and `just quick` goes on. Where no build uses sccache, it is skipped.

### Merge queue

GitHub offers the merge queue to a private repository only on GitHub Enterprise Cloud, so it starts when the repository is public in the organization ([ADR 0108](../adr/0108-while-the-repository-is-private-the-release-suite-runs-its-macos-cells-on-the-owners-machine-and-its-hosted-cells-under-a-ceiling.md)). Until then the Release suite runs on manual dispatch, as above. On that day:

- **Turn on the queue for `main` with ADR 0061's settings:** "Only merge non-failing pull requests" on, a status check timeout of 120 minutes, and group size and build concurrency within the free plan's 5 concurrent macOS jobs. "all green" and the Chromium build gate are required there too.
- **Run the Release suite on `merge_group`,** on the full native matrix of ADR 0024 (native macOS Intel and Windows arm64 included), on hosted runners only: `release-suite.yml` stops naming `owner-machine` and loses its ceiling, and the allowlist loses its entries.
- **In the queue the Chromium build gate only takes its fast path,** failing on a digest with no verdict attestation for the group's head, and the Release suite fetches the Goodfetch Chromium by digest from the committed manifest (ADR 0074).
- **In a group, each entry's base is the tree of the entry before it**, which is how GitHub builds groups, so its increase check reads the size report keyed by that tree.
- **The queue saves its per-target size reports and no cache.** Pull requests cannot restore a cache saved on a queue's `gh-readonly-queue/…` branch: GitHub's cache scopes give a pull request its own, its base's and the default branch's, and name no queue branch ([dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). Its jobs set `save-if: false` on their caches.
- **`main` reruns no tests after a merge,** and pull requests then run only the touched Sinks: `xtask affected` switches its `sinks` output to the touched set (#134's `sinks-touched`).
