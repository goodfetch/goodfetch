# Portails : sessions longues, HTTP adaptatif et frontier (D-session-model, D-adaptive-routing, D-frontier), 9 octobre 2026

Nouvelle lane `portal`, mesurée en `local-dev` sur sources commitées, Mac en usage (un onglet Chrome à environ 100 % CPU et `ffprobe` empêchaient `local-controlled`). Chaque cellule tourne contre un site neuf dont l'oracle connaît les vrais enregistrements et compte ce que fait le client : logins, refreshs, requêtes HTML et API. Un run qui déclare un résultat complet que l'oracle réfute est un **faux succès**.

Runs retenus, 5 blocs chacun :

- `portal-routing-2026-10-09T15-12-56-291Z-1eb2f9` : six rendus d'un même listing, cinq politiques, job récurrent de 4 runs par cellule ;
- `portal-frontier-2026-10-09T15-08-28-035Z-e66949` : pièges et table changeante, 3 runs par cellule.

Le premier run des sessions, `portal-sessions-2026-10-09T15-08-30-076Z-7ccb85`, est classé `diagnostic` : j'ai commité des sources du lab pendant qu'il tournait, et le moteur l'a marqué `invalid-provenance`.

## Sessions

### Le site

Un portail de 5 pages de rapports (100 enregistrements) derrière un login à jeton CSRF : un cookie de pré-session porte le jeton du formulaire, et un jeton faux donne `403`. Cinq situations :

| Variante | Ce qui arrive à la session |
| --- | --- |
| `login-csrf` | rien : un login, cinq pages |
| `session-expiry` | la session expire après 4 pages ; le portail répond **`200` avec le formulaire de login** à l'URL du rapport, comme beaucoup de portails |
| `session-refresh` | la session expire après 3 pages, avec redirection vers le login ; un cookie `rt` permet `POST /session/refresh` |
| `session-resume` | le processus s'arrête après 2 pages, écrit son journal (curseur, enregistrements et, selon la politique, ses cookies) sur disque ; un nouveau processus, avec un nouveau client ou un nouveau contexte navigateur, le relit et continue |
| `resume-revoked` | comme `session-resume`, mais le site révoque toutes les sessions pendant l'arrêt |

### Les politiques

La recette déclare l'URL de login, le refresh et son cookie, et la référence des identifiants. Trois politiques :
- `status-only` : cookies repris ; la session est jugée perdue sur un `401`, un `403` ou une arrivée sur `/login`.
- `contract` : cookies repris ; chaque page doit être le listing authentifié attendu. Un formulaire de login à la place est une session perdue, et toute autre page arrête la tâche (`E_CONTRACT`).
- `relogin-each-run` : même contrat de page, mais aucun cookie repris ; login au début de chaque run.

Une session perdue tente d'abord le refresh déclaré, si son cookie est présent, puis le login, deux fois au plus.

### Lecture

- **Le statut HTTP ne dit pas si la session tient.** Quand le portail répond `200` avec son formulaire de login, `status-only` lit une page sans enregistrement et sans lien suivant, puis déclare le crawl fini. Il lui manque 20 enregistrements en HTTP, 40 dans le navigateur, où le login suivi de sa redirection consomme une page de session de plus. Cela fait 20 faux succès sur 20. Juger chaque page sur son contrat suffit à les supprimer.
- **Reprendre la session journalisée évite un login par redémarrage.** Après un arrêt, `contract` reprend avec ses cookies et ne se reconnecte pas. `relogin-each-run` se reconnecte, soit un login de plus par reprise, ce qu'un portail avec MFA ou alerte de connexion fait payer cher. Quand le site a révoqué la session pendant l'arrêt, la reprise le voit à la première page et se reconnecte une fois, sans perte ni doublon : le curseur et les enregistrements viennent du journal.
- **Le refresh déclaré évite un second login** pour les trois politiques, parce qu'ici l'expiration passe par une redirection, que même `status-only` reconnaît.
- Les deux tiers donnent les mêmes comptes : la session porte les mêmes cookies en HTTP et dans le navigateur, et un contexte navigateur neuf repart des cookies exportés.

### Ce que cela dit pour l'architecture

1. **Le moteur juge chaque page d'une session sur le contrat de la recette**, pas sur le statut HTTP : un listing authentifié attendu, ou un formulaire de login reconnu comme session perdue. Une page inconnue arrête la tâche avec une erreur typée.
2. **L'état de session fait partie du journal du run.** Cookies, curseur et enregistrements déjà validés sont repris par un nouveau processus. L'état repris est revalidé sur la première page, et une session révoquée appelle un login, jamais une donnée vide.
3. La recette déclare la récupération de session : refresh, puis login, sous le même budget de tentatives que le reste. Comme l'architecture le demande, l'import et l'export de la session restent des opérations distinctes de l'export du plan.

## HTTP adaptatif

### Le site

Un listing de 100 produits, servi de six façons :

| Variante | Ce que reçoit un client HTTP | Ce que montre le navigateur |
| --- | --- | --- |
| `static` | les 20 produits de chaque page, liens de pagination | la même chose |
| `js-shell` | une coquille vide ; un script appelle `/api/list?page=N` | les 20 produits, le lien suivant ajouté par le script |
| `partial-hydration` | 8 produits par page ; un script charge les 12 autres | les 20 produits |
| `stale-html` | les 20 produits avec un prix périmé ; un script corrige les prix | les prix à jour |
| `graphql` | une coquille ; GraphQL derrière un bouton « load more » | les 100 produits après 5 clics |
| `infinite-scroll` | les 20 premiers ; la suite au défilement, par curseur | les 100 produits après défilement |

Chaque listing déclare son total (`data-total="100"`).

### Les politiques

- `browser-only` : toujours le navigateur. La page est stabilisée ainsi : réseau calme, puis défilement et clic sur un « load more » visible, jusqu'à ce que le nombre d'enregistrements ne bouge plus.
- `http-only` : HTTP seul.
- `heuristic` : HTTP, puis le navigateur si la page HTTP ne contient aucun enregistrement. C'est la règle « résultat vide » que l'architecture juge insuffisante.
- `sampled-contract` : au premier passage d'une route, la première page passe en HTTP et dans le navigateur. HTTP n'est retenu que s'il donne les mêmes enregistrements, prix compris, et les mêmes liens. En fin de route, le total déclaré est vérifié : s'il n'est pas atteint, la route est réapprise en navigateur et refaite.
- `api-capture` : comme `sampled-contract`. Quand le navigateur est requis, le trafic JSON de l'échantillon est capturé et un plan de rejeu en est inféré :
  - **par page** : un champ de la requête égale un paramètre de l'URL de la page ;
  - **par chaîne** : un champ de l'appel suivant est une valeur de la réponse précédente, comme un curseur.

  Le plan n'est retenu que s'il redonne exactement le résultat du navigateur sur l'échantillon. Le HTML et les objets de l'API sont fusionnés par identifiant, et l'API l'emporte sur les prix.

Ce qu'une route apprend est réutilisé aux runs suivants du même job. Le total déclaré sert d'événement d'invalidation.

### Lecture

- **La règle du résultat vide ne suffit pas, comme l'architecture le dit.** `heuristic` passe la coquille et GraphQL, parce que la page HTTP y est vide. Elle échoue sur les trois cas où la page HTTP n'est pas vide mais fausse :
  - hydratation partielle : 40 produits au lieu de 100 ;
  - prix périmés corrigés par script : 100 prix faux ;
  - scroll infini : 20 produits au lieu de 100.

  Chaque fois, elle déclare un succès.
- **L'échantillon comparé ne se trompe jamais.** `sampled-contract` est exact sur les 120 runs. Il ne garde HTTP que sur le listing statique, où il coûte une seule page navigateur pour tout le job.
- **La découverte d'API change l'ordre de grandeur.** `api-capture` est exact sur les 120 runs et infère un plan de rejeu sur les cinq rendus scriptés :
  - par page : `/api/list`, `/api/prices` ;
  - par chaîne : curseur GraphQL `pageInfo.endCursor`, curseur `nextCursor` du flux.

  Une fois la route apprise, un run tient en 10 à 20 ms au lieu de 0,8 à 1,3 s dans le navigateur, sans aucune page navigateur.
- Les prix périmés montrent pourquoi l'échantillon compare les champs et pas seulement le nombre d'enregistrements. Le HTML a les 20 produits attendus, seuls leurs prix sont faux.

### Ce que cela dit pour l'architecture

1. Le routage `auto` est un **apprentissage par route validé sur échantillon**, pas une heuristique sur la page. La comparaison porte sur les identités, les champs et les liens. Le total déclaré ou un autre oracle de complétude invalide ce qui a été appris.
2. **La découverte d'API devient un tier de routage à part entière**, entre HTTP et navigateur : capture du trafic JSON pendant l'échantillon, inférence d'un plan par page ou par curseur, validation contre le navigateur avant usage. Pour un job récurrent, c'est le tier le moins cher qui reste exact.
3. Un plan d'API appris a la même portée et les mêmes événements d'invalidation qu'une décision HTTP : il est lié à la route et refait si le contrat de fin de route échoue.

## Frontier

### Le site

- `crawler-trap` : 60 produits derrière 3 catégories et 6 événements dans un calendrier. Le site tend plusieurs pièges :
  - chaque lien porte un `sid` neuf, et certains un `utm_source` ;
  - chaque catégorie propose 4 tris de la même liste ;
  - le calendrier a des liens « mois précédent » et « mois suivant » sans fin, alors que seuls trois mois ont des événements.
- `large-table` : 1 500 lignes, les plus récentes en premier, paginées par 50. Un lien numéroté `<a class="next">` sert la pagination par décalage, et un `<link rel="next">` sert la pagination par curseur. Toutes les trois pages servies, le site supprime deux lignes déjà parcourues et en insère une en tête. L'oracle exige, une fois chacune, les lignes présentes pendant tout le crawl.

### Les politiques

- `naive` : la clé de déduplication est l'URL exacte, tous les liens `<a>` sont suivis, avec un budget de 300 requêtes.
- `canonical` :
  - les paramètres déclarés par la recette (`sid`, `utm_*`) sont retirés et les clés triées ;
  - deux pages d'un même chemin qui ont les mêmes enregistrements et les mêmes liens rendent leurs paramètres différents « sans effet » pour ce chemin ;
  - un chemin dont trois pages de suite n'apportent ni enregistrement ni lien hors de lui-même est fermé ;
  - une page qui déclare `rel=next` est suivie par ce lien plutôt que par les numéros de page du même listing.

### Résultats

Sur 15 runs par cellule :

| Variante | Politique | Runs aux données exactes | Faux succès | Requêtes par run | Fin |
| --- | --- | --- | --- | --- | --- |
| `crawler-trap` | naive | 0/15 | 0 | 300 | budget épuisé, 2 140 URL encore en file, 2 événements manqués |
| `crawler-trap` | canonical | 15/15 | 0 | 75 | frontier vide |
| `large-table` | naive | 0/15 | **15** | 30 | frontier vide, 8 à 9 lignes perdues |
| `large-table` | canonical | 15/15 | 0 | 30 | frontier vide |

### Lecture

- **Dans le piège, le crawler naïf ne sait pas qu'il a fini.** Il épuise son budget sans manquer de produit, mais il lui manque les événements du troisième mois. Il le dit honnêtement : budget épuisé, résultat non déclaré complet. Le canonique termine en 75 requêtes et apprend en route trois faits :
  - `sort` et `order` ne changent rien aux catégories ;
  - le calendrier est un piège ;
  - le reste est couvert sans rien perdre.
- **La pagination par décalage sur une table vivante perd des lignes sans s'en apercevoir.** Chaque suppression avant le décalage courant fait glisser des lignes que le crawler ne verra jamais. Il finit, frontier vide, et déclare un résultat complet : 15 faux succès sur 15. Avec le curseur, la même table est exacte, pour le même nombre de requêtes.

### Ce que cela dit pour l'architecture

1. La canonicalisation déclarée par la recette ne suffit pas seule. La frontier doit aussi **apprendre les paramètres sans effet** par signature de page, et **fermer les chemins piégés** sur un critère de rendement. Ces faits appris ont la portée du domaine et du chemin.
2. **La pagination par curseur est la règle quand le site l'offre.** La pagination par décalage n'est sûre que sur une collection figée, et une frontier ne peut pas le vérifier seule : il faut un oracle de complétude, comme un total déclaré ou un recrawl comparé.
3. La fin de crawl est un résultat à part entière : épuisement de la frontier, ou budget atteint. Un crawl arrêté par son budget n'est jamais un résultat complet.

## Verdicts mécaniques

`pnpm lab verdict`, sur les runs retenus :

| Décision | Option contre référence | Résultat |
| --- | --- | --- |
| D-session-model | `contract` contre `relogin-each-run` | **meilleur** : 0,50 login par run repris, 5/5 blocs, en HTTP et dans le navigateur ; `local-dev` suffit, car les logins ne dépendent pas de l'hôte |
| D-session-model | `status-only` | bloqué par le contrat (`oracle-exact`) |
| D-adaptive-routing | `heuristic`, `http-only` | bloqués par le contrat |
| D-adaptive-routing | `sampled-contract` | équivalent sur les rendus scriptés, où il garde le navigateur ; sur `static`, ratio 0,007, mais `insufficient-n` |
| D-adaptive-routing | `api-capture` | ratio de 0,008 à 0,021 selon le rendu, soit 50 à 120 fois plus rapide une fois la route apprise ; `insufficient-n` partout |
| D-frontier | `naive` contre `canonical` | bloqué par le contrat |

Pourquoi `insufficient-n` malgré un écart de deux ordres de grandeur : la règle calcule le nombre de blocs nécessaire pour détecter l'écart déclaré de 10 % à partir de la dispersion des rapports par bloc. Elle ne tient pas compte de l'effet observé. Avec une dispersion des log-rapports de 0,3 environ, elle demande de 99 à 204 blocs. D-adaptive-routing exige de toute façon `local-controlled` pour ses durées. Le résultat de contrat, lui, est acquis : seules `sampled-contract` et `api-capture` passent, et `browser-only` reste la référence exacte la plus chère.

## Limites

- Fixtures synthétiques, conçues pour reproduire chaque piège isolément ; un vrai portail les combine.
- Le plan d'API ne couvre que des requêtes GET ou JSON dont la pagination est un champ simple : pas de signature de requête, de jeton à usage unique ni de corps chiffré.
- Les durées viennent d'un hôte `local-dev` ; seuls les comptes de requêtes et de logins sont indépendants de l'hôte.
