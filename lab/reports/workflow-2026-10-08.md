# Workflow durable et SQLite commun — 8 octobre 2026

Le lab possède désormais le prototype **acquisition → extraction → validation → queue bornée → writer batché → commit → ack**, avec reprise idempotente. La piste d'écriture ajoute Rust synchrone et Go, comparés à Node avec **le même artefact SQLite 3.53.4**.

**Résultats retenus : 153/153 cellules vérifiées, 606 528 lignes SQLite relues, 1 344 jobs de workflow acquittés et vérifiés, soit 19 776 records extraits.** La suite complète a passé 28 tests, puis le nouveau test réel de pool Crawlee a passé après sa correction : **29 tests distincts qualifiés**. TypeScript, doctor des backends et formats Rust/Go passent. [Vérification détaillée](verification-2026-10-08.json).

Ce sont des mesures exploratoires sur un Mac partagé, pas une preuve d'architecture ou de supériorité universelle. Les tables concernent des workloads locaux précis ; Rust/Tokio reste un candidat pour le noyau portable.

## Écriture : runtime et binding sous un moteur SQL commun

Les trois bindings synchrones chargent une bibliothèque C unique, avec statement réutilisé et un appel au shim commun par insertion : Node N-API, Rust FFI, Go/cgo. Node **25.5.0**, Rust **1.93.0**, Go **1.27.1**, Apple M3 Max, macOS 27 arm64. Le SHA-256 de la bibliothèque effectivement contrôlée est `d2d6f564187c2a0e2dd4f83e11316c50beca8023ff1bb4a5083b840d9c5dd170`. Version, source ID, compile options, chemin chargé et PRAGMAs sont contrôlés pour chaque connexion. Les sources de compilation et des campagnes sont figées.

Les bindings, allocations, encodeurs JSON et protocoles restent différents : les chiffres comparent ces implémentations, sans isoler une propriété du langage. Le Node SQLite incorporé et le Rust SQLx historiques restent dans leurs pistes séparées ; ils n'emploient pas cet artefact commun.

Débit de lignes vérifiées : somme des lignes / somme des durées d'écriture des deux blocs. Chaque cellule a 48 batches, payload ASCII 512 octets, huit producteurs ; W désigne de vrais processus sur une même base. Démarrage, fermeture/checkpoint final et oracle sont séparés. ## Workflow HTTP complet

Le sink intégré est **Node SQLite WAL FULL**. Rust et Go sont comparés dans la piste d'écriture, pas encore comme noyaux intégrés. Chaque cellule a 24 jobs × 8 pages × 2 records, un délai serveur de 2 ms, leases de 30 s et une base neuve. Deux blocs randomisés donnent 960 jobs / 15 360 records. Aucun échec ni dépassement de la borne de résultats active.

Débit = jobs acquittés et vérifiés / (travail + fermeture des workers + réouverture et oracle). Le démarrage est séparé dans les bruts ; le débit incluant le démarrage est également disponible. Node HTTP est un témoin fetch + parser spécialisé pour ces fixtures ; il ne fournit pas le service complet d'un crawler général.

## Résultat d'ingénierie : réveil du pool Crawlee

Le workflow a exposé une interaction entre backpressure du writer et pool : la queue Crawlee peut devenir vide entre deux admissions. Le pool vérifie alors périodiquement les tâches, avec un défaut de 500 ms observé dans Crawlee 3.18.2. L'API publique `notify()` déclenche une vérification immédiate. Une série séparée compare les deux intégrations, sans modifier les garanties de records. [API AutoscaledPool](https://crawlee.dev/js/api/core/class/AutoscaledPool).

Une première intégration a appelé `notify()` avant la fin de l'initialisation native. Le test a détecté le timeout ; la campagne expérimentale a été arrêtée et exclue. La correction attend qu'un premier handler ait effectivement démarré avant d'autoriser la notification. Le test réel et les 20 cellules suivantes passent. Les diagnostics et sources de l'expérience interrompue restent conservés.

La série A/B utilise **12 jobs par cellule**, deux blocs randomisés et les mêmes fixtures que ci-dessus. Comparer les modes au sein de cette série ; ne pas confondre ses petits lots avec ceux de 24 jobs de la table précédente. Chaque p95 agrège 24 jobs.

À C1, le débit progresse d'environ **9×**. À C8/B1, notify ne gagne pas dans cette série. La réponse dépend de l'admission, du cycle de vie et de la taille du lot ; un réglage ne suffit pas à devenir un vainqueur général. Ce résultat montre pourquoi l'intégration acquisition/sink doit être testée avant de conclure sur un langage.

## Reprise : contrat réellement vérifié

Douze cellules injectent un SIGKILL du writer : avant COMMIT, après insertions dans la transaction ; ou après COMMIT, avant la réponse. Chacune redémarre une fois. Les **144 jobs / 576 records** finissent acquittés et exacts, sans doublon. Avant commit, la transaction est annulée et la lease est attendue puis remplacée. Après commit, les receipts persistés sont validés et réconciliés ; les autres jobs interrompus sont repris après expiration de leur lease. Les tentatives abortées restent dans les bruts, et la reprise appartient à la durée du workflow.

Deux tests fonctionnels arrêtent aussi un coordinateur avec ses workers, puis démarrent un **nouveau processus coordinateur**, après claim ou entre commit et ack. Le serveur de fixtures et l'oracle externe restent vivants. La reprise est exacte ; sa latence traversant cet arrêt complet n'est pas encore mesurée. Les autres tests couvrent fencing des tokens périmés, rejeu identique, conflit de données, borne de queue, batching et rejet d'un faux succès avant écriture.

Ce prototype n'a pas de migration, heartbeat, admission continue du backlog ou garantie exactement une fois sur un effet externe. Les reprises qualifiées concernent des lectures HTTP idempotentes. Aucun crash pendant clic/paiement, lecteur distribué, disque plein ou arrêt électrique n'est qualifié. [Contrat détaillé et commandes](../docs/workflow.md).
