# Proving ground

The website Goodfetch owns and generates (ADRs 0025, 0032 and 0063): every page comes from a seed, generated on request and never stored, and every task has an expected result derived from the same seed data, never from a tool's output. It depends on no Goodfetch crate but `goodfetch-test-support`, which `xtask dependency-direction` checks.

## `serve`

```sh
cargo run -p goodfetch-proving-ground -- serve --seed 158 --copy local --address 127.0.0.1:0 --network-profile none
```

The first output line is one JSON object: `address` (the bound address, port 0 replaced), `version` (the workspace version plus the commit, `0.0.0+<sha>`), `seed` (an unsigned 64-bit integer), `hosts` (every host name it serves, sorted, which a caller's `resolve` maps to the address's IP), `certificate_authority` (the seed's certificate authority as PEM, the same as `GET /certificate-authority`), `network` (below), and the address of each [network fixture](#network-fixtures): `proxies` (each forward proxy's address by name), `proxy_credentials` (`username` and `password`, derived from the seed), `dns`, `target` and `udp`. It serves until Ctrl-C or `SIGTERM`, which it listens for before it writes the line, so a caller may stop it as soon as it reads the line. Only the `local` copy exists yet; the online copy is #168's. `--browser-builds <folder>` gives `browser-builds.test` the files it serves (below).

## Network profiles

`--network-profile` adds a round trip to every connection (ADR 0025): `none` (nothing added, shaped or calibrated), or `rtt-0`, `rtt-20`, `rtt-100` and `rtt-300` (0, 20, 100 and 300 ms, through the shaper). `--loss <percent>` (default `0`, such as `1` or `0.5`) loses that share of packets in each direction; it needs a shaped profile. `--shaper` picks what applies it:

- `proxy` (the default), the lab's user-space latency proxy, ported, on any OS without privileges, for unpublished runs. It listens on `--address`, forwards each connection to the server on a loopback port of its own, and delays each chunk of bytes by half the round trip in each direction, in order. A lost chunk waits a retransmission timeout more (200 ms plus the round trip, Linux's least) and holds back the chunks behind it, as TCP does; which chunks are lost is drawn from the seed. This approximates loss; `tc netem` loses real packets.
- `netem`, `tc netem` on Linux's `lo`, for published figures. It needs `CAP_NET_ADMIN` (root on the machine that runs it) and iproute2's `tc` on `PATH`. It takes `lo`'s root: a `prio` root whose fourth band holds a `netem` of half the round trip and the loss, and `u32` filters that send it only the packets to or from the Proving ground's port, IPv4 and IPv6, so no other loopback traffic is shaped. One netem Proving ground runs per network namespace at a time; it removes the root when it stops, and a killed one leaves it (`tc qdisc del dev lo root` removes it).

Before the output line, a shaped profile is calibrated as the lab calibrates it: 50 one-byte round trips to an echo through the shaper, each paired with a direct one to another echo. `network` records it: `profile`, and for a shaped one `round_trip_microseconds`, `loss_percent`, `shaper`, `calibration` (`round_trip_microseconds` declared, `samples`, `shaped_median_microseconds`, `shaped_p95_microseconds`, `direct_median_microseconds`, `added_median_microseconds`, the median of each pair's shaped minus direct round trip, and `within_tolerance`) and `time_metrics`. The added median is within tolerance when it is off the declared round trip by at most the larger of 10% and 2 ms; outside, `time_metrics` is `unavailable`: the run keeps its correctness results and loses its time metrics. The calibration is a measurement recorded with the run, never asserted by a test (ADR 0064).

## `tasks`

```sh
cargo run -p goodfetch-proving-ground -- tasks --seed 158
```

Prints the task list `GET /tasks` serves for the seed (below) as one JSON line and exits, binding nothing: each `start_url` has no port, and every digest is the one `serve` lists on any port. `xtask journeys tasks` commits it for each seed the Journey catalog uses (ADR 0063).

## HTTP/1.1, HTTP/2 and TLS

The one address serves plain text and TLS: a connection whose first byte starts a TLS handshake gets TLS, any other plain text. Either way it speaks HTTP/2 when its first bytes are HTTP/2's preface (ALPN offers `h2` and `http/1.1`) and HTTP/1.1 otherwise.

TLS comes from a certificate authority the Proving ground makes from its seed (ADR 0059's one seeded authority): the same seed gives the same authority byte for byte, its keys derived from the seed and every signature RFC 6979's deterministic ECDSA on P-256. `GET /certificate-authority` serves it as PEM. A client trusts it explicitly (the engine's per-domain `trusted_cas`, ADR 0042, or a competitor's documented option); nothing turns verification off. Each host name below has its own leaf certificate, never a wildcard, dated from the clock and valid for 397 days, since some platforms refuse a longer-lived server certificate.

The `certificates` family's host names are pitfall H03's certificates a client must refuse (ADR 0042), each failing verification in one way only, and each answering any path with a page naming its defect to a client an exception lets through: `expired.certificates.test` (signed by the seed's authority, its validity ended the day before `serve` started), `not-yet-valid.certificates.test` (valid from 30 days after), `unknown-issuer.certificates.test` (signed by a second authority from the seed, never published), `name-mismatch.certificates.test` (a leaf for `elsewhere.certificates.test` alone) and `self-signed.certificates.test` (signed by its own key). Beside them, `client-certificate.certificates.test` and `other-client-certificate.certificates.test` serve a valid leaf and require mutual TLS (story 4-34): each refuses a handshake without a client certificate that the seed's client authority signed, and answers any path with a page saying it was reached with one. `GET /set-cookie` on any host of the family sets `session=c00k1e` on the whole `certificates.test` domain, the Session cookie a client must not send a host it reaches through an exception (ADR 0042). `GET /client-certificate` and `GET /client-key` on the Proving ground's own address serve that client certificate and its PKCS #8 private key as PEM, the same seed giving the same bytes.

Five families hold pages whose state only a browser reaches (#1536), each task on `<n>.<family host>`. Their scripts post what an action did to `POST /effects` (`{"event", "target", "trusted", "details"}`, `trusted` the browser's `isTrusted`), recorded as an `event` Effect of the task, and count the posts in flight in the root element's `data-posting`, so a tool knows when the site has them all:

- `1.live.test` and `2.live.test`: the `live` family. `/board` holds a WebSocket (`/socket`, a text message every 250 ms) and a server-sent events stream (`/events`, an event every 250 ms) open for as long as it is open, and makes periodic requests one after another (`/updates/<n>`), each held 100 ms by the server, so a request is in flight until the last is answered. On `live/1`'s board they stop after six and the board says `settled`; on `live/2`'s they never stop. Nothing else differs, so `networkidle` (no request in flight for 500 ms, WebSockets and server-sent events left out) comes on the first and never on the second: a board read before its last update is stale, and on the second the only right result is a failure.

- `1.keys.test` to `3.keys.test`: the `keys` family. `/type` asks for a text and logs every key, input and composition event its field receives, in order, with each one's key, code, data, input type, composition state and `isTrusted`, and the keyboard layout when the browser tells it. Their tests in `tests/it` read the pages over plain HTTP, and reach what only a browser does through a stock Chromium driven by Playwright (spec #152's Seam 1), never an engine crate: `tests/it/browser.mjs` holds the programs, each run by `node` the way a right tool or one that makes a known mistake would, printing the result it would submit, which the test submits to the oracle. - `bombs.test` (`bombs/1` to `bombs/6`): `/` serves a decompression bomb — a small body whose `Content-Encoding` decodes to far more than it sends, past the engine's decompression-ratio limit (`network.max_decompression_ratio`, 100 once a decoded body passes 1 MiB): `bombs/1` gzip, `bombs/2` raw deflate, `bombs/3` Brotli, `bombs/4` zstd (a 128 KiB window, within RFC 9659's 8 MB) and `bombs/5` gzip applied twice (`Content-Encoding: gzip, gzip`). `bombs/3` and `bombs/4` start over `https://`, since a browser offers `br` and `zstd` only to a secure origin (Chromium fails such a body over `http://` to any host but localhost before reading it); the others over `http://`. A correct tool refuses each at the limit with `response_limit_exceeded` naming that setting, rather than reading it to the end; a tool that inflates it and claims a success is a false success. Each task's expected result declares the bomb's `content_encodings`, `compressed_bytes` and `expanded_bytes`. `bombs/6` is the positive control: a page legitimately gzip-compressed, well within the ratio, kept as one Record. `bombs.test/past-the-window`, of no task, serves `bombs/4`'s blocks in a single-segment zstd frame, whose window is its whole 10 MiB content, past RFC 9659's 8 MB: a decoder that enforces it, as Chromium does (`net::ERR_ZSTD_WINDOW_SIZE_TOO_BIG`), refuses the frame before a byte decodes, a decoding failure (the page suite's case). The bomb bodies are generated at run time by streaming one repeated byte through each encoder (the zstd frame is RLE blocks written by hand, RFC 8878, since no zstd encoder is a dependency), never committed, so the source stays small. Endless bodies and deeply nested JSON are a separate concern — the engine's `network.max_body_size` and `network.max_json_depth`, not the decompression ratio — and are not part of this family.

An unexpected sighting is a `secret_canary_leaked` finding of the canary's task.

## The Fake model

`model.test` serves the Fake model (ADR 0065), ported from the lab's `fake-llm.ts`: point a Model provider's base URL at `http://model.test:<port>/v1` (OpenAI-compatible chat, `POST /v1/chat/completions`), `http://model.test:<port>` (Anthropic Messages, `POST /v1/messages`) or `http://model.test:<port>/v1beta` (Gemini, `POST /v1beta/models/<model>:generateContent`, and `:streamGenerateContent`, with `alt=sse` or as one JSON array). Each format answers whole or streamed (`stream: true`; OpenAI's `stream_options.include_usage` adds the usage chunk), with the format's fields, stream events and error bodies.

- **What it answers.** The task whose description appears in a string of the request (the instruction a Journey passes), else the task whose host name does (a page URL). Its answer is the task's Records at the current time step (a booking's fields for `agent/1`), shaped as the request asks: a call of the tool `tool_choice` names, else of the first tool offered, its parameters' schema filled from the Records; the structured output's schema filled from them (`response_format`'s `json_schema`, Anthropic's `output_format`, Gemini's `responseJsonSchema` or `responseSchema`); else the text `{"records": […]}`. After a tool result it answers in text, but for an Agent step. A request naming no task answers `400` in the format's error body.
- **AI verbs.** A schema (a tool's parameters or the structured output's) with one of these top-level properties asks for that verb's answer, which the task declares at each time step, in place of its Records: `candidates` (`observe`: `{"candidates": [{"element", "description"}]}`, empty where nothing fits), `action` (`act`: `{"action": {"method", "element", "arguments"}}`, `null` where nothing fits), `locators` (compiled `extract`: `{"locators": [{"field", "element"}]}`, one per field the page shows) and `actions` (one `page.agent` step: `{"message", "actions": [{"method", "element", "arguments"}]}`, the step after as many as the request's turns hold of the model's own, the last ending with `done` and its arguments, or with `give_up`). The `agent` tasks declare them: `agent/1` the booking button (`click`), and five steps filling the form then booking; `agent/2` to `agent/9` the Pro price cell, and one step that ends with the Record; `agent/10` nothing. Every other task declares nothing, as `agent/10`. An element is named by the reference the request's `ai` aria snapshot gives the line of its role and name (`- button "Book the demo" [ref=e15]` names `e15`), else by its selector on the page at the time step (`#xsubmit` once renamed). Each fault applies to these answers too; `agent/9`'s names the Starter price cell. Answers depend only on the request, the seed and the time step; IDs come from a hash of the seed and the request.
- **Tokens.** It counts each call itself: input tokens are a quarter of the characters of every string in the request body, rounded up; output tokens a quarter of the characters of the answer's text, refusal, or tool name and arguments, rounded up. The response's usage carries them, and `GET /model-calls` on the control host lists every call (`sequence`, `format`, `model`, `stream`, `task`, `fault`, `input_tokens`, `output_tokens`), so a test checks the engine's Usage against an independent count.
- **Faults**, asked for by a task, never by a switch in the binary: `agent/3` a rate limit (`429`, `Retry-After: 1`), `agent/4` an overload (`503`, Anthropic's `529`), `agent/5` a timeout (no answer until the client gives up), `agent/6` a cut stream (the body ends after its first content event, or halfway through a whole answer), `agent/7` malformed JSON (in OpenAI's tool arguments, else as text), `agent/8` a refusal (OpenAI's `refusal`, Anthropic's `stop_reason: "refusal"`, Gemini's `finishReason: "SAFETY"`), `agent/9` a wrong but plausible price, which the oracle refutes.
- **Model recordings.** `tests/it/model_recordings.rs` checks the Fake model's answer to every committed Model recording's request (a JSON file in any `recordings/` folder) against the recorded response's shape: fields, types, stream event kinds and order, and error bodies.

## The replay proxy

Point a browser's proxy at the bound address (`--proxy-server`, with no loopback exception): a `GET` in absolute form to an archived page's original URL over `http://` gets the archived page, and a `CONNECT` to an archived host's port 443 opens a tunnel whose TLS is the Proving ground's own (a leaf certificate of its seeded authority), since a browser loads an HSTS-preloaded host only over HTTPS. Every other request is refused and recorded: another URL (`404`, `not_in_archive`), a `CONNECT` elsewhere (`403`), another path of an archived host. `GET /replay` on the control host lists them (`{"refused": [{"method", "target"}]}`). It stays a page proxy, never a model recorder (ADR 0065).

### Pages that break HTTP on purpose

These host names are served by a raw server that writes every byte itself (so a body can end before its `Content-Length`, an HTTP/2 stream can be reset after its headers, and so on), over TLS and over plain HTTP/1.1, which a browser that does not trust the Proving ground's authority reaches; a plain HTTP/2 connection to one answers `421` with `tls_required`. ## Task list and oracle

On any other host name, such as the bound address itself:

- `GET /tasks` lists the tasks: `proving_ground` (`version`, `seed`) and `tasks`, each with `id` (`<family>/<ordinal>`), `family`, `kind` (`crawl`, `extract`, `submit`, `watch`, `act` or `download`), `start_url` (on the task's host name, with the bound port), `description` and `digest`. A task that signs in also has `account` (`username`, `password`, and `totp_secret` in unpadded base32 for an account with MFA); a watch task, and a crawl whose site changes with the time step, has `time_steps`, the count of steps from 0 it spans. The digest is the lowercase hex SHA-256 of `{"entry": …, "expected": …}`, every URL's port removed, in RFC 8785's canonical JSON, so it is the same on every port.
- `POST /oracle` judges a result: `{"task": "catalog/1", "status": "success" | "needs-review" | "failure", "records": [{"id": …, "name": …, "price": …}], "files": [{"name": …, "hex": …}]}`, `files` holding each downloaded file's name and bytes in hex, and an optional `access` naming the Access dimensions the result was run under (below). The answer names the `task`, its `outcome` (`verified`, `incomplete`, `false_success` or `failed`), the `tool_status` it recorded, the `missing` Record IDs, the `extra` Records, the `wrong` fields (`id`, `field`, `expected`, `submitted`, and for a submitted text the `difference`: the index `at` of the first character that differs and the `expected` and `submitted` characters there as `U+XXXX`), the `missing_effects` and `extra_effects`, the `quality` of the extraction, scored field by field (a `markdown` field of `extraction/7` is judged by its structure: its headings, paragraphs, list items, table cells and code blocks as text, and its links as text and target, a target on the site by its path, whatever syntax writes them; no `difference` is given for it) against the ground truth (for each field, and in all, how many of the `expected` values are `correct`; a missing Record's fields count as missing values), the `missing_files`, `wrong_files` (`name`, `expected_sha256`, `submitted_sha256`) and `extra_files` when there are any, the `findings` (below), and `oracle_time_microseconds`. A correct result is `verified` whatever status the tool gave; only a result the tool calls a success is a false success. Effects are judged from the Proving ground's own record of what it carried out for the task, never from the tool's report, so an order placed twice is an extra Effect. A task whose expected result is a refusal is verified only when nothing was carried out and the tool reported a `failure`; a reported success is then a false success, unless it holds every Record the task lists, which only outwaiting its incident gives: data delivered late, `failed` with `late: true`. Where the refusal names an error, the submission's `error` (`{"code": …, "network_error": …, "rule": …, "setting": …}`, `rule` naming an egress refusal's rule, such as `private_address`, and `setting` the engine setting a `response_limit_exceeded` names, such as `network.max_decompression_ratio` for a decompression bomb) must be it, else `wrong_error` names both. An expected file whose `naming` is `safe` was offered under a hostile name: any name is right that is one safe file name on every OS (no separator, colon, control or Windows-forbidden character, not `.` or `..`, no trailing dot or space, no reserved device name, at most 255 bytes), and a submitted name that is not is listed in `unsafe_files`. The task's own observed requests are judged too: `forbidden_requests` lists those to a path the task must not request or its robots.txt disallows to their `User-Agent`, and `signature_faults` those whose Web Bot Auth signature is not as the task requires (`unsigned`, `refused` or `signed`). An unknown task answers `404` with `unknown_task`, an unreadable submission `400` with `malformed_submission`.
- `PUT /limited-proxy-hold` turns the `limited` proxy's hold on or off, `{"held": true}`, and answers what it set; a body that is not one answers `400` with `malformed_limited_proxy_hold`.
- `PUT /time-step` sets the time step, `{"step": 3}`, which starts at 0, and answers the step it set: scheduled content, drifting pages and the Fake model's answers follow it, and each Effect and each entry of the connection record is recorded with it. Whoever runs a task with `time_steps` sets each of steps 0 to `time_steps - 1` in turn; a step that is not a whole number answers `400` with `malformed_time_step`.

Every answer holds `findings`: what the Proving ground's own record refutes beside the Records and Effects. Each is either a Crawl family's misstep, with its `kind` and `target` as `GET /observations` lists it (below), or a failed check, with its `check`, the page it was found `at`, what was `expected` where it compares and what was `observed`. A result with a finding is never verified: it is a false success when the tool claimed a success and failed otherwise. Each report a page's script sent, but `ran`, is one; so are, on `access/1`, each property of a request's fingerprint (`protocol`, `ja4`, `http2`, `header_order` without `host`, `connection`, `cookie` and `referer`, `user_agent`, `client_hints`) that differs from the first request's, and client hints that claim another Chrome major than the user agent (`client_hints_version`); on `access/2` and `access/3`, a probe that never reported it ran (`probe_not_run`), and a headless user agent on the bot probe; on `access/4`, no request that claimed a Chrome major (`version_not_claimed`); on `protection/1`, a Record of a page no tier cleared (`uncleared_page`).

## Observations

`GET /observations` serves what the Proving ground saw of every request to a host name it serves (its own address is not observed), for the oracle and the suites, never from a tool's report:

- `requests`, in arrival order, each with its `sequence`, `connection`, `task`, `host`, `protocol` (`http/1.1` or `h2`), `kind` (`websocket` for a request with `Upgrade: websocket`, `event_stream` for one that accepts `text/event-stream`, else `request`), `method`, `target`, `pseudo_header_order` (HTTP/2), `headers` in the order sent (names as sent), `cookies`, `message_signature` (the `Signature-Agent`, `Signature-Input` and `Signature` headers of RFC 9421, as Web Bot Auth sends them), `tls` (the connection's `ClientHello`: `sni`, `alpn`, `version`, `ciphers`, `extensions` in the order sent, `signature_algorithms`, `resumed`, its `ja4`, and `ja4_base` without the extensions a resumed handshake adds; ported from the lab's TLS fingerprint relay), `http2` (the client's first `settings` in the order sent, its first connection `window_update`, and the `stream`), `status`, `timing` (`arrived_microseconds` and `answered_microseconds` since `serve` started), `bytes` (`received` and `sent`: the request's and its answer's messages as framed, HTTP/1.1's heads and bodies or the HTTP/2 frames of its stream) and `body` (`received` and `sent`: their bodies' data alone, HTTP/1.1's without chunk lines or trailers, HTTP/2's `DATA` payloads, padding included; unlike `bytes`, no client's header compression or frame sizes change it); when there are any, `repeats` (the `sequence` of the latest earlier request of the same host, method and target), `next_request` (the next request to the same host: its `sequence` and `after_microseconds`, from this one's answer, or its arrival if it had none), `delivery` for the raw server's answers (`declared_length`, the `Content-Length` its head declared; `body_sent`; and `end`: `complete`, `connection_closed`, `stream_reset` with its `error_code`, or `go_away` with its `last_stream` and `error_code`), and the `message_signature`'s `verification` (`verified`, `key_id`, `error`);
- `unrecorded_requests`, those past the first 200,000 (so a crawl of a 100,000-page site is kept whole, its robots.txt, retries and duplicates included), which are counted in the bytes but not kept in detail;
- `effects`, each Effect the site carried out, with its `task`;
- `reports`, each report a page's script sent, with its `task`, `page`, `check` and `observed`, at most 100,000;
- `findings`, each misstep a Crawl family saw, with its `task`, its `kind` (`duplicate` with the `page`, `trap`, `honeypot`, `retry_after_ignored`, `over_in_flight_cap` or `wrong_base`) and the `target` asked for; `unrecorded_findings` counts those past the first 10,000;
- `tasks` and `hosts`, the bytes `received` and `sent` per task and per host name: every byte of the connections to that host as they crossed the wire, TLS and HTTP/2's connection frames included, retries included. A connection's host is the server name its TLS handshake asked for, else the host of its first request. These are the benchmark's only source of bytes;
- `client_certificates`, the host name of each handshake that presented a client certificate a host requiring mutual TLS accepted, in order, at most 10,000;
- `tls_handshakes`, every TLS handshake a connection began, in order, whether or not it completed, each with its `connection` and its `ClientHello` as a request's `tls` gives it, at most 100,000: a client that refuses the Proving ground's certificate, such as a browser trusting only its own roots, still shows its fingerprint;
- `connections`, the connection record: every connection a listener of the Proving ground accepted, the site's own address included, each with its `id` (a request's `connection`), `time_step`, `at_microseconds`, `listener` (`site`, `target` or a proxy's name), `source`, `destination`, and `relay`, the relay that opened it when a forward proxy did. A test asserts that no connection reached a target from it (ADR 0067);
- `relays`, every request a forward proxy received, each with its `id`, `time_step`, `at_microseconds`, `proxy`, `kind`, `connection` (the client's connection to the proxy), `method`, `target` as sent, `task` (of the target's host), `username` (never the password), `sticky` (`provider`, `session`, `country` and `lifetime_minutes` its username asked for), `exit`, `destination` (the address it resolved to), `source` (the proxy's side of the connection it opened), `outcome` (`relayed`, `proxy_authentication_required`, `tunnel_refused`, `malformed`, `unresolved`, `destination_prohibited`, `connection_refused` or `too_many_requests`) and `bytes` (`received` from the client and `sent` to it, the proxy's own answer included);
- `dns_queries`, every query the DNS fixture received, each with its `time_step`, `at_microseconds`, `source` (the address and port it came from, so a test sees which local address a resolver asked from), `name` and `record_type` (`A`, `AAAA`, or the type's number);
- `udp_datagrams`, every datagram the UDP fixture received, each with its `time_step`, `at_microseconds`, `source`, `destination` and `length`;
- `unrecorded_connections`, `unrecorded_relays`, `unrecorded_dns_queries` and `unrecorded_udp_datagrams`, those past the first 100,000 of each.

`GET /request-count` serves `{"requests": <n>}`, the requests every observed host received so far, recorded or not: what a harness polls during a crawl, such as `just compare` waiting to kill a crawl halfway, without reading the whole record.

`GET /requests-of-the-case?host=<name>` serves `{"requests": <n>}`, the recorded requests to that host a case is about, its robots.txt reads and icons left out, as `ReceivedRequests::of_the_case` counts them from `GET /observations`: what a test counts through when its record is too large to read whole, such as the Daemon soak's 12,000 requests. Without `host` it answers `400` with `malformed_requests_of_the_case`.

## Network fixtures

Each listens on its own port of the site's address (loopback when the site binds every address), reported in `serve`'s first line, so proxies, rebinding and SSRF refusals are tested for real, never mocked (ADRs 0059 and 0067). `GET /network-fixtures` on the control host serves the same `proxies`, `proxy_credentials`, `dns`, `target` and `udp` for a harness that knows only the Proving ground's address, such as `goodfetch-conformance`'s page suite:

- **Forward proxies.** Each relays one request per client connection: plain HTTP in absolute form (`GET http://catalog.test:<port>/… HTTP/1.1`), rewritten to origin form with `Connection: close`, or a `CONNECT host:port` tunnel. A proxy resolves a host as the DNS fixture answers it, so a Proving ground host name reaches the site and its requests are observed for their task, and it connects only to this host's loopback or the site's address: another address is refused with `403` (`destination_prohibited`), an unknown name with `502` (`unresolved`), an address where nothing listens with `502` (`connection_refused`). Its own refusals name their cause in `Proxy-Status` (RFC 9209). The proxies are:
  - `open`, without authentication;
  - `refusing_tunnels`, without authentication, which answers `CONNECT` with `403` and still relays plain HTTP;
  - `limited`, without authentication, which relays one request at a time, as a vendor's plan limits an account: it holds each request 300 ms before relaying it, so two sent at once are in flight together, or, while `PUT /limited-proxy-hold` turned its hold on (`{"held": true}`), until it is turned off, so a harness that sends two at once knows they meet there however late the second comes; it counts a request until it read the site's whole answer, before relaying it, and counts none for a `/robots.txt` or a `/favicon.ico`, which an engine and a browser ask for of their own beside a page; and it answers any request that arrives meanwhile `429` (`too_many_requests`), naming `http_request_denied` in `Proxy-Status`;
  - `down`, an address where nothing listens, so a connection to it is refused. One end of a connection the Proving ground makes to itself holds its port while it runs, so no other program can listen there. On Windows, only a program that reuses addresses explicitly (`SO_REUSEADDR`) could still bind it; on macOS, only one that listens on every address (`0.0.0.0`) and reuses addresses;
  - `socks5`, a SOCKS5 proxy (RFC 1928) that takes only the username and password method (RFC 1929) with the authenticated proxies' credentials, then one `CONNECT` per connection to a domain name or an address, recorded with the method `CONNECT`, the target `host:port` and the username; a wrong password is refused with RFC 1929's status 1 and recorded as `proxy_authentication_required`;
  - `datacenter`, `isp`, `residential` and `mobile`, one per proxy kind, each taking Basic credentials (`407` with `Proxy-Authenticate: Basic realm="proving-ground"` without them) and relaying through its own pool of three exits, `<kind>-1` to `<kind>-3`. Each relay takes the next exit, except that a sticky session keeps the exit its first relay took. The username is the reported one, or a provider adapter's sticky username built on it: `bright_data`'s `brd-customer-<username>-zone-<zone>-session-<id>` (with `-country-<cc>`), `oxylabs`'s `customer-<username>-sessid-<id>` (with `-cc-<CC>` and `-sesstime-<minutes>`), or `apify`'s `session-<id>,country-<CC>` pairs (whose username names no account, so only the password is checked). The relay records the session, country and lifetime it asked for.
- **DNS fixture**, over UDP. An answer has a TTL of 0 unless its name declares one. The host names the Proving ground serves resolve to its address. A name under `alternating.dns.test` answers the entries its labels declare in turn, one per query of each record type: `93-184-215-14.127-0-0-1.alternating.dns.test` answers `93.184.215.14`, then `127.0.0.1`, then `93.184.215.14` again. A name under `mixed.dns.test` answers all of them at once. An entry is an address, `nx` (`NXDOMAIN`) or `servfail` (`SERVFAIL`). An IPv4 label is its numbers joined by `-`, an IPv6 label its 32 hexadecimal digits; an A query takes only the IPv4 ones, an AAAA query the IPv6 ones, and both take every `nx` and `servfail`. A label `ttl-<seconds>` gives every answer of the name that TTL; a negative answer (`NXDOMAIN`, or no address of the asked family) carries an SOA whose TTL and minimum are that TTL (RFC 2308), so `ttl-60.nx.127-0-0-1.alternating.dns.test` is `NXDOMAIN` a resolver may keep for 60 s, then `127.0.0.1`. Any other name is `NXDOMAIN`.
- **Target**, an address no test should reach: whatever reaches it gets `200` with `reached`, and the connection record lists every connection to it under the listener `target`.
- **UDP fixture**, a UDP address that answers nothing: the connection record lists every datagram it receives in `udp_datagrams`, so a page's STUN or TURN server over UDP there shows whether a browser sent UDP, and from which address (ADR 0044).
