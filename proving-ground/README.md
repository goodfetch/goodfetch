# Proving ground

The website Goodfetch owns and generates (ADRs 0025, 0032 and 0063): every page comes from a seed, generated on request and never stored, and every task has an expected result derived from the same seed data, never from a tool's output. It depends on no Goodfetch crate but `goodfetch-test-support`, which `xtask dependency-direction` checks.

## `serve`

```sh
cargo run -p goodfetch-proving-ground -- serve --seed 158 --copy local --address 127.0.0.1:0 --network-profile none
```

The first output line is one JSON object: `address` (the bound address, port 0 replaced), `version` (the workspace version plus the commit, `0.0.0+<sha>`), `seed` (an unsigned 64-bit integer) and `network` (below). It serves until Ctrl-C or `SIGTERM`. Only the `local` copy exists yet; the online copy is #168's.

## Network profiles

`--network-profile` adds a round trip to every connection (ADR 0025): `none` (nothing added, shaped or calibrated), or `rtt-0`, `rtt-20`, `rtt-100` and `rtt-300` (0, 20, 100 and 300 ms, through the shaper). `--loss <percent>` (default `0`, such as `1` or `0.5`) loses that share of packets in each direction; it needs a shaped profile. `--shaper` picks what applies it:

- `proxy` (the default), the lab's user-space latency proxy, ported, on any OS without privileges, for unpublished runs. It listens on `--address`, forwards each connection to the server on a loopback port of its own, and delays each chunk of bytes by half the round trip in each direction, in order. A lost chunk waits a retransmission timeout more (200 ms plus the round trip, Linux's least) and holds back the chunks behind it, as TCP does; which chunks are lost is drawn from the seed. This approximates loss; `tc netem` loses real packets.
- `netem`, `tc netem` on Linux's `lo`, for published figures. It needs `CAP_NET_ADMIN` (root on the reference host) and iproute2's `tc` on `PATH`. It takes `lo`'s root: a `prio` root whose fourth band holds a `netem` of half the round trip and the loss, and `u32` filters that send it only the packets to or from the Proving ground's port, IPv4 and IPv6, so no other loopback traffic is shaped. One netem Proving ground runs per network namespace at a time; it removes the root when it stops, and a killed one leaves it (`tc qdisc del dev lo root` removes it).

Before the output line, a shaped profile is calibrated as the lab calibrates it: 50 one-byte round trips to an echo through the shaper, each paired with a direct one to another echo. `network` records it: `profile`, and for a shaped one `round_trip_microseconds`, `loss_percent`, `shaper`, `calibration` (`round_trip_microseconds` declared, `samples`, `shaped_median_microseconds`, `shaped_p95_microseconds`, `direct_median_microseconds`, `added_median_microseconds`, the median of each pair's shaped minus direct round trip, and `within_tolerance`) and `time_metrics`. The added median is within tolerance when it is off the declared round trip by at most the larger of 10% and 2 ms; outside, `time_metrics` is `unavailable`: the run keeps its correctness results and loses its time metrics. The calibration is a measurement recorded with the run, never asserted by a test (ADR 0064).

## HTTP/1.1, HTTP/2 and TLS

The one address serves plain text and TLS: a connection whose first byte starts a TLS handshake gets TLS, any other plain text. Either way it speaks HTTP/2 when its first bytes are HTTP/2's preface (ALPN offers `h2` and `http/1.1`) and HTTP/1.1 otherwise.

TLS comes from a certificate authority the Proving ground makes from its seed (ADR 0059's one seeded authority): the same seed gives the same authority byte for byte, its keys derived from the seed and every signature RFC 6979's deterministic ECDSA on P-256. `GET /certificate-authority` serves it as PEM. A client trusts it explicitly (the engine's per-domain `trusted_cas`, ADR 0042, or a competitor's documented option); nothing turns verification off. Each host name below has its own leaf certificate, never a wildcard, dated from the clock and valid for 397 days, since some platforms refuse a longer-lived server certificate.

## Page families

Each family is served on its own host name, and each of its tasks on a host name of its own, `<ordinal>.<family host>`, which serves the same pages, so every request names its task. A client maps them to the bound address (the `resolve` setting, ADR 0059):

- `catalog.test`, and `1.catalog.test` to `3.catalog.test` for its tasks: the `catalog` family, ported from the lab's HTTP catalog. Listing pages `/catalog/1` to `/catalog/10` link ten products each and the next page (`rel="next"`); product pages `/products/P-0001` to `/products/P-0100` show each product's ID, name and price; `/products/P-NNNN/order` is the product's order form, which posts `product=P-NNNN` to `/orders` and orders it once.
- `rendered.test`, and `1.rendered.test` and `2.rendered.test` for its tasks: the `rendered` family, ADR 0025's AJAX loading, infinite scroll, shadow DOM and iframes. `/feed`'s script loads its 24 items from `/api/feed/1` to `/api/feed/4` by AJAX, the next page each time the end of the list comes into view. Each item page `/items/I-0001` to `/items/I-0024` loads its item from `/api/items/<id>`, puts the name in the open shadow root of its `item-card` element and the price in the page, and shows the description in a same-origin frame, `/items/<id>/details`. None of a Record's data is in a page's own HTML.
- `login.test`, and `1.login.test` and `2.login.test` for its tasks: the `login` family, ADR 0025's logins with MFA and logins that expire. `/login` takes a username and password; account 1 then asks for a TOTP code (RFC 6238: HMAC-SHA-1, 30-second steps, six digits) at `/mfa`, accepting the steps before and after the current one; account 2's login expires after three pages behind it. `/account` lists six orders, `/account/orders/O-01` to `O-06`; without a live session both send to `/login` (`303`). The accounts come from the seed, so each seed (and each Journey) has its own, and the task list names them.
- `schedule.test`, and `1.schedule.test` for its task: the `schedule` family, ADR 0025's content that changes on a known schedule. `/board` shows the revision of the current time step: it changes at every step but those that leave a remainder of 2 when divided by 3 (`R-0` at step 0, `R-1` at 1 and 2, `R-2` at 3, `R-3` at 4 and 5, and so on). The board at a step is a pure function of the seed and the step, never of the wall clock.
- `1.portal.test` to `13.portal.test`: the `portal` family, the lab's portal site, one variant per task, each Record an `id` and a `price`. Tasks 1 to 5 hold five pages of twenty reports (`/reports?page=N`) behind a login form (`/login`) whose CSRF token is tied to a `pre` cookie, with the account the task list gives; a session (`sid`) of task 2 serves four pages and is then answered with the login form and a `200`, one of task 3 serves three and is renewed by `POST /session/refresh` with its `rt` cookie, and a harness revokes every session between the two runs of task 5 (`POST /revoke-sessions` on the bound address). Each sign-in is an Effect, so a crawl that signs in more than it needs is judged by the site's own record. Tasks 6 to 11 hold one listing of a hundred products behind six renderings: server HTML (`/list?page=N`), a script shell (`/api/list`), partial hydration (eight in the HTML), stale HTML prices a script corrects (`/api/prices`), GraphQL behind "Load more" (`/catalog`, `POST /graphql`) and an infinite feed (`/feed`, `/api/feed?cursor=`). Task 12 is a crawler trap (`/shop`): every link carries a new `sid` and tracking parameters, categories have four sort orders and the events calendar pages on without end; a page is a pure function of the seed and its URL. Task 13 is a table of 1,500 orders (`/orders?page=N`, or `?after=<id>` through `rel="next"`) that, every third request, loses two rows already paged past and gains one on top; the oracle requires every row that lived through the crawl, once each, and tolerates the rows added or deleted.
- `<n>.actionability.test` and `<n>.navigation.test`: the hand-made `actionability` and `navigation` families, written by hand with their expected results in `pages/actionability.toml` and `pages/navigation.toml` (story 29), ported from the lab's actionability, primitive, form, navigation, frames and files fixtures. Each page's script posts the event that reaches one of its controls to `POST /effects` (`{"event", "target", "trusted", "details"}`, `trusted` the browser's `isTrusted`), recorded as an `event` Effect of the task; the oracle requires exactly the events listed: one trusted event of the right kind on the right control, none on a decoy, none twice. Tasks whose control never becomes actionable, stays covered, is ambiguous or is swapped for a destructive one under the pointer (`retarget`) expect a refusal. Cross-origin frames come from `<n>.navigation-frame.test`; the download (`navigation/7`) serves seeded bytes with a CRLF, a NUL and a `0xff` byte.
- `agent.test`, and `1.agent.test` to `9.agent.test` for its tasks: the `agent` family, ported from the lab's Agent pages. `/demo` shows a pricing table (Starter and Pro, prices drawn from the seed) and a demo-booking form whose script posts the booking (`{"kind": "booking", "name", "email", "plan", "consent", "trusted"}`, `trusted` being the submit event's `isTrusted`), or a click on its delete control (`{"kind": "delete_account", "trusted"}`), to `/effects`; the Proving ground records each as an Effect with the time step it arrived at. The pages of `agent.test`, `agent/1` and `agent/2` drift on the time step (step mod 4): 0 the baseline, 1 every `id` and `class` renamed, 2 a delete control where the booking button was, 3 the Pro price changed. The fault tasks' pages never drift.
- `blog.rust-lang.org` and `www.fda.gov`: the `replay` family, two frozen real pages (the lab's WCXB snapshots, in `fixtures/archive/` with their `.source.toml`), served at their original paths through the replay proxy below, or on their own host names.
- `extraction.test`, and `1.extraction.test` to `6.extraction.test`: the `extraction` family, ADR 0025's Extraction cases on seeded products (J-011). `/products` links product pages carrying schema.org JSON-LD (brand, GTIN, rating, currency) and Open Graph metadata (description); `/shop` loads its products only from its hidden API, `/api/products/1` and `/api/products/2`; `/churn` links pages whose class names differ on every page; `/variants` links pages in six layouts; `/huge` is one table of 2,000 products, over 5 MiB, generated on request; `/<region>/products/X-0100` shows one product in `us`, `de`, `fr`, `jp` and `in`, each in its locale's language, currency and number format, linked by `hreflang` alternates.
- `encodings.test`, `1.encodings.test` and `2.encodings.test`: the `encodings` family (ADRs 0073 and 0119, CO-24). `/pages` links one page per case: Shift_JIS, EUC-KR, GB18030, Big5, windows-1251, ISO-8859-2, ISO-8859-15, UTF-16 with a BOM, a charset that contradicts its `<meta>`, no declared charset in UTF-8 and in a legacy encoding, the `latin1` and `ascii` labels with byte 0x80, a `<meta>` UTF-16 label, `x-user-defined`, a `<meta charset>` past the first 1,024 bytes among head tags and one after the body tag, and a byte UTF-8 cannot decode. Each page's expected text is held in UTF-8, with the encoding ADR 0119's order reads it with and where that comes from (`bom`, `header`, `meta`, `utf8` or `detected`).
- `languages.test` and `1.languages.test`, and the IDN host name `bücher.languages.test` (`xn--bcher-kva.languages.test`): the `languages` family (ADR 0073). `/pages` links Arabic and Hebrew with their marks, Japanese and Chinese without spaces, Devanagari, Thai, combining marks served decomposed (NFD), emoji sequences, astral characters, the Unicode record (bidi text with marks, NFC and NFD forms of one word, a ZWJ sequence, an astral character, a zero-width joiner, a BOM, a tab and a newline), and a page at the non-ASCII path `/wörter/日本語?q=café&ort=Zürich`, which needs its query. Every expected text is in the normalization form served.
- `files.test`, and `1.files.test` to `3.files.test`: the `files` family (ADRs 0025 and 0119). `/files` links a PDF, a ZIP, a JSON response, a 404 typed `text/csv`, an HTML page and a PDF served with no `Content-Type`, and a page whose `<a download>` link offers `/files/export.csv`.

The Crawl families (ADR 0025's Crawl cases, and ADR 0005's parameter that looks like it has no effect) keep, per task host, what they saw a crawl do, and record each misstep as a finding (see Observations); the rules that depend on the client's address read the address of the connection, which is the latency proxy's own behind a network profile:

- `statuses.test` (`statuses/1`): an index of 40 articles, 30 linked directly, 5 through one redirect each (`301`, `302`, `303`, `307`, `308`) and 5 through a chain of four; a link to every HTTP error status IANA registers but the unused 418, `402` included, each answering its status with an error page in the articles' template (and the headers the status requires); soft 404s, `200` pages in that template that say the article does not exist (every unknown article number is one); and three redirect loops (`/loops/a` and `/loops/b`, `/loops/self`, and `/loops/endless/<n>`). A task may make 100 requests to the loops; each one past it is a `trap` finding.
- `traps.test` (`traps/1`): a shop of 30 items in three categories, each item linked at two URLs that the fixed URL rules (ADR 0120) make one: a fragment, `utm_*`, `gclid`, `fbclid`, `;jsessionid=`, a percent-encoded `-`, or parameters in another order. A page fetched again under any of its URLs is a `duplicate` finding. Two traps page on without end: the events calendar `/calendar/<yyyy-mm>` and the archive's relative `more/` link; a task may make 30 requests to them together, and each one past it is a `trap` finding. Each page carries four honeypot links under `/hp/`, hidden by `hidden`, `display:none`, `visibility:hidden` and an `aria-hidden` element off screen, and disallowed by `/robots.txt`: a request for one is a `honeypot` finding and flags the address that made it, refused with `403` on that task's host from then on.
- `parameters.test` (`parameters/1`): four listing pages `/products?page=<n>` of twelve products, each linked in three colours, `/product?id=P-NNNN&colour=<1..3>&ref=listing`. `ref` never changes the page, and neither does `colour` on the first listing page, whose products come in one colour (a page shows a product's first colour for one it lacks); further on, some products have a distinct page per colour, with its own ID `P-NNNN-<colour>` and price. A crawl that learned `colour` has no effect loses those pages.
- `limits.test` (`limits/1` to `limits/3`): one list of 24 items behind a rule per task. `limits/1` lets each address make 10 requests, then answers `429` with `Retry-After: 1` and pauses it for that second; a request in the pause is a `retry_after_ignored` finding, and the third flags the address. `limits/2` lets each address fetch 10 pages and flags the one that asks for more, so a complete crawl needs more than one address. `limits/3` holds each page 50 ms and allows 2 requests in flight on its host at once; one more is answered `503` with `Retry-After: 1` and is an `over_in_flight_cap` finding.
- `scale.test` (`scale/1`, `scale/2`): 4,194,304 item pages `/items/1` to `/items/4194304`, generated on request, in sections of 256 listed by `/sections/<n>`; each section has a sitemap index `/sections/<n>/sitemap.xml` of two sitemaps, and `/sitemap.xml` indexes 128 sitemaps of 32,768 items each. Sitemaps name absolute `http://` URLs on the host and port the request named. `measurements/scale/` holds the declared measurement of how fast the family is served beside how fast a competitor consumes it (`node proving-ground/measurements/scale/measure.ts --proving-ground <release binary> --crawlee <node_modules with crawlee>`), and its runs in `runs/`. Its first run, on 2026-10-19, met its threshold (the Proving ground's slowest trial served 542 pages a second, Crawlee's fastest consumed 125) on a host far past the `local-controlled` gates, with a one-minute load of 553 on 14 CPUs; it is to be run again on a quiet host.

## The Fake model

`model.test` serves the Fake model (ADR 0065), ported from the lab's `fake-llm.ts`: point a Model provider's base URL at `http://model.test:<port>/v1` (OpenAI-compatible chat, `POST /v1/chat/completions`), `http://model.test:<port>` (Anthropic Messages, `POST /v1/messages`) or `http://model.test:<port>/v1beta` (Gemini, `POST /v1beta/models/<model>:generateContent`, and `:streamGenerateContent`, with `alt=sse` or as one JSON array). Each format answers whole or streamed (`stream: true`; OpenAI's `stream_options.include_usage` adds the usage chunk), with the format's fields, stream events and error bodies.

- **What it answers.** The task whose description appears in a string of the request (the instruction a Journey passes), else the task whose host name does (a page URL). Its answer is the task's Records at the current time step (a booking's fields for `agent/1`), shaped as the request asks: a call of the tool `tool_choice` names, else of the first tool offered, its parameters' schema filled from the Records; the structured output's schema filled from them (`response_format`'s `json_schema`, Anthropic's `output_format`, Gemini's `responseJsonSchema` or `responseSchema`); else the text `{"records": […]}`. After a tool result it answers in text. A request naming no task answers `400` in the format's error body. Answers depend only on the request, the seed and the time step; IDs come from a hash of the seed and the request.
- **Tokens.** It counts each call itself: input tokens are a quarter of the characters of every string in the request body, rounded up; output tokens a quarter of the characters of the answer's text, refusal, or tool name and arguments, rounded up. The response's usage carries them, and `GET /model-calls` on the control host lists every call (`sequence`, `format`, `model`, `stream`, `task`, `fault`, `input_tokens`, `output_tokens`), so a test checks the engine's Usage against an independent count.
- **Faults**, asked for by a task, never by a switch in the binary: `agent/3` a rate limit (`429`, `Retry-After: 1`), `agent/4` an overload (`503`, Anthropic's `529`), `agent/5` a timeout (no answer until the client gives up), `agent/6` a cut stream (the body ends after its first content event, or halfway through a whole answer), `agent/7` malformed JSON (in OpenAI's tool arguments, else as text), `agent/8` a refusal (OpenAI's `refusal`, Anthropic's `stop_reason: "refusal"`, Gemini's `finishReason: "SAFETY"`), `agent/9` a wrong but plausible price, which the oracle refutes.
- **Model recordings.** `tests/it/model_recordings.rs` checks the Fake model's answer to every committed Model recording's request (a JSON file in any `recordings/` folder) against the recorded response's shape: fields, types, stream event kinds and order, and error bodies.

## The replay proxy

Point a browser's proxy at the bound address (`--proxy-server`, with no loopback exception): a `GET` in absolute form to an archived page's original URL over `http://` gets the archived page, and a `CONNECT` to an archived host's port 443 opens a tunnel whose TLS is the Proving ground's own (a leaf certificate of its seeded authority), since a browser loads an HSTS-preloaded host only over HTTPS. Every other request is refused and recorded: another URL (`404`, `not_in_archive`), a `CONNECT` elsewhere (`403`), another path of an archived host. `GET /replay` on the control host lists them (`{"refused": [{"method", "target"}]}`). It stays a page proxy, never a model recorder (ADR 0065).

## Task list and oracle

On any other host name, such as the bound address itself:

- `GET /tasks` lists the tasks: `proving_ground` (`version`, `seed`) and `tasks`, each with `id` (`<family>/<ordinal>`), `family`, `kind` (`crawl`, `extract`, `submit`, `watch`, `act` or `download`), `start_url` (on the task's host name, with the bound port), `description` and `digest`. A task that signs in also has `account` (`username`, `password`, and `totp_secret` in unpadded base32 for an account with MFA); a watch task has `time_steps`, the count of steps from 0 it spans. The digest is the lowercase hex SHA-256 of `{"entry": …, "expected": …}`, every URL's port removed, in RFC 8785's canonical JSON, so it is the same on every port.
- `POST /oracle` judges a result: `{"task": "catalog/1", "status": "success" | "needs-review" | "failure", "records": [{"id": …, "name": …, "price": …}], "files": [{"name": …, "hex": …}]}`, `files` holding each downloaded file's name and bytes in hex. The answer names the `task`, its `outcome` (`verified`, `incomplete`, `false_success` or `failed`), the `tool_status` it recorded, the `missing` Record IDs, the `extra` Records, the `wrong` fields (`id`, `field`, `expected`, `submitted`, and for a submitted text the `difference`: the index `at` of the first character that differs and the `expected` and `submitted` characters there as `U+XXXX`), the `missing_effects` and `extra_effects`, the `quality` of the extraction, scored field by field against the ground truth (for each field, and in all, how many of the `expected` values are `correct`; a missing Record's fields count as missing values), the `missing_files`, `wrong_files` (`name`, `expected_sha256`, `submitted_sha256`) and `extra_files` when there are any, the `findings` the Proving ground recorded for the task, and `oracle_time_microseconds`. A correct result is `verified` whatever status the tool gave; only a result the tool calls a success is a false success. Effects are judged from the Proving ground's own record of what it carried out for the task, never from the tool's report, so an order placed twice is an extra Effect. A task with any finding is never `verified`: a false success when the tool claimed success, `failed` otherwise. A task whose expected result is a refusal is verified only when nothing was carried out and the tool reported a `failure`; a reported success is then a false success. An unknown task answers `404` with `unknown_task`, an unreadable submission `400` with `malformed_submission`.
- `PUT /time-step` sets the time step, `{"step": 3}`, which starts at 0, and answers the step it set: scheduled content, drifting pages and the Fake model's answers follow it, and each Effect is recorded with it. Whoever runs a task with `time_steps` sets each of steps 0 to `time_steps - 1` in turn; a step that is not a whole number answers `400` with `malformed_time_step`.

## Observations

`GET /observations` serves what the Proving ground saw of every request to a host name it serves (its own address is not observed), for the oracle and the suites, never from a tool's report:

- `requests`, in arrival order, each with its `sequence`, `connection`, `task`, `host`, `protocol` (`http/1.1` or `h2`), `method`, `target`, `pseudo_header_order` (HTTP/2), `headers` in the order sent (names as sent), `cookies`, `message_signature` (the `Signature-Agent`, `Signature-Input` and `Signature` headers of RFC 9421, as Web Bot Auth sends them), `tls` (the connection's `ClientHello`: `sni`, `alpn`, `version`, `ciphers`, `extensions` in the order sent, `signature_algorithms`, `resumed`, its `ja4`, and `ja4_base` without the extensions a resumed handshake adds; ported from the lab's TLS fingerprint relay), `http2` (the client's first `settings` in the order sent, its first connection `window_update`, and the `stream`), `status`, `timing` (`arrived_microseconds` and `answered_microseconds` since `serve` started) and `bytes` (`received` and `sent`: the request's and its answer's messages as framed, HTTP/1.1's heads and bodies or the HTTP/2 frames of its stream);
- `unrecorded_requests`, those past the first 100,000, which are counted in the bytes but not kept in detail;
- `effects`, each Effect the site carried out, with its `task`;
- `findings`, each misstep a Crawl family saw, with its `task`, its `kind` (`duplicate` with the `page`, `trap`, `honeypot`, `retry_after_ignored` or `over_in_flight_cap`) and the `target` asked for; `unrecorded_findings` counts those past the first 10,000;
- `tasks` and `hosts`, the bytes `received` and `sent` per task and per host name: every byte of the connections to that host as they crossed the wire, TLS and HTTP/2's connection frames included, retries included. A connection's host is the server name its TLS handshake asked for, else the host of its first request. These are the benchmark's only source of bytes.
