# Automan — matrice des capacités de crawl, ressources et workers

État des sources au **7 octobre 2026**. Ce document alimente l’architecture, le design et le PRD ; les contrats Automan sont **proposés**, ils ne décrivent pas une implémentation existante. Périmètre : Crawlee TS/Python, Spider, Scrapy, Colly, Crawl4AI, Firecrawl, Scrapling, Katana, Apache StormCrawler et transports/clients navigateur pertinents. Il ne prétend pas couvrir chaque projet mondial ni chaque option de chaque dépôt.

Recherche complémentaire : **`sources_reviewed = 10`**, deux appels Exa de cinq résultats pour Katana et StormCrawler, puis inspection primaire des sources. Réutilisation des recherches précédentes ([moteurs](./2026-10-07-crawl-engines.md), [contrats Crawlee/Spider](./2026-10-07-crawlee-spider-contracts-followup.md), [moteurs/workers/navigateurs](./2026-10-07-engines-workers-browsers.md)) sans recompter leurs résultats. Les archives et fichiers ont été lus ; aucun benchmark ni lancement de ces projets n’a été effectué pour cette matrice.

## 1. Lecture de la matrice et références figées

**Présent** signifie qu’un mécanisme est observable dans les sources ; **option** qu’un backend, plugin, feature ou paramètre doit l’activer ; **non établi** que l’audit ne permet pas de promettre la propriété, sans prouver son impossibilité. « Durable » doit toujours préciser ce qui est persisté, quand et avec quel backend. « Pool », « adaptatif » et « worker » ne sont pas des capacités uniques.

## 2. Familles : ne pas reprendre le mauvais niveau d’abstraction

| Outil | Rôle fort | Runtime / acquisition | Navigateur | Distribution native observée | Position utile pour Automan |
|---|---|---|---|---|---|
| Crawlee TS | Traitement d’URLs, handlers, queue, sessions, autoscale, storage | Node/TS, clients HTTP remplaçables ; Impit facultatif | Playwright/Puppeteer ; Stagehand adapter séparé | Un pool async local n’est pas une flotte distribuée ; queue multi-client selon backend | Référence fonctionnelle et bridge d’écosystème. |
| Crawlee Python | Même famille, clients de stockage distincts | Python async, HTTP et parsing | Playwright ; Stagehand REST + Playwright/CDP | SQL/Redis coordonnent les claims ; déploiement de workers reste à fournir | Référence de queues indépendantes du moteur navigateur. |
| Spider | Collecte Rust HTTP/rendering/budgets, smart et hooks | Rust/Tokio, reqwest | Chromey → Chrome/Chromium CDP ; features optionnelles | `decentralized` + `spider_worker` HTTP Rust/Warp/Hyper | Adapter et composants spécialisés ; frontier durable appartenant à Automan. |
| Scrapy | Scheduler/downloader/middlewares/pipelines | Python ; frontières moteur/downloader/scraper | Plugins tel scrapy-playwright | Distribution via extensions, pas une flotte universelle de base | Contrats de middlewares, pipelines et reprise locale. |
| Colly | Collecteur Go HTTP à callbacks | Go/net/http, transport personnalisable | Rendu JS non intégré équivalent à Playwright | Queue à goroutines ; storage injectable | Baseline HTTP simple, limites par domaine et callbacks. |
| Crawl4AI | Contenu/corpus/extraction pour IA, deep crawling | Python, stratégies HTTP/browser | Playwright, managed browser/CDP, sessions | Dispatcher local ; service Docker/API distinct d’une queue distribuée durable | Extraction, cache, sessions et contrôle de mémoire. |
| Scrapling | Parsing adaptatif + fetchers + spiders | Python, curl_cffi | Dynamic/Stealthy sessions, Patchright | Scheduler/checkpoints locaux ; pas flotte durable démontrée | Recettes de parsing, transport et checkpoints explicites. |
| Katana | Découverte/scope/forms/JS/XHR, pipelines de reconnaissance | Go HTTP avec retryablehttp/fastdialer | Rod, modes hybrid et full headless distincts | Parallelism des inputs et fetchers ; pas leases de flotte démontrés | Découverte enrichie et contrôles de périmètre. |
| StormCrawler | Crawl continu distribué et statut d’URLs | Java, Apache Storm, protocoles dont OkHttp | Module Playwright optionnel/CDP/serveur distant | Topologie Storm + spouts/bolts/frontier persistante configurée | Référence de partitionnement, politeness, recrawl et feedback. |

### Clause Stagehand à conserver dans le PRD

`@crawlee/stagehand` 3.18.2 déclare **Stagehand TS `^3.0.0`**, pas v4. Le plugin lance Stagehand puis connecte Playwright au même browser ; `_newPage` utilise `contexts()[0]` et ignore les context options. `act`/`observe`/`extract` lient la page, **`page.agent` n’injecte pas cette page**. Python1.10.4 utilise le SDK REST `>=3.19.5,<4.0.0`, une API différente, et lie `execute` à sa page ; son intégration documente **incognito et fingerprint complet non supportés**. La parité BrowserPool générale ne s’applique donc pas automatiquement à tous les adapters. [Package TS](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/package.json), [controller](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-controller.ts), [wrapper TS](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/utils/stagehand-utils.ts), [wrapper Python](https://github.com/apify/crawlee-python/blob/v1.10.4/src/crawlee/browsers/_stagehand_types.py).

## 5. Matrice durabilité, reprise et portée des retries

| Mécanisme | Ce qui est effectivement présent | Ce que cela n’établit pas | Contrat Automan proposé |
|---|---|---|---|
| C-TS RequestQueueV2 | Claim avec lock, prolongation, reclaim, handled ; backend stockage local ou service configuré | Transaction avec dataset/effets métier ; frontière de reprise inchangée après crash | Lease token + epoch fencing ; tentative séparée du job ; commit atomique résultat/état lorsqu’ils partagent le store. |
| C-PY SQL | Block expiry/client_key ; `FOR UPDATE SKIP LOCKED` pour PG/MySQL/MariaDB, autre chemin de claim pour autres dialectes | Même comportement/performance pour tous dialectes ; garantie globale cloud | Backend contract tests par dialecte ; capacité multiworker annoncée seulement après tests concurrence/kill. |
| C-PY Redis | Scripts Lua claim atomique et récupération stale ; sets ou Bloom selon stratégie | Durabilité indépendante de la config Redis ; dataset/job atomicité ; absence de faux positifs du mode Bloom | Store durable explicite ; dédup exacte par défaut pour complétude ; Bloom seulement accélérateur ou mode pertes accepté. |
| C-TS defaults storage | `persistStorage=true` et **`purgeOnStart=true`** | Reprise automatique du même run avec files par défaut | Run ID stable, reprise explicitement liée au run ; aucune purge implicite d’état durable en mode production. |
| SP SQLite disk | Tables `resources(id,url)` et `signatures` : visited/signatures ; persist=false par défaut, conservation opt-in | Pending frontier, leases, checkpoint des steps et sink atomique | Spider adapter publie découvertes ; frontier durable Automan reste source de vérité. |
| SP queue et pages | Tokio broadcast in-memory ; `ChannelGuard` avec timeout250ms ; spool optionnel | Journal durable de jobs/résultats ; absence de perte par retard du consommateur | IPC/streams backpressured + spool durable référencé ; acquitter après commit, traiter les messages en retard explicitement. |
| SC JOBDIR | Priority queue disque + dupefilter persisté ; requests non sérialisables peuvent rester mémoire | Chaque callback externe atomique ; snapshots de navigateur | Schéma de Request sérialisable indépendant du SDK ; refuser ou isoler callback non persistable dans un run durable. |
| CO queue/storage | Queue goroutines ; Storage `GetRequest()` pop ; défaut mémoire ; visited/cookies Storage séparé | API claim/ack/lease dans l’interface de base ; exactement-une-fois | Ne pas adapter un simple pop en prétendant conserver la sémantique durable ; adapter doit déclarer ses garanties. |
| SL checkpoint | Snapshot pending + inflight conservés dans scheduler, seen ; pickle temp puis rename ; interval défaut300s | Persistence par opération, état complet browser/sinks ; fsync crash/power-loss établi | Snapshot périodique seulement accélérateur ; journal durable de transitions ; import checkpoint contrôlé/versionné. |
| KA resume | `RunnerState.InFlightUrls` des **inputs racines** ; JSON écrit sur SIGINT/SIGTERM | Capture de tout le frontier découvert ; recovery après SIGKILL avant snapshot | Reprise au niveau URL/step/lease ; seed restart distingué d’un frontier resume. |
| ST status frontier | URL statut/metadata/nextFetchDate ; SQL/OpenSearch/URLFrontier selon topology ; ack/fail Storm ; SQL batch ack après executeBatch | Une transaction universelle index/results/status ; instantané d’un workflow navigateur | Frontier de recrawl et statut des docs ; output sink idempotent ; redelivery possible documentée. |
| FC NuQ PG snapshot | queued/active/completed/failed, claim `SKIP LOCKED`, lock UUID, heartbeat, finish conditionné lock ; route FDB optionnelle | Réussite d’extraction métier ; copy-paste légal/performance gratuit ; parité SaaS | Queue service à owner unique ; heartbeat/fencing/deadletter et reconciliation visibles ; pas deux moteurs de queue silencieusement divergents. |

## 10. Contrat cible Automan : sources de vérité et invariants

### Objets et propriétaires proposés

| Objet | Responsable canonique | Champs/relations essentiels | Invariant |
|---|---|---|---|
| `Run` / `WorkflowSpec` / `CrawlSpec` | Control plane Rust | Version spec, seeds, identity requirements, budgets, validators, adapters | Un SDK ne réimplémente ni leases ni logique de commit. |
| `WorkItem` | Frontier/workflow scheduler | run_id, work_id, URL/action input, unique_key, priority, ready_after, desired capabilities | Identité d’un travail séparée des tentatives et de l’URL finale après redirect. |
| `Attempt` | Worker executor + journal | attempt_id, owner, lease token/epoch, started/deadline, transport/profile/proxy, costs | Un worker dont le lease a expiré ne peut pas publier un commit tardif autoritatif. |
| `IdentityContext` | Session manager | Compte/proxy/fingerprint/storage_state/version, owner/exclusive lease, capabilities | Deux workflows à effets ne mutent pas concurremment le même état auth sans politique explicite. |
| `BrowserHost` / `PageLease` | Browser pool | Owned/borrowed, backend version, pages/contexts, memory, health, drain status | Aucune page/future/permit orpheline après cancel ou crash ; page/frame liés à chaque appel IA/action. |
| `Observation` / `ResultEnvelope` | Executor + validator | Origin status, redirects, MIME, raw/artifact refs, DOM/screenshot, extraction/schema, completeness | HTTP200 ou LLM done ne suffit pas pour état succeeded. |
| `Commit` / `OutboxEvent` | Durable store | Résultats idempotents, transition état, découvertes validées, output revision, sink delivery | Commit durable avant ack ; sink externe livré/rejoué idempotemment depuis outbox. |
| `CrawlDocument` | Frontier recrawl | Canonical key, last fetch/result/error, ETag/date, next_fetch_at, provenance | Visited ne signifie ni résultat valide ni forever-complete. |

### États et garanties proposées

Cycle de job : **queued → leased → running → validating → committed**, ou **retry_wait / failed_terminal / cancelled / unknown_effect**. `unknown_effect` concerne une action dont l’effet externe pourrait avoir eu lieu avant timeout/perte de connexion ; il ne doit pas être reclassé arbitrairement en échec rejouable.

Pour collecte sans effet métier, viser **at-least-once execution + résultats idempotents**. Lorsque job/outputs/discovered URLs partagent le même store transactionnel, une transaction peut couvrir leur commit interne. Elle ne rend pas transactionnel un site externe. Pour workflows à effets, combiner check-before/check-after, clés d’idempotence disponibles, reçus et règles de reconciliation ; promettre « exactly once sur le Web » serait injustifié.

Les transports HTTP et browser reçoivent le même budget/deadline/identity policy. Le mécanisme d’escalade change la tentative de fetch/render, pas le propriétaire du run. Les plugins déclarent capacités et garantie effective — `http`, `browser`, `context_isolation`, `remote_connect`, `durable_claim`, `stream_backpressure`, `auth_snapshot`, `actionability`, formats — et doivent refuser les exigences qu’ils ne satisfont pas.

| F-14 P2 | Proxy/profile providers, Impit/wreq adapters, resource interception | F-03/F-05/F-09 | Gains e2e à réussite égale et sites/proxies/versions fixés ; pas de « stealth absolue ». |
| F-15 P2 | Recrawl/cache/ETag/change detection | F-02/F-06/F-07 | Contenu unchanged/changed, identité/cache partition, invalidation schema/recipe ; revisits schedulés. |
| F-16 P2 | Multi-format/PDF/OCR/WARC/Markdown transforms | F-05/F-06 | Corpus goldsets, pertes/limites explicites, artefacts/provenance ; parse coût distinct du fetch. |
| F-17 P2 | Multi-backend race/hedge/quality comparison | F-06/F-09/F-10 | Seulement acquisition sûre ; frères annulés et costs comptabilisés ; résultat qualité≥baseline. |
| F-18 P3 | Bridges Crawlee/Scrapy/Spider/Katana/Storm/Firecrawl APIs | F-01/F-02/F-06 | Chaque adapter passe contract suite ; capability gaps visibles, source/cloudversion pinned. |

**Dépendance structurante :** avancer F-02/F-03/F-06 avant de multiplier les moteurs et workers. Sans eux, Automan accumulerait des features de marché tout en laissant les trois gaps identifiés — durabilité, commit et concurrence de session — au code utilisateur.

## 12. Protocole de preuve et choix build/reuse

Le benchmark compare un **travail validé**, pas seulement des URLs « visitées ». Publier site fixtures, payloads/goldsets, versions, hardware, concurrency, cold/warm browser/connexion/cache, proxy/IP, modèle/température, tokens et features. Mesurer p50/p95, wall time, CPU/RSS, sockets/browser/page peak, bytes, tokens/coût, complétude et taux d’échec final ; inclure queues/sinks lents et interruption. Les microbenchmarks de parsing ou transport restent utiles, mais ne sont pas convertis en promesse de workflow « sans égale ». Voir l’[audit de benchmark](./2026-10-07-benchmark-audit-followup.md).

Décision proposée : **posséder protocol/journal/frontier/identity/result-policy ; réutiliser transports, drivers et parsers via adapters versionnés**. Crawlee sert de référence de profondeur des pools et de queues ; Spider de référence Rust acquisition/rendering/features ; StormCrawler de référence frontier/recrawl distribués ; les autres fournissent extraction, middleware, discovery et corpus de régression. Réutilisation ou contribution upstream d’un composant étroit précède un fork global. Aucun choix de langage ne dispense de tests sur Chrome réel, de garanties de stockage et d’une matrice de maintenance/licences.

### Limites de cette matrice

- Faits de sources figées, sans validation complète d’installation ou stress réseau/DB/Chrome.
- Snapshot Firecrawl et code stable des autres projets ne sont pas interchangeables ; infra SaaS privée non extrapolée.
- Les lignes « Automan » sont des propositions de contrat/PRD ; elles nécessitent une implémentation et leurs tests d’acceptation.
- Plusieurs capacités requièrent flags/features/plugins/backends ; les défauts et restrictions cités priment sur les slogans de README.
- Les capacités agent/perception/repair détaillées appartiennent au rapport navigateur/agent complémentaire ; cette matrice se concentre sur leur intégration sûre avec crawl/pools/workers.
