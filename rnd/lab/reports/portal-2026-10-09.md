## Sessions

### The site

A portal of 5 report pages (100 records) behind a login with a CSRF token: a pre-session cookie carries the form token, and a wrong token gives `403`. Five situations:

| Variant | What happens to the session |
| --- | --- |
| `login-csrf` | nothing: one login, five pages |
| `session-expiry` | the session expires after 4 pages; the portal responds with **`200` and the login form** at the report URL, like many portals |
| `session-refresh` | the session expires after 3 pages, with a redirect to the login; an `rt` cookie allows `POST /session/refresh` |
| `session-resume` | the process stops after 2 pages and writes its journal (cursor, records and, depending on the policy, its cookies) to disk; a new process, with a new client or a new browser context, rereads it and continues |
| `resume-revoked` | like `session-resume`, but the site revokes all sessions during the stop |

### The policies

The recipe declares the login URL, the refresh and its cookie, and the credentials reference. Three policies:
- `status-only`: cookies reused; the session is judged lost on a `401`, a `403` or a landing on `/login`.
- `contract`: cookies reused; each page must be the expected authenticated listing. A login form in its place is a lost session, and any other page stops the task (`E_CONTRACT`).
- `relogin-each-run`: same page contract, but no cookies reused; login at the start of each run.

A lost session first tries the declared refresh, if its cookie is present, then the login, at most twice.

### Reading

- **The HTTP status does not tell whether the session holds.** When the portal responds `200` with its login form, `status-only` reads a page with no records and no next link, then declares the crawl finished. It is missing 20 records over HTTP and 40 in the browser, where the login followed by its redirect consumes one more session page. That makes 20 false successes out of 20. Judging each page against its contract is enough to eliminate them.
- **Resuming the journaled session avoids one login per restart.** After a stop, `contract` resumes with its cookies and does not log in again. `relogin-each-run` logs in again, i.e. one more login per resume, which a portal with MFA or login alerts makes expensive. When the site has revoked the session during the stop, the resume detects it on the first page and logs in once, with no loss or duplicate: the cursor and the records come from the journal.
- **The declared refresh avoids a second login** for all three policies, because here expiry goes through a redirect, which even `status-only` recognizes.
- The two tiers give the same counts: the session carries the same cookies over HTTP and in the browser, and a fresh browser context restarts from the exported cookies.

### What this says for the architecture

1. **The engine judges each page of a session against the recipe's contract**, not against the HTTP status: an expected authenticated listing, or a login form recognized as a lost session. An unknown page stops the task with a typed error.
2. **Session state is part of the run journal.** Cookies, cursor and already-validated records are taken over by a new process. The resumed state is revalidated on the first page, and a revoked session triggers a login, never empty data.
3. The recipe declares session recovery: refresh, then login, under the same attempt budget as the rest. As the architecture requires, session import and export remain operations separate from plan export.

## Adaptive HTTP

### The site

A listing of 100 products, served in six ways:

| Variant | What an HTTP client receives | What the browser shows |
| --- | --- | --- |
| `static` | the 20 products of each page, pagination links | the same thing |
| `js-shell` | an empty shell; a script calls `/api/list?page=N` | the 20 products, with the next link added by the script |
| `partial-hydration` | 8 products per page; a script loads the other 12 | the 20 products |
| `stale-html` | the 20 products with a stale price; a script corrects the prices | the up-to-date prices |
| `graphql` | a shell; GraphQL behind a "load more" button | the 100 products after 5 clicks |
| `infinite-scroll` | the first 20; the rest on scroll, by cursor | the 100 products after scrolling |

Each listing declares its total (`data-total="100"`).

### The policies

- `browser-only`: always the browser. The page is stabilized as follows: network idle, then scrolling and clicking a visible "load more", until the number of records stops changing.
- `http-only`: HTTP only.
- `heuristic`: HTTP, then the browser if the HTTP page contains no records. This is the "empty result" rule that the architecture considers insufficient.
- `sampled-contract`: on the first pass over a route, the first page goes through both HTTP and the browser. HTTP is retained only if it gives the same records, prices included, and the same links. At the end of the route, the declared total is checked: if it is not reached, the route is relearned in the browser and redone.
- `api-capture`: like `sampled-contract`. When the browser is required, the sample's JSON traffic is captured and a replay plan is inferred from it:
  - **per page**: a request field equals a parameter of the page URL;
  - **by chain**: a field of the next call is a value from the previous response, like a cursor.

  The plan is retained only if it reproduces the browser's result exactly on the sample. The HTML and the API objects are merged by identifier, and the API wins on prices.

What a route learns is reused in subsequent runs of the same job. The declared total serves as an invalidation event.

### Reading

- **The empty-result rule is not enough, as the architecture says.** `heuristic` handles the shell and GraphQL, because the HTTP page is empty there. It fails on the three cases where the HTTP page is not empty but wrong:
  - partial hydration: 40 products instead of 100;
  - stale prices corrected by script: 100 wrong prices;
  - infinite scroll: 20 products instead of 100.

  Each time, it declares a success.
- **The compared sample is never wrong.** `sampled-contract` is exact on all 120 runs. It keeps HTTP only on the static listing, where it costs a single browser page for the whole job.
- **API discovery changes the order of magnitude.** `api-capture` is exact on all 120 runs and infers a replay plan on the five scripted renderings:
  - per page: `/api/list`, `/api/prices`;
  - by chain: GraphQL cursor `pageInfo.endCursor`, the feed's `nextCursor` cursor.

  Once the route is learned, a run takes 10 to 20 ms instead of 0.8 to 1.3 s in the browser, with no browser page at all.
- The stale prices show why the sample compares fields and not just the number of records. The HTML has the 20 expected products; only their prices are wrong.

### What this says for the architecture

1. `auto` routing is **per-route learning validated on a sample**, not a heuristic on the page. The comparison covers identities, fields and links. The declared total or another completeness oracle invalidates what has been learned.
2. **API discovery becomes a full-fledged routing tier**, between HTTP and browser: capture of JSON traffic during the sample, inference of a per-page or cursor plan, validation against the browser before use. For a recurring job, it is the cheapest tier that remains exact.
3. A learned API plan has the same scope and the same invalidation events as an HTTP decision: it is tied to the route and redone if the end-of-route contract fails.

## Frontier

### The site

- `crawler-trap`: 60 products behind 3 categories and 6 events in a calendar. The site sets several traps:
  - each link carries a fresh `sid`, and some a `utm_source`;
  - each category offers 4 sort orders of the same list;
  - the calendar has endless "previous month" and "next month" links, whereas only three months have events.
- `large-table`: 1,500 rows, most recent first, paginated by 50. A numbered `<a class="next">` link serves offset pagination, and a `<link rel="next">` serves cursor pagination. Every three pages served, the site deletes two already-traversed rows and inserts one at the top. The oracle requires, once each, the rows present throughout the crawl.

### The policies

- `naive`: the deduplication key is the exact URL, all `<a>` links are followed, with a budget of 300 requests.
- `canonical`:
  - the parameters declared by the recipe (`sid`, `utm_*`) are removed and the keys sorted;
  - two pages of the same path that have the same records and the same links make their differing parameters "no-effect" for that path;
  - a path where three consecutive pages bring neither records nor links outside itself is closed;
  - a page that declares `rel=next` is followed through that link rather than through the page numbers of the same listing.

### Results

Over 15 runs per cell:

| Variant | Policy | Runs with exact data | False successes | Requests per run | End |
| --- | --- | --- | --- | --- | --- |
| `crawler-trap` | naive | 0/15 | 0 | 300 | budget exhausted, 2,140 URLs still queued, 2 events missed |
| `crawler-trap` | canonical | 15/15 | 0 | 75 | frontier empty |
| `large-table` | naive | 0/15 | **15** | 30 | frontier empty, 8 to 9 rows lost |
| `large-table` | canonical | 15/15 | 0 | 30 | frontier empty |

### Reading

- **In the trap, the naive crawler does not know it has finished.** It exhausts its budget without missing any product, but it is missing the events of the third month. It says so honestly: budget exhausted, result not declared complete. The canonical crawler finishes in 75 requests and learns three facts along the way:
  - `sort` and `order` change nothing in the categories;
  - the calendar is a trap;
  - the rest is covered without losing anything.
- **Offset pagination over a live table loses rows without noticing.** Each deletion before the current offset shifts rows that the crawler will never see. It finishes, frontier empty, and declares a complete result: 15 false successes out of 15. With the cursor, the same table is exact, for the same number of requests.

### What this says for the architecture

1. Canonicalization declared by the recipe is not enough on its own. The frontier must also **learn no-effect parameters** by page signature, and **close trapped paths** based on a yield criterion. These learned facts are scoped to the domain and the path.
2. **Cursor pagination is the rule when the site offers it.** Offset pagination is only safe on a frozen collection, and a frontier cannot verify this on its own: it needs a completeness oracle, such as a declared total or a compared recrawl.
3. The end of a crawl is a result in its own right: frontier exhaustion, or budget reached. A crawl stopped by its budget is never a complete result.

## Mechanical verdicts

`pnpm lab verdict`, on the retained runs:

| Decision | Option versus reference | Result |
| --- | --- | --- |
| D-session-model | `contract` versus `relogin-each-run` | **better**: 0.50 logins per resumed run, 5/5 blocks, over HTTP and in the browser; `local-dev` is sufficient, because logins do not depend on the host |
| D-session-model | `status-only` | blocked by the contract (`oracle-exact`) |
| D-adaptive-routing | `heuristic`, `http-only` | blocked by the contract |
| D-adaptive-routing | `sampled-contract` | equivalent on the scripted renderings, where it keeps the browser; on `static`, ratio 0.007, but `insufficient-n` |
| D-adaptive-routing | `api-capture` | ratio of 0.008 to 0.021 depending on the rendering, i.e. 50 to 120 times faster once the route is learned; `insufficient-n` everywhere |
| D-frontier | `naive` versus `canonical` | blocked by the contract |

Why `insufficient-n` despite a gap of two orders of magnitude: the rule computes the number of blocks needed to detect the declared 10% gap from the dispersion of the per-block ratios. It does not take the observed effect into account. With a log-ratio dispersion of about 0.3, it requires 99 to 204 blocks. D-adaptive-routing requires `local-controlled` for its durations in any case. The contract result, on the other hand, is settled: only `sampled-contract` and `api-capture` pass, and `browser-only` remains the most expensive exact reference.

## Limitations

- Synthetic fixtures, designed to reproduce each trap in isolation; a real portal combines them.
- The API plan only covers GET or JSON requests whose pagination is a simple field: no request signing, single-use token or encrypted body.
- The durations come from a `local-dev` host; only the request and login counts are host-independent.
