# Installing the engine bindings: native vs RPC sidecar

> **PROTOTYPE, throwaway.** This was built for wayfinder ticket [#74](https://github.com/Jbmanllr/automan/issues/74), "Prototype: engine binding, native vs RPC", and covers the install slice only. It lives on branch `prototype/engine-binding-install` and is never merged. It records evidence, not a decision.

## Question

What does installing each binding strategy feel like on a clean machine?

- **(A) In-process native:**
  - Node: a napi-rs `.node` addon, shipped as npm per-platform packages through `optionalDependencies` (the esbuild, Biome and Rspack layout).
  - Python: a PyO3 extension wheel built with maturin, using abi3 where possible.
- **(B) RPC sidecar:**
  - One Rust binary, `engined`.
  - Node: the binary is shipped in npm per-platform packages (esbuild style).
  - Python: the binary is shipped in `py3-none-<platform>` wheels (ruff/uv style).
  - Thin pure-JS and pure-Python SDKs spawn the binary and talk to it over stdio JSON-RPC.

For each cell, the matrix records:
- whether the install succeeded
- whether first use succeeded
- the exact error a user sees
- wall time, bytes downloaded and bytes on disk
- how many artifacts the release must publish
- whether first use needed anything extra: exec bit, PATH, quarantine or signing

Prior research: [`rnd/research/2026-10-10-sdk-binding.md`](https://github.com/Jbmanllr/automan/blob/research/sdk-binding/rnd/research/2026-10-10-sdk-binding.md) on `origin/research/sdk-binding`. It reported that PyO3 adds a Python-ABI axis; pydantic-core, for example, ships 136 wheels.

## Method

**Artifacts.** Every artifact is a hello-world: install friction does not depend on engine logic. Sources are in `src/` and `sdk/`.

| Artifact | What it is |
|---|---|
| `src/native-node` | napi-rs 3 addon exposing `hello()` |
| `sdk/native-js` | The JS loader, generated by `@napi-rs/cli` 3.10.8 (`napi build --platform`). It is the stock napi-rs loader, with its stock error message. |
| `src/native-py` | PyO3 0.29 module exposing `hello()`, with a `--features abi3` switch (`abi3-py39`) |
| `src/engined` | Dependency-free Rust binary that answers newline-delimited JSON-RPC on stdio. With maturin `bindings = "bin"` it also becomes the `automan-rpc` wheel: the binary goes in `.data/scripts`, plus the pure-Python `automan_rpc` package. The SDK finds the binary the way ruff's `find_ruff_bin` does. |
| `sdk/rpc-js` | Thin JS SDK. It resolves `@automan-proto/engined-<platform>/bin/engined` and pings it. |

**Builds.**
- **Linux:** built inside Docker in `docker/builder.Dockerfile` (Rust 1.93, maturin 1.15, cargo-zigbuild, zig).
  - **glibc targets** link against glibc 2.17 (manylinux2014), as real napi-rs and maturin pipelines do.
  - **musl:** the napi addon uses `-crt-static` (it is a dynamic `.so` against musl), while `engined` is fully static.
  - **x86_64** is cross-compiled. Building it needed no emulation; only running it does.
- **macOS arm64:** built on the host (`scripts/build-macos.sh`).

**What was built:**

| Strategy | Artifacts | Platforms |
|---|---|---|
| (A) | `.node` addons | linux arm64/x64 × gnu/musl, darwin-arm64 |
| (A) | PyO3 wheels, each as `cp39-abi3`, `cp313-cp313` and `cp314-cp314t`, plus an sdist | linux arm64/x64 × manylinux2014/musllinux_1_2, macosx_11_0_arm64 |
| (B) | `engined` binaries | the same 5 platforms |
| (B) | `py3-none` wheels, plus an sdist | per libc |
| (B) | Retagged copies of the static-musl wheel, `manylinux_2_17 + manylinux2014 + musllinux_1_2`, one per arch | uv's trick |

**Registries.**
- **npm:** a local [verdaccio 6](https://verdaccio.org/) registry (`docker/verdaccio.yaml`). It holds these packages:

  | Package | Versions | Contents |
  |---|---|---|
  | `@automan-proto/native` | 0.1.0 | |
  | `@automan-proto/native-<plat>` | 0.1.0 | |
  | `@automan-proto/engined-<plat>` | 0.1.0, 0.1.1 | 0.1.1 adds `preferUnplugged` |
  | `@automan-proto/rpc` | 0.1.0, 0.1.1 (`latest`) | |
  | `@automan-proto/rpc` | 0.2.0 (dist-tag `static`) | Depends on `@automan-proto/engined-linux-<arch>`: one static-musl binary per arch, with no `libc` field |

- **Python:** a PEP 503 simple index served over HTTP (`scripts/make-pyindex.py`), with three variants:

  | Variant | Native package | RPC package |
  |---|---|---|
  | `full` | Every wheel + sdist | Every wheel + sdist |
  | `abi3sdist` | abi3 wheels + sdist only | Dual-tagged static wheels + sdist |
  | `abi3` | abi3 wheels only, no sdist | Dual-tagged static wheels, no sdist |

  PyPI is an extra index, so an sdist fallback can fetch its build backend the way a real user's would. Neither project name exists on PyPI.

**Install cells.**
- Every cell is a fresh `docker run --rm` of a stock image plus the package manager under test (`docker/node-tools.Dockerfile`, `docker/py-tools.Dockerfile`).
- **No Rust toolchain or C compiler** is in any cell image.
- **Tool versions:** Node 24.21.0 / npm 11.19.0, Node 20.20.2 / npm 10.8.2, pnpm 12.12.0, Yarn 4.18.1, Bun 1.4.3, Python 3.13 / 3.9 (pip 23.0.1) / 3.14.3t (uv-installed), uv 0.9, Poetry 2.5.1.
- **Measurement:**
  - Time and bytes cover only the install command.
  - `rx_bytes` is the container's `eth0` receive counter.
  - "On disk" is `du` of the project dir (npm) or of the installed package plus `bin/engined` (Python).
  - First use loads the module and calls it (native), or spawns the binary and pings it (RPC). Python first use runs with the venv **not** activated and PATH untouched.
- **macOS lockfiles and caches:** the host produced them (`scripts/macos.sh fixtures`); the Linux cells then consumed them.
- **Host checks:** `scripts/macos.sh cells` installs into fresh temp dirs and venvs on the macOS host. It records `xattr com.apple.quarantine`, `codesign -dv` and `spctl --assess`.

**Platforms.** The host is an Apple Silicon Mac, so all Linux cells are **linux/arm64**. linux/amd64 got only 4 cells under QEMU (`./run.sh amd64`); host load was very high, with a load average of 400–900, so emulation was kept to a minimum. Their timings are not comparable.

**Rerun.**
```sh
./run.sh                      # images build registry fixtures node python amd64 macos report
./run.sh node --only 'node24-alpine:*'   # one slice; any phase + a cell-name glob
./run.sh report               # matrix (Markdown) + logs/ from out/results
./run.sh down                 # stop verdaccio + the Python index
```
- Raw per-cell logs and `kv` results are in [`logs/cells/`](logs/cells/), with long logs trimmed to 120 lines.
- [`logs/matrix.json`](logs/matrix.json) holds the matrix as data. Build logs and artifact sizes are next to it.

**First use needed nothing extra in any passing cell:**
- **Exec bit:** every RPC cell found `engined` with mode `755` (49 of 49). That covers npm, pnpm, Yarn (including PnP), Bun, pip, uv and Poetry.
- **PATH:** not needed. The SDKs resolve the binary themselves, and Python ran with the venv not activated.
- **Yarn PnP:** it unplugged the binary package to `.yarn/unplugged/…` even for `rpc@0.1.0`, which has no `preferUnplugged`. Both strategies need `yarn node` under PnP.
- **macOS:** no `com.apple.quarantine` xattr after npm, pip or uv. Both the `.node`/`.so` and `engined` are `Signature=adhoc` with `flags=0x20002(adhoc,linker-signed)`. `spctl --assess` says `rejected` for all of them (no Developer ID), but nothing consulted Gatekeeper, because nothing was quarantined: the files loaded and spawned normally.
- **Bytes and disk:** per platform these are equal for the hello-world artifacts. A tarball or wheel is about 0.19–0.21 MB and an install about 0.4–0.46 MB, so neither strategy differed for users.

## Release matrix for V1

V1 targets: macOS arm64/x64, Linux x64/arm64 × glibc/musl, Windows x64/arm64. That is **8 platforms**.

Counts follow the layout the prototype actually published. The Python floor is any abi3 version.

| Per release | (A) native | (B) RPC, per-libc binaries | (B) RPC, one static-musl Linux binary per arch |
|---|---|---|---|
| Separately linked engine artifacts | 8 napi `.node` + 8 abi3 + 8 `cp314t` = **24**. Add 8 `abi3.abi3t` for 3.15t+ = **32**. Add 8 per PyPy/GraalPy if supported. | **8** | **6** |
| npm packages | 8 platform + 1 loader = **9** | 8 platform + 1 SDK = **9** | 6 + 1 = **7** |
| PyPI files | 8 abi3 + 8 `cp314t` (+ 8 `abi3t`) + 1 sdist = **17 (25)** | 8 `py3-none` wheels (+ sdist) = **8–9** | 6 dual-tagged/mac/win wheels (+ sdist) = **6–7** |
| Total files published | **26 (34)** | **17–18** | **13–14** |
| CLI / MCP server binary | Not covered: needs another 8 binaries, so **34 (42)** in total | Same artifacts as the SDKs | Same artifacts |
| Python ABI axis | Yes: abi3, free-threaded `cp3xxt` until abi3t is the floor, PyPy `pp3xx` | None: one wheel serves 3.9, 3.13, 3.14t and PyPy (measured on 3.9 / 3.13 / 3.14t) | None |
| Smoke-test matrix | Each artifact × each runtime ABI it claims: Node-API once per platform plus Bun; Python per ABI tag per platform | The binary once per platform; the pure SDKs on any one platform per runtime version | Same |

**Notes on the counts**
- **What fails without the extra wheels:**
  - **No `cp314t` wheels:** a free-threaded 3.14 user gets uv's "No solution found" error, or pip's sdist fallback. Both are measured below.
  - **No sdist:** an unsupported platform gets "no matching distribution" instead of a Rust build attempt.
- **PEP 803 `abi3t`:** it is Final and targets 3.15 ([PEP 803](https://peps.python.org/pep-0803/)), and PyO3 0.29 already has the `abi3t-py315` feature. It does **not** cover 3.14t. The `cp314t` axis therefore stays until 3.14 leaves the support window, around October 2030.
- **Static musl (RPC only):** one static-musl Linux binary per arch served glibc and musl in every cell that tried it:
  - npm (`node24-slim`, `node24-alpine`) and Bun (`bun1-alpine`), through `@automan-proto/rpc@0.2.0`;
  - pip and uv, through the dual-tagged wheel (`py313-slim`, `py313-alpine`, `py314t`).

  This is what esbuild does on npm (no `libc` field) and what uv does on PyPI for aarch64, with `manylinux_2_17_aarch64.manylinux2014_aarch64.musllinux_1_1_aarch64` ([uv files](https://pypi.org/pypi/uv/json)). Ruff does not ([ruff files](https://pypi.org/pypi/ruff/json)).
  - **A native addon cannot do this:** a `.node` or `.so` is `dlopen`ed into the host's libc.
  - **Trade-offs for an engine:** musl's allocator is slow under heavy threading, so the engine would bundle mimalloc or jemalloc. The resolver also differs: no NSS, so no `/etc/nsswitch.conf` sources such as LDAP or mDNS.

**CI build cost**
- **Hello-world build times (measured), on a host under extreme load (load average 400–900), with a warm cargo registry:**

  | Target | napi `.node` | 3 PyO3 wheels | `engined` + its wheel |
  |---|---|---|---|
  | Each Linux target, via zig | 15–89 s | 28–125 s | 1–68 s |
  | macOS arm64 | 22 s | ~240 s (incl. the rpc wheel) | 1 s |

  These numbers only show that **each extra artifact is another compile/link step**. They do not show engine-sized build times: `engined` has no dependencies, while napi and pyo3 bring proc-macro crates.
- **Real-engine shape:**
  - **Native:** the engine crates compile once per target per job. Each binding variant then recompiles the binding crate (pyo3 cfgs differ between abi3, cp314t and abi3t) and re-links the whole engine. Per target that is 1 engine compile + 3–4 links. Shipping the CLI separately adds 1 more.
  - **RPC:** per target, 1 engine compile + 1 link, reused by npm, PyPI, the CLI and MCP.
- **Runner prices** (private repos; standard runners are free for public repos, [GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)):
  - Linux x64: $0.006/min
  - Linux arm64: $0.005/min
  - Windows: $0.010/min
  - macOS: $0.062/min, about 10× Linux
- **Where builds can run:**
  - Linux targets cross-compile from one Linux runner with zig, as done here: the x86_64 artifacts were built on arm64 without emulation.
  - The 2 macOS targets need macOS runners in both strategies. Native needs 3–4 artifacts there per target, RPC needs 1.
  - Windows: napi-rs supports `cargo-xwin` cross-builds from Linux (`napi build -x`). For PyO3, maturin documents cross-compiling Windows wheels with `cargo-xwin`.

## Windows (not run: documented from sources, unverified by this prototype)

Gathered from primary sources on 2026-10-10. Nothing in this section was executed.

**Both strategies**
- **Artifacts:** Windows adds two targets, `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`.
  - npm: esbuild ships [`@esbuild/win32-arm64`](https://registry.npmjs.org/esbuild/latest) and Biome ships [`@biomejs/cli-win32-arm64`](https://registry.npmjs.org/@biomejs/biome/latest).
  - PyPI: uv 0.13.0 and ruff 0.17.0 ship `win_arm64` wheels ([uv](https://pypi.org/pypi/uv/json), [ruff](https://pypi.org/pypi/ruff/json)).
  - python.org ships an official ARM64 installer for 3.15.0 ([installer](https://www.python.org/ftp/python/3.15.0/python-3.15.0-arm64.exe)).
- **VC++ runtime:** build with `+crt-static` on every `windows-msvc` target, as uv does ([uv `.cargo/config.toml`](https://github.com/astral-sh/uv/blob/main/.cargo/config.toml)).
  - The napi-rs package template sets it only for `x86_64-pc-windows-msvc` ([template](https://github.com/napi-rs/package-template/blob/main/.cargo/config.toml)), and the CLI adds nothing for MSVC ([build.ts](https://github.com/napi-rs/napi-rs/blob/main/cli/src/api/build.ts)). An arm64 addon built from the template would therefore need `vcruntime140.dll`.
  - Ruff hit this with its exe ([ruff#11503](https://github.com/astral-sh/ruff/issues/11503)).
  - `node.exe` is `/MT` ([common.gypi](https://github.com/nodejs/node/blob/main/common.gypi)), so Node does not bring the runtime along. CPython's Windows installer does bundle `vcruntime140.dll` ([cpython#18918](https://github.com/python/cpython/pull/18918)).
- **Smart App Control (Windows 11) is the larger risk than SmartScreen.**
  - In enforcement mode, "unknown, unsigned code [is] blocked by default" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)). This does not depend on Mark-of-the-Web.
  - One user reports it blocking an unsigned exe that uv launched ([uv#10336](https://github.com/astral-sh/uv/issues/10336)). It likely applies equally to an unsigned `.node` or `.pyd` DLL (inference).
  - **Signing practice:** uv signs its Windows and macOS binaries as of [0.12.12](https://github.com/astral-sh/uv/releases/tag/0.12.12). esbuild declined to sign ([esbuild#1561](https://github.com/evanw/esbuild/issues/1561)) and has seen Defender false positives ([#579](https://github.com/evanw/esbuild/issues/579)). Biome's winget copy was blocked by Defender ([biome#10505](https://github.com/biomejs/biome/issues/10505)).
  - **Implication:** Authenticode signing is a release cost for *either* strategy on Windows.
- **Mark-of-the-Web:** it is written by the downloading app, normally through `IAttachmentExecute`. curl does not write it ([Eric Lawrence](https://textslashplain.com/2022/12/02/mark-of-the-web-additional-guidance)). Whether npm or pip write it is unconfirmed; they are expected not to.
- **Defender scanning:** Microsoft recommends putting package caches on a Dev Drive in Defender "performance mode" ([Dev Drive](https://learn.microsoft.com/en-us/windows/dev-drive/)). No measured first-spawn delay was found.
- **File locking on upgrade:** a loaded `.node`/`.pyd` (native) or a running `engined.exe` (RPC) cannot be replaced while it is in use. Reported for a running exe in [uv#11930](https://github.com/astral-sh/uv/issues/11930) and [uv#14520](https://github.com/astral-sh/uv/issues/14520), and generically for pip in [pip#7865](https://github.com/pypa/pip/issues/7865).
  - **Native:** the lock is held by the user's own Node or Python process.
  - **RPC:** a daemon that outlives the SDK process keeps holding it. Upgrades then need "stop the daemon first" logic, which per-call child processes avoid.

**(A) Native only**
- **napi-rs:** no `node.lib` at link time; napi-sys resolves Node-API symbols from the host process at runtime ([napi-sys](https://github.com/napi-rs/napi-rs/blob/main/crates/sys/src/lib.rs)). Packages are named like `@rspack/binding-win32-arm64-msvc` ([npm](https://registry.npmjs.org/@rspack/binding-win32-arm64-msvc/latest)).
- **PyO3:** wheels are tagged `win_amd64` and `win_arm64`. The abi3 build links correctly through `raw-dylib`, so no import library is needed ([PyO3 guide](https://pyo3.rs/main/building-and-distribution.html)).
  - The same ABI axis applies on Windows. cryptography 50.0.2 ships `cp39-abi3`, `cp311-abi3`, `cp314-cp314t`, `cp315-abi3.abi3t` and `pp311` for `win_amd64`, and **no `win_arm64`** ([PyPI](https://pypi.org/pypi/cryptography/json)).
  - PyPy on Windows is x64 only ([pypy.org](https://pypy.org/download.html)).

**(B) RPC only**
- **Naming:** the npm platform package contains `engined.exe`, as `@esbuild/win32-x64` contains `esbuild.exe` ([unpkg](https://unpkg.com/@esbuild/win32-x64@0.28.2/?meta)). The SDK must append `.exe`; [esbuild does](https://github.com/evanw/esbuild/blob/main/lib/npm/node-platform.ts), and so does this prototype's SDK.
  - **PyPI:** `.data/scripts/engined.exe` is copied verbatim into `Scripts\`, with no launcher wrapper generated ([PEP 427](https://peps.python.org/pep-0427/)). Ruff's shim finds it the same way ([`_find_ruff.py`](https://github.com/astral-sh/ruff/blob/main/python/ruff/_find_ruff.py)).
- **Transport:** stdio works everywhere and is what esbuild ([node.ts](https://github.com/evanw/esbuild/blob/main/lib/npm/node.ts), `windowsHide: true`) and Playwright ([`_transport.py`](https://github.com/microsoft/playwright-python/blob/main/playwright/_impl/_transport.py)) use.
  - **A long-lived daemon reached by several SDK processes needs a socket.** On Windows:
    - **Node:** speaks named pipes, `\\.\pipe\…` ([Node net](https://nodejs.org/api/net.html)).
    - **AF_UNIX:** exists since Windows 10 1803, stream sockets only ([MS blog](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)).
    - **Python asyncio:** has **no AF_UNIX on Windows**; the Proactor loop takes only overlapped pipe handles ([asyncio-platforms](https://docs.python.org/3/library/asyncio-platforms.html), open issue [cpython#77589](https://github.com/python/cpython/issues/77589)).
  - **agent-browser:** uses a Unix socket elsewhere but **TCP on 127.0.0.1 on Windows**, with an ephemeral-port fallback for Hyper-V excluded port ranges ([daemon.rs](https://github.com/vercel-labs/agent-browser/blob/main/cli/src/native/daemon.rs)).
  - **Firewall:** binding 127.0.0.1 does not trigger a Windows Firewall prompt; binding 0.0.0.0 does. This is common knowledge; no Microsoft page was found.
- **Process lifecycle:**
  - **Node:** maps SIGTERM to forced termination on Windows ([child_process](https://nodejs.org/api/child_process.html)).
  - **Python asyncio:** has no `add_signal_handler` on Windows.
  - **Playwright:** kills trees with `taskkill /T /F` ([processLauncher.ts](https://github.com/microsoft/playwright/blob/main/packages/utils/processLauncher.ts)).
  - **Job objects:** a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` kills the children when the last handle closes ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)).
  - This is extra SDK code that the native strategy does not need for the engine itself. Chromium child processes need it in both strategies.

## Caveats

- **Hello-world artifacts.** Sizes are 0.35–0.42 MB per binary and about 0.2 MB per tarball or wheel, so bytes and times here measure package-manager overhead, not engine size.
  - Prior research gives real-world sizes: Rspack binding 39–70 MB, agent-browser 15.6–18.3 MB per binary, browser-use-core wheels 22–27 MB.
  - A real engine scales each strategy's per-artifact size about equally. The native strategy additionally multiplies it by the Python ABI variants *on the publisher side*; users still download one artifact.
- **Wall times are noisy.** The host was saturated (load average 400–900, other agents' containers running). Sub-second differences mean nothing. Only the outliers are meaningful:
  - the sdist fallback: 55 s and 146 MB before failing;
  - pnpm's update check;
  - uv's double download from a non-PEP 658 index.
- **linux/arm64 only.** Apart from 4 QEMU amd64 cells, everything ran on arm64. x86_64 artifacts were built and published but not run beyond those cells.
- **Local registries differ from npmjs and PyPI:**
  - **verdaccio:** we published every package seconds apart. Real releases can publish platform packages minutes apart, which widens the "main package visible, platform package not yet visible" window.
  - **Python index:** a static PEP 503 index without PEP 658 metadata. That is why uv downloads each wheel twice and why the rx bytes for uv are about 2×.
- **Lockfile URLs.** `bun.lock` stores full tarball URLs, so bun cells rewrite `localhost:4873` to the in-network registry name. npm cells use `--replace-registry-host=always` for the same purpose. On npmjs.org neither step is needed.
- **Release-age gates.** Yarn 4.18 (`npmMinimalAgeGate`, default 1440 min) and pnpm 12 (`minimumReleaseAge`) both refuse versions younger than 24 h by default. Our cells disable Yarn's gate except in the two `agegate-default` cells.
  - `pnpm add` auto-adds the fresh versions to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml`; it writes 6 entries per dependency, one for each platform package.
  - A frozen install from a lockfile *without* that file fails (cells `*:pnpm:maclock-agegate-default`).
  - This hits both strategies identically, but it matters for hotfix releases.
- **The npm "classic bug" sequence** is: lockfile deleted, `node_modules` kept, `npm install` again on macOS. It reproduced with **npm 10.8.2**, the npm that ships with Node 20 and 22. With npm 11.x it did not reproduce; the fix is [npm/cli#8184](https://github.com/npm/cli/pull/8184), in npm 11.3.0.
- **Windows was not run** (see the Windows section).
- **Not measured:** macOS x64; Windows; PyPy; Python 3.15 and `abi3t`; Deno; corporate proxies; antivirus on Linux.
- **macOS quarantine was observed, not provoked.** The check shows npm, pip and uv install files without `com.apple.quarantine`. It does not show what Gatekeeper does to a quarantined, ad-hoc-signed binary; for example, a binary fetched by a browser-based download or an Electron auto-updater. That case would need Developer ID signing and notarization in either strategy.

## What this suggests for the binding decision

This section states evidence, not a decision.

**1. On npm, both strategies install the same way, so they fail the same way.**
- Both use `optionalDependencies` with `os`/`cpu`/`libc`. Every npm, pnpm, Yarn and Bun failure cell failed for both, and so did every passing cell pass for both.
- The dangerous failures are **silent**: the install exits 0 and the error appears only at first use. That happened in 22 cells: `--omit=optional`, the npm 10 regenerated lockfile, a macOS-primed offline cache, and a vendored main tarball.
- An RPC sidecar does not by itself buy install robustness on npm. Only a different distribution mechanism would, for example:
  - one package carrying every binary plus a `postinstall` selector (agent-browser), which pnpm 10+ blocks by default;
  - a first-run download (Playwright-style).
- What RPC *does* control is the error text. The stock napi-rs message blames npm/cli#4828 even when the user passed `--omit=optional`. A native SDK could also wrap the loader, so this is a smaller difference than it looks.

**2. On PyPI, RPC removes the Python-ABI axis, and that showed up as real failures.**
- **RPC:** one `py3-none` wheel per platform installed and ran on CPython 3.9, 3.13 and free-threaded 3.14t, on glibc and musl, through pip, uv and Poetry.
- **Native:** it needed a separate `cp314t` wheel for free-threaded Python. With an abi3-only release:
  - uv refused outright;
  - pip fell back to the sdist, which **silently pulled a 146 MB Rust toolchain** and still failed.
- `abi3t` (PEP 803) helps only from 3.15.

**3. RPC can collapse glibc and musl into one static binary per Linux arch; native cannot.**
- Measured working on npm (no `libc` field) and on PyPI (a dual-tagged wheel, as uv does).
- It also removes the 2× download seen with Bun (no `libc` filtering) and with npm-10 lockfiles (no `libc` recorded) for the RPC package.
- Release files: 13–14 for RPC with static musl, against 26–34 for native. Native also needs a separate CLI/MCP binary on top (34–42).

**4. Some friction is common to both strategies, and the binding choice does not change it:**
- **Release-age gates:** Yarn 4.18 and pnpm 12 refuse any release younger than 24 h by default.
- **Old pip:** pip that predates `manylinux2014` / `musllinux` cannot install either strategy.
- **Signing:** on macOS, both installed with ad-hoc signatures and no quarantine. Windows Smart App Control and Defender treat unsigned DLLs and EXEs alike (documented, not run), so Authenticode signing is a cost of either strategy.

**5. Evidence that argues against, or complicates, the current direction** (Rust engine as a sidecar or daemon binary, thin SDKs over JSON-RPC):
- **No install-time advantage on npm.** The current direction's install story on npm is exactly the napi-rs story, with the same silent failure modes.
- **Static musl is not free for an engine:**
  - musl's malloc under heavy threading means bundling mimalloc or jemalloc;
  - no NSS, so name resolution differs (no LDAP or mDNS);
  - a static binary cannot `dlopen` anything.

  Shipping per-libc binaries avoids these costs but gives back the 8-vs-6 artifact saving and the Bun/npm-10 double download.
- **A daemon adds Windows-only work that in-process bindings avoid** (documented, not run):
  - Python asyncio has no AF_UNIX on Windows, so a shared daemon needs named pipes or loopback TCP, as agent-browser does;
  - child-tree cleanup needs job objects or `taskkill`;
  - a daemon that outlives the SDK keeps `engined.exe` locked during `pip install -U` or `npm update`.

  A per-process stdio child, the esbuild model, avoids the socket and lock problems. That is a design constraint the RPC direction would have to accept or engineer around.
- **Old-pip and age-gate failures are not solved by RPC,** so they are not arguments *for* it.

**Net:**
- **Install friction alone does not decide** between the strategies on npm.
- **On PyPI and in release-matrix size**, the measured evidence favours a single binary in `py3-none` wheels: no ABI axis, free-threaded Python works out of the box, and 8 or 6 engine links per release instead of 24–32.
- **The costs the RPC direction carries are runtime and Windows-lifecycle costs**, which this install slice did not measure.
