# Frameworks et agents navigateur — enquête au 7 octobre 2026

> **Mise à jour du périmètre :** l'utilisateur a retiré la contrainte de petite équipe et de sortie en 3–6 mois après la première rédaction. Les conseils TypeScript/calendrier ci-dessous documentent cette hypothèse initiale. La recommandation actuelle, moteur Rust canonique et validation par capacités, figure dans [la synthèse mise à jour](2026-10-07-direction-automan.md). Les faits techniques et leurs réserves restent applicables.

Cette note couvre les frameworks navigateur, leurs primitives, le passage de l’agent au code réutilisable et la frontière entre bibliothèques publiques et services payants. Elle complète les autres volets crawling/infrastructure. Contexte produit : petite équipe, première version en 3–6 mois. Aucune performance n’a été reproduite ici.

**Méthode :** Exa, 12 requêtes en quatre passes, `sources_reviewed = 110` selon la convention Exa (somme des `numResults` demandés). Ce nombre inclut doublons et résultats écartés : ce n’est pas 110 sources indépendantes validées. Les conclusions reposent sur les documents primaires cités, les API publiques GitHub/npm/PyPI et des lectures ciblées du code. Quinze fichiers LICENSE ont été réellement ouverts. Les dates de poussée GitHub mesurent l’activité d’un dépôt, pas la qualité de son produit. L’API GitHub anonyme a atteint sa limite pendant la recherche ; les lectures suivantes ont utilisé `gh api` et `raw.githubusercontent.com`.

## Conclusions utiles à Automan

1. **« Un Stagehand plus rapide en Rust » est une position insuffisante.** Stagehand déplace déjà le runtime dans une extension Chrome ; Browser Use possède désormais un cœur Rust ; Kernel exécute du Playwright à côté du navigateur. La latence vient beaucoup de l’emplacement du code, du nombre de commandes et de l’inférence, pas seulement du langage. [Stagehand architecture](https://github.com/browserbase/stagehand/blob/main/CONTRIBUTING.md), [Browser Use 0.13](https://github.com/browser-use/browser-use/releases/tag/0.13.0), [Kernel execution](https://www.kernel.sh/docs/browsers/playwright-execution).
2. **Apprendre une fois, rejouer sans LLM, puis réparer existe déjà.** Skyvern cache des scripts par bloc et par branche ; Workflow Use génère des workflows ; Lightfeed sauvegarde des plans ; Imprint compile les requêtes réseau et les interactions DOM. Le replay vérifié constitue un terrain concurrentiel, pas une invention à revendiquer. [Skyvern cache](https://www.skyvern.com/docs/developers/features/code-caching), [Workflow Use](https://github.com/browser-use/workflow-use), [Lightfeed](https://github.com/lightfeed/browser-agent), [Imprint architecture](https://github.com/ashaychangwani/imprint/blob/main/docs/architecture.md).
3. **La meilleure promesse mesurable est un coût par résultat correct sur un périmètre concret.** Une exécution rapide peut retourner une ancienne sortie, cliquer le mauvais contrôle ou ne pas prouver que l’objectif est atteint. Lightfeed documente explicitement que sa sortie programmatique enregistrée reste figée ; Browser Use V4 demande fraîcheur et validation dans le prompt de rerun. Ce sont des distinctions produit indispensables. [Lightfeed replay](https://github.com/lightfeed/browser-agent/blob/main/src/agent/replay.ts), [Browser Use scripts](https://docs.browser-use.com/cloud/agent/scripts).
4. **Pour 3–6 mois, construire la couche de contrats, exécution, preuves et maintenance autour d’un pilote éprouvé.** TypeScript/Playwright constitue une hypothèse raisonnable de départ, avec connexions CDP locales/distantes et adaptateurs facultatifs Stagehand. Mesurer ensuite avant d’introduire un cœur Rust. Cette recommandation est une inférence de calendrier et de risque, pas un benchmark comparatif de langages.

## Stagehand et Browserbase : ce qui est vraiment actuel

### Version et architecture

Le registre npm donne `latest = 4.1.0`, publié le **9 septembre 2026**, `v3-latest = 3.7.3`, et une branche alpha 4.2. Le SDK Python `stagehand` est aussi en 4.1.0. Attention : l’endpoint GitHub `releases/latest` renvoie encore 3.7.3 ; une recherche limitée aux Releases ferait donc conclure à tort que v3 est actuel. [npm 4.1.0](https://www.npmjs.com/package/@browserbasehq/stagehand/v/4.1.0), [PyPI](https://pypi.org/project/stagehand/4.1.0/), [package TS](https://github.com/browserbase/stagehand/blob/main/packages/sdk-ts/package.json).

Le runtime des opérations réside dans une **extension Chrome** ; les SDK vivent dans le processus consommateur et communiquent en **JSON-RPC bidirectionnel transporté sur CDP**. Le contrat provient de Zod, devient JSON Schema, puis génère les modèles Python et Go. La version du protocole et les versions des SDK sont distinctes. L’extension est embarquée dans chaque SDK. [CONTRIBUTING](https://github.com/browserbase/stagehand/blob/main/CONTRIBUTING.md), [protocole](https://github.com/browserbase/stagehand/blob/main/packages/protocol/README.md).

La couche Chromium propre au projet, `understudy`, pilote le navigateur sans dépendance runtime Playwright/Puppeteer. Le runtime TypeScript utilise Vercel AI SDK, différents fournisseurs de modèles et OpenTelemetry. Le SDK expose des opérations déterministes, une perception structurée et `act`, `observe`, `extract`. Les SDK couvrent TypeScript, Python et Go ; cela ne rend pas leurs processus hôtes identiques. [Dépendances extension](https://github.com/browserbase/stagehand/blob/main/packages/extension/package.json), [introduction v4](https://docs.stagehand.dev/v4/first-steps/introduction).

`agent()` est retiré. Browserbase recommande le **code mode**, où un assistant écrit un script, ou une boucle externe disposant de toute l’API. Le snapshot fournit arbre d’accessibilité et carte XPath ; les actions stables peuvent être exécutées directement. La documentation précise de faire l’escalade sur `observe()`, car une erreur d’`act()` peut survenir après un effet déjà exécuté. [Migration v3 → v4](https://docs.stagehand.dev/v4/migrations/v3).

**Point de performance déjà présent dans la version stable :** `experimentalBatch()` exécute un callback JavaScript autoportant dans le service worker et évite un aller-retour SDK–navigateur par opération. La présence de cette API a été vérifiée dans `dist/index.d.mts` du tarball npm **4.1.0**, pas seulement sur `main`. Limites : données JSON, pas de fermeture lexicale, pas d’API filesystem hôte, pas de transaction atomique. [Référence](https://docs.stagehand.dev/v4/reference/stagehand).

### Cache, réparation et ouverture

Stagehand est MIT. Browserbase reste une infrastructure commerciale distincte. Le cache standard v4 est **hébergé chez Browserbase** et requiert navigateur/session Browserbase + clé API ; l’option ne donne pas de cache local équivalent. Les clés incluent instruction, page/options et URL ; le modèle est exclu. Les appels `locator`/`ignoreLocators` contournent le cache. Les changements de contenu peuvent réduire les hits ; un seuil d’observations identiques est configurable. [Licence](https://github.com/browserbase/stagehand/blob/main/LICENSE), [cache](https://docs.stagehand.dev/v4/best-practices/caching), [code cache](https://github.com/browserbase/stagehand/blob/main/packages/extension/services/cacheService.ts).

Le code rejoue les actions mises en cache avec `selfHeal: false`, puis retombe sur l’inférence si l’application échoue. La réparation existe aussi sur l’action déterministe quand activée. **Un sélecteur qui résout encore vers le mauvais élément constitue une autre catégorie d’erreur** : l’absence d’exception ne prouve pas la justesse sémantique. La PR expérimentale de contrôle de cache décrit précisément ce cas. [Code act](https://github.com/browserbase/stagehand/blob/main/packages/extension/services/actService.ts), [PR 2954](https://github.com/browserbase/stagehand/pull/2954).

Stagehand offre pages, opérations concurrentes, lancement/connexion et réparation ; le différencier par « absence de concurrence/retries/navigateurs » serait erroné. Son API standard n’est pas un moteur de file persistante de crawling ni un workflow métier durable complet. Ce constat porte sur le contrat public, pas sur les capacités du cloud Browserbase.

### Jev et modèles de décision : statut et limites

GitHub API a confirmé le **7 octobre 2026** que **2952, 2953, 2954, 2955 et 3103 restent ouvertes et non fusionnées**. Elles sont empilées sur d’autres branches, pas toutes directement sur `main`. Le SDK stable npm 4.1.0 ne comporte pas `experimentalDecisions`.

| Proposition | Mécanisme et état probant |
| --- | --- |
| [2952](https://github.com/browserbase/stagehand/pull/2952) | Client TypeSafe Jev, candidats issus de l’arbre d’accessibilité, contexte pour distinguer doublons, abstention, circuit breaker. Bibliothèque initialement non branchée. |
| [2953](https://github.com/browserbase/stagehand/pull/2953) | Intent → arguments → sélection → action existante → checks déterministes, fallback LLM. p50 annoncé 1,97 s → 0,46 s sur suite act ; **seuils ajustés sur les suites évaluées**, scripts/breadth non publiés dans la pile. Sans LLM, succès moindre : fast path, pas remplacement. |
| [2954](https://github.com/browserbase/stagehand/pull/2954) | Observation et validation sémantique de la cible mise en cache. **Aucun eval de cache end-to-end**, seuil dérivé de probes ; erreurs/timeouts du contrôle n’empêchent pas le replay. |
| [2955](https://github.com/browserbase/stagehand/pull/2955) | Sélection des éléments puis copie déterministe des valeurs, judge de complétude ; schémas complexes/screenshot gardent le LLM. Succès annoncé égal au baseline sur 25 tâches, non reproduit ici. |
| [3103](https://github.com/browserbase/stagehand/pull/3103) | Namespace explicite `experimentalDecisions.act/observe/extract`, trois RPC, option de création TS/Python/Go. Les méthodes ordinaires gardent leur pipeline LLM. |

La piste est intéressante pour réduire l’inférence sur les décisions à ensemble fermé. Elle ne prouve ni performance hors distribution ni fiabilité supérieure universelle. Ne pas figer un fournisseur dans Automan avant essais ; conserver un contrat de décision avec confiance, abstention, métriques et escalade.

## Browser Use : deux générations et trois surfaces

Le dépôt Python MIT est en **0.13.11**, publié le **7 octobre 2026**. L’agent Python historique reste importable via `browser_use.Agent`. Sa `BrowserSession` utilise `cdp-use`, un bus `bubus` et des watchdogs spécialisés : crashes, downloads, DOM, captures, sécurité, storage, CAPTCHA. Le service DOM fusionne snapshot DOM et arbres d’accessibilité, notamment par frame. [Release](https://github.com/browser-use/browser-use/releases/tag/0.13.11), [configuration](https://github.com/browser-use/browser-use/blob/main/pyproject.toml), [session](https://github.com/browser-use/browser-use/blob/main/browser_use/browser/session.py), [DOM](https://github.com/browser-use/browser-use/blob/main/browser_use/dom/service.py).

Depuis **0.13.0, le 8 juin 2026**, `browser_use.beta.Agent` utilise un **runtime Rust natif** distribué en wheels par l’extra `[core]`. Le wrapper Python lance `browser-use-terminal sdk-server --transport stdio`, client JSON-RPC ; le serveur conserve agent/session/browser et les follow-ups. Le dépôt `browser-use/terminal` MIT comporte runtime, protocole, browser, LLM, store SQLite, secrets et worker Python. Tokio, Serde, Reqwest et rusqlite apparaissent effectivement dans Cargo.toml. [Release 0.13.0](https://github.com/browser-use/browser-use/releases/tag/0.13.0), [wrapper](https://github.com/browser-use/browser-use/blob/main/browser_use/beta/service.py), [ledger d’intégration](https://github.com/browser-use/browser-use/blob/main/BETA_AGENT_INTEGRATION_FEATURES.md), [Cargo](https://github.com/browser-use/terminal/blob/main/Cargo.toml).

Le **Browser Harness** séparé permet au coding agent de piloter Chrome au travers d’un daemon et de helpers ; ce n’est pas obligatoirement une boucle autonome embarquée. Le cloud V4 distingue agents hébergés, navigateurs CDP et workspaces persistants. Ne pas confondre numéro d’API cloud V4, version du package Python 0.13 et runtime natif. [Harness](https://github.com/browser-use/browser-harness), [cloud quickstart](https://docs.browser-use.com/).

La création/refinement de **Skills est retirée** : 410 Gone ; les skills existants peuvent encore être exécutés. V4 recommande désormais des scripts enregistrés dans un workspace. Chaque rerun V4 démarre encore un modèle et consomme des tokens ; la réutilisation évite la redécouverte, mais n’est pas une garantie d’exécution zéro LLM. Les pages `.md` anciennes indexées par Exa décrivent encore création de skills : la page actuelle et le contrat récent gouvernent. [Skills actuels](https://docs.browser-use.com/cloud/legacy/skills), [scripts](https://docs.browser-use.com/cloud/agent/scripts).

`workflow-use`, séparé et **AGPL-3.0**, enregistre/génère des workflows sémantiques paramétrés, peut les rejouer sans IA et prévoit fallback/réparation. Le README avertit explicitement de son état très précoce et déconseille la production ; sa roadmap indique encore des lacunes de self-healing. Il a néanmoins reçu une poussée le 2 octobre 2026 : ne pas le classer « abandonné » sur son seul README. [README](https://github.com/browser-use/workflow-use), [licence](https://github.com/browser-use/workflow-use/blob/main/LICENSE).

## Skyvern constitue le benchmark produit prioritaire

Son code caching enregistre une exécution réussie, produit un script, puis exécute `run_with="code"`. Les caches sont **par bloc** ; la couverture des branches augmente au fil des runs. Les conditions/waits/code restent exécutés au runtime. Le moteur peut revenir à l’agent et régénérer. [Documentation cache](https://www.skyvern.com/docs/developers/features/code-caching), [SDK run_workflow](https://skyvern.com/docs/sdk-reference/workflows/run-workflow).

L’OSS contient génération de scripts, versions/déploiements de scripts, épisodes de fallback et calcul de fiabilité des workflows. Ce n’est pas uniquement une annonce marketing. La conditionnelle doit toutefois être prise en charge par le DAG, pas seulement un fichier linéaire lancé à la CLI. [Code generation et progressive caching](https://github.com/Skyvern-AI/skyvern/pull/4603), [outils MCP scripts](https://github.com/Skyvern-AI/skyvern/commit/31d37a5b01cff92dcd49ae5281fbc4d4b82aaa7d), [service fiabilité](https://github.com/Skyvern-AI/skyvern/blob/main/skyvern/services/self_heal_reliability_service.py).

Automan peut donc rivaliser sur **simplicité d’intégration, contrat portable, local-first, coût auditable, qualité sur une verticale et service de maintien**, pas sur la seule existence du replay. L’affirmation doit être testée avec des workflows identiques et des assertions externes.

Prix publics consultés le 7 octobre ; dollars US, tarifs indicatifs du fournisseur, pas devis. Des crédits, minimums et frais de réseau empêchent de comparer seulement les prix affichés.

**Conséquence :** si le temps navigateur ne coûte que quelques fractions de centime sur un run court, une optimisation CPU de quelques millisecondes peut avoir moins de valeur que réduire une inférence, un GB de proxy, un incident ou une fausse sortie. Mesurer coût total / succès vérifié, durée p50/p95, nombre d’appels LLM, reruns ratés, intervention humaine et volume réseau.

## Ce que les benchmarks établissent — et pas davantage

Le `steel-dev/browserbench` ouvert mesure création → connexion Playwright CDP → première navigation `domcontentloaded` → release sur EC2 us-east-1 vers google.com, 5 000 runs/fournisseur, dix warmups, succès après éventuels retries SDK. Ses données donnent **Kernel 794 ms et Steel 894 ms** en moyenne ; elles ne soutiennent donc pas sans qualification le slogan « Steel fastest ». Elles mesurent le cycle minimal remote, pas une extraction correcte, un login, un CAPTCHA ou une charge de workflows. [Méthodologie et résultats](https://github.com/steel-dev/browserbench).

Le protocole Automan doit séparer première compilation, replay chaud, replay froid, changement UI, changement de données, expiration d’auth et panne réseau. Un jeu réel tenu hors calibrage est indispensable ; les suites Jev in-sample montrent exactement pourquoi. Les comparaisons doivent fixer navigateur/région/proxy/modèle, publier les données brutes et compter les fails dans coût/latence.

## Première livraison proposée pour 3–6 mois

**Cible recommandée :** développeurs réalisant des workflows récurrents de lecture/extraction sur quelques portails autorisés, avec assertions de fraîcheur et de schéma. Commencer par des tâches sans effet irréversible facilite les fixtures et les comparaisons. L’intérêt économique reste à tester avec des clients pilotes.

- **Mois 1 :** 10–20 workflows de référence, baselines Playwright/Stagehand/Skyvern ; définition résultat correct, fraîcheur et budget ; runtime TS local/CDP distant.
- **Mois 2–3 :** contrats typés entrées/sorties, steps déterministes, checkpoints, secrets injectés, preuves source par champ ou résultat, JSON de run portable ; création assistée du script et tests de rerun.
- **Mois 4 :** replay, invalidation explicable, réparation limitée au segment cassé, version du plan, comparaison avant/après ; contrôle des effets avant retry.
- **Mois 5–6 :** API/MCP/CLI, offre hébergée et observabilité, scheduling, intégration 2–3 pilotes ; SLA seulement sur périmètre mesuré. Ne pas ajouter marketplace, navigateur fork, SDK trois langages ni moteur crawling complet avant usage établi.

**Portes de décision :** Rust uniquement si le profil montre une part significative du coût/latence end-to-end sous notre contrôle (exemple de seuil interne : gain reproductible ≥20 % sur workloads représentatifs). Cache et plan entièrement utilisables localement ; cloud monétisé par exécution, historique, maintien et support. Les seuils et le packaging sont des propositions, pas des décisions validées.

**Incertitudes restantes :** aucun déploiement des projets, aucun benchmark exécuté, aucun coût de tâche payé, aucun audit complet de sécurité ni compatibilité, limites contractuelles de cache cloud non accessibles, maturité des niches non démontrée. Les statuts/version/date sont des snapshots du 7 octobre 2026. Les mécanismes du code public ne garantissent pas la disponibilité ou le comportement identique du cloud.
