# Browser frameworks and agents — survey as of October 7, 2026

> **Scope update:** the user removed the small-team and 3–6-month release constraint after the first draft. The TypeScript/timeline advice below documents this initial assumption. The current recommendation, a canonical Rust engine and capability-based validation, appears in [the updated synthesis](2026-10-07-direction-automan.md). The technical facts and their caveats remain applicable.

This note covers browser frameworks, their primitives, the shift from agent to reusable code and the boundary between public libraries and paid services. It complements the other crawling/infrastructure strands. Product context: small team, first version in 3–6 months. No performance figure was reproduced here.

**Method:** Exa, 12 queries in four passes, `sources_reviewed = 110` according to the Exa convention (sum of the requested `numResults`). This number includes duplicates and discarded results: it is not 110 validated independent sources. The conclusions rest on the primary documents cited, the public GitHub/npm/PyPI APIs and targeted code readings. Fifteen LICENSE files were actually opened. GitHub push dates measure a repository's activity, not the quality of its product. The anonymous GitHub API hit its limit during the research; subsequent reads used `gh api` and `raw.githubusercontent.com`.

## Conclusions useful to Goodfetch

1. **"A faster Stagehand in Rust" is an insufficient position.** Stagehand already moves the runtime into a Chrome extension; Browser Use now has a Rust core; Kernel runs Playwright next to the browser. Latency comes largely from where the code runs, the number of commands and inference, not only from the language. [Stagehand architecture](https://github.com/browserbase/stagehand/blob/main/CONTRIBUTING.md), [Browser Use 0.13](https://github.com/browser-use/browser-use/releases/tag/0.13.0), [Kernel execution](https://www.kernel.sh/docs/browsers/playwright-execution).
2. **Learn once, replay without an LLM, then repair already exists.** Skyvern caches scripts per block and per branch; Workflow Use generates workflows; Lightfeed saves plans; Imprint compiles network requests and DOM interactions. Verified replay is a competitive field, not an invention to claim. [Skyvern cache](https://www.skyvern.com/docs/developers/features/code-caching), [Workflow Use](https://github.com/browser-use/workflow-use), [Lightfeed](https://github.com/lightfeed/browser-agent), [Imprint architecture](https://github.com/ashaychangwani/imprint/blob/main/docs/architecture.md).
3. **The best measurable promise is a cost per correct result on a concrete scope.** A fast execution can return a stale output, click the wrong control or fail to prove that the goal was reached. Lightfeed explicitly documents that its recorded programmatic output remains frozen; Browser Use V4 asks for freshness and validation in the rerun prompt. These are indispensable product distinctions. [Lightfeed replay](https://github.com/lightfeed/browser-agent/blob/main/src/agent/replay.ts), [Browser Use scripts](https://docs.browser-use.com/cloud/agent/scripts).
4. **For 3–6 months, build the contracts, execution, evidence and maintenance layer around a proven driver.** TypeScript/Playwright is a reasonable starting assumption, with local/remote CDP connections and optional Stagehand adapters. Then measure before introducing a Rust core. This recommendation is an inference from timeline and risk, not a comparative language benchmark.

## Stagehand and Browserbase: what is really current

### Version and architecture

The npm registry gives `latest = 4.1.0`, published on **September 9, 2026**, `v3-latest = 3.7.3`, and a 4.2 alpha branch. The Python SDK `stagehand` is also at 4.1.0. Caution: the GitHub `releases/latest` endpoint still returns 3.7.3; a search limited to Releases would therefore wrongly conclude that v3 is current. [npm 4.1.0](https://www.npmjs.com/package/@browserbasehq/stagehand/v/4.1.0), [PyPI](https://pypi.org/project/stagehand/4.1.0/), [TS package](https://github.com/browserbase/stagehand/blob/main/packages/sdk-ts/package.json).

The operations runtime resides in a **Chrome extension**; the SDKs live in the consuming process and communicate via **bidirectional JSON-RPC transported over CDP**. The contract comes from Zod, becomes JSON Schema, then generates the Python and Go models. The protocol version and the SDK versions are distinct. The extension is embedded in each SDK. [CONTRIBUTING](https://github.com/browserbase/stagehand/blob/main/CONTRIBUTING.md), [protocol](https://github.com/browserbase/stagehand/blob/main/packages/protocol/README.md).

The project's own Chromium layer, `understudy`, drives the browser without a Playwright/Puppeteer runtime dependency. The TypeScript runtime uses Vercel AI SDK, various model providers and OpenTelemetry. The SDK exposes deterministic operations, structured perception and `act`, `observe`, `extract`. The SDKs cover TypeScript, Python and Go; that does not make their host processes identical. [Extension dependencies](https://github.com/browserbase/stagehand/blob/main/packages/extension/package.json), [v4 introduction](https://docs.stagehand.dev/v4/first-steps/introduction).

`agent()` is removed. Browserbase recommends **code mode**, where an assistant writes a script, or an external loop with access to the whole API. The snapshot provides an accessibility tree and an XPath map; stable actions can be executed directly. The documentation specifies escalating via `observe()`, because an `act()` error can occur after an effect has already been executed. [Migration v3 → v4](https://docs.stagehand.dev/v4/migrations/v3).

**Performance point already present in the stable version:** `experimentalBatch()` executes a self-contained JavaScript callback in the service worker and avoids one SDK–browser round trip per operation. The presence of this API was verified in `dist/index.d.mts` of the npm **4.1.0** tarball, not only on `main`. Limits: JSON data, no lexical closure, no host filesystem API, no atomic transaction. [Reference](https://docs.stagehand.dev/v4/reference/stagehand).

### Cache, repair and openness

Stagehand is MIT. Browserbase remains a distinct commercial infrastructure. The standard v4 cache is **hosted at Browserbase** and requires a Browserbase browser/session + API key; the option does not provide an equivalent local cache. Keys include instruction, page/options and URL; the model is excluded. `locator`/`ignoreLocators` calls bypass the cache. Content changes can reduce hits; a threshold of identical observations is configurable. [License](https://github.com/browserbase/stagehand/blob/main/LICENSE), [cache](https://docs.stagehand.dev/v4/best-practices/caching), [cache code](https://github.com/browserbase/stagehand/blob/main/packages/extension/services/cacheService.ts).

The code replays cached actions with `selfHeal: false`, then falls back to inference if applying them fails. Repair also exists on the deterministic action when enabled. **A selector that still resolves to the wrong element is a different category of error**: the absence of an exception does not prove semantic correctness. The experimental cache-check PR describes precisely this case. [act code](https://github.com/browserbase/stagehand/blob/main/packages/extension/services/actService.ts), [PR 2954](https://github.com/browserbase/stagehand/pull/2954).

Stagehand offers pages, concurrent operations, launch/connection and repair; differentiating it by "no concurrency/retries/browsers" would be wrong. Its standard API is neither a persistent crawling queue engine nor a complete durable business workflow. This observation concerns the public contract, not the capabilities of the Browserbase cloud.

### Jev and decision models: status and limits

The GitHub API confirmed on **October 7, 2026** that **2952, 2953, 2954, 2955 and 3103 remain open and unmerged**. They are stacked on other branches, not all directly on `main`. The stable npm SDK 4.1.0 does not include `experimentalDecisions`.

| Proposal | Mechanism and evidentiary status |
| --- | --- |
| [2952](https://github.com/browserbase/stagehand/pull/2952) | TypeSafe Jev client, candidates from the accessibility tree, context to distinguish duplicates, abstention, circuit breaker. Library initially not wired in. |
| [2953](https://github.com/browserbase/stagehand/pull/2953) | Intent → arguments → selection → existing action → deterministic checks, LLM fallback. Announced p50 1.97 s → 0.46 s on the act suite; **thresholds tuned on the evaluated suites**, scripts/breadth not published in the stack. Without an LLM, lower success: a fast path, not a replacement. |
| [2954](https://github.com/browserbase/stagehand/pull/2954) | Observation and semantic validation of the cached target. **No end-to-end cache eval**, threshold derived from probes; errors/timeouts of the check do not prevent replay. |
| [2955](https://github.com/browserbase/stagehand/pull/2955) | Element selection then deterministic copy of values, completeness judge; complex schemas/screenshot keep the LLM. Announced success equal to the baseline on 25 tasks, not reproduced here. |
| [3103](https://github.com/browserbase/stagehand/pull/3103) | Explicit namespace `experimentalDecisions.act/observe/extract`, three RPCs, TS/Python/Go creation option. The ordinary methods keep their LLM pipeline. |

The avenue is interesting for reducing inference on closed-set decisions. It proves neither out-of-distribution performance nor universally superior reliability. Do not lock a vendor into Goodfetch before trials; keep a decision contract with confidence, abstention, metrics and escalation.

## Browser Use: two generations and three surfaces

The MIT Python repository is at **0.13.11**, published on **October 7, 2026**. The historical Python agent remains importable via `browser_use.Agent`. Its `BrowserSession` uses `cdp-use`, a `bubus` bus and specialized watchdogs: crashes, downloads, DOM, captures, security, storage, CAPTCHA. The DOM service merges the DOM snapshot and accessibility trees, notably per frame. [Release](https://github.com/browser-use/browser-use/releases/tag/0.13.11), [configuration](https://github.com/browser-use/browser-use/blob/main/pyproject.toml), [session](https://github.com/browser-use/browser-use/blob/main/browser_use/browser/session.py), [DOM](https://github.com/browser-use/browser-use/blob/main/browser_use/dom/service.py).

Since **0.13.0, on June 8, 2026**, `browser_use.beta.Agent` uses a **native Rust runtime** distributed as wheels through the `[core]` extra. The Python wrapper launches `browser-use-terminal sdk-server --transport stdio`, as a JSON-RPC client; the server holds agent/session/browser and the follow-ups. The MIT `browser-use/terminal` repository includes runtime, protocol, browser, LLM, SQLite store, secrets and Python worker. Tokio, Serde, Reqwest and rusqlite do appear in Cargo.toml. [Release 0.13.0](https://github.com/browser-use/browser-use/releases/tag/0.13.0), [wrapper](https://github.com/browser-use/browser-use/blob/main/browser_use/beta/service.py), [integration ledger](https://github.com/browser-use/browser-use/blob/main/BETA_AGENT_INTEGRATION_FEATURES.md), [Cargo](https://github.com/browser-use/terminal/blob/main/Cargo.toml).

The separate **Browser Harness** lets the coding agent drive Chrome through a daemon and helpers; it is not necessarily an embedded autonomous loop. The V4 cloud distinguishes hosted agents, CDP browsers and persistent workspaces. Do not confuse the V4 cloud API number, the Python package version 0.13 and the native runtime. [Harness](https://github.com/browser-use/browser-harness), [cloud quickstart](https://docs.browser-use.com/).

Creation/refinement of **Skills is removed**: 410 Gone; existing skills can still be executed. V4 now recommends scripts saved in a workspace. Each V4 rerun still starts a model and consumes tokens; reuse avoids rediscovery, but is not a guarantee of zero-LLM execution. Old `.md` pages indexed by Exa still describe skill creation: the current page and the recent contract govern. [Current skills](https://docs.browser-use.com/cloud/legacy/skills), [scripts](https://docs.browser-use.com/cloud/agent/scripts).

`workflow-use`, separate and **AGPL-3.0**, records/generates parameterized semantic workflows, can replay them without AI and plans for fallback/repair. The README explicitly warns of its very early state and advises against production use; its roadmap still indicates self-healing gaps. It nevertheless received a push on October 2, 2026: do not classify it as "abandoned" on the basis of its README alone. [README](https://github.com/browser-use/workflow-use), [license](https://github.com/browser-use/workflow-use/blob/main/LICENSE).

## Skyvern is the priority product benchmark

Its code caching records a successful execution, produces a script, then executes `run_with="code"`. Caches are **per block**; branch coverage increases over the runs. Conditions/waits/code are still executed at runtime. The engine can fall back to the agent and regenerate. [Cache documentation](https://www.skyvern.com/docs/developers/features/code-caching), [SDK run_workflow](https://skyvern.com/docs/sdk-reference/workflows/run-workflow).

The OSS contains script generation, script versions/deployments, fallback episodes and computation of workflow reliability. It is not only a marketing announcement. Conditionals must, however, be handled by the DAG, not just by a linear file launched from the CLI. [Code generation and progressive caching](https://github.com/Skyvern-AI/skyvern/pull/4603), [MCP script tools](https://github.com/Skyvern-AI/skyvern/commit/31d37a5b01cff92dcd49ae5281fbc4d4b82aaa7d), [reliability service](https://github.com/Skyvern-AI/skyvern/blob/main/skyvern/services/self_heal_reliability_service.py).

Goodfetch can therefore compete on **ease of integration, portable contract, local-first, auditable cost, quality on one vertical and maintenance service**, not on the mere existence of replay. The claim must be tested with identical workflows and external assertions.

Measure total cost / verified success, p50/p95 duration, number of LLM calls, failed reruns, human intervention and network volume.

## What the benchmarks establish — and no more

The open `steel-dev/browserbench` measures creation → Playwright CDP connection → first `domcontentloaded` navigation → release on EC2 us-east-1 to google.com, 5,000 runs/vendor, ten warmups, success after any SDK retries. Its data give **Kernel 794 ms and Steel 894 ms** on average; they therefore do not support the slogan "Steel fastest" without qualification. They measure the minimal remote cycle, not a correct extraction, a login, a CAPTCHA or a workflow load. [Methodology and results](https://github.com/steel-dev/browserbench).

The Goodfetch protocol must separate first compilation, warm replay, cold replay, UI change, data change, auth expiration and network failure. A real set held out from calibration is indispensable; the in-sample Jev suites show exactly why. Comparisons must fix browser/region/proxy/model, publish the raw data and count failures in cost/latency.

## Proposed first delivery for 3–6 months

**Recommended target:** developers running recurring read/extraction workflows on a few authorized portals, with freshness and schema assertions. Starting with tasks without irreversible effects makes fixtures and comparisons easier. The economic value remains to be tested with pilot customers.

- **Month 1:** 10–20 reference workflows, Playwright/Stagehand/Skyvern baselines; definition of correct result, freshness and budget; local TS runtime/remote CDP.
- **Months 2–3:** typed input/output contracts, deterministic steps, checkpoints, injected secrets, source evidence per field or result, portable run JSON; assisted script creation and rerun tests.
- **Month 4:** replay, explainable invalidation, repair limited to the broken segment, plan version, before/after comparison; control of effects before retry.
- **Months 5–6:** API/MCP/CLI, hosted offering and observability, scheduling, integration of 2–3 pilots; SLA only on a measured scope. Do not add a marketplace, a forked browser, three-language SDKs or a full crawling engine before usage is established.

**Decision gates:** Rust only if profiling shows a significant share of end-to-end cost/latency under our control (example internal threshold: reproducible gain ≥20% on representative workloads). Cache and plan fully usable locally; cloud monetized through execution, history, maintenance and support. The thresholds and the packaging are proposals, not validated decisions.

**Remaining uncertainties:** no deployment of the projects, no benchmark run, no task cost paid, no complete security or compatibility audit, contractual limits of the cloud cache not accessible, maturity of the niches not demonstrated. The statuses/versions/dates are snapshots as of October 7, 2026. The mechanisms of the public code do not guarantee the availability or identical behavior of the cloud.
