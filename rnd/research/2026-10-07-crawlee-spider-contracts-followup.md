# Stagehand, Crawlee + Stagehand and Spider: contracts actually observed

Research of **October 7, 2026**, a targeted supplement to the [report on crawling engines](2026-10-07-crawl-engines.md). The goal is Automan's ambitious architecture: canonical Rust engine, multi-language SDKs, native HTTP and CDP, composable workflows and crawling. The facts below come from the published versions and their sources; the architectural implications are explicitly analysis conclusions.

**Research traceability: `sources_reviewed = 20`**, i.e. four Exa searches each requesting five results. This counter measures requested results, not twenty fully audited sources nor twenty independent validations. After discovery, direct reading of the npm/PyPI/crates.io registries, published archives, sources and tests. No benchmark or test of the third-party projects was run locally during this supplement.

## 1. Conclusion that changes the decision

**Stagehand alone, Crawlee + Stagehand and Spider do not carry the same contract.** Stagehand provides interpretation and browser actions. Crawlee brings a URL processing infrastructure — queue, deduplication, locking, retries, sessions, browser pool, storage and concurrency regulation — around the handler that uses Stagehand. Spider has a highly developed Rust HTTP/rendering path and a genuine OSS agent engine; its SQLite crawling persistence does not, however, by itself constitute a durable job queue with acknowledgment and resumption of in-progress work.

Automan will therefore not win with a simple "Rust crawler + agent" addition. **It must unify the verified-result contract, session identity, execution resumption and cost control**, while keeping the workflow engine independent of URL traversal. Crawlee and Spider are useful references to compare against, not proofs of business reliability or of superior performance in all tasks. [Crawlee architecture](https://github.com/apify/crawlee/blob/v3.18.2/packages/basic-crawler/src/internals/basic-crawler.ts), [published Spider architecture](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs), [Spider agent engine](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/browser.rs).

## 3. What the Crawlee + Stagehand combination actually does in TS

### Two connections to the same browser, not two merged engines

The `StagehandPlugin` builds a Stagehand instance, calls `init()`, retrieves `connectURL()`, then connects **Playwright `chromium.connectOverCDP()` to the browser launched by Stagehand**. A `WeakMap` links the Playwright browser to the Stagehand instance. Crawlee keeps the pool, the navigation and the request lifecycle; Stagehand keeps its CDP connection and its AI functions. Closing cleans up Stagehand and the anonymized proxy, if any. [Pinned plugin](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-plugin.ts).

The controller creates the pages in **`browser.contexts()[0]`**. Its `_contextOptions` argument is ignored. It retrieves the `mainFrameId` via a temporary Playwright CDP session and waits for Stagehand to register this page: polling every **25 ms**, limit **10 s**. The comment explains the race between the resolution of `newPage()` on the Playwright side and the reception of `Target.attachedToTarget` on the Stagehand side. If registration fails, the page is closed and an error is raised. This is a real cost and a real coordination point between two CDP clients, not a systematically observed failure. [Controller, page creation and binding](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-controller.ts#L37).

The adapter enriches the Playwright page: `act`, `extract`, `observe` delegate to Stagehand by explicitly passing `{ page }`. **`page.agent(config)`, on the other hand, returns `stagehand.agent(config)` without injecting the current page.** In Stagehand npm 3.0.7, the agent preparation normalizes a page provided in the execution options; otherwise the execution path retrieves the active page of the Stagehand context. Thus, the name `page.agent` is not enough to guarantee that two concurrent agents each work on the page of their own handler. This limit stems from the wrapper; a wrong cross-page action was not reproduced here. [AI function wrapper](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/utils/stagehand-utils.ts), [Stagehand 3.0.7 npm bundle](https://unpkg.com/@browserbasehq/stagehand@3.0.7/dist/index.js).

### Fingerprints, cookies and identity: the integration's clauses must be read

The crawler constructor sets `useFingerprints` to `true` by default. But the plugin specifies **Chromium only** and warns that some fingerprint options do not fully apply, since Stagehand controls the launch. The local parameters actually passed include in particular headless, arguments, executable, proxy and viewport. It would be misleading to carry over Crawlee's general fingerprinting promise as if all properties were guaranteed by this adapter. [Crawler options and defaults](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-crawler.ts), [plugin restrictions](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-plugin.ts#L25).

The pages use the same context per browser. The controller's cookie functions perform Playwright operations, but handle some failures on a best-effort basis: reading may return `[]`, writing may ignore the error. In `BrowserCrawler`, saving the session cookies happens after navigation and before the user handler; a comment plans to move this save to after the handler. This does not mean that a login's cookies disappear immediately: they remain in the browser context. It means that this step is not an explicit checkpoint of the authentication state created by the handler. [Controller cookies](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-controller.ts), [navigation/cookies/handler order](https://github.com/apify/crawlee/blob/v3.18.2/packages/browser-crawler/src/internals/browser-crawler.ts).

**Implication for Automan:** an account identity must be an explicit and exclusive object, distinct from the page and the pool. An additional page in a shared context is not a new isolated identity. The backend must announce its isolation capabilities and reject an option it cannot honor.

### Python is a different integration

In Crawlee Python 1.10.4, the plugin uses **`AsyncStagehand` REST**, creates an `AsyncSession`, retrieves `session.data.cdp_url`, then connects Playwright with `chromium.connect_over_cdp()`. Locally, it can provide the Chromium executable installed by Playwright. The Python SDK 3.19.5 launches a local server in the form of an SEA binary resolved by version; remote mode targets the Stagehand API. It is therefore not the same in-process wrapper as in TS. [Python plugin](https://github.com/apify/crawlee-python/blob/v1.10.4/src/crawlee/browsers/_stagehand_browser_plugin.py), [session creation and CDP connection](https://github.com/apify/crawlee-python/blob/v1.10.4/src/crawlee/browsers/_stagehand_browser_controller.py), [Python SDK release](https://pypi.org/project/stagehand/3.19.5/).

The Python `StagehandPage` injects **`page=self._page` into `act`, `observe`, `extract` and `execute`**, including agentic execution. The controller initializes its session only once, reuses its context, and documents that the context/proxy options of subsequent page creations are ignored. The announced limitations are more precise: **incognito pages and full canvas/WebGL/screen fingerprint not supported; consistent HTTP header generation only**. [Python wrapper](https://github.com/apify/crawlee-python/blob/v1.10.4/src/crawlee/browsers/_stagehand_types.py#L74), [official guide](https://crawlee.dev/python/docs/guides/stagehand-crawler).

## 4. Crawlee's infrastructure guarantees: strong, but bounded

| Primitive | Behavior observed in 3.18.2 | Practical limit |
|---|---|---|
| Queue | The `RequestQueue` exported by default is **V2**: head retrieval with lock, lock extension, handling of locked requests and acknowledgment. | An expired lease, a process stop or an error around the acknowledgment remain resume boundaries. It is not a universal transaction with the handler's effects. |
| Retry | Defaults `maxRequestRetries=3`, `maxSessionRotations=10`, `useSessionPool=true`. A handler error can cause the handler to be executed again in full. | An external action that already succeeded before an error can be replayed. A URL retry is not a retry of only the faulty step. |
| Session error | `SessionError` inherits from `RetryRequestError`, which goes through a special retry rule; rotations bounded separately. | Do not simply announce "four attempts maximum": rotations and forced-retry errors modify this bound. `retryCount` still increases in the recovery path. |
| Final failure | Request marked `handled` before the `failedRequestHandler` callback. | The number of handled requests is not the number of successful business results. |
| Local storage | `persistStorage=true`, memory + disk storage. | **`purgeOnStart=true` as well**: the default storages are purged at the start of a new run. Resuming requires an adapted configuration, for example a named and retained queue or a disabled purge. |
| Results | `pushData` writes at call time; array split into sequential chunks. | Append-only dataset, **no transaction** over the whole array nor between the dataset and the queue acknowledgment. |
| Concurrency | `AutoscaledPool` observes memory, CPU, event loop and client load; starts low and adjusts its target. Default `maxConcurrency=200`. | This cap is not a universal recommendation. This mechanism does not automatically optimize the LLM budget, business quality or each domain's limit. |
| Proxies/anti-blocking | Sessions, proxy assignment and fingerprint integrations available; `retryOnBlocked=false` by default. | Proxy configured, fingerprint enabled and success against a WAF are three different assertions. |

Sources: [V2 export](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/storages/index.ts), [V2 queue](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/storages/request_queue_v2.ts), [request lifecycle and errors](https://github.com/apify/crawlee/blob/v3.18.2/packages/basic-crawler/src/internals/basic-crawler.ts#L1608), [error types](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/errors.ts#L48), [storage configuration](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/configuration.ts#L284), [`Dataset.pushData` contract](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/storages/dataset.ts#L251), [automatic pool](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/autoscaling/autoscaled_pool.ts), [load signals](https://github.com/apify/crawlee/blob/v3.18.2/packages/core/src/autoscaling/system_status.ts).

**Decisive scenario:** the handler extracts ten products, calls `pushData`, then the process stops before `markRequestHandled`. The queue may trigger a new processing while the previous results already exist. Even without a crash, an array whose first chunks were written can fail afterward. The dataset code and documentation make this window explicit. Automan must therefore define idempotency keys and a result commit boundary; the presence of a queue must not be turned into an "exactly once" promise.

### URL discovery is not understanding pagination

`enqueueLinks` discovers and filters URLs among the page's links, with selectors and strategy options; the handler chooses when to call it and which links to accept. A JavaScript button, an infinite scroll, an XHR response or pagination without `href` require an interaction or an additional recipe. Stagehand can help find and actuate these controls; **Crawlee does not automatically derive a complete and bounded traversal from them**. An end criterion, entity deduplication and a budget must be defined. [Crawler handler/links interface](https://github.com/apify/crawlee/blob/v3.18.2/packages/stagehand-crawler/src/internals/stagehand-crawler.ts), [implementation of the adaptive helpers](https://github.com/apify/crawlee/blob/v3.18.2/packages/playwright-crawler/src/internals/adaptive-playwright-crawler.ts#L548).

## 5. Crawlee's adaptive mode is not already included in StagehandCrawler

`AdaptivePlaywrightCrawler` is a distinct class. It exposes a restricted handler compatible with both HTTP and browser. If an HTTP handler accesses `page`, an error is raised to switch to the browser. `querySelector`, `parseWithCheerio`, `waitForSelector`, `pushData`, `enqueueLinks` and a controlled state constitute the common interface. **A Stagehand handler that systematically uses `page.act` is not made HTTP-first merely by going through Crawlee.** [Published adaptive class](https://github.com/apify/crawlee/blob/v3.18.2/packages/playwright-crawler/src/internals/adaptive-playwright-crawler.ts).

The predictor uses a **logistic regression**, similarities between URL components and the results observed per label. It starts without prior knowledge, recommending the browser with a detection probability of 1; the target detection ratio is **0.1** by default. During a detection, the outputs of a browser handler and of an HTTP handler are compared. `resultChecker` can reject an HTTP output; `resultComparator` can declare equal/different/inconclusive. In the absence of both, the comparison is performed on the dataset items. This model seeks to determine whether **the handler produces the expected result without a browser**, rather than merely noting the presence of scripts. [Published predictor](https://github.com/apify/crawlee/blob/v3.18.2/packages/playwright-crawler/src/internals/utils/rendering-type-prediction.ts), [comparison and learning](https://github.com/apify/crawlee/blob/v3.18.2/packages/playwright-crawler/src/internals/adaptive-playwright-crawler.ts#L373).

The adaptive handler **buffers** dataset/queue calls and key-value store changes so as not to publish the rejected HTTP attempt. Beware of the vocabulary: `commitResult` applies them with `Promise.all`; it is **not an atomic transaction** across all these storages. Arbitrary external effects performed by the handler are not undone. [Actual commit](https://github.com/apify/crawlee/blob/v3.18.2/packages/playwright-crawler/src/internals/adaptive-playwright-crawler.ts#L470).

**Implication for Automan:** intermediate outputs must be buffered until validation, but actions with external effects must have a distinct contract. HTTP/CDP selection must depend on the task and its invariants, not on a global "static site" label.

## 6. Spider 2.53.9: HTTP contract, smart, concurrency and resume

### Smart is a real escalation, conditioned by Cargo features

`crawl_smart()` runs the HTTP-first + conditional rendering path when the **`smart`** feature is compiled in local mode. Without `smart`, the function is an alias of `crawl()`. With `decentralized`, it also delegates to `crawl()`; the variants are therefore not interchangeable. In the manifest, `smart` enables Chrome and interception. [Published `crawl_smart` branches](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L7601), [Cargo features](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/Cargo.toml).

The HTML analysis assigns an upgrade score, **threshold 10**: framework/hydration markers, messages requiring JavaScript, certain DOM/script usages, content and anti-bot detection. The browser is created lazily via `OnceBrowser` and then reused; separate tabs serve the upgrades and guards ensure they are closed on exit paths. It is not an LLM that decides each rendering. [Heuristics and threshold](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/page.rs#L8305), [lazy creation and tab guard](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/page.rs#L8627).

The smart bootstrap also has a specific fallback **after the retry loop**: if Chrome has not already been tried, `page.needs_retry()` holds and the content is empty, a Chrome attempt is made even with the default `retry=0`. This safeguard was added to prevent a transport failure from making smart equivalent to HTTP only. One should neither present the old bug as a current failure, nor generalize this bootstrap branch to all backend/feature combinations. [Published fallback](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L6745).

**Distinction from Crawlee's adaptive mode:** the ordinary smart heuristics mostly detect the probable need for rendering. Crawlee's adaptive mode compares the handler's outputs. Spider, however, also has the optional **`parallel_backends`** feature, a scored HTML quality and a **customizable `QualityValidator`** that can modify or reject a score. Calling it a simple crawler without validation would be inaccurate; this optional content/backend validation is not the same API as AdaptivePlaywrightCrawler's comparison of handler outputs. [Quality hook](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L14248), [selection of alternative responses](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L8923).

### Budgets and retries: explicit parameters, not implicit success

`with_limit(n)` configures a wildcard budget `"*"`; **0 means unlimited**, 1 enables the single-page fast path. Budgets can also apply to paths, with depth, filtering, delays and a global timeout. They bound the admitted traversal; they do not mean "n valid business results". Budgets restored for irrelevant pages exist in feature-gated agentic paths. [Limit configuration](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/configuration.rs#L1719), [budget consumption](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L2291).

The configuration retry is **0 by default**. `Page::needs_retry()` combines a flag, a truncated response, temporary statuses and some 401s under a proxy. The classification excludes several failures considered permanent — DNS, unreachable address/SSL, redirect limit — and some deterministic 5xx; it includes the other 5xx, 429 and 408. A **`RetryStrategy`** can replace the limit with `max_retries()`, change proxy/profile/backend and backoff, or refuse to continue. The loops return a final `Page` and its metadata; this notion does not replace a business acknowledgment of the extraction. [Retry default and setter](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/configuration.rs#L1965), [exact classification](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/page.rs#L1680), [`needs_retry`](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/page.rs#L4456), [strategy contract](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/retry_strategy.rs#L180).

**Doc/code divergence not to be copied:** the `request_timeout` comment announces 15 seconds; **`Configuration::new()` sets 120 seconds**, with and without Chrome. Limits must be set explicitly in a product and in a benchmark. [Published comment and initialization](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/configuration.rs#L1037).

### Concurrency and browser reuse

`setup_semaphore()` first chooses a provided adaptive semaphore, otherwise a global semaphore if `shared_queue`, otherwise a semaphore with `concurrency_limit` or `DEFAULT_PERMITS`. The default concurrency setting is derived from the system; **the presence of `AdaptiveSemaphore` does not mean that every crawl automatically adapts its throughput to CPU/RAM**. The external handle is opt-in and runtime-only. Spider offers real control and memory mechanisms and additional auto-throttle/hedge/parallel-backends paths; the comparison protocol must specify the enabled features. [Semaphore resolution](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L6956), [external handle and static default](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L1537).

The normal browser path installs a browser controller, creates tabs and keeps the browser during the crawl, then disposes of it. `fetch_chrome_persisted()` allows the caller to provide a retained controller. One must therefore not measure "a new Chromium per URL" against Spider reusing the same browser. [Browser lifecycle](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L9180), [fetch with a retained browser](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L7575).

### Disk and queue: what exactly persists

The `disk` feature creates two SQLite tables: **`resources(id,url)` and `signatures(id,url)`**. The code looks up/inserts already visited URLs and moves sets from memory to disk under certain conditions of memory pressure or shared state. In this schema, it does not contain pending/running/done states, leases, step checkpoints or an output transaction. `persist` is **false by default** and the handler's `Drop` deletes its file if this option has not been enabled. `set_disk_persistance(true)` acts on an already present SQLite handler. [Schema and defaults](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/features/disk.rs#L96), [end of life of the database](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/features/disk.rs#L323), [moving visited to disk](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L1883).

`Website::queue()` is an **in-memory Tokio broadcast channel** for injecting links during the crawl, available under `sync`. `persist_links()` changes a status to chain several passes on the same object, for example sitemap then crawl. This does not prove a restoration of the entire pending frontier after a crash. With the database retained, a restart can have the previous visits available; **reconstructing unfinished work and its acknowledgments remains a contract to be provided on top**. [Actual queue](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L14692), [actual `persist_links`](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L2719).

Page results also use a broadcast. The `ChannelGuard` synchronizes producers and consumers, but its wait has a **250 ms safety deadline**, after which it resumes. This mechanism provides practical coordination; it is not a durable results journal. A consumer that is too slow must manage the channel capacity and delays, or quickly send the data to a durable sink. [Page sending](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L15080), [guard deadline](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider/src/website.rs#L15165).

## 7. `spider_agent` is a real OSS competitor, but its checklist deserves inspection

The **MIT `spider_agent` 2.53.9** crate is not only the SDK of the Spider Cloud service. `RemoteMultimodalEngine` calls a configurable model API, processes HTML and screenshots, and provides `extract_from_html`, `extract_with_screenshot`, URL classification, model routing and control of concurrent LLM calls. With the **`chrome`** feature, its implementation uses Chromey for `run`, `act` and `observe` on a local or CDP-connected page. `default=[]`: not all browser capabilities are present without the appropriate features. The cloud tools are additional integrations, not a necessary dependency for all these primitives. [Published license and features](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/Cargo.toml), [LLM engine](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/engine.rs), [browser actions](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/browser.rs#L4597).

The browser loop has round bounds, model call retries, action failure feedback and repetition/stagnation detection. It can stop with `success=false` when the rounds are exhausted. **`success=true` stems mainly from the `plan.done` provided by the model**, after the steps are executed; this flag does not constitute a business invariant independent of the model. Some URL gates also return a success result for an unauthorized URL. Field names must be interpreted in light of the execution context. [Loop and limit](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/browser.rs#L656), [model-driven success and exhaustion](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/browser.rs#L2081).

**Caveat verified by static inspection:** the options `html_diff_mode`, `planning_mode`, `confidence_strategy`, `self_healing` are exposed in the builders and types; the presets `fast()`/`fast_with_planning()` configure them and the comments announce in particular a 50–70% token reduction. A search for these four names in **all published `.rs` files** of `spider_agent`, `spider_agent_types`, `spider_agent_html` found occurrences only in setters/configuration/types, with no read of these fields in the audited runtime loop. Tool calling, by contrast, has an explicit branch in the engine. This justifies classifying the four features as **exposed API, runtime activation not demonstrated by the audit**, not as acquired gains. Associated types and helpers exist; no accusation of intentionally misleading code nor any test of non-functioning is established here. [Exposed options](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/config.rs#L619), [presets and promises](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent_types/src/config.rs#L997), [tool calling branch actually consumed](https://github.com/spider-rs/spider/blob/e4b53c5b582357e46433fa9ba3d91f930fb67cb4/spider_agent/src/automation/browser.rs#L2540).

**Consequence:** Automan must evaluate `spider_agent` as a reference and a candidate for permissive reuse, but test each feature that enters the product promise. An architectural preference for Rust does not exempt us from requiring behavioral proof for each option.

## 9. Three concrete workflows to distinguish the solutions

| Requested work | Stagehand alone | Crawlee + Stagehand | Spider / Spider agent | Contract to own in Automan |
|---|---|---|---|---|
| Public catalog: collect detail pages and link-based pagination | Can navigate/extract; the queue and the traversal policy must be built. | Queue/filtering/retries/pool ready; AI handler if useful. The browser is used by StagehandCrawler even if the detail pages are static. | HTTP parsing then relevant smart upgrade; budget and page stream. | Validated HTTP first; complete schema, entity dedup, persisted final errors. |
| Logged-in area: search for an item then manipulate a form | Suitable AI and browser primitives. | Adds parallelism/pool; the shared context and the retry scope must be controlled. | OSS agent can act; gate, round budget and success validation to be specified. | Exclusive identity, auth checkpoint, preconditions and postconditions per step. |
| Long crawl interrupted then resumed during a sink incident | Logic to be provided. | Persistent queue reusable if correctly configured; the dataset may contain writes made before acknowledgment. | Visited can be retained; frontier and stream are not a durable journal. | Leases, idempotent results, outbox/sink, resumption of pending/running and failure classification. |

This table describes **consequences of the inspected contracts**, not the results of an executed benchmark. "Faster" must be measured on successful work and under identical isolation conditions, with p50/p95 latency, total cost, bytes, RAM/CPU, number of navigations, LLM calls/tokens, rate of valid results and behavior after interruption.

## 10. Concrete reuse direction for the target architecture

1. **Keep a canonical Rust runtime independent of the crawler.** HTTP, CDP, page/context/session, observation, action, extraction and cancel are common primitives. The workflow engine owns the steps, their state and their resumption; the crawl module owns frontier, dedup and discovery policies. A crawling library must not determine Automan's entire business model.
2. **Evaluate Spider as an adapter and a source of specialized components.** Reuse parsing, filters, budgets, proxy/retry strategies and smart paths when their contracts fit. Keep a durable queue and a results journal owned by Automan. MIT is favorable to commercial use; respect the license and the notices. A pinned crate dependency is preferable to a global fork as long as the cost of the adaptations remains under control.
3. **Put Chromiumoxide and Chromey in competition on Automan CDP tests.** Chromey powers Spider's browser functions and has interesting specific adaptations. The decision must measure auto-wait/actionability, iframes/OOPIF, downloads, network/proxies, CDP losses, cancellation and Chromium updates. Neither "Chromiumoxide fork" nor "used by Spider" is enough to validate a backend; see the initial report for licenses and maintenance.
4. **Offer Stagehand as a versioned skills backend.** The adapter must explicitly bind every operation to a page, trace the LLM cost and announce its context/isolation limits. Publish the SDK/backend version matrix. In TS, the current Crawlee integration remains on v3; the v4 changes must be a validated port, not a forced install of the peer.
5. **Treat Crawlee as a compatibility contract and an infrastructure reference.** Queue, sessions, autoscale and hooks are an excellent baseline, even if Automan chooses a Rust core. Offer an optional TS/Crawlee bridge for the ecosystem, without making this framework mandatory for workflow users.
6. **Own the escalation policy and the proof of result.** Combine a cheap HTML signal, schema/invariant results, per-task and per-session history, HTTP/CDP sampling and post-action feedback. Crawlee's adaptive mode and Spider's smart/quality-validator already compete on this angle: the difference must be the unified and measured contract, the cost and the resumption.

The technical priority is not to rewrite Chromium. It is to build **the execution and verification layer that makes HTTP/CDP/AI choices consistent and reusable**, then to prove the gains against these references in workloads where the results and the effects are controlled.

### Remaining uncertainties to turn into tests

- Stagehand v4 port of the TS adapter, and precise compatibility of the Python REST protocol depending on the server version: not executed.
- Actual behavior of two concurrent TS agents on distinct pages of the same browser: the missing binding is demonstrated in the wrapper, the concrete incident remains to be reproduced.
- Resilience of Crawlee's local storage under a kill in the middle of writes and leases: code inspected, stress/kill test not executed.
- Spider resume with retained sqlite and an external frontier: resume model to be defined; no promise of durable pending retained.
- Effects of the advanced `spider_agent` options flagged without runtime reads: to be verified with a fake LLM server and deterministic responses, comparing traces/payloads/options.
- Crawlee/StagehandCrawler/Spider performance comparison: no new quantitative conclusion; a common benchmark remains to be built.
