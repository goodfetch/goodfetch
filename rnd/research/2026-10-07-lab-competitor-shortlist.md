# Automan Lab — competitors to measure and comparison limits

State of the sources consulted: **October 7, 2026**. This note complements the existing research, in particular [the crawl matrix](2026-10-07-crawl-capability-matrix.md), [the browser/agent contracts](2026-10-07-stagehand-alternatives-followup.md) and [the commercial landscape](2026-10-07-commercial-landscape.md). It proposes the scope of a lab; it contains **no locally executed measurement**, no reproduced performance ranking and no installation.

Method: official documentation and repositories read via Exa; direct reading of manifests, license files and npm metadata to confirm package names. The facts cited concern these public surfaces, not all of a vendor's products. `latest` versions and `main` branches are dated observations: the trials will need to pin versions, SHAs and browser binaries.

## What the selection must make it possible to decide

The requested trio — Crawlee, Spider and Stagehand — is relevant, but it covers three different layers: crawling engine, Rust HTTP/browser engine, and control/perception/action SDK. To judge Automan's architecture, add controls that isolate transport, browser, protocol, orchestration and inference. A difference observed between two complete products does not make it possible to attribute its cause to the language.

**Proposed immediate priority:** the requested trio, then Playwright, Puppeteer, chromiumoxide, agent-browser, Scrapy and a Go reference. This is the foundation for testing the "Rust + HTTP + CDP" thesis. **Second wave:** Crawl4AI, Scrapling, Browser Use, Skyvern and Lightpanda. **Third wave:** managed services and complementary semantic agents, depending on product needs. This order is a recommendation, not a quality ranking.

## 5. Proposed protocol to avoid false winners

1. **Controlled common foundation.** Same Chrome, same host, same profile policy, viewport and corpus; fresh state and reused state kept separate. Run each competitor separately to avoid unintended contention. Document impossible features without silently emulating them.
2. **Three complementary modes.** Deterministic primitives with a common minimum guarantee; flows with native guarantees; optimized configuration of each product. The first isolates overhead, the second measures the cost of reliability, the third measures real potential. No averaging across these tracks.
3. **Identical waits in the common track.** A navigation waits for the same verifiable condition and an action for the same postcondition. Default values do not necessarily perform the same work. Playwright's actionability guarantees must be present in, or explicitly absent from, the other configurations. [Actionability](https://playwright.dev/docs/actionability).
4. **Representative primitives.** `navigate`, `click`, `fill`, `select`, `press`, `scroll`, `evaluate`, DOM reading, extraction, AX snapshot, screenshot, download/upload, cookies/storage, network interception, frames and new pages. A command success is not a scenario success: verify on the fixture side the object identity, the entered value and the business event.
5. **Stress and quality.** Progressively increased concurrency; large DOMs; re-render between resolution and click; overlays; iframes/OOPIF; shadow DOM; slow navigation; 429/503; stop/resume; crash of a browser; saturation of the destination. Publish useful throughput, p50/p95/p99, RSS of the entire process tree, CPU, bytes, errors, false successes and losses/duplicates after resumption.
6. **Distinct AI measurements.** Same task, objective and validation policy; model and parameters recorded. Measure token cost, success rate and latency on discovery, replay and repair. The cost per correct task outweighs a speed score that includes failed tasks.
7. **Distribution and evidence.** Raw logs, environment, commits, versions, fixtures, repetitions and confidence intervals publishable. Settings developed on one batch, then evaluated on a held-out batch. A corpus calibrated for a single competitor is not enough to conclude "the most performant".

## Decisions this lab makes possible

- **Control plane language**: compare orchestration, queue, persistence and memory cost; do not use Chromium navigation time alone to choose Rust/Go/TypeScript.
- **Chromium driver**: if chromiumoxide/Rust reduces overhead with correct results on the required scope, justify this backend; keep a Playwright backend for its missing capabilities. If browser load or RTTs dominate, optimize placement, batching and reuse before a rewrite.
- **HTTP first**: demonstrate which scenarios can switch from browser to HTTP without changing data, auth and postconditions; then measure the gain per valid result.
- **Local fleet or vendor**: compare co-located code + browser, Steel/Browserless server and remote vendors in their dedicated track.
- **Agents and replay**: choose discovery/repair components according to results and costs; the first generation of the plan and its qualified execution remain separately measurable.

The defensible formulation before the trials is **"build a lab capable of demonstrating the best trade-off of throughput, latency, memory, cost and accuracy on our workloads"**. Universal worldwide superiority cannot be demonstrated by marketing multipliers alone, nor by a CDP microbenchmark.
