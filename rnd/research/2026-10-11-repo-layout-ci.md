### Why projects merged

- **Pydantic merged pydantic-core in November 2025.** The import used `git subtree add` and rewrote commit messages to link back to the old repo ([PR #12436](https://github.com/pydantic/pydantic/pull/12436), [PR #12481](https://github.com/pydantic/pydantic/pull/12481), merged 2025-11-05). The PR says all future core development happens in the main repo, and the old repo gets only 2.12 backports ([PR #12481](https://github.com/pydantic/pydantic/pull/12481)). The 2.13 changelog only says that "the `pydantic-core` repository was merged" and gives no reason ([changelog](https://pydantic.dev/docs/validation/latest/get-started/changelog/)). The two packages still carry separate version lines: pydantic 2.13.x pairs with pydantic-core 2.46.x ([Fern changelog](https://www.buildwithfern.com/learn/sdks/generators/python/changelog/2026/5/4)).
- **The pydantic-core split caused real pinning pain.** Pydantic pins pydantic-core to an exact patch. It raises an error when the versions don't match ([changelog 2.12.0b1, #12196](https://pydantic.dev/docs/validation/latest/get-started/changelog/)). Distro packagers must upgrade the two in lockstep ([Buildroot](https://lists.buildroot.org/pipermail/buildroot/2025-October/788557.html)). Users on Python 3.14 got an old core that would not build, because pydantic `main` pinned a newer core than the last pydantic release ([issue #12220](https://github.com/pydantic/pydantic/issues/12220)).
- **Stagehand v4 merged everything into a "protocol-first monorepo with three SDKs over a shared core"** ([PR #2671](https://github.com/browserbase/stagehand/pull/2671), merged 2026-08-10). The TS and Python SDKs both shipped as 4.0.0. [`packages/protocol`](https://github.com/browserbase/stagehand/tree/main/packages/protocol) defines bidirectional JSON-RPC with Zod. A generated `stagehand.v4.json` schema then produces the Python models and Go structs. This is the closest match to Automan's design. The old Python repo was archived after its 3.23.0 release ([stagehand-python](https://github.com/browserbase/stagehand-python)).
- **Polars moved its user guide into the main repo.** The reason given: with a separate repo, "code examples in the user guide will not work anymore" after breaking changes ([issue #10560](https://github.com/pola-rs/polars/issues/10560), [polars-book #403](https://github.com/pola-rs/polars-book/issues/403)).
- **Firecrawl keeps the API and nine language SDKs in `apps/`**, together with its own test website ([apps/](https://github.com/firecrawl/firecrawl/tree/main/apps)). The old standalone [firecrawl-py](https://github.com/firecrawl/firecrawl-py) repo was last pushed in May 2024. The Go SDK is still pulled in as a [git submodule](https://github.com/firecrawl/firecrawl/blob/main/.gitmodules).
- **Browser Use moved its separate Python cloud SDK** into a combined Node + Python [browser-use/sdk](https://github.com/browser-use/sdk) repo ([archive note](https://github.com/browser-use/browser-use-python)).
- **Tauri gathers its official plugins in [plugins-workspace](https://github.com/tauri-apps/plugins-workspace)**, separate from core. Its stated reason was not found (unverified).
- **Dagger keeps nine SDKs under `sdk/`**, all tagged in lockstep with the engine (`v0.21.10`, `sdk/typescript/v0.21.10`, `sdk/rust/v0.21.10`, all on 2026-09-30) ([releases](https://github.com/dagger/dagger/releases)).

### Why projects split

- **Biome removed its website from the monorepo** in April 2024 ([PR #2505](https://github.com/biomejs/biome/pull/2505)). No reason is given in the PR (unverified rationale). The site still generates its rule pages from the code repo ([README](https://github.com/biomejs/website)).
- **Playwright keeps one core repo and separate port repos.** Each port bundles the Node `playwright-core` driver, pinned in a `DRIVER_VERSION` file. To "roll" a release, a maintainer bumps the pin and regenerates the API from a nearby checkout of the core repo ([ROLLING.md](https://github.com/microsoft/playwright-python/blob/main/ROLLING.md)).
- **Temporal keeps a shared Rust core in its own repo** ([sdk-rust](https://github.com/temporalio/sdk-rust), "used as the base of" the TS, Python, .NET and Ruby SDKs). Each SDK pulls it in as a git submodule: [TS](https://github.com/temporalio/sdk-typescript/blob/main/.gitmodules) at `packages/core-bridge/sdk-core`, [Python](https://github.com/temporalio/sdk-python/blob/main/.gitmodules) at `temporalio/bridge/sdk-core`. Cross-SDK conformance lives in yet another repo, [temporalio/features](https://github.com/temporalio/features).
- **Apache OpenDAL stays a monorepo but proposed separate versions per binding.** The reason: each core change forced a minor bump on every binding, and some bindings were immature ([discussion #4126](https://github.com/apache/opendal/discussions/4126)). This is a counterpoint to lockstep versioning.

### Lockstep impact: evidence

- **Playwright ports lag the core by 1 to 3 weeks.** Core v1.63.0 shipped 2026-09-04. Python followed on 09-15, Java on 09-14 and .NET on 09-21. Core v1.64.0 shipped 10-07, and no port had it by 10-11 ([core](https://github.com/microsoft/playwright/releases), [python](https://github.com/microsoft/playwright-python/releases), [java](https://github.com/microsoft/playwright-java/releases), [dotnet](https://github.com/microsoft/playwright-dotnet/releases)). Users ask when ports will catch up ("Release v1.59?", [#3048](https://github.com/microsoft/playwright-python/issues/3048)) and file parity requests ([#2826](https://github.com/microsoft/playwright-python/issues/2826) "API parity with Node.js", [#2867](https://github.com/microsoft/playwright-python/issues/2867) snapshotForAI).
- **spider-rs bindings drift far behind.** The core crate was at v2.52.2 (GitHub release, 2026-03-31). spider-py was at 0.0.58 (2026-01-19) and spider-nodejs at 0.0.163 (2026-01-21), each on its own version line ([spider](https://github.com/spider-rs/spider/releases), [spider-py](https://github.com/spider-rs/spider-py/releases), [spider-nodejs](https://github.com/spider-rs/spider-nodejs/releases)).
- **Crawlee JS and Python use independent versions:** JS v3.18 / v4.0.0-rc, Python v1.10 ([JS](https://github.com/apify/crawlee/releases), [Python](https://github.com/apify/crawlee-python/releases)). Parity is tracked by hand ([#1739](https://github.com/apify/crawlee-python/issues/1739) "Align exception hierarchy with Crawlee JS").
- **Temporal SDKs release on their own schedules:** sdk-rust v1.1.0 (10-06), TS v1.24.0 (09-15), Python 1.34.0 (09-30) ([releases](https://github.com/temporalio/sdk-rust/releases)). Submodules leak into packaging: published Python wheels once shipped a stray submodule `.git` file ([sdk-python #1659](https://github.com/temporalio/sdk-python/issues/1659)).
- **Prisma users hit CLI/client version mismatches.** One user asked for mismatches to be an error rather than a warning ([prisma/orm #24382](https://github.com/prisma/orm/issues/24382), [#15924](https://github.com/prisma/orm/issues/15924)).
- **The Firebase Genkit maintainers argue for one shared version** for core and all plugins, so users don't need "compatibility matrices". They warn that split repos lead to version-skew bugs and to plugin CI that runs against the last published core instead of HEAD ([WHY_MONOREPO.md](https://github.com/firebase/genkit/blob/3e0317eac483aa2c1b63652b2d15323196620468/py/docs/WHY_MONOREPO.md)).

### Patterns

1. **Rust-core multi-language projects that move fast now use one repo.** Examples: Ruff, uv, Biome, Polars, Turborepo, Bun, Deno, Dagger, Firecrawl, and since their 2025–2026 merges, Pydantic and Stagehand. Common folders: `crates/` for Rust, `packages/` for npm (Biome ships `cli-<os>-<arch>` packages under [`packages/@biomejs`](https://github.com/biomejs/biome/tree/main/packages/%40biomejs), the same optionalDependencies pattern Automan plans), and `python/` or `py-*` for the maturin package.
2. **Per-language repos lead to lag and parity tickets.** Playwright, spider-rs, Crawlee and Temporal all show this. Their releases are not lockstep. Pinning files (`DRIVER_VERSION`) or submodules carry the coupling.
3. **Docs are split about evenly.** In-repo: Ruff, uv, Polars, Pydantic, Bun, Dagger, Turborepo, Crawlee (Docusaurus), Stagehand. Separate repo: Deno, Biome, Tauri, Prisma, Temporal, Firecrawl, Lightpanda, Playwright's website. Projects that keep docs in-repo give a concrete reason: examples break otherwise (Polars). Projects that split the site out still generate content from the code repo (Playwright, Biome).
4. **Test websites and fixtures usually live in the main repo.** Examples: Firecrawl `apps/test-site`, Playwright `tests/assets`, Crawlee `test/e2e`, Bun `test/fixtures`. Large shared external suites come in as submodules (Deno and WPT) or as separate repos (Temporal `features`, Lightpanda `demo` and `wpt`, uv's `packse`).
5. **Merges keep history.** Pydantic used `git subtree add` and rewrote commit messages to link back to the old repo, then archived it ([PR #12436](https://github.com/pydantic/pydantic/pull/12436)). Stagehand froze its old line on a protected `v3` branch ([PR #2671](https://github.com/browserbase/stagehand/pull/2671)).


## B. Release automation for a lockstep multi-registry release

Checked on 2026-10-11. Versions, dates and activity come from `gh release list` and `gh api .../commits` on each repo, unless a link says otherwise. Workflow facts come from each project's `.github/workflows` on its default branch, read on the same day.

### B.1 The tools, one by one

**release-plz.** It opens a "release PR" that bumps Rust crate versions and changelogs, then publishes to crates.io, tags the commit and creates the GitHub release. `version_group` gives packages the same version, so lockstep works ([config docs](https://release-plz.dev/docs/config)). `git_only = true` versions a crate from git tags without publishing it ([config docs](https://release-plz.dev/docs/config)). With `git_release_type = "auto"`, a version such as `1.0.0-rc1` is marked as a GitHub prerelease. The docs do not explain how prerelease numbers get bumped ([config docs](https://release-plz.dev/docs/config)). It supports crates.io trusted publishing; a maintainer issue on per-crate tokens shows this ([#2401](https://github.com/release-plz/release-plz/issues/2401)). It does not build binaries. It points to a separate tag-triggered job and names cargo-dist as one option ([releasing binaries](https://release-plz.dev/docs/extra/releasing-binaries)). It handles Cargo only, not npm or PyPI. Latest is v0.3.171 (2026-10-10), with commits on 2026-10-11 ([releases](https://github.com/release-plz/release-plz/releases)). napi-rs releases its own crates with the release-plz action ([napi-rs commit](https://github.com/napi-rs/napi-rs/commits/main)).

**dist (formerly cargo-dist, axodotdev).** It plans and builds release artifacts for a Rust app. It then generates installers and writes the GitHub Actions workflow itself. Installers are shell, PowerShell, npm, Homebrew and MSI ([installers](https://axodotdev.github.io/cargo-dist/book/installers/index.html)). Its npm installer downloads the binary when the package is installed. It does not publish per-platform packages ([installers](https://axodotdev.github.io/cargo-dist/book/installers/index.html)). It has no built-in crates.io publish job ([#405](https://github.com/axodotdev/cargo-dist/issues/405), open) and no PyPI job ([#86](https://github.com/axodotdev/cargo-dist/issues/86), open since 2023). Projects add these as custom `publish-jobs`; uv does this ([uv dist-workspace.toml](https://github.com/astral-sh/uv/blob/main/dist-workspace.toml)). For lockstep, one `v{version}` tag releases the whole workspace ([cargo-release guide](https://axodotdev.github.io/cargo-dist/book/workspaces/cargo-release-guide.html)). It does not bump versions itself, and its guide points to cargo-release for that ([same guide](https://axodotdev.github.io/cargo-dist/book/workspaces/cargo-release-guide.html)). Prereleases: dist itself ships `-prerelease.N` versions ([releases](https://github.com/axodotdev/cargo-dist/releases)). uv's workflow says dist uses the Cargo SemVer version to spot prereleases ([uv release.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/release.yml)). It supports GitHub attestations and CycloneDX SBOMs through cargo-cyclonedx and cargo-auditable ([supply-chain docs](https://github.com/axodotdev/cargo-dist/blob/main/book/src/supplychain-security/index.md)). v0.33.0 (2026-09-11) added Azure Artifact Signing for Windows only ([v0.33.0 notes](https://github.com/axodotdev/cargo-dist/releases/tag/v0.33.0)). npm trusted publishing is not supported. The feature request is [#2403](https://github.com/axodotdev/cargo-dist/issues/2403), and its pull request [#2434](https://github.com/axodotdev/cargo-dist/pull/2434) has been open since 2026-06-17.
- *Maintenance status.* The repo is not archived. The last two stable releases are v0.32.0 (2026-05-22) and v0.33.0 (2026-09-11), so releases are slow. There were 100+ commits since 2026-01-01, but the most recent 30 are mostly Dependabot (18 of 30). Most of the remaining human commits are by Misty De Meo ([commits](https://github.com/axodotdev/cargo-dist/commits/main)). It has 346 open issues. I found no announcement about the company's status (shutdown, pivot or acquisition), so the state of axo as a company is **(unverified)**. Third-party package trackers only show steady crate releases ([depscope](https://mcp.depscope.dev/pkg/cargo/cargo-dist)). Astral is the biggest user, and uv's workflow now says it is "maintained manually" after first being generated by dist ([uv release.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/release.yml)). Read this as: alive, low velocity, and kept going largely by its users.

**release-please (Google).** It reads Conventional Commits, opens a release PR, then tags and creates GitHub releases. It does not publish to registries. Release types include `node`, `python` and `rust` ([manifest docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). Lockstep comes only from the `linked-versions` plugin. `cargo-workspace` and `node-workspace` only update internal dependency references ([manifest docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). Prereleases use `prerelease: true` with `prerelease-type`, plus the `prerelease` versioning strategy ([manifest docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). Latest is v17.11.2 (2026-08-24), with commits in October 2026. It has 367 open issues.

**Changesets.** Contributors add changeset files. A bot opens a "Version Packages" PR, then publishes to npm. `fixed` groups force packages to one version ([config options](https://github.com/changesets/changesets/blob/main/docs/config-file-options.md)). Biome uses `fixed` to tie `@biomejs/biome` to all its `@biomejs/cli-*` platform packages ([Biome .changeset/config.json](https://github.com/biomejs/biome/blob/main/.changeset/config.json)). Prereleases use `pre enter <tag>`, and the docs themselves warn that "Prereleases are very complicated!" ([prereleases](https://github.com/changesets/changesets/blob/main/docs/prereleases.md)). Snapshot releases cover nightly or canary builds ([config options: snapshot](https://github.com/changesets/changesets/blob/main/docs/config-file-options.md)). It is npm-centric: Cargo.toml and pyproject.toml are not versioned natively. Trusted publishing works through changesets/action ([#542 closed](https://github.com/changesets/action/issues/542)). Latest is @changesets/cli 3.0.3 (2026-09-14).

**knope.** One tool for changesets or Conventional Commits that bumps versions across ecosystems. It edits `Cargo.toml`/`Cargo.lock`, `package.json`, `pyproject.toml`, `go.mod`, `pom.xml` and more, or any file through a regex ([packages config](https://knope.tech/reference/config-file/packages/)). All `versioned_files` in one package share a single version, which is lockstep by design ([same page](https://knope.tech/reference/config-file/packages/)). `prerelease_label` creates prereleases ([PrepareRelease](https://knope.tech/reference/config-file/steps/prepare-release/)). It does not publish to registries; that stays in CI. Latest is 0.23.0 (2026-05-24). The last commit was 2026-09-15, it has 197 stars, and it is mostly run by one maintainer, so health is small but active.

**semantic-release.** Fully automatic: commit messages decide the version, and plugins publish it. It is Node-first. Cargo and PyPI support comes from community plugins **(unverified for current quality)**. It supports prerelease branches. The npm plugin supports OIDC trusted publishing, but open issues report failures on maintenance branches and with registry URLs ([#1023](https://github.com/semantic-release/npm/issues/1023), [#1066](https://github.com/semantic-release/npm/issues/1066)). Latest stable is v25.0.9 (2026-08-05). v26.0.0-beta.2 came out 2026-09-25. It has 405 open issues.

**GoReleaser.** A full build, package and publish pipeline. v2.5 (Dec 2024) added Rust (via cargo-zigbuild) and Zig builders, labelled alpha ([v2.5 post](https://goreleaser.com/blog/goreleaser-v2.5/)). The Rust page still says alpha and warns that cargo workspaces "might not work" ([Rust builds](https://goreleaser.com/customization/builds/rust)). crates.io publishing is a custom `cargo publish` publisher ([same](https://goreleaser.com/customization/builds/rust)). npm publishing is Pro-only (since v2.8) and uses a `postinstall` download, which breaks under `--ignore-scripts`. Its docs do not mention npm trusted publishing ([npm publisher](https://goreleaser.com/customization/publish/npm/)). It has no PyPI publisher in the publish list ([publish index](https://goreleaser.com/customization/publish/)). It is strong for Homebrew casks, Scoop, Winget, Docker, SBOMs, signing, attestations and nightlies ([publish index](https://goreleaser.com/customization/publish/)). Latest is v2.18.3 (2026-10-09), with nightly builds every day and only 26 open issues. It is the healthiest tool here, but Rust is a second-class citizen in it.

**cargo-release (crate-ci).** A local or CI command that bumps, commits, tags and publishes a Cargo workspace. `shared-version` gives lockstep, and `alpha`/`beta`/`rc` levels bump prereleases, e.g. `1.0.1-rc.1 -> 1.0.1-rc.2` ([reference](https://github.com/crate-ci/cargo-release/blob/master/docs/reference.md)). It handles Cargo only. Latest is v1.1.6 (2026-09-16). Health: maintained, low churn.

**git-cliff.** Only generates the changelog, from git history with templates. Rolldown runs it through `git-cliff-action` in its prepare-release PR ([Rolldown prepare-release.yml](https://github.com/rolldown/rolldown/blob/main/.github/workflows/prepare-release.yml)). Latest is v2.14.2 (2026-09-18). 12k stars, active.

**maturin `generate-ci`.** `maturin generate-ci github` writes a wheel build-and-publish workflow. `--bindings bin` packs a Rust binary into a wheel ([distribution docs](https://www.maturin.rs/distribution.html)). Setting `trusted-publishing = true` makes the workflow use `uv publish --trusted-publishing always`, and attestations are on by default ([same](https://www.maturin.rs/distribution.html)). It does not version anything. Ruff builds its PyPI wheels with `maturin-action` and `--compatibility pypi` ([Ruff build-binaries.yml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/build-binaries.yml)). uv 0.13.0 on PyPI ships `py3-none` wheels ([PyPI JSON](https://pypi.org/pypi/uv/json)). Latest is maturin v1.15.0 (2026-08-24), with commits on 2026-10-08.

**napi-rs packaging.** This is the de facto npm pattern: one root package plus one package per target, each with `os`/`cpu`/`libc`. The root lists them as exact-version `optionalDependencies` ([napi release guide](https://napi.rs/docs/deep-dive/release)). `napi pre-publish` syncs versions and publishes the platform packages, but not the root ([same](https://napi.rs/docs/deep-dive/release)). The guide warns that a multi-platform publish is not atomic and npm has no rollback. Recovery is to re-run, since versions that already exist are skipped. It also warns that `npm publish --dry-run` can still publish real platform packages ([same](https://napi.rs/docs/deep-dive/release)). The guide's template still uses `NPM_TOKEN` and only mentions trusted publishing as a swap-in option ([same](https://napi.rs/docs/deep-dive/release)). Latest is napi v3.14.2 (2026-10-06), very active.

npm trusted publishing has one catch for the per-platform pattern. A trusted publisher can only be configured on a package that already exists. The dist feature request makes this point ([#2403](https://github.com/axodotdev/cargo-dist/issues/2403)), and the same holds for crates.io ([Rust blog](https://blog.rust-lang.org/2025/07/11/crates-io-development-update-2025-07)). So every new `@scope/cli-<platform>` package needs one manual first publish. The napi guide also says the publishing identity must be allowed on the root package and on every platform package ([napi release guide](https://napi.rs/docs/deep-dive/release)).

SBOM options:
- **cargo-cyclonedx** (v0.5.9, 2026-03-19) writes a CycloneDX `bom.xml` from Cargo metadata. dist can ship it in each archive ([dist supply-chain](https://github.com/axodotdev/cargo-dist/blob/main/book/src/supplychain-security/index.md)).
- **cargo-auditable** (v0.7.7, 2026-10-02) embeds the dependency list inside the binary. dist supports it too ([same](https://github.com/axodotdev/cargo-dist/blob/main/book/src/supplychain-security/index.md)). Scanners can then read it from the shipped binary. Syft reading it is **(unverified)**.
- **syft** (v1.54.1, 2026-10-06) generates SBOMs for images and directories.
- **BuildKit** `sbom: true` attaches an SBOM to OCI images, as uv does ([build-docker.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/build-docker.yml)).
- **GoReleaser** has a built-in SBOM stage ([publish index](https://goreleaser.com/customization/publish/)).

### B.4 Complaints and pain points

- **npm `optionalDependencies` platform packages.** The long-running npm bug was that platform optional deps went missing from `package-lock.json` on reinstall. It had 307 comments and stayed open from 2022 until it was closed on 2025-04-03 ([npm/cli#4828](https://github.com/npm/cli/issues/4828)). Lockfiles produced by older npm versions may still carry the problem **(unverified)**. napi-rs users report that `pre-publish` overwrote root `optionalDependencies` ([#3206](https://github.com/napi-rs/napi-rs/issues/3206)). They also report that the CLI breaks Yarn's lifecycle-hook rules ([#3263](https://github.com/napi-rs/napi-rs/issues/3263)). Publishing is not atomic: a half-published set cannot be rolled back ([napi release guide](https://napi.rs/docs/deep-dive/release)). Rolldown adds a wait because "npm publish can succeed before npm's malware scan" makes the tarball available ([publish-to-npm.yml](https://github.com/rolldown/rolldown/blob/main/.github/workflows/publish-to-npm.yml)). Oxc has a `publish-if-needed.sh` for the same reason ([release_apps.yml](https://github.com/oxc-project/oxc/blob/main/.github/workflows/release_apps.yml)).
- **Postinstall-download npm wrappers** (dist, GoReleaser) fail under `--ignore-scripts` and offline installs ([GoReleaser npm](https://goreleaser.com/customization/publish/npm/), [dist installers](https://axodotdev.github.io/cargo-dist/book/installers/index.html)). This is why all eight leaders use per-platform packages instead.
- **release-please monorepos.** `linked-versions` fails to link when `node-workspace` forces bumps ([#2707](https://github.com/googleapis/release-please/issues/2707)). It also stops bumping after `cargo-workspace` runs ([#2558](https://github.com/googleapis/release-please/issues/2558)). Cascaded Cargo bumps ignore the prerelease window ([#2828](https://github.com/googleapis/release-please/issues/2828)). There are repeated "how do I make prereleases" issues ([#2294](https://github.com/googleapis/release-please/issues/2294), [#2515](https://github.com/googleapis/release-please/issues/2515)).
- **Changesets prereleases.** The official docs warn that mistakes lead to states that are "very hard to fix" ([prereleases](https://github.com/changesets/changesets/blob/main/docs/prereleases.md)). Publishing failures in monorepos are their own topic ([#579](https://github.com/changesets/action/issues/579), [problems-publishing-in-monorepos.md](https://github.com/changesets/changesets/blob/main/docs/problems-publishing-in-monorepos.md)).
- **dist limitations.** It has no PyPI job ([#86](https://github.com/axodotdev/cargo-dist/issues/86)), no crates.io job ([#405](https://github.com/axodotdev/cargo-dist/issues/405)), no npm OIDC ([#2403](https://github.com/axodotdev/cargo-dist/issues/2403)), and no macOS or Sigstore signing yet ([supply-chain index](https://github.com/axodotdev/cargo-dist/blob/main/book/src/supplychain-security/index.md)). Also, `--artifacts=global` produced Homebrew formulas without sha256 ([#1672](https://github.com/axodotdev/cargo-dist/issues/1672)). uv forked its generated workflow into a hand-maintained one and patches dist manifests with scripts ([uv release.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/release.yml)).
- **crates.io workspace publishing.** Ruff and uv need nightly Cargo's `-Zpublish-timeout` because the index lags during workspace publishes ([Ruff publish-crates.yml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/publish-crates.yml)). release-plz has an open bug where `wait_until_published` returns too early ([#2946](https://github.com/release-plz/release-plz/issues/2946)).
- **semantic-release and OIDC.** OIDC breaks on the first publish from a maintenance branch ([#1023](https://github.com/semantic-release/npm/issues/1023)).

### B.5 Patterns

1. **Split versioning from publishing.** A PR-based tool decides the version: Changesets (Biome), git-cliff (Rolldown), a custom tool (Oxc, Rspack, Deno) or dist plan (Ruff/uv). Hand-written, reusable per-registry jobs do the publishing. No off-the-shelf tool covers crates.io + npm platform packages + PyPI + brew + OCI from one version.
2. **Build once, publish many.** One build matrix makes artifacts. Each registry is a separate `publish-*` job, gated on all builds, with only `id-token: write`. This is uv/Ruff's shape (`publish-jobs = ["./publish-pypi", "./publish-crates"]`).
3. **Per-platform npm packages with exact-version `optionalDependencies`**, not postinstall downloads. All eight do this. Lockstep is enforced by tooling, such as Changesets `fixed` or `napi pre-publish`.
4. **OIDC everywhere it exists.** npm (2025-07-31), crates.io (2025-07-11) and PyPI (2023) are all tokenless now. Most leaders have already switched; Biome and Deno still use a crates.io token secret.
5. **Order and idempotence.** Platform packages go before the root package. Tag only after npm succeeds (Turborepo). Skip versions that already exist on re-run (napi, Oxc). Smoke-test against a local registry before the real publish (Deno with Verdaccio).
6. **Channels as npm dist-tags plus SemVer prerelease suffixes.** `nightly` (Biome), `canary` (Turborepo, Rspack), `rc`/`beta` (Rspack), `lts` (Deno). Canary builds are promoted to rc by commit hash (Deno).
7. **Supply chain.** Add `attest-build-provenance` on archives (Biome, uv via dist). Use BuildKit provenance and SBOMs on images (uv). PEP 740 attestations come free through the PyPA action. `uv publish` uploads attestations but does not create them.
8. **Homebrew is usually homebrew-core, not a tap**, once a tool is popular. A tap automated by dist or GoReleaser is the usual starting point **(unverified as a general trend)**.

**Limits** ([Actions limits](https://docs.github.com/en/actions/reference/limits)):

- A job runs for at most 6 hours on hosted runners. A workflow run lasts at most 35 days.
- Concurrent jobs: Free plan 20 in total, of which 5 macOS. Pro 40/5, Team 60/5, Enterprise 500/50. Each personal or organization account has one shared pool.
- A matrix can create at most 256 jobs per run.
- Cache: 10 GB per repository, plus 200 cache uploads per minute per repository.

**Cache changes in 2025-2026.** Since 2025-11-20 a repository cache can grow past 10 GB on a pay-as-you-go basis. The first 10 GB stay free. Raising the cap needs a Pro, Team or Enterprise account. The default retention is 7 days, and the least recently used entries are evicted first ([changelog](https://github.blog/changelog/2025-11-20-github-actions-cache-size-can-now-exceed-10-gb-per-repository/), [billing doc](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). Eviction moved from every 24 hours to hourly, and GitHub warned this "could cause additional cache thrashing" ([changelog](https://github.blog/changelog/2025-09-29-new-date-for-enforcement-of-cache-eviction-policy/)). The upload rate limit was announced on 2026-01-16 ([changelog](https://github.blog/changelog/2026-01-16-rate-limiting-for-actions-cache-entries/)).

**Pricing changes.** Hosted-runner prices fell by up to 39% on 2026-01-01. The $0.002/minute platform fee was planned for 2026-03-01 and would also have covered self-hosted runners. On 2025-12-15 GitHub postponed it with no new date. No later update appears on the page ([GitHub pricing notice](https://github.com/resources/insights/2026-pricing-changes-for-github-actions)). None of this affects public repositories on standard runners. Since 2026-01-29, arm64 standard runners also exist for private repos, with 2 vCPU instead of 4 ([changelog](https://github.blog/changelog/2026-01-29-arm64-standard-runners-are-now-available-in-private-repositories)).

**Merge queue availability.** Merge queue is available on "all public repos owned by organizations" and on Enterprise Cloud ([GA changelog](https://github.blog/changelog/2023-07-12-pull-request-merge-queue-is-now-generally-available/)). A public repo owned by a **personal account**, like `Jbmanllr/automan` today, therefore does not get it (inferred from that wording; not tested). Workflows must listen to `merge_group` or checks never start for queued PRs ([merge queue doc](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)).

**Path filters versus required checks.** When a whole workflow is skipped by `paths:` filtering, its required checks stay "Pending" and block the merge. A job skipped by an `if:` condition reports "Success" ([required checks troubleshooting](https://docs.github.com/en/enterprise-server@3.8/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)). This is why large projects compute changes in a job instead of filtering at the workflow level.

### C.4 Rust caching in CI

- **Swatinem/rust-cache** is the default in almost every sampled repo (Ruff, uv, pydantic-core, testcontainers-rs, Biome through its setup action). It caches dependencies, not workspace crates, by default. uv saves the cache only on chosen runs (`save-if`) and prunes it with a script ([uv test.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/test.yml)). Ruff disables `cache-bin` because of a macOS bug ([rust-cache #341](https://github.com/Swatinem/rust-cache/issues/341), cited in [ruff ci.yaml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/ci.yaml)).
- **Custom `actions/cache` on `target/`**: Deno restores on PRs and always saves a new entry on `main`, so PRs reuse `main`'s cache. It also bumps a `cacheVersion` number to purge ([ci.ts](https://github.com/denoland/deno/blob/main/.github/workflows/ci.ts)). Turborepo keys `target/` on lockfile and toolchain hashes ([turborepo-test.yml](https://github.com/vercel/turborepo/blob/main/.github/workflows/turborepo-test.yml)).
- **sccache with the GHA backend**: set `SCCACHE_GHA_ENABLED` plus `RUSTC_WRAPPER=sccache`. The action says versions before sccache v0.11.0 "probably will not work" ([sccache-action](https://github.com/Mozilla-Actions/sccache-action)). sccache writes many small entries, and if it hits the rate limit "the build will continue, but the storage might not be performed" ([sccache GHA doc](https://github.com/mozilla/sccache/blob/main/docs/GHA.md)). That collides with the 200 uploads/minute cap above (inference). None of the sampled leaders use sccache in CI. Ruff and uv explicitly pass `sccache: false` to `maturin-action` ([ruff build-binaries.yml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/build-binaries.yml)).
- **Complaints**: the 10 GB cap gets eaten by per-branch near-duplicates. Penumbra reached about 22 GB from active PRs and rebases ([penumbra#2460](https://github.com/penumbra-zone/penumbra/pull/2460)). Hourly eviction raises the thrashing risk ([changelog](https://github.blog/changelog/2025-09-29-new-date-for-enforcement-of-cache-eviction-policy/)). The usual fix is to save only from `main` and restore on PRs, as Deno and uv do.

### C.5 Tests that need containers and browsers

**Containers are Linux-only on hosted runners.** Docker container actions, job containers and service containers need a Linux runner: "If you are using GitHub-hosted runners, you must use an Ubuntu runner" ([service containers doc](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)). On macOS arm64 runners, Colima and Docker Desktop fail with `HV_UNSUPPORTED` because there is no nested virtualization ([runner-images #9460](https://github.com/actions/runner-images/issues/9460)). Windows runners run only Windows containers ([runner-images #1143](https://github.com/actions/runner-images/issues/1143)). The arm64 Ubuntu image does include Docker ([arm Ubuntu 24.04 image](https://github.com/actions/partner-runner-images/blob/main/images/arm-ubuntu-24-image.md)).

**How leaders handle it:**

- **Vector**, which has many sink integrations, keeps one folder per service under `tests/integration/<svc>/config/` with a `compose.yaml` and a `test.yaml`. The `test.yaml` lists the Cargo feature, the test filter, a version matrix and the trigger paths ([kafka test.yaml](https://github.com/vectordotdev/vector/blob/master/tests/integration/kafka/config/test.yaml)). CI builds one test-runner image and pushes it to GHCR. It then fans out a matrix of 36 services on `ubuntu-24.04-8core`, runs `vdev integration run <svc>`, and retries up to 3 times. All of this runs only in the merge queue or on manual dispatch, not on every PR push ([integration.yml](https://github.com/vectordotdev/vector/blob/master/.github/workflows/integration.yml)). Its AWS suite uses LocalStack **pinned by digest** ([aws compose.yaml](https://github.com/vectordotdev/vector/blob/master/tests/integration/aws/config/compose.yaml)). Windows-only integration tests use a separate path-filtered workflow ([integration_windows.yml](https://github.com/vectordotdev/vector/blob/master/.github/workflows/integration_windows.yml)).
- **testcontainers-rs** runs all CI on `ubuntu-latest` only, with no `services:` ([ci.yml](https://github.com/testcontainers/testcontainers-rs/blob/main/.github/workflows/ci.yml)).
- **Debezium** has one workflow per connector (MySQL, Postgres, MongoDB, Oracle...) plus a file-changes workflow ([workflows](https://github.com/debezium/debezium/tree/main/.github/workflows)). Its internal details were not inspected (unverified).
- **LocalStack warning.** Since LocalStack 2026.03.0 (2026-03-23), the single LocalStack for AWS image needs an auth token, including in CI. The community image is no longer maintained. Open-source projects can apply for a free licence ([LocalStack release post](https://blog.localstack.cloud/localstack-for-aws-release-2026-03-0/), [pricing post](https://blog.localstack.cloud/2026-upcoming-pricing-changes/)). Pinning an old digest, as Vector does, avoids the token but gets no security patches.

**Browsers.**

- Playwright's docs say to run `npx playwright install --with-deps`, or to use its Docker image on Linux. They advise against caching browser binaries because restoring takes about as long as downloading. They recommend one worker on CI, and sharding across jobs for scale ([Playwright CI docs](https://playwright.dev/docs/ci)).
- Playwright's own CI installs one browser per matrix cell (`browsers-to-install`). Oxc installs only Chromium (`playwright install chromium`) ([playwright tests_primary.yml](https://github.com/microsoft/playwright/blob/main/.github/workflows/tests_primary.yml), [oxc ci.yml](https://github.com/oxc-project/oxc/blob/main/.github/workflows/ci.yml)).
- Branded Chrome is missing on Linux arm64 runners; use Playwright's Chromium build there ([arm Ubuntu 24.04 image](https://github.com/actions/partner-runner-images/blob/main/images/arm-ubuntu-24-image.md)).

### C.6 Complaints and known pain points

- **macOS capacity and queues.** TomTom reported macOS queues averaging 90 minutes at peak and moved to EC2 Mac hosts ([TomTom engineering](https://engineering.tomtom.com/macos-actions-runner-cotroller/)). The macos-13 Intel runners became scarce before retirement (Apache Doris commit, secondary, unverified). The free plan allows only 5 concurrent macOS jobs ([Actions limits](https://docs.github.com/en/actions/reference/limits)).
- **macOS label churn.** `macos-13` was retired in December 2025 and `macos-14` retires on 2026-11-02 ([changelog](https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement)). Pinned macOS labels need a yearly migration.
- **Windows arm64 gaps.** Coverage instrumentation on `aarch64-pc-windows-msvc` is broken ([rust#150123](https://github.com/rust-lang/rust/issues/150123), open). PyO3 skips coverage on `windows-11-arm` because of it. Native builds can pick up the x64 Python on that runner and fail at link time (pybind11 report, unverified). Python 3.10 has no official Windows arm64 installer; 3.11 is the first (unverified).
- **Arm image ownership.** GitHub took over the arm64 images from Arm Ltd. The `partner-runner-images` repo is archived on 2026-06-12, and issues move to `actions/runner-images` ([partner-runner-images README](https://github.com/actions/partner-runner-images)).
- **Cache thrashing.** See C.4.

### Patterns

1. Use one cheap Linux job to detect changes: a `git diff` script or `dorny/paths-filter`. Skip work with job-level `if:`, never workflow-level `paths:` on required checks. Finish with an "all green" gate job that is the only required check.
2. Keep fast checks on every PR. Run the expensive matrices (all OSes, all runtimes, container integration suites) in the merge queue, on `main`, nightly, or behind a label (Vector, Deno, uv, Rolldown). Merge queue needs an org-owned public repo.
3. Build musl and arm64 natively on the free arm64 runners, or with `maturin-action` musllinux containers for Python wheels. Keep `cross` and `cargo-zigbuild` for exotic targets (riscv, s390x, FreeBSD).
4. Run every container-backed sink test on Linux runners only. Use one Compose file per service and a manifest of trigger paths, as Vector does. Pin images by digest, and plan for LocalStack's auth token.
5. On macOS and Windows, run unit tests and browser tests without containers. Install only the browsers each cell needs, and do not cache Playwright binaries.
6. Use `Swatinem/rust-cache`, saving only from `main`. sccache with the GHA backend gets no endorsement from the projects sampled.
7. Test free-threaded Python (3.14t, and 3.15t-dev) on Linux at least, and widen to all OSes in a full or nightly run (PyO3 pattern).

Checked on 2026-10-11 against primary sources, mostly the repositories themselves (read through the GitHub API) and official docs.

- **TechEmpower FrameworkBenchmarks.** Everything is in one repo: each framework, the [`toolset/`](https://github.com/TechEmpower/FrameworkBenchmarks/tree/master/toolset) runner and a `continuous` systemd service. Results do not go into git. Continuous runs are published live at [tfb-status.techempower.com](https://tfb-status.techempower.com/), and anyone can upload a `results.json` to visualize it ([README](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/README.md)). Noise example: Round 23 showed spring-mongo about 10x slower than Round 22. TechEmpower later traced it to environment and configuration, not code ([TechEmpower blog, 2026-03](https://techempower.com/blog/2026/03/16/how-our-benchmarks-led-to-a-25x-mongodb-performance-improvement/)).
- **ClickBench.** Each system has a folder in the one repo. Results are JSON in git at `<system>/results/YYYYMMDD/<machine>.json`. Older runs are kept, and the site shows the latest one ([README](https://github.com/ClickHouse/ClickBench/blob/main/README.md), e.g. [`duckdb/results`](https://github.com/ClickHouse/ClickBench/tree/main/duckdb/results)). A generated `data.generated.js` at the repo root feeds the static site (the repo has a `CNAME`). The README fixes the hardware (AWS c6a.4xlarge and later named EC2 types). It defines "true cold" and "lukewarm cold" runs. Tuned results are separate and "out of competition".
- **rustc-perf.** Benchmarks are in-repo. Third-party crates are vendored with the version in the folder name (`cargo-0.87.1`, `syn-2.0.101`) ([compile-benchmarks](https://github.com/rust-lang/rustc-perf/tree/master/collector/compile-benchmarks)). The policy is a mass update of third-party crates every three years. New versions are added before old ones are removed, and changed benchmarks get `-2`, `-3` suffixes ([README](https://github.com/rust-lang/rustc-perf/blob/master/collector/compile-benchmarks/README.md)). Results go into a Postgres (or SQLite) database ([schema.md](https://github.com/rust-lang/rustc-perf/blob/master/database/schema.md)) and are served at perf.rust-lang.org. Collectors are dedicated Hetzner machines ([deployment.md](https://github.com/rust-lang/rustc-perf/blob/master/docs/deployment.md)). Each benchmark stays on the same machine "to avoid unnecessary environment noise" ([job-queue.md](https://github.com/rust-lang/rustc-perf/blob/master/docs/job-queue.md)). The headline metric is `instructions:u` ([metrics.ts](https://github.com/rust-lang/rustc-perf/blob/master/site/frontend/src/pages/compare/metrics.ts)). Human triage reports are committed as Markdown in [`triage/`](https://github.com/rust-lang/rustc-perf/tree/master/triage).

It can also keep an `external-data-json-path` in the Actions cache ([README](https://github.com/benchmark-action/github-action-benchmark)). Its own caveats say its examples swing **±10–20%** on hosted runners. They recommend self-hosted runners. They also warn not to run it on PRs, because a PR could rewrite `gh-pages`.
- **CodSpeed.** It is a hosted service. CPU simulation runs a benchmark once and charges each instruction a cost, plus cache-miss penalties ([docs](https://codspeed.io/docs/instruments/cpu)). It is built on a Valgrind fork ([CodSpeedHQ/valgrind-codspeed](https://github.com/CodSpeedHQ/valgrind-codspeed)). Walltime mode on "Macro Runners" covers code heavy on syscalls and I/O. **Ruff** uses `cargo codspeed` in `simulation,memory` mode ([ci.yaml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/ci.yaml)). - **Bencher.** It is a hosted or self-hostable continuous-benchmarking service with statistical thresholds and alerts. It markets bare-metal runners at "<2% variance" ([README](https://github.com/bencherdev/bencher)).
- **Deno.** Benchmarks are in-repo at [`tests/bench/`](https://github.com/denoland/deno/tree/main/tests/bench). The README points to a Grafana dashboard as "new" and to deno.land/benchmarks as "old". Historical data is in a separate git repo, [denoland/benchmark_data](https://github.com/denoland/benchmark_data), which is about 3 GB and still pushed in October 2026. This shows how results-in-git grows.
- **ripgrep.** The harness is in-repo ([`benchsuite/`](https://github.com/BurntSushi/ripgrep/tree/master/benchsuite)). Raw runs are committed by date and machine name (`runs/2022-12-16-archlinux-duff`). The folder is excluded from the published crate via `exclude = ["/benchsuite/", ...]` ([Cargo.toml](https://github.com/BurntSushi/ripgrep/blob/master/Cargo.toml)).

### Patterns

- **Unit and conformance fixture servers live in the product repo** (Playwright, Scrapy, Crawlee, wpt's own `serve`). They are pinned by being in the same commit. The fixture server is moved out only when **several independent products** consume the suite, as with wpt. That split is what creates sync bots, conflict handling and rate-limit pain.
- **Agent benchmarks freeze sites as Docker images or snapshots** (WebArena, Mind2Web). Benchmarks on live sites drift and need manual upkeep (WebVoyager). Crawlee's live `crawlee.dev` e2e tests carry the same risk.
- **Results rarely stay in the main git history at scale.** Small, curated, dated JSON works in git (ClickBench, ripgrep). High-frequency CI results go to a database or service (rustc-perf, tfb-status, CodSpeed, Bencher), to CI artifacts (Playwright), or to a side repo or branch (`gh-pages`, Deno's `benchmark_data`, wpt's `results-analysis-cache`). Those side repos reach GBs.
- **Fight noise with instruction counts or dedicated hardware.** Use Valgrind-style simulation (CodSpeed, Cachegrind) or `instructions:u` for PR gating. Use dedicated machines with a fixed benchmark-to-machine mapping for wall time (rustc-perf, Bencher bare metal). Hosted runners alone give ±10–20%.
- **Version vendored fixtures explicitly** (rustc-perf's `name-version` folders and refresh policy, WebArena's dated images). Exclude harnesses from published packages (ripgrep `exclude`).


## E. R&D and archive folders

Checked on 2026-10-11 against the repositories (read through the GitHub API) and official docs.

### Separate proposal repos

- **Rust RFCs.** They live in a separate repo, [rust-lang/rfcs](https://github.com/rust-lang/rfcs). Accepted texts sit in `text/` and are rendered as a book (`book.toml`, `generate-book.py`). The README says that "once accepted, RFCs should not be substantially changed", and only minor amendments are allowed ([README](https://github.com/rust-lang/rfcs/blob/master/README.md)). Its [`.gitattributes`](https://github.com/rust-lang/rfcs/blob/master/.gitattributes) sets `*.md linguist-detectable`, so the Markdown **counts** in language stats rather than being hidden.
- **Complaint.** Users point out that RFCs drift from the shipped language and that their status is hard to tell. Threads: [Life after an RFC](https://internals.rust-lang.org/t/life-after-an-rfc/4126), [Improve format of Rust RFC, like Python PEP](https://internals.rust-lang.org/t/improve-format-of-rust-rfc-like-python-pep/20180), [Where can I check the status of all the RFCs](https://users.rust-lang.org/t/where-can-i-check-the-status-of-all-the-rfcs/54635). The forum consensus is to treat RFCs as design rationale and the Reference as normative. That is community opinion, not official policy.
- **Python PEPs.** They live in a separate repo, [python/peps](https://github.com/python/peps). [PEP 1](https://github.com/python/peps/blob/main/peps/pep-0001.rst) says that once resolved, a PEP "is considered a historical document rather than a living specification". Normative docs live elsewhere (the Language Reference, the Library Reference, the PyPA specs). This is enforced in rendering. A `canonical-doc` directive adds an "important" banner, "This PEP is a historical document", that links to the current docs ([pep_banner_directive.py](https://github.com/python/peps/blob/main/pep_sphinx_extensions/pep_processor/parsing/pep_banner_directive.py)). Its [`.gitattributes`](https://github.com/python/peps/blob/main/.gitattributes) marks `peps/*.rst linguist-detectable`.
- **Kubernetes KEPs.** They live in [kubernetes/enhancements](https://github.com/kubernetes/enhancements) under `keps/<sig>/`. Each KEP has a machine-readable `kep.yaml` with `status: provisional|implementable|implemented|deferred|rejected|withdrawn|replaced` ([template](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/kep.yaml)). Each SIG folder has its own `OWNERS` file for approvers ([sig-node/OWNERS](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/OWNERS)). The older design proposals went to a separate **archived** repo, [kubernetes/design-proposals-archive](https://github.com/kubernetes/design-proposals-archive). Its README banner says they are "**historical**" and "should not be considered up to date". Separately, [kubernetes/community](https://github.com/kubernetes/community/tree/master/archive) keeps an in-repo `archive/` folder for inactive SIGs and WGs, with a one-line README.
- **Go.** Design docs live in a separate repo, [golang/proposal](https://github.com/golang/proposal), under `design/`. The workflow (issue, then optional design doc, then accept or decline) is in its [README](https://github.com/golang/proposal/blob/master/README.md). I found no explicit "frozen" banner there (unverified).
- **TC39.** [tc39/proposals](https://github.com/tc39/proposals) is only an index of Markdown tables. It includes [`finished-proposals.md`](https://github.com/tc39/proposals/blob/main/finished-proposals.md) and [`inactive-proposals.md`](https://github.com/tc39/proposals/blob/main/inactive-proposals.md), which lists withdrawn or rejected proposals with a rationale. Each proposal has its own repo, which is archived once done. For example, [tc39/proposal-optional-chaining](https://github.com/tc39/proposal-optional-chaining) has `archived: true`.
- **Swift Evolution.** It lives in a separate repo, [swiftlang/swift-evolution](https://github.com/swiftlang/swift-evolution). Each proposal has a header line such as `Status: **Implemented (Swift 2.2)**` ([SE-0001](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0001-keywords-as-argument-labels.md)). Its [`.gitattributes`](https://github.com/swiftlang/swift-evolution/blob/main/.gitattributes) sets `*.md linguist-detectable=true` and `linguist-documentation=false`.

### In-repo design folders, frozen or archived

- **CockroachDB `docs/RFCS/`.** This is an in-repo, date-prefixed RFC folder (`20150720_schema_gossip.md`). Each file has a `Status:` header. The folder is now **frozen**: its README begins "This review process is deprecated. Existing docs are left for archival purposes" and points to an internal wiki ([README](https://github.com/cockroachdb/cockroach/blob/master/docs/RFCS/README.md)). [CODEOWNERS](https://github.com/cockroachdb/cockroach/blob/master/.github/CODEOWNERS) assigns `/docs/RFCS/` to `@cockroachdb/rfc-prs`.
- **Vector `rfcs/`.** This is an in-repo RFC folder with a process README ([rfcs/README.md](https://github.com/vectordotdev/vector/blob/master/rfcs/README.md)). It is hidden from language stats with `rfcs/* linguist-detectable=false`, alongside `docs/*`, `website/*` and `soaks/*` ([.gitattributes](https://github.com/vectordotdev/vector/blob/master/.gitattributes)).
- **open-constructs/cdk-terrain** marks `docs/** linguist-documentation` and generated files `linguist-generated=true` ([.gitattributes](https://github.com/open-constructs/cdk-terrain/blob/main/.gitattributes)).

### Keeping such folders out of packages and CI

- **Source archives.** Protobuf uses `compatibility/ export-ignore` in [`.gitattributes`](https://github.com/protocolbuffers/protobuf/blob/main/.gitattributes) so that `git archive` tarballs skip the folder.
- **Crates.** ripgrep's [Cargo.toml](https://github.com/BurntSushi/ripgrep/blob/master/Cargo.toml) uses `exclude = [... "/benchsuite/", "/scripts/" ...]`. regex and hyper use an `include = [...]` allow-list instead ([regex](https://github.com/rust-lang/regex/blob/master/Cargo.toml), [hyper](https://github.com/hyperium/hyper/blob/master/Cargo.toml)). With an allow-list, a new R&D folder cannot leak into a published crate by accident.
- **CI path filters.** Biome gates its benchmark job with `paths:` and `dorny/paths-filter` ([benchmark.yml](https://github.com/biomejs/biome/blob/main/.github/workflows/benchmark.yml)). Scrapy's walltime benchmarks run only for PRs that touch measured paths ([codspeed-walltime.yml](https://github.com/scrapy/scrapy/blob/master/.github/workflows/codspeed-walltime.yml)). A GitHub code search for `paths-ignore` naming `rfcs/` or `design/` found no notable example. Most projects filter CI by what to run (allow-list `paths:`) rather than by what to ignore (unverified that none exist).

### Patterns

- **Large multi-team projects keep proposals in a separate repo** (Rust, Python, Kubernetes, Go, TC39, Swift). The gain is a separate review cadence and permissions, and no noise in the code repo. The cost is drift from the implementation (the Rust complaints). **Single-product repos keep them in-repo** (CockroachDB, Vector).
- **Mark normativity explicitly.** The strongest pattern is Python's: one rule that resolved documents are historical, plus a rendered banner that links to the canonical doc. The light version is a one-line README banner (CockroachDB, the Kubernetes archive repo) or a `Status:` header per file (CockroachDB, Swift, KEP `kep.yaml`).
- **Freeze, do not delete.** Retired material is either left in place with a "deprecated / archival" README (CockroachDB, kubernetes/community `archive/`) or moved to a GitHub-archived read-only repo (kubernetes/design-proposals-archive, TC39 proposal repos).
- **Ownership is set by path.** Use CODEOWNERS or `OWNERS` per folder (CockroachDB `/docs/RFCS/`, KEP per-SIG `OWNERS`).
- **Packaging and stats hygiene uses three cheap levers.** `.gitattributes` with `linguist-detectable=false` or `linguist-documentation` hides prose from language stats (Vector, cdk-terrain). Note that docs-only repos do the opposite to make prose count (rfcs, peps). `export-ignore` keeps folders out of `git archive` (Protobuf). A Cargo `include` allow-list or `exclude` keeps folders out of crates (regex, hyper, ripgrep). CI exclusion is usually done with `paths:` allow-lists on the jobs that matter, not with `paths-ignore` on R&D folders.
