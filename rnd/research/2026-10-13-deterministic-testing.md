# Deterministic time, randomness, storage and OS services in a multi-process Tokio system

Research for [#264](https://github.com/Jbmanllr/automan/issues/264), feeding [#274](https://github.com/Jbmanllr/automan/issues/274) (injection and determinism) and [#275](https://github.com/Jbmanllr/automan/issues/275) (simulation and crash testing) on the map [#262](https://github.com/Jbmanllr/automan/issues/262). Gathered on 2026-10-13 from official docs, source code at named versions or tags, project READMEs and issue trackers. Crate versions are the latest on crates.io that day. "Fit for Goodfetch" notes are analysis, kept apart from the facts.

## Question

How do mature Rust and Tokio systems make time, randomness, storage, network and OS services replaceable in tests, test distributed and crash behaviour deterministically, and isolate test data? Which approaches fit Goodfetch: an engine binary and a Daemon driven by SDK Clients over JSON-RPC, SQLite run state, work-item leases and run epochs (ADR 0003), Daemon groups over mutual TLS (ADR 0055), and a Valkey Politeness store (ADR 0053)?

## Summary: the facts a decision rests on

1. **Tokio's paused clock covers only `tokio::time` inside one current-thread runtime.** `pause` "only affects the `Instant` type in Tokio, and the `Instant` in std continues to work as normal", needs the current-thread runtime, and panics elsewhere (tokio 1.53.2 source). It never touches `SystemTime`, other processes, Chromium, or the Valkey server. Auto-advance jumps to the next timer whenever the runtime is idle, including while it waits on real sockets or child processes. Users have asked for an opt-out since 2022 (tokio #4522, #6113, both open). A running `spawn_blocking` task holds auto-advance back (merged December 2022).
2. **Cross-process time control is done with a test-only control channel or environment settings, not with LD_PRELOAD.** Temporal ships a test-only `TestService` RPC that skips time. Neon configures failpoints in its running processes over HTTP, in builds made with a `testing` Cargo feature. Cargo's own test suite passes `__CARGO_TEST_FIXED_RETRY_SLEEP_MS=1` to the binary. libfaketime "cannot work with statically linked binaries", and Goodfetch's Linux binary is static musl (ADR 0024).
3. **Wall time has no local stand-in, so projects inject it.** Materialize passes a `NowFn` closure and has a `NOW_ZERO` for tests. TigerBeetle passes a `Time` interface with `monotonic` and `realtime`. rustls takes a `TimeProvider` for certificate checks. Quickwit's actor `Universe::with_accelerated_time()` advances time only when no actor is busy.
4. **Seeded randomness must cover hidden sources.** `StdRng` output is "non-portable" across rand versions (rand 0.10.3). std `HashMap` is "randomly seeded". S2, madsim and Amazon's ShardStore each name hash-map order as a source of nondeterminism. madsim reads `MADSIM_TEST_SEED`, turmoil takes `Builder::rng_seed`, and proptest takes `PROPTEST_RNG_SEED` and keeps failing cases in regression files.
5. **Every Rust simulator runs a single process.** turmoil 0.7.2 runs many simulated hosts on one thread with simulated `tokio::net`, plus an unstable simulated `std::fs`. madsim 0.2.34 replaces tokio under `--cfg madsim` and overrides libc's `clock_gettime` and `getrandom`; its last release was 2025-10-11. Shuttle and loom check thread interleavings. None of them runs Chromium, sink processes, Script sandbox workers or SQLite's own C file I/O. Antithesis runs whole Linux x86-64 containers deterministically as a paid service. etcd's robustness table credits it with three of etcd's 2025 bugs.
6. **Power-cut testing needs a layer that drops unsynced writes.** SQLite tests itself through a crash VFS that reorders and corrupts unsynced writes, then checks `integrity_check`. LazyFS (FUSE, Linux) "only flushes data if explicitly requested", and etcd's robustness tests use it. dm-log-writes (Linux kernel, root) replays writes in flush order. `kill -9` tests only a process crash, since the OS page cache survives. Only failpoints, `kill`, and a VFS shim inside the process run on all three OSes.
7. **Real OS services run on GitHub-hosted runners, with caveats.** keyring-rs tests the macOS Keychain and the Windows Credential Manager as they are, and starts and unlocks `gnome-keyring` on Ubuntu. service-manager-rs runs real systemd user and system units, launchd agents, `sc.exe` and WinSW in CI. Docker service containers need an Ubuntu runner. Valkey "is not officially supported on Windows".
8. **Isolation rules from the leaders:** one process per test (nextest's default). In Rust 2024, `std::env::set_var` is `unsafe`, so environment changes go to child processes through `Command::env`. Servers bind port 0 and report the port back (nextest docs, Oxide's `port-file`). Temporary homes and an explicit data-root override, since `dirs` reads Known Folders on Windows. Per-test certificate authorities with rcgen. Per-slot resources keyed on `NEXTEST_TEST_GLOBAL_SLOT`.

## 1. Time

### Facts

**Tokio's paused clock** (tokio 1.53.2, released 2026-10-03; source `tokio/src/time/clock.rs` at tag `tokio-1.53.2`):

- `pause()`: "The current value of `Instant::now()` is saved and all subsequent calls to `Instant::now()` will return the saved value… This only affects the `Instant` type in Tokio, and the `Instant` in std continues to work as normal." "Pausing time requires the `current_thread` Tokio runtime. This is the default runtime used by `#[tokio::test]`." It panics "if called from outside of a `current_thread` Tokio runtime". `Builder::start_paused` panics at construction on the multi-thread runtime ([source](https://github.com/tokio-rs/tokio/blob/tokio-1.53.2/tokio/src/time/clock.rs), [builder](https://github.com/tokio-rs/tokio/blob/tokio-1.53.2/tokio/src/runtime/builder.rs)).
- `start_paused` "requires the `test-util` feature" ([tokio-macros](https://github.com/tokio-rs/tokio/blob/master/tokio-macros/src/lib.rs)).
- **Auto-advance:** "If time is paused and the runtime has no work to do, the clock is auto-advanced to the next pending timer." "When a blocking task is running, the clock's auto-advance is temporarily inhibited" ([PR #5115](https://github.com/tokio-rs/tokio/pull/5115), merged 2022-12-17, fixing [#4614](https://github.com/tokio-rs/tokio/issues/4614)).
- **`advance(d)`** jumps in one step: timers due before the new time "complete 'at the same time', and the runtime is free to poll them in any order". The docs advise `sleep` with auto-advance rather than `advance` for "forcing timeouts" and "simulating freezes".
- **Complaints:** [#4522](https://github.com/tokio-rs/tokio/issues/4522) (open since 2022-02) says that mixing I/O with timers makes auto-advance "quite unpredictable"; [#6113](https://github.com/tokio-rs/tokio/pull/6113) (open) proposes a flag to turn it off. [#8232](https://github.com/tokio-rs/tokio/issues/8232) (open, 2026-06) reports `timeout` under `start_paused` firing early after an upgrade from 1.49 to 1.50, in tests that use real sockets and files. [#5423](https://github.com/tokio-rs/tokio/issues/5423) (open) reports paused-time results that differ slightly between macOS and Linux.
- **Select order:** `Builder::rng_seed` makes "the order that branches are polled" in `tokio::select!` deterministic. It needs `--cfg tokio_unstable`, and repeatability also needs the same Tokio, dependency and compiler versions (builder source above).

**Controlling time across processes:**

- **Test-only control channel.** Temporal's test server exposes `TestService` ("supported only by the Temporal Test Server", "EXPERIMENTAL") with `LockTimeSkipping`, `UnlockTimeSkipping`, `Sleep`, `SleepUntil` and `GetCurrentTime`. While unlocked it fast-forwards the server's time, and SDKs drive it over gRPC from another process ([service.proto](https://github.com/temporalio/sdk-java/blob/master/temporal-test-server/src/main/proto/temporal/api/testservice/v1/service.proto)). Neon's pytest suite reconfigures failpoints in running pageservers and safekeepers through an HTTP endpoint that refuses if "compiled without failpoints support". The tests need `--features testing` ([test_runner README](https://github.com/neondatabase/neon/blob/main/test_runner/README.md)).
- **Environment and settings.** Cargo's test harness starts the `cargo` binary with `__CARGO_TEST_FIXED_RETRY_SLEEP_MS=1` ("Set retry sleep to 1 millisecond"), among other test-only variables ([cargo-test-support](https://github.com/rust-lang/cargo/blob/master/crates/cargo-test-support/src/lib.rs)). The `faketime` crate (0.2.1, last pushed 2021-05-19) reads a fake Unix time from a file named by `FAKETIME=path` in a binary ([README](https://github.com/nervosnetwork/faketime)).
- **libfaketime** (v0.9.13, 2026-08-31, GPL-2.0) "cannot work with statically linked binaries or binaries that have the setuid-flag set". Runtimes that "use vDSO/direct system calls" bypass it. JVMs need `FAKETIME_DONT_FAKE_MONOTONIC`. On macOS it uses `DYLD_INSERT_LIBRARIES` ([README](https://github.com/wolfcw/libfaketime/blob/master/README)). Under the hardened runtime, which notarization needs (ADR 0039), dyld reads `DYLD_` variables only with the `com.apple.security.cs.allow-dyld-environment-variables` entitlement ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-dyld-environment-variables)).
- **The browser's clock.** CDP `Emulation.setVirtualTimePolicy` (experimental) replaces "real-time with a synthetic time source" for all frames, with policies `advance`, `pause` and `pauseIfNetworkFetchesPending` and an `initialVirtualTime` ([browser_protocol.json](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)). Playwright's `Clock` (since v1.45) overrides `Date`, `Temporal.Now`, timers and `performance` for a whole BrowserContext ([clock.md](https://github.com/microsoft/playwright/blob/main/docs/src/clock.md)).
- **Competitors.** Crawlee uses Vitest fake timers in five test files, including `autoscaled-pool` and `throttling-request-manager`. Scrapy uses Twisted's `Clock()` in one. spider-rs has no `start_paused` (code search, 2026-10-13).

### Fit for Goodfetch

- **Leases (ADR 0003)** are judged on the monotonic clock. When the lease code reads `tokio::time::Instant`, the paused clock covers in-process tests. They must run on the current-thread runtime, and no real socket or child-process wait may let auto-advance expire a lease early (#4522, #8232). SQLite work through the owner's tracked `spawn_blocking` holds auto-advance back.
- **Schedules (ADR 0036)** need wall time in an IANA zone, which the paused clock does not cover. croner 4.0.1 computes occurrences from an explicit start (`find_next_occurrence(&time, …)`, `iter_from`), so the DST conformance cases need no clock at all. Only the loop that sleeps until the next occurrence needs one. Under STYLE.md's own rule, a wall clock has no local stand-in, so an injected wall-time source would count as the second adapter, as `NowFn`, TigerBeetle's `Time` and rustls's `TimeProvider` do.
- **Binary-level tests** (an Attached engine or a Daemon under an SDK, a Daemon group) cannot share a paused clock. libfaketime is ruled out for the static musl binary and signed macOS builds. That leaves area 3's "short durations through settings" (Cargo's pattern) and, where a test must cross a long interval such as a Schedule's next day or a lease expiry at its default, a test-only control operation (Temporal's pattern). It would be compiled or enabled only in test builds, as Neon gates its endpoint.
- **The Script sandbox (ADR 0051)** keeps `Date.now` and `Math.random` live by design, so tests that need a fixed time cannot get one from inside a script. They can only assert on the order of Effects, which is what ADR 0051 compares.
- **Chromium** keeps its own clock. CDP virtual time and Playwright's Clock are the browser-side levers if a Proving ground case needs page time to move.

## 2. Randomness

### Facts

- **rand 0.10.3:** `StdRng` is "Non-portable: any future library version may replace the algorithm and results may be platform-dependent. (For a portable version, use the chacha20 crate directly.)" It is ChaCha12 today, and "even with a fixed seed, output is not portable" ([std.rs](https://github.com/rust-random/rand/blob/0.10.3/src/rngs/std.rs)).
- **std `HashMap`:** "The algorithm is randomly seeded… each `HashMap` instance uses a different seed" ([map.rs](https://github.com/rust-lang/rust/blob/master/library/std/src/collections/hash/map.rs)). Amazon's ShardStore paper names this: "the default hash algorithm for HashMap types in Rust is randomized and so the iteration order of a map's contents varies across runs" ([SOSP 2021](https://cdn.amazon.science/77/5e/4a7c238f4ce890efdc325df83263/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3-2.pdf)). madsim issue [#240](https://github.com/madsim-rs/madsim/issues/240) (open) reports that "std HashSet is not deterministic on repeated simulation runs".
- **Seeds that reproduce a failure:**
  - madsim reads `MADSIM_TEST_SEED` (default: seconds since the epoch), `MADSIM_TEST_NUM` (the seed increases by one per run) and `MADSIM_TEST_CHECK_DETERMINISM` ("run at least twice with the same seed") ([builder.rs](https://github.com/madsim-rs/madsim/blob/main/madsim/src/sim/runtime/builder.rs)). Issue [#217](https://github.com/madsim-rs/madsim/issues/217) (open) asks how to recover the seed when cargo-nextest kills a test on timeout.
  - turmoil's simulation RNG "is randomly seeded. To make your tests deterministic, you can provide your own seed through `Builder::rng_seed`". It also seeds each host's Tokio runtime under `tokio_unstable` ([builder.rs](https://github.com/tokio-rs/turmoil/blob/v0.7.2/src/builder.rs), [rt.rs](https://github.com/tokio-rs/turmoil/blob/v0.7.2/src/rt.rs)).
  - proptest 1.12.0 reads `PROPTEST_RNG_SEED`, a random seed by default. It persists failing cases through `FileFailurePersistence` unless `PROPTEST_DISABLE_FAILURE_PERSISTENCE` is set ([config.rs](https://github.com/proptest-rs/proptest/blob/main/proptest/src/test_runner/config.rs)).
  - TigerBeetle's VOPR replays "the seed and Git commit hash" ([vopr.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)). Turso's `thesis` runner prints `thesis: reproduce with: … --seed 42 --steps 57` ([testing/antithesis](https://github.com/tursodatabase/turso/blob/main/testing/antithesis/README.md)).
  - S2 checks determinism with a CI "meta test" that reruns a seed and compares TRACE-level logs. It overrides `getrandom`, `getentropy` and macOS's `CCRandomGenerateBytes` through mad-turmoil, and also calls `fastrand::seed` ([S2 blog, 2025-04-02](https://s2.dev/blog/dst); [mad-turmoil](https://github.com/s2-streamstore/mad-turmoil)).
- **Antithesis** replaces `/dev/random` and `/dev/urandom` with platform entropy and discourages in-process PRNGs that are never reseeded ([environment docs](https://antithesis.com/docs/environment/the_antithesis_environment/)).
- **Valkey and Redis Lua:** since Redis 5, scripts replicate by effects, and verbatim replication is gone in 7.0. In that mode "you can… use the TIME or SRANDMEMBER commands inside your scripts freely", and "The Lua PRNG in this mode is seeded randomly on every call" ([Redis docs](https://redis.io/docs/latest/develop/programmability/eval-intro/)). Valkey's page confirms effects replication and the 7.0 removal ([Valkey](https://valkey.io/topics/eval-intro/)).

### Fit for Goodfetch

- The places where Goodfetch needs randomness include a Schedule's fixed jitter (ADR 0036, "the same delay at every occurrence"), backoff jitter, Session pool picks and fingerprint seeds (area 3 story 62). A seed held in run state reproduces a run on any machine only with a portable generator (`chacha20`), not `StdRng`.
- A printed seed reproduces a failure only if every other source is fixed: `HashMap` order in anything that reaches output or ordering, `select!` branch order (unstable `rng_seed`), and thread scheduling. Printing the seed when the test starts, not only when it fails, covers nextest timeouts (madsim #217).
- The Script sandbox's `Math.random` and `crypto.getRandomValues` stay live (ADR 0051). Seeding them is outside what ADR 0051 compares.

**Prior art outside Rust:**

- **FoundationDB:** "deterministic simulation of an entire FoundationDB cluster within a single-threaded process", built into its Flow runtime. It runs "tens of thousands of simulations every night", at about "a 10-1 factor of real-to-simulated time" ([Simulation and Testing, 8.0.0 docs](https://apple.github.io/foundationdb/testing.html)).
- **TigerBeetle VOPR:** "all non-deterministic parts of the system are stubbed out. This includes the clock, network, and disk operations". A failing run replays from "the seed and Git commit hash" ([vopr.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)).
- **Turso** (Rust rewrite of SQLite) owns its storage engine and has its own seeded simulator with `--seed` and `--doublecheck` (run the plan twice and compare), plus `testing/unreliable-libc` ([simulator README](https://github.com/tursodatabase/turso/blob/main/testing/simulator/README.md)).
- **Amazon ShardStore** (SOSP 2021, over 40,000 lines of Rust) uses property-based tests against reference models. It adds a `DirtyReboot` operation for crash states, Loom for small primitives, and Shuttle for larger harnesses ([paper](https://cdn.amazon.science/77/5e/4a7c238f4ce890efdc325df83263/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3-2.pdf), §§4–6).

### Fit for Goodfetch

- The logic of ADR 0003 (leases, run epochs, compare-and-set at the destination), ADR 0055 (Lead Daemon, peer link) and ADR 0053 (permits, heartbeats, granted shares) can run under turmoil only if the code reaches the network and time through types that can be swapped. That is the STYLE.md "Remote but owned" category, tested through an in-memory adapter of the protocol. turmoil is Tokio's own and actively maintained. madsim's runtime swap and crate patches touch every Tokio dependency, and its releases have slowed.
- None of these tools covers the real binary with Chromium, sink processes and Script sandbox workers. Only Antithesis or Hermit run real processes deterministically, and both are Linux x86-64 only.
- loom and Shuttle fit small concurrency primitives (the Politeness file's permit accounting in one process, the governor). `--cfg loom` and `--cfg madsim` are custom `cfg`s, which STYLE.md allows when declared for `unexpected_cfgs`. Shuttle's switch is a Cargo feature, which STYLE.md limits to the `goodfetch` crate.

## 4. Crash and power-cut testing of SQLite-backed state

### Facts

- **SQLite's own crash tests** ([testing.html](https://sqlite.org/testing.html)): "crash testing is done in simulation. An alternative Virtual File System is inserted that allows the test harness to simulate the state of the database file following a crash." In the TCL harness a child process "randomly crashes somewhere in the middle of a write operation". A special VFS "randomly reorders and corrupts the unsynchronized write operations to simulate the effect of buffered filesystems". The parent then checks that the change "either completed successfully or else were completely rolled back" with `PRAGMA integrity_check`. TH3 snapshots an in-memory VFS after N I/O operations and adds "random file damage". Compound tests stack an I/O error or OOM during recovery from a crash. The crash VFS is `src/test6.c`: writes go to an in-memory write-list until a sync ([test6.c](https://github.com/sqlite/sqlite/blob/master/src/test6.c)). A "journal-test VFS" checks nothing reaches the database before the journal is synced.
- **Rust crates to build a VFS:** `sqlite-plugin` 0.11.0 (2026-07-21, "building a custom SQLite virtual file system") and `sqlite-vfs` 0.2.0 (2022-07-08).
- **LazyFS** 0.3.1 (2026-05-07): "A FUSE file system with an internal dedicated page cache that only flushes data if explicitly requested by the application. This is useful for simulating power failures and losing unsynced data." It was tested on ext4 under Debian 11 and Ubuntu 20.04 and needs FUSE 3 and `user_allow_other`. Faults go through a named pipe: `clear` the cache, torn writes ([README](https://github.com/dsrhaslab/lazyfs); VLDB 2024 paper co-authored by Kyle Kingsbury). etcd builds LazyFS 0.2.0 for its robustness tests ([Makefile](https://github.com/etcd-io/etcd/blob/main/Makefile), [lazyfs.go](https://github.com/etcd-io/etcd/blob/main/tests/framework/e2e/lazyfs.go)).
- **dm-flakey:** a device-mapper target that is available for `<up interval>` seconds, then for `<down interval>` errors, drops writes (`drop_writes`) or corrupts bytes ([kernel docs](https://www.kernel.org/doc/html/latest/admin-guide/device-mapper/dm-flakey.html)). **dm-log-writes** logs writes "in order of completion once we are sure the write is no longer in cache… to simulate the worst case scenario with regard to power failures" for replay ([log-writes.rst](https://github.com/torvalds/linux/blob/master/Documentation/admin-guide/device-mapper/log-writes.rst)). Both need a Linux block device and root.
- **Failpoints:** `fail` 0.5.1 (2022-10-08; commits through 2026-07-20; TiKV). "Fail points are disabled by default and can be enabled via the `failpoints` feature. When failpoints are disabled, no code is generated by the macro." They are configured by `FAILPOINTS=name=action` or `fail::cfg`. "Fail points are global resources, and Rust tests run in parallel", so tests hold `FailScenario`, and the docs advise "all fail point unit tests into their own binary" ([lib.rs](https://github.com/tikv/fail-rs/blob/master/src/lib.rs)). Neon adds an `exit` action "to immediately kill the process" and a pausable failpoint. etcd uses `gofail` failpoints plus `kill` ([robustness/failpoint](https://github.com/etcd-io/etcd/tree/main/tests/robustness/failpoint)).
- **`kill -9`:** `Child::kill` "is equivalent to sending a SIGKILL on Unix platforms" ([process.rs](https://github.com/rust-lang/rust/blob/master/library/std/src/process.rs)). A process crash leaves the OS page cache intact, which is why SQLite and LazyFS model buffered writes separately.
- **Turmoil's unstable fs:** "Writes go to a pending buffer and become durable on `sync_all()` or randomly"; `Sim::crash` discards pending writes. It mirrors `std::fs` and `std::os::unix::fs` ([lib.rs v0.7.2](https://github.com/tokio-rs/turmoil/blob/v0.7.2/src/lib.rs)).
- **History checkers:** Jepsen runs "a Clojure program on a control node" that drives the system's machines over SSH ([README](https://github.com/jepsen-io/jepsen)). Elle checks transactional anomalies "based purely on client observations" ([README](https://github.com/jepsen-io/elle), EPL-2.0). Porcupine (Go, MIT) checks linearizability, and etcd's robustness suite uses it (v1.3.1 in [tests/go.mod](https://github.com/etcd-io/etcd/blob/main/tests/go.mod)). Rust's stateright 0.31.0 (2025-07-27) has "a linearizability tester that can be run within the model checker". Garage runs Jepsen on VirtualBox VMs with clock-scramble and partition nemeses.
- **ShardStore's crash checks:** `DirtyReboot(RebootType)` in property tests, checking persistence and forward progress. The block-level variant "has not found additional bugs and is dramatically slower".

**What runs where** (GitHub-hosted runners; image readmes of 2026-09/10):

| Technique | Linux | macOS | Windows | What it proves |
|---|---|---|---|---|
| `kill -9` / `TerminateProcess` loop | yes | yes | yes | process-crash recovery, journal replay, epoch handling |
| Failpoints (`fail`, exit or panic at a named point) | yes | yes | yes | recovery from a crash at exact points |
| SQLite VFS shim dropping or reordering unsynced writes | yes | yes | yes | power-cut behaviour of the SQLite file as SQLite sees it, in-process |
| LazyFS | yes (FUSE 3; runner availability unverified) | no (FUSE needs macFUSE) | no | unsynced data lost below a real process |
| dm-flakey, dm-log-writes | yes, with root (runner availability unverified) | no | no | block-level flush ordering |
| Jepsen, Porcupine, Elle | Linux machines or containers | no | no | histories from many Clients |
| Antithesis | hosted, x86-64 | no | no | everything above, deterministic |

### Fit for Goodfetch

- ADR 0002's "an acknowledged commit survives a power cut" is a claim about `synchronous=FULL` reaching the disk. A VFS shim (SQLite's method, built with `sqlite-plugin`) tests it on every OS in-process. LazyFS tests it on Linux below a real engine process, as etcd does. `kill -9` alone tests only the opt-in fast mode's promise ("surviving a process crash only").
- None of these tools can check that macOS `fullfsync` reaches the drive's cache. They model the page cache, not the drive. A test can assert the pragma is set.
- The `fail` crate's switch is a Cargo feature on the dependency (`fail/failpoints`) plus a global registry. Under nextest's process per test, the registry is per test process. A crash point in a real binary needs either a test build, as Neon and etcd use, or a setting.
- ADR 0003's conformance test "runs two copies of one run against such a store". Recording each commit attempt with its epoch and checking the history (Porcupine-style, or stateright in Rust) is the established way to judge it.

### Fit for Goodfetch

- **Secret providers** (ADR 0015): a mock store exists, and the real keychains are testable on all three hosted runners, with `gnome-keyring` started on Linux. The OS keychain is user-global, so parallel tests that touch it need a test group or unique service names.
- **Daemon install** (systemd user units, launchd agents, Windows services): service-manager-rs shows each runs on hosted runners, with sudo for system scope.
- **Environment and home folders:** with `set_var` unsafe and `unsafe_code` denied, tests reach the environment only through child processes or through an explicit environment value passed into the settings resolver (ADR 0028). On Windows, `dirs` ignores per-test environment for Known Folders (see Unverified), so per-test isolation of the per-user data, Run index, Usage ledger, Politeness file and browser cache needs an explicit data-root override. ADR 0024 already has `GOODFETCH_ENGINE_PATH` and `GOODFETCH_BROWSERS_PATH`.
- **Local addresses** (ADR 0044) are the one network case that needs extra interfaces. Namespaces work on Linux with sudo. macOS and Windows need loopback aliases (see Unverified).

## 6. Isolation under parallel test processes

### Facts

- **One process per test:** nextest "runs each test in a separate process… now, and will always be, process-per-test", so "test authors and libraries don't need to coordinate global state usage" ([why-process-per-test](https://github.com/nextest-rs/nextest/blob/main/site/src/docs/design/why-process-per-test.md); cargo-nextest 0.9.148, 2026-10-08).
- **Slots:** `NEXTEST_TEST_GLOBAL_SLOT` (since 0.9.90) is unique within the run while the test lives and is reused afterwards. `NEXTEST_TEST_GROUP_SLOT` works within a test group ([env-vars](https://github.com/nextest-rs/nextest/blob/main/site/src/docs/configuration/env-vars.md)). Test groups (since 0.9.48) act as "logical semaphores and mutexes"; nextest's process model "does not support" in-process mutexes ([test-groups](https://github.com/nextest-rs/nextest/blob/main/site/src/docs/configuration/test-groups.md)). Setup scripts are still experimental ([setup-scripts](https://github.com/nextest-rs/nextest/blob/main/site/src/docs/configuration/setup-scripts.md)).
- **Ports:** nextest says a group around a fixed port "is not the 'correct' way". "Use a randomly assigned port… by binding to port 0", and pass the bound port back. For another process, use Oxide's `port-file` 0.1.0 ("without racy port probing"), or "bind to a Unix domain socket in a temporary directory. This approach also works on Windows". Neon's pytest fixture probes a port with `can_bind` and then hands it to a child ([port_distributor.py](https://github.com/neondatabase/neon/blob/main/test_runner/fixtures/port_distributor.py)). The port can be taken between the probe and the bind.
- **Temporary folders:** `tempfile` 3.27.0's `TempDir` and `NamedTempFile` "rely on Rust destructors" and leak "if the process exits through an unhandled signal" ([lib.rs](https://github.com/Stebalien/tempfile/blob/master/src/lib.rs)).
- **Per-test certificate authorities:** `rcgen` 0.14.10 (rustls org) builds certificates with `self_signed` and `signed_by`, with `not_before` and `not_after` defaulting to 1975 and 4096 ([certificate.rs](https://github.com/rustls/rcgen/blob/main/rcgen/src/certificate.rs)). rustls's `TimeProvider` sets the wall time used to judge expiry.
- **Containers:** `testcontainers` 0.28.0, with `testcontainers-modules` 0.15.0 features `valkey`, `redis`, `postgres`, `minio` and `localstack`. GitHub: "If your workflows use Docker container actions, job containers, or service containers, then you must use a Linux runner… you must use an Ubuntu runner" ([docs](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)). The `macos-26-arm64` image lists no Docker. `Windows2025` lists Docker 29.7.2 for Windows containers. `Ubuntu2404` lists Docker 28.0.4 and Podman 4.9.3 ([runner-images](https://github.com/actions/runner-images/tree/main/images)). Valkey: "not officially supported on Windows… for development using WSL"; on macOS through Homebrew or MacPorts ([installation](https://valkey.io/topics/installation/)).
- **Server-side time in the store:** redis-cell, which ADR 0053 names as its GCRA reference, takes "now" from `OffsetDateTime::now_utc()` inside the Redis server process ([store.rs](https://github.com/brandur/redis-cell/blob/master/src/cell/store.rs)). Key expiry is also server time.

### Fit for Goodfetch

- **Per test:** a temporary data root holding the run folders, Run index, Usage ledger and Politeness file. Each test's own SQLite files (STYLE.md's stand-in) need no trait.
- **Per process:** listeners on port 0 reported back to the Client, or Unix sockets and named pipes in the test's folder, the transport ADR 0053 already uses for wake endpoints. The Proving ground, the Daemon's HTTP listener and the ops listener all follow this.
- **Per test, for a Daemon group (ADR 0055):** a group certificate authority made by the product's own `goodfetch group init` into the temporary folder. Certificate-renewal tests need a wall-time source (rustls `TimeProvider`).
- **Per test, for Valkey (ADR 0053):** one Valkey per CI job, as a container on Ubuntu or Homebrew on macOS, with a namespace per test (ADR 0053 already scopes by namespace) or per nextest slot. Windows has no supported Valkey. Area 3's "a real Valkey container" holds only on Linux runners.
- **Time in the store:** GCRA deadlines and permit expiry come from the Valkey server's clock, not the engine's. A paused engine clock does not reach them, which bears on whether the Lua script uses `TIME` or a time the engine passes in.

## Bearing on the existing text (analysis)

- **STYLE.md, "Concrete types first; a trait only where two adapters exist":** the facts support it for SQLite, folders and ports, where a temporary stand-in exists, and for monotonic time inside one runtime (the paused clock). Wall time, the browser's clock and the Valkey server's clock have no local stand-in. The projects above inject a clock handle for wall time.
- **Area 3, "Time-dependent cases set short durations through settings rather than mocking clocks":** this is Cargo's practice and works across processes. It cannot reach a Schedule's day-long interval, DST dates, or a lease at its default length. Temporal's test-only time control covers those cases, and in-process tests can inject a clock.
- **ADR 0003:** the monotonic lease clock fits the paused clock in process. Run-epoch fencing across copies is a history-checking problem (Porcupine, stateright).
- **ADR 0036:** croner's explicit-start API makes the DST conformance cases free of any clock.
- **ADR 0051:** live `Date.now` and `Math.random` stay untestable for fixed values from inside scripts. Only the order of Effects is compared, as decided.
- **ADR 0002:** until now untested. A VFS shim covers all three OSes, and LazyFS covers Linux below a real process. Neither reaches the drive cache that macOS `fullfsync` targets.

## Unverified

- Whether LazyFS (FUSE 3 with `user_allow_other`) and dm-flakey or dm-log-writes run on GitHub-hosted Ubuntu runners without extra setup. etcd runs its robustness suite outside GitHub Actions.
- That `dirs`' Known Folder lookups ignore `USERPROFILE` and `APPDATA` set in a child's environment. Inferred from the README naming the Known Folder API, not tested.
- That macOS configures only `127.0.0.1` on `lo0` and needs `sudo ifconfig lo0 alias` for more, while Linux and Windows answer on all of `127.0.0.0/8`.
- That turmoil's `fs` shim cannot carry SQLite's file I/O. Inferred: rusqlite's bundled SQLite calls the OS through its C VFS, not through Rust's `std::fs`.
- That changing `RUSTFLAGS` (for `--cfg madsim` or `--cfg loom`) rebuilds every dependency. Not checked in Cargo's docs.
- Antithesis's price and whether it can run on-premises. Neither appears in the pages read.
- The cause of tokio #8232 (early `timeout` under `start_paused` since 1.50); the issue is open.
- Whether a temporary keychain made with `security create-keychain` isolates parallel macOS tests from each other.
- GitHub code-search counts in the section 1 table cover default branches only, and code search can miss files.
