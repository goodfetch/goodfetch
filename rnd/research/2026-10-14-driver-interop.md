# A third-party automation library driving a page another program owns

Research of **October 14, 2026** for ticket [#452](https://github.com/goodfetch/automan/issues/452). Question: what works, and what breaks, when a browser-automation library drives a page that another program (a crawler or an engine) launched and owns, over CDP or WebDriver BiDi? Four parts: third-party libraries on a lent page (Foxhound lending to others); two CDP clients on one target; the reverse (Collie inside another crawler); and leading practice for lending a session to untrusted code.

**Sources.** Source code read through the GitHub API and Chromium's Gitiles at pinned versions: Playwright **v1.64.1** (2026-10-14), Puppeteer **puppeteer-core v25.13.0** (2026-10-08), Stagehand `main` at **`1da7359`** (2026-10-13, SDK 4.2.1) plus the installed **4.1.0** bundle, Chromium `main` at **`3ea9312`** (2026-10-14), and the DevTools protocol at **r1718299** (`dfad770`, 2026-10-14). Official docs, release notes and issue trackers. The Stagehand v4 packaging facts reuse the salvaged ticket #448 report, whose sources are cited inline. Prior notes reused and re-checked: [Rust CDP clients](https://github.com/goodfetch/automan/blob/research/rust-cdp-clients/rnd/research/2026-10-10-rust-cdp-clients.md), [Stagehand CDP latency](2026-10-07-stagehand-cdp-latency.md), [Crawlee and Stagehand contracts](2026-10-07-crawlee-spider-contracts-followup.md), [stealth state of the art](https://github.com/goodfetch/automan/blob/research/stealth-state-of-the-art/rnd/research/2026-10-10-stealth-state-of-the-art.md) and [AI browser frameworks](https://github.com/goodfetch/automan/blob/research/ai-browser-frameworks/rnd/research/2026-10-10-ai-browser-frameworks.md).

**Measured versus cited.** Facts read from source or docs are cited inline. A localhost experiment (§6, when present) is marked **M**. Like everything in `rnd/`, this note informs a decision; it does not make one.

## 1. Summary

*(Draft; completed after the remaining sections.)*

- **Every mainstream library attaches at the browser level, not the page level.** Playwright's `connectOverCDP` sends `Target.setAutoAttach {autoAttach, waitForDebuggerOnStart, flatten}` on the browser session and adopts every page of every browser context it did not create into its "default context" (source comment: "TODO: auto attach only to pages from our contexts") ([crBrowser.ts v1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crBrowser.ts)). Puppeteer's `connect` does the same through `Target.setDiscoverTargets` and auto-attach ([TargetManager.ts v25.13.0](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/TargetManager.ts)). Stagehand v4 needs browser-level commands too (`Target.getTargets`, `Target.createTarget`, `Extensions.*`). Lending "one page" over a browser endpoint therefore lends every page unless a relay filters targets.
- **Attaching changes the owner's browser.** By default Playwright redirects the default context's downloads into its own temporary folder (`Browser.setDownloadBehavior allowAndName`), turns on focus emulation and applies its media defaults on every adopted page; since **v1.60** `noDefaults: true` skips those three ([class-browsertype.md v1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/api/class-browsertype.md), [#40158](https://github.com/microsoft/playwright/issues/40158)). Puppeteer sets an 800×600 viewport on every page it wraps unless `defaultViewport: null` ([ConnectOptions.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/common/ConnectOptions.ts)). Both enable `Runtime`, the domain ADR 0019 keeps off for stealth.
- **"Close" means different things.** Playwright's `browser.close()` on a connected browser only disconnects and disposes the contexts it created ([class-browser.md](https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/api/class-browser.md)). Puppeteer's `browser.close()` sends `Browser.close` and quits the owner's browser; `disconnect()` is the safe call ([BrowserConnector.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/BrowserConnector.ts)). Stagehand v4's `browser.close()` on a `localBrowser.connect()` browser also sends `Browser.close` ([factories.ts @1da7359](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/sdk-ts/src/browser/factories.ts)). A relay has to block `Browser.close` or a lent handler can kill a whole crawl.
- **Stagehand v4 cannot use a lent page without loading its extension into the owner's browser.** `localBrowser.connect({cdpUrl})` discovers or loads (`Extensions.loadUnpacked`, needing a shared filesystem) its "Stagehand Runtime" extension, then attaches to the extension's service worker, which needs `--enable-unsafe-extension-debugging` ([browser.mdx](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/docs/v4/configuration/browser.mdx)). It has no Playwright or Puppeteer page interop ([playwright.mdx](https://github.com/browserbase/stagehand/blob/main/packages/docs/v4/migrations/playwright.mdx)).
- **Two CDP clients on one target are supported by Chrome, but many states are last-writer-wins.** Chrome has supported several clients per tab since Chrome 63 ([DevTools 63](https://developer.chrome.com/blog/new-in-devtools-63)). Download behaviour is one slot per browser context: a second client's `setDownloadBehavior` replaces the first's, and when that client detaches the behaviour resets to the browser default rather than to the first client's ([devtools_download_manager_delegate.cc @3ea9312](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/protocol/devtools_download_manager_delegate.cc)). Fetch interception is daisy-chained per session ([devtools_url_loader_interceptor.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/devtools_url_loader_interceptor.cc)). Playwright's maintainers say Playwright "is not designed to work with multiple Playwright sessions connected to the same browser" ([#32821](https://github.com/microsoft/playwright/issues/32821), 2024-09-27).

## 2. Third-party libraries on a lent page

### 2.1 Playwright `connectOverCDP` (v1.64.1)

**What the docs promise.** `connectOverCDP` "attaches Playwright to an existing browser instance using the Chrome DevTools Protocol". The docs say "this connection is significantly lower fidelity than the Playwright protocol connection" and warn that "if you launch the browser without Playwright and do not pass the exact same arguments, some of Playwright functionality may be broken upon connecting" ([class-browsertype.md v1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/api/class-browsertype.md)). Options, with the version that added them:
- `headers` (v1.11), `slowMo`, `timeout` (30 s default);
- `isLocal` (v1.58): "runs on the same host as the CDP server", enabling file-system optimizations;
- `noDefaults` (v1.60): "Playwright will not apply its default overrides to the existing default browser context": downloads stay at the browser's setting, focus emulation is off, media emulation (`colorScheme`, `reducedMotion`, `forcedColors`, `contrast`) is not applied. New contexts are not affected;
- `artifactsDir` (v1.61): where traces and downloads go;
- the first argument may also be a channel name (`'chrome'`), resolved through the profile's `DevToolsActivePort` file, which is how Playwright reaches Chrome 144's consented debugging mode ([chromium.ts v1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/chromium.ts), `resolveChannelEndpoint`; [#40177](https://github.com/microsoft/playwright/pull/40177));
- a `ConnectionTransport` object instead of a URL (since [#40972](https://github.com/microsoft/playwright/pull/40972), May 2026), refused when Playwright itself runs remotely ([client browserType.ts](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/client/browserType.ts)). This lets an SDK hand Playwright a CDP channel without opening a WebSocket port.

**What it does on connect** (from source, [crBrowser.ts](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crBrowser.ts) and [crPage.ts](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crPage.ts)):
1. `Browser.getVersion`; "headful" is read from the user agent, since the launch options "may lie".
2. `Target.setAutoAttach {autoAttach: true, waitForDebuggerOnStart: true, flatten: true}` on the browser session. Every existing and future page, in every browser context, is attached. A page whose context Playwright did not create is put in the default context ("TODO: auto attach only to pages from our contexts"). Service workers are kept; other target types are detached "to avoid side-effects".
3. The default context is initialized: unless `noDefaults`, `Browser.setDownloadBehavior {behavior: 'allowAndName', downloadPath: <artifacts dir>, eventsEnabled: true}` with no `browserContextId`, which is the browser's default context ([crBrowser.ts `initialize`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crBrowser.ts)). The artifacts dir is a fresh temp folder that Playwright removes on disconnect ([chromium.ts `_connectOverCDPImpl`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/chromium.ts)).
4. For each page: `Page.enable`, `Page.getFrameTree`, `Log.enable`, `Page.setLifecycleEventsEnabled`, **`Runtime.enable`**, `Page.addScriptToEvaluateOnNewDocument` and `Page.createIsolatedWorld` for a world named `__playwright_utility_world_<guid>` with `grantUniveralAccess: true`, `Network.enable`, a page-level `Target.setAutoAttach` (OOPIFs and workers), `Emulation.setFocusEmulationEnabled` and media emulation unless `noDefaults`, file-chooser interception (`Page.setInterceptFileChooserDialog`), default font families in headless, `Inspector.enable` for pages attached while connecting, then `Runtime.runIfWaitingForDebugger`. The default context gets `noDefaultViewport: true`, so the window size is not touched.
5. Connect waits until every pre-existing page has answered its init commands. A frozen or discarded tab used to hang connect forever ([#42882](https://github.com/microsoft/playwright/issues/42882), 2026-09-23, "noDefaults does not help"); [PR #42936](https://github.com/microsoft/playwright/pull/42936), merged 2026-09-30 and in 1.64, sends `Inspector.enable` so such a page reports `Inspector.targetCrashed` and is dropped.

**New contexts** are `Target.createBrowserContext {disposeOnDetach: true}`, so they vanish when Playwright disconnects. `browser.close()` on a connected browser "clears all created contexts belonging to this browser and disconnects" ([class-browser.md](https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/api/class-browser.md)); in code it closes the WebSocket and removes the temp folders, and never sends `Browser.close`. Closing the default context returns `'close-browser'`, which for a connected browser also only disconnects. There is no `detach()`; a maintainer's answer to [#39011](https://github.com/microsoft/playwright/issues/39011) (2026-01-28) was "Call browser.close()".

**What users hit:**
- **Downloads** land in Playwright's temp folder, unnamed, even for tabs the person opened by hand, and are lost when it is removed ([#40158](https://github.com/microsoft/playwright/issues/40158), 2026-04-10). Fixed by `noDefaults` ([PR #40185](https://github.com/microsoft/playwright/pull/40185)). Remotely, `download.saveAs()` throws `ENOENT` because the file is on the browser's host ([#41060](https://github.com/microsoft/playwright/issues/41060), 1.60).
- **Forced light colour scheme** on attach ([#37627](https://github.com/microsoft/playwright/issues/37627)), also fixed by `noDefaults`.
- **Two Playwright clients on one browser.** `Runtime.bindingCalled` "is broadcast to all connections and only one of them is aware of the binding, the other one throws"; closed as out of scope: Playwright "is not designed to work with multiple Playwright sessions connected to the same browser, they will conflict in more places even if we fix it here" ([#32821](https://github.com/microsoft/playwright/issues/32821), 1.47.2).
- **Input on a headed browser** the person also uses: a collaborator answered that a headed browser "responds to real mouse events", and recommended Playwright's own launch arguments ([#41286](https://github.com/microsoft/playwright/issues/41286), 2026-06-15).
- **Video, tracing and context options** were long missing on connected browsers ([#29065](https://github.com/microsoft/playwright/issues/29065), [#42776](https://github.com/microsoft/playwright/issues/42776)).

### 2.2 Puppeteer `connect` (puppeteer-core v25.13.0)

**Options** ([ConnectOptions.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/common/ConnectOptions.ts)):
- `browserWSEndpoint`, `browserURL`, or a `transport`; `channel` (experimental) reads `DevToolsActivePort` for Chrome's consented mode;
- `defaultViewport`, **default `{width: 800, height: 600}`**, applied to "each page";
- `downloadBehavior`, unset by default;
- `targetFilter`, a callback deciding which targets Puppeteer attaches to;
- `networkEnabled` and `issuesEnabled` (experimental, default `true`);
- `protocolTimeout`, default 180 s;
- `blocklist` and `allowlist` (experimental) of URLPatterns; `allowlist` needs Chrome 149. The docs say it "is meant as an additional guardrails to LLM-based usage under Puppeteer control and not a complete network sandbox", and that on connect Puppeteer "will silently detach from any already open targets that violate the patterns". It is enforced with `Network.emulateNetworkConditionsByRule` (blocked requests are made offline), and Puppeteer refuses the user's own `emulateNetworkConditions` calls while it is on ([TargetManager.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/TargetManager.ts), [Browser.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/Browser.ts)).

**What it does on connect** (from source):
- `Target.getBrowserContexts`, then `Target.setDiscoverTargets {discover: true}` and a browser-level `Target.setAutoAttach {waitForDebuggerOnStart: true, flatten: true}` that excludes `page` targets; pages are reached through their `tab` targets, on which Puppeteer sets auto-attach again ([TargetManager.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/TargetManager.ts)).
- A `Page` object is created when code asks for it (`browser.pages()`, `target.page()`). Its init sends `Page.enable`, `Page.getFrameTree`, `Page.setLifecycleEventsEnabled`, **`Runtime.enable`**, `Performance.enable`, `Log.enable`, `Network.enable`, and creates the isolated world through `Page.addScriptToEvaluateOnNewDocument` plus `Page.createIsolatedWorld {grantUniveralAccess: true}`; then it calls `setViewport(defaultViewport)` ([Page.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/Page.ts), [FrameManager.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/FrameManager.ts)).
- **`browser.close()` sends `Browser.close`** even on a connected browser: the connector passes `() => connection.send('Browser.close')` as the close callback. `browser.disconnect()` only disposes the connection ([BrowserConnector.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/BrowserConnector.ts), [Browser.ts](https://github.com/puppeteer/puppeteer/blob/puppeteer-core-v25.13.0/packages/puppeteer-core/src/cdp/Browser.ts)).

### 2.3 Stagehand v4 (SDK 4.2.1, `main` at `1da7359`)

**Attach model.** v4's runtime (driver, `act`/`observe`/`extract`, LLM clients) lives in an MV3 extension, "Stagehand Runtime", with the `debugger`, `offscreen`, `scripting` and `tabs` permissions and `<all_urls>` host permissions ([manifest.json](https://github.com/browserbase/stagehand/blob/main/packages/extension/manifest.json), via the #448 report). The SDK talks to it as JSON-RPC carried over CDP: it finds the extension's service worker with `Target.getTargets` (waking it with `Target.createTarget` on `wake-service-worker.html` if needed), attaches with `Target.attachToTarget {flatten: true}`, sends `Runtime.enable` and `Runtime.addBinding`, then `Runtime.evaluate` for each message ([cdpClient.ts @1da7359](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/sdk-ts/src/cdpClient.ts)).

**Three browser factories** ([browser.mdx @1da7359](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/docs/v4/configuration/browser.mdx)):
- `localBrowser.launch()` starts system Chrome with `--remote-debugging-port`, `--enable-unsafe-extension-debugging`, `--remote-allow-origins=*` and about 25 automation flags, and loads the extension over CDP with `Extensions.loadUnpacked` (#448 report, from the Go launcher and the 4.2.1 wheel).
- `localBrowser.connect({cdpUrl})` attaches to "a running Chromium browser through its DevTools endpoint. It discovers an installed Stagehand extension first, then loads the bundled extension if none is found or discovery is unsupported. Loading requires a shared filesystem." Without `Extensions.loadUnpacked` it fails: "This Chrome build does not support Extensions.loadUnpacked. Launch with --load-extension and connect using extensionId instead." ([cdpClient.ts](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/sdk-ts/src/cdpClient.ts); `extensionId` on connect is deprecated and ignored since 4.2.0, per the #448 report).
- `browserbase.connect({sessionId})` needs a session created with the extension: "Extensions cannot be added after a browser session starts."

The docs say `--enable-unsafe-extension-debugging` is "required so the SDK can attach a CDP session to the service worker hosting Stagehand's runtime. Chrome blocks debugger access to extension targets without it" (#448 report, [browser.mdx](https://github.com/browserbase/stagehand/blob/main/packages/docs/v4/configuration/browser.mdx)).

**On a lent page.** v4 has "no interop": "you can't hand a Playwright `Page` to `act()`", and the `page` option "only accepts a page from `browser.context`"; one context per browser ([playwright.mdx](https://github.com/browserbase/stagehand/blob/main/packages/docs/v4/migrations/playwright.mdx)). So a Foxhound handler cannot give Stagehand v4 one page: Stagehand needs the browser endpoint, installs an extension with `debugger` permission in the owner's profile, and drives its own pages from inside the browser. The extension's own CDP traffic goes through `chrome.debugger`, inside the browser, so a relay in front of the WebSocket never sees it.

**Close.** "Stagehand closes only the browsers it launched, so `browser.close()` is yours to call" (browser.mdx). In code, `browser.close()` on a `localBrowser.connect()` handle sends `Browser.close` ([factories.ts](https://github.com/browserbase/stagehand/blob/1da7359172f1c057487b8918af118e389fe76615/packages/sdk-ts/src/browser/factories.ts)); `stagehand.close()` only releases the claim (4.1.0 bundle, `Stagehand.close`).

**Stagehand v3 (`v3-latest` 3.7.3).** v3 ran its own CDP driver in Node, accepted `localBrowserLaunchOptions.cdpUrl`, and had peer dependencies on `playwright-core`, `puppeteer-core` and `patchright-core` so a page from those libraries could be passed to `act` (#448 report, [npm 3.7.3](https://www.npmjs.com/package/@browserbasehq/stagehand/v/3.7.3)). Crawlee's TS integration is built on it (§4).

## 3. Two CDP clients on one target

### 3.1 What Chrome supports

- **Several clients per target since Chrome 63** (2017): "two separate WebSocket protocol clients" can connect to the same tab, and several `chrome.debugger` extensions can share a tab ([DevTools 63](https://developer.chrome.com/blog/new-in-devtools-63)).
- **Flat sessions are the intended mode.** `setAutoAttach`'s `flatten` "enables flat access to the session"; Chrome plans to "make this the default, deprecate non-flattened mode, and eventually retire it" (crbug.com/991325) ([Target.pdl r1718299](https://github.com/ChromeDevTools/devtools-protocol/blob/dfad770693/pdl/domains/Target.pdl)).
- **Scoped auto-attach exists.** `Target.autoAttachRelated {targetId}`, browser target only, experimental, "adds the specified target to the list of targets that will be monitored for any related target creation" and auto-attaches it, so a client can follow one page and its children without seeing the rest (Target.pdl).
- **Chromium has a permission model for clients**, used for `chrome.debugger`: `DevToolsAgentHostClient` asks the client `MayAttachToURL`, `IsTrusted` ("allowed to attach to the browser agent host and perform other privileged operations"), `MayReadLocalFiles`, `MayWriteLocalFiles` ("manipulating a default downloads path") and `AllowUnsafeOperations` ([devtools_agent_host_client.h @3ea9312](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/public/browser/devtools_agent_host_client.h)). An extension client is untrusted (except Perfetto's), may never write local files, has its navigations treated as renderer-initiated from the extension's origin, and raises the "is debugging this browser" infobar unless `--silent-debugger-extension-api` is set ([debugger_api.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/chrome/browser/extensions/api/debugger/debugger_api.cc)). Chrome builds whole domain handlers only for trusted clients unless the domain is marked available to untrusted ones ([chrome_devtools_session.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/chrome/browser/devtools/chrome_devtools_session.cc)). A WebSocket or pipe client is trusted: there is no protocol-level way to hand one a reduced set.

### 3.2 State the clients share, and who wins

| State | Scope in Chromium | When two clients set it | When one detaches | Source |
|---|---|---|---|---|
| Download behaviour (`Browser.setDownloadBehavior`) | one slot per browser context | last writer wins | if the detaching client was the last writer, the behaviour resets to `default`, not to the earlier client's value | [devtools_download_manager_delegate.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/protocol/devtools_download_manager_delegate.cc), [browser_handler.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/protocol/browser_handler.cc) |
| Device metrics, touch, geolocation, sensors (`Emulation.*`) | per session handler, applied to the one WebContents | last writer wins on the page | the detaching session's `Disable` clears device emulation and restores the view size (`ClearDeviceEmulationSize`), whoever set it | [emulation_handler.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/protocol/emulation_handler.cc) |
| Request interception (`Fetch.enable`) | one interceptor per session, daisy-chained | each intercepting session sees and must continue the request, from "outermost (client-facing) to innermost (network-facing)" | its interceptor leaves the chain | [devtools_url_loader_interceptor.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/devtools_url_loader_interceptor.cc) |
| New targets with `waitForDebuggerOnStart` | one navigation throttle per auto-attaching session | a new target waits for each client that asked to pause it **(Unverified: §6)** | — | [target_handler.cc](https://chromium.googlesource.com/chromium/src/+/3ea93124568e116f89d7493360b8e7257c78e186/content/browser/devtools/protocol/target_handler.cc) |

### 3.3 What a second client adds to detection

- **`Runtime.enable`.** Both Playwright and Puppeteer send it on every page they wrap (§2). The stealth note records two published signals that need the Runtime domain on: the 2024 console-serialization getter and the March 2026 Proxy-prototype preview trap ([stealth note](https://github.com/goodfetch/automan/blob/research/stealth-state-of-the-art/rnd/research/2026-10-10-stealth-state-of-the-art.md)). A guarded, Runtime-free owner (ADR 0019) loses that property for as long as a lent library is attached.
- **Named isolated worlds** with universal access: `__playwright_utility_world_<guid>` (Playwright) and Puppeteer's utility world, each with a `//# sourceURL` marker (§2).
- **Viewport and focus changes:** Puppeteer's 800×600 default and Playwright's focus emulation alter `innerWidth`, `document.hasFocus()` and `visibilityState`-dependent behaviour unless switched off.
- **Stagehand v4** adds an extension with `<all_urls>` content scripts at `document_start` in all frames (#448 report).
