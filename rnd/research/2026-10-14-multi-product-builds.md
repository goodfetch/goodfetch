# Shipping several products from one native codebase, and what each mechanism costs

Research of **October 14, 2026** for ticket [#450](https://github.com/goodfetch/automan/issues/450) (map [#447](https://github.com/goodfetch/automan/issues/447), feeding [#454](https://github.com/goodfetch/automan/issues/454)). Question: how do native (Rust or similar) projects ship several products or editions from one codebase, and what does each mechanism cost in build, test, signing and user experience? The decision it informs: whether Collie and Foxhound ship as separately installable products from one repository, Foxhound's binary containing Collie, with CI proving no Collie crate depends on a Foxhound crate. That would amend ADRs 0024, 0026, 0032, 0038, 0039 and 0057 and `STYLE.md`'s crate rules.

**Sources.** Source code, Cargo manifests, lockfiles and CI workflows read through the GitHub API at each project's default branch on 2026-10-14 unless a commit or version is given; release asset sizes from `gh api repos/<o>/<r>/releases/latest`; crates.io, npm and PyPI metadata APIs; official docs; issue trackers. Prior Goodfetch research reused and re-checked where cited: [binary-size limits](https://github.com/goodfetch/automan/blob/research/binary-size-budget/rnd/research/2026-10-12-binary-size-limits-and-costs.md) (2026-10-12), [repository layout and CI](https://github.com/goodfetch/automan/blob/research/repo-layout-ci/rnd/research/2026-10-11-repo-layout-ci.md) (2026-10-11), [platform code signing](https://github.com/goodfetch/automan/blob/research/platform-code-signing/rnd/research/2026-10-11-platform-code-signing.md) (2026-10-11), [JavaScript sandbox engines](https://github.com/goodfetch/automan/blob/research/js-sandbox-engines/rnd/research/2026-10-12-js-sandbox-engines.md) (2026-10-12), [Rust test tooling](https://github.com/goodfetch/automan/blob/research/rust-test-tooling/rnd/research/2026-10-13-rust-test-tooling.md) (2026-10-13).

**Versions inspected.** Codex `rust-v0.162.1` (2026-10-09) and `main` at `835cd7552` (2026-10-14); Deno v2.9.7 (2026-09-17); uv 0.13.1 (2026-10-14); Ruff 0.17.0 (2026-10-09); ty 0.0.87 (2026-10-13); Bun v1.4.3; `spider` 2.53.9 (2026-09-05); Tokio 1.53.3 (2026-10-13); cargo-hack 0.6.45; cargo-deny 0.20.2. Others are given where cited.

## 1. Summary

(Draft; completed at the end of the research.)

- **Codex is the closest precedent for "Foxhound contains Collie".** One Cargo workspace (`codex-rs`) ships a superset binary (`codex`, whose `codex app-server` subcommand runs the app server) and a subset binary (`codex-app-server`) built in separate per-target jobs, plus helper executables. Windows x64 sizes: `codex.exe` 333.5 MB, `codex-app-server.exe` 255.2 MB **M**. In 2026-07 Codex moved V8 out of both into a companion executable, `codex-code-mode-host` (74.7 MB on Windows), and made a missing host fall back to direct tools with a one-time warning, or fail closed when code mode is required **C**.

## 2. Mechanisms and what each costs

Six mechanisms, each with the projects seen using it in §3–4. "Per extra product" means what one more product or part adds on top of a single binary.

| | A. Several fixed binaries from one workspace | B. Cargo features chosen by packagers or users | C. A part downloaded on first use | D. A companion executable shipped beside the binary | E. One binary with subcommands (multi-call) | F. Plugins as dynamic libraries or Wasm |
|---|---|---|---|---|---|---|
| **Seen in** | Codex `codex` ⊃ `codex-app-server`; uv ⊃ `uv_build`; sccache / `sccache-dist`; Zed app / remote server; Ruff / ty | spider (129 features), ripgrep `pcre2`, Deno `upgrade` and `v8`/`quickjs`, uv `self-update`, Wasmtime (44) for embedders, Tauri v1 | `denort` for `deno compile`, DuckDB extensions, Zed remote server, Prisma engines, Playwright browsers; Goodfetch's browsers and Clean-up rules today | Codex `codex-code-mode-host` (V8), Codex sandbox helpers, `uvx`; Goodfetch's sink processes and `goodfetch-sandbox` today | Bun, Deno, Codex's `arg0` aliases (`apply_patch`, `codex-linux-sandbox`), `goodfetch` today | DuckDB (signed `dlopen` extensions), SWC and Zed (Wasm), Bevy (dylib, deprecated), Nushell (plugins as executables) |
| **Build per target** | One `cargo build -p <product>` per product (Codex: a runner per bundle; uv: a second maturin call with its own profile). Building both in one invocation unifies their features (§5.1) | One build per shipped feature set; mutually exclusive features need separate invocations (Deno's QuickJS `denort`: two to three more per target) | One more artefact per target and per version, plus a download host and cache (`dl.deno.land`, `extensions.duckdb.org`) | One more `--bin` per target; Codex builds the host twice per target (once per bundle) | None extra | The host plus each plugin per target and per host version (DuckDB: per DuckDB version and platform) |
| **Test** | Each product's own suites; the subset's tests must run under its own feature set, not the workspace union | `--each-feature` is N+3 builds; `--feature-powerset --depth 2` is N + C(N,2) (8,385 for 129 features); Tokio runs both on 17 features, Wasmtime hand-picks about 40 checks for 44, spider tests a handful and ships broken combinations | The download path (proxy, mirror, offline, missing target) needs its own tests; Deno's users hit them in CI | Protocol skew between the two executables (Codex #42111), discovery from every install layout (#36217 tests "missing hosts and symlinks") | One configuration | ABI or protocol compatibility per host version; SWC: "not backwards compatible" |
| **Signing and notarization** | Every product's executables, per target (uv signs `uv`, `uvx`, `uv-build`) | Only what is shipped is signed; user-built feature sets carry no Platform signature | The part must be signed like the binary unless the user re-signs it (Deno leaves `denort` unsigned because `deno compile` rewrites it) | One more executable per target; Codex shipped one notarized and one not (#47521) | Once | Signed by the host's publisher (DuckDB's keys); a third-party library fails macOS library validation (ADR 0057) |
| **Debug symbols** | An archive per product per target, each larger than its binary (Codex: 204.5 MB app server, 262.6 MB CLI, Linux x64) | Per shipped set | Per part | Per executable | Once | Per plugin |
| **Size reported** | Per product; Deno logs `du` of `deno` and `denort` on `main`, no gate found | Per shipped set | Per part | Per executable | Once (ADR 0057 today) | Per plugin |
| **A missing part** | Not applicable: each product is whole; the subset lacks commands rather than failing them | ripgrep: "PCRE2 is not available in this build of ripgrep"; Tauri fails the app's build when config and features disagree | Download error (`Failed downloading '<url>'`; DuckDB `Extension Autoloading Error`), or a cached copy | Codex: fall back with a one-time warning, or fail closed when required | Not applicable | Nushell refuses an incompatible plugin; DuckDB "will throw an error and refuse to load the extension" |
| **Offline** | Works | Works | First use needs the network unless pre-seeded (`DENORT_BIN`, `extension_directories`, `upload_binary_over_ssh`) | Works if packaged together | Works | Works once installed |
| **What users filed** | Few found; Zed's exact version match is documented, not complained about | Broken untested combinations (spider #245, #288, #348, #349); "reach out to the maintainer of that package" (ripgrep) | CI download failures (Deno #27988), no part for the platform (Deno #30386, Prisma), part missing after a split (Playwright #34508), offline upgrade break (duckdb-java #623) | Omitted by a channel (WinGet, #38975), not notarized (#47521), stale path after upgrade (#47432, #44261), version skew (#42111), start failures (#41049, 46 comments) | Size (Bun's own docs: "way too big"; Deno 2 at 136 MB) | Version-mismatch tables (SWC), unsound ABI (Bevy) |

**Patterns.**
- **The superset product links the subset product's crates; the subset is never a feature of the superset.** Codex (`codex` links `codex-app-server`), uv (links the `uv_build` backend) and Deno (`deno` and `denort` share `deno_lib`) all ship the smaller product as its own package with its own `[[bin]]`, built by its own `cargo build -p`, rather than as the big binary with features turned off.
- **Heavy optional runtimes leave the main process before they leave the install.** Codex moved V8 into `codex-code-mode-host` but still ships it in the same package (`codex-package-*`), and the app-server package carries it too, so the split bought a process boundary and remote code-mode hosts ([#35098](https://github.com/openai/codex/pull/35098)), not a smaller download.
- **Cargo features as editions survive where the user compiles** (Wasmtime embedders, ripgrep's packagers, Tauri app authors) and are avoided where the project ships binaries: Homebrew dropped them (§5.1), Tauri moved capabilities out of core features, and spider's untested combinations reach users.
- **Per-product dependency checks are cheap and rare.** Only uv's `uv_build` ban list and uutils' `cargo tree -i` check were found as CI steps (§5.4).

## 3. Cases

### 3.1 OpenAI Codex: a superset binary, a subset binary and companion executables

**What ships.** Codex `rust-v0.162.1` (2026-10-09) has 176 release assets **M**. Per target it publishes these executables (Linux x86_64 musl and Windows x64 sizes, **M**):

| Executable | Role | Linux x64 musl, `.tar.gz` | Windows x64 `.exe`, raw |
|---|---|---|---|
| `codex` | the CLI; also runs the app server through `codex app-server` | 111.4 MB | 333.5 MB |
| `codex-app-server` | the app server alone, for IDE and desktop clients | 86.1 MB | 255.2 MB |
| `codex-code-mode-host` | V8 sandbox for code mode, a separate process | 27.5 MB | 74.7 MB |
| `codex-responses-api-proxy` | a privileged proxy | 5.0 MB | 6.0 MB |
| `bwrap` (Linux) / `codex-windows-sandbox-setup`, `-service`, `codex-command-runner` (Windows) | OS sandbox helpers | 0.26 MB | 17.7 / 56.1 / 8.2 MB |
| `codex-package-<target>` | archive of the CLI with its helpers | 162.9 MB | 159.7 MB `.tar.gz` |
| `codex-app-server-package-<target>` | archive of the app server with its helpers | 116.3 MB | 125.8 MB `.tar.gz` |
| `codex-symbols-<target>[-app-server]` | debug symbols, per product | 262.6 MB (CLI), 204.5 MB (app server) | 589.5 MB |

- The CLI depends on the app server's crate: `codex-cli` lists `codex-app-server`, `codex-app-server-daemon` and `codex-app-server-protocol` ([cli/Cargo.toml](https://github.com/openai/codex/blob/main/codex-rs/cli/Cargo.toml)), and its `AppServer` subcommand is "[experimental] Run the app server or related tooling" ([cli/src/main.rs](https://github.com/openai/codex/blob/main/codex-rs/cli/src/main.rs)). `codex-app-server` declares its own `[[bin]]` ([app-server/Cargo.toml](https://github.com/openai/codex/blob/main/codex-rs/app-server/Cargo.toml)) **C**. So the subset product is a library crate with a thin binary, and the superset binary links it, which is the shape the working hypothesis gives Collie and Foxhound.
- **One binary, several names.** The `codex-arg0` crate dispatches on the executable's name: invoked as `codex-linux-sandbox` it runs the Landlock sandbox, as `apply_patch` it applies a patch, and the CLI puts such aliases on a temporary `PATH` entry for its children ([arg0/src/lib.rs](https://github.com/openai/codex/blob/main/codex-rs/arg0/src/lib.rs)) **C**. The Linux sandbox helper is therefore not a separate file to sign, while the Windows sandbox helpers are.

**V8 moved into a companion executable.** Code mode (an agent writing JavaScript that calls tools) runs in V8.
- In the lockfile at `main` (2026-10-14), `v8` is a dependency only of `codex-code-mode-runtime` (and of a `codex-v8-poc` crate), and `codex-code-mode-runtime` only of `codex-code-mode-host`; `codex`, `codex-app-server` and `codex-core` depend on `codex-code-mode`, the client side, which has no V8 **M** ([Cargo.lock](https://github.com/openai/codex/blob/main/codex-rs/Cargo.lock), queried with `tomllib`). The runtime turns on V8's sandbox (`v8 = { features = ["v8_enable_sandbox"] }`) and links ICU data through `deno_core_icudata` ([code-mode-runtime/Cargo.toml](https://github.com/openai/codex/blob/main/codex-rs/code-mode-runtime/Cargo.toml)) **C**.
- The move was a four-phase stack: "Add protocol and host crates…", "Create the new standalone binary", "Create a new IPC `CodeModeSessionProvider`", "Remove v8 from core and only use IPC provider" ([#27724](https://github.com/openai/codex/pull/27724), merged 2026-06-12). The last phase "Move[d] the V8 implementation into a dedicated `codex-code-mode-runtime` crate used by `codex-code-mode-host`, removing the embedded runtime fallback from the Codex process" ([#36217](https://github.com/openai/codex/pull/36217), merged 2026-07-30) **C**.
- **How a missing part fails.** The same PR resolves "the host executable from the active installation layout", checks "its availability before selecting tools", and falls back "to direct tools with a one-time warning when optional code mode is unavailable", while "`code_mode_only` and `disable_in_process_fallback` configurations" stay "fail-closed"; its tests cover "missing hosts and symlinks" ([#36217](https://github.com/openai/codex/pull/36217)) **C**. Later PRs added gRPC transport and remote code-mode hosts for the app server ([#35098](https://github.com/openai/codex/pull/35098), 2026-07-24; [#38041](https://github.com/openai/codex/pull/38041), 2026-08-11) **C**.

**What it costs in CI.**
- The release workflow builds per target and per **bundle**: `primary` builds `codex codex-code-mode-host codex-responses-api-proxy` (plus `bwrap` on Linux), `app-server` builds `codex-app-server codex-code-mode-host`, each with its own `cargo build --bin …` on its own runner, for four Unix targets and, in a separate workflow, two Windows targets with a third bundle of sandbox helpers ([rust-release.yml](https://github.com/openai/codex/blob/main/.github/workflows/rust-release.yml), [rust-release-windows.yml](https://github.com/openai/codex/blob/main/.github/workflows/rust-release-windows.yml)) **C**. Each matrix is also doubled across `build-system: [cargo, bazel]`, the Bazel half `continue-on-error`. So the host is compiled twice per target, and the workflow skips the copy from the `app-server` bundle: "Both variants package the host, but only the primary bundle publishes standalone binary archives to avoid duplicate release asset names" **C**.
- Build jobs have `timeout-minutes: 120` on `macos-15-xlarge` and similar runners **C**. Larger runners are billed even for public repositories (§5.4), so this layout is not available on Goodfetch's free tier as written.
- macOS signing runs as a separate job per target and bundle, on `ubuntu-latest`, in the protected `codesigning` environment, with `rcodesign` and an Azure Key Vault key reached over PKCS#11 ([rust-release.yml](https://github.com/openai/codex/blob/main/.github/workflows/rust-release.yml)) **C**: four signing jobs per build system for two macOS targets, each signing two or three executables.
- Debug symbols are archived per bundle "before stripping the Cargo binaries", with `CARGO_PROFILE_RELEASE_SPLIT_DEBUGINFO=packed` on macOS ([rust-release.yml](https://github.com/openai/codex/blob/main/.github/workflows/rust-release.yml)) **C**; each product's symbol archive is larger than its binary (table above).

**Boundary enforcement.** Codex's `deny.toml` uses cargo-deny's `wrappers` as a dependency-direction ratchet: `reqwest` is banned except as a direct dependency of `codex-http-client` ("Intended owner"), `codex-code-mode`, `codex-responses-api-proxy` ("owns its blocking upstream HTTP transport independently of Codex") and listed third-party crates, with the reason "new direct reqwest dependencies must use codex-http-client; temporary wrappers track migration debt"; `async-trait` is banned the same way ([deny.toml](https://github.com/openai/codex/blob/main/codex-rs/deny.toml)) **C**. No check was found that the `codex-app-server` binary lacks CLI-only crates (**unverified**: only `deny.toml` and the release workflows were read).

**What users filed after V8 became a companion executable** (issues opened after [#36217](https://github.com/openai/codex/pull/36217), all open on 2026-10-14) **C**:
- **Packaging drops the part.** "The ZIP omits `codex-code-mode-host.exe`, which can make Code Mode unavailable when the in-process fallback is disabled", found while asking why "winget updates regularly fail validation" ([#38975](https://github.com/openai/codex/issues/38975), 2026-08-17, codex-cli 0.147.0).
- **Signing covers one file and not the other.** On a Homebrew Cask install, `codex-code-mode-host` "is Developer ID signed but not notarized, blocked by Gatekeeper"; `spctl` reports `rejected source=Unnotarized Developer ID` ([#47521](https://github.com/openai/codex/issues/47521), 2026-09-23, 0.156.0).
- **Upgrades leave stale paths.** "After updates, Codex keeps looking for codex-code-mode-host.exe in an old directory, causing 'os error 2'" ([#47432](https://github.com/openai/codex/issues/47432), 2026-09-23); a long-lived app server launched from Homebrew's transient `.upgrading` directory "fails to spawn `codex-code-mode-host` because it resolves the helper relative to the stale install path" ([#44261](https://github.com/openai/codex/issues/44261), 2026-09-09).
- **Version skew between the two executables.** With CLI 0.152.0 and app server 0.151.0, "All tool calls fail … caused by an IPC/protocol mismatch between the code-mode tool host and the client": `failed to decode code-mode IPC frame` on an unknown field `code_mode_host_duration_ns` ([#42111](https://github.com/openai/codex/issues/42111), 2026-09-01; again in [#49014](https://github.com/openai/codex/issues/49014)).
- **The helper fails to start.** "code-mode host exited during handshake", 46 comments ([#41049](https://github.com/openai/codex/issues/41049), 2026-08-27); on Windows the same with `0xC0000022` ([#40913](https://github.com/openai/codex/issues/40913)); "timed out negotiating with code-mode host" ([#38816](https://github.com/openai/codex/issues/38816)).

So within three months of the split, each cost of a companion executable that ADR 0057 listed in the abstract (a second file to sign, ship and pin, and a failure mode under offline or broken installs) appeared as a user-filed issue. Several are channel packaging (WinGet, Homebrew Cask) rather than the release workflow itself.

### 3.2 Deno: `deno` and `denort`, a subset binary downloaded on first use

**What ships.** Deno v2.9.7 (2026-09-17) publishes per target `deno` (the CLI and runtime), `denort` (the runtime only, "Provides the denort executable", [cli/rt/Cargo.toml](https://github.com/denoland/deno/blob/main/cli/rt/Cargo.toml)) and `libdenort` (the same runtime as a shared library, for `deno desktop`) **C**. Sizes from the zip central directories of the release assets **M**:

| Target | `deno` zip / unpacked | `denort` zip / unpacked | `libdenort` zip / unpacked |
|---|---|---|---|
| x86_64 Linux glibc | 41.6 / 95.8 MB | 34.4 / 104.6 MB | 31.5 / 78.4 MB |
| aarch64 macOS | 38.5 / 81.0 MB | 28.7 / 67.6 MB | 28.9 MB / not read |
| x86_64 Windows | 42.6 / 97.5 MB | 32.7 / 79.8 MB | 32.9 MB / not read |

- The runtime-only binary saves 13.4 MB (17%) on macOS and 17.7 MB (18%) on Windows **M**. On Linux it is **larger** than `deno`: CI strips `deno` fully but keeps `denort`'s symbol table, because "libsui rewrites its ELF to embed user code, and that rewrite drops `.relr.dyn` relative relocations when the symbol table is gone, producing a compiled binary whose C++ static-init guards deadlock" ([ci.ts](https://github.com/denoland/deno/blob/main/.github/workflows/ci.ts)) **C**. Most of either binary is V8 and its snapshot, which both carry.
- `deno` and `denort` are separate packages sharing workspace crates (`deno_lib`, `deno_runtime`, `deno_core`); `deno` does not depend on the `denort` crate ([cli/Cargo.toml](https://github.com/denoland/deno/blob/main/cli/Cargo.toml)) **C**.

**How `deno compile` gets the part.** The docs say "Deno downloads the matching `denort-<target>.zip` from `dl.deno.land` and caches it in `DENO_DIR`", "Subsequent compiles reuse the cached binary and work offline", and "To use a custom or locally built runtime as the base, set the `DENORT_BIN` environment variable" ([deno compile](https://docs.deno.com/runtime/reference/cli/compile/), read 2026-10-14) **C**. The code builds `https://dl.deno.land/release/v{version}/denort-{target}.zip` (or `canary/{git_hash}/…`), downloads it with retries and a progress bar, and writes it under the download folder; a failure surfaces as `Failed downloading '<url>'` with the context "Setting up base binary." ([cli/standalone/binary.rs](https://github.com/denoland/deno/blob/main/cli/standalone/binary.rs)) **C**. The version is the running `deno`'s own, so the pair is always version-locked.

**Engine as a Cargo feature.** Deno added "mutually exclusive `v8` and `quickjs` Cargo features through `deno_core`, `deno`, `denort`, and `denort_desktop`" and an `--engine v8|quickjs` flag to `deno compile`, which downloads `denort-quickjs-<target>.zip` ([#36194](https://github.com/denoland/deno/pull/36194), merged 2026-08-04) **C**. The docs call it "experimental", note that "The QuickJS backend does not receive the same security updates as V8" and that it "produces a smaller executable" ([deno compile](https://docs.deno.com/runtime/reference/cli/compile/)) **C**. The v2.9.7 GitHub release lists no `denort-quickjs-*` asset, while `dl.deno.land/release/v2.9.7/denort-quickjs-x86_64-unknown-linux-gnu.zip` answers HTTP 200 **M**.
- Mutually exclusive features cost separate builds: CI builds `deno`, `denort` and `test_server` in one `cargo build --release --locked -p deno -p denort -p test_server --bin …` invocation, then rebuilds `denort` with `--no-default-features --features quickjs` in a second one; on Windows in two more, because "Both packages produce denort.pdb on Windows. Building them in one Cargo invocation lets their linkers race to write it" ([ci.ts](https://github.com/denoland/deno/blob/main/.github/workflows/ci.ts)) **C**. A debug job runs `cargo check --locked -p deno -p denort --no-default-features --features quickjs` on two targets **C**.
- Deno also has a packager feature: `upgrade` "enables the upgrade subcommand and the background check for available updates … This is typically disabled for (Linux) distribution packages" ([cli/Cargo.toml](https://github.com/denoland/deno/blob/main/cli/Cargo.toml)) **C**. uv's `self-update` feature is the same idea (§3.3).

**Signing.** Only `deno` is Platform-signed: `rcodesign sign target/release/deno --code-signature-flags=runtime …` on macOS and Azure Artifact Signing with `files-folder-filter: deno.exe` on Windows; `denort` is stripped and zipped unsigned ([ci.ts](https://github.com/denoland/deno/blob/main/.github/workflows/ci.ts)) **C**. That fits its role: `deno compile` appends the user's code to `denort`, which would invalidate any signature, so the docs tell users to sign the output themselves ("on macOS, the compiled executable will be signed using an ad-hoc signature"; on Windows it "can be signed using the `SignTool.exe` utility", [deno compile](https://docs.deno.com/runtime/reference/cli/compile/)) **C**. A companion that runs as shipped, as a Goodfetch one would, has no such reason to skip ADR 0039.

**Complaints.**
- Downloads in CI: "Runtime download of compile assets (`denort-x86_64-unknown-linux-gnu.zip`) fails" under GitHub Actions ([#27988](https://github.com/denoland/deno/issues/27988), 2025-02-06); a maintainer answered that it is "much better practice to pre-download and cache the `denort` binary in CI … Then, you can set `DENORT_BIN`", and a user replied "I had to look into the code to find this option. This definitely should be publicly documented" **C**. It is documented now (above).
- Wrong edition for the platform: `deno` installed from Alpine's package manager asked for `denort-x86_64-alpine-linux-musl.zip`, which Deno does not publish; `--target=x86_64-unknown-linux-gnu` compiled, but the binary did not run on Alpine ([#30386](https://github.com/denoland/deno/issues/30386), 2025-08-13) **C**.
- Confusing names: "There doesn't appear to be anything … which states the difference between 'deno' and 'denort' builds" ([#30856](https://github.com/denoland/deno/issues/30856), 2025-09-26) **C**.
- Size: users asked for Cargo features to drop large extensions from `denort` (`ext/webgpu`, `ext/node`, `ext/crypto`, [#22669](https://github.com/denoland/deno/issues/22669), 2024-03-02, closed) **C**; the Deno 2 binary-size question is in the prior research ([deno#26516](https://github.com/denoland/deno/issues/26516)).

### 3.3 Astral: uv, `uvx`, `uv_build`, Ruff and ty from shared crates

**uv and `uv_build`: a superset product and a lean subset product from one workspace.**
- The build backend is "published as a separate package (`uv_build`)", "optimized for portability and small binary size", and "the `uv` executable also includes a copy of the build backend, which will be used during builds performed by uv … if its version is compatible with the `uv_build` requirement. If it's not compatible, a compatible version of the `uv_build` package will be used" ([build backend](https://docs.astral.sh/uv/concepts/build-backend/), read 2026-10-14) **C**. So the larger product contains the smaller one, and the smaller one ships alone for users who need only it: the shape of "Foxhound contains Collie".
- Sizes, 0.13.1 manylinux x86_64 wheels **M**: `uv` 37.85 MB unpacked (17.3 MB wheel), `uvx` 0.33 MB, `uv-build` 3.42 MB (1.50 MB wheel). The subset is 9% of the superset.
- **The boundary is checked per product.** uv's lint workflow runs, after the workspace-wide `cargo deny … check bans`, a step "Check uv_build dependencies": `cargo deny --manifest-path crates/uv-build/Cargo.toml --all-features check bans` ([check-lint.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/check-lint.yml)) **C**. Its own `crates/uv-build/deny.toml` bans `rustls`, `openssl` and `reqwest` ("The build backend does not need network access") and `schemars` ("JSON Schema generation is a development feature, not a runtime feature") ([deny.toml](https://github.com/astral-sh/uv/blob/main/crates/uv-build/deny.toml)) **C**. This is the one production example found of a per-product ban list run in CI, and it is the cheapest mechanism of §5.4: one `cargo deny` invocation per product (the job's timeout is 10 minutes).
- **Built separately, per target.** Each release job runs maturin twice: `--release --locked --features self-update` for uv and `--profile minimal-size --locked -m crates/uv-build/Cargo.toml` for `uv_build` ([build-release-binaries.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/build-release-binaries.yml)) **C**. `minimal-size` inherits `release` with `opt-level = "z"` and `codegen-units = 1`; `release` is fat LTO, `codegen-units = 1`, `strip`, `panic = "abort"` ([Cargo.toml](https://github.com/astral-sh/uv/blob/main/Cargo.toml)) **C**. A separate product can thus take its own speed/size trade-off, which a subcommand of the same binary cannot.
- **Signing per executable.** The signing workflow maps each package to its executables: `"macos": {"uv": ["uv", "uvx"], "uv_build": ["uv-build"]}`, with the `.exe` equivalents on Windows ([sign-release-binaries.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/sign-release-binaries.yml)) **C**.
- **`uvx` is a launcher, not a second product.** It finds `uv` beside itself (honouring a suffix such as `uvx-0.13`) and execs it ([crates/uv/src/bin/uvx.rs](https://github.com/astral-sh/uv/blob/main/crates/uv/src/bin/uvx.rs)) **C**: 0.33 MB for a second command name, signed like any executable.
- `self-update` "is only enabled for uv's cargo-dist installer and should be left unselected when building uv for package managers" ([crates/uv/Cargo.toml](https://github.com/astral-sh/uv/blob/main/crates/uv/Cargo.toml)) **C**.

**Ruff and ty: two products, shared crates, two repositories.** ty's code lives in the Ruff repository (`crates/ty`, `ty_python_semantic`, `ty_server`, …) beside Ruff's, and `ty` depends on the shared `ruff_db`, `ruff_python_ast`, `ruff_diagnostics` and others ([crates/ty/Cargo.toml](https://github.com/astral-sh/ruff/blob/main/crates/ty/Cargo.toml)) **C**. The `astral-sh/ty` repository holds only release, docs and issues, with Ruff as a git submodule, and releases with dist (`members = ["cargo:./ruff"]`, `packages = ["ty"]`, [dist-workspace.toml](https://github.com/astral-sh/ty/blob/main/dist-workspace.toml)) **C**. The two version lines are independent (Ruff 0.17.0, ty 0.0.87). Wheel sizes: Ruff 10.4 MB, ty 14.5 MB (manylinux x86_64) **M**. No CI check that `ruff` excludes `ty_*` crates was found in Ruff's workflows, which run workspace-wide `cargo deny` and `cargo shear` only **M**.

### 3.4 Wasmtime: one crate with 44 features, a hand-picked check list

- `wasmtime` 50.0.0-rc.1 (2026-10-05) declares 44 features (crates.io API) **M**, among them `cranelift`, `winch`, `pulley`, `runtime`, `component-model`, `gc-*`, `threads`, `pooling-allocator` and `debug`.

## 5. Cargo features, combination testing and product boundaries

### 5.1 Cargo features as the product switch

- The Cargo book says features "should be _additive_. That is, enabling a feature should not disable functionality", and that mutually exclusive features "should be avoided if at all possible, because it requires coordinating all uses of the package in the dependency graph" ([Features, feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification), read 2026-10-14). Removing a feature, or removing one from `default`, is a SemVer-breaking change ([SemVer compatibility](https://doc.rust-lang.org/cargo/reference/features.html#semver-compatibility)) **C**.
- "By default, tests, docs, and other tooling such as Clippy will only run with the default set of features." The book leaves the combination strategy to each project ([Feature combinations](https://doc.rust-lang.org/cargo/reference/features.html#feature-combinations)) **C**.
- **A workspace build unifies features across the packages it selects.** "When a dependency is used by multiple packages, Cargo will use the union of all features enabled on that dependency" ([feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification)). So `cargo build --workspace` builds a shared dependency once with the union of every product's features, and a Collie binary built that way can differ from the same binary built with `cargo build -p collie`. The issue has been open since 2017 ([cargo#4463](https://github.com/rust-lang/cargo/issues/4463), "Feature selection in workspace depends on the set of packages compiled", 36 thumbs-up). The fix is unstable: `-Z feature-unification` with `resolver.feature-unification = "selected" | "workspace" | "package"`, default `"selected"`; `"package"` builds dependencies per package "preferring duplicate builds" ([Cargo unstable: feature-unification](https://doc.rust-lang.org/cargo/reference/unstable.html#feature-unification), tracking [cargo#14774](https://github.com/rust-lang/cargo/issues/14774), open) **C**. Until it is stable, each product binary must be built in its own `cargo build -p <product>` invocation to match what a user's `cargo install` gets. Codex's per-bundle release builds (§3.1) are consistent with that, though its workflow does not give the reason.
- **Feature-chosen editions are what Homebrew gave up.** Homebrew 2.0.0 (2019-02-02) removed every option from homebrew-core because "Formulae with options had to be built from source, could not be tested on our CI system and provided a disproportionate support burden on our volunteer maintainers" ([Homebrew 2.0.0](https://brew.sh/2019/02/02/homebrew-2.0.0/)) **C**. Options survive only in third-party taps.

### 5.2 Spider-rs: 129 features, a handful tested

No `cargo hack` anywhere in its workflows.

Its workspace holds `spider`, `spider_worker`, `spider_cli`, `spider_utils`, `spider_agent`, `spider_agent_types`, `spider_agent_html` and `spider_mcp` ([Cargo.toml](https://github.com/spider-rs/spider/blob/main/Cargo.toml)) **C**. The last GitHub release with assets is v2.52.2 (2026-03-31).

### 5.3 Tokio and cargo-hack

- Tokio 1.53.3 (2026-10-13) has 17 features ([crates.io](https://crates.io/crates/tokio/1.53.3/features)) **M**. Its CI uses `cargo hack` in at least six places ([ci.yml](https://github.com/tokio-rs/tokio/blob/master/.github/workflows/ci.yml), read 2026-10-14) **C**:
  - `cargo hack test --each-feature` for the integration and macro build test crates;
  - `cargo hack check --all --feature-powerset --exclude-features "…" --depth 2 --keep-going`, in a three-way matrix (stable flags, `--cfg tokio_unstable`, unstable plus `io-uring,taskdump,schedule-latency`);
  - `--feature-powerset --depth 2` again for i686, and `--each-feature` for cross targets with `-Zbuild-std` and for `wasm32-unknown-emscripten`, each with an exclusion list;
  - `cargo hack --remove-dev-deps` plus `-Z minimal-versions` checks.
  The workflow has 45 `runs-on` jobs in total.
- cargo-hack v0.6.45 (2026-05-30) options ([README](https://github.com/taiki-e/cargo-hack#readme)) **C**: `--each-feature` runs each feature alone plus `--no-default-features`, default, and `--all-features`; `--feature-powerset` runs every combination, "deduplicate[s] any fully equivalent feature combinations", and recommends `--depth` "when using this flag results in a very large number of feature combinations"; `--group-features`, `--mutually-exclusive-features`, `--at-least-one-of`, `--exclude-features`, `--optional-deps`, `--partition M/N` (split runs across CI jobs) and `--keep-going`. It recommends `--no-dev-deps` to avoid [cargo#4866](https://github.com/rust-lang/cargo/issues/4866).
- **Arithmetic** for 129 features (not run) **M**: the full powerset is 2^129 builds; `--depth 2` is 129 + C(129,2) = 129 + 8,256 = 8,385 builds plus the default, no-default and all-features runs; `--each-feature` is 132. Tokio keeps its powerset tractable with 17 features, exclusions and depth 2.

### 5.4 Proving product A contains none of product B's code

Cargo itself enforces the first boundary: a crate can only name crates it depends on, and the crate graph has no cycles. So "the `collie` crates never depend on `foxhound` crates" is a compile error to break, not a convention. What it does not catch is a heavy dependency reaching Collie through a shared crate, or through a feature turned on in a shared crate. The tools below close that gap.

| Tool | What it proves | How it runs in CI | Who uses it | Limits |
|---|---|---|---|---|
| `cargo tree -i <crate> -e normal -p <product>` | The crate is absent from one product's normal-dependency graph for a given feature set; exits non-zero when absent | uutils coreutils: "Verify ariadne is compiled out" fails if `cargo tree -p coreutils --no-default-features --features feat_os_unix -e normal -i ariadne` succeeds ([CICD.yml](https://github.com/uutils/coreutils/blob/main/.github/workflows/CICD.yml), 2026-10-14) | uutils | Crate-level only; checks a graph, not the linked binary; one feature set per run |
| cargo-deny `[bans] deny` | Named crates are banned from the graph; `wrappers` allows only listed direct parents; `features` deny/allow/exact per crate ([bans config](https://embarkstudios.github.io/cargo-deny/checks/bans/cfg.html)) | `cargo deny --manifest-path crates/<product>/Cargo.toml check bans`: a normal package manifest makes that crate the only root ([CLI common options](https://github.com/EmbarkStudios/cargo-deny/blob/main/docs/src/cli/common.md)); one config per product | Codex's `reqwest` ratchet (§3.1); widespread for licences and advisories (0.20.2, 2026-07-09) | Crate-level; `--features` only for a single crate; a per-product ban list needs one config or invocation per product |

### 5.5 Sharing one protocol between products

- Cargo forbids a product crate from reaching another product's crates, so the shared contract has to live in a crate both depend on. Goodfetch already has one (`goodfetch-protocol`, ADR 0038). Codex does the same: `codex-app-server-protocol` is shared by the CLI and the app server, and `codex-code-mode-protocol` was extracted first, as "shared session, runtime, response, and tool-definition types", before V8 left the main binaries ([#27724](https://github.com/openai/codex/pull/27724)) **C**.
- Rust has no stable ABI, so the protocol crate is shared at build time, not at run time: Bevy deprecated dynamic plugins in 0.14 because "the current dynamic plugin system is unsound and will be removed in 0.15", noting that Rust "may produce incompatible libraries across Rust versions, or even subsequent compilations" ([bevy_dynamic_plugin docs](https://docs.rs/bevy_dynamic_plugin), feedback [bevy#13080](https://github.com/bevyengine/bevy/issues/13080)); its docs point to `stabby` for a stable ABI **C**.

### 5.6 Parts downloaded on first use: DuckDB extensions

- Built-in extensions are "statically linked into the binary"; others are installed once and loaded each session, and autoloading "can install and load the core extensions as soon as they are used in a query" ([extensions overview](https://duckdb.org/docs/current/extensions/overview.html)) **C**.
- Installed extensions live under `~/.duckdb/extensions/<duckdb_version>/<platform>/` and are shared only between clients of "the same DuckDB version"; `extension_directories` exists for "package managers or air-gapped environments"; `INSTALL … FROM '<url>'` and `custom_extension_repository` point at a mirror ([installing extensions](https://duckdb.org/docs/current/extensions/installing_extensions.html)) **C**.
- Moving a part out of the binary broke offline users on upgrade: after DuckDB JDBC 1.5.0.0, `CALL start_ui_server()` "now attempts to automatically download the `ui` extension", failing with `Extension Autoloading Error … Failed to download extension "ui" at URL "http://extensions.duckdb.org/v1.5.0/osx_arm64/ui.duckdb_extension.gz"` ([duckdb-java#623](https://github.com/duckdb/duckdb-java/issues/623), 2026-03-26, open) **C**. ADR 0057 already records why signed, dlopen'ed extensions do not fit a static musl binary or the hardened runtime.

## 6. Release cost per extra executable

### 6.1 Signing and notarization

- Platform-signing facts are in the [platform code signing research](https://github.com/goodfetch/automan/blob/research/platform-code-signing/rnd/research/2026-10-11-platform-code-signing.md) (2026-10-11). The ones that scale with the number of executables:
  - The notary service accepts DMG, signed flat `.pkg` and ZIP; a ticket "can't be stapled" to a ZIP or to a standalone binary, so a bare CLI is checked online ([Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow), as cited there). One ZIP can carry several binaries in one submission, but each Mach-O inside must be signed with the hardened runtime and a timestamp ([Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)) **C**.
  - Windows SmartScreen reputation builds "from the file hash plus the publisher certificate", and each new unsigned version starts from zero ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)) **C**. A second executable is a second file to sign on every release; signed with the same certificate it inherits publisher reputation.
  - Astral (uv, ruff) and Codex sign and notarize from Linux with `rcodesign` and a Key Vault key; that is per file but scripted ([uv sign-release-binaries.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/sign-release-binaries.yml), [codex rust-release.yml](https://github.com/openai/codex/blob/main/.github/workflows/rust-release.yml)) **C**.
- Packaging tools treat each product as its own app: dist (cargo-dist) makes each Cargo package with binaries an "App" with its own archive per target; several binaries of one package ship together in one archive; a bare `v1.0.0` tag releases every package with that version, while `my-app-v1.0.0` releases one ([dist concepts](https://axodotdev.github.io/cargo-dist/book/reference/concepts.html)) **C**.

### 6.2 Debug symbols

- Codex rust-v0.162.1 publishes symbols per product and per target: on aarch64-apple-darwin `codex-symbols-…-app-server.tar.gz` is 267.6 MB beside 346.5 MB for the CLI; Windows x64 symbols are 589.5 MB (GitHub release assets, read 2026-10-14) **M**. So every extra product adds a symbol archive per target, each larger than the binary.
- Bun publishes a `-profile` build per target (145.9–380.2 MB zipped, bun-v1.4.3) **M**, presumably its unstripped variant (**unverified**: Bun's installation docs do not describe profile builds). Bun's docs now say it ships "a single x64 binary per platform", keeping the `-baseline` assets only as aliases ([installation](https://bun.com/docs/installation), read 2026-10-14) **C**. uv 0.13.1, ruff 0.17.0, Deno v2.9.7 and sentry-cli 3.8.0 publish no symbol assets (asset lists, read 2026-10-14) **M**.

### 6.3 Reproducibility

- Because of workspace feature unification (§5.1), a product binary is only reproducible if it is built with the same package selection every time.
- Cargo's `profile.trim-paths` (RFC 3127) went through a call for testing on 2026-09-09 before stabilization; its tracking issue closed on 2026-10-06 ([cargo#12137](https://github.com/rust-lang/cargo/issues/12137)) **C**. Whether it is in a stable Cargo release yet is **unverified**.

### 6.4 CI matrix and the free tier

- GitHub Actions is free for "public repositories that use standard GitHub-hosted runners"; larger runners "are always charged for" ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)) **C**. The Free plan runs 20 concurrent jobs, at most 5 on macOS; a job may run 6 hours; a matrix may generate 256 jobs per run ([Actions limits](https://docs.github.com/en/actions/reference/limits)) **C**.
- ADR 0057 records fat LTO at about 20 minutes per target. A second product binary built in its own `cargo build -p` (needed for the reason in §5.1) roughly doubles release-profile link work per target, unless the products share one binary. That figure is arithmetic, not a measurement.

### 6.5 How a missing part fails

- Codex: a missing code-mode host falls back to direct tools with a one-time warning, or fails closed when configured as required (§3.1) **C**.
- Playwright 1.64.1 throws `Executable doesn't exist at <path>` with a box saying "Looks like Playwright was just installed or updated. Please run the following command to download new browsers:" and the exact install command for the SDK's language, or for `ffmpeg` "Video rendering requires ffmpeg binary" ([registry/index.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/registry/index.ts)) **C**. Issues with that text are among its most commented: [#7249](https://github.com/microsoft/playwright/issues/7249) (caching browsers in CI, 60 comments), [#5767](https://github.com/microsoft/playwright/issues/5767) (21), [#12772](https://github.com/microsoft/playwright/issues/12772) (16), [#33673](https://github.com/microsoft/playwright/issues/33673) (2024-11-19).
- Splitting one part into two variants breaks pipelines that mirror parts: after Playwright split Chromium into `chromium` and `chromium-headless-shell`, a user mirroring browsers from `browsers.json` found the shell missing in 1.50.0 ([#34508](https://github.com/microsoft/playwright/issues/34508), 2025-01-27), and another got `Executable doesn't exist at …/chromium_headless_shell-1200/…` only on 1.58 inside Docker ([#39122](https://github.com/microsoft/playwright/issues/39122), 2026-02-04) **C**.
- Cargo answers a missing subcommand with "no such command: `x`", then "help: view all installed commands with `cargo --list`" and "help: find a package to install `x` with `cargo search cargo-x`" ([cargo main.rs](https://github.com/rust-lang/cargo/blob/master/src/bin/cargo/main.rs)) **C**.
- pandas 3.0.6 names the package to install for a missing optional dependency: "`Import X` failed. … Use pip, conda, or your preferred package management tool to install the X package." ([_optional.py](https://github.com/pandas-dev/pandas/blob/main/pandas/compat/_optional.py)) **C**.

### 6.6 Editions that share a namespace

- opencv-python ships four packages and says "you should **SELECT ONLY ONE OF THEM**. Do not install multiple different packages in the same environment. There is no plugin architecture: all the packages use the same namespace (`cv2`)" ([README](https://github.com/opencv/opencv-python#installation-and-usage)) **C**. Its headless edition still broke headless hosts in 4.13.0.90 ([#1183](https://github.com/opencv/opencv-python/issues/1183), 2026-01-19).
- psycopg2 ships `psycopg2` and `psycopg2-binary` with the same import name ([README](https://github.com/psycopg/psycopg2#installation)) **C**.

### 6.7 What the direct competitors do

- Crawlee layers its crawler on browser libraries as optional peers, not as an edition: `crawlee` 3.18.2 depends on every `@crawlee/*` package and declares `playwright` and `puppeteer` as optional `peerDependencies`; `@crawlee/playwright` does the same (npm metadata, read 2026-10-14) **C**. Crawlee for Python 1.10.4 uses extras: `crawlee[playwright]`, and a `stagehand` extra that pulls Playwright, so a Crawlee handler can hand its page to Stagehand ([PyPI](https://pypi.org/project/crawlee/1.10.4/)) **C**.
- Playwright and Puppeteer each split a core library from the package that downloads browsers: `playwright-core` 1.64.1 (13.66 MB unpacked, no dependencies) under `playwright` (5.03 MB); `puppeteer-core` 25.13.0 (6.01 MB) under `puppeteer` (npm metadata, 2026-10-14) **C**.

## 7. Sizes

### 7.1 What each part costs

Two sets of measurements, both macOS arm64 (`aarch64-apple-darwin`), Rust 1.93.0, release profile with `lto = "thin"` and `strip = true`, each part added to the same Tokio + serde_json baseline and called on input from `argv` so the linker keeps its code (method in §10):
- **ADR 0057's probe** ([binary-size research](https://github.com/goodfetch/automan/blob/research/binary-size-budget/rnd/research/2026-10-12-binary-size-limits-and-costs.md) §3.1, 2026-10-12), cited **C**;
- **this note's probe** (2026-10-14), measured **M**, for the parts that research did not cover (a real CDP client, the TLS provider) and for the Collie set built as one binary.

| Part | Variant | Added to the binary | gzip -9 of the probe | Source |
|---|---|---|---|---|
| Tokio + serde_json | baseline (`tokio` 1.53.3) | 0.62 MB total | 0.29 MB | **M** (0.62 MB in ADR 0057's probe too) |
| SQLite | `rusqlite` 0.40.2 `bundled` | +1.76 MB | — | **C**; SQLite itself is "less than 900KiB" with all features ([about](https://www.sqlite.org/about.html)) |
| CDP, transport only | `tokio-tungstenite` 0.30 | +0.37 MB | — | **C** |
| **CDP, full client** | `chromiumoxide` 0.9.1 with its generated protocol types (`chromiumoxide_cdp`, 111k generated lines) | **+6.17 MB** | 2.53 MB | **M** |
| **rustls, ring provider** | `rustls` 0.23.46 + `tokio-rustls` 0.26.6, `ring` 0.17.14 | **+1.38 MB** | 0.97 MB | **M** |
| **rustls, aws-lc-rs provider** | same, `aws-lc-rs` 1.18.2 (rustls' default) | **+2.82 MB** | 1.62 MB | **M** |
| HTTP + rustls | `reqwest` 0.13.5, aws-lc-rs, http2, compression | +5.15 MB | — | **C** |
| HTTP impersonation | `wreq` (BoringSSL) | +5.49 MB | — | **C** |
| Console server | `axum` 0.8.9 + `tower-http` 0.7.1 | +2.11 MB | — | **C** |
| Default extractor | `dom_smoothie` 0.18.2 | +1.43 MB | — | **C** |
| Filter list engine | `adblock` 0.13.3 | +2.91 MB alone; **+2.60 MB** on top of the Collie set | — | **C**; **M** |
| DuckDB | core, bundled (`duckdb` 1.10506.0) | +33.02 MB | — | **C** |
| V8 | `v8` 152.2.0 prebuilt, jitless; 10.88 MB of it is ICU data | +42.81 MB | ≈15.3 MB (34.5 − 19.2) | **C**; static libraries 38–41 MB gzipped per target ([rusty_v8 v152.2.0](https://github.com/denoland/rusty_v8/releases/tag/v152.2.0)) |

- **The CDP client is the one part the earlier estimate under-counted.** The transport stand-in was +0.37 MB; a client with the whole generated protocol is +6.17 MB **M**. How much of that a Goodfetch CDP crate costs depends on how much of the protocol it generates (STYLE.md already isolates "generated CDP bindings" as their own crate).
- **ring is 1.44 MB smaller than aws-lc-rs** for the same rustls client **M**. `reqwest`'s `rustls` feature pulls aws-lc-rs ([reqwest 0.13.5 Cargo.toml](https://docs.rs/crate/reqwest/0.13.5/source/Cargo.toml)) **C**, so choosing ring means `rustls-no-provider` plus installing the ring provider; the `.crate` sizes differ as much (`aws-lc-sys` 0.46.0 9.66 MB, `ring` 0.17.14 1.50 MB, binary-size research §2.2).

### 7.2 Measured Collie set, and the estimate around it

**One binary with the Collie set** (`mimalloc`, `rusqlite` bundled, `chromiumoxide`, `reqwest` with rustls/aws-lc-rs, http2 and compression, `axum` + `tower-http`, `dom_smoothie`) is **16.02 MB stripped, 6.81 MB gzip -9**; with `adblock` added, **18.63 MB, 7.79 MB gzip** **M**. The sum of the same parts measured one at a time is 17.34 MB, so shared code makes the combined binary 1.3 MB (7.6%) smaller than the sum **M** (the earlier research found 0.8 MB on its set).

| Build | How it is obtained | macOS arm64, stripped | gzip -9 |
|---|---|---|---|
| Collie core: page driving, run state, HTTP for model calls, Console server, extraction | measured as one binary | **16.0 MB** | 6.8 MB |
| + filter list engine (Clean-up rules code) | measured as one binary | **18.6 MB** | 7.8 MB |
| + embedded data: Clean-up rules (3.67 MB zstd), Console assets (0.40 MB brotli) | + ADR 0057's figures | ≈ 22.7 MB | ≈ 11.9 MB (the data is already compressed) |
| + V8 for Code mode and Script Hooks | + 42.8 MB (prebuilt, measured separately) | **≈ 65 MB** | ≈ 27 MB |
| Foxhound, i.e. today's full `goodfetch` | ADR 0057's projection | 105–130 MB | 40–50 MB |

So, before the engine's own code, a Collie binary without V8 is about **14–22% of the full binary**, and with V8 about **47–62%**. V8 is the whole question: it is two thirds of a Collie binary that keeps Code mode and Script Hooks (ADR 0051), and DuckDB plus the Sinks and `wreq` (≈ 60 MB together) are what Foxhound adds on top.

**Error bars, largest first.**
- **The engine's own code is not counted** in either column (as in ADR 0057's projection). It adds the same order of size to both products and so shifts the ratios toward 1.
- **V8 built from source with its sandbox (ADR 0051) has no Goodfetch measurement.** For scale, Codex's `codex-code-mode-host`, which is V8 150.4.0 with `v8_enable_sandbox`, ICU data from `deno_core_icudata` and a tonic/axum host, unpacks to 65.4 MB on macOS arm64, 66.9 MB on aarch64 musl and 74.0 MB on x86_64 musl (gzip trailers of the rust-v0.162.1 assets) **M**. So the V8 term could be anywhere from +42.8 MB to roughly +60 MB; how much of the host is V8 was not measured.
- **Platform spread.** Static musl is 8–12% larger for V8 (prior research) and Codex's host is 13% larger on x86_64 musl than on macOS arm64 **M**; Deno's `deno` is 18% larger on x86_64 Linux than on macOS arm64 (95.8 vs 81.0 MB) **M**. Windows was not measured.
- **CDP coverage.** +0.4 MB (transport only) to +6.2 MB (whole protocol), as above.
- **Profile.** Fat LTO with one codegen unit was −4.4% on the full probe (prior research); `opt-level = "z"` on a lean product is the trade uv makes for `uv_build` (§3.3).
- **Overlap.** Adding parts one at a time over-counts by 4–8%.
- Load on the host (load average 30–40 during the builds) affects build times only, not sizes.

**Reference points** for a lean product beside a full one, unpacked **M**: uv 37.9 MB and `uv_build` 3.4 MB (9%); Codex CLI 294.4 MB and app server 226.9 MB (77%, x86_64 musl); Deno 81.0 MB and `denort` 67.6 MB (83%, macOS arm64); Zed app 118–131 MB and remote server 34–41 MB compressed. The browser download dwarfs every Collie figure: Chrome headless shell is about 124 MB compressed (ADR 0057).

**Where the Collie set's code goes.** `cargo bloat --crates` on the same set built without `strip` attributes 2.6 MiB of 10.5 MiB of `.text` (25%) to `chromiumoxide` and `chromiumoxide_cdp`, the largest share, then `std` (1.7 MiB), `aws_lc_sys` (0.7 MiB), `reqwest`, `h2` and `rustls` (0.4 MiB each); 1.9 MiB is unattributed, which includes SQLite's and other C code **M**. cargo-bloat warns its crate attribution is "a result of guesswork".

## 8. Implications for Goodfetch

Considerations for [#454](https://github.com/goodfetch/automan/issues/454) and the other tickets of [#447](https://github.com/goodfetch/automan/issues/447); none of this is a decision.

- **The working hypothesis has direct precedents.** Codex (`codex` links the `codex-app-server` crate), uv (the `uv` executable "includes a copy of the build backend" that also ships alone as `uv_build`) and Deno (`deno` and `denort` share `deno_lib`) each ship a larger product that contains a smaller one, from one workspace, at one version, with the smaller one as its own package and binary. None of them makes the smaller product a Cargo-feature edition of the larger. So ADR 0038's "capabilities are settings, never Cargo features" can survive the split unchanged if each product is a binary crate with its own dependency set, and a Foxhound capability is absent from Collie because Collie's crates do not depend on it, not because a feature is off.
- **Each product binary needs its own `cargo build -p` per target.** Feature unification (§5.1) means a Collie binary built in the same invocation as Foxhound can contain features only Foxhound needs. Codex and uv build the smaller product in a separate invocation; Deno builds both together (acceptable there because `denort` is a pure subset with the same features). The cost is a second release-profile build per target (ADR 0057 measured fat LTO at about 20 minutes per target), either in the same job, as uv does on standard runners, or in a second job, as Codex does on larger runners that a free-tier public repository cannot use (ADR 0076). The same applies to tests: a Collie test run whose invocation includes Foxhound crates tests the union, not what ships.
- **The CI boundary check is cheap and has a production precedent.** Cargo already makes "a Collie crate depends on a Foxhound crate" impossible to express without editing a manifest. What it does not stop is a heavy dependency reaching Collie through a shared crate. uv's pattern, `cargo deny --manifest-path <product>/Cargo.toml check bans` with a per-product `deny.toml` banning named crates (here `duckdb`, `libduckdb-sys`, `wreq`, the sink libraries, `parquet`), runs in seconds; rustc's allowlist is the stricter variant. A workspace-hack crate (cargo-hakari) would defeat the boundary and fits STYLE.md's crate rules poorly. ADR 0057's Size budget, measured per product, is the artefact-level backstop.
- **V8 decides how different the two binaries are.** Measured: the Collie set without V8 is 16.0–18.6 MB (6.8–7.8 MB gzip); with V8 about 65 MB. So Collie is about a fifth of Foxhound without Code mode and Script Hooks, and about half with them. Either way the 124 MB compressed browser is most of a Collie user's download.
- **Moving V8 into a companion executable does not shrink a download unless the companion is optional.** Codex split V8 out and still ships the host in both packages. What the split bought was a process boundary, which ADR 0051 already gets from running the worker as the same binary. Codex's three months of issues (omitted by WinGet, not notarized, stale paths after upgrade, version skew, start failures) are the costs ADR 0057 named when it rejected V8 as a download; they now have field evidence.
- **If any part does leave the binary,** the precedents say: version-lock it to the engine and check at handshake with a tolerant decoder (Codex's `unknown field` skew, Nushell's semver rule, Zed's exact match); resolve it relative to the install layout and test missing and stale paths; make every channel (npm platform packages, wheels, Homebrew, WinGet, OCI images) carry it; list it in ADR 0039's release gate, which already verifies every signed file; offer an override and an offline seed (`DENORT_BIN`, `extension_directories`, `upload_binary_over_ssh`), as Goodfetch already does for browsers; and decide per setting whether a missing part falls back with a warning or fails closed (Codex).
- **A setting or command that needs the other product should fail by naming the fix.** The patterns found: ripgrep's "PCRE2 is not available in this build of ripgrep", Cargo's "no such command" with an install hint, pandas naming the package, Playwright printing the install command. For Goodfetch this would be a typed Error code (ADR 0038) naming the product that has the capability. ADR 0028's settings schema then needs to say, per key, which product honours it.
- **Release cost per product, arithmetic for ADR 0024's six targets:** six more release builds, six more signed and (on macOS) notarized executables, six more debug-symbol archives (Codex's are 200–600 MB each, under GitHub's 2 GiB per asset), and on Windows two more Artifact Signing signatures per nightly. ADR 0057's ceilings and increase checks would need a row per product.
- **Packaging two products side by side** has known pitfalls: opencv's editions share the `cv2` namespace and must not be co-installed; psycopg2 the same. Crawlee's layering (the crawler declares the browser library as an optional peer) and Turborepo's "the global binary defers to" the local one are two ways to make two installs cooperate rather than collide. This belongs to the map's "coexistence on one machine" item.
- **Two version lines are possible but not required.** Astral releases Ruff and ty from shared crates on separate version lines, with ty's packaging in its own repository; Codex, uv/`uv_build` and Deno/`denort` keep one version. The map's recommended single version line matches the latter group.
- **The Browser host and Cloud engines** have a precedent in Zed's remote server: a subset binary of the same workspace, 34–41 MB compressed beside a 118–131 MB app, fetched to the remote host at the exact client version on first use.

## 9. Unverified / open

- **Size of V8 built from source with its sandbox** (ADR 0051): no Goodfetch measurement. Codex's V8 host (65–74 MB) includes other crates; how much of it is V8 was not measured.
- **Size of the engine's own code**, per product: not measured, as in ADR 0057.
- **Windows and musl sizes** of this note's probe: macOS arm64 only.
- **An in-house CDP crate generating only the domains Goodfetch uses**: its size was not measured; `chromiumoxide` generates the whole protocol.
- **Why Codex builds its CLI and app-server bundles in separate jobs** (feature unification, parallelism or runner limits): its workflow does not say.
- **Whether Codex checks that the app-server binary lacks CLI-only crates**: only `deny.toml` and the release workflows were read.
- **Whether `profile.trim-paths` is in a stable Cargo release**: its tracking issue [cargo#12137](https://github.com/rust-lang/cargo/issues/12137) closed on 2026-10-06, and the stable Cargo reference's profiles page did not mention it on 2026-10-14.
- **Deno's `denort-quickjs` for v2.9.7**: only an HTTP 200 from `dl.deno.land` was checked; it is not among the GitHub release's assets.
- **Bun's `-profile` assets**: assumed to be unstripped builds; Bun's docs do not describe them.
- **The exact Wasmtime error** when a module is compiled without a compiler feature: the docs say only that errors are "worse".
- **User complaints about Biome, Turborepo and Sentry CLI packaging** were not searched.
- **Ruff/ty**: no per-product dependency check was found; one may exist outside the workflows read.
