# Two Products on one machine: shared daemons, caches and state

Research of October 15, 2026. All sources were read on that date. Code was read at the tagged release named in each section. A line that says "from the source" means the behaviour was read in the code, not run. Nothing was installed or executed against these tools for this note.

**Why this note exists.** Goodfetch ships two Products on one version line: Collie, which drives browser pages, and Foxhound, a crawler whose executable contains Collie's code. Both carry a per-user Daemon with a local web Console, a per-user Run index (SQLite), Schedules, a Usage ledger and a per-user browser cache. Each cached browser takes about 150 MB, and a new build arrives every two weeks. Four questions are open. What do the two Products share when one user installs both? Do one or two Daemons serve them? How does a browser-cache clean-up avoid deleting a build another install still needs? What happens when the two Products are installed at different versions? This note gathers how comparable tools handle shared daemons, caches and state across tools and versions. Nothing here is adopted.

## 1. Playwright's browser cache (`ms-playwright`)

### One cache for every Playwright on the machine

- All Playwright installations of one user share one registry directory by default: `~/Library/Caches/ms-playwright` on macOS, `~/.cache/ms-playwright` (or `$XDG_CACHE_HOME`) on Linux, `%LOCALAPPDATA%\ms-playwright` on Windows. `PLAYWRIGHT_BROWSERS_PATH` overrides it. The value `0` selects a private folder inside the package (`.local-browsers`), which the docs call a "hermetic install". [registry/index.ts L380-417](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L380-L417), [browsers.md "Managing browser binaries", "Hermetic install"](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/docs/src/browsers.md#L953-L1143).
- Browsers are stored one directory per browser revision, for example `chromium-1228`, `firefox-1532`. Each Playwright build pins exact revisions in its `browsers.json` and only looks for those revisions. (Directory naming: [index.ts L470-480](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L470-L480).)
- The link that registers an installation names the `playwright-core` package root (`PACKAGE_PATH = packageRoot`, [index.ts L37-44](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L37-L44)). `@playwright/test@1.64.1` depends on `playwright@1.64.1`, which depends on `playwright-core@1.64.1` (npm registry). So each copy of `playwright-core` on disk is one "installation" for the clean-up, whichever wrapper brought it.
- Other bindings embed the same Node driver. playwright-python runs `playwright/driver/package/cli.js` inside the Python package, so its installation path is in the virtual environment ([`_driver.py`](https://github.com/microsoft/playwright-python/blob/387a8a943bb397962f19085c376a301b440029b6/playwright/_impl/_driver.py)). playwright-java extracts the driver into a new temporary directory (`playwright-java-*`, deleted on JVM exit) and runs `install` from it each time it starts, unless `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` is set ([DriverJar.java L36-L112](https://github.com/microsoft/playwright-java/blob/4653824d88e3516ad31523f04d4d3e0cdcaf503d/driver/src/main/java/com/microsoft/playwright/impl/driver/jar/DriverJar.java#L36-L112)). That `install` runs the clean-up described below.
- `@playwright/mcp` pins its own prerelease of `playwright` and `playwright-core`. `@playwright/mcp@0.0.78` depends on `1.62.0-alpha-1783623505000`, and `0.0.83` (latest) depends on `1.64.0-alpha-1790635538000` (npm registry, read 2026-10-15). It therefore asks for browser revisions that no stable `playwright` release installs.

### How the automatic clean-up decides

From the source ([`Registry.install`, L934-L1014](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L934-L1014); [`_validateInstallationCache` and `_deleteStaleBrowsers`, L1187-L1259](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L1187-L1259)):

1. `install` takes a lock file, `__dirlock`, in the registry directory. It retries for about ten minutes and then fails with "An active lockfile is found".
2. It writes `.links/<sha1(package path)>`, a file whose content is the package path. The comment reads: "Create a link first, so that cache validation does not remove our own browsers."
3. Unless `PLAYWRIGHT_SKIP_BROWSER_GC` is set or `--no-remove` was passed, it reads every link. For each one it loads `browsers.json` from the linked path and keeps the revisions listed there, but only if the browser directory holds its `INSTALLATION_COMPLETE` marker. A link whose path is gone or unreadable is a "broken link". It protects nothing and is deleted.
4. Every browser directory in the registry that no live link keeps is deleted, with the message "Removing unused browser at …".

What this design implies (inference from the code above):

- **Liveness is "the package directory still exists on disk", checked only at install time.** The clean-up runs during `install` and `uninstall`. Nothing runs when a browser launches. Running browser processes are not checked, and only the installing process takes the lock.
- **One reference per path, not per version.** The link file is named after the hash of the package path. Upgrading Playwright in the same `node_modules` path replaces what that link protects. The previous revisions become unreferenced and are deleted on the next install anywhere on the machine.
- **Any path that disappears frees its browsers**: a deleted `node_modules`, an `npx` cache entry, a removed virtual environment, playwright-java's temporary directory after the JVM exits. The same applies to a path that is not visible from the process doing the clean-up, for example a cache volume shared between containers (unverified scenario, consistent with the code).

### Opt-outs and removal commands

- `PLAYWRIGHT_SKIP_BROWSER_GC=1` turns the clean-up off for `install` ([index.ts L960](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L960)).
- `playwright install --no-remove` does the same for one command. It was added in [PR #42222](https://github.com/microsoft/playwright/pull/42222) (merged 2026-08-12, first released in v1.63.0) to answer [#42214](https://github.com/microsoft/playwright/issues/42214). In that issue, a user who switched git branches pinned to different Playwright versions saw `chromium-1228`, `firefox-1532` and `webkit-2311` removed on every install. The docs: "Playwright keeps track of the clients that use its browsers. When there are no more clients that require a particular version of the browser, that version is deleted from the system." ([browsers.md, Stale browser removal](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/docs/src/browsers.md#L1145-L1153)).
- `playwright uninstall` deletes only the current installation's link and then runs the clean-up. `uninstall --all` deletes every link first, so every browser is removed. `uninstall` ignores `PLAYWRIGHT_SKIP_BROWSER_GC` (`delete process.env.PLAYWRIGHT_SKIP_BROWSER_GC`). After a plain `uninstall` it prints that N browsers are "used by other Playwright installations" ([installActions.ts L145-L153](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/cli/installActions.ts#L145-L153), [index.ts L1016-L1032](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/registry/index.ts#L1016-L1032), [program.ts L74-L107](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/cli/program.ts#L74-L107)).
- `playwright install --list` prints the browsers of every Playwright installation found through `.links`.
- `@playwright/mcp install-browser` and `playwright-cli install-browser` rewrite the argument to `install` and run the same program, so they run the same clean-up ([cli-client/program.ts L347-L354](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/cli-client/program.ts#L347-L354)).

### Issue #40995: the clean-up deleted browsers the user still needed

[microsoft/playwright#40995](https://github.com/microsoft/playwright/issues/40995) exists and matches the topic. It was opened 2026-05-25 against `@playwright/test` 1.59.1 on Ubuntu, in a container. Its title: "Playwright keeps deleting downloaded browsers automatically and this is an absolutely terrible default behavior".

- **What happened.** The reporter installed browsers and ran tests. After "Stop the process / restart environment / reinstall dependencies / switch containers", the next run failed with `browserType.launch: Executable doesn't exist`, and Playwright asked to download the browsers again. The reporter named monorepos, several Playwright versions, CI, containers and "automation agents" as affected cases. They asked for opt-in garbage collection and a manual `npx playwright prune`.
- **Maintainer answer.** Skn0tt (Contributor), 2026-05-26: the clean-up "runs during `playwright install`, and detects which browsers are still needed via heuristics based on file presence". It is "finely tuned … for the common case", and "since it's right in the heart of the project we're unlikely to touch it". The recommendation was to keep `PLAYWRIGHT_SKIP_BROWSER_GC` set and run `npx playwright uninstall --all` by hand when disk runs short. The issue was closed as *not planned* on 2026-06-01.
- **Why it happened** (reading of the v1.64.1 source above, not confirmed by the maintainer for this exact setup). Reinstalling dependencies, or switching to a container where the earlier package path does not exist, breaks the earlier link or replaces what it points to. The next `install` from any Playwright installation sharing the cache then sees those revisions as unreferenced and deletes them. The code has no notion of "still in use".
- **Follow-up.** Ten weeks later the project added `--no-remove` (v1.63.0, above) after a feature request with the same root cause. The default did not change.

### Issue #41871: `@playwright/mcp` asked for browsers the project had not installed

[microsoft/playwright#41871](https://github.com/microsoft/playwright/issues/41871) exists and matches the topic. It was opened 2026-07-19: "Playwright MCP Server Fails in LM Studio: Browser Version Mismatch + Electron Env Var Propagation Failure". Setup: Windows Server 2022, LM Studio 0.4.19, Node 24.18.0.

- **What happened.** The reporter ran `npm install -g @playwright/mcp`, then `npx playwright install chromium firefox`. That `npx` resolved the standalone `playwright@1.61.1`, which installed `chromium-1228` and `firefox-1532`. `@playwright/mcp@0.0.78` bundles `playwright-core@1.62.0-alpha-1783623505000`, which expects `chromium-1232` and `firefox-1534`. The MCP server started and registered its tools. The first `browser_navigate` failed with `Browser "firefox" is not installed. Run npx @playwright/mcp install-browser firefox`. The MCP's error wrapper had swallowed the original "Executable doesn't exist at <path>" message, which named the expected version directory. A second, separate problem: LM Studio (Electron) did not pass `PLAYWRIGHT_BROWSERS_PATH` to the processes the MCP server started. The workaround was to run the bundled `playwright-core/cli.js install` from inside the MCP package.
- **Maintainer answer.** dcrousso merged [PR #41941](https://github.com/microsoft/playwright/pull/41941) on 2026-07-23. Its commit message: the expected path "holds the version-specific directory (e.g. `firefox-1534`), which is what tells a genuinely missing install apart from a version mismatch". The fix keeps that path in the error ([browserFactory.ts L278-L292](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/mcp/browserFactory.ts#L278-L292)). dgozman (Collaborator) closed the issue on 2026-07-27 as *not planned*: "This works as intended - the error message is clear and the suggested command fixes the issue." He added that since v1.62, `npx playwright mcp` ships in the `playwright` package itself, which "should help with the versioning".
- **Why it happened.** Each package build pins exact browser revisions. Two Playwright distributions at different versions share one cache, but each finds only its own revisions. An install run through one distribution never satisfies the other.

### Playwright's own daemon and local UI (relevant to question 9)

- `playwright-cli` keeps per-workspace browser sessions served by a daemon. Session files live in `<cache>/ms-playwright/daemon/<sha1(workspace)[0:16]>/` ([cli-client/registry.ts L145-L198](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/cli-client/registry.ts#L145-L198)). Version rule: a client may drive a session only if the client's version is greater than or equal to the session's. Otherwise it fails with "Client is vX, session 'name' is vY. Run … open to restart the browser session." The listing marks such sessions `[incompatible please re-open]` ([session.ts L41-L48](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/cli-client/session.ts#L41-L48), [output.ts L410-L414](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/cli-client/output.ts#L410-L414)).
- The dashboard is a per-user singleton. It listens on a fixed Unix socket, `$TMPDIR/pw-<sha1(user)[0:8]>/dashboard/app.sock` (a named pipe on Windows). A second launch, of any version, connects to that socket, sends its options and exits ("Dashboard is running pid=…"). The handshake carries no version check ([dashboardApp.ts L206-L300](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/tools/dashboard/dashboardApp.ts#L206-L300), [utils/fileUtils.ts L134-L150](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/utils/fileUtils.ts#L134-L150)). So the first version to start serves every later caller until it exits.

## 2. Puppeteer's cache (`~/.cache/puppeteer`, `@puppeteer/browsers`)

- **Shared location.** "Starting in v19.0.0, Puppeteer stores browsers in `~/.cache/puppeteer` to globally cache browsers between installation." The same paragraph warns that this breaks when `puppeteer` is packed in a build step and moved, and shows `cacheDirectory` in `.puppeteerrc` as the fix ([configuration.md L98-L115](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/docs/guides/configuration.md#L98-L115)).
- **No automatic clean-up.** The install path never removes other builds. The only deletion in `install.ts` is the downloaded archive after extraction ([install.ts L530](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/packages/browsers/src/install.ts#L530)). Builds accumulate, one directory per `<platform>-<buildId>`.
- **Removal commands.** The CLI (`npx @puppeteer/browsers …`, also `npx puppeteer browsers …`) has `install`, `launch`, `clear`, `list` and `bisect`. `clear` asks for confirmation, then deletes the whole cache directory recursively ([CLI.ts L447-L471](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/packages/browsers/src/CLI.ts#L447-L471), [Cache.ts L223-L230](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/packages/browsers/src/Cache.ts#L223-L230)). There is no per-build `uninstall` command in the CLI. A programmatic `uninstall({browser, buildId, cacheDir})` removes one build and its aliases from `.metadata` ([install.ts L596-L610](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/packages/browsers/src/install.ts#L596-L610), [Cache.ts L232-L262](https://github.com/puppeteer/puppeteer/blob/d1b9a2162a0113356db5093f055b4a2e1979c6a8/packages/browsers/src/Cache.ts#L232-L262)).
- **Open request.** [puppeteer#15418](https://github.com/puppeteer/puppeteer/issues/15418), open since 2026-09-04, asks for `clear --old` or `--keep N`, because CI teams run `clear` before each install and re-download Chrome every deployment. The maintainer OrKoN noted that "old" can mean the newest local version, the remote latest, or "the pinned browsers" of the Puppeteer version running the command. He suggested keying the CI cache by Puppeteer version instead.

## 3. uv, Ruff and ty (Astral)

### uv's cache across uv versions

- **Versioned buckets.** The cache is split into buckets whose names carry a format version. In 0.13.1: `wheels-v7`, `sdists-v10`, `simple-v26`, `flat-index-v6`, `interpreter-v4`, `environments-v2`, `archive-v0`, `files-v0`, `builds-v0`, `python-v1`, `binaries-v0`, `git-v1`, `osv-v1` ([uv-cache/src/lib.rs L1297-L1322](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-cache/src/lib.rs#L1297-L1322)). The docs: a release with a breaking cache-format change bumps the bucket version, so "multiple versions of uv can safely read and write to the same cache directory". Within one bucket version, changes are "both forwards- and backwards-compatible". Two uv versions on different bucket versions duplicate entries instead of sharing them ([cache.md, Cache versioning](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/docs/concepts/cache.md#L212)).
- **Disposable versus persistent data.** uv keeps the cache ("disposable, but is useful to be long-lived") apart from the persistent data directory (`$XDG_DATA_HOME/uv` or `~/.local/share/uv`), which holds installed tools and Pythons ([storage.md](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/docs/reference/storage.md)).
- **Concurrent processes.** Every uv command opens the cache with a *shared* file lock on `<cache>/.lock` ([`Cache::init`, L523-L557](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-cache/src/lib.rs#L523-L557)). `uv cache clean` and `uv cache prune` need the *exclusive* lock on the same file ([`with_exclusive_lock`, L233-L264](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-cache/src/lib.rs#L233-L264)). The docs: "uv blocks cache-modifying operations while other uv commands are running", with a 5-minute default wait set by `UV_LOCK_TIMEOUT`, and `--force` to skip the lock. Installing into a virtual environment takes a separate lock on that environment. Readers and writers otherwise run concurrently ([cache.md, Cache safety](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/docs/concepts/cache.md#L126-L136)). If the file system does not support shared locks, uv warns of "reduced parallel process safety with `uv cache clean` and `uv cache prune`" and continues.
- **`uv cache clean`** removes every entry, or every entry for the named packages. "The directory and its lock file remain so that other uv processes can safely share the cache." ([cache.md, Clearing the cache](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/docs/concepts/cache.md#L138-L150)).
- **`uv cache prune`** ([`Cache::prune`, L678-L828](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-cache/src/lib.rs#L678-L828)), in order:
  1. It deletes every top-level directory that is not a bucket name known to *the running uv* ("outdated cache buckets (e.g., `wheels-v0`, when latest is `wheels-v1`)"), plus stray files.
  2. It deletes all cached project environments (recreated on demand).
  3. It deletes temporary build environments.
  4. With `--ci`, it also deletes unzipped pre-built wheels but keeps wheels built from source.
  5. It deletes archives no longer referenced from the remaining buckets, and content files with one hard link left.
- **Cross-version consequence** (inference from step 1). Prune decides what is "unused" from the bucket list compiled into the running binary. A newer uv's prune deletes the buckets an older uv still on the machine uses. An *older* uv's prune would delete a newer uv's buckets, because their names are unknown to it. Each side then rebuilds its entries on next use. This costs time and bandwidth, not correctness, because the cache is disposable.
- **Tool binaries in uv's cache.** uv downloads standalone Ruff, ty and uv binaries into the `binaries-v0` bucket ("Downloaded tool binaries (e.g., Ruff)"). In 0.13.1 the default constraint for Ruff is `>=0.15,<0.16`, and for ty `>=0.0,<0.1` ([uv-bin-install/src/lib.rs L36-L66](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-bin-install/src/lib.rs#L36-L66)). Which commands use this (for example a `uv format` command) was not checked.

### Ruff's `.ruff_cache`

- Layout: `<cache_dir>/<ruff version>/<hash of package root and settings>`, with `CACHEDIR.TAG` and a `.gitignore` at the root ([ruff/src/cache.rs L94-L99](https://github.com/astral-sh/ruff/blob/5b27c1ccfaa230fb195855f5cf3404a21e3379cd/crates/ruff/src/cache.rs#L94-L99), [L374-L392](https://github.com/astral-sh/ruff/blob/5b27c1ccfaa230fb195855f5cf3404a21e3379cd/crates/ruff/src/cache.rs#L374-L392)). Each Ruff version has its own directory, so versions never read each other's entries. Within a version, file entries unseen for 30 days are dropped on save. Writes go to a temporary file renamed into place, against interrupted writes and "races between different ruff" processes ([L160-L216](https://github.com/astral-sh/ruff/blob/5b27c1ccfaa230fb195855f5cf3404a21e3379cd/crates/ruff/src/cache.rs#L160-L216)).
- Ruff never deletes another version's directory; old version directories accumulate. `ruff clean` walks the current directory tree and removes every `.ruff_cache` it finds, all versions included ([commands/clean.rs](https://github.com/astral-sh/ruff/blob/5b27c1ccfaa230fb195855f5cf3404a21e3379cd/crates/ruff/src/commands/clean.rs)). The location is set by `--cache-dir` or `RUFF_CACHE_DIR`.

### Shared state or daemon between uv, Ruff and ty

- Nothing found. They are separate binaries with separate state: uv's per-user cache and data directories, Ruff's per-project `.ruff_cache`, and for ty, no documented on-disk cache (its documented environment variables are `TY_CONFIG_FILE`, `TY_LOG`, `TY_LOG_PROFILE`, `TY_MAX_PARALLELISM` and `TY_OUTPUT_FORMAT`; [environment.md](https://github.com/astral-sh/ty/blob/ea4c3d27376773ffe9237fe72a917ec766095d8e/docs/reference/environment.md)). Ruff and ty each run their own language server (`ruff server`, `ty server`), started by the editor; no shared daemon exists ([ty editors.md](https://github.com/astral-sh/ty/blob/ea4c3d27376773ffe9237fe72a917ec766095d8e/docs/editors.md)). The only links: uv can install them as tools (`uv tool install ty`), and uv can download their binaries into its cache (above).

## 4. Gradle

### One user home, many versions

- "It is common to share a single Gradle User Home between multiple versions of Gradle." "Different versions of Gradle will perform maintenance on only the version-specific caches associated with each version", while "some caches are shared between versions" ([Gradle-managed directories, 9.8.1](https://docs.gradle.org/9.8.1/userguide/directory_layout.html)).
- Version-specific caches live under `caches/<gradle-version>/` (generated Gradle jars, compiled Kotlin and Groovy DSL scripts). Shared caches live directly under `caches/`, each name carrying a layout version: `modules-2` (downloaded dependencies), `jars-9`, `transforms-3`, `build-cache-1` (same page).
- The shared caches' layouts change with Gradle versions, and the code keeps a full history. `CacheLayout.META_DATA`, for example, maps Gradle versions to metadata layouts: `.changedTo(106, "8.2-milestone-1")`, `.changedTo(107, "8.11-rc-1")` ([CacheLayout.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/platforms/software/dependency-management/src/main/java/org/gradle/api/internal/artifacts/ivyservice/CacheLayout.java)).

### Daemon: one per compatible request, never shared across versions

- "Currently, a given Gradle version can only connect to Daemons of the same version." A daemon is reused when it is idle and compatible. Compatibility is "based on exact matches" of the requested Java version, JVM attributes and JVM properties, plus the Gradle version. Otherwise Gradle starts a new daemon. Daemons stop after 3 hours idle or when system memory runs low ([Gradle Daemon, 9.8.1](https://docs.gradle.org/9.8.1/userguide/gradle_daemon.html)).
- The registry is per version: `DaemonDir` puts it at `<user home>/daemon/<GradleVersion.current()>/registry.bin` ([DaemonDir.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/platforms/core-runtime/daemon-protocol/src/main/java/org/gradle/launcher/daemon/registry/DaemonDir.java)). A client never even sees other versions' daemons. Within one version, `DaemonCompatibilitySpec` rejects a daemon whose JVM, daemon options, process priority, agent status or native-services mode differ ([DaemonCompatibilitySpec.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/platforms/core-runtime/daemon-protocol/src/main/java/org/gradle/launcher/daemon/context/DaemonCompatibilitySpec.java)).
- `gradle --stop` "terminates all Daemon processes started with the same version of Gradle used to execute the command." Daemons of other versions must be killed by PID (same docs page).

### Automatic clean-up that never deletes what another version uses

- When it runs: by default in the background when a daemon stops, at most once every 24 hours. With `--no-daemon` it runs in the foreground after the build. `Cleanup.DISABLED` or `Cleanup.ALWAYS` can be set in an init script; this can only be configured there ([directory_layout.html](https://docs.gradle.org/9.8.1/userguide/directory_layout.html)).
- Defaults: version-specific caches of release versions are deleted after 30 days unused, snapshots after 7. Downloaded resources after 30 days, created resources after 7, local build cache entries after 7, daemon logs after 14. "Unused distributions are deleted." Since Gradle 8.0 these retention periods can be changed (`removeUnusedEntriesAfterDays`), and "if the retention period is not customized, all versions that perform cleanup will have the same retention periods" (same page).
- How "in use" is decided, from the source:
  - **Version-specific caches.** A Gradle version only ever deletes the directories of *older* versions: `if (cacheDir.getVersion().compareTo(GradleVersion.current()) >= 0) return false`. It deletes one only when the marker file `fileHashes/fileHashes.lock` in that directory has not been touched for the retention period. At least one snapshot per base version is kept ([VersionSpecificCacheCleanupAction.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/subprojects/core/src/main/java/org/gradle/cache/internal/VersionSpecificCacheCleanupAction.java)).
  - **Shared caches.** The set of Gradle versions "in use" is the set of `caches/<version>/` directories still present ([UsedGradleVersionsFromGradleUserHomeCaches.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/platforms/core-runtime/versioned-cache/src/main/java/org/gradle/internal/versionedcache/UsedGradleVersionsFromGradleUserHomeCaches.java)). A shared cache directory such as `modules-N` is deleted only if its layout version is *older than the current latest* and *no used Gradle version older than the current one maps to it* ([UnusedVersionsCacheCleanup.java](https://github.com/gradle/gradle/blob/39daf39feb60a18b1b6ddccde53366522fef516f/platforms/core-runtime/versioned-cache/src/main/java/org/gradle/internal/versionedcache/UnusedVersionsCacheCleanup.java)). An older Gradle never deletes a newer layout, because it only deletes layouts older than its own latest.
  - **Wrapper distributions.** These are "in use" when there is a "corresponding version-specific cache directory" (docs, above).
- Net effect: two steps. A version's own cache expires after N days without use. Only then do the shared layouts and distributions it alone needed become deletable. Each step is decided by a Gradle newer than the data it deletes, using a version-to-layout table compiled into it.

## 5. Docker: one engine, many clients, one contested socket

### API version negotiation

- From the docs: "If a client connects to an older version of the Docker Engine, it negotiates the highest version of the API supported by both the client and daemon, downgrading to an older version of the API if necessary." A client newer than the daemon "can request API endpoints that the daemon doesn't know about". A daemon newer than the client keeps serving older API versions. `DOCKER_API_VERSION` forces a version and "disables API version negotiation". The current engine (29.8.2 in the docs example) serves API 1.56 with a minimum of 1.40 ([Engine API docs](https://docs.docker.com/reference/api/engine/)).
- **Which side downgrades.** The client does. It pings the daemon, reads the daemon's API version and lowers its own: `// if server version is lower than the client version, downgrade` ([client/client.go L337-L363](https://github.com/moby/moby/blob/b26fb77d3e7b01f9d21b89539c1ab428f5ca431f/client/client.go#L337-L363); client range `MaxAPIVersion = "1.56"`, `MinAPIVersion = "1.40"`, [L105-L115](https://github.com/moby/moby/blob/b26fb77d3e7b01f9d21b89539c1ab428f5ca431f/client/client.go#L105-L115)). The daemon serves any request version within its range and rejects the rest with "client version X is too old. Minimum supported API version is Y, please upgrade your client to a newer version" or "client version X is too new. Maximum supported API version is Y" ([daemon/server/middleware/version.go L55-L62](https://github.com/moby/moby/blob/b26fb77d3e7b01f9d21b89539c1ab428f5ca431f/daemon/server/middleware/version.go#L55-L62)). The daemon's default minimum is 1.40. `DOCKER_MIN_API_VERSION` can lower it to 1.24 ([daemon/config/config.go L65-L71](https://github.com/moby/moby/blob/b26fb77d3e7b01f9d21b89539c1ab428f5ca431f/daemon/config/config.go#L65-L71)).

### Several products wanting `/var/run/docker.sock`

- The default Docker context talks "to a daemon through the local `/var/run/docker.sock` Unix socket". Contexts are stored under `~/.docker/contexts/`. The active one is chosen by `docker context use`, overridden by `DOCKER_CONTEXT`, `--context`, `DOCKER_HOST` or `--host` ([Docker contexts](https://docs.docker.com/engine/manage-resources/contexts/)).
- **Docker Desktop (Mac).** Installing the `/var/run/docker.sock` symlink is an opt-in setting, so that "various Docker clients relying on the default Docker socket path work". `/var/run` is a tmpfs, so a `launchd` task recreates the link at boot. The CLI's current context "is set to `desktop-linux` on Docker Desktop startup" ([Mac permission requirements](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/)).
- **OrbStack.** "OrbStack will automatically update the `/var/run/docker.sock` symlink to point to its own Docker engine." It coexists with Docker Desktop through contexts: `docker context use orbstack` or `desktop-linux` ([OrbStack install](https://docs.orbstack.dev/install)).
- **Colima.** Its socket is `$HOME/.colima/default/docker.sock`. "Colima makes itself the default Docker context on startup." It can run "alongside Docker for Mac" through contexts. Linking its socket to `/var/run/docker.sock` is possible, but "may break other Docker servers" ([Colima FAQ, main branch](https://github.com/abiosoft/colima/blob/main/docs/FAQ.md)).
- **Rancher Desktop.** Docker Desktop can be installed alongside, "but they cannot be run at the same time. Be sure to stop one before starting the other." ([Rancher Desktop FAQ](https://docs.rancherdesktop.io/faq/)). Its design ticket says it repoints `/var/run/docker.sock` at its own socket on start and assumes "other tools set up their own symlinks on startup" ([rancher-desktop#939](https://github.com/rancher-sandbox/rancher-desktop/issues/939), 2021).
- **The conflict in practice.** In [colima#365](https://github.com/abiosoft/colima/issues/365) (open since 2022-07-12), a user had to delete Docker Desktop's old socket link and point it at Colima for testcontainers and `act`, then found the link gone again later. The owner's answer: tools are moving to contexts, and contexts let users "try out Colima without breaking your current workflow". In short: the fixed default path has one owner at a time (last writer wins). Contexts are the documented way for several engines to coexist, but clients that hard-code the path do not read them.

## 6. Homebrew

- **What `brew cleanup` removes.** "Remove stale lock files and outdated downloads for all formulae and casks, and remove old versions of installed formulae … Removes all downloads more than 120 days old. This can be adjusted with `$HOMEBREW_CLEANUP_MAX_AGE_DAYS`." Further options: `--prune=<days>|all`, `--scrub` (which still keeps downloads for installed formulae and casks), `--prune-prefix`, and `-n` for a dry run ([cmd/cleanup.rb](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/cmd/cleanup.rb); defaults in [env_config.rb L261-L269](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/env_config.rb#L261-L269)).
- **Automatic runs.** `brew install`, `upgrade` and `reinstall` clean the formulae they touched, and run a full clean-up every `HOMEBREW_CLEANUP_PERIODIC_FULL_DAYS` (default 30), tracked by the mtime of `$(brew --cache)/.cleaned` ([cleanup.rb L418-L428](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/cleanup.rb#L418-L428)). `HOMEBREW_NO_INSTALL_CLEANUP` turns all of this off. `HOMEBREW_NO_CLEANUP_FORMULAE=foo,bar` turns it off for named formulae ([env_config.rb L605-L611](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/env_config.rb#L605-L611), [FAQ](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/docs/FAQ.md#how-do-i-keep-old-versions-of-a-formula-when-upgrading)).
- **What it keeps.** An old keg (installed version) is eligible only when the newest version is installed. It is skipped when it is linked, pinned, or listed in a `.keepme` file, with the message "Skipping … as it is needed by …" ([`eligible_kegs_for_cleanup`, formula.rb L3767-L3810](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/formula.rb#L3767-L3810)). `.keepme` arrived in [PR #19138](https://github.com/Homebrew/brew/pull/19138) (merged 2025-01-23) as "essentially providing reference counting": each line names a file on disk, and while that file exists the keg is kept ([keg.rb L763-L768](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/keg.rb#L763-L768)).
- **Dependencies.** Dependencies point at formulae, not versions. Homebrew "doesn't support arbitrary mixing and matching of formula versions", so upgrading one formula upgrades its dependents and dependencies together ([FAQ](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/docs/FAQ.md)). Clean-up therefore has no "old version needed by formula X" case, apart from linked, pinned and `.keepme` kegs. `brew uninstall` refuses a formula other installed formulae depend on unless `--ignore-dependencies` is passed ([cmd/uninstall.rb](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/cmd/uninstall.rb)).
- **`brew services`** manages launchd or systemd services, one per formula, named after the formula. The current label is `sh.brew.<formula>`. The legacy `homebrew.mxcl.<formula>` (launchd) and `homebrew.<formula>` (systemd) are still recognised ([service.rb L86-L126](https://github.com/Homebrew/brew/blob/cdc1ca503231b9a96da64526774915d913c3ec9f/Library/Homebrew/service.rb#L86-L126)). Versioned formulae such as `postgresql@16` and `postgresql@17` are separate formulae and so get separate services. Whether they then collide on ports is up to each formula (not checked).

## 7. Browser profiles and editor data across versions and installs

### Firefox 67: a dedicated profile per installation, plus downgrade protection

- Firefox 67.0, released May 21, 2019: "Users will be able to run different Firefox installs side by side by default", and "Firefox will now protect you against running older versions of the browser", since older versions can cause data corruption and stability issues ([release notes](https://www.firefox.com/en-US/firefox/67.0/releasenotes/)).
- **Why** (Dave Townsend, firefox-dev, 2018-10-18): "Firefox stores all of its settings in the user's profile". Upgrades make changes "that can render the profile unusable by earlier versions of Firefox. This can cause anything from certain features of Firefox being broken after a downgrade to Firefox crashing on startup." ([firefox-dev post](https://groups.google.com/d/msg/firefox-dev/wDjPSU9OWq8/PnS-MSdkCAAJ)).
- **Behaviour** ([Mozilla support, "Dedicated profiles per Firefox installation"](https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation), last updated 2023-10-24; read through a Web Archive copy of 2025-12-22 because the live page blocks automated reading). "Firefox uses a dedicated profile for each installation of Firefox, including Nightly, Beta, Developer Edition and Extended Support Release (ESR) installations." Existing profile data went to "the first Firefox installation opened after the change". Launching with a profile "last used in a more recent version" shows a warning that an older version "can corrupt profile data". The user is offered "Create New Profile", and the newer profile stays available. `--allow-downgrade` overrides the check.
- **Mechanism, from the source.** The profile's `compatibility.ini` records the last version. On start, Firefox compares *major* versions. If the profile is newer it calls `HandleDetectedDowngrade`, unless `--allow-downgrade` or `MOZ_ALLOW_DOWNGRADE` is set ([nsAppRunner.cpp L3881-L3901, L3970-L3978, L5899-L5915](https://github.com/mozilla-firefox/firefox/blob/976279105b2e78b8666a959eb3f25c9176cefaf8/toolkit/xre/nsAppRunner.cpp#L5899-L5915)).

### Chrome: refusing data written by a newer version

- Each SQLite store in the profile records a version and a *compatible version*. The compatible version is "the lowest current version embedded in Chrome code that can still use this database". "Rule of thumb: check the version number when you're upgrading, but check the compatible version number to see if you can use the file at all. If it's larger than you code is expecting, fail." ([sql/meta_table.h L106-L123](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/sql/meta_table.h)). Example: the history database returns `INIT_TOO_NEW` when the compatible version is above what the code knows ([history_database.cc](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/components/history/core/browser/history_database.cc)). That maps to `IDS_PROFILE_TOO_NEW_ERROR`: "Your profile can not be used because it is from a newer version of Chromium. Some features may be unavailable. Please specify a different profile directory or use a newer version of Chromium." ([sql_init_error_message_ids.cc](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/chrome/browser/profiles/sql_init_error_message_ids.cc), [chromium_strings.grd](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/chrome/app/chromium_strings.grd)).
- At the User Data level, Chrome writes a `Last Version` file. On a downgrade, `DowngradeManager` does one of three things. After an administrator-driven downgrade (Windows) it moves User Data aside (`.CHROME_DELETE`). It restores a snapshot when snapshots are enabled. Otherwise it treats the downgrade as `kUnsupported` ("Unsupported downgrade with no data processing") ([downgrade_manager.cc](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/chrome/browser/downgrade/downgrade_manager.cc), [downgrade_manager.h](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/chrome/browser/downgrade/downgrade_manager.h), [user_data_downgrade.cc](https://chromium.googlesource.com/chromium/src/+/d854ee801f33a48f7babc8d79670d2a7d9b6998d/chrome/browser/downgrade/user_data_downgrade.cc)).

## 8. Bazel: a different version or changed startup options restart the server

- There is one server per output base. The output base comes "by default" from the workspace path and the user, so several workspaces mean several servers. "When running `bazel`, the client first checks that the server is the appropriate version; if not, the server is stopped and a new one started." Idle servers stop after 3 hours (`--max_idle_secs`) ([client/server docs](https://bazel.build/run/client-server)).
- From the source ([blaze.cc L93-L129](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/cpp/blaze.cc#L93-L129)), the client kills the running server if "The server is of the wrong version (as determined by the `$OUTPUT_BASE/install` symlink)", if "The server has different startup options than the client wants", or if the client wants batch mode.
  - **Version check.** `EnsureCorrectRunningVersion` compares the `install` symlink in the output base with the client's own install base (one per Bazel binary). On a mismatch it logs "Killing running server because it is using another version of Bazel" and repoints the symlink ([L1143-L1175](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/cpp/blaze.cc#L1143-L1175)).
  - **Startup options.** These produce "Running Bazel server needs to be killed, because the following startup options are different" ([L1088-L1140](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/cpp/blaze.cc#L1088-L1140)).
  - So two Bazel versions alternating in one workspace keep killing each other's server. Different workspaces do not interfere.
- **Install-base clean-up, a safe pattern for a shared per-user cache.** With `--experimental_install_base_gc_max_age` (default `30d`), an idle server deletes *other* install bases unused for that long ([CommonCommandOptions.java](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/java/com/google/devtools/build/lib/runtime/CommonCommandOptions.java)). The mechanism ([InstallBaseGarbageCollector.java](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/java/com/google/devtools/build/lib/server/InstallBaseGarbageCollector.java), [blaze.cc L296-L318](https://github.com/bazelbuild/bazel/blob/e89755babf3e941bc1e9d8120b1cd48854ab9dfa/src/main/cpp/blaze.cc#L296-L318)):
  1. The client updates the install base's mtime on every invocation.
  2. The client and the server each hold a *shared* lock on `<install base>.lock` while they use it.
  3. The collector skips its own install base. It takes the *exclusive* lock with a non-blocking try, and backs off if the lock is held or the mtime is recent.
  4. Otherwise it renames the directory to `<uuid>.deleted`, removes the lock file and deletes the tree.
  5. Interrupted deletions are finished on the next run.

  The source admits one gap: an older binary that does not take the lock can race the mtime check.

## 9. Two products, one local daemon and one local UI

- **Playwright CLI and dashboard** (section 1). Sessions accept only clients of the same or a newer version. The dashboard is a per-user singleton on a fixed socket: whichever version starts first serves everyone, with no version handshake.
- **Ollama.** One server (`ollama serve`, default `127.0.0.1:11434`, `OLLAMA_HOST`). The CLI is an HTTP client of it. Version skew is only reported: `ollama --version` prints the server's version, then "Warning: client version is X" when the two differ ([cmd/cmd.go L2303-L2321](https://github.com/ollama/ollama/blob/45e6011815c74acde6a346512856b69dd79dd22b/cmd/cmd.go#L2303-L2321), [envconfig/config.go](https://github.com/ollama/ollama/blob/45e6011815c74acde6a346512856b69dd79dd22b/envconfig/config.go)).
- **Docker** (section 5). One engine serves CLI versions old and new through API negotiation, but only one engine can own the default socket.
- Docker Desktop's CLI plugins and JetBrains Toolbox were not examined.

## Implications for two Products on one machine

These are observations for the coming decision, not decisions.

1. **Reference by consumer and version, and check that the consumer is alive.** Playwright's `.links` show both sides of reference counting. It is cheap and shared across bindings. But a reference is one per *path*, liveness is "the directory still exists", and the check runs only at install time. That combination produced #40995 and #42214. Homebrew's `.keepme` has the same shape (a reference is valid while its file exists). Gradle and Bazel instead use *recency*: a marker or install-base mtime touched on each use, plus a retention period. Bazel adds locks: a shared lock while in use, an exclusive try-lock to delete, rename before delete. For a browser cache where Collie and Foxhound at different versions each need their own builds, the evidence favours per-build references naming the install *and* the version, refreshed on use. Deletion should require both "no live reference" and "unused for N days", and in-use builds should be protected by a lock rather than by file presence alone.
2. **Only the newer side should judge the older side's data.** Gradle deletes only caches of *older* versions and only layouts older than its own latest. uv's prune deletes any bucket name the running binary does not know, which lets an old uv destroy a newer uv's buckets. If either Product can run a clean-up, it needs a rule like Gradle's, or it must refuse to delete entries whose format or version it does not recognise.
3. **A version-pinned consumer must ask for exactly what it pins, and say what it expected.** #41871 shows the failure: two distributions on one cache, each with its own pinned revisions, and an error that hid which revision was expected. Playwright's fix was to show the expected path and to ship `npx playwright mcp` inside the main package so the versions line up. For Collie and Foxhound on one version line, the same split can occur whenever the two are installed at different versions.
4. **Daemons: per version, or one daemon with explicit skew rules.** Gradle and Bazel never share a server across versions: Gradle by a per-version registry, Bazel by killing a mismatched server. That is safe but leads to restarts, or to several daemons. Docker shares one daemon across many client versions through a negotiated, bounded API range, rejecting clients outside it. The Playwright CLI rejects older clients against newer sessions. Its dashboard and Ollama do not check versions at all. A shared Collie and Foxhound Daemon would need one of these rules written down, including which side downgrades.
5. **One well-known endpoint has one owner.** The `/var/run/docker.sock` disputes show what happens when several products claim a single fixed path: last writer wins, and clients that hard-code it break. Docker contexts are the documented way out. A single Console port or socket shared by two Products raises the same ownership question.
6. **Persisted state needs a "lowest compatible reader" marker.** Firefox's `compatibility.ini` and Chrome's SQLite `compatible version` let an older binary refuse data written by a newer one, instead of corrupting it. Chrome's rule ("check the compatible version number to see if you can use the file at all") applies directly to a shared Run index, Schedules or Usage ledger. Firefox's answer to concurrent installs, a dedicated profile per installation, is the other option, at the cost of not sharing.
7. **Separate disposable caches from durable state.** uv documents a disposable cache and a persistent data directory, and only the cache is ever pruned. Ruff simply versions its cache directory per release. Run index, Schedules and Usage ledger are durable state. Browser builds are a cache. Their clean-up rules can differ accordingly.
