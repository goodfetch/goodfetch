# Hybrid / bursting precedents: local orchestrator + remote capacity

Research date: 2026-10-24. Method: WebSearch + WebFetch of primary docs; one GitHub raw-source read for spider. Read-only; no repo files touched. Items marked **[unverified]** come from search snippets or third-party pages only. Items marked **[page-reported]** were read on the vendor page but the page itself was thin or odd.

Key distinction used throughout:
- **Manual switch**: user sets an endpoint / flag / config; everything goes remote.
- **Static split**: the user declares a mix (n local + m remote), the system never rebalances by itself.
- **Automatic burst**: the system decides per job/task, based on queue length / resource pressure / race, to use remote capacity.

## A. Browser automation and scraping

### 1. Playwright Workspaces (Azure App Testing), successor of Microsoft Playwright Testing
- **Name and status (2026).** Microsoft Playwright Testing (Preview) was retired on **2026-03-08** (Azure Updates notice AZ499860, posted 2025-09-09; via search result, secondary mirror [unverified for exact text]). Replacement: **Playwright Workspaces**, a part of **Azure App Testing** (alongside Azure Load Testing), documented as generally available. Learn page last updated 2026-09-29. It is now framed as "managed cloud browser platform for tests, browser workflows, and AI agents" and adds a remote MCP server and CDP connection, Live View / Take Control.
- **How it works.** `npm init @azure/playwright@latest` generates `playwright.service.config.ts`. Run `npx playwright test --config=playwright.service.config.ts --workers=20`. Playwright's test runner and its **worker processes keep running on the client machine** (laptop or CI agent); only the **browsers** run in Azure. Results, traces stay on the client. Docs: "the worker processes continue to run locally, but the resource-intensive browser instances are now running remotely in the cloud."
- **Manual or automatic.** Manual and total: choosing the `--config` file flips every browser to remote. No "use local until full". Local default workers = 1/2 of CPU cores; service runs allow up to 100 parallel workers per workspace (default quota; docs elsewhere on same site say 50 in the quickstart, so the quota changed or pages are inconsistent).
- **What stays local.** Test runner, test code, worker processes, queue of tests (Playwright's own scheduling), reporters, artifacts. Remote: browsers (Linux and Windows, all Playwright browsers, Playwright OSS >= 1.50).
- **Reaching local apps.** Uses Playwright's `browserType.connect({exposeNetwork})`: "exposes network available on the connecting client to the browser" (`<loopback>` for localhost, or host patterns). Traffic from the cloud browser to localhost is tunneled back through the client connection, with no inbound firewall rules.
- **Latency.** Docs list "latency between the client machine and the remote browsers" as a factor, and the client becomes the bottleneck as workers rise. Regional affinity (default on): browsers run in the Azure region nearest the client; results are moved to the workspace region. 7 regions (Australia East, East Asia, East US, Japan East, Switzerland North, West Europe, West US 3).
- **Auth.** Microsoft Entra ID (default, `az login`) or workspace access tokens (disabled by default, "like long-lived passwords").
- **Pricing.** Billed by browser/test minutes (plus test-results storage in the older service). 30-day / 100-test-minute free trial for the first workspace (search snippet of Azure pricing page [unverified]); dollar rates did not render, so not stated here.
- **Playwright protocol caveat.** `connect` requires matching Playwright major.minor between client and server.
- **Sources.** https://learn.microsoft.com/azure/app-testing/playwright-workspaces/overview-what-is-microsoft-playwright-workspaces (updated 2026-09-29); https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/quickstart-run-end-to-end-tests; https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/concept-determine-optimal-configuration (updated 2026-03-25); https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/how-to-test-local-applications; https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/how-to-optimize-regional-latency; https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/resource-limits-quotas-capacity (updated 2026-09-14); https://playwright.dev/docs/api/class-browsertype#browser-type-connect; retirement: https://mc.merill.net/message/AZ499860 [secondary].

### 2. Spider (spider-rs): `decentralized` + `spider_worker`; Spider Cloud
- **`decentralized` feature.** Cargo feature on the `spider` crate: "Enables decentralized processing of IO, requires the spider_worker startup before crawls." Install `cargo install spider_worker`, run it (port 3030; scraper variant on 3031), set `SPIDER_WORKER=http://host:3030[,http://host2:3030]` (comma list; `SPIDER_WORKER_SCRAPER` for the `scrape`-flavoured worker). The README says it speeds things up even with the worker on the same machine ("splits the IO work across separate runtimes").
- **What I saw in source** (`spider/src/website.rs`, main branch): the workers are read once into a global set from the env vars; the crawl loop's concurrency semaphore is sized `calc_limits(3) * WORKERS.len()`; and the HTTP client is configured with each worker URL as a `Proxy::all(worker)`. So the worker acts as a fetch proxy: the **crawl loop, link frontier, dedup and page handling stay in the local `Website` process**; the worker does the network I/O (and, with `full_resources`, link gathering) and returns the page. I did not find any queue-length / resource-pressure rule, health check or failover; worker choice is whatever the HTTP-proxy layer does with several proxies (not verified). Treat as **manual, static split**.
- **Gotchas documented.** Workers rewrite response headers with a `zz-spider-r--` prefix (needs `decentralized_headers` feature to restore). Worker has optional TLS (`SPIDER_WORKER_CERT_PATH`, `SPIDER_WORKER_KEY_PATH`), optional `SPIDER_WORKER_MAX_CONCURRENCY` (default 0 = unlimited), and an opt-in SSRF guard `SPIDER_WORKER_BLOCK_PRIVATE_HOSTS`. No auth token documented in README (use network controls/TLS). Worker count is process-global (a per-`Website` override exists in recent versions: `worker_connection_urls`).
- **Spider Cloud (`spider_cloud` feature).** `spider = { features = ["spider_cloud"] }`, attach `SpiderCloudConfig` to `Website` via `.with_spider_cloud_config(...)`; "for anti-bot bypass and proxy rotation". Modes include a **Smart** mode: proxy first, escalate to stealth/unblocker "only on pages that fight back" (automatic escalation, but *within* the vendor's service; local machine is not the escalation source). Hosted REST API `https://api.spider.cloud` (crawl, scrape, search, links, screenshot; bearer auth; response formats include `application/jsonl`; request mode default `smart`: HTTP first, JS rendering when needed); a residential proxy (`proxy.spider.cloud`) and a `WS /v1/browser` CDP endpoint exist.
- **Pricing (spider.cloud/pricing, read 2026-10-24).** Pay-as-you-go: $1/GB bandwidth + $0.0001 per CPU-minute; failed requests $0; JS rendering and proxy rotation have no multiplier. "Unlimited": flat monthly per concurrency (example $350/mo for 25 concurrent); over-limit requests get **immediate 429, no queueing**. Zero-data-retention 2.5x.
- **Sources.** https://raw.githubusercontent.com/spider-rs/spider/main/spider/README.md; https://raw.githubusercontent.com/spider-rs/spider/main/spider_worker/README.md; https://raw.githubusercontent.com/spider-rs/spider/main/spider_worker/src/main.rs; https://raw.githubusercontent.com/spider-rs/spider/main/spider/src/website.rs (lines ~1196-1222, 3784-3793); https://docs.rs/spider_worker/; https://spider.cloud/docs/api; https://spider.cloud/pricing.

### 3. Apify + Crawlee (local vs platform)
- **Local run.** `apify run` runs the Actor locally with simulated Apify env vars, storing data in `./storage`. Flags: `--purge/--no-purge`, `--resurrect`, input via `--input`/`--input-file`. `apify push` uploads source and **builds** on the platform (`.actor/actor.json`); `apify call` runs the Actor **remotely** on your account (`-m` memory, `-t` timeout, `-o` print dataset). So local-vs-cloud is a **choice of command**, not automatic.
- **Mixing local code with platform storage/proxy.** Crawlee storage env rules: no vars or only `CRAWLEE_STORAGE_DIR` = local; `APIFY_TOKEN` alone = platform storage; both = **local by default**, with `forceCloud: true` on `Actor.openDataset()/openKeyValueStore()/openRequestQueue()` to put selected storages on the platform. Apify Proxy works from a local run once logged in (`Actor.createProxyConfiguration({groups, countryCode})`). So a **local crawler can use a cloud request queue (shared frontier), cloud dataset and cloud proxy**, manually per storage. This is the closest "local orchestrator + remote state" in the scraping world.
- **Auto-offload.** None found. `apify run` docs list no platform-storage/proxy flag; Crawlee's AutoscaledPool scales concurrency to *local* CPU/memory/event-loop only (not read in this pass; listed as known design, [unverified here]).
- **Auth.** API token (`apify login -t`, `APIFY_TOKEN`); proxy password inferred from token.
- **Pricing (apify.com/pricing).** Compute unit = 1 GB RAM-hour: $0.20 (Free/Starter), $0.16 Scale, $0.13 Business; residential proxy $7-8/GB; datacenter proxies per IP; Free plan $5 usage; Starter $19/mo; Scale $199/mo; Actors may be pay-per-event or pay-per-usage.
- **Sources.** https://crawlee.dev/docs/deployment/apify-platform; https://docs.apify.com/cli/docs/reference; https://crawlee.dev/docs/guides/request-storage; https://apify.com/pricing. CLI reference says commands are labelled PoC (search result summary [unverified]).

### 5. Test-grid ecosystem

**Selenium Grid 4 + dynamic grid + KEDA**
- Grid 4 splits into Router, Distributor, SessionQueue, Event Bus, Session Map, Nodes. Nodes register with the Hub/Distributor and heartbeat; a **SessionQueue** holds new-session requests until a slot frees (`--session-request-timeout`, example 300 s). Dynamic grid (`--docker/-D`) maps image names to stereotype capabilities so nodes start browser containers on demand.
- **Autoscaling is external**: the CLI docs describe no autoscaler. The official Selenium blog (2022-08-19, modified 2026-07-11) explains HPA's CPU/memory metrics do not fit Grid; **KEDA** reads queue + active-session counts via the Grid GraphQL endpoint, `minReplicaCount: 0`, `maxReplicaCount: 80`; scale-down kills pods at random, so use a preStop drain hook and `terminationGracePeriodSeconds: 3600`. A newer `selenium/keda-external-scaler` (gRPC; strategies default/custom/accurate/eager) is on Docker Hub [search snippet, unverified].
- **Pattern.** The client is dumb (just a WebDriver URL); the scale decision is **queue length** at the grid, which is the one genuinely automatic burst trigger in this section. Hybrid local+cloud capacity is possible because nodes can sit anywhere and register to the hub, but this is operator-assembled, not a product feature.
- Sources: https://www.selenium.dev/documentation/grid/configuration/cli_options/; https://www.selenium.dev/blog/2022/scaling-grid-with-keda/.

**Moon (Aerokube)**
- Kubernetes/OpenShift-native; Moon pods start one browser pod per session (a "defender" sidecar enforces one session per pod and timeouts); stateless; config as CRDs; quotas per namespace. Scales via the cluster's autoscaling on AWS/GCP. Can **route sessions to external hosts** (Selenoid, Appium, Selenium Grid) for browsers the cluster cannot run (macOS/iOS) — a static routing fan-out, not a load-based burst. Licence keys are cluster-wide.
- Source: https://aerokube.com/moon/latest/ (first 100k chars read).

**BrowserStack Local (reverse direction pattern)**
- Cloud browsers, local private resources. `BrowserStackLocal` agent runs inside your network, authenticates with your access key, is assigned a **repeater** in BrowserStack's cloud and keeps a persistent connection; the cloud browser sends traffic through the repeater, which forwards private-network requests to the agent (`force-local` forces all traffic through it). Same shape as Playwright `exposeNetwork`.
- Source: https://www.browserstack.com/docs/automate/selenium/local-testing-introduction.

**LambdaTest HyperExecute**
- Only secondary sources found: a vendor comparison says HyperExecute runs the test script on the same VM as the browser (no hub/node hop) and has Auto-Split / Matrix / **Hybrid** modes; "hybrid" there means split+matrix, **not** local+cloud [unverified; competitor blog]. No documented self-hosted hybrid grid found.

### 6. Scraping frameworks with a "hybrid" story
- **Scrapy / scrapy-redis**: Redis-backed scheduler + dupefilter; "start multiple spider instances that share a single redis queue"; items can be pushed to a Redis queue for shared post-processing. Manual configuration via settings (`REDIS_PARAMS`, etc.). No cloud bursting or elasticity in the README. Workers can live anywhere that reaches Redis, so a laptop+cloud mix is possible by deployment, not by feature. Source: https://github.com/rmax/scrapy-redis.
- **Crawlee**: request queue/list local by default (`./storage`, in memory plus disk); no distributed mode in that guide; hybrid arises only via Apify storage (section 3). Source: https://crawlee.dev/docs/guides/request-storage.
- **Firecrawl self-host**: docs present self-host and Cloud as **alternatives**; "no hybrid mode and no automatic fallback to Cloud". Self-host stack: API (3002), Redis, PostgreSQL (default queue; FoundationDB optional), a separate Playwright service, long-lived workers. Missing vs Cloud: fire-engine (anti-bot), screenshots/actions, agent/browser/interact. Quickstart disables API auth. Source: https://docs.firecrawl.dev/contributing/self-host.
- **Crawl4AI**: Docker server (port 11235, API token, `/crawl` sync and `/crawl/job` async), memory-adaptive dispatcher (v0.5.0 release notes) that adapts concurrency to local memory. No hybrid/cloud-burst mode found. All from search snippets and mirrors, official page fetch 404'd [unverified]. Source: https://docs.crawl4ai.com/blog/releases/0.5.0/.
- **Spider** (section 2): the only scraping framework with a built-in *remote I/O worker* feature, still manual.

## B. General compute that sets user expectations

### 7. Modal
- **Model.** Local Python entrypoint (`@app.local_entrypoint()`, `modal run`) drives remote Functions: `f.remote()` runs in Modal's cloud, `f.map(inputs)` fans out to many containers and returns results **in input order**; `return_exceptions=True` collects errors. Ephemeral App lives only while the client is connected ("stop when the calling program exits or the server detects the client has disconnected"; `--detach` to survive).
- **Automatic or manual.** Which code is remote is **declared per function** by the author (decorator). The *amount* of remote capacity is automatic: per-Function autoscaler adds containers when no capacity is free, scales to zero; knobs `min_containers`, `max_containers` (hard cap 4,000), `buffer_containers`, `scaledown_window`; can be updated at runtime without redeploy.
- **Local.** Entrypoint, orchestration, anything not decorated. Remote: function bodies and their container images.
- **Pricing.** Per-second CPU ($0.0000131/core-s), memory ($0.00000222/GiB-s), GPU rates; Starter $0 + compute with $30/mo credit; 100 containers on Starter, 5,000 on Team ($250/mo); billed load time, input processing and a default 60 s keep-alive.
- **Sources.** https://modal.com/docs/guide/apps; https://modal.com/docs/guide/scale; https://modal.com/pricing.

### 8. Coiled / Dask
- **Model.** `coiled.Cluster(n_workers=100)` + `cluster.get_client()`: client on laptop, VMs in your cloud account started in "about a minute"; Coiled inspects your machine and syncs packages/scripts/credentials to the remote workers. Cleaned up when done; idle shutdown default 20 min.
- **Automatic or manual.** `cluster.scale(n)` manual; `cluster.adapt(minimum, maximum)` lets the Dask scheduler decide. Dask adaptive: target = cumulative expected runtime of pending tasks / `target_duration` (5 s default), clipped to min/max; scale-down moves data off idle workers first and needs repeated suggestions (`wait_count`) to avoid flapping. The scheduler cannot launch workers itself; it asks a Cluster manager (Kubernetes, Slurm, ...).
- Scheduler placement and client-to-scheduler network details were not on the pages I fetched (pages link to firewall/network architecture pages not read). Pricing: not stated on pages read.
- **Sources.** https://docs.coiled.io/user_guide/index.html; https://docs.coiled.io/user_guide/clusters/scale.html; https://docs.dask.org/en/stable/adaptive.html.

### 9. Ray
- **Ray Client.** `ray.init("ray://head:10001")` runs the **driver locally** and tasks/actors on the cluster; `working_dir` uploaded; requires identical Ray and Python minor version; **a lost connection of more than 30 s kills the workload** (`RAY_CLIENT_RECONNECT_GRACE_PERIOD` extends); anyone with client access can run arbitrary code on the cluster; docs steer long-running/ML work to the Ray Jobs API.
- **Autoscaler.** Reacts to **logical resource requests** that cannot be satisfied (pending tasks/actors/placement groups), not physical utilisation; `min_workers`, `max_workers` (default 2), `upscaling_speed` (1.0), `idle_timeout_minutes` (5); worker idle = no tasks, actors or referenced objects.
- **Hybrid.** On-prem launcher takes a fixed `worker_ips` list; cloud launchers autoscale. I found **no documented single config mixing on-prem nodes with auto-scaled cloud workers**; a custom/external node provider would be needed [search-based, unverified].
- **Sources.** https://docs.ray.io/en/latest/cluster/running-applications/job-submission/ray-client.html; https://docs.ray.io/en/latest/cluster/vms/user-guides/configuring-autoscaling.html.

### 10. Kubernetes cloud bursting
- **Virtual Kubelet** (CNCF sandbox): a fake kubelet; a "node" backed by Azure Container Instances, AWS Fargate, Alibaba ECI, Nomad, Liqo, etc. **AKS virtual nodes** (ACI): "You don't need to wait for Kubernetes cluster autoscaler to deploy VM compute nodes"; pay per second; many limits (no init containers, DaemonSets, PVCs, managed identity, needs Azure CNI); docs say start with **Virtual Nodes v2 (preview)**. Page updated 2026-10-20. Pods reach the virtual node through normal scheduling (taints/tolerations typical; not detailed on the pages read).
- **Liqo**: peers clusters; each remote cluster appears as a **virtual node**; `NamespaceOffloading` with pod offloading strategy `LocalAndRemote` (default: scheduler chooses local or virtual nodes), `Local`, `Remote`; `runtimeClassName: liqo` forces remote; namespace label `liqo.io/scheduling-enabled=true`. So: manual opt-in per namespace, then scheduler-driven placement.
- **Admiralty**: "Kubernetes controllers that intelligently schedules workloads across clusters"; repository page gives no mechanism or burst claim; maintenance status not determined. [mechanism unverified]
- **Pattern.** Capacity is exposed as another node; placement uses standard scheduler pressure (Pending pods spill onto the virtual node). This is automatic *spillover* once configured, and the app does not know.
- **Sources.** https://virtual-kubelet.io/; https://learn.microsoft.com/en-us/azure/aks/virtual-nodes; https://docs.liqo.io/en/stable/; https://docs.liqo.io/en/stable/usage/namespace-offloading.html; https://github.com/admiraltyio/admiralty.

### 11. Slurm cloud bursting
- Nodes defined `State=CLOUD`; when a job is allocated powered-down nodes Slurm runs **ResumeProgram** (hostlist + `SLURM_RESUME_FILE` JSON mapping jobs to nodes); idle nodes are suspended by **SuspendProgram** after `SuspendTime`. Order of allocation: powered-up, powering-up, then powered-down. Resumed node must register within `ResumeTimeout` (default 60 s) or goes DOWN and its jobs requeue. Rate limits `ResumeRate` 300/min, `SuspendRate` 60/min. Cloud nodes can be a separate partition; users target them with `--constraint`. Early allocation: job granted before nodes are ready; steps wait.
- **Automatic** from job queue pressure (a pending job that only fits cloud nodes triggers boot) with the user able to **pin** to cloud via constraint. Closest classic definition of "cloud bursting".
- Sources: https://slurm.schedmd.com/elastic_computing.html; https://slurm.schedmd.com/power_save.html.

### 12. CI runners: GitHub Actions and Buildkite
- **GitHub Actions self-hosted + ARC.** Routing is **label-based and manual** (`runs-on` matches a runner scale set name/label). ARC listener holds an HTTPS long-poll to GitHub, on "Job Available" patches the replica count of an `EphemeralRunnerSet`, creates just-in-time ephemeral runner pods (retry up to 5; unassigned after 24 h), deletes them after the job. No documented fallback from self-hosted to GitHub-hosted if scale set is full; the job just waits (24 h) [page confirms 24 h unassign; no fallback statement].
- **Buildkite.** SaaS control plane + agents in your infra; agents **poll outbound over HTTPS** (no inbound ports); jobs route by **queue**; agents are ordered by recency of last successful job (warm cache preference); self-hosted scaling is manual or via Elastic CI Stack / Agent Stack for Kubernetes; hosted agents scale automatically; hooks and secrets live on your machines; agents upload logs/status/artifacts.
- **Pattern.** Work *pulls* to capacity: any worker anywhere polls; scaling is a separate controller watching queue depth. No inbound connectivity needed.
- Sources: https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/about-self-hosted-runners; https://docs.github.com/en/actions/concepts/runners/actions-runner-controller; https://buildkite.com/docs/agent/v3.

### 13. Build systems: distcc, icecream, Bazel RBE and dynamic execution (closest analogy)
- **distcc.** Client preprocesses locally and "sends the complete preprocessed source code across the network for each job"; servers need only `distccd` and a compiler; hosts listed in env (`DISTCC_POTENTIAL_HOSTS='localhost red green blue'`), restricted by `--allow`; used with `make -j`; `pump` mode; mentions dmucs/ccontrol/tcpbalance as external scheduling helpers. Local fallback and host-blacklisting not covered on the page read (known behaviour from memory, not source-verified here [unverified]). Static host list, no auth beyond IP allow.
- **icecream.** Central `icecc-scheduler` assigns compile jobs "to the fastest free server" using load reported by each `iceccd`; algorithms `fastest` (default), `least_busy`, `round_robin`, `random`. **The scheduler prefers the local machine if it is free and has >= 70% of the fastest machine's speed** (explicit local-first bias). Ships the client's compiler as a tarball/chroot to nodes. Multiple schedulers elect a master (>= 1.1). Local fallback when no scheduler: not stated on page.
- **Bazel remote execution.** Same build, same Bazel client; `--remote_executor=HOST:PORT` (gRPC REAPI) sends action execution to a pool; **analysis, graph and scheduling stay on the client**. `--remote_local_fallback`: "Whether to fall back to standalone local execution strategy if remote execution fails." `--remote_retries` for transient errors; `--remote_download_outputs=minimal|toplevel|all` controls what is materialised locally. Remote execution imposes constraints on rules (hermeticity, declared inputs).
- **Bazel dynamic execution (the key precedent).** Runs the **same action locally and remotely at the same time; first to finish wins, the other is cancelled** (`--internal_spawn_scheduler`, `--strategy=<Mnemonic>=dynamic`, `--dynamic_local_strategy`, `--dynamic_remote_strategy`). If the winner fails the action fails (deliberately, so local/remote differences are not hidden). With a remote cache, `--dynamic_local_execution_delay` (default 1000 ms) delays the local branch to avoid redundant local work. Needs real remote execution (a cache miss counts as a failure); slow local actions can hog resources; macOS/Windows sandbox overhead. This is the only mainstream tool that makes a *per-task* local-vs-remote decision automatically by racing.
- Sources: https://www.distcc.org/; https://github.com/icecc/icecream; https://bazel.build/remote/rbe; https://bazel.build/remote/dynamic; https://bazel.build/reference/command-line-reference (flag text).

## Patterns (architectural)

1. **Endpoint swap (remote data plane, local control plane).** Local code stays, one URL/config flips every browser (or function) to remote: Playwright Workspaces, Browserbase/Steel/Kernel/Hyperbrowser/Anchor/Browserless/Bright Data/Zyte CDP endpoints, Stagehand `env`, Ray Client, Modal `.remote()`, Coiled. Manual, total, per run. Failure modes seen: 429 with no queue (Browserbase, Spider "Unlimited"), Ray Client's 30 s disconnect kill, client machine becoming the bottleneck (Playwright Workspaces), version-match requirements (Playwright connect, Ray).
2. **Static pool of remote I/O workers.** A configured list of helpers, local process owns the queue/frontier/state: spider `decentralized` (SPIDER_WORKER list), distcc (host list), Moon routing to external grids, scrapy-redis (Redis as shared state). No pressure-based decision.
3. **Capacity pulls work, scaler watches the queue.** Workers poll or register, a separate controller scales workers from queue depth: Selenium Grid + KEDA (session-queue), ARC and Buildkite (long-poll / queue), Ray autoscaler (unsatisfied logical resources), Dask adaptive (pending task runtime), Slurm ResumeProgram (job allocation), icecream (scheduler by load). This is where "automatic burst on queue length" actually exists; none of these is browser-automation/crawl-specific except Selenium Grid.
4. **Capacity as a pretend local resource.** Remote capacity exposed as one more node so unmodified callers spill over: Virtual Kubelet / AKS virtual nodes / Liqo, and Slurm cloud partitions. The caller is unaware; explicit pinning exists (`runtimeClassName: liqo`, `--constraint`).
5. **Race or fallback per task.** Bazel dynamic execution (race, first wins, cancel loser), `--remote_local_fallback` (remote then local on failure), icecream (local preferred at >= 70% speed). The only precedents for a per-unit-of-work decision made by the tool.
6. (Cross-cutting) **Reverse tunnel for local resources**: BrowserStack Local (agent + cloud repeater) and Playwright `exposeNetwork` let remote browsers reach local/private apps over the client's own outbound connection; Buildkite/ARC likewise need only outbound HTTPS.

## Gaps (nobody offers, per what I could find)

- **No browser or crawl product ships "run on local browsers up to N / until CPU-memory pressure, then overflow new sessions to cloud browsers automatically."** Every browser vendor is endpoint-swap or a separate self-host/BYOC deployment; Browserless, Browserbase, Firecrawl and Anchor docs explicitly or implicitly treat local and managed as alternatives. Overflow today means writing your own router in front of a local pool plus a vendor CDP URL.
- **No scraper frontier that spans local and cloud with a pressure-based policy.** Spider `decentralized` is a static list and I found no health/failover logic; Crawlee's storage can be cloud per-storage but not auto; scrapy-redis needs manual worker launches.
- **No documented per-URL / per-session race or hedge between local and remote** for browsers (Bazel-style first-wins). Spider has a `hedge` feature flag in source (cfg seen in `website.rs`, `hedge` + `chrome`, not enabled with `decentralized`), whose semantics I did not read.
- **No cost-aware policy** ("burst only while spend < X", "prefer local unless p95 latency > Y") in any vendor; the nearest are Slurm node weights and icecream's 70% local bias.
- **No cloud-fallback on 429/queue-full**: Browserbase and Spider return 429 with no queue and leave retry to the caller.
- **Result-streaming guarantees**: most hybrid systems stream results back over the same control connection (Playwright, Modal, Ray Client), so loss of the client connection loses the run (Ray 30 s; Modal ephemeral apps stop on disconnect unless `--detach`). Only detached/job-style systems (Ray Jobs, Modal `--detach`, Apify `call`) decouple the run from the laptop.
- Not found despite searching: "Steel Outpost", any documented HyperExecute self-hosted hybrid grid, a Ray config mixing on-prem and autoscaled cloud nodes, Admiralty's mechanism.
