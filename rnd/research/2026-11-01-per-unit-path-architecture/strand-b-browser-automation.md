# Strand B: per-unit paths in browser-automation frameworks

Research of 2026-11-01. Question: how do proven browser-automation frameworks structure the paths that every command, read, action, navigation, intercepted request and protocol message goes through, so that Collie can give each of its paths an owner module, a cost contract (counted work per unit) and a benchmark?

## Settled fact: `Page.createIsolatedWorld` with the same `worldName` does not create a fresh context

**Answer: no.** Within one document, calling `Page.createIsolatedWorld` again with the same `worldName` on the same frame returns the existing world's context (same `executionContextId`); it does not create a new one. A new document (navigation) gets a new context in that world.

Evidence, Chromium `main` at `fc2ff626`:

- [`InspectorPageAgent::createIsolatedWorld` and `CreateIsolatedWorldImpl`](https://github.com/chromium/chromium/blob/fc2ff6268dba526072d02d1e8db9536ee9cda624/third_party/blink/renderer/core/inspector/inspector_page_agent.cc#L1724-L1777) call `EnsureDOMWrapperWorld(...)`, then `frame.DomWindow()->GetScriptController().WindowProxy(*world)` and return `executionContextId(isolated_world_window_proxy->ContextIfInitialized())`. A window proxy exists once per (window, world), so the same world on the same document yields the same context.
- [`InspectorPageAgent::EnsureDOMWrapperWorld`](https://github.com/chromium/chromium/blob/fc2ff6268dba526072d02d1e8db9536ee9cda624/third_party/blink/renderer/core/inspector/inspector_page_agent.cc#L1052-L1073) calls [`DOMWrapperWorld::EnsureInspectorIsolatedWorldWithName`](https://github.com/chromium/chromium/blob/fc2ff6268dba526072d02d1e8db9536ee9cda624/third_party/blink/renderer/platform/bindings/dom_wrapper_world.cc#L111-L127), which scans the isolate's world map and returns an existing `kInspectorIsolated` world whose name matches; only otherwise does it create one. It re-applies the security origin and CSP on every call (cheap).
- Same lookup at tag [`156.0.8078.4`](https://github.com/chromium/chromium/blob/156.0.8078.4/third_party/blink/renderer/core/inspector/inspector_page_agent.cc#L1015). Older releases reached the same result differently: at [`130.0.6723.0`](https://github.com/chromium/chromium/blob/130.0.6723.0/third_party/blink/renderer/core/inspector/inspector_page_agent.cc#L1010-L1034) and `120.0.6099.0` the agent kept a per-frame `isolated_worlds_` map keyed by world name and returned the cached world.
- On a provisional frame (navigation not committed) the request is queued in `pending_isolated_worlds_` and served at `DidCreateMainWorldContext` ([L1081-L1086](https://github.com/chromium/chromium/blob/fc2ff6268dba526072d02d1e8db9536ee9cda624/third_party/blink/renderer/core/inspector/inspector_page_agent.cc#L1081-L1086)).
- A script registered with `Page.addScriptToEvaluateOnNewDocument` and a `worldName` makes Chromium create that world in every new document: [`InspectorInjectedScriptManager::EvaluateScriptOnNewDocument`](https://github.com/chromium/chromium/blob/fc2ff6268dba526072d02d1e8db9536ee9cda624/third_party/blink/renderer/core/inspector/inspector_injected_script_manager.cc#L75-L108) calls `EnsureDOMWrapperWorld(&frame, world_name, true)` and evaluates the source in that world's context. Playwright and Puppeteer register an empty or comment-only script for exactly this side effect (below).

Consequence for Collie's C2: re-creating the world on every read does not leak contexts or reset the world's globals. Its cost is one extra CDP round trip per read, plus the lost chance to keep injected code alive in the world. Not verified: the behaviour for an empty `worldName` (the lookup compares names, so an empty name may match a previous unnamed world), and no live run was made.

## Playwright 1.64.1

### 1. Per CDP command

Every Chromium command goes through [`CRSession.send`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crConnection.ts#L145-L155) → `CRConnection._rawSend` in `packages/playwright-core/src/server/chromium/crConnection.ts` (lines 145-155 and 68-76): allocate an id, build `{id, method, params, sessionId?}`, call `this._protocolLogger('send', message)`, `transport.send(message)`, and store `{resolve, reject, error: new ProtocolError('error', method)}` in a per-session `Map`. Replies come back through `CRConnection._onMessage` → `CRSession._onMessage` (lines 78-85 and 161-183): one `Map` lookup and delete; events are re-emitted in a microtask. The launched browser uses a pipe (`--remote-debugging-pipe`, [`chromium.ts` L358](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/chromium.ts#L358)); the WebSocket transport does one `JSON.stringify` per send ([`transport.ts` L187-189](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/transport.ts#L187-L189)).

Protocol logging is **off by default** and costs no formatting when off. The logger passed to `CRConnection` is [`helper.debugProtocolLogger`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/helper.ts#L83-L95): it calls an optional caller-supplied logger, then `if (debugLogger.isEnabled('protocol'))` and only then `JSON.stringify`, truncates and logs under `pw:protocol`. [`debugLogger.isEnabled`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/utils/debugLogger.ts#L64-L66) is `debug.enabled('pw:protocol')`, so it turns on with `DEBUG=pw:protocol`. When `DEBUG_FILE` is set, the logger opens **one** `fs.createWriteStream` at construction and every line is written to it (lines 40-51): no per-line open. Cost when off: two closure calls and one `debug.enabled` check per message in each direction (the `debug` package's internal check was not read: **unverified** detail). The one always-on per-command cost is the `new ProtocolError(...)` allocated in `send`, which captures a stack so a later failure names the caller.

Note: there is no per-command timeout; deadlines live in the `Progress` of the API call that issued the commands (`CDPSession.send` races `progress.race`, crConnection.ts L232-234).

### 2. Per page read / evaluate

- **One utility world per page, created by registration, not per read.** `CRPage` names it `__playwright_utility_world_${page.guid}` ([crPage.ts L108](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crPage.ts#L108)). At session start `FrameSession` sends `Page.addScriptToEvaluateOnNewDocument({ source: '', worldName })` (L537-540), so Chromium creates the world in every future document, and sends `Page.createIsolatedWorld` once per frame that already exists (L513-517). No read ever calls `createIsolatedWorld`.
- **Context ids come from events.** [`_onExecutionContextCreated`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crPage.ts#L732-L745) classifies each `Runtime.executionContextCreated` as `main` (auxData.isDefault) or `utility` (name match) and calls `frame.contextCreated(world, context)`, which replaces the previous context and fails anything still racing on it ([frames.ts L1787-1806](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L1787-L1806)). `executionContextDestroyed` and `executionContextsCleared` remove contexts (crPage.ts L746-757).
- **Injected code evaluated once per context, then called by handle.** [`FrameExecutionContext.injectedScript()`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dom.ts#L95-L128) memoises one `Runtime.evaluate` of the whole injected bundle and keeps the `JSHandle`; `ExecutionContext._utilityScript()` does the same for the utility script ([javascript.ts L105-121](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/javascript.ts#L105-L121)).
- **Each evaluate is one `Runtime.callFunctionOn`** whose `functionDeclaration` is the fixed one-liner `(utilityScript, ...args) => utilityScript.evaluate(...args)`, called on the utility-script object, with the user expression and serialized arguments passed as values ([javascript.ts L256-293](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/javascript.ts#L256-L293), [crExecutionContext.ts L59-76](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crExecutionContext.ts#L59-L76)). The large bundle never crosses the wire again for that context.
- **Reset on navigation**: the old contexts are destroyed by Chromium's events; the memoised promises live on the context object, so the next context starts empty and re-injects lazily on first use.

### 3. Per action (click, fill, press)

Actionability is server-side orchestration around in-page checks:

- Locator actions enter [`Frame._retryWithProgressIfNotConnected`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L1197-L1250), which resolves the selector with backoff `[0, 20, 50, 100, 100, 500]` ms ([`retryWithProgressAndBackoff`, L1143-1151](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L1143-L1151)), then hands the element to the action.
- [`ElementHandle._retryAction`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dom.ts#L328-L378) retries on not-visible, not-in-viewport, hit-target-intercepted and missing-state, waiting `[0, 20, 100, 100, 500]` ms; pointer actions cycle scroll alignments per retry (L380-395).
- [`_performPointerAction`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dom.ts#L397-L518): one in-page `checkElementStates(['visible','enabled','stable'])`; `DOM.scrollIntoViewIfNeeded`; `DOM.getContentQuads` in parallel with a viewport-size evaluate; a hit-target interceptor installed in the page; the input; then the interceptor's verdict.
- Stability is polled **in the page with `requestAnimationFrame`**, not by protocol round trips: [`_checkElementIsStable`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/injected/src/injectedScript.ts#L712-L758) compares `getBoundingClientRect()` across frames; Chromium needs one stable frame (`rafCountForStablePosition() = 1`, crPage.ts L335-337).
- Mouse `click` sends `move`, `down`, `up` concurrently (pipelined) when there is no delay ([input.ts L263-290](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/input.ts#L263-L290)).
- After the input, [`waitForSignalsCreatedBy`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L192-L205) sends `Page.enable` as a barrier (`inputActionEpilogue`, crPage.ts L358-360) and waits for navigations the action started.
- The injected script lives in `packages/injected/src/injectedScript.ts`, bundled into `generated/injectedScriptSource` and evaluated once per context (section 2).

Round trips for `locator.click()` on a main-frame element, happy path, Chromium (counted from the code, not measured): selector resolve and two reads of its result (3), `checkElementStates` (1), `DOM.scrollIntoViewIfNeeded` (1), `DOM.getContentQuads` and the viewport evaluate in parallel (2), hit-target interceptor set-up (1), three pipelined `Input.dispatchMouseEvent` (3), `Page.enable` barrier (1), interceptor verdict (1), plus fire-and-forget `Runtime.releaseObject` for released handles (about 2). About 15-16 messages and about 10 sequential waits, plus the one-time injection on the first use in a new context.

### 4. Per navigation

- `goto` defaults to `waitUntil: 'load'` ([frames.ts L697-760](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L697-L760)): one `Page.navigate`, then it waits for the navigation event of the expected `documentId` and for the lifecycle event.
- Lifecycle state is a per-frame set filled from `Page.lifecycleEvent` (enabled once per session with `Page.setLifecycleEventsEnabled`, crPage.ts L535); `networkidle` is computed from child frames' states. On commit, [`frameCommittedNewDocumentNavigation`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/frames.ts#L234-L275) clears child frames, clears the lifecycle set and fires the internal navigation event.
- What re-runs on every navigation is done by Chromium, not by Playwright commands: registered init scripts (`Page.addScriptToEvaluateOnNewDocument`, [crPage.ts L1098-1102](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crPage.ts#L1098-L1102)), the utility world, and `Runtime.addBinding` bindings (installed once per session, L1115-1117; CDP bindings survive navigation by design). Playwright sends no per-navigation re-install command.

### 5. Per intercepted request

- The Fetch domain is enabled **only when a route exists** (or HTTP credentials are set). [`_updateProtocolRequestInterception`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/crNetworkManager.ts#L157-L178) returns early when the desired state equals the current one and otherwise sends `Fetch.enable({ patterns: [{ urlPattern: '*' }] })` or `Fetch.disable` per session, plus `Network.setCacheDisabled` (interception disables the HTTP cache). `Page.needsRequestInterception()` is "any page or context interceptor" ([page.ts L695-706](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/page.ts#L695-L706)); the page dispatcher removes its interceptor when the pattern list becomes empty, with the comment "that disables the slow-path interception in the browser itself" ([pageDispatcher.ts L209-222](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dispatchers/pageDispatcher.ts#L209-L222)).
- No route: zero per-request interception work.
- A route exists but this request does not match: every request still pauses (pattern `*`), the server runs `urlMatches` against each pattern and answers `route.continue({ isFallback: true })`, which is one `Fetch.continueRequest` ([pageDispatcher.ts L102-109](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dispatchers/pageDispatcher.ts#L102-L109)).
- Anti-pattern to avoid: regex patterns are compiled once when the patterns are set ([`deserializeURLMatch`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/isomorphic/urlMatch.ts#L166-L172)), but **glob patterns are recompiled to a `RegExp` on every match**: [`urlMatches`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/isomorphic/urlMatch.ts#L180-L197) does `new RegExp(resolveGlobToRegexPattern(...))` per call. That is per request × per pattern.

### 6. Per protocol message between client and server

- **Server side**, [`DispatcherConnection.dispatch`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/dispatchers/dispatcher.ts#L297-L395): look up the dispatcher by guid; find the generated validator by name (`type + Method + 'Params'`, a string concat and an object lookup in [`maybeFindValidator`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/protocol/src/validatorPrimitives.ts)); validate params and metadata; build `CallMetadata` (params kept by reference); run instrumentation `onBeforeCall`; call the method; validate the result with the `Result` validator; run `onAfterCall`; send. Events are validated too (`sendEvent`, L207-210).
- **The validators are also the wire conversion.** Generated `tObject` validators ([validatorPrimitives.ts L119-138](https://github.com/microsoft/playwright/blob/v1.64.1/packages/protocol/src/validatorPrimitives.ts#L119-L138)) walk the value and build a new object, converting channel references (`tChannel`) and binaries (base64 or `Buffer`) on the way. So validation and conversion are one walk, and each walk is also a copy.
- **Client side**: the channel `Proxy` validates params before sending ([channelOwner.ts L158-166](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/client/channelOwner.ts#L158-L166)) and [`Connection.dispatch`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/client/connection.ts#L235-L290) validates results and events. A full call therefore costs four validator walks (client params, server params, server result, client result) plus the metadata walk.
- **Serialization**: in-process (Node library) there is none: [`inprocess.ts` L32-49](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/inprocess.ts#L32-L49) wires the two connections directly (`setImmediate` hop). The driver used by Python/Java/.NET does one `JSON.parse` per inbound and one `JSON.stringify` per outbound message ([cli/driver.ts L37-46](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/cli/driver.ts#L37-L46)).
- Channel logging is guarded before formatting: `if (debugLogger.isEnabled('channel')) debugLogger.log(..., JSON.stringify(message))` ([connection.ts L196-200](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/client/connection.ts#L196-L200)).

### 7. Tracing and logging per unit

- **Off by default**: Playwright Test documents `trace`, `screenshot` and `video` as "Defaults to `'off'`" ([TestOptions](https://playwright.dev/docs/api/class-testoptions)); in the library, `Tracing` adds itself as an instrumentation listener only in `start` and removes itself in `stop` ([tracing.ts L229, L466](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/trace/recorder/tracing.ts#L229)). With no listener, the instrumentation `Proxy` loop over listeners does nothing for it ([instrumentation.ts L136-172](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/instrumentation.ts#L136-L172)).
- **Buffered, serialized writes**: `_appendTraceEvent` serializes the event and calls `SerializedFS.appendFile(traceFile, line, flush)`; action events flush, noisy `event`/`console`/`log` events are buffered unless in live UI mode ([tracing.ts L793-798](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/trace/recorder/tracing.ts#L793-L798)). [`SerializedFS`](https://github.com/microsoft/playwright/blob/v1.64.1/packages/utils/serializedFS.ts) keeps per-file buffers, flushes at 64 KiB (`APPEND_CHUNK_SIZE`, L40), merges queued appends, and runs all filesystem operations on one serialized queue. Each flush is `fs.promises.appendFile(path, ...)` (L161), so no file handle is held between flushes, but there is no open/close per event either. `mkdir` is done once per trace start.
- **Resources are content-addressed and written once**: `_appendResource` skips files already written and writes with `skipIfExists` (L800-806); snapshot blobs are named by SHA-1.
- **Snapshots cost**: per action, up to three phases (before, input, after), each one `Runtime.evaluate` per frame of a streamer installed once by init script ([snapshotter.ts L63-121](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/trace/recorder/snapshotter.ts#L63-L121)). Snapshots are incremental: unchanged nodes are emitted as back-references to an earlier snapshot, invalidated by a `MutationObserver` ([snapshotterInjected.ts L367-430](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/trace/recorder/snapshotterInjected.ts#L367)). Screenshots come from the screencast stream when enabled (tracing.ts L299-310, L773-790).

### 9. How Playwright guards per-unit cost

- **Leak tests run in the normal suite.** [`tests/page/page-leaks.spec.ts`](https://github.com/microsoft/playwright/blob/v1.64.1/tests/page/page-leaks.spec.ts) performs 25 clicks, fills, expects and waitFors on fresh elements, then asserts that no `JSHandle` was leaked (a test-only global map filled in `JSHandle`'s constructor, [javascript.ts L142-143](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/javascript.ts#L142)) and that page objects are garbage-collected (weak refs). It is a per-action resource contract checked by count, not by time. There is also `tests/library/events/check-listener-leaks.spec.ts`.
- **A stress suite exists but no workflow runs it**: `npm run stest` (`tests/stress/`, package.json L26); no workflow at v1.64.1 (`tests_primary.yml`, `tests_secondary.yml` and the other `tests_*.yml` checked) invokes it.
- **No latency or throughput benchmark and no performance gate** was found in the tree or the workflows. Plainly: Playwright does not benchmark per-unit cost in CI.

## Stagehand 3.7.3 (drives CDP directly through its "understudy" layer)

### 1. Per CDP command

Every command goes through [`CdpConnection.send`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/cdp.ts#L144-L178) (`packages/core/lib/v3/understudy/cdp.ts` L144-178; sessions forward to the same root, L455-500) over a WebSocket: `JSON.stringify` per send, `JSON.parse` per receive (L294-295), an `inflight` `Map` for replies.

Always-on per-command costs, even with every log sink off:

- `new Error().stack?.split("\n").slice(1, 4).join("\n")` on every send (L147, L455): a stack capture and string split per command, stored in the inflight record.
- A flow event per command: `FlowLogger.resolveContext` clones the current `AsyncLocalStorage` context, and [`logCdpEvent`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/flowlogger/FlowLogger.ts#L267-L294) builds a `FlowEvent` and emits it on the session bus, skipping only `*.enable` commands and a list of noisy events. Responses and unsolicited events are logged under the latest call (cdp.ts L319-345, L400-441).
- The bus feeds an [`EventStore`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/flowlogger/EventStore.ts#L120-L150) that always keeps a 500-event in-memory window (`DEFAULT_IN_MEMORY_EVENT_LIMIT`, L13) and adds file sinks only when `BROWSERBASE_CONFIG_DIR` is set and a stderr sink only when `BROWSERBASE_FLOW_LOGS=1` (L14-15; v3.ts L462-477). File sinks open **one** append `WriteStream` lazily and keep it ([EventSink.ts L82-90](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/flowlogger/EventSink.ts#L82-L90)).

So Stagehand's protocol logging is "on, in memory" by default: the formatting into files is off, but the per-command event is not.

### 2. Per page read / evaluate

- Main-world context ids are cached per (session, frame) from `Runtime.executionContextCreated`/`Destroyed`/`Cleared` in [`ExecutionContextRegistry`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/executionContextRegistry.ts#L14-L60); a cache miss sends `Runtime.enable` and waits up to 800 ms for the event (L52-95).
- The isolated world is **not** cached: [`resolveCss`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/selectorResolver.ts#L119-L175) and `countCss` (L239-250) call `Page.createIsolatedWorld({ worldName: "v3-world" })` on every resolution. Per the Chromium fact above this returns the same context each time, so it costs one round trip per read, not a new context. This is the same pattern as Collie's C2 today.
- Injected code: each call sends `(() => { <bootstrap>; return globalThis.__stagehandLocatorScripts.<fn>(...) })()` as a `Runtime.evaluate` expression ([`buildLocatorInvocation`, L111-117](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/selectorResolver.ts#L111-L117)). The bootstrap is generated as `if (!globalThis.__stagehandLocatorScripts) { <whole bundle>; globalThis.__stagehandLocatorScripts = factory; }` ([build-dom-scripts.ts L166](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/scripts/build-dom-scripts.ts#L166)). So the bundle runs once per world per document, but its full source is sent and parsed on every call. Same shape as Collie's C3 today, with an execution guard Collie may lack.
- A shadow-DOM "piercer" is registered once per target with `Page.addScriptToEvaluateOnNewDocument({ runImmediately: true })` before the target resumes (context.ts L945-955; [piercer.ts](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/piercer.ts)).

### 3. Per action

[`Locator.click`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/locator.ts#L385-L447) has **no actionability checks and no retry**: `resolveNode` (`Runtime.enable`, `DOM.enable`, `Page.createIsolatedWorld`, `Runtime.evaluate` with the bootstrap, `DOM.requestNode`; L923-942 and selectorResolver L367-383), then `DOM.scrollIntoViewIfNeeded`, `DOM.getBoxModel`, three `Input.dispatchMouseEvent` sent together ("pipelined burst"), and `Runtime.releaseObject`. Counted from the code: 10 messages, about 8 sequential waits. Waiting is the caller's job (and `act()`'s DOM/network quiet wait, section 8). The 2026-10-07 follow-up already noted that a prior explicit wait does not replace a per-action retry.

### 4. Per navigation

`page.goto` defaults to `waitUntil: "domcontentloaded"` (page.ts L1190-1194, Playwright defaults to `load`) and uses a [`LifecycleWatcher`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/lifecycleWatcher.ts) over `Page.lifecycleEvent`; `networkidle` is computed by the network manager with an idle window (L226-240). Init scripts, the piercer, auto-attach and domain-policy `Fetch.enable` are all queued once per target before `Runtime.runIfWaitingForDebugger` (context.ts L885-955); nothing is re-sent per navigation.

### 5. Per intercepted request

Stagehand v3 exposes no general route API; its interception is the domain policy. `Fetch.enable` is sent only when a domain policy is configured, and the **block-list patterns are pushed into `Fetch.enable` itself** ([`toBlocklistFetchPatterns`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/domainPolicy.ts#L155-L176)), so the browser pauses only requests to listed hosts; an allow-list must pause all HTTP(S) requests (L178-182). Per paused request: one host decision, then `Fetch.continueRequest` or `Fetch.failRequest`; a blocked request also produces one `v3Logger` line at level 2 ([context.ts L559-597](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/context.ts#L559-L597)), routed to the instance logger; whether level-2 lines are dropped at the default `verbose: 1` was not traced to the line (**unverified**).

### 6. Per protocol message between client and server

In 3.7.3 the SDK runs in-process; there is no per-command client/server protocol. The optional `server-v3` API server is Fastify with Zod schemas compiled as both request validator and response serializer (`setValidatorCompiler`/`setSerializerCompiler`, [server.ts L151-152](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/server-v3/src/server.ts#L151-L152); route schemas such as [`act.ts` L85-92](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/server-v3/src/routes/v1/sessions/_id/act.ts#L85-L92)). The unit there is a coarse operation (act, extract, navigate), not a CDP command. v4's JSON-RPC-over-CDP is covered by the 2026-10-07 notes.

### 7. Tracing / logging per unit

See section 1: in-memory flow events always, file and stderr sinks opt-in by environment, each file sink one long-lived stream. No trace recorder comparable to Playwright's in v3 core.

### 8. Per `act` / `extract` / `observe`

- **`act(instruction)`** ([actHandler.ts L137-250](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/handlers/actHandler.ts#L137-L250)): wait for DOM and network quiet; one hybrid snapshot; one LLM call; the action. If the model marks the step `twoStep`, a second snapshot, a tree diff and a second LLM call. On failure with `selfHeal`, another snapshot and LLM call (L333-380).
- **`observe`**: one snapshot, one LLM call ([inference.ts L342](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/inference.ts#L342)).
- **`extract`**: one snapshot, two LLM calls (extraction, then metadata; inference.ts L110 and L176), consistent with what the 2026-10-07 follow-up found in 4.1.0.
- **Snapshot cost** ([`captureHybridSnapshot`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/a11y/snapshot/capture.ts#L59)): per CDP session (one per out-of-process frame), one `DOM.getDocument({ depth: -1, pierce })` turned into an XPath index ([`buildSessionDomIndex`](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/a11y/snapshot/domTree.ts#L257), with depth fallback when CBOR limits are hit, L138-170); per frame, one `Accessibility.getFullAXTree` ([a11yTree.ts L18-42](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/understudy/a11y/snapshot/a11yTree.ts#L18-L42)). The index is cached within one capture (the `Map` is built per call, capture.ts L314-330), not across calls.
- **Action cache** (v3, local): enabled only with `cacheDir`; key = SHA-256 of `{instruction, normalized URL, sorted variable keys}` ([ActCache.ts L45-69, L188-199](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/packages/core/lib/v3/cache/ActCache.ts#L188-L199)); one JSON file per key read on lookup and written on store. The key does not include page content.
- **Built once per page/target**: the piercer init script, auto-attach, the context-id registry listeners. Not built once: the isolated world handle, the locator bundle handle, the DOM index.

### 9. How Stagehand guards per-unit cost

CI runs model evals per category with three trials and **fails below an 80 % Braintrust score** ([ci.yml L25-29, L799-809](https://github.com/browserbase/stagehand/blob/3554b02b2a9165d5d09ece58ed74ec4e11f48f5e/.github/workflows/ci.yml#L799-L809)). That gates accuracy, not cost: no latency, round-trip, token or per-command budget is checked in the workflows, and no benchmark of the understudy layer was found in the tree. Plainly: Stagehand has no per-unit cost guard.

## Puppeteer 25.16.0: patterns the other two lack

- **Logger resolved once, not checked per message.** The connection asks the logger factory for `puppeteer:protocol:SEND ►` and `RECV ◀` once in its constructor and stores `undefined` when disabled ([Connection.ts L51-73](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/cdp/Connection.ts#L51-L73), [Debug.ts L104-141](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/common/Debug.ts#L104-L141)); per message the cost is one optional call `this.#debugProtocolSend?.(...)` (L179-188, L207). Enabled with `NODE_DEBUG` in Node.
- **A timeout per CDP command.** Every command registers a `Callback` with a `setTimeout` of `protocolTimeout`, default 180 000 ms ([Connection.ts L69](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/cdp/Connection.ts#L69), [CallbackRegistry.ts L137-157](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/common/CallbackRegistry.ts#L137-L157)); like Playwright, each callback also pre-allocates a `ProtocolError` for its stack.

- **Injected utility versioned and lazy.** `ExecutionContext.puppeteerUtil` evaluates the shared injected source once per context and re-evaluates only when the global [`ScriptInjector`](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/common/ScriptInjector.ts) has been amended since (an "updated" flag), so new helpers can be appended without re-sending to contexts that are current ([ExecutionContext.ts L225-250](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/cdp/ExecutionContext.ts#L225-L250)). Arguments that need the utility are `LazyArg`s resolved only when used (L444-495).
- Fetch is toggled only on state change, like Playwright ([NetworkManager.ts L172-176, L355-357](https://github.com/puppeteer/puppeteer/blob/puppeteer-v25.16.0/packages/puppeteer-core/src/cdp/NetworkManager.ts#L172)).
- Puppeteer's tests and CI were not examined for perf gates.

## Cross-project synthesis

1. **One connection seam owns every command, and logging is decided before any formatting.** Playwright checks `isEnabled('protocol')` before `JSON.stringify`; Puppeteer resolves its logger to `undefined` once; neither touches the filesystem per command, and when file logging is on both write to one stream opened once. Stagehand disagrees: it always builds an in-memory flow event per command (500-event window) and adds file sinks by environment, each one stream opened once. No project opens, writes and closes a file per command.
2. **Every command pays a small fixed bookkeeping cost by design.** All three allocate an `Error` per command so failures carry the caller's stack (Playwright `ProtocolError`, Puppeteer `Callback`, Stagehand `new Error().stack` with string split); Puppeteer adds a timer per command. These are the accepted floor; they are named in the code, which makes them auditable.
3. **The utility world is registered once and discovered through events, never re-created per read.** Playwright and Puppeteer register `addScriptToEvaluateOnNewDocument(worldName)` once per session so Chromium creates the world in each new document, call `createIsolatedWorld` once for frames that already exist, and keep the context id from `Runtime.executionContextCreated`, replacing it when Chromium destroys it. Stagehand v3 disagrees: it calls `createIsolatedWorld` on every resolve, which Chromium answers with the same context, so the cost is a round trip.
4. **Injected code is evaluated once per execution context and then called by handle.** Playwright (injected and utility scripts, memoised promise per context) and Puppeteer (`PuppeteerUtil`, re-injected only when the source changed) send the bundle once per context; each later call is one `Runtime.callFunctionOn` with a small fixed declaration. Stagehand guards execution with a global flag but still sends the whole bundle in every expression.
5. **Actionability is one in-page call that polls with `requestAnimationFrame`, wrapped in a server-side retry ladder.** Playwright: one `checkElementStates` call per attempt, retries at 0/20/100/100/500 ms, selector polling at 0/20/50/100/100/500 ms, cycled scroll alignments, a hit-target interceptor. Stagehand v3 has none of this. Both pipeline the mouse events of a click.
6. **Interception is off until a rule exists, and toggled only on state change.** All three. They disagree on where matching happens: Playwright and Puppeteer pause every request (`urlPattern: '*'`) and match in Node, so an unmatched request still costs a pause and a `Fetch.continueRequest`; Stagehand pushes host patterns into `Fetch.enable` so unmatched requests never pause. Playwright recompiles glob patterns into a `RegExp` on every match, a per-request compile the others avoid by not having globs or by compiling regexes once.
7. **The client/server boundary validates with generated code that also converts.** Playwright's generated validators run once per side per direction and are the channel and binary conversion, so validation is not a separate pass; in-process wiring skips JSON entirely, the driver does one parse and one stringify per message. Even so, a Playwright call walks the payload four times (each walk a copy). Stagehand's API server uses Zod as validator and serializer per coarse request.
8. **Tracing is off by default; when on, writes are buffered, content-addressed and incremental.** Playwright: per-file buffers flushed at 64 KiB or at action boundaries, one serialized write queue, resources written once by SHA-1, DOM snapshots as diffs against earlier snapshots. Stagehand: in-memory window plus opt-in streams.
9. **Per-unit cost is guarded by counts of leaked resources, not by benchmarks.** Playwright's suite asserts zero leaked `JSHandle`s and collected objects after 25 actions of each kind; its stress suite is not wired into CI. Stagehand gates model accuracy at 80 %. Neither has a latency, round-trip or throughput gate. A Collie benchmark per path would go beyond what these projects do.
