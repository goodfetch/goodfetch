# How crawlers keep their frontier and crawl state

Date: 2026-11-06. Read-only research. Covers where each crawler keeps its seen set, queue and per-URL status, when it writes it and what a crash loses. Every claim comes from current official docs or source at the stated version or commit; anything unverified is marked **unverified**.

Versions read: Scrapy master `b1849344da` (latest release 2.19.0) and queuelib master `db508ea50b`; Crawlee JS v3.18.2 (`master` is v4.0.0-rc.1, restructured); Heritrix3 master `0d1eae1082` (latest release 3.18.0); Apache Nutch master `2f6c28bcbf` (1.x line, latest release 1.23); Apache StormCrawler 3.7.0; Colly v2.2.0 and gocolly/redisstorage master; spider 2.53.9 (local registry source); Firecrawl main `48a3f1bff7` (latest release v2.11.0).

## The common pattern

1. **The working set lives in memory; disk is a log or a snapshot behind it.** No crawler makes the hot path wait on durable per-URL writes. The seen set is always a memory structure first (a Python set, a Go map, an LRU cache, a `HashSet`, BDB's cache), and the disk copy is appended or synced later.
2. **The cheap per-URL write is an append, and the structural write happens rarely.** Scrapy appends each fingerprint and request but saves the queue pointers at close. Heritrix journals each URL event but syncs BDB only at a checkpoint. Nutch rewrites the whole CrawlDb once per cycle. StormCrawler bulks 500 writes or 5 s. Only Crawlee writes one file per request, and even it neither fsyncs nor waits for background batches.
3. **No one fsyncs per URL.** None of the code read calls `fsync` on the per-URL path, so the OS cache can lose a crash's last writes everywhere.
4. **Recovery is replay plus dedupe, not exact restore.** Heritrix replays a journal into an approximate frontier. Nutch and StormCrawler re-select URLs whose status never advanced. Firecrawl's reaper requeues stalled jobs. Scrapy needs a clean stop. All of them accept at-least-once fetching of the last few URLs.
5. **The opposite failure is "marked seen before it is done".** When the seen mark lands before the fetch and there is no status to roll back, a crash silently drops in-flight URLs. Colly does this: it marks a URL visited before the request and pops it from Redis before processing. Firecrawl's `lockURL` code has explicit rollback for its own error path (`crawl-redis.ts:798-856`). Status-based designs (Nutch, StormCrawler, NuQ) avoid it by keeping "selected" separate from "done".
6. **Durable resume is opt-in or a separate tier.** Scrapy needs `JOBDIR`, Crawlee keeps storage only with `purgeOnStart: false`, and Heritrix needs checkpoints configured. Spider and default Colly have no resume. Distributed crawlers (Nutch, StormCrawler, Firecrawl) get durability by putting status in an external store (HDFS, OpenSearch, PostgreSQL).
